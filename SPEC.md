# Sphyrna (Loom) Product & Behavioral Specification (`SPEC.md`)

**Updated:** 25 October 2026 · **Target Release:** **Sphyrna 1.6.2** (1.6.1 is promoted and 1.6.0 is installed; [D-77](DECISIONS.md), [D-83](DECISIONS.md), [D-93](DECISIONS.md))

This document is the single authoritative specification of what Sphyrna (internal code name **Loom**) must provide: its product guarantees, process ownership boundaries, session lifecycle, deletion and retention contract, Studio shell, Native Chat face, Pinned Request Cards, Inspector review & aside surfaces, Cross-Session Channel, Remora assistant, macOS system integration, and resource/context budgets.
- Visual tokens, colours, typography, and geometry live in [`design/DESIGN.md`](design/DESIGN.md) and [`design/reference.html`](design/reference.html).
- Code targets, runtime actors, UI surface-to-code mappings, and technical gotchas live in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## 1. Identity, Founding Goals & Core Experience

### 1.1 Three Founding Goals ([D-83](DECISIONS.md))
1. **Light:** RAM, CPU, disk, and energy never tire the user, while every capability remains intact. Abandoned or ended sessions must never accumulate live processes, terminal buffers, or background polling.
2. **Sessions, not harnesses:** Sphyrna is the central place that manages every session regardless of its underlying harness, so work can pass between Claude and Codex, and sessions can discover (`"$SPHYRNA_CLI" sessions`), identify (`"$SPHYRNA_CLI" whoami`) or request opening (`"$SPHYRNA_CLI" open`) other sessions under the user's authority.
3. **Cost out of sight:** Subscription quota and context cost stay invisible. Nothing enters a session's context beyond the project's own instructions except the ≤ 300-character Sphyrna plugin skill description (and `sphyrna:Ask` output style when in Ask mode).

### 1.2 Core Experience & Scope ([D-01](DECISIONS.md), [D-57](DECISIONS.md), [D-69](DECISIONS.md), [D-77](DECISIONS.md), [D-83](DECISIONS.md))
- **Core experience contract:** *The live session is always the user's own unmodified Claude Code CLI in a process Sphyrna owns, in its terminal or in its structured mode, with one owner at a time. One app-wide switch in Settings chooses which; the terminal is always one of the choices. Codex runs in its terminal.*
- **Since 1.7.0, terminal-first ([D-100](DECISIONS.md), [RESCUE-PLAN](plans/archive/RESCUE-PLAN.md)):** the Chat face is frozen (`ChatFreeze.isFrozen`). Every Claude start, resume and approved opening runs in the real terminal; a stopped session shows its kept screen or record, never a chat; the "Sessions run in" switch is hidden and a stored Chat reads as Terminal. Sections §6.1 (the switch), §7 and §8.1, §8.3, §8.5, §8.6 describe the frozen code, which stays in the tree with its tests but is unreachable in the product. No surface draws the art ([D-102](DECISIONS.md)); Remora is unchanged.
- **Platform:** Native macOS 27 and later (`Swift 6`, `SwiftUI` + `AppKit`, vendored `SwiftTerm` with local patches, `SQLite` catalog).
- **Name & bundle identity (`D-77`, `D-83`):** User-facing app name is **Sphyrna**; assistant name is **Remora**. To preserve macOS TCC permissions and user data, the production bundle ID remains `local.loom.desktop` (`~/Library/Application Support/Loom`, sockets in `~/.loom`), and the development bundle ID remains `local.loom.desktop.dev` (`~/Library/Application Support/Loom-Dev`, sockets in `~/.loom-dev`).
- **Harnesses in 1.6.0 (`D-08`, `D-28`, `D-69 (5)`):** Claude Code is active in both faces. Codex code remains in the tree and its UI entries stay visible on first-run Home and in new-session model menus (`"Codex comes in a later version"`), but Codex is **non-startable** in the production build (`BuildIdentity.startableProviders = [.claude]`).
- **Harnesses in 1.6.2 (`D-94`, as built):** the freeze is over, and Codex is given its app-wide infrastructure; starting and resuming its sessions still wait for 1.7.0 (`D-93`).
  - **One capability table.** `HarnessCapabilities` says what a harness may do (§6.7). Every gate asks the table, never `provider == .claude`; a source guard fails a comparison with `.claude` outside the few dispatch files.
  - **Read and connected:** a short supervised probe reads Codex's account, limits, tokens and models, and the connect switch decides which harnesses Sphyrna offers (§2.1, §6.7). Codex's models fill the composer's popover, its limits and tokens fill Usage, and Settings → Connections shows its health.
  - A harness's CLI version is still never pinned (see `Unpinned provider CLIs` below): the version table of §6.7 only says whether to suggest an update.
- **Codex in1.8.0 (D1/D2):** production start/resume is enabled after native acceptance. A new terminal session uses its explicit model/effort and supported read-only or workspace-write/on-request mode; the native user reviewer and no added network/roots are preserved. Resume adopts the exact native session's reported model/effort/permissions without injecting an input or a settings override. Recorded bounded text/context/usage/changes reads are separate from Chat and deletion capabilities.
- **Unpinned provider CLIs:** Claude and Codex CLI versions are never pinned on the user's behalf. Capability flags (`--help`, `--version`, `system/init`) are probed and refreshed when the executable stamp changes; unsupported features degrade explicitly without false success reports.
- **Truthful outcomes:** The words *started*, *stopped*, *delivered*, and *deleted* always describe verified outcomes. User-facing text always says **"session"**, never **"conversation"** (`scripts/check-user-wording.sh`).

## 2. Process Ownership, Run Scopes & App Quit

### 2.1 Exclusive Run Scope Guarantee ([D-05](DECISIONS.md))
- **Why application coalitions are insufficient:** Apple XPC services join the main app's coalition dynamically, and `KERN_PROCARGS2` environment markers are unreadable on Apple platform binaries (e.g. `/bin/sleep`) and can be escaped via `setsid` / double-fork before a snapshot.
- **Per-run `LoomRunHost` coalition:** Every managed run (`SPAWN_PTY` for terminal or `SPAWN_STDIO` for pipe/Chat/Remora) is spawned by a dedicated instance of the bundled AppKit-less helper `Contents/Helpers/LoomRunHost.app` launched via LaunchServices (`open -n -g -j`). Each launch receives a new, exclusive XNU resource coalition inherited across `fork`/`exec`/`setsid`/double-fork.
- **Distinguishing forked children from `launchd` XPC members:** `p_orig_ppidversion` in the kernel process table preserves the parent at `fork` time even after `exec` and reparenting to `launchd`, allowing Sphyrna and `LoomRunHost` to target only forked descendants while never signalling `launchd`-spawned XPC services.
- **Refusal on broken scope:** Coalition and lineage data are read via `proc_pidinfo`. If a run scope cannot be established or verified, the session is **not** started and an explicit error banner is shown.
- **Out of scope by construction:** Work handed off to external daemons via LaunchServices or `launchd` (`open -a`, `launchctl`, `brew services`, Docker daemon jobs), or processes that switched to another UID (reported as a stop failure if they cannot be terminated).
- **Codex server scope (`D-05`):** When Codex is active, each live Codex session runs its own `codex app-server` inside the same run scope as its TUI so stopping the session stops its server (`0` cached server state left behind).
- **Codex probe scope (`D-94`, 1.6.2):** Reading Codex's account, limits, tokens and models starts one short `codex app-server` in its own run scope, with a folder of Sphyrna's own as its working directory (`<data root>/harness-probe`, never a project and never home), and stops it again, never a thread or a turn (it initializes, then sends `account/read`, `account/rateLimits/read`, `account/usage/read` and `model/list`, and nothing else). The whole ask is bounded to about `10 s`; on an answer, a failure, a timeout or a cancelled caller the server and its scope are stopped and its socket file removed, and a stop that cannot be verified is logged and the scope kept. The account it names (the email included) lives in memory only: it is never stored, logged or journaled.

### 2.2 Stop, Window Close, Normal Quit & Crash Recovery ([D-03](DECISIONS.md), [D-45](DECISIONS.md))
- **Window close (`Cmd+W` or red close button):** Closes the window only; the app and all running sessions continue running (`applicationShouldTerminateAfterLastWindowClosed` is `false`).
- **Session Stop (`Cmd+.` or header Stop square):**
  - Blocks new input (`TerminalInputGate`), runs the graceful leave sequence (in Chat: sends `interrupt`, waits up to 2 s for `result`, closes stdin, waits for exit), freezes forked coalition members, re-verifies identities (`loom_signal_if_matches`), escalates (`SIGHUP` → `SIGTERM` → `SIGKILL` for PTY; `SIGTERM` → `SIGKILL` for pipe), and verifies that the run scope is completely empty before reporting stopped.
  - Verified Stop closes the stopped session's tab unless the user navigated elsewhere while Stop was verifying.
- **Normal Quit (`Cmd+Q`):**
  - **Acceptance criterion:** Zero running processes started and owned by Sphyrna remain; external user terminal sessions are untouched.
  - **Confirmation (`D-45`):** When user-initiated and any session is Working, Waiting for approval, or Ready with background shells or crons its turn left running (`D-103`), Quit shows a confirmation alert with `Cancel` as the filled default (`Return`). System logout, restart, and shutdown (`keyAEQuitReason`) skip confirmation so Sphyrna never blocks macOS shutdown.
  - **Unverified stop alert:** If any scope cannot be verified empty on a user-initiated Quit, Sphyrna presents a 3-button vertical alert (`Try Again` default, `Keep Sphyrna Open`, and destructive `Quit Anyway`).
- **Loom crash / Force Quit (`D-05`, `O-09`):** If the control socket between Sphyrna and `LoomRunHost` breaks without an orderly `EXIT` frame, `LoomRunHost` immediately stops all forked processes in its coalition and exits. On next launch, `PreviousRunRecovery` and `StaleSocketSweep` clean up any abandoned run scopes and sockets and surface interrupted sessions in Home's `Continue` card.

## 3. Managed CLI Environment & Session Integration

- **Clean login-shell environment inheritance (`DP-CP4-8`):** Managed CLIs inherit the user's login shell environment (`.zshrc`, `PATH`, SSH agent, proxy, user env vars) captured once at app launch from an initial environment stripped of parent `CLAUDE_CODE_*` variables (preventing session ID, socket, or token leaks if Sphyrna itself was launched from a terminal). Shell startup warnings/errors do not block session start and are surfaced as non-fatal notices; if the environment cannot be resolved at all, a retryable error is shown.
- **Harness-neutral launch choices (1.8.0 C4):** drafts, presets and approved openings carry a harness, model, effort and product mode. Descriptors define only verified modes; a narrow Claude bridge preserves the existing runtime flags. No first-message launch is enabled for another harness before its engine slice (Codex: D1).
- **Claude Agent View disabled:** Sphyrna sets `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` on managed Claude sessions so all subagents stay inside the managed session boundary.
- **Session-specific Claude hooks & settings (`--settings`, `--plugin-dir`):**
  - New sessions pass `--session-id <uuid>`; resumed sessions pass `--resume <id>`.
  - **A session's title at start (FB6-16 part 1):** a new session that starts with a title (an approved `"$SPHYRNA_CLI" open --title`, an approved task) passes it as `-n <title>` (Claude's `--name`) in every face, so Claude's own `/resume` list names it as Sphyrna does. A draft carries no title, so Claude names that session itself; a resume passes no name; a later rename stays Sphyrna's only. Codex takes no name at launch (its only way is the app-server's `thread/name/set` once the thread exists), so a Codex session's title stays Sphyrna's in 1.8.0.
  - Every spawn passes `--model`, `--effort`, and `--permission-mode` explicitly from the session's catalog record so neither face loses the user's choices across Resume or handover (`ClaudeDefaultModel` omits `--model` on resume only when the transcript model matches the user's configured default without `[1m]`, preserving 1M context windows).
  - `--settings` injects session-only hooks (`loom-hook` over an authenticated `0600` Unix socket `LOOM_HOOK_SOCKET`) and `crossSessionInbound: refuse` (blocking unauthorized inbound cross-session messages without disabling the `SendMessage` tool needed by subagents). The user's global `~/.claude/settings.json` is never modified.
  - `/clear` in Claude (and `/new` in Codex) creates a new session card for the cleared conversation while preserving the old session card and its transcript.

## 4. Session Lifecycle & State Model

### 4.1 Lifecycle States vs. Momentary Agent Work States
Lifecycle state (`active`, `idle`, `stale`, `deleted`) and momentary agent work state are strictly orthogonal:

| Lifecycle State | Meaning | Resource Expectation |
| --- | --- | --- |
| **`active`** | Running session (terminal or pipe run alive). Need not be selected on screen. | Managed CLI, run scope, and bounded output buffers exist. |
| **`idle`** | Stopped session that is not stale; can be resumed in the same session at any time. | **Zero live processes or PTYs.** Terminal face keeps only a static `TerminalScreenSnapshot` (≤ 400 rows / 1 MiB, `D-54`). |
| **`stale`** | Stopped session unused (no prompt and no deliberate user view) for **15 days**. | Zero live processes. Viewing a stale session does **not** clear `stale` or start a process; only explicit `"Reactivate and Resume"` reactivates it. |
| **`deleted`** | Session whose permanent deletion contract (§5) has completed and been verified. | Catalog row, caches, and claimable local provider files are gone. |

- **No automatic idle stop (`D-38`):** Running sessions are **never** stopped automatically after 60 minutes of inactivity; they run until the user stops them or quits.
- **Refreshing usage time:** Sending a prompt or deliberately selecting/viewing a non-stale session refreshes its usage timestamp and delays `stale`. Background list refreshes, usage scans, or hook events do not count as user viewing.

### 4.2 Status Derivation Priority & Signals
Every status surface (sidebar row, activity card, tab, header state pill, Home, palette, menu bar) derives a single status from `SessionIndicator` in this priority order:
1. **`stopUnverified` / `failed` / `problem`** (Failure dot `#F2615C` / `#C8322C`, or `7 pt` diamond under macOS `"Differentiate without color"`, `D-69 (11)`).
2. **`identityUnclear`** (Hollow attention ring).
3. **`waitingForApproval` / `waitingForInput`** (`"Needs approval"` / `"Waiting for you"`, `7 pt` attention dot `#FF9E0A` / `#C46A00`; includes pending agent `"$SPHYRNA_CLI" open` requests).
4. **`working`** (`12 fps` 10-frame `BrailleSpinner` `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏`). Working means a turn is running: `UserPromptSubmit` to `Stop`, an automatic turn, or the registry's `busy` (which covers background subagents). A finished turn whose `Stop` lists background shells, crons or subagents reads `ready` (`finished` while unviewed), with `"N background"` beside the state — the header pill (`StatePillStyle`'s suffix), the Active card's reason line and the Overview (`D-103`). The count (`BackgroundWork.total`) still holds Quit's confirmation and the automatic idle-stop blockers.
5. **`unviewedCompletion`** (`"Finished"`, `7 pt` unviewed blue dot `#5C8CFF` / `#2557CC`; cleared by viewing the session or clicking `"Mark as Read"`, `D-39`).
6. **`ready` / `idle` / `stale` / `ended`** (No mark in lists/tabs; `ended` shows no header state pill; `stale` dims the title to secondary).
- **Hook watchdog:** If the Claude session registry marks a session `"busy"` with zero hook events for `3 s` (`hookSilenceGrace`), Sphyrna raises a `hookSilenceIssue` notice and journals `hook_silence` until a hook arrives.

## 5. Permanent Deletion & Session Retention (`Settings → Sessions`)

### 5.1 Seven-Step Permanent Deletion Contract ([D-26](DECISIONS.md), [D-37](DECISIONS.md))
Deletion is an end-to-end state machine persisted in the `deletions` table (`requested` → `stopping` → `provider_data` → `catalog` → `verifying`) so an interrupted deletion resumes at next launch:
1. Close input gates and refuse new messages, starts, or resumes.
2. Cancel pending jobs, handovers, and queued deliveries bound to the session (and first delete any child side chats through the same verified path).
3. Stop owned live processes and verify the run scope is empty.
4. Remove claimable local Claude files for all provider session IDs of the session using the **CP4-A allowlist** (`ClaudeDataInventory`, descriptor-relative with `O_NOFOLLOW`, same-device `st_dev`, never following symlinks):
   - `<profile>/projects/<folder>/<id>.jsonl` (transcript), `<id>.orphaned-*.jsonl`, `<id>.jsonl.superseded-*`, and `<id>/` (conversation folder including subagents);
   - `<profile>/file-history/<id>`, `session-env/<id>`, `debug/<id>*`, `tasks/<id>`, `image-cache/<id>`, `uploads/<id>`, `todos/<id>-agent-*.json`;
   - Tier-2 temporary output directory matching `<id>`.

   For a **Codex** session (D2, D-121) Sphyrna removes no Codex file itself. The deletion records the session's Codex home (the one its runs used, symlinks resolved; never a reconstructed default) and starts an app-server of its own for this step: its own unix socket and run scope, that home, `--disable daemon_auto_start --disable memories --disable multi_agent`, never the default daemon. A native id with spawned native sessions that are not part of the deletion (`thread/list` by `ancestorThreadId`) is refused before the record is written and again before the delete, because Codex's `thread/delete` removes the whole spawn subtree. `thread/delete` runs for each native id; the step ends only when `thread/read` answers that the id is unknown (0.164: `thread not loaded: <id>`; an existing unloaded thread still reads), no rollout carries the id (`sessions/` and `archived_sessions/`, plain or `.zst`, and the transcript reader's locator) and `session_index.jsonl` has no record whose parsed top-level `id` is it. A retry meets Codex's exact "no such thread" answer (`no rollout found for thread id <id>`) after a delete that already succeeded and continues only once the absence is shown; any other Codex error leaves the step failed. The server is stopped and its scope shown empty before the step returns.
5. Delete catalog rows (`DELETE` with `PRAGMA secure_delete = ON` + `wal_checkpoint(TRUNCATE)` so zero bytes of deleted titles remain in `catalog.sqlite3` or `-wal`), purge **all** catalog backups and `.damaged` copies before taking a fresh backup, and fence the deleted provider IDs in `ProcessSupervisor`.
6. Run all registered `ConversationForgetting` hooks (`ChatSessionHost` queues/drafts/rewinds, `ClaudeUsageIndex`, `RemoraMemoryForgetter` stripping cited lines from day/week journals, project notes, and `day-brief.json`, plus in-flight call fences), drop the session's state in its harness adapter, and verify that `ClaudeDataDeleter.verify` finds zero remaining claimable files (for Codex: no rollout or index record of its native ids; anything back is deleted natively again and checked once more).
7. Report deletion complete only after verification succeeds.

- **Shared data & explicit boundaries:** Shared `~/.claude/history.jsonl` and Codex's `<codex_home>/history.jsonl` are **never** rewritten (concurrent CLI appends could be lost; Codex's writers give up after about a second of lock contention and a rewrite is not crash-atomic), and Codex's zero-byte `tui-thread-reference-capabilities/<id>` marker is left too; a Codex preview names both as kept and `CLAUDE_CODE_SKIP_PROMPT_HISTORY` is **never** set (it disables transcript writing and breaks `--resume`). Project source code, git worktrees, and remote provider copies are never deleted by session deletion.
- **`"Remove from Sphyrna Only"` (`DP-CP4-7`, `D-69 (10)`):** When a deletion is blocked by an unreachable folder or fails verification, the user can choose `"Remove from Loom Only"`, which stops the run and removes all Sphyrna catalog rows, caches, and Remora memory entries while leaving Claude's files on disk.

### 5.2 Retention & Cleanup Review (`Settings → Sessions`, [D-69 (10)](DECISIONS.md))
- Ships in every build; **nothing is ever deleted without user confirmation** (automatic silent deletion is off).
- **Default policy (`DP-CP4-2`):** Targets only `stale` sessions (unused ≥ 15 days) that have waited at least the **deletion wait** (default **15 days**, configurable in `Settings → Sessions`) since the later of becoming stale and last being viewed.
- **Review triggers:** A cleanup review is due **30 days** after the last review (configurable), or immediately when the app reopens after a **≥ 45-day absence** or when **> 10 eligible sessions** accumulate.
- **Protected exceptions (never selected for automatic cleanup):** Pinned sessions, sessions whose git worktree has uncommitted changes or unpushed commits (`CleanupWorktreeProtection`), and sessions involved in an unfinished authorized cross-session task.

### 5.3 Storage (`Settings → Sessions → Storage`, 1.7.0, RESCUE C1)
- Lists Sphyrna's sessions (side chats go with their parent) with each one's disk size, largest first, by project with each project's total and an overall total. A session's size is what step 4's allowlist would delete for its provider ids (one dry run, `runtime.deletionPreviews`); links count by their own size and are never followed. Measured off the main actor, only while the section shows, kept until a deletion or a refresh. The whole profile's `projects` folder is shown as context ("including sessions started outside Sphyrna").
- Checked sessions are deleted through the seven steps of §5.1, with the review's confirmation; a running session cannot be checked and is refused again by the coordinator.
- **Claude's retention:** "Claude deletes transcripts older than N days" (`cleanupPeriodDays` in the profile's `settings.json`, 30 when absent). Change… asks for confirmation, then writes that one key and nothing else: in place or as the first member, atomically, keeping the file's mode and every other byte, through a link to the real file; an unreadable file, a non-object or an edit that would not parse back to the same object is refused with its reason. This is the only write Sphyrna makes to a Claude profile's settings.

## 6. Faces, Studio Shell, Sidebar & Navigation

### 6.1 App-Wide Face Switch & Handover ([D-57](DECISIONS.md), [D-69 (1)](DECISIONS.md), `R1`)

> **Frozen since 1.7.0 ([D-100](DECISIONS.md)):** the switch is hidden and every Claude session runs in the terminal; the handover below is unreachable.
- **App-wide switch:** `Settings → General → Sessions run in` chooses **`Chat`** (default) or **`Terminal`**.
- **Start & Resume (`FacePolicy`):** Starting or resuming a Claude session uses the current Settings switch. A running session keeps its current face until it stops. While the switch is `Chat`, a stopped Claude session displays its interactive Chat view (keeping its composer so sending a message resumes it in place). Codex always uses the terminal face.
- **One-way Chat → Terminal handover (`V19`, `R1`):** Per-session face switches in the header, `⋯` menu, and `/` menu are gone, and Terminal → Chat handover is removed (`R1`). Only the Chat policy banner's **`"Switch to Terminal"`** action performs a live handover: it sets Settings to `Terminal`, waits for any active turn to finish (refusing if a request card or background task waits), stops the pipe run after a point of no return (pausing any queued messages with `"Queue paused because the session moved to the terminal"`), and resumes the session in `TerminalSurface`.

### 6.2 Window Chrome & Sidebar (`V04`, [D-74](DECISIONS.md), [D-75](DECISIONS.md), [D-81](DECISIONS.md), Ink v4 B2/B3)

Explicit stored fills and 1.7.0's legacy styles preserve their existing fill and opacity. The split divider is opaque under its hairline.
- **Top:** a full-width 32 pt Search door (`⌘K` / `⌘F`) opens the palette; it does not filter inline. Home and New session are 28 pt nav rows. Home's attention badge matches the Dock count; New session (`⌘N`) opens the last-used project's empty draft, preserving drafts with text. Claude's entry/action is hidden while it is not offered by the shared availability rule (§6.7).
- **Heading:** sentence-case Projects or Activity in Small medium secondary, with the view toggle and the view's action at the trailing edge. One toggle changes the view; its accessible representation remains a two-option picker. `⌘1` and `⌘2` still select Activity and Projects.
- **Projects:** collapsible 28 pt heads, a 16 pt mark, 13 pt medium name, trailing attention mark (failure > attention > unread completion), and chevron, New Session and actions on hover. The name opens the project page and remains plain content with a button trait so it can start a drag. A live reorder starts past 4 pt: the head lifts, measured blocks slide for 150 ms (at once under Reduce Motion), and the list scrolls near its edge. Release calls `moveProject` once; Escape, loss of key status, release outside, its own place or a rejected move restores the order. Move Up/Down remain menu and accessibility actions. Branch stays in accessible metadata/tooltip when the reason takes its visual place. Cards pad10 vertically and12 horizontally, radius10; a one-line childless card is74pt. Rest has no fill, hover uses the hover fill, selection is neutral raised with the strong edge at elevation2. The whole surface includes child rows, with independent accessible card/child actions. The project tone stays on its mark and tab.
- **Status and time:** Working has a spinner, word and elapsed time; Needs you, Failed and Finished have their word and mark. Exceptional states retain precise words. Ready shows only last-activity age. Elapsed time starts when the event hub first observes this turn working or awaiting approval; it survives tool/approval updates and frame coalescing, clears at a definitive turn/run boundary, and is omitted when unknown. Only the visible working label ticks once per second in an active window with an expanded sidebar; no hidden/idle card clock runs and the card body does not tick.
- **Activity:** drafts with text, then Active (working turns, waits, unread completion/failure and the selected session held until selection changes), then day buckets. Drafts stay 28 pt italic rows without a status gap. Subagent rows stay 24 pt with still working marks, branching from the card mark's column rather than a former status column.
- **Peek:** after a pointer rests for 400 ms, one bounded off-main-actor transcript read (last 64 KiB, two pages at most, in the session's folder) gives the last ask/answer, each capped at 160 characters. A scroll or departure cancels it; at most 64 cached sessions are retained, invalidated by last activity. A harness without a transcript reader keeps the existing tooltip.
- **One bottom bar (D-110):** Settings and Help are24pt ghost icon buttons at the leading end of the single26pt window-wide status bar. The sidebar has no separate utility footer. Help opens the existing app Help menu; Settings opens the existing Settings window. The existing fullscreen bar hiding and keyboard/menu routes remain.

It hides in full screen; the palette, shared popover host and sheets cover the whole root, including the strip. Connected harnesses that report limits have a mark, a 40×4 pt meter of the tightest remaining share (orange below 20 %), and each current window's percent left and reset countdown. With no cached limits the segment says "No limits read". The leading segments scroll horizontally when needed. A click opens a 360 pt popover with pace lines, reset/read times, Check Again for only that harness and Open Usage; more than four pace lines scroll. Opening the strip/popover makes no read; the existing Usage cache and cadence supply it, and displayed values publish only when changed.

Remora appears only while reading a brief; harness update advice appears only for a known installed version below the existing recommendation/minimum. No new polling or scan is added; the working animation stops while the window is inactive or invisible.

## 7. Native Chat Face (`LoomChat`)

> **Frozen since 1.7.0 ([D-100](DECISIONS.md)):** this section describes code that stays in the tree, unreachable in the product. Model names everywhere are the full release names from the CLI's `initialize` list ("Opus 5.5").

### 7.1 Stream-JSON Protocol, Turn Model & Cold Open (`V12`, `V15`, `V16`)
- **Wire framing (`StreamJSONDecoder`):** Reads NDJSON over `SPAWN_STDIO` pipes in arbitrary chunk sizes with a `64 MiB` line limit (oversized or unknown records become visible raw/marker frames, never fatal crashes).
- **Chronological entries & turns (`TurnModel`):** User messages, assistant prose, thinking blocks, in-place tool calls (`tool_use` + `tool_result`), subagent cards (`--forward-subagent-text`), plan cards, settled request lines, and hairline markers. Every row has a stable ID (`message uuid + block index` or `tool_use_id`) so streaming deltas update only the active row. A turn runs from a user prompt to the main thread's `result` (subagent completion never ends the parent turn).
- **Cold open & paging (`TranscriptLens`):** Opens the newest **10 user turns** (capped at ~`1.5 MiB` from the tail, always cut at a human prompt or first record of an API message, never splitting a tool call from its result). Scrolling within 1 viewport of the top loads the next **20 user turns** while holding the scroll anchor. Tool outputs keep head+tail (`64 KiB`); `"Show All"` reads up to `1 MiB` / `10,000` lines from the transcript file.

### 7.2 Stream Presentation, Folding, Live Row & Scroll Latch (`V13`, `C7`)
- **User messages:** Right-aligned bubbles; collapse when `> 600` chars or `> 8` lines to `~7` lines (`"Show full message"`). Hover footer offers time, `Copy`, and (on delivered prompts at the prompt) `Rewind Files to Before This Message`.
- **Assistant prose & C7 streaming split:** While streaming, `ChatContent.streamingBlocks` splits prose into an `Equatable` settled head (`ChatSettledBlocksView`) and an open tail so `ChatRowMeasurer` measures only the open tail block.
- **Streaming interval is cost-aware (FB5-10, S2):** Streaming text is shown at most once per interval of `80 ms`. The interval stretches with the cost of the last flush: the wait is `max(80 ms, 5 × the last flush's cost)`, up to `160 ms`; one cheap flush (about `16 ms`) brings it back to `80 ms` at once. A flush deferred in the same pass as a costly rebuild is scheduled before that turn's cost is known, so the timer asks the due time again when it wakes and waits the stretched interval. Any change that is not streaming text (a new row, a tool, the end of a block, the reader's state) derives its rows at once (`ChatPresentation.streamingInterval`).
- **A streaming answer is selectable once it finishes (S1, Q16):** Text selection builds a second text layout, and each selectable text is a keyboard-focusable view that SwiftUI walks again on every flush to rebuild the key view loop. So no part of an answer that is still streaming takes selection: not the open tail, not the settled head and not an open fence's settled chunks. Every finished message is selectable. `Copy` (the source text) and the VoiceOver label are unchanged. `@user` traded selection during the stream for its cost (24 Oct).
- **The head parses only what settled; a long open fence settles in chunks (S3):** The streaming head no longer re-parses its whole text when it grows: only the newly settled piece is parsed and its blocks appended (when the head ends in a list, which a blank line can continue, the list's piece is parsed again with the new one). A three-backtick fence still open at the end **settles every 40 complete lines**: each chunk is parsed once and kept, and only the lines after it are parsed per flush, so the cost of a flush stays flat as the block grows. The chunks and the open lines are drawn as **one code block** (one card, as high as the same lines in one text); a settled block is **one view**, and its `Copy` appears when the fence closes (the header holds its place while the block streams). A fence inside a list item or a quote, and a longer fence holding shorter ones, are drawn as before. The split reads a fence in a list item as the parser does (1.6.2): it ends with the item, at a non-blank line left of the item's content column that follows a blank line or starts a block, and that line is read again outside the fence, so a fence marker at column 0 opens a top-level fence instead of closing the item's. A streamed message then shows the blocks of the finished one.
- **Work rows & group summaries:** Consecutive tools fold into a summary naming the top two categories by rank (`Rank 0:` commands, edits, agents; `Rank 1:` reads, searches, web; `Rank 2:` other; e.g. `"Changed 3 files, ran 2 commands and 4 other actions"`). `TodoWrite` is hidden from the stream and updates the `Tasks` line.
- **Success is quiet; failure is loud:** Only `is_error`, denied (`non_execution_kind`), or interrupted tools fail (`grep`/`diff` exit code 1 is not an error). Failed commands auto-expand their last 12 lines with a failure-edged box.
- **Turn fold:** When a turn settles cleanly (not live, no waiting card, not failed or interrupted), all intermediate work between the user prompt and the final answer folds into one row (`"Worked for 4m 12s · changed 5 files and ran 3 commands"`). Plan cards stay visible outside the fold. Starting a new turn closes the previous turn's manually opened fold.
- **Live row & thinking:** Fixed-ID row at the bottom of a running turn showing the current tool or `"Thinking"` / `"Compacting"` / `"Waiting for you"` + elapsed timer (persisted from send timestamp; paused when window is hidden; switches to `"No activity for 40s"` after 40 s of silence). Above it sits the 4-line italic thought summary (`--thinking-display summarized`).
- **Views (`⌃O`):** Cycles **`Normal`**, **`Thinking`** (keeps thinking blocks visible after turn), and **`Verbose`** (expands all folds and tool groups).
- **Scroll latch (`ChatScrollLatch`):** Two states—`Following` (within `40 pt` of true bottom, measured in `NSScrollView` minus composer inset) and `Free` (entered immediately on upward wheel/trackpad, scroller drag, or `Page Up`/`Home`/`↑`). Sending a message animates it to `24 pt` below the top without spacer views; `Jump to Latest` appears `150 ms` after leaving bottom and hides instantly on return.

### 7.3 Composer, Keys, Queue & Delivery (`V17`, `V24`)
- **Key bindings:**
  - `↵`: Sends message (starts turn when idle; when working, sends **`Send Now`** with `priority: "next"` so the running tool finishes without being cancelled). Never fires during IME composition (`hasMarkedText`) or key repeat.
  - `⌘↵`: Queues message in Sphyrna's **Queue** (`"After this turn"`). Text-only (refuses attachments).
  - `⇧↵` / `⌥↵`: Inserts newline.
  - `Esc`: Closes open menu or cancels queue edit first; otherwise sends **`Interrupt`** if working and no request card waits (keeps CLI process alive and pauses queue).
  - `↑` / `↓`: Recalls up to 200 earlier sent text prompts of the session when caret is on line 1 of an empty or unedited recall composer.
  - `⌘⇧V`: Pastes as plain inline text (bypassing the `≥ 32 KiB` pasted-text chip).
  - **Type-to-focus:** Typing a printable key while the stream has focus moves focus into the composer through the input method (supporting Option-typed characters).
- **Read Now:** While a `priority: "next"` message waits on a long tool step, clicking `Read Now` cancels the async message (`cancel_async_message`) and resends with `priority: "now"` (moving a running Bash command to the background).
- **Sphyrna-owned Queue (`<data root>/chat-queues/<id>.json`, max 100 items / 1 MiB):** Collapsible drawer above the composer (`Edit`, `Send Now`, `Remove`, drag or `⌥↑`/`⌥↓` reorder). Releases one item at a time when a turn settles with no waiting card. Pauses automatically on user Interrupt, failed turn, app relaunch, or Chat → Terminal handover.
- **Crash-safe drafts & delivery (`ChatDraftStore`, `command_lifecycle`):** Drafts save 300 ms after edits, on blur, on send, and on Quit. Messages sent during a running turn stay in `held` until Claude reads them (`isReplay` / `started`), returning to the composer on interrupt/crash/stop, or showing `"Not delivered · Retry · Copy"` if the process exits before `queued`.
- **`/` and `@` menus & Attachments:**
  - `/` at message start lists user-invocable skills/commands from `system/init` plus `Ask on the side` (terminal-only commands point to Settings).
  - `@` lists up to 80 files/folders (120 ms debounce; **never** walks `$HOME`, `/`, an ancestor of home, or a volume root; caps scan at 2,000 entries/folder, 20,000 total, depth 8, 0.5 s) and other sessions; picking a session inserts a **mention pill** (below).
  - Images scale to `≤ 2000 px` long side; files `> 40 MB` are refused; pastes `≥ 32 KiB` become a chip.
- **Mention pills ([D-96](DECISIONS.md), W3-a):**
  - A Claude session dragged from the sidebar, a tab or Home onto the **live Chat composer** (its field or its chip row), or picked in the `@` list, becomes a pill in the chip row (harness mark, title, remove button; VoiceOver reads `"Mentions session <title>"`). The `@` pick removes the typed `@query`.
  - Only a session the catalog lists whose harness has a transcript Sphyrna reads (`readsTranscript`; a Claude session today) can be mentioned: never the composer's own session, never a side chat, and never twice. A refused drag shows the not-allowed feedback, and a session drop never inserts the title as text. The draft page, Side and Quick Question refuse sessions.
  - **Pills persist in the draft as session IDs** (`ChatDraft.mentions`; an older draft without them loads), so they survive a session switch and a relaunch; titles are the catalog's when restored.
  - **On send** (or on enqueue while Claude works) each pill becomes the mention text (`[Another session, "<title>" · transcript <path> · its last answer began: …]`), in pill order, **before the typed words**, so the queue strip shows the message as it will be sent. A pill whose session is gone or has no transcript is left out, and the info line says so (`"One mention was skipped: …"`). A failed send puts the pills back; editing a queued message keeps them, and a pill added during the edit counts as a change, so it stays in the composer when the queue sends the item first. A mention's transcript is looked for only in the session's own folder (`ClaudeTranscriptLocator.locate(…, onlyIn:)`), never by listing every project.
- **Files and folders drop into every composer ([D-96](DECISIONS.md), W3-d):** A dropped file becomes `@path` and a folder `@folder/`, relative to the session's folder when inside it. The live Chat composer takes them as before (an image file is still an image attachment). The draft page's, Side's and Quick Question's composers send text only, so an image file is a path there. A drop **anywhere on the live stream** lands in that session's composer, and a drop **anywhere on the draft page** lands in the draft's composer; the field then takes the keyboard. Nothing is sent. The Changes tab drags a changed file out as the `@path` text, never as the file (§8.2).
- **Terminal:** A file dropped on the terminal pastes its shell-quoted path; it was done in CP5 (`O-07`'s Finder file drop, [D-21](DECISIONS.md)). **A session dropped on a terminal** (1.6.2; dragged from the sidebar, a tab or Home) pastes its transcript path, shell-quoted like a file's: only a session whose transcript Sphyrna reads, never the terminal's own session (also after `/clear`). The path is looked up off the main actor in the session's own folder; without a transcript nothing is pasted and it beeps.

## 8. Pinned Request Cards & Inspector Surfaces

### 8.1 Pinned Request Cards (`V18`, `V23`, [D-75](DECISIONS.md))

> **Frozen since 1.7.0 ([D-100](DECISIONS.md)),** with Rewind (§8.3), Quick Question (§8.5) and the Side tab (§8.6).
- **Safety invariants:**
  1. **Zero self-answers:** `ChatSessionDriver` never answers a `can_use_tool` request on its own in any mode (except policy-enforced denials in `Ask` and `SideChat`).
  2. **`1.5 s` typing guard:** A request arriving within `1.5 s` of user keystrokes in the composer stays collapsed as `"1 request waiting"` until typing pauses for `1.5 s`, focus leaves, or the message is sent—preventing a prompt meant for Claude from accidentally submitting as a denial note.
  3. **Keyboard safety:** **`↵` never approves and `Esc` never denies.** `Tab`/`Shift+Tab` moves focus to the card (starting with no button ring so an immediate `Space` presses nothing), `←`/`→` moves between buttons, and `Space` activates the focused button. While a card is open, `↵` and `⌘↵` in the composer are disabled unless the user typed text that acts as the card's note (`Deny with note`, `Answer`, or `Keep planning`).
  4. **Subagent attribution (`V23`):** Requests carrying `agent_id` display the subagent's type and description (joined from `system/task_started` or the `PermissionRequest` hook) and highlight that subagent in the sidebar tree and Inspector `Agents` tab (`"Show the request"`).
  5. **Cut-off card:** If Claude stops while a card waits, the card remains pinned with `"Claude stopped before you answered"` and `Resume`. Answered cards fold to a 1-line summary for `4 s` and leave a permanent 1-line audit record in the stream (`"Allowed once: …"`, `"Denied: …"`).
- **Three card kinds:**
  - **Tool Approvals:** Shows tool kind, 5-line scrolling mono command/diff, `description`, and `decision_reason`. Buttons: **`Allow Once`**, **`Allow for This Session`** (rewrites suggestions to `destination: "session"`, never touching settings files; omitted for commands with file redirections `>` or here-docs), **`Deny`** (uses composer text as note if non-empty), and **`⋯ → Deny and Stop`** (`interrupt: true`, pausing the queue).
  - **User Questions (`AskUserQuestion`):** Renders markdown question and options (`1–9` digit shortcuts when focused; single-select advances after `200 ms`; multi-select toggles with `Submit`; typing in composer selects `"Other"`). Cannot be dismissed without answering or stopping the turn.
  - **Plan Review (`ExitPlanMode`):** Renders plan document card in stream and a pinned decision card offering **`Approve`** with a build-mode picker (`Ask before edits` preselected, `Accept edits`, `Auto`—or `"Stays in Ask"` when in Ask mode—passed via `updatedPermissions` `setMode` so the turn continues without restarting) and **`Keep Planning`** (`deny` with composer feedback).

### 8.2 Inspector: `Overview` & `Changes` Tabs (`I2c`, `V20`, [D-78](DECISIONS.md))

- **Usage (1.7.0, RESCUE C2):** the Overview shows the session's input, cache write, cache read and output tokens for Main, Subagents and Total, and the API equivalent (`UsagePricing`; "—" when a part has no price). The split comes from the transcript path the usage index stores (`<session>/subagents/*.jsonl` is Subagents); the session's own transcripts are tailed before a read, when the tab shows and when the session leaves Working, never on a timer.

- **Inspector container (`⌥⌘B`):** Three width classes, each with a remembered width: **narrow** (`Overview` and the `Agents` list, `328 pt` by default), **side** (`Side`, `392 pt`) and **review** (`Changes` and an `Agents` transcript, `556 pt`).   - A `6 pt` handle inside the inspector's leading edge (column-resize pointer) sets the width of the class that is open. **While the pointer drags, only an accent guide line (`2 pt`) follows it**; the inspector and its content keep their width and do not re-lay out. **On release the class takes the guide's width once**, so a terminal resizes once and Chat re-measures once (D-78's rule holds).

- **`Overview` tab (`I2c`):** Five sections—`Session` (harness, model, effort, mode, CLI version, ID), `Context` (`30 pt` ring, token breakdown, session total), `Worktree` (project, branch, path, base branch), `Changes · last turn` (`+A −R` summary + up to 5 files linking to `Changes`), and `Agents · N running` (linking to `Agents`).

  2. **`Branch`:** Runs bounded git (`-c core.fsmonitor=false --no-optional-locks`, `10 s` list / `15 s` diff timeout, `1 MiB` / `2,000` line cap) against the merge-base with `origin/HEAD` / `main` / `master`.

The footer's **`Send to <harness>`** (the capability table's name: `Send to Claude`, `Send to Codex`) bundles all comments into one message; the user's click is the approval, with no further card. A Chat session (frozen) gets `path:line`, the quoted diff line and the comment per block, sent as `next` (or resuming a stopped Chat session), and the comments clear. It is stored as sent from `You, in Changes`, the one pointer line is typed only on the session's next Ready edge, and the session reads the text with `inbox`. The footer reads `Sent · waiting for <title> to be ready` while the comments stay, then `Delivered` once `inbox` read it, when exactly the sent comments go (one written meanwhile stays). The button is absent with no comments, for a stopped session (`Comments are sent while the session runs`) and for a run the runtime has not confirmed takes messages.
  - **Drag a file out (W3-e):** A changed file's row, and the open diff's header, are drag sources. A submission no recorded input explains (an edited line, input from outside the terminal's path) keeps automatic input back until a later submission is observed exactly as typed; the pending delivery retries on each Ready edge.

Codex 0.164 allows named Unix sockets only together with its managed network proxy, which Sphyrna does not open. So a Codex session in such a mode has no session channel, and every surface says `Codex's sandbox in this mode blocks Sphyrna's session channel`: Changes offers no `Send to Codex` and shows the reason as its footer note; a peer send to such a session is refused with the reason before anything is stored; the Codex discovery entry names the block and offers no channel command; the helper, when the sandbox denies its connect, prints the reason instead of a connection error. Claude sessions are unaffected.

### 9.1 Cross-harness child agents (1.8.0, D-111/D-114/D-116)
- **Managed child interaction (D-116):** the parent remains an ordinary interactive terminal; a child runs in a managed view that exposes its real progress, results and individual user-owned tool approvals. Free-form human terminal input is available after **Take Over**, which revokes the parent's pending automatic intervention before transferring control. Preserve the child's app/native identity and effective safe settings across any required verified stop/resume handover; no implicit prompt replay, parallel owner, permission broadening or general Native Chat unfreeze. A provider without a proved native execution/approval transport must remain explicitly unavailable rather than inventing successful automation.
- A parent session can delegate to a different harness/model as a separately owned child session. Bind stable parent/child app IDs separately from each round's task/run ID and provider-native session/turn IDs; a model label alone is insufficient. A second or third round retains the child session and receives a fresh round ID; a completed round's result is not overwritten.
- The parent can inspect status on demand, read bounded completed feedback and send second/third turns to the same child identity. Result delivery is deduplicated, records its source round/turn, and fences late/stale results after cancellation or deletion. Cancelling an already completed round cannot stop a later round; stopping the child is an explicit separate scope. Unknown delivery is retained for verification rather than resent blindly.
- The parent can wait for a relevant event, check on request, and interrupt/update an exact working round under its delegation authority. Retire that round and queue a fresh one for the same child at a verified safe input boundary; never type an update blindly into work or a native approval. The required example is an Opus parent assigning Gemini implementation, GPT review and opencode documentation, with later follow-ups and notifications.
- Child completion, failure or a request for parent input can notify/nudge the parent. Event-driven completion and explicit status reads avoid background polling. A provider turn consuming a result uses the explicitly authorized delegation/delivery path under §12.2; a notification is not evidence that a model already read it.
- The session-directory metadata rule remains; readable child results are a scoped, approved-task payload, not unrestricted access to unrelated session histories. F0 defines stable relationships, fresh rounds, explicit child reports/questions and typed trusted bindings. Initial delegation approval discloses the task's bounded follow-ups and parent notices (default3 child rounds and6 parent wakes for1h); renewal requires approval. Ordinary peer sends keep per-send approval. Read/status/wait/app-only notices make no model input. Provider consumption and unknown delivery retain separate durable receipts and counts. Full-access provenance and user-only native approvals remain.
- Sidebar branches and Inspector Agents show the child's name, harness mark and model, not a brief preview. Requested/reported/unknown metadata remain distinct; native legacy role/short-ID fallback is honest, and the parent's model never supplies the child's. App-owned child rows open the actual child session; native rows open their own transcript. Discovery remains tiny and launch-local; unrelated sessions do not receive a broadcast of every task's content.
- Task completion, turn completion and verified process shutdown are separate. Parent/child Stop, Quit and deletion revoke pending input/delivery authority and verify all owned run scopes before success. Resuming a child preserves its provider identity and effective safe settings.

## 10. Remora (Home Assistant, `LoomRemora`)

### 10.1 Role & Hard Boundaries ([D-64](DECISIONS.md), [D-77](DECISIONS.md), [D-80](DECISIONS.md), [D-95](DECISIONS.md))
- **Strictly read-only:** Remora reads session transcripts and catalog metadata to brief the user on `"Where you left off"`, answer questions across sessions in the question's language, cite sessions as clickable chips, and draft unsent next steps (`Put in Draft` / `Draft Brief`).
- **Never acts:** Remora **never** sends a message to a session, starts or stops a session, runs a tool or shell command, reads git directly, or answers an approval/question/plan request. `Put in Draft` places unsent text in the session's Chat composer, below any text already there, and opens the session (`§10.5`, [D-95](DECISIONS.md)); a session that runs in the terminal gets `Copy to Clipboard` instead.
- **Seven excluded places (`DESIGN §20 Left out`):** Remora never appears on (1) the Project page, (2) inside a live session (Quick Question `⌘;` and Side Chat already have the full session context), (3) on a request card, (4) in the Changes tab, (5) on failure banners, (6) in system notifications or the menu bar, or (7) in session cleanup.

### 10.2 Call Isolation, Schedule & Guardrails (`L1a`–`L3a2`)
- **Process isolation (`RemoraCall`):** One `claude -p` child per brief or question via `ProcessSupervisor.streamHelper`, in an empty working directory (`<data root>/remora/run`), with `--output-format stream-json --verbose --include-partial-messages --model <model> --effort <effort> --settings {"disableAllHooks":true} --strict-mcp-config --no-session-persistence --tools "" --setting-sources ""`, `CLAUDE_CODE_DISABLE_AGENT_VIEW=1`, and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`.
- **Defaults & deadlines:** Defaults to **Sonnet 5.5** (`sonnet`) at **low** effort (`D-64`). The model list in `Settings → Remora` is every Claude model `ModelCatalog` knows (Opus included), each with its own effort levels; a model without levels hides the effort row (FB6-22, D-103). A brief's request sets a number: two short sentences, about 35 words, only what moved, what needs the user and the next step, with the language as an instruction in the request (FB6-20). Hard deadlines: **`60 s`** for a question or a draft (Draft Brief's call is question-kind), **`120 s`** for a brief (`SIGTERM` then `SIGKILL`). At most one call in flight at a time (`RemoraHost`), whichever door started it.
- **Morning brief schedule (`RemoraSchedule`):**
  - Day boundary is **`04:00` local time**.
  - In `Automatic` mode (default), runs at most **once per day**, triggered only when Home is actually shown on screen, online, and at least one non-excluded session has moved since the last brief (`L3b Home`: `HomeRemoraCalls.homeShown` + `NetworkReach`).
  - **Plan-limit guard:** Pauses the automatic brief while the 5-hour plan window has less than **`10 %`** remaining (configurable stepper in `Settings → Remora`; questions still run with a warning line, and `Catch Me Up Anyway` is offered).
  - **Slot retention:** Once a brief call reaches the model, it consumes that day's automatic slot even if stopped or errored (unless Claude was not logged in or the process could not spawn), and the result is persisted in `<data root>/remora/day-brief.json` (`0600`) until the next `04:00` boundary.

### 10.3 Two-Part Memory & Deletion Forgetting (`L2`, `L3a2`)
1. **Working memory (`<data root>/remora/`, `0700` dirs / `0600` files):**
   - **Journal (`journal/YYYY-MM-DD.md` & `journal/YYYY-Www.md`):** Mechanical 1-line records of questions and briefs kept by day for **14 days**, then folded into ISO weekly summaries for **12 weeks**. Any line can be deleted (`×`) in the Memory sheet.
   - **Project notes (`projects/<project id>.md`):** Up to **`1.5 KiB`** (5 items of 160 characters) of dated bullet items per project, rewritten on morning briefs (FB6-23, D-103). A note holds only what stays true for about a month and beyond one session (how the project is built, tested and released; conventions and standing decisions with their reason; recurring pitfalls; where key things live), never events. It is written only for a project with at least two sessions read or one that already has a note. An item the model re-confirms takes today's date; an item not re-confirmed for 90 days leaves the share (it stays on disk until the next brief rewrites the note). Where to pick up is a per-chip `next` line of the brief, kept in `day-brief.json`. Users can `Edit` in place or `Remove` (each removal with its own Undo, `L3a3`) in the Memory sheet. Excluding a project in `Settings → Remora` deletes its note and excludes its sessions from all packs.
2. **Durable note (`Remora.md`, default `<data root>/remora/Remora.md` or user-chosen path in Obsidian vault, `≤ 8,000` bytes):**
   - Remora writes **only** under its `## Remembered` heading—either when the user clicks **`Save`** on a brief's `"Remember this?"` proposal, or **immediately with zero model call** when a question starts with `"Remember …"` / `"Hatırla …"` (without `?`), always offering `Undo`.
   - In the Memory sheet (`560 pt`), `Open in Obsidian` is shown only when `Remora.md` sits inside a folder with `.obsidian`; otherwise `Open` opens the default editor (`28635fb`).
3. **Session deletion forgetting (`RemoraMemoryForgetter`):** Deleting a session strips all lines/items citing it from day/week journals, project notes, and `day-brief.json`, and records the deleted ID in an in-flight fence so a concurrent Remora call can never write it back (`L3a2`).

### 10.4 Pack Layout, Token Budgets & Mixed Prompt Cache TTL ([D-84](DECISIONS.md), [D-85](DECISIONS.md), [D-86](DECISIONS.md))
- **Token caps & secret masking:** Question pack **`≤ 14,000` tokens**; brief pack **`≤ 30,000` tokens** (`RemoraMemoryShare` capped at `3,000` tokens: `≤ 8 KiB` stable + `≤ 6 KiB` recent journal; reads up to 8 sessions, 6 backward pages of `128 KiB`, ~`6 KiB` excerpt per session off `@MainActor`). Secrets (`sk-ant-*`, bearer tokens, API keys) and XML tags are masked/defused before packing.
- **Mixed cache TTL layout (`D-85`, `D-86`):**
  - **System prompt file (`--system-prompt-file`, `CLAUDE_CODE_PROMPT_CACHE_TTL=1h`):** Holds `RemoraRules` + `stablePrefix` (`<memory>` durable note & project notes + `<self>` + `<sessions>` directory sorted by session ID without volatile timestamps or state words).
  - **Stdin user message (`CLAUDE_CODE_MESSAGES_PROMPT_CACHE_TTL=5m`):** Holds dynamic per-call blocks (`<excerpt>`s by last activity, today's `<journal>`, `<previous>` exchange, `<activity>` state/timestamps, `<now>`, and `<question>` / `<request>` with optional 1-line language directive from `Settings → Remora → Brief language` or `NLLanguageRecognizer`).

### 10.5 Home UI & Two External Doors (`L3b`, `L3c`, [D-80](DECISIONS.md), [D-95](DECISIONS.md))
- **On Home:** Shows `"Where you left off"`, up to 3 ranked project tiles (`Put in Draft`, `Open`), further/quiet project lines, `"Remember this?"` bar, the `Ask Remora` field (`All projects` or single-project scope), 1 streamed answer with session chips + 1 folded `Earlier` line, and the `Sources` footer. Once an entry is opened, the brief folds into a single line.
- **Remora's face is Front (FB5-4):** the menu bar's hammerhead mark (`D-77`), drawn from the same path data, still, in the art colour at about `0.8`: about `64 pt` wide in the brief's `136 pt` column and `36 pt` at the start of the folded line. When a new brief starts being written (the first Home of the day, `Catch Me Up`) it fades in over `0.6 s` (at once under `Reduce Motion`); nothing ticks afterwards. The old arrival (the band's hammerhead carrying an ASCII remora across Home, `D-80`) is gone, and no frame clock runs for the face. The band's hammerhead keeps its own loop.
- **`Put in Draft` says what it does ([D-95](DECISIONS.md)):** On a tile (and on an answer's chip), where the session's Chat composer can be filled, the button reads `Put in Draft`: a click puts the line **below** whatever the composer (or the session's saved draft) holds, after a blank line, never sent, then **opens the session** and asks its composer for the keyboard. A stopped Chat session keeps the line in its saved draft. A terminal session (and a Codex session, which Sphyrna cannot open yet) gets **`Copy to Clipboard`**, with a help tag that says why; after the click it reads `Copied`. Either label goes back to normal on Home's next read or a new line (FB5-11). The button's hover shows the whole line and where it goes; the composer's own `↵` sends it, Sphyrna never does.
- **Door 1 — `⌘K` Command Palette:** When the query reads as a question, `Ask Remora` appears at the top (`All projects` default; `⇥` narrows to current project or current ended/terminal session; `↵` streams the answer inside the palette; `⌘↵` opens it on Home). "Reads as a question" is a fixed rule with no model call (`PaletteRemoraQuestion`): the text ends in `?`, `？` or `؟` or a Chinese, Japanese or Korean question ending, holds a CJK question word, has a Turkish question particle after its first word, or has three words or more and starts with an interrogative in English, German, French, Spanish, Italian, Portuguese, Dutch or Turkish; a plain search term ("login flow") stays a search. Nothing is called while typing; an excluded project is never offered as a scope; Esc, or any close of the palette, stops the call it started; `⌘↵`, once the answer has ended, hands the question to Home's field as its `Earlier` line. Busy with another call, the row says so and `↵` does nothing.
- **Door 2 — Draft Session Page:** Under the preset chips, `Draft Brief` makes one call on click and writes an unsent brief (goal, current state, next step, key files, watch-outs) into a draft of the project. The call (`draftRemoraBrief`, `L3c`) reads the project the way a question about it does, with the same cached stable prefix; it runs only with Remora on, for a project that has a session and is not excluded, and while no other Remora call runs. Usage counts it as a draft and the journal marks its line `for=draft`. The row shows the call's states (reading with Stop; drafted, with the call's time and Draft Again; drafted in a new draft; failed; stopped; busy while another call runs), and a line above the composer says where the text came from, with **Sources** and Clear (Sources sits there only, not on the row). Nothing is ever sent (`D-64`).
  - **A brief never overwrites the user's draft.** It lands in the draft `Draft Brief` was clicked in when that is empty or still holds Remora's last brief untouched (`Draft Again` replaces its own untouched brief in the same draft). When that draft holds the user's text, the brief goes into a **new draft of the same project**, which the page then shows; the user's draft keeps every word and stays listed in the sidebar, and the row says so (`"Remora drafted the brief in a new draft. Your draft keeps its text, in the sidebar. …"`). **Nothing is copied to the clipboard any more.**

## 11. macOS System Integration ([D-45](DECISIONS.md), [D-49](DECISIONS.md), [D-52](DECISIONS.md), [D-79](DECISIONS.md))

- **Dock badge:** Counts the exact set of sessions that need the user (`AttentionOrder`: failed unread, waiting for approval/input/open-request, and finished unread)—matching the sidebar `Home` badge and the menu bar's count.
- **Menu bar item (`Settings → General → Show in menu bar`, default on):** Displays the `20 pt` `Front` hammerhead mark (`D-77`) with a lower-right badge slot where the strongest status dot (failure > attention > unviewed) wins over the working mark, the braille spinner's first frame standing still (since 1.7.0: an animation in the menu bar cost WindowServer about 8 on its energy score for as long as a session worked, RESCUE-PLAN §5). Clicking opens a menu with **`Needs you`** (up to 5 rows, failures first, then `"and N more…"`), **`Working`** (up to 5 rows with static first spinner frame), `New Claude Session`, `Open Sphyrna`, `Settings…`, and `Quit Sphyrna`. When nothing is working or waiting, shows disabled `"Nothing is working or waiting."`
- **Dock menu (W3-f):** Right-clicking the Dock icon lists **`Needs you`** (the sessions with a request waiting: approvals first, then questions and plans, most recent first), then **`Working`**, at most 5 rows each (title and project), then **`New Claude Session`** (what `⌘N` does). A session row brings Sphyrna forward with that session selected. The menu is built when the Dock asks, from the menu bar's in-memory entries; nothing is read.
- **Approval notifications (`Settings → General → Notify when a session needs approval`, default on):** Fires a silent macOS notification (no sound, **no action buttons**; title = session title, body = project + reason) **only** when a session transitions into waiting for an approval, question, or plan while Sphyrna is not the active app. Clicking brings Sphyrna forward on that session; the notification is removed immediately when the session stops waiting, at quit, and at launch.
- **Long-turn notifications (`Settings → General → Notify when a long turn finishes`, opt-in, default off; [D-49](DECISIONS.md) as amended):** Posts one silent banner, `"<session title> finished"` with the project as its subtitle, **with one action, `Open`**, when a turn that ran for **at least 30 s** ends while its session is **not on screen**: Sphyrna is not the active app, or another session is shown. A turn runs while the session works, or waits for an approval in the middle of it, and ends when the session is at its prompt again (finished or ready); a turn that ends in a request waiting for the user, in a failure or in a stop posts nothing (the approval banner speaks for the first). `Open` and a click on the banner both bring Sphyrna forward on the session. Turns are followed from the menu bar's changes with no timer, also while the switch is off, so turning it on mid-turn counts the whole turn. macOS asks for permission once. This is the one banner with a button; the approval banner stays button-free.
- **Keep Mac awake (`Settings → General → Keep Mac awake`, `Off` default or `While a session works`):** With the second, Sphyrna holds one IOKit power assertion against **idle system sleep** (`kIOPMAssertionTypePreventUserIdleSystemSleep`; **never display sleep**, so the screen still sleeps) for as long as any session works (the menu bar summary's working count is above 0), and releases it when none works, when the setting goes `Off`, and at quit. It keeps no timer, and a refused assertion is logged, not shown.
- **Open at Login (`Settings → General → Open at login`, default off):** Managed via `SMAppService.mainApp`.

## 12. Resource, Performance, Subscription & Context Budgets ([D-07](DECISIONS.md), [D-83 (c)](DECISIONS.md))

### 12.1 Resource & Performance Guarantees
- **CPU40 ceiling (`D-07`, `D-19`):** At 1 MiB/s visible terminal output over 60 s, total CPU across Sphyrna app + fixture + run-scope hosts must not exceed **40 % of one logical core** (Package I baseline: app `23.8–24.0 %`, total `25.4–25.6 %`; hidden stream `3.5 %`; input-to-draw p95 `~20 ms`; reduced-motion indicator `~0.005 %`; idle observer with 1 real Claude `0.044 %`).
- **Visible Chat stream parity (`C7`, `D-70`, `D-83`; frozen with the Chat face, [D-100](DECISIONS.md)):** A visible Chat stream at `600` and `6,000` chars/s must cost no more CPU than the terminal face for the same output.
- **Zero hidden/idle waste:**
  - Hidden, occluded, or unselected terminals suspend rendering (`suspendsRenderingWhenNotVisible = true`) and retain dirty signals without waking `@MainActor` (SwiftTerm Patch 11).
  - The working braille spinner and ASCII shark animations stop all timers and wakeups when the window is hidden, inactive, or off-screen.
  - Stopped/idle/stale sessions hold **zero** live `TerminalSurface` or CLI processes; unused `LiveChatFeed` instances are trimmed to an LRU of **4**.
  - Scrollback (`2,000` lines), inline terminal images (`8 MiB` / `1,024` per screen), pipe unread stdout (`16 MiB`), hook ingress (`1,024` frames), diagnostic journals (`2 × 512 KB`), and transcript reads are strictly bounded.

### 12.2 Subscription Model-Call & Agent Context Guards (`C3`, [D-83 (c)](DECISIONS.md))
- **Allowed model calls on the user's subscription:** Sphyrna makes a model call **only** when the user explicitly sends, asks, or approves (prompt, Quick Question, Side Chat question, Compact, diff comment / side note sent to main, approved session opening, or explicit Remora question / `Draft Brief` / `Catch Me Up`), plus **at most two background calls**:
  1. **Chat session title (`generate_session_title`):** At most **once per session** (max 3 tries), passing at most **`2,000` characters** of the first user message (matching the terminal CLI's own title call; skipped for approved `"$SPHYRNA_CLI" open` sessions and side chats).
  2. **Remora's automatic morning brief:** At most **once per day** after `04:00` local time when Home is shown on screen, online, Remora is on + `Automatic`, a session moved, and ≥ 10 % of the 5-hour limit remains.
  - Nothing else ever calls a model in the background (no timers, watchers, or per-turn summaries; `get_usage` plan-limit reads do not call a model).
  - **Reading a harness is not a model call (1.6.2, `D-94`).** Claude's plan-limits child sends `initialize` before `get_usage` so its answer names the account, and Codex's probe reads `account/read`, `account/rateLimits/read`, `account/usage/read` and `model/list` from a short `codex app-server` (§2.1): none starts a turn or a thread, writes a transcript or spends tokens. Both go through one `HarnessProbe` that never asks a harness switched off, keeps an answer for **5 minutes** unless a person forces a new one (Update, Check Again) and runs on no timer, so a broken CLI is not started again and again. A failed ask is an ask too: inside the floor it stays failed with its reason, and it keeps the last good reading. The health check (`HarnessHealthChecker`) has the same 5-minute floor, and `claude doctor` / `codex doctor --no-color` run only when the person presses Deep Check.
- **Session context additions:** A session started by Sphyrna receives zero injected system prompts, zero written instruction files, and zero hook stdout. Its context differs from a plain terminal session only by the `sphyrna:open-session` skill description (**≤ 300 characters**) and, while in `Ask` mode, the `sphyrna:Ask` output style.
- **Enforced by failing-first tests and guards:** `PluginContractTests`, `LaunchContractTests`, `HookSilenceTests`, `RemoraCallTests` and `RemoraPackBuilderTests`; `ChatModelCallTests` in the frozen lane (TF, `D-119`); Remora's reach rule in `scripts/check-source-guards.py` (formerly `RemoraReachTests`).
