# Loom architecture

Loom is a native macOS 27 app (Swift 6.2 tools, SwiftPM, SwiftUI + AppKit, vendored SwiftTerm) that hosts Claude Code
sessions in one window, each in its terminal or in a native chat over the same CLI, and tracks them in a local
catalog. From 1.6.0 the app is named Sphyrna (D-77, D-83); the code keeps the name Loom. Every provider process is started inside a
Loom-owned run scope, so Loom can stop exactly what it started, and nothing else, on stop, quit, or after a crash.
The exceptions are a few short-lived helpers that run outside a scope; Section 4 lists them.
Read this before touching code; verify against the source when in doubt (the code wins).

- **Scope of 1.6.0 (D-68, D-69 (5), D-83):** Claude only. Codex code stays in the tree and its entries are shown, but it is **paused
  and cannot start in 1.6.0** (see Section 8). The product renderer is Core Graphics; Metal is development-only (`--metal` with `--evidence`).

## 1. Layers

```
loom-app (exe: NSApplication, AppDelegate, window, menus, dev evidence)
   |-- LoomCatalogUI  (SwiftUI sidebar/detail, CatalogModel, ConversationController)
   |       |-- LoomTerminal  (TerminalSurface over SwiftTerm, input queue wiring, quit state)
   |       |       |-- SwiftTerm (Vendor/SwiftTerm, local patches)
   |       `-------+-- LoomCore  (no UI: runtime, supervisor, catalog, ownership, hooks)
   |                       `-- CLoomPOSIX (C: PTY, process table, coalition reads, scope IO)
   `-- LoomLaunchOptions (pure CLI-flag rules, no dependencies)
LoomChat (v2 chat engine: stream-json protocol, TurnModel, TranscriptLens, TranscriptGrowthFeed, the Chat-face driver; no UI, spawns nothing) -> LoomCore; LoomCatalogUI links it (the Chat view, V13)
LoomRemora (v2 Remora's call: one owned `claude -p` child per question or brief, its streamed answer; the pack it reads and the brief's schedule; its working memory; no UI) -> LoomCore, LoomChat; `LoomCatalogUI` links it (L3a: the host and the model API; L3b Settings: preferences and memory sheet on `v2`; prompt-call APIs uncalled on `v2` until `L3b Home` integrates from `wt/ink-remora-home`)
helpers: loom-run-host (C, bundled LoomRunHost.app) -> CLoomPOSIX;  loom-hook -> LoomCore
dev/test only: loom-test-child, loom-fake-provider, loom-catalog-fixture, loom-probe
```

Rules: `LoomCore` imports no UI framework and keeps process/PTY/wait work off MainActor. Dependencies only point down the
diagram. AppKit appears only in `LoomTerminal`, `LoomCatalogUI` and `loom-app`. `LoomChat` imports `LoomCore` and no UI
framework (`LoomCatalogUI` imports `LoomChat`, never the other way round); starting and stopping the `claude` process stays in `LoomCore`'s supervisor (pipe children, Section 4). `LoomRemora` imports `LoomCore` and `LoomChat` (the stream decoder) and no UI framework; its child is the supervisor's owned streaming helper (Section 4), never a `Process` of its own.

Roles: `SessionRuntime` is the one application runtime, and `SessionService` (LoomCore, `@MainActor`) is the UI's one door to a session's lifecycle: the UI sends intents (`ConversationIntents`, which `ConversationController` forwards) and reads state. The service owns start, resume, Stop, the Chat → terminal handover, the answers to a session's requests and to an agent's open requests, deletion, when a side chat's process ends (D-72), and the user's writes to a session's own record (title and pin: `SessionRecordWrites`, the same catalog methods underneath; a model with no service reads the same writes over its own catalog), and the state they pass through (`SessionTransitions`: busy per session, the start keys, `preparingStarts`, and `handovers`; observed, read by the views through `CatalogModel.busy` / `startingKeys` / `preparingStarts` / `handovers`, which forward). It reaches a structured face through `StructuredFaceHost` (`ChatSessionHost` conforms, in LoomChat; the lifecycle verbs, whether a session's run is live, idle or being moved, and the Close stop) and holds that host, the one strong owner (the app makes it with the model's closures, `CatalogModel.makeChatSessionHost`, and gives it to the service it creates; the model reads it through the service as `chatSessions`, and a model with no service keeps a host of its own, as it keeps its own transitions), and a terminal face through `TerminalFaceSinks` (`ConversationController` implements it with its `TerminalSurface`s); the face of a start, a resume and an approved opening is `FacePolicy`'s, fed by the switch the model sets on the service and the host the service holds. The UI's effects stay in the UI: the service tells them by the closure an operation takes (a card exists, a Stop answered) and by `failureHandler` (a `SessionFailure` the controller words). Chat-specific calls (send, mode, model, rewind, cards) are still the UI's direct calls on the driver. The runtime manages sessions, not harnesses: the provider-specific part of a start, resume, run end and deletion sits behind `Harness` (`ClaudeHarness`, `CodexHarness`), looked up by provider in `SessionRuntime.harnesses`. `ProcessSupervisor` (actor) owns runs, scopes,
ledger, stop/shutdown and catalog commits. `SessionCatalog` (actor) is the durable store. `SessionEventHub` (actor) publishes
sequenced frames to subscribers.

**Sidebar events, search and redraws** (H1-D2) A frame about one session a visible list already shows (run start/end/detach,

The live model keeps line counts only, so it is not a source of hunks.
- **Branch:** `ChangesReader.gitList` / `gitDiff` (the app's reader is set by `CatalogModel.chatSessionsInstalled(runtime:host:)` from the runtime's supervisor; a model without one says "Git is not available here") -> `GitChanges` (LoomCore) -> `ProcessSupervisor.withHelperScope` (the git calls of one list, and of one file's diff, share one run scope, released when the read returns or throws; each call is still its own owned job with its deadline and byte limit, cancelled and awaited by `shutdown`) with the fixed environment of `CleanupWorktreeProtection.live`, `-c core.fsmonitor=false --no-optional-locks` (`GitChanges.safety`; the diffs also pass `--no-ext-diff --no-textconv`, so nothing a repository's own config names runs while Loom reads), a deadline per call (10 s the list, 15 s a file) and a byte limit on the answer (`LoomError.outputTooLarge`; 1 MiB a file's diff). The list is `diff --numstat -z` against the merge base plus `ls-files --others --exclude-standard`, cut to 1,000 files before any untracked file is read for its line count; a file's diff is read when it is shown (an untracked file's is built from the file). `DiffHunk` and `UnifiedDiff` (LoomCore) are the hunk model both scopes share.
- **Comments:** drafts are `SessionChanges` state; `sendChangeComments` builds one message (`ChangesMessage`) and calls `sendChatMessage(_:to:)`, the composer's path (a live driver sends `next`; a stopped Chat session resumes first), and clears the drafts once the send was accepted. A session outside the Chat face cannot send (`changesSendAvailability`).

**Side tab (V22 part 3)**
`InspectorContainer` (`.side`) -> `SideTab`. The tab is offered by `CatalogModel.inspectorTabs` only for a Claude session with a provider conversation id; `shownInspectorTab` falls back to Overview where the chosen tab is not offered. `CatalogModel.sideTrigger` is nil while the inspector is closed or the session is not offered the tab, and the inspector's `.task(id:)` runs `runSideRead()` when it turns non-nil: `CatalogModel.refreshSideChats(for:)` reads the session's forks from `SessionCatalog.sideChats(of:)` and makes a `SideChatItem` of each, and `SideState` keeps one `SideSession` (items, open one, typed text, notice, discard state) per parent, in memory only. Nothing else touches part 2's engine: `startSideChat`, `sideChatDriver(for:parentSessionID:)` and `discardSideChat(id:)` are called from `CatalogModel+Side.swift` only.
- **Question:** `submitSideQuestion` refuses "/" text before any fork (`ChatDriverError.commandsRefused` is the engine's own guard behind it), starts a fork with `startSideChat` when none is open (a CLI that cannot fork sets `forkUnsupported`: Loom tries and learns), and otherwise sends through the open fork's driver, resuming it first when stopped; the driver turns allow-edits off at every start (`launch`), so a side chat that resumes, after Close or after its process ended, starts with edits off, and Close also turns the toggle off at once.
- **Thread:** `sideFeed(for:in:)` makes a `LiveChatFeed` through `ChatAttachments.attachment(for:make:)` with `sideFirstUUID`; the feed hands every history it reads to `TurnModel.sideThread(startingAt:hasOlder:)` (`LoomChat/Model/TurnModel+SideThread.swift`), which drops the fork's copy of the parent (found: cut there; not found with older records: keep all and keep asking; not found with nothing older: keep nothing). The view model has no composer, so the rows offer no Rewind files; `offersSessionGrants = false` hides "allow for session" on the side chat's request cards.
- **Waiting:** a side chat's pending request is shown by the tab's dot only. The side chat has no `SessionRowModel`, so no attention count, menu bar item, Home or palette entry, and no notification can see it.
- **Note:** `sendSideNote` builds `SideText.note(question:answer:)` and calls `sendChatMessage(_:to:)`, the composer's path.
- **Retiring (D-72):** a side chat's process runs only while it is the open one in its parent's tab. The rule is `SessionService`'s (the section "Side chats (D-72)"), keyed by session id, and it asks the face (`StructuredFaceHost`: `isLive`, `isLiveAndSettled`, `isHandingOver`, `closeSession`); the Side tab only reports what it observes. `SideSession.show` tells which side chat the tab shows (`sideChatShown`), and `openSideChat` and `startNewSideChat` tell that the one that was open is left (`sideChatLeft`): an idle one (`ChatSessionDriver.isLiveAndSettled`: ready, no turn, no card, nothing queued) stops at once with Close's own stop (`closeSession`: "Allow edits" turns off); one with a turn or a waiting card is remembered by the service and stops the moment it settles, unless it was shown again. Each `SideChatLive.read` tells the service (`sideChatRead`) that a followed side chat was read, which is how a remembered one is noticed settled. The parent's run is read from the model's live states, on either face: `CatalogModel.noteSideParentRuns` runs on every run frame (`runStarted`, `runEnded`, `runDetached`) and after missed frames, and `SideSession.parentRunEnded(in:)` follows the run onto the card a `/clear` moves it to. When the run is gone and its card has none, the service is told (`parentRunEnded`), which retires every side chat the tab follows by the same rule, the open one too and a reopen does not save it, unless the run ended in a move to the terminal: not while the service's or the face's handover runs (`transitions.handovers`, `isHandingOver`), nor once the card's terminal run is live (`currentRun`), whichever order the frames come in. `retire` checks again, just before it closes, that the side chat was not shown again. A side chat with no live run is left alone. A Close that fails in a retirement is `SessionService.sideChatCloseFailed`, which the model words as the tab's notice; the user's own Close takes the failure from `closeSideChat`. The thread stays, and the next question resumes the chat. Closing the inspector or selecting another session changes no `openID`, so retires nothing.
- **Discard:** `discardSideChat` -> `host.discardSideChat(id:)`; `.deleted` -> `session.forget`, `.incomplete` -> the deletion's pending state plus a failure line with Try again. `DeletionCopy.confirmBody` names a session's side chats.

**Session directory (R2)**
`SessionRuntime.directory` -> `SessionDirectory.summaries(SessionQuery)` -> `[SessionSummary]`. A read model that answers "which sessions exist, in which state" for the channel's `sessions` command and the pack builder; harness-neutral (a `SessionHarness`, never a provider switch) and additive (no existing caller). Pure reading: it writes nothing, starts nothing, and returns no transcript content and no path.
- **Read:** one `SessionCatalog.directoryRows` query (the lists' `listed` predicate, so no side chat and nothing being deleted; no synthetic session; the project's name joined in; newest activity first, ties by id; the project filter and the excluded ids are in the SQL; no SQL `LIMIT`, so undecodable rows do not count toward the limit), then one `SessionEventHub.snapshot()` for the live state, and the runtime's open requests for the requesters that wait on the user. The limit is clamped to 1...100 (default 20).
- **State word:** `SessionStateWord.of(record:live:awaitingOpenApproval:)` is a pure mapping that follows `SessionIndicator` (LoomCatalogUI) case by case: working, `needs-approval` (a hook approval, a waiting request, an open request), `waiting` (for you), `failed`, `problem` (a problem or a stop not verified), `unknown` (state unknown or identity unclear), `finished` (unviewed), `ready`, `idle`, `stale`, `stopped` (ended). `SessionDirectoryAgreementTests` holds the two together over a table of every indicator case: a change to one must change the other.
- **Face:** `terminal` or `chat` from the live run's `runEndpoint` (`pipe` is `chat`); nil without a live run or before the endpoint is known.

**Chat view (V13)**
`ChatTranscriptView` -> `ChatTranscriptModel` -> `ClaudeTranscriptLocator.locate` -> `TranscriptLens` (cold open: the newest turns into a `TurnModel`; older turns on demand) -> `ChatRowBuilder` rows -> `ChatStreamController` (table). While the view is on screen and the window visible, `TranscriptGrowthFeed` watches the file (50 ms coalescing); a hidden window or a closed view has no watcher and no timer.
- The stream derives rows incrementally: `ChatRowStore` keeps rows per turn and returns a full list or patches; `ChatStreamController.apply(patches:)` patches the table (a reader action that changes the length of an earlier stretch, such as opening an old fold, rebuilds the row index). `ChatRowBuilder.rows` is the from-scratch reference.
- `ChatPresentation` (per session) holds the model copy, the reader's state and the store; a view attaches and detaches. `ChatTranscriptModel` is the transcript source adapter.
- Streaming text is shown at most once per `ChatPresentation.rowsInterval` (`streamingRowsInterval`, 80 ms, set by `LiveChatFeed`; a transcript follower has none). A change that only grew the text of a block that is still streaming derives its rows at once after a quiet interval, otherwise a timer does it with everything that came meanwhile; any other change derives at once and takes the waiting text with it. A presentation nobody shows keeps no wait and no timer. `ChatStreamController` updates a changed row that is on screen in place (`refresh`: configure, remeasure, `noteHeightOfRows` only when the height changed) and reloads only rows without a cell, because `reloadData(forRowIndexes:)` makes AppKit walk the cell's view tree for its key view loop (57 % of a delta in a profile).
- A streaming prose row (C7) splits its message into a settled head and the open tail (`ChatContent.streamingBlocks`, incremental: it scans only the new bytes once the old text is proven a prefix, for up to 24 messages). The head is one Equatable view (`ChatSettledBlocksView`), so a flush that only grows the tail builds none of the settled blocks; appearance and tone reach them through the environment and `ThemeState`. `ChatRowMeasurer` composes the row's height from `ChatProseView`'s insets, the head blocks' cached heights (keyed on row, index, content hash, width and wrap flag) and the tail measured with the hosting controller, and `ChatRowGeometry` gives the view and the measurer one content width. The split reads fences by the parser's own rules (`ChatContent.SplitFence`, with `ChatMarkdown.openingFence` and `isClosingFence`), so the head ends only at a blank line outside any fence the parser sees, and only a message's newest head is kept in `blockCache`. Settled rows, other row kinds and a head that still holds an open code fence (one the split does not see, as in a quote) keep the whole-row measure. `ChatStreamMeasureTests` pins the measured characters per rebuild, the block builds per flush, the look after an appearance, tone or width change, the composed height against the whole-row measure (0.5 pt) and the incremental split.
- Sources emit `ModelChange` (`.replaced`, `.older`, `.growth`) with consecutive sequence numbers (`ModelChangeSource`). `TranscriptGrowthFeed(delivery: .changes)` yields one change at a time and waits for `acknowledge()`, so a slow main thread gets one merged change; it always delivers its first read after a start, and an empty change carries the source's current sequence, so a receiver behind it asks for a snapshot. An `.older` change reuses rows only when it is the next in sequence. A status with no entry is a change (`activityChanged`).
- The receiver's copy of the model carries entries, turns, `activity` and the unknown-record count; it does not update `tasks`, `latestInit`, `contextUsage`, `rateLimit` or `sessionState` after a snapshot.
- A live source (V16) must name every mutation in the `ModelDelta` it returns and set `activityChanged` when `activity` changes.

**Chat driver and live view (V16)**
`SessionRuntime.startChatConversation` / `resumeChatConversation` start a `claude` stream-json child with pipes inside the run scope and hand its `PipeEndpoint` to a `ChatSessionDriver`. `ChatSessionHost` (LoomChat, MainActor) owns the drivers in a lock-protected registry and re-keys one when its run moves to a new card (`/clear`); the app creates the host with the model's closures (`CatalogModel.makeChatSessionHost`) and gives it to the `SessionService`, which holds it (tests call `installChatSessions`, which makes and installs one in a step), and `CatalogModel+LiveChat.swift` holds the model's side. What the app keeps per driver is not the host's: `ChatAttachments` (LoomCatalogUI/Chat) holds the live chat's `LiveChatFeed` and the composer's `ChatComposerModel` by driver and type, trims the feeds past `ChatAttachments.limit` (one in use stays), and lets go of a driver's attachments when the host tells it (`driverForgotten`, at the start of `ChatSessionHost.forget`). Since V19 Chat is the default face: Settings → General → "Sessions run in" (`UIPreferences.newSessionFace`, default Chat) picks the face of a new session, and `SessionService.startSession` starts in Chat when the app's Chat host exists, else in the terminal. There is no `liveChatEnabled` flag any more. The driver's code is split in eleven files by cluster (`ChatSessionDriver.swift` and `ChatSessionDriver+Lifecycle`, `+Handover`, `+Sending`, `+Requests`, `+Mode`, `+Queue`, `+Ingestion`, `+Rewind`, `+Side`, `+SideChat`); they are one actor, so an `await` is a reentrancy point wherever it sits. Stored properties stay in the core file, grouped by the file that works on them, and the members the extensions share are internal to LoomChat. The two request cases of `ingest` call `receiveToolRequest` and `receiveCancel` in `+Requests`, the one place where a control request becomes a card; `ingest` ends with its `switch`.
- *Launch choices and face.* Permission mode, model, effort and the owning run endpoint live in the catalog's `sessions` table (`SessionCatalog+Launch.swift`; the columns are added on open by `ensureLaunchColumns`, like the origin columns). The runtime writes the choices when it starts a session and after a live change in the Chat face succeeds (`recordLaunchChoices`); every spawn in either face reads them. The same call updates what the session's project starts its next session with, in `app_state` key `launch.last-used` (by project id, `none` for no project; Full access is never remembered), which the draft reads (`lastUsedLaunchChoices`). `NewSessionDefaults.resolve` orders the mode as the draft's pick, then `NewSessionSettings.permissionMode` (Settings → "Mode of new sessions", D-69; nil is "Last used in the project"), then the project's last used mode, then Ask before edits; Full access is allowed at the Settings level only, and a remembered one is skipped. The endpoint is written when a run starts, and a run that moves card carries both to the new card (`carryLaunchState`). The older `new-session.json` lists (`launched` per session, `lastUsed` per project) are copied into the catalog once (`importLaunchChoices`, `importLastUsedLaunchChoices`, from `ConversationController.begin()`), marked by `app_state` key `launch.legacy-import-done`; nothing writes them any more.
- *State.* `SessionViewState.runEndpoint` (terminal or pipe) says how the live run is driven; `SessionViewState.waitingRequests` lists both providers' waiting requests (`ProviderPendingRequest`: the Chat face's `pendingRequests`, Codex's answerable `userRequests`). "Running" means a run, never a terminal view (`CatalogModel.runEndpoint(of:)`, `isRunning(_:)`).
- *Work state.* The driver is the only source of a pipe run's work state (`ClaudeSessionAdapter.handOverWorkState`). Hooks still keep identity, use times, subagents and the reason line; their activity is not published, and a run with a driver has no registry watch (`sdk-cli` entries are ignored: `ClaudeRegistrySnapshot.isStreamChild`).
- *Stop.* `ManagedRunStopHooks.leave(ManagedRunLeave)` interrupts a running turn or a waiting request and waits for the `result`, within the input-close grace, before stdin closes; Stop, Quit and a face switch all go through it. It is not called when the leader already exited (`processExited`). `moved(card)` tells a run's owner that the run changed card. Quit waits for pipe stops already under way. Nothing in the driver sends a signal.
- *Bounds.* `ControlChannel`'s outgoing queue holds 256 lines (a full queue refuses the line with `outputFull`; the driver reports `inputFull`); the stdout a driver has not taken is bounded at 16 MiB (`ChatPipeSink`: the read waits, nothing is dropped); stdin keeps `PipeEndpoint`'s 1 MiB limit.
- *Queue.* `<data root>/chat-queues/<session id>.json` (`ChatQueueStore`): at most 100 items and 1 MiB of text. An item leaves the queue only once it is written; an unreadable file is set aside as `<id>.unreadable-<epoch>.json`, never overwritten; deleting a session deletes its queue (`ChatSessionHost.forget`), and a launch removes queues of sessions the catalog no longer has.
- *Live view.* The driver's `modelChanges()` is a `ModelChangeSource`: a snapshot first, then growth with consecutive numbers, a snapshot after `/clear`; `snapshotChange()` answers a reader that missed one. `LiveHistoryJoin` joins the transcript's history with the newest run's live model: it cuts the history at its first entry of that run (the same id, a uuid Read now re-sent a prompt under (`sentAliases`), or a prompt with one of the run's prompt texts written since `RunStart.time`), renames history ids that clash, and carries the earlier runs' Loom-only rows (markers, failure notices, answered cards) into the history by time. `RunStart` holds the run's counts, launch time and `generation` (one more per launch, kept across `/clear`, published in `ChatLiveState`). `LiveChatFeed` (one per driver, held through `ChatSessionHost.attachment(for:make:)`) owns the session's `ChatPresentation`, asks the driver for a snapshot after a gap, reads the history again when the generation changes, follows `/clear` with a new presentation (the driver's registry re-keys the driver to the new card and refuses, with a log line, to replace another driver already there), and uses the transcript only for the cold open, older turns and "Show all"; no `TranscriptGrowthFeed` runs for a session a driver owns. The host keeps a feed while a view shows it or its run lives (`ChatDriverAttachment.isInUse`; the feed counts its views and calls `onUnused`), otherwise it is released as soon as it is not in use (the feed calls `onUnused`, the host `releaseAttachment`), and the trim to the four last used (`attachmentLimit`) only covers any left; the composer's model, which holds an unsent draft, is never trimmed; the ended view of a session counts as a view (`endedViewAppeared`). Every view binds the composer to the feed it shows (`ChatComposerModel.environment` holds its feed weakly). One stream shows a feed at a time; the last view to attach takes it over. `LiveChatView` shows it.
- *Composer (V17).* `ChatComposerModel` (LoomCatalogUI/Chat) holds a session's text, attachments, menus, history and queue editing. `ChatAttachments` keeps one per driver (attachments are keyed by driver and type; only feeds are trimmed); Quit flushes them through `kept(ofType:)`, and the host's `forget` stops their writes (it tells `ChatAttachments` first, before the queue and draft files go). `ChatSessionDriver.composerState()` gives the model the driver's part. `ChatDraftStore` keeps drafts in `<data root>/chat-drafts` (owner-only). When a run ends (exit, Stop, Quit), the driver itself writes the messages the CLI never read into the draft, in front of the typed text. A message written while a turn runs is also in the draft file's `held` list from before it goes out until Claude reads it (`ChatDraftStore.hold`, `release`), so a crash leaves it there too: a driver made afterwards moves held messages into the text (`recoverHeld`), and sweeps the attachment files no draft file lists (the only place it does: a write removes just the files the previous file listed and the new one does not, because the composer writes an attachment's file before its next save lists it). Each writer owns its part (`save` writes the composer's text and attachments and keeps `held`), and every draft operation takes one process-wide lock, so a save, a `prepend` and a `move` never lose each other's text. On `/clear` the driver moves the draft file with the run (`move` merges `held`), and the composer saves under the new card. Key rules are the pure `ComposerKeys.resolve`, by key code. `send` takes `ChatOutgoingAttachment`s; `ChatSendTiming` is `next` or `afterTurn`.
- *Requests (V18).* `ChatRequestAnswers.swift`: `ChatRequestAnswer` builds the CLI decision and the stream line; `ChatSettledRequest` keeps the last 16 settled requests as summaries. `ChatLiveState` carries `requests` and `settled`; `ChatLiveSource` adds `answer(requestID:_:)` and `resume()`. A request takes one answer (`answerInProgress`) and none while the session stops. `ProviderPendingRequest` has a `note`; `SessionViewState.displayReason` is the first waiting request's reason, else `reason`; `SessionIndicator` reads a live run with a waiting request as waiting for approval even after a `result`; `ApprovalNotificationPlanner.body(project:kind:)` words a notification by kind. The composer and the cards meet in `PinnedNoteLink` (`cards.attach`): the composer's text is the card's text, and the typing guard (`composerIsBusy`, `releaseHoldIfIdle(at:)`, on system uptime) follows the composer.
- *Quick question (V22).* `side_question` (S6 Q3, Claude Code 2.1.300) answers from the session's context with one `control_response` (`{response, synthetic:false}`, after a single `system/control_request_progress{started}`) and nothing else: no `result`, no usage, no tool event and no transcript record, so the session never sees the question and it costs one model call over the parent's cached context (an identical question asked twice is two calls). It works while the session is idle, while a card waits and while a tool runs; text streaming at the same time can pollute the answer (1 of 2 samples). So `ChatSessionDriver+Side.swift` changes no state for it (no phase, queue, mode, model or request) and only awaits the reply: `sideQuestion(_:)` is allowed while a process is live and no handover holds the session (`SideQuestionAvailability.of`: `ready`, `working` or `needsYou`), and throws `SideQuestionError` otherwise or for an empty question (`notAvailable(.launching | .stopping | .stopped | .handover)`, `emptyQuestion`, nothing sent), and `noAnswer` (120 s, `ChatSessionDriver.sideQuestionTimeout`; the channel tells the CLI to drop the request), `unsupported` (an error frame "Unsupported control request subtype", which is how a CLI without the request answers) and `failed(message)` (the CLI's own text). A cancelled asker ends with `CancellationError`. The journal gets `chat.sideQuestion` with the outcome and the latency, never the text. The UI state (panel open, text, last question and answer, the waiting task) lives in `CatalogModel.quick`, never in the driver; the answer is in memory until the panel closes, and an answer that arrives after the close is discarded. The fake provider scripts the answer per run: `LOOM_FAKE_CHAT_SIDE_ANSWER` (text), `LOOM_FAKE_CHAT_SIDE_DELAY_MS`, `LOOM_FAKE_CHAT_SIDE` = `error` | `unsupported` | `silent`.
- *Side chat: the fork underneath (V22, engine only; the Side tab is part 3).* A side chat is a fork of a session: `claude --resume <parent> --fork-session --session-id <new>` (S6, S6b, Claude Code 2.1.300; `ClaudeRoute.fork`, which refuses a `<new>` that is not a UUID because the CLI exits before any output for one). The fork takes `<new>` everywhere (init, hook, transcript file name), copies every uuid-bearing parent record into its own file under the new session id (same uuids and timestamps; nothing in it names the parent) and leaves the parent's file untouched; with the parent's model, tools and effort it reads about 97 to 100 percent of its context from the cache, which is why nothing that changes the tool set (`--disallowed-tools`, `--tools`, plan mode) is used. *Identity and link.* `SessionRuntime.startSideChat(parentSessionID:sessionID:outputSink:)` chooses the fork's id (lower case), makes the card with `providerConversationID` set to it **before** the spawn (same project and folder as the parent, `--permission-mode default`, the parent's model and effort from the catalog), and writes three nullable columns on `sessions` (added on open like the launch columns, no `user_version` bump): `parent_session_id` (the parent's Loom id), `forked_at` (taken before the spawn: what the fork can see ends there) and `side_first_uuid` (the uuid of the fork's first user message, written once; the copied records before it are the parent's). Every later launch is a plain `--resume` of the fork's own id, again in `default` mode with the same ask rules. A spawn that fails removes the card (and whatever the fork wrote) through the verified deletion path; a fork that spawned and never became Ready is discarded the same way by `ChatSessionHost.startSideChat`. *One card.* The fork's SessionStart hook has source `fork`, which the adapter used to read as a new conversation (a second card). Two guards: the stored id (`ProcessSupervisor.adoptConversation` now compares ids case-insensitively and returns early when the run's card already holds the id) and a safety net in `ClaudeSessionAdapter` (runs marked by `markForkRun` never adopt on `source: fork`; an id other than the card's is journaled as `side_chat_identity_mismatch` and changes nothing). *Hiding rule.* One SQL predicate (`SessionCatalog.notSideChat`, combined with `notDeleting` as `listed`) is applied at every list, count and search of the catalog (`sessions()`, `sessionPage`, `searchSessions`, `sessionCounts`, `sessionCount(activeSince:)`, `lastUsedProjectID`, `oldestLastUsed`, `classifyStale`, `oldestStaleCandidate`, `sessionsEndedByQuit`, `listedSession(id:)`, `removeProject`'s emptiness check); the direct lookups the runtime needs (`session(id:)`, `sessions(ids:)`, `session(provider:conversationID:)`) stay unfenced, and `sideChats(of:)` is how the Side tab finds them. One Swift predicate (`CatalogSession.isSideChat`) is applied where live state is turned into something the user sees: Active, `attentionCandidates` (Dock badge, Home, notifications), `menuBarEntries`, the palette's session rows and a project's attention dot. A side chat is therefore never in a list, never raises a badge, and is never cleaned up as stale. *Policy and classifier.* A driver may be given a `ChatRequestPolicy`, consulted where a `can_use_tool` request would become a card: `.ask` (the card, as in a main session), `.allow` or `.deny(text)` (answered at once on the same channel call as a card's answer, nothing is listed, so no card flashes and nothing reaches the hub, Dock or Home). A refusal leaves one Loom-only line in the stream ("Refused Write · path") and counts in `SideChatState.refusedCount`; an allowed read-only command only counts. `SideChatPolicy`: Edit, Write, MultiEdit and NotebookEdit are denied; Bash is allowed when `ReadOnlyCommand.isReadOnly` proves it changes nothing (a short list of programs and flag rules, pipes of such programs, `>/dev/null` and `2>&1`; any other redirection, `;`, `&&`, `||`, `&`, newline, substitution, `$`, a leading assignment, `sudo`, `env`, `xargs`, `sh -c`, `tee`, `sed`, `awk`, `find -delete/-exec`, `sort -o`, `git ... --output` and every unlisted program are may-write) and denied otherwise; EnterPlanMode and ExitPlanMode are denied; everything else (AskUserQuestion, MCP and web tools) is a card. A subagent's request (`agent_id`) gets the same answer. "Allow edits" (`ChatSessionDriver.setAllowsEdits`, off on every launch, never kept) turns the two edit denials into cards; it never turns a card into an allow. Because the policy only sees a request the CLI asks for, a side chat's launch settings carry `permissions.ask` for Edit, Write, MultiEdit, NotebookEdit and Bash (`SessionRuntime.sideChatAskRules`): in the real CLI an ask rule wins over the project's own allow rules (shown with `Write` and `Bash(echo:*)` allowed), and an ask rule is a launch setting that does not change the cache prefix. *Guards.* A side chat sends no text that starts with `/` (`ChatDriverError.commandsRefused`: `/clear` would make a visible card), never asks Claude for a title (the card is titled with the first question's first line, once, never custom), changes no mode, model or effort (`notInSideChat`; the cache prefix is the parent's), has no handover to the terminal, writes no launch choices to the project's last-used presets, and gets no rewind store (the fork shares the parent's folder). "Allow for this session" is not offered on its cards. *Usage.* The fork's file holds copies of the parent's messages under the same message ids, which the usage index counts once. `ClaudeUsageIndex` is given the side chats' provider ids (a source closure asked at every refresh); rows read from a side chat's file carry a stored flag (bit 16, never returned by a query) and a record from such a file never takes a message another session holds, while a record from any other file takes it back, whichever file is read first. So forgetting (discarding) a side chat unlinks only its own messages, never the parent's copies, and its own messages count as usual. *Deletion.* `SessionRuntime.discardSideChat(id:)` stops the fork's process in the supervisor's order and deletes it through `deleteConversation` (the plan names the fork's own ids, so the parent's transcript is never part of it; shown byte for byte on the real CLI). Deleting a session first deletes its side chats, each through the same path, and fails (keeping the parent) when one cannot be deleted; `removeFromLoomOnly` does the same for its side chats; `ConversationDeletionPreview.sideChatCount` tells the sheet; removing a project deletes its side chats first (`SessionRuntime.removeProject(id:)`, and `CatalogModel.removeProject` through `ConversationIntents.deleteSideChats(inProject:)`), because they are hidden from the project's count, and only once no session is left in it (`projectNotEmpty` otherwise, with nothing deleted). **Hook silence and CLI drift (D-45)**
- *Unknown registry values.* `ClaudeRegistry` no longer requires the registry file's `cwd` to equal the run's folder (identity is pid, process birth, `startedAt` and the session id; a Claude that changes folder, or a case/symlink difference, would otherwise make the read unavailable for good); a non-absolute `cwd` is still refused. An unknown `status` becomes a snapshot the tracker ignores; `ClaudeRegistryDiagnostics` reports each unknown value once (log notice plus a `cli_compat_warning` journal event).
- *Launch profile.* A required option (`--settings`, `--session-id`, `--name`) missing from `claude --help` no longer refuses the start: `ProviderLaunchProfile.missingRequiredClaudeOptions` names it, `SessionRuntime.reportCompatibility` logs and journals it once per run of the app, and Loom starts Claude anyway.
- *Toolchain freshness.* `ExecutableStamp` (inode, mtime, size) is taken before each probe. `SystemProviderToolchains` and the runtime's cache re-resolve when the executable is gone or its stamp changed, and the runtime invalidates the cached toolchain after a launch failure that is not a Loom refusal (`SessionRuntimeConfiguration.toolchainInvalidator`, which `AppDelegate.runtimeConfiguration` points at `SystemProviderToolchains.invalidate`, makes the app's resolver forget its cache too, so the plan-limits ask shares the same fresh answer). `SessionRuntime.resolveToolchain` retries a failed capability probe once after `toolchainProbeRetryPause` (1 s), and journals `toolchain_probe_failed` with the provider, the kind (`timeout`, `exit N` or `spawn`) and the attempt, never output; a second failure fails the start.
- *Watchdog.* The registry reports "busy" for a run and no hook has reached the adapter since the run started: after `hookSilenceGrace` (3 s) the adapter publishes `ClaudeSessionAdapter.hookSilenceIssue` as the session's `.issue` and journals `hook_silence`. The first hook event for the run clears it. A live terminal or chat shows the issue's text as a failure box in the top banner stack, with no × (`BannerItems`; the card alone only says "Problem"; the text otherwise shows on the record view). "Idle" is deliberately not a signal: a Claude at a folder-trust or first-run question runs no hooks. Hook server counters (`HookDiagnostics`: received, applied, wrong token, malformed, lost to overflow, dropped by reason) feed the export. A wrong token gets a one-byte NAK (`ClaudeHookTransportError.rejected` in the client; `loom-hook` logs under category HookClient). A step back of the hook clock clears the ambiguous-clock input state at the next hook with a sane timestamp.
- *Runtime catalog failures.* `markProviderUsed` failing logs (rate-limited) and never blocks the state update; `ProcessSupervisor.queueCatalogFinish` retries `finishRun` three times (120 ms, 350 ms backoff) before leaving it to the next launch's abandoned-run close; `SessionLifecycleController.timerFired` logs a catalog error and reschedules after 30 s.

Shared prefix, measured without a model on 30 sessions and a 600-token memory (13,800-token packs; `SHARE` lines of `theSharedPrefixOfTheThreePairs…`): question to follow-up 94 %, brief to question 11 %, question to a new question 11 % (the stable prefix, 1,570 tokens), and the same after one session changes state or moves. ## 4. Process ownership model

- **Run host per scope.** `RunScopeLauncher.launch` starts `Contents/Helpers/LoomRunHost.app` through LaunchServices, so
  it is the only member of a fresh resource coalition; everything it spawns, including `setsid`/double-fork escapees, stays
  in that coalition. App and host talk over a short-lived Unix socket (`<home>/.loom[-dev]/scopes/h-<12>.sock`) with a token;
  the host serves only its owner (`LoomOwnerRequirement` in the host Info.plist, checked by the host's `peer_is_owner` in `Sources/loom-run-host/main.c`; the app side, `RunScopeLauncher.verify`, checks peer UID, LaunchServices lineage and the exclusive coalition).
  If Loom disappears without an orderly EXIT frame, the host kills forked members itself and exits. The host is its own
  TCC-responsible app: packages, fixtures and build scratch must live outside `~/Documents` (`scripts/dev-paths.sh`); the source checkout may stay there.
  Tests assemble a host bundle with `RunScopeLauncher.assembleOwnedBundle(executable:in:)` and remove it with `removeOwnedBundle(in:)`,
  which also unregisters it from LaunchServices (launching through `open` registers the bundle, and the record outlives the folder).
- **Owned helpers inside the supervisor (V20 addition).** `ProcessSupervisor.captureHelper(_:_:environment:timeout:outputLimit:)` takes a byte limit for each stream (4 MiB unless the caller sets it); a helper that writes more is stopped and the call throws `LoomError.outputTooLarge(limit:)`. `GitChanges` (the Changes tab's Branch scope, read only, `/usr/bin/git`) uses the same job through `withHelperScope` (one scope for all the calls of a read; `captureHelper` opens one per call, as `CleanupWorktreeProtection.live` and the provider probes use it), so its children are in the ledger, cancelled and awaited by `shutdown`.
- **Remora's working memory (L2a).** `RemoraMemory(directory:timeZone:clock:)` is an actor, the one writer of `<data root>/remora/` (the caller gives the folder; folders 0700, files 0600, every write a temporary file and a rename, nothing logged). `journal/YYYY-MM-DD.md` has one line per call, written mechanically (`- 09:14 <id> question model=… tokens=… sessions=<ids> q="…" a="…" s="…"`: the question cut to 200 characters, a brief has none, the answer's first sentence cut to 240, both masked by `RemoraSecretMask`; `s` is a brief's day summary; the 8-hex id is what the × removes). The last 14 local days (today and 13 back) stay as day files; older days fold into `journal/YYYY-Www.md` (ISO weeks), one line per day (its summary, or "n questions", with the ids of the sessions the day cited), and week files from the 12th week back are deleted. The fold runs when the store opens and after each write, and is idempotent. `projects/<project id>.md` holds at most 2 KiB of dated items, one per line (`- 2026-10-20 · text (sessions: <id>, <id>)`, so a reader sees the ids); `replaceNote` (the daily update: today's date, an item whose text the note already had keeps its date, the newest items stay over 2 KiB), `editNote` (a line that is an item keeps its date and the citations it still has; any other line becomes an uncited item dated today; cut to 2 KiB), `removeNote` returning an undo token, `undo`. `forget(session:)` (`RemoraMemoryForgetter` is the `ConversationForgetting`; registering it is L3's) removes every journal line that cites a session, a day's or a folded week's, whatever else it cites (a line holds a question and an answer's first sentence that may be about it; LOMBOT §3.5), removes a note item that cites only that session, and drops the id from a note item that cites others too (the next brief rewrites the note); `excludeProject` deletes the note; `clearWorkingMemory` removes the journal and the notes and keeps `usage.json`. `RemoraUsage(persistedAt:)` (the store's `usage` is the one counter: give it to `RemoraCall`) keeps today and the 13 days before in `usage.json`. `share(for:excludedProjects:sessionProjects:projectNames:durableNote:)` builds `RemoraMemoryShare` in its two parts (L1c, D-85): `text`, the stable part (`Remora.md`, the projects' ids and names, the notes with "as of 17 Oct" dates), is a function of those alone and does not change when a journal line is added; `recent` is today's and yesterday's lines, newest last. Caps: 3,000 estimated tokens in all, `text` at 8 KiB and `recent` at 6 KiB (the layout's own cuts, so it never has to cut); over them the older journal lines go first, and the notes of the projects that moved longest ago go only when `text` itself passes 8 KiB. A journal line that cites a session of an excluded project (through the caller's session-to-project map) stays on disk and never enters `recent`.
- **Remora.md, the brief's block and applying an answer (L2b).** `RemoraDurableNote(url:)` is `Remora.md` at a path the caller gives: a missing file is created with Remora's headings (`## Who I am`, `## How you want answers`, `## Remembered`); Remora writes only under `## Remembered` (`remember(_:project:)` appends `- 2026-10-21 · <project> · <fact>` and returns an undo token, `undo` removes exactly that line, the last identical one), reads the file fresh before every write, keeps everything else byte for byte (the file's own mode too) and replaces it atomically. A save that would pass 8,000 bytes (or a fact over 500 characters, or a file that is not UTF-8) is refused with a `Refusal` whose `reason` the UI shows; nothing is cut. `RemoraRemember.fact(in:)` is the pure "Remember …" check: a question that starts with `remember`, `hatırla` or `hatirla` (any case, then a space, colon or comma, not ending in `?`) returns the fact (a leading "that" dropped) and makes no call; other languages are ordinary questions. A brief's ` ```remora ` block may carry `"notes":[{"project":"<id>","items":[{"text":"…","sessions":["<id>"]}]}]` and `"summary":"<one line>"` (`RemoraRules.text` says they are for the brief only, one constant for every call): at most 6 projects, 8 items of 300 characters, 4 sessions an item; a project id and session ids must be UUIDs; an item with no session is dropped; a `notes` of the wrong type costs only the notes. `RemoraMemory.apply(answer:request:pack:sessionProjects:excludedProjects:)` writes the journal line (the sessions the pack read, then the ones the answer cites), and for a brief replaces the notes of the projects of the sessions the pack read (through the caller's map; never another project, never an excluded one), keeping from an item only the sessions the pack names or the project's earlier note cited, and writes the summary on the line; it returns the answer's proposed facts that `Remora.md` does not hold yet and saves none; it does not add the call's tokens to the use again. `RemoraCall.removeStaleSystemPrompts(in:)` removes the `system-*.txt` files a crashed call left in `<data root>/remora/` (L3 calls it when Remora starts).
- **Remora's host and model API (L3a).** Remora is wired into the app's core; a model call starts only from one of its doors (Home, §11.10; ⌘K's Ask Remora, §11.8; the new-session page's Draft Brief, §11.9) or an evidence command, each pinned by `RemoraReachTests`. `RemoraHost` (`LoomRemora`, `@MainActor`) is the one owner of Remora in a running app. `CatalogModel.installRemora(runtime:dataRoot:toolchain:profile:)` makes it (in `AppDelegate.startRuntime`, after the runtime is made and **before** `created.start()`), registers its forgetter on the runtime's `ConversationForgetters` and hands it to the model's one `remora` state (`RemoraModelState`); the app imports nothing of `LoomRemora`. - **The memory sheet's reads, Draft Brief's call and the evidence hold (L3a3, L3c core, devguard).** (1) L3a3: `remoraJournalWeeks()` (`[RemoraWeekSummary]`, each with its `start` and lines: the last 14 days, then one folded line a week for 12 weeks; a line's id is its folded day, which `removeRemoraJournalLine(id:)` takes), `RemoraHostNote.rewrittenAt` (the note's last rewrite), `remoraWorkingMemoryUpdatedAt()` (nil when empty) and `removeRemoraNoteWithUndo(project:) async -> RemoraUndoToken?` (that removal's own token; it also sets `lastUndo`, so Home's one Undo holds the newest). Tests: `RemoraDraftTests`, `RemoraModelTests`, `RemoraFollowUpMemoryTests`.
- **Streaming one-shot helper (L1a).** `ProcessSupervisor.streamHelper(_:_:environment:workingDirectory:input:timeout:terminationGrace:outputLimit:errorLimit:)` is the owned helper for a child that is fed a stdin and answers as a stream (Remora's `claude -p`). It is a job like `captureHelper`'s (`runOwnedJob(scope: .perCall)`: an `environmentJobs` entry that `shutdown` cancels and awaits, its own run scope when a scope launcher exists, observed into the ledger when it has none), but `LaunchEnvironment.streamHelper` (`LaunchEnvironment+Stream.swift`) writes `input` through a pipe in pieces while it reads (then closes it; it never goes on argv) and hands each piece of stdout to an `AsyncThrowingStream<Data, Error>` as it arrives. stdout is bounded (4 MiB by default, `LoomError.outputTooLarge`), stderr too (256 KiB); a non-zero exit finishes the stream with `LoomError.helperExit` and the head of stderr; one deadline (`StreamHelperError.timedOut`). The deadline and a cancel by the caller (cancelling the consuming task or dropping the stream) send SIGTERM at once and SIGKILL after `terminationGrace` (2 s by default; in a scope the signal goes only to the member that still holds the pid); Quit and any error kill at once, and whatever the child left in its group or scope is removed before the job ends. Local children (no scope launcher: tests and the probe) are spawned with the default signal dispositions and an empty mask, as the run host spawns its own, so a SIGTERM that the spawning thread would have blocked still reaches them. Nothing the child writes is logged.
- **Short-lived helpers outside a run scope.** Three things run as plain children of Loom, not in a scope, and end within
  seconds: `GitWorkspace` (V07; `/usr/bin/git` as a short-lived child, run only on a draft's first send when its strip asked for a new branch or worktree, and again to put the change back when the start then fails: a `Foundation.Process` that runs `rev-parse`, `check-ref-format` and `show-ref`, then `switch -c` or `worktree add`. Each call waits on a thread of its own (`loom.git`), never on the cooperative pool. One 30 s deadline covers the whole call, output included and capped at 64 KiB: the output is read with `poll` against that deadline and stops at end-of-file, at the deadline, or when git has exited and the pipe stays quiet, so a hook that leaves a background job holding the pipe (`post-checkout` with `sleep 600 &`) cannot hang the start; the read ends are closed and git is terminated at the deadline. The new worktrees live under `<repo>/.claude/worktrees/`, a folder the repository does not ignore, so `git status` lists it as untracked until the user ignores it; Loom does not edit `.gitignore` or `.git/info/exclude`), the plan-limits child (`ClaudePlanLimitsFetcher`, a `Foundation.Process` of `claude -p` that gets one `get_usage`
  request, is asked to leave by closing its stdin, then `SIGTERM` and `SIGKILL` by pid, after a timeout or on cancel) and the
  `log show` read of the diagnostics export (`DiagnosticsExport.runLogShow`, bounded in size and time). The helper
  spawner is a fourth path: `HelperSpawner.scoped` puts an environment shell or a `--version`/`--help` probe in a scope
  when a `scopeLauncher` is configured (the app always has one), while `HelperSpawner.local`, the default, starts it as
  Loom's own child in its own process group, used when no scope launcher exists (tests and the probe) and killed by group on
  abort. In a scope the environment job observes nothing, since the scope owns what the shell starts: a shell that the host
  reaped before the job registered it is a finished capture, not a missing identity (`RunScopeTests`). Every long-lived
  provider process still starts in a scope.
- **Pipe children.** A run's child is either a PTY child (`SPAWN_PTY`: `launch`, `TerminalEndpoint`) or a pipe child
  (`SPAWN_STDIO`: `launchPipes`, `PipeEndpoint`). For a pipe child the host receives three descriptors (stdin, stdout, stderr)
  instead of a PTY master, and the child is otherwise the same: same scope, ledger, markers and same-session guard. The run
  keeps a `RunEndpoint` (`Runtime.endpoint`, formerly `Runtime.terminal`), so the shared stop path asks it, not a terminal.
  The stdout and stderr pipes are drained whatever the consumer does (`PipeOutputSink` must bound its own storage); stdin
  has a bounded queue, so a child that does not read stalls its writers instead of growing memory. A pipe run alone in its
  scope is watched through the scope's members (`exclusiveScopeMembers`), not the whole process table.
- **Stop order.** A PTY child: `SIGHUP`, `SIGTERM`, `SIGKILL`, each after its grace period. A pipe child is asked to leave the
  way its protocol says: stdin is closed first, the run gets its own input-close grace to exit on its own
  (`inputCloseGraceSeconds`, default 2 s; the real CLI exits about 0.7 s after end-of-file), and only then `SIGTERM` and
  `SIGKILL` after the signal grace (no `SIGHUP`: it means nothing without a terminal). Before stdin closes, the run's owner may
  end the work under way through its `leave` stop hook, bounded by that same grace (the Chat driver, see "Chat driver and live
  view (V16)"). Quit does the same on its one
  app-wide clock: stdin of every pipe child closes, one shared input-close wait, then the signals (`SIGHUP` goes to terminal
  runs only, never to a pipe run); a pipe run's stop takes longer by design, so Quit waits for pipe stops already under way
  up to a longer deadline. A pipe child that exits before Loom reads its identity still delivers its output and
  exit status.
- **Scope and members.** `RunScope`/`RunScopeTable` track members via `CLoomPOSIX` reads. `RunScopeMember.launchdSpawned`
  separates launchd-spawned members (never signalled) from forked work (frozen, re-verified, killed). The app's own
  coalition is never an ownership seed.
- **Ledger.** `OwnershipLedger` (Codable: `runID`, `sessionLeaders`, `descendants`, `scopes`) is persisted to
  `runs/<uuid>/ledger.json` before any spawn. Scope records carry the boot-session UUID; coalition IDs from another boot
  are ignored.
- **Birth identity.** A process is identified by `ProcessIdentity` (pid + start time seconds/microseconds from
  `ProcessTable`); signalling goes through `loom_signal_if_matches`, so a reused pid is never signalled.
- **Markers.** Launched processes carry `LOOM_RUN_ID`, `LOOM_SESSION_ID`, `LOOM_MANAGED_RUN_ID` in their environment
  (read back through `KERN_PROCARGS2`, works for non-Apple binaries); launch refuses if they do not match.
- **"Owned" means**: a member of a scope Loom opened in this run (or recorded by an earlier Loom in this boot), identified by
  birth identity, and for forked members re-verified before a signal. Scoped processes of another UID are reported as
  unverified, never as success. Without a `scopeLauncher` (tests/probe only) ownership narrows to session leaders and
  descendants; the app refuses to start runs when the bundled host is missing.
- **Identities are separate:** catalog session id, provider conversation id, run id. `run_sessions` and
  `provider_identity_changes` record `/clear`, `/new`, fork and resume transitions.
- **Dev vs prod identity.** Production bundle id is `local.loom.desktop`; anything else is development
  (`Loom Dev.app`, `local.loom.desktop.dev`, built by `scripts/package-dev-app.sh`; the production `Loom.app` is built by the clean loom tree's `build.sh`, [DEVELOPMENT.md §10](../DEVELOPMENT.md#10-loom-dev-and-the-clean-loom-tree)).

**Backup and restore.** `SessionCatalog.backupStore` (derived from the catalog's folder) backs up through `scheduleCatalogBackup` 10 s after runtime start (`SessionRuntimeConfiguration.catalogBackupDelay`) and forced after a deletion; none is scheduled once shutdown has begun (the next launch's daily backup covers a deletion that ends during Quit), and Quit waits for a copy being written. A generation counter discards a copy that was being written when a deletion finished. When opening the catalog fails with `SessionCatalogError.isDamaged` (corrupt or not a database), the launch prompt (`AppDelegate.offerCatalogRecovery` in `AppDelegate+Diagnostics.swift`, an `NSAlert` run before the window or the runtime exist; what it says and which buttons it has come from `CatalogRecoveryPrompt.make(backups:)`, a pure function) lists `CatalogRecovery.backups(forCatalogAt:)` and offers "Restore Backup" (only when a backup exists; the newest, named by date), "Start Fresh" (`startFresh(catalogAt:)`) and "Quit"; after a restore or a fresh start the launch goes on with the reopened catalog, a failed recovery falls back to the usual catalog-error screen, and any other open error (newer schema, busy, foreign) gets no offer. Restore copies the backup to `catalog.sqlite3.restoring`, verifies it, sets `-wal`, `-shm` and the main file aside as `catalog.damaged-<stamp>.sqlite3` (the sidecars first, so a stray WAL is never replayed into another main file) and renames the copy into place; `SessionCatalog.init` finishes an interrupted restore from the files left on disk.

Catalog schema v3 (CP4-B; `CatalogDatabase.swift` holds schema, migration and SQLite helpers, `SessionCatalog+Deletions.swift` the deletion API):
- **Migration.** `migrate(from:)` runs the chain v1 to v2 to v3 in one transaction (`BEGIN IMMEDIATE`, `user_version` set last, test failpoint after each version's DDL); an interrupted migration leaves the old file untouched. v3 adds `deletions`, `sessions.stale_since`, `app_state` (`last_cleanup_at`, `last_launch_at`) and the child indexes `run_sessions(session_id)`, `runs(initial_session_id)`, `provider_identity_changes(session_id)`.
- **No downgrade (DP-CP4-4).** Loom 0.1.0 (schema v2) refuses a v3 catalog through the existing `user_version > schemaVersion` guard (`unsupportedSchema`) and does not modify the file; there is no v3 to v2 path. Users who go back to 0.1.0 keep their catalog but cannot open it with that build.
- **Deletion record.** `deletions(session_id, provider, provider_ids JSON, config_dir, working_directory, state, requested_at, updated_at, attempts, last_error)`, state one of `requested`, `stopping`, `provider_data`, `catalog`, `verifying`. No foreign key and no title or content; `last_error` is a category plus a file basename (`CatalogDeletionFailure`). API: `beginDeletion` (refuses a second record), `advanceDeletion` (same state records a retry, never backwards), `pendingDeletions`, `finishDeletion`. `deleteSessionRows` deletes identity changes and links of the conversation, repoints each run that started from it to its earliest remaining linked conversation (deleting the run when none remains), deletes the `sessions` row in the same transaction, then `wal_checkpoint(TRUNCATE)`; with `secure_delete = ON` no title bytes remain in `catalog.sqlite3` or `-wal` (trace test).
- **Fences.** A conversation with a `deletions` row is excluded from `sessions()`, `sessionPage`, `sessionCounts`, `classifyStale` and `oldestStaleCandidate`, and `markUsed`, `startRun` and `transitionRun(toExistingSessionID:)` throw `deletionPending`. Direct lookups (`session(id:)`, `sessions(ids:)`) stay unfenced because the deleter needs the row. A side chat's row (V22: `parent_session_id` set) is fenced the same way by `SessionCatalog.notSideChat` in those lists and in `searchSessions`, `sessionCount(activeSince:)`, `lastUsedProjectID`, `oldestLastUsed`, `sessionsEndedByQuit`, `listedSession(id:)` and the emptiness check of `removeProject`; the queries in `SessionCatalog+SideChats.swift` find it.
- **Deletion orchestration (CP4-C).** `isProviderIDShared` ignores a conversation that has its own `deletions` row (its data is going away too); `isProviderIDPendingDeletion(id)` answers whether any record lists the provider id (used by the late-event fence). `ClaudeDataInventory.plan` also returns `unreachable` (a link or other-device folder the scan cannot enter) so a deletion is never reported complete while one exists, and takes `ignoringLiveSessions` for the dry run; the deleter still refuses a live session. `sessions/<pid>.json` is parsed by the same helpers as the registry reader (`ClaudeRegistryFields`; a boolean `pid` is not a pid). Failure categories stored in `last_error`: `config_unavailable`, `stop_failed`, `stop_unverified`, `live_session`, `unsafe_directory`, `partial_failure: <file>`, `unreachable_folder: <folder>`, `leftover_files: <file>`, `provider_id_reappeared`, `forget_hook_failed`, `still_running`, `step_failed`.
- **Undecodable rows.** `sessions()`, `sessions(ids:)` and `sessionPage` skip and count a row with an unknown provider or malformed identity instead of failing the list (`SessionCatalog.skippedRowCount`, `CatalogPage.skippedRowCount`); such rows are never written or deleted.

## 9. Hotspots and scaling notes (facts, no redesign)

- Large actors, split by responsibility into extension files (the stored state stays in the core file, so access is internal
  rather than private): `ProcessSupervisor` (core: ~35 mutable fields, registry, launch, adopt; `+Stop`, `+Shutdown`,
  `+Sampling`, `+Scopes`, `+EnvironmentJobs`, `+CatalogCommits`), `SessionRuntime` (core; `+Codex` ~550 lines, `+Claude`),
  `SessionCatalog` (core; `+Sessions`, `+Runs`, `+Projects`, `+Titles`, `+Paging`; `CatalogDatabase`; synchronous sqlite on
  an actor).
- Codex share of `LoomCore`: ~2,700 lines in `Codex*.swift` plus adapter and `SessionRuntime` parts, roughly a tenth of the target's ~26,000 lines.
- UI-layer coupling: `ConversationController` (live terminals plus the ended runs' snapshots, at most 16 and 4 MiB; the lifecycle itself is `SessionService`'s) and `CatalogModel` hold `SessionRuntime`/`ProcessSupervisor` directly;
  `CatalogModel` (1,814 lines in `CatalogModel.swift`, plus extensions) mixes paging, search, selection, projects, rename, event consumption and branch reads;
  `CatalogModel` imports AppKit and `ConversationIntents.terminalView` returns `NSView`.
  The model layer's capability gates no longer ask which harness a session has: `CatalogModel.capabilities(of:)` returns `HarnessCapabilities` and the gates read its fields (the harness switches that remain: `LoomCore`'s runtime start, resume, deletion and reconcile, `CatalogModel+Deletion`'s refusal words, and the Codex-later reason).
- Launch measurements (F5, release package, 5 runs each, `scripts/perf/launch_paint.py`): window creation (`WindowShown`,
  ~125-136 ms) dominates app delegate to first page; catalog open including `PRAGMA quick_check` is 0.7 / 1.5 / 8 ms at 0 /
  1,000 / 10,000 rows, so it stays on the main thread. Git branch reads are off the main actor (`BranchCache`).
  A run, lifecycle, identity or activity frame patches its one row (`CatalogModel+Patching.swift`, H1-D2) when no frame was
  missed before it and the row is loaded; otherwise, and for batched catalog changes such as aging, `CatalogModel.scheduleRefresh`
  reloads every loaded row of every visible list.
- Logging and diagnostics (D-45): `LoomLog` categories under subsystem `local.loom.desktop` (Lifecycle, Catalog, ClaudeHooks, Registry, Toolchain, Scope, Usage, Recovery, Quit, Diagnostics, HookClient for the `loom-hook` process). Notice and error levels are for transitions and failures; per-event detail is `debug`; ids, counts, durations and error categories are public, user paths private; a repeating error is rate-limited to once a minute per key (`LogRateLimiter`). Loom writes no log files of its own; the only files are the journal and exports above. Cost: a logger call without a listener is a cheap level check, a journal write is one `O_APPEND` line on a rare event, a backup is at most one `VACUUM INTO` a day off the main thread. Entry points: Help > Collect Diagnostics… and Settings > About > Collect Diagnostics… share one `DiagnosticsCollection` (LoomCatalogUI; one export at a time, both disabled while it runs and before the runtime exists) that `AppDelegate+Diagnostics.swift` points at `SessionRuntime.collectDiagnostics(to: DiagnosticsExport.defaultFolder(dataRoot:), usage:, planLimitsFailure:)` (the facts come from `UsageModel.diagnosticsSnapshot()`), then reveals the folder in Finder; a failure shows a modal alert with the error category only. The Usage page shows the same two facts: "Plan limits unavailable" with a short reason while the last ask failed (`UsageModel.limitsFailure`, cleared by a success; an earlier answer stays with "could not refresh"), and one line "N usage records could not be understood, so totals may be low" (`UsageModel.linesNotUnderstood`). Known limits: the usage scan's not-understood line total and `PlanLimitsFailure` are per app run; the journal records the Claude CLI version/capabilities at the first toolchain resolution (`claude_cli`), not at launch.
- Quit path: `AppShutdownCoordinator` (`LoomCore`) owns the quit state machine; `AppDelegate.startRuntime` builds it with the
  shutdown closure when the supervisor exists, and with no coordinator quit returns `.terminateNow`. `TerminalRunController`
  now carries only the evidence-only synthetic dev terminal.
- Identity: `BuildIdentity` (LoomLaunchOptions) is the one Swift owner of production vs development names (data and
  socket directories, command-channel prefix, startable providers); the Python runners share one channel helper
  (`scripts/perf/perf_paths.py`); `scripts/dev-paths.sh` keeps its own copy for the zsh scripts.
- Evidence code compiles only into the development flavor (§7); `scripts/check.sh --release-tree` fails when the release
  binary carries any of it.
- Ownership sampling in `ProcessSupervisor` scans the process table; `persistLedger` rewrites the ledger JSON.
- No `.github/` and no CI. Packaging: `scripts/package-dev-app.sh` for development packages and the clean loom tree's
  `build.sh` (`scripts/release/build-loom.sh`) for `Loom.app`, both signed with the stable local identity; notarization is not
  used ([D-47](../DECISIONS.md), [D-56](../DECISIONS.md)). `CFBundleVersion` is loom-dev's commit count for a development package and
  major × 10000 + minor × 100 + patch of `VERSION` for `Loom.app`. `loom-app` has no unit tests; `AppDelegate`/`MainSplitViewController` and the views are
  covered only by manual acceptance scripts.

## 12. Hard-Won Technical Gotchas & Source Guards

Read these invariants before modifying UI, concurrency, terminal, or runtime code. Breaking any of them will either fail a source-guard test or reintroduce a subtle production bug.

### 12.1 Theme, Appearance & SwiftUI/AppKit Rendering Gotchas

1. **Tone-Dependent `Surface` Tokens Must Be `static var`, Never `static let` (`scripts/check-theme-literals.sh`):**
   - Because pane tone (`Neutral`, `Warm`, `Cool`) cannot ride on SwiftUI's `ColorScheme`, the surface family (`Surface.sidebar`, `backdrop`, `panel`, `panelNS`, `canvas`, `canvasNS`, `inspector`, `card`, `raised1`, `raised2`, `popover`, `segmentOn`, `tree`) reads `Surface.current` from the observable `ThemeState.tone` (`ObservationRegistrar` over a `Mutex`). Storing any of them in a `static let` freezes the tone it was first read with. `scripts/check-theme-literals.sh` enforces both: (a) no `Color(red:)`, `Color.white`, `.system(size:)`, or `cornerRadius: <num>` outside `LoomTheme*.swift`, and (b) no `static let … = … Surface.<panel family>` inside `LoomTheme*.swift`.
2. **User-Visible Wording Guard (`scripts/check-user-wording.sh`):**
   - User-facing string literals in `Sources/LoomCatalogUI` and `Sources/loom-app` must say `"session"`, never `"conversation"` / `"Conversation"` (unless allowlisted in `scripts/check-user-wording.allow`).
3. **Why `Typography` Is Named `Typography` Instead of `Type`:**
   - In Swift, `Type` is a reserved metatype keyword inside a type namespace (`LoomTheme.Type`), so the font namespace is named `LoomTheme.Typography` (and `InkType`).
4. **No Root `.preferredColorScheme` & Terminal Dark Override (`DetailRoute.drawsDark`):**
   - Root views must **not** carry `.preferredColorScheme`, so windows, alerts, and open panels follow `NSApp.appearance` (`darkAqua`, `aqua`, or `nil` for Match system; launch sets `darkAqua` before the model exists so the damaged-catalog alert is dark). However, `DetailView` forces `.dark` on the entire subtree (header, tab strip, banners, and inspector included) when `DetailRoute.drawsDark` is true (`devTerminal`, `terminal`, `endedScreen`), because CLI tools choose ANSI colors for dark backgrounds.
5. **CALayers Cannot See SwiftUI Environment & `TerminalTheme` Thread-Safety:**
   - `BrailleSpinner` / `ChaseDots.LayerView` cannot read SwiftUI environment values; it takes the effective scheme and rebuilds its 10 pre-drawn frames in `viewDidChangeEffectiveAppearance` (and on backing scale / Increase Contrast changes).
   - `TerminalTheme.backgroundRGB` is read on the terminal engine's background feeding thread as well as MainActor, so it is protected by a lock (`setBackground`). `EndedScreenContainerView` is `darkAqua` by construction and reads `ThemeState.tone` in `updateNSView` to repaint its background on tone changes.
6. **Settings Exact Line Height & Glyph Drop (`Settings.glyphDrop`):**
   - SwiftUI's `.lineHeight(.exact(17))` shifts glyphs away from CSS `line-height` centering; `SettingsRow` help/notice/mono facts apply `Settings.glyphDrop` to align with the HTML reference.
7. **Traffic Lights Centered via Empty Unified `NSToolbar`:**
   - Traffic lights are native and not manually repositioned; an empty `NSToolbar("loom-main")` with `.unified` style and no separator is installed on both the main window and Settings window solely so AppKit vertically centers traffic lights at `y = 26 pt` (matching the 52 pt header rows).
8. **`visibleRect` Is Not Clipped to the View's Own Bounds:**
   - With `clipsToBounds` off (AppKit's default since macOS 14), a view's `visibleRect` in a scroll view can be the clip view's whole visible area, even when the view is scrolled out or laid out to zero. Intersect it with `bounds` before reading it as on screen (`ArtLayerView.clockInput`, `ArtVisibilityTests`).
9. **Settings Tabs Need the Band Above the Page and a Window That Is Not Movable by Its Background (`SettingsWindowConfiguration`, `SettingsWindowClickTests`):**
   - With `isMovableByWindowBackground` on, AppKit takes a mouse-down on SwiftUI's drawn controls as the start of a window drag, so the section tabs and the pages' controls never saw their clicks (1.6.0). The window is not movable by its background any more (its title strip still moves it). That was not enough: the page's scroll view reaches up under the title strip and took the tabs' clicks, so `SettingsBand` carries `zIndex(1)` over the page. Only a click in a **shown** window sees either fault (the evidence and the other tests switch tabs through `navigation.section`, and a synthesised click does not reach SwiftUI in a window that was never shown); `aClickOnATabSwitchesItAndAPageControlAnswersItsClick` is a window test (`--windows --idle`) and fails on the 1.6.0 shape. The window's shape lives in `SettingsWindowConfiguration` so the app and the test build the same window.

### 12.2 Chat Stream, Table View & Layout Invariants

10. **`ChatScrollView.tile()` Must Refit `NSTableView` Column on Every Pass (`ChatStreamController.fitColumnToView`):**
   - Without explicitly resizing the single `NSTableColumn` to the scroll view's visible width inside `ChatScrollView.tile()`, `NSTableView` retains a wider column after the detail pane shrinks (e.g., when opening the inspector) and clips rows at the right edge.
11. **Never Call `NSTableView.reloadData(forRowIndexes:)` for On-Screen Streaming Rows (`ChatStreamController.refresh`):**
   - Calling `reloadData(forRowIndexes:)` causes AppKit to walk the cell's entire view hierarchy to recalculate its key-view loop (which took **57% of delta time** in profiling). Instead, `ChatStreamController` updates visible cells in place (`configure`, remeasure, and call `noteHeightOfRows(withIndexesChanged:)` **only** when the height actually changed), using `reloadData` only for rows without a live cell.
12. **C7 Streaming Prose Split & Equatable Settled Head (`ChatSettledBlocksView`, `ChatRowMeasurer`):**
    - A streaming prose row (`ChatContent.streamingBlocks`) incrementally scans only new bytes once the old text is proven a prefix (for up to 24 messages), splitting the message into an `Equatable` settled head (`ChatSettledBlocksView`) and an open tail. A streaming flush that only grows the tail rebuilds **zero** settled blocks and composes the row height from `ChatProseView`'s insets + cached head block heights (keyed on row, index, content hash, width, wrap flag) + hosting-controller measurement of the tail alone (falling back to whole-row measurement if the head has an open code fence). Guarded by `ChatStreamMeasureTests` (within 0.5 pt of whole-row measure).
13. **Inspector Layout Must Never Use SwiftUI `.inspector` or Animate Width:**
    - `detailInspector(model:)` computes `InspectorPlacement` (`.closed`, `.column`, `.overlay`) in a single layout pass with explicit content width and animations stripped from the layout transaction. Because content width equals PTY width on the terminal route, animating it would flood the child process with `SIGWINCH` PTY resizes on every animation frame.
14. **Sidebar Fine-Grained Observation & `SidebarRenderProbe`:**
    - `SessionRowModel.isSelected` and `inActiveSection` are stored per row so selecting a session evaluates only the old and new card bodies; `RowHighlight` holds its own `@State` hover so hovering evaluates only that pill and no card or list; `CardTimeLabel` isolates the `model.now` minute tick; `DraftRows` isolates `visibleDrafts` so typing in a draft never re-evaluates `ProjectList` or session cards. Pinned by `SidebarRenderTests`.
15. **Streaming Text Is Spaced by Its Cost, and the Open Tail Takes No Selection (`ChatPresentation.streamingInterval`, `chatTextSelection`):**
   - A live stream shows streaming text at most once per `streamingRowsInterval` (80 ms). The wait stretches to `flushCostFactor` (5) times the last flush's total cost (`lastTimings.total`), at most `streamingRowsCeiling` (160 ms), so a costly flush is never followed back to back; one cheap flush (about 16 ms) brings it back. Any change that is not streaming text still derives its rows at once (`ChatStreamCostTests` inject the cost). The wait is for text only: a new row, a tool or the end of a block is never held.
   - The open tail is drawn again on every flush, and text selection built a second text layout of it each time. Paragraphs, headings, table cells and code of a block that is still streaming therefore take selection only when it is settled (`chatTextSelection`, recorded by `ChatSelectionProbe` for the hosted test); the settled head and every finished message stay selectable, and Copy and the VoiceOver label read the source text either way. A long open three-backtick fence settles in chunks of 40 lines (`ChatContent.fenceChunkLines`), each chunk parsed once and drawn with the open lines as one card (`ChatCodePieces`); its Copy stays hidden, holding its place, until the fence closes. `ChatMarkdown.isRule` stops at the first character that rules a rule out (a parity test checks it against the old version).

### 12.3 Keyboard, Responder Chain & Input Gotchas

16. **`ShellMenuTarget.runShellCommand(_:)` vs `NSObject.perform(_:)` Collision (V02b / V06):**
    - `ShellMenuTarget`'s `@objc` action selector **must** be named `runShellCommand(_:)`. Naming it `perform(_:)` collided with `NSObject.perform(_:)` in the Objective-C runtime and left every View menu item silently disabled/dead.
17. **AppKit `Cmd+J` vs `Shift+Cmd+J` Ambiguity & Hidden Twin Menu Item:**
    - AppKit dispatches `Cmd+J` and `Shift+Cmd+J` ambiguously when two menu items differ only by Shift on the same letter (which is also why Home is `Ctrl+Cmd+H`, not `Shift+Cmd+H` next to `Cmd+H` Hide). For `Jump to Next/Previous Session That Needs You`, a hidden twin menu item catches uppercase `J`, and the action handler inspects `NSEvent.modifierFlags.contains(.shift)` directly to decide direction.
18. **Turkish Q Keyboard Layout & Bracket / Semicolon Shortcuts:**
    - AppKit maps `Shift+Cmd+]` and `Shift+Cmd+[` by character, which on Turkish Q are the `ü` and `ğ` keys; hidden twins `Ctrl+Tab` and `Ctrl+Shift+Tab` are installed so tab switching works on any keyboard layout.
    - View menu shortcuts avoid Turkish Q letters that differ from US (`ı, ğ, ü, ş, ö, ç`).
    - `Cmd+;` (Ask a Quick Question) requires Shift on Turkish Q, so the Command Palette (`Cmd+K` -> "Ask a quick question") is the layout-independent entry point.
19. **Option Key Character Layer Before Meta (`LoomTerminalView.keyDown` & SwiftTerm Patch 13):**
    - On non-US macOS keyboard layouts (e.g., Turkish, German, French), Option combinations type essential ASCII characters (`@`, `[`, `]`, `{`, `}`, `\`, `|`, `~`). Patch 13 (`swiftterm-open-keydown.patch`) makes `TerminalView.keyDown(with:)` `open` so `LoomTerminalView` sends any Option chord that produces a printable character in the current layout as that character, falling back to `Meta` (ESC prefix) only when it does not.
    - `LoomTerminalView` also offers `Command` key equivalents to `NSApp.mainMenu` before the terminal sees them (pinned by `TerminalKeptScreenTests`), so menu shortcuts never leak into the PTY.
20. **No `.cancelAction`, `.defaultAction`, `onExitCommand`, or `onSubmit` in `InkHost`, Composer, Banners, or Sheets:**
    - **Source Guards in `PinnedFixRoundTests` & `InkSettingsSheetTests`:** SwiftUI's `.cancelAction` / `onExitCommand` and `.defaultAction` / `onSubmit` steal `Esc` and `Return` across the window responder chain even when a popover is closed or a terminal/composer has focus.
    - `InkHostView.keyDown` intercepts `Esc` **only** while a popover is open (scanned by `PinnedFixRoundTests`, just like the composer files).
    - `SheetKeys` (`SheetFamily.swift`) handles `Esc`, `Return`, and `Tab`/`Shift+Tab` via `onKeyPress` (scanned by `InkSettingsSheetTests`): **"Filled means Return"**—`Return` triggers a sheet action **only** when the primary button is `.filled` (e.g., Rename Save); destructive sheets (Delete, Discard Side Chat, Clear Memory, Rewind) use tinted buttons where `Return` intentionally does nothing and focus starts on Cancel.
    - Similarly, `EndedScreenNotice`, `OpenRequestBox`, and `ConversationDetail` Resume buttons never bind `.defaultAction`, so pressing `Return` after switching tabs or while typing in a terminal never accidentally approves a request or launches a session.

### 12.4 Claude CLI, Protocol, Hook & Process Quirks

21. **`/clear` in Chat: Never Adopt `conversation_reset.new_conversation_id` (Fix Round 1):**
    - In real Claude Code, the `conversation_reset` stream message fills `new_conversation_id` with the reset record's own UUID, **not** the new session ID. `ChatSessionDriver` uses `conversation_reset` only for the `"Session cleared"` stream marker and moves the run's card on `SessionStart(clear)` hook or `system/init` (whichever arrives first).
22. **Side Chat `SessionStart(fork)` Double-Card Trap:**
    - When `claude --resume <parent> --fork-session --session-id <new>` starts, Claude fires a `SessionStart` hook with `source: "fork"`, which `ClaudeSessionAdapter` previously treated as a new conversation (creating a duplicate visible card). Fixed by two guards: (1) `SessionRuntime.startSideChat` creates the card with `providerConversationID = <new>` (lowercased UUID) **before** spawning and `ProcessSupervisor.adoptConversation` compares IDs case-insensitively and returns early if already held; (2) `ClaudeSessionAdapter` marks the run via `markForkRun` so `source: fork` never adopts, and logs any mismatched ID as `side_chat_identity_mismatch`.
23. **Side Chat Cache-Prefix Preservation & `permissions.ask` Override:**
    - Passing `--disallowed-tools`, `--tools`, or changing permission mode to `plan` invalidates Claude's prompt cache prefix (dropping cache hits from ~97–100% to 0%). Therefore, side chats launch in `--permission-mode default` with the parent's exact model, effort, and tool set, and pass `permissions.ask` rules for `Edit`, `Write`, `MultiEdit`, `NotebookEdit`, and `Bash` (`SessionRuntime.sideChatAskRules`), which override project-level allow rules in the real CLI without altering the cached system/tool prefix.
24. **Side Chat Usage Index Double-Counting Guard (Bit 16 in `ClaudeUsageIndex`):**
    - A forked side-chat transcript file copies all parent messages with their original message IDs. `ClaudeUsageIndex` tags rows read from side-chat files with bit 16 (never returned by queries): a side-chat file can never claim a message ID held by another session, while a parent session's file always reclaims it regardless of scan order. Thus discarding a side chat unlinks only its own new messages, never the parent's.
25. **Claude `[1m]` Context Window Suffix Stripped in Transcripts (`ClaudeDefaultModel`):**
    - Claude transcripts record model IDs without the `[1m]` suffix. If resume blindly passed the transcript's model as `--model`, a user whose default model in `settings.json` or `ANTHROPIC_MODEL` has `[1m]` would lose their 1M context window on resume. `ClaudeDefaultModel` omits `--model` on resume when the transcript's model matches the configured default (ignoring `[1m]`), unless the session record explicitly names a model.
26. **`ClaudePlanLimitsFetcher` Must Pass `skip_behaviors: true`:**
    - Without `skip_behaviors: true` on the headless `get_usage` control request, the Claude CLI scans every transcript from the past 7 days on every single plan-limits check.
27. **Remora Prompt Caching Split (`--system-prompt-file` + `CLAUDE_CODE_MESSAGES_PROMPT_CACHE_TTL=5m`, D-85 / D-86):**
    - The Anthropic API only matches a cached prefix at a content-block boundary, and `claude -p` sends all of stdin as a single user content block. Therefore, `RemoraPack.stablePrefix` (`<memory>` + `<self>` + `<sessions>` sorted by ID, without state or timestamps) is placed in `--system-prompt-file <data root>/remora/system-<uuid>.txt` with `CLAUDE_CODE_PROMPT_CACHE_TTL=1h`, while the dynamic stdin tail gets the undocumented `CLAUDE_CODE_MESSAGES_PROMPT_CACHE_TTL=5m` (honored by Claude 2.1.300) so 1-hour cache writes (which cost 2× input price) aren't wasted on per-call stdin. `RemoraUsage` tracks a `drift` count whenever 1h cache writes exceed 3× the system prompt estimate (detecting if a newer CLI ignores the 5m env var).
28. **`RemoraReachTests` Source Scanner Guard:**
    - Scans every Swift source file (with comments and strings blanked) to enforce: (a) `RemoraHost` is instantiated only once (`CatalogModel+Remora.swift`); (b) `RemoraCall` is instantiated only once (`RemoraHost.swift`); (c) `briefIfDue` has an exact allowlist of callers; (d) the model API's call entries (`askRemora(`, `briefRemora(`, `briefRemoraIfDue(`) have exact counts per file: Home's `HomeRemoraCalls.swift` 3, the evidence commands 2, ⌘K's `PaletteRemora.swift` 1, and Draft Brief's `draftRemoraBrief(` its own list (the row's `DraftRemoraViews.swift` 1, the evidence commands 1); and (e) `LoomRemora` and `CatalogModel+Remora.swift` contain **zero** timers, dispatch sources, path monitors, file-event streams, notification observers, delayed dispatches, or sleeps.
29. **`SessionDirectoryAgreementTests` State Word Guard:**
    - Pins `SessionStateWord.of(record:live:awaitingOpenApproval:)` (`LoomCore`) against `SessionIndicator` (`LoomCatalogUI`) across every indicator case so the CLI's `"$LOOM_CLI" sessions` output and Remora's pack builder never drift from the UI's status dots.
30. **`GitWorkspace` Hung `post-checkout` Hook & `.claude/worktrees/` Protection (V07):**
    - A repository's `post-checkout` hook that spawns a background process (`sleep 600 &`) inheriting stdout/stderr would hang a naive process wait forever. `GitWorkspace` runs on its own `loom.git` thread with a 30 s deadline and `poll()`, stopping at EOF, deadline, or when `git` has exited and the pipe goes quiet; `GitWorkspace.undo` runs with `-c core.hooksPath=/dev/null` so rollback never runs hooks. `GitChanges` (V20) runs inside `ProcessSupervisor.withHelperScope` with `-c core.fsmonitor=false --no-optional-locks --no-ext-diff --no-textconv`.
31. **TCC & `LoomRunHost.app` Location (`scripts/dev-paths.sh`):**
    - `LoomRunHost.app` is its own TCC-responsible app bundle launched via LaunchServices (`open -n -g -j`). Packages, fixtures, and build `--scratch-path` **must** live outside `~/Documents` (`~/Library/Caches/loom-v2/...`), otherwise macOS TCC prompts or blocks background helper execution; `RunScopeLauncher.removeOwnedBundle` must also unregister temporary test bundles from LaunchServices.
32. **SQLite Catalog Safety (`CatalogDatabase`, `CatalogBackupStore`, `SessionCatalog+Deletions`):**
    - Schema v3 uses `PRAGMA secure_delete = ON` on every connection and runs `wal_checkpoint(TRUNCATE)` inside `deleteSessionRows` so zero bytes of a deleted session's title remain in `catalog.sqlite3` or `-wal` (verified by a binary trace test).
    - Every permanent deletion purges **all** backups in `backups/` and **all** `catalog.damaged-<stamp>.sqlite3` copies (including `-wal` and `-shm`) before taking a fresh backup, and a generation counter discards any in-flight background `VACUUM INTO` copy that started before the deletion finished.
    - When setting aside a damaged catalog during `CatalogRecovery.restore`, `-wal` and `-shm` sidecars are moved aside **before** the main file so a stray WAL is never replayed into another database file.
    - New columns added after v3 (`last_activity_at`, `ticket_key`, `opened_by`, `permission_mode`, `model`, `effort`, `run_endpoint`, `parent_session_id`, `forked_at`, `side_first_uuid`, `projects.color`) are added via idempotent `ALTER TABLE` helpers on open without bumping `user_version`.
33. **`loom-run-host` Checks Its Peer on a Thread of Its Own (FB5-12, `owner_check_thread` in `Sources/loom-run-host/main.c`):**
    - `peer_is_owner` calls `SecCodeCopyGuestWithAttributes` and `SecCodeCheckValidity`, and the Security framework logs a runtime-issue fault for such calls on a main thread. The host now runs the check on a `pthread` of its own that the main thread joins before anything is served; a failed check, or a thread that cannot be started, refuses the peer as before. Nothing is served before the answer.
