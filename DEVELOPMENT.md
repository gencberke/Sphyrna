# Loom development guide

How agents build, test, package, verify and measure Loom without hurting the user's machine or each other. Workflow and roles: [AGENTS.md](AGENTS.md). Product limits: [contract](LOOM-PRODUCT-CONTRACT.md). Structure: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Script index: [scripts/README.md](scripts/README.md). Facts below were checked against the code and scripts on 14 Oct 2026.

## 1. Toolchain

- macOS 27, `xcode-select -p` = `/Applications/Xcode.app/Contents/Developer`, Swift 6.4 (arm64-apple-macosx27.0.0); `xctrace` and Instruments exist. Command Line Tools also exist. Verify again before relying on this; versions of provider CLIs are never pinned.
- Macro plugin workaround: not needed with Xcode selected (7 Oct 2026, `scripts/check.sh --suite LoomLaunchOptionsTests`, a plain `swift test --filter` without the flag, 5/5 passed). Only if `swift test` cannot find the Testing macro plugin (for example with only the Command Line Tools selected), pass `scripts/check.sh --macro-plugin <libTestingMacros.dylib>` (it appends `-Xswiftc -load-plugin-library -Xswiftc <dylib>`). The CLT copy is `/Library/Developer/CommandLineTools/usr/lib/swift/host/plugins/testing/libTestingMacros.dylib`; the Xcode copy sits under `/Applications/Xcode.app/Contents/Developer/Toolchains/XcodeDefault.xctoolchain/usr/lib/swift/host/plugins/testing/`.
- C code (`CLoomPOSIX`, `CLoomTestSupport`) must be clean under `clang -Wall -Wextra -Werror`; after `fork` only async-signal-safe calls.

## 2. Build and test

- Always give your own scratch path and keep it outside `~/Documents`: `scripts/dev-paths.sh` provides `loom_scratch_path` (`$LOOM_SCRATCH_PATH`, default `~/Library/Caches/loom-dev-build`) and `loom_refuse_documents` (exit 2). Release builds run `dsymutil`, which blocks on a Documents consent prompt (TCC); packages, fixtures and scratch under `~/Documents` break run hosts the same way.
- Routine change: `scripts/check.sh [--suite <Suite>…] [--scratch <mine>]` (or `LOOM_SCRATCH_PATH`; there is no CI). Default: `git diff --check`, `git diff --cached --check`, trailing whitespace in untracked files (which `git diff --check` skips), `zsh -n` on `scripts/**/*.sh`, `py_compile` on `scripts/**/*.py` (bytecode goes to a temp dir), `clang -Wall -Wextra -Werror -fsyntax-only` on the C sources, the theme-literal guard (`check-theme-literals.sh`: no colour, font-size or radius literal in `LoomCatalogUI` outside `LoomTheme*.swift`, and no panel-family token (`Surface.panel`, `panelNS`, `canvas`, `inspector`, `card`, `raised`, `popover`) kept in a `static let`; it follows the main pane's tone, so inside `LoomTheme*.swift` such a token is a `static var`), the wording guard (`check-user-wording.sh`: user-visible string literals in LoomCatalogUI and loom-app say "session", never "conversation"; exceptions in `check-user-wording.allow`), then `swift build --scratch-path <mine>`. `--suite <Name>…` adds `swift test --filter` per name (targets: LoomCoreTests, LoomChatTests, LoomTerminalTests, LoomCatalogUITests, LoomLaunchOptionsTests, or any suite or test name); `--tests` runs every target. The four window tests (`byteQuotaCoversRasterRounding`, `layerBackingStorePreservesPixelsOutsideTheDirtyRect`, `hostedWorkingIndicatorRunsOnlyWhenTheEnvironmentAllowsIt`, `realSidebarRunsAWorkingRowOnlyForAnActiveWindowAndExpandedSidebar`) are skipped unless `--windows --idle`. It prints one line per check, the "N tests passed" line and a verdict, logs to `~/Library/Caches/loom-check-logs/`, and exits 0 pass, 1 a check failed, 2 usage or refusal, 3 build slot timeout. Docs-only: links, consistency, whitespace (`scripts/check.sh` covers the whitespace).
- Build slot: every swift build, test, package and measurement runs as `scripts/with-build-slot.sh <command…>` (`check.sh` does this itself): one `lockf -k` lock (`LOOM_BUILD_LOCK`, default `~/Library/Caches/loom-run1/build-slot.lock`, never under `~/Documents`), waits up to `LOOM_SLOT_TIMEOUT` seconds (3600), exit 3 when the slot stayed busy, `<lock>.holder` names the current holder.
- Full suite (checkpoint close or large combined change; about 1,150 tests on 13 Oct): `scripts/check.sh --full --idle` (the checks above plus `swift build -c release`, the staged release-tree build and `swift test -c release --scratch-path <path>`, window tests included; without `--idle` it exits 2).
- Release flavor: `scripts/check.sh --release-tree` exports the promote allowlist from the checked-out tree into `<scratch>-release-stage` with `Package.release.swift` as the manifest, builds it with `swift build -c release`, and fails when the `loom-app` binary carries development-evidence symbols or strings (`LOOM_EVIDENCE` code, §5). `--full` includes it. Tests that open a real window fail with a locked screen.
- A regression test must fail without the fix. Test success is not proof of UI or real-provider behavior.
- The chat budget tests (`ChatDeltaBudgetTests`, `ChatBudgetTests`) print `BUDGET …` lines in the check log. Debug builds can verify the stream's rows after every rebuild (`ChatPresentation.verifiesRows`; costly, tests only).
- Process-heavy suites (supervisor, runtime, run scope, shutdown, session deletion, launch choices, the Chat driver and its view) carry the `.processHeavy` trait (`Tests/<target>/ProcessHeavyGate.swift`, one copy in each of `LoomChatTests`, `LoomCoreTests` and `LoomCatalogUITests`; keep the three identical). It takes a lock file named after the test process, so these suites run one at a time across targets; others still run side by side.
- The fake provider's Chat mode (`loom-fake-provider`, `ChatEngine.swift`) reads `LOOM_FAKE_CHAT_DELAY_MS`, `LOOM_FAKE_CHAT_CAPABILITIES`, `LOOM_FAKE_CHAT_INIT` (`silent`: never answers `initialize`; `exit`: one stderr line and exit 1; `exit-on-resume`: only a resume does that) and `LOOM_FAKE_CHAT_IGNORE_INTERRUPT=1` (an interrupt is answered, the turn goes on). Scenarios are sent as `/scenario <name>`; `api-retry [n] [error]` writes `n` (default 2) `system/api_retry` records, error `overloaded` by default, then an answer. Request scenarios (V18): `approval <variant>` (`edit`, `write`, `web`, `mcp`, `redirect`, `bare`, `long`), `approvals [n]` and `orphan [resolve]`. The fake accepts a live change to `bypassPermissions` only when launched with `--allow-dangerously-skip-permissions`, as the CLI does. It mirrors the CLI's permission layers (V24, `ChatPermissions.swift`: `set_permission_mode`, `apply_flag_settings`, `list_permission_rules`, `dontAsk` refusals) and refuses an `outputStyle` that no `--plugin-dir` provides. More scenarios: `file <name> <text>` (a Write), `run <command>` (a Bash call; `mkdir` and `touch` take effect), `web WebFetch|WebSearch` and `bg-agent [ms]` (a background Agent whose end starts a turn that tries to write), each decided by the rules in force. `flood [n]` sends n small assistant rows at once (default 1,000) with no transcript, then an answer. `stream <seconds> <chars/s>` (`ChatStreamScenario.swift`) is the Chat stream cost cells' load: Markdown text deltas at that rate for that time (a fixed seed, paced by the clock; paragraphs, headings, lists, fenced code), a Read or Bash tool call every 3–5 s of text, then a normal result; `scripts/perf/chat_stream_rate_check.py --fixtures <dir>` checks its rate without the app. More environment: `LOOM_FAKE_CHAT_USER_RULES` (a JSON list of `{behavior, source, rule}` the user's own settings hold), `LOOM_FAKE_CHAT_FAIL_MODE` (a comma list of modes `set_permission_mode` refuses), `LOOM_FAKE_CHAT_FAIL_ASK_RULES=1`, `LOOM_FAKE_CHAT_RESET_FORGETS_SETTINGS=1`, `LOOM_FAKE_CHAT_FAIL_PICKS` (a comma list of `model` and `effort`: those live picks are refused), `LOOM_FAKE_CHAT_RESET_ORDER=init-first` (on `/clear` the init comes before the SessionStart hook; by default the fake sends the real CLI's order, with a decoy `new_conversation_id` in the reset as the CLI does), `LOOM_FAKE_CHAT_INIT_DELAY_MS` and `LOOM_FAKE_CHAT_CONTROL_DELAY_MS` (slow answers, for races). The fake's terminal mode answers `/idle-prompt` with a turn and then Claude's own `idle_prompt` reminder: the session rests at its prompt and asks for nothing.
- Test rigs: `LiveRig.make(environment:)` (LoomCatalogUITests) runs the app's runtime against the fake provider and passes `environment` to it, so a test sets the `LOOM_FAKE_CHAT_*` flags; the driver tests' `Rig.make(environment:version:plugin:)` (LoomChatTests) does the same, and `plugin: false` is a Loom that cannot write its plugin folder.
- Flaky tests, triaged before the Release B gate: the Chat driver, handover and composer tests, the Codex runtime tests and the run-scope tests wait for a state instead of the clock (a Stop held open at its `leave` hook, a handover parked at its hold), and `RunScopeTests`, `SessionRuntimeCodexTests` and `SessionRuntimeCodexRecoveryTests` carry `.processHeavy`. One cause was in the product: in a run scope, a shell that ended before it was registered failed the terminal's environment capture ("Environment shell identity unavailable"). `OpenSessionTests` and `DiagnosticsExportTests` had no flaky test. Still open: `SidebarStatusTests.hostedWorkingIndicatorRunsOnlyWhenTheEnvironmentAllowsIt` (a window test) waits for its view now but has not run since the change (`--windows --idle`); `RunScopeTests.quitDrainsAdversarialChurnWithoutTouchingOutsideProcesses` can fail when the CPU is starved, because the Quit drain is bounded in time; `ChatDeltaBudgetTests.aDeltaCostsTheNewestTurnNotTheTranscript` is a timing ceiling that load can cross (the Chat stream's performance work).
- Real-Claude smoke for the Chat driver (V16; four short Haiku turns, one approval interrupted, a Stop and a resume; prints phases and counts only): `LOOM_V16_REAL_CLAUDE=1 LOOM_V16_CLAUDE_CONFIG=<isolated, logged-in profile> LOOM_V16_WORK_DIR=<perf_paths.real_work_dir()> scripts/check.sh --suite RealClaudeSmokeTests`. Without `LOOM_V16_REAL_CLAUDE=1` it does not run. The child needs `USER` in its environment (the test passes it, as the app's launch environment does), or the CLI does not find its login. It spends real turns: record them (§4).
- Real-Claude acceptance for Release B, driver level (checks 1 to 8: the uuid join, an approval, a question and a plan, an interrupt with a queued message, `stop_task`, Full access live, Ask, `/clear`; about 17 Haiku turns; phases, counts and key names only): `LOOM_ACC_REAL_CLAUDE=1 LOOM_ACC_CLAUDE_CONFIG=<isolated, logged-in profile> LOOM_ACC_WORK_ROOT=<a folder outside HOME whose subfolders the suite names exist and are trusted in that profile> LOOM_ACC_DIR=<evidence folder> scripts/check.sh --suite RealClaudeAcceptanceTests`. Without `LOOM_ACC_REAL_CLAUDE=1` it does not run. Each test is a check with its own runtime and child: `a8` checks that one `/clear` makes one move and two cards, and `a2b` that a refused tool reads Denied. The app-level checks 9 to 13 are `scripts/perf/release_b_accept.py` (scripts/README); `b12` also checks that the sidebar shows two rows and the journal one `chat.moved`.
- Tests remove what they create: their temporary folders when the test ends, and a run host they assembled (`RunScopeLauncher.assembleOwnedBundle`) through `RunScopeLauncher.removeOwnedBundle(in:)`, which also drops the LaunchServices record that launching it through `open` made (the record outlives the folder).
- Evidence of a run: command, result, run id, file path; never tokens, credentials or environment values. Durable evidence lives under `~/Library/Application Support/Loom-Dev/probe/` or value-free `plans/experiments/`.

## 3. Test and heat policy (user decision 6 Oct 2026, renewing 4 Oct)

The Mac is fanless and overheats. Therefore:
- No parallel builds or tests. Exactly one agent owns and runs the full suite for a combined change; separately passing slices prove nothing about integration.
- Implementers run only `scripts/check.sh` (build and whitespace/syntax checks) and short narrow tests (`--suite`).
- Heavy measurements, release suite runs and screen-flashing UI/window tests only when the user says the computer is idle and the Loom window may stay on screen. Screen unlocked, no concurrent build, Terminal windows out of the way, power adapter plugged in.
- 90 s cooldown between heavy cells.

| Without asking | Only when the user says the Mac is idle | Only when the user asks |
| --- | --- | --- |
| `swift build` with your own scratch path, `git diff --check`, short narrow `swift test --filter` on suites that open no window (LoomCatalogUITests and LoomTerminalTests contain window tests: run them only when idle), `py_compile`/`zsh -n`, reading and grep | full release suite, packaging, any `cp5-*`/`perf/*` runner that opens a window or measures, screen-flashing window tests (short real-Claude turns inside these are pre-authorized, D-04) | long or costly model budgets, anything touching user apps or data, commits, pushes, PRs |

Builds are serialized: only the agent whose Brief says it holds the build slot builds at a time; the planner-reviewer hands the slot out. Scripts that use the repo-local `.build` (`cp5-c-observer-smoke.py`) count as builds and need the slot.

## 4. Isolation

- The real `~/.claude`, `~/.codex`, running sessions and ChatGPT.app are read-only and never test data. Use isolated profiles: `CLAUDE_CONFIG_DIR` = `~/Library/Application Support/Loom-Dev/probe/claude-config`; Codex home `~/.loom-dev/codex-home` (Darwin `sun_path` limit).
- Never replace, modify, kill or test with the user's installed `~/Library/Application Support/Loom-Dev/app/Loom Dev.app`, and never run tests while the user's own instance is running. Tests use a dedicated package: the single build owner runs `scripts/package-dev-app.sh ~/Library/Application\ Support/Loom-Dev/packages/<name>` and Briefs name that package; the perf runners require `--app` and refuse the installed app. Never point anything at the default dev catalog `~/Library/Application Support/Loom-Dev/catalog.sqlite3` (size/mtime must stay unchanged; a synthetic-polluted copy is kept as `catalog-backup-20261005-synthetic`). Package experiments into a separate directory, e.g. `Loom-Dev/packages/<name>`.
- Dev data layout, `~/Library/Application Support/Loom-Dev/`: `catalog.sqlite3`, `ui-preferences.json`, `app/`, `packages/` (test packages), `probe/` (profiles, `runs/`; real-Claude work dirs are not here, see §4), `runs/`, `signing/`. `~/.loom-dev/`: `scopes/` (run-host sockets), `h-*.sock` (hook sockets), `codex-home`. Tests must not clean other agents' or earlier evidence.
- Production identity (built by the clean loom tree's `build.sh`, §10): bundle `local.loom.desktop`, data `~/Library/Application Support/Loom`, sockets `~/.loom`. Dev bundle: `local.loom.desktop.dev` ("Loom Dev").
- Real provider tests: Claude only. Codex is paused and not in the first production release (user decision 6 Oct 2026). Short real-Claude turns for acceptance are pre-authorized (2 Oct decision); large budgets (long autonomous tasks, many repeats, costly models) need the user. Record the number of turns spent.
- Real-Claude work dirs live outside `HOME`, under `/private/tmp/loom-real/` (`perf_paths.real_work_dir` creates one and trusts it in the isolated profile; every real-Claude script uses it). Claude Code loads the `CLAUDE.md` of every ancestor folder of its working directory as project memory, also with an isolated `CLAUDE_CONFIG_DIR`, so a work dir under `HOME` (the old `probe/workspace`) loads the user's real `~/.claude/CLAUDE.md` into the probe (v2 spike S0). To see which memory files a run loaded, read its transcript (`<profile>/projects/<folder>/<session id>.jsonl`): an `attachment` record of type `instructions` lists them in `files[]` (`path`, `type`, `content`), and a run that loaded none has no such record. Check with paths only, never print `content`; prove the check with a positive control first (a marker in `X/.claude/CLAUDE.md`, work dir `X/work`, both under `/private/tmp`). Checked 17 Oct 2026 with Claude Code 2.1.300 and 2 Haiku turns: the control listed the marker file as `Project`, a run in `/private/tmp/loom-real/workspace` listed nothing.

## 5. Evidence mode

`Loom Dev --evidence <dir>` is acceptance tooling that drives the same model actions as the user and writes JSON state into `<dir>`. It exists only in the development flavor: `Sources/loom-app/Evidence/` is compiled when the dev manifest's `LOOM_EVIDENCE` define is set (`loom-app` in `Package.swift`); the release flavor (clean loom tree, built from `Package.release.swift`) contains none of it, and `--evidence` there does nothing beyond the data-root isolation rule below.
- Data root is always isolated: `--data-root <path>` if given, else `<dir>/data`. `--data-root` without `--evidence`, or a flag without its value, refuses to open the catalog (`LaunchOptions.resolveDataRoot`).
- The `--fake-providers` toolchain's `--help` text (`AppDelegate+Evidence.swift`) must list every flag Loom gates on (`--permission-mode`, `--model`, `--effort`, `--name`, `--plugin-dir`, besides `--settings` and `--session-id`): a flag the help does not list is left out (`--effort`, `--name`, `--plugin-dir`) or refuses the start (`--permission-mode`, `--model`), and the run no longer tests what it claims.
- Evidence-only flags (ignored or absent without `--evidence`): `--fixture <argv…>` (first terminal), `--fake-providers <dir>` (dir with `loom-fake-provider`; unredacted evidence), `--claude-config <dir>`, `--codex-home <dir>`, `--evidence-tokens a,b` (token presence in screen text; real-provider evidence stays redacted and `screenshot` is disabled), `--evidence-transparency glass|opaque` (sets the sidebar style Glass | Solid in the isolated data root), `--metal` (dev renderer only; product is Core Graphics), `--fake-toolchain-delay <s>`, `--fail-first-quit`. Environment: `LOOM_FORCE_SCOPE_FAILURE=1` (missing run host); with `--fake-providers`, `LOOM_FAKE_NO_CLAUDE=1` (the Claude toolchain fails as on a machine without the CLI, so Home shows its first-run state) and `LOOM_FAKE_USAGE*` (read by the fake provider's plan-limits answer; the app passes them on from its own environment).
- Command channel, one per instance: distributed notification `local.loom.desktop.dev.command.<first 16 hex of sha256(realpath(dir))>`, object = command string. Send with `source scripts/dev-paths.sh; loom_send_command <dir> '<command>'`; read results from `<dir>/state-<label>.json` etc. Launch through LaunchServices (`open -n -a <app> --args --evidence <dir> …`) for acceptance runs; `cp5-d-measure.py` execs the binary directly unless given `--launch-services`; `perf/run-final-matrix.py` does not pass that flag, so the CP5 matrices were measured with direct exec.
- An evidence script quits its own app however it ends: a `trap` on EXIT sends `quit`, then the script waits for that instance's process to exit (`pgrep -f -- "--evidence <dir>"`) and kills that PID if it is still alive after about 10 s. Set the trap at the script's top level, never inside a function: zsh fires a function's EXIT trap when the function returns, so the app quits as soon as that function returns. A script stops at its first failed step. Delete `<dir>` only after its app has exited. (18 Oct: an app whose script failed midway, and whose folder was deleted right after a hand-sent `quit`, stayed open for an hour.)

## 6. Packaging

`scripts/package-dev-app.sh [output-dir]` (default `Loom-Dev/app`): release-builds the four products with `loom_scratch_path`, assembles `Loom Dev.app` (+ `LoomRunHost.app`) in a temp dir next to the target, signs, verifies (`codesign --verify --deep --strict`, owner requirement), then swaps. Exit 2 if the output is under `~/Documents`; exit 3 if anything runs from the target app (quit it first; never kill the user's app). `CFBundleVersion` is the commit count (`git rev-list --count HEAD`; LaunchServices needs a number) and `LoomRevision` the short commit (shown in About and diagnostics); neither reflects uncommitted changes, so identify packages by SHA of the binary. `LSApplicationCategoryType` is developer tools, as in the release.
- Identity: `LOOM_CODESIGN_IDENTITY` (name or SHA-1, `-` = ad-hoc), else local `Loom Dev Code Signing`, else the first `Apple Development`/`Developer ID Application` identity, else ad-hoc. Ad-hoc loses TCC grants (Documents prompts return) and the run host can only check Loom's identifier. The script prints the chosen signing. Do not create certificates per build; the private key stays out of repo and logs. Signing blocks while the screen is locked.
- Changing bundle id, signer or install path invalidates earlier TCC consent ([evidence](plans/experiments/cp5-stable-signing.json)).

## 7. Measurement method

Contract [§10](LOOM-PRODUCT-CONTRACT.md#10-resource-and-performance-acceptance) defines the budgets. Loom, providers and WindowServer are judged separately; CPU says nothing about GPU.
- Load: realistic, repeatable; keep synthetic and real-provider results apart. Record duration, input, warm-up, repetitions, command. Comparative claims need at least five runs, median and spread, in absolute units compared against noise; the 3-run `perf/run-final-matrix.py` is a regression check against the baseline, not a comparative claim.
- CPU: `proc_pid_rusage` (user+system) over the sample window, summed over app, fixture and run-scope hosts (`scripts/cp5-d-measure.py`; an unreadable scope member invalidates the cell). Alternate with a reference package (A/B/A/B), 90 s cooldown, frozen input hashes. Tools: `top -l`, `ps`, `sample`, `vmmap`, `xctrace`.
- Conditions: Loom window visible and not covered (the scripts never raise it), screen unlocked, nothing else building or testing. The visible-window cells of the performance matrix need the window uncovered: during the Release A run the Claude desktop app covered it and made the first attempt invalid. Bring Finder to the front first (`open -a Finder`) and check that the window is not occluded. Known limit: `scripts/perf/indicator_cost.py` launches the app without activating it, so its first cells can run occluded; activate the app first.
- Runners: `scripts/perf/run-final-matrix.py`, `indicator_cost.py`, `claude_real.py` (see scripts/README.md). Output goes to a run dir under `~/Library`.
- Chat stream cost (Release B): `scripts/perf/chat_stream_cost.py` (visible, `--hidden`, `--sessions N`, `--long`) samples a fake-provider Chat stream with the matrix sampler: the app, the total with the Chat sessions' children, idle wakeups and footprint. Its terminal counterpart is `cp5-d-measure.py --scenario stream600|stream6000`. A visible cell brings Finder to the front inside the same build-slot call, so no window covers Loom while the slot waits.
- Judging a matrix run: `scripts/perf/compare_baseline.py <run-dir> [--baseline <json>]` pairs the reference and candidate cells and exits 1 on a regression gate (stream1 total >= 40 %, candidate stream1 app median above the reference median + 1.5 points or, without a reference, above the baseline max + 1.5, spinner1 median above the baseline max + 2.5, hidden stream1 app above the baseline + 1.0, latency p95 median above 25 ms, any invalid cell). The thresholds are this run's regression gates, not product budgets (O-01 is open). `--self-test` checks it on synthetic runs built from the baseline JSON.
- Baseline, package I, Core Graphics, CPU % of one core ([data](plans/experiments/cp5-final-matrix-I-20261006.json)): stream1 1 MiB/s visible app 23.8-24.0 (total 25.4-25.6; CPU40 passes), spinner1 12.6-14.7, stream1 hidden 3.5, input-to-draw p95 about 20 ms, working indicator under reduced motion about 0.005 (idle wakeups near 0), idle observer with one real Claude 0.044.

## 8. Swarm rules for the shared tree

Flow: finish and verify a release in loom-dev (full suite, real-Claude check, perf baseline), tag it `release/<version>`, then run `scripts/release/promote.sh <version> <loom-tree-path>`, push it to GitHub, build, and attach the built app to the GitHub release (Publish below). Rolling back means rebuilding an earlier `v<version>` in loom.

- **Promote** (`scripts/release/promote.sh`, light: no build): exports a fixed allowlist (`scripts/release/allowlist.sh`, shared with `check.sh`; it excludes `Sources/loom-app/Evidence`) from the tag with `git archive` (never the working tree) into a temp dir, generates the release `Package.swift` (from `scripts/release/Package.release.swift`; promote fails if its target declarations differ from the tagged dev manifest; the one dev-only setting, `.define("LOOM_EVIDENCE")` on `loom-app`, is stripped before the comparison), `build.sh` (a copy of `scripts/release/build-loom.sh`), `README.md` (from `scripts/release/README.release.md` with `@VERSION@` filled in; promote fails on a leftover placeholder or on a picture the README shows that the release lacks), `LICENSE` (from `scripts/release/LICENSE`, MIT), `VERSION` and `.gitignore`, rejects any path outside the allowlist, then replaces the loom tree's content (keeping `.git`), commits `Loom <version> (from loom-dev release/<version> <short-sha>)` and tags `v<version>`. Allowlist: `Package.resolved`, `THIRD-PARTY-NOTICES.md`; `Sources/{CLoomPOSIX,LoomCore,LoomTerminal,LoomCatalogUI,LoomChat,LoomLaunchOptions,loom-app,loom-run-host,loom-hook}`; `Vendor/SwiftTerm/{Package.swift,LICENSE,Sources,Plugins,swifterm-terminfo}` without `Sources/SwiftTerm/Documentation.docc`; `assets/Loom.icns`, `assets/harness/harness-{claude,codex}.png`, `assets/readme` (the README's pictures; not bundled into the app). Refuses (exit 1, nothing written): missing tag; a loom path equal to, inside or containing loom-dev, or nested in another git repository; a non-empty directory that is not a git repository; uncommitted changes in loom; an existing tag `v<version>`. The templates (manifest, build script, README, LICENSE) come from the tag too, so a release is reproducible from its tag alone; commit them before tagging.
- **Build** (`build.sh` in the loom tree, heavy: release build and signing, run only when the user says the Mac is idle): release-builds `loom-app`, `loom-hook`, `loom-run-host` into `~/Library/Caches/loom-release-build` (`LOOM_SCRATCH_PATH`), assembles `Loom.app` (`local.loom.desktop`, executable `Loom`, `CFBundleShortVersionString` from `VERSION`, `CFBundleVersion` from `VERSION` as major × 10000 + minor × 100 + patch (0.4.4 is 404; it only grows, whatever the tree's history), `LoomRevision` its short commit, `LSApplicationCategoryType` `public.app-category.developer-tools`, `loom-hook` beside the executable, `THIRD-PARTY-NOTICES.md` in `Contents/Resources` (the build fails without it), `LoomRunHost.app` as `local.loom.desktop.run-host` with a `LoomOwnerRequirement` of identifier plus signing-certificate leaf; no `loom-test-child`), signs with `LOOM_CODESIGN_IDENTITY` or the local `Loom Dev Code Signing` identity (ad-hoc refused), runs `codesign --verify --deep --strict`, and swaps the bundle into `/Applications/Loom.app` (`--target <path>` or `LOOM_INSTALL_PATH` for tests). Exit 2 for a target or scratch under `~/Documents` or bad arguments; exit 3 while Loom runs from the target; it also refuses a dirty tree. `./build.sh --check-only` validates arguments, tree, identity and the running check without building. It duplicates the assembly of `scripts/package-dev-app.sh` (standalone by design); keep the Info.plist layout of the two in step.
- **Publish** (user decision [D-56](DECISIONS.md), 14 Oct 2026): the loom tree is public at https://github.com/gencberke/loom under the MIT license. Its `main` starts at 0.4.4 as one root commit; the earlier promote commits and the tags `v0.1.0` to `v0.4.3` stay only in the local loom tree, on the branch `history`, for rollback, and are never pushed. The loom tree's own git config commits with the GitHub noreply address. After a promote: `git -C <loom> push origin main v<version>`, naming the new tag (never `--tags`). After `build.sh` and its checks: `ditto -c -k --norsrc --noextattr --noqtn --keepParent /Applications/Loom.app <dir>/Loom-<version>.zip` (without these flags the `com.apple.provenance` attributes of the built files land in the zip as `._` entries, which break the signature when the zip is opened with plain `unzip`), check that a copy extracted with `unzip` passes `codesign --verify --deep --strict`, then `gh release create v<version> <zip> --repo gencberke/loom --title "Loom <version>" --notes-file <notes> --latest`. The zip is signed with the local identity and not notarized (D-47); the README tells downloaders how to clear the quarantine flag.
- **README pictures**: sources in `design/readme/*.html`, cut from the design previews with neutral sample data (never the user's real projects, branches or tickets), rendered by `scripts/release/readme-shots.sh` (headless Chrome with a throwaway profile, light, no window) into `assets/readme/`. Commit both after a change.

Rules: the daily `Loom.app` and its data are user data like the installed `Loom Dev.app` — never test material. Evidence code is compiled only into the development flavor of `loom-app` (`LOOM_EVIDENCE`, directory `Sources/loom-app/Evidence/`); `scripts/check.sh --release-tree` (part of `--full`) exports the allowlist from the checked-out tree, builds it with `Package.release.swift` and fails when the binary carries `DevelopmentEvidence`, `EvidenceResourcePool` or the evidence-only flags, so the release flavor keeps building. ## 11. Logs and diagnostics

Loom logs through unified logging, subsystem `local.loom.desktop`, one category per area: `Lifecycle`, `Catalog`, `ClaudeHooks`, `Registry`, `Toolchain`, `Scope`, `Usage`, `Recovery`, `Quit`, `Diagnostics`, and `HookClient` (the `loom-hook` helper). Notice and error entries are state transitions and failures; per-event detail is `debug`. Entries carry ids, counts, durations and error categories, never prompts, messages, titles or transcript text; user paths are private. Loom keeps no log files of its own.

```
/usr/bin/log show --last 1h --info --debug --predicate 'subsystem == "local.loom.desktop"'
/usr/bin/log show --last 1h --predicate 'subsystem == "local.loom.desktop" && category == "Catalog"'
/usr/bin/log stream --level debug --predicate 'subsystem == "local.loom.desktop" && category == "ClaudeHooks"'
```

Rare events also go to `<data root>/diagnostics/journal.jsonl` (rotated at 512 KB to `journal.1.jsonl`, two files kept): launch and quit summaries, `claude_cli` (version, detected options), `cli_compat_warning`, `hook_silence`, recovery, catalog backup and restore. One JSON object per line, so `jq -c . <data root>/diagnostics/journal.jsonl` reads it.

`SessionRuntime.collectDiagnostics(to:)` writes a folder with `summary.json`, the journal files and `log.ndjson` (last 24 h of the subsystem from processes inside the running app's bundle only, at most 5 MB). It is built for sending to the developer: no session content, home paths shortened to `~`. At most 3 exports are kept under `<data root>/diagnostics/exports/`. Tests use temporary data roots only; the real `log show` is not run by tests (a stand-in executable is).
