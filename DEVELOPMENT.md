# Loom development guide

How agents build, test, package, verify and measure Loom without hurting the user's machine or each other. Workflow and roles: [AGENTS.md](AGENTS.md). Product & behavioral specification: [SPEC.md](SPEC.md). Structure & UI code index: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Script index: [scripts/README.md](scripts/README.md). Its scripts, paths, environment variables and test names were checked against the code on 22 Oct 2026.

## 1. Toolchain

- macOS 27, `xcode-select -p` = `/Applications/Xcode.app/Contents/Developer`, Swift 6.4 (arm64-apple-macosx27.0.0); `xctrace` and Instruments exist. Command Line Tools also exist. Verify again before relying on this; versions of provider CLIs are never pinned.
- Macro plugin workaround: not needed with Xcode selected (7 Oct 2026, `scripts/check.sh --suite LoomLaunchOptionsTests`, a plain `swift test --filter` without the flag, 5/5 passed). Only if `swift test` cannot find the Testing macro plugin (for example with only the Command Line Tools selected), pass `scripts/check.sh --macro-plugin <libTestingMacros.dylib>` (it appends `-Xswiftc -load-plugin-library -Xswiftc <dylib>`). The CLT copy is `/Library/Developer/CommandLineTools/usr/lib/swift/host/plugins/testing/libTestingMacros.dylib`; the Xcode copy sits under `/Applications/Xcode.app/Contents/Developer/Toolchains/XcodeDefault.xctoolchain/usr/lib/swift/host/plugins/testing/`.
- C code (`CLoomPOSIX`, `CLoomTestSupport`) must be clean under `clang -Wall -Wextra -Werror`; after `fork` only async-signal-safe calls.

## 2. Build and test

- Always give your own scratch path and keep it outside `~/Documents`: `scripts/dev-paths.sh` provides `loom_scratch_path` (`$LOOM_SCRATCH_PATH`, default `~/Library/Caches/loom-dev-build`) and `loom_refuse_documents` (exit 2). Release builds run `dsymutil`, which blocks on a Documents consent prompt (TCC); packages, fixtures and scratch under `~/Documents` break run hosts the same way.
- Routine change: `scripts/check.sh [--suite <Suite>…] [--scratch <mine>]` (or `LOOM_SCRATCH_PATH`; there is no CI). Default: `git diff --check`, `git diff --cached --check`, trailing whitespace in untracked files (which `git diff --check` skips), `zsh -n` on `scripts/**/*.sh`, `py_compile` on `scripts/**/*.py` (bytecode goes to a temp dir), `clang -Wall -Wextra -Werror -fsyntax-only` on the C sources, the theme-literal guard (`check-theme-literals.sh`: no colour, font-size or radius literal in `LoomCatalogUI` outside `LoomTheme*.swift`, and no panel-family token (`Surface.panel`, `panelNS`, `canvas`, `inspector`, `card`, `raised`, `popover`) kept in a `static let`; it follows the main pane's tone, so inside `LoomTheme*.swift` such a token is a `static var`), the wording guard (`check-user-wording.sh`: user-visible string literals in LoomCatalogUI and loom-app say "session", never "conversation"; exceptions in `check-user-wording.allow`), the selectable-label guard (`check-selectable-labels.sh`: no `.textSelection(.enabled)` Text in LoomCatalogUI or loom-app carries its own `.accessibilityLabel`; the label goes on an `.accessibilityElement(children: .contain)` wrapper, [ARCHITECTURE §12.1](docs/ARCHITECTURE.md#121-theme-appearance--swiftuiappkit-rendering-gotchas)), the source guards (`check-source-guards.py`: rules about what `Sources/` may contain, such as D-94's harness questions, Remora's call sites, loggers, keys where cards live, and real input read only through an injected reader) and the test guard (`check-tests.py`, the ratchet of §3.1's standard), then `swift build --scratch-path <mine>`. After a test step the log goes into the test ledger (`scripts/test-ledger.py`; `summary`, `failures`, `flakes`) and the wall time per target and the five slowest tests are printed; they are reported, not gated. Tests run by tier, and a tier is its targets (§3.1): `--unit` runs T1, the area targets (LoomCoreTests, LoomChatTests, LoomRemoraTests, LoomTerminalTests, LoomCatalogUITests, LoomLaunchOptionsTests), the routine slice check; `--integration` runs T2, LoomIntegrationTests; `--tests` runs both, in debug; `--frozen` runs TF, LoomFrozenTests, after them; `--windows --idle` runs T3, LoomWindowTests, in a `swift test` of its own after every other step. `--suite <Name>…` adds `swift test --filter` per name (a target, suite or test name) and never reaches LoomWindowTests; it reaches LoomFrozenTests only with `--frozen`, which then runs the named suites there instead of the whole lane (the opt-in real-CLI suites of the Chat face are there). A window test lives in LoomWindowTests and nowhere else, so a new one cannot open a window during an off-screen run. It prints one line per check, the "N tests passed" line and a verdict, logs to `~/Library/Caches/loom-check-logs/`, and exits 0 pass, 1 a check failed, 2 usage or refusal, 3 build slot timeout. Docs-only: links, consistency, whitespace (`scripts/check.sh` covers the whitespace).
- `--suite` takes swift-testing filter regexes. An anchored `^Target\.Suite$` matches only a suite that carries an explicit `@Suite` attribute: a plain `struct FooTests` is skipped silently, with no failure (22 Oct: `MenuBarTests` and `RemoraReachTests`). Pass the plain suite name, or `^Target\.Suite(/|$)`, and read the log's `✔ Suite …` lines to see that every suite meant actually ran.
- Tier-routing regression: `python3 scripts/check-window-routing.py` exercises the real checker in a temporary fixture with a recording Swift stub. It checks each flag's targets, that `--suite` never reaches the window target (nor the frozen one without `--frozen`), that the window target runs alone and last behind `--idle`, and that `--full` builds no plain release product, without building Swift or presenting a window.
- Build slot: every swift build, test, package and measurement runs as `scripts/with-build-slot.sh <command…>` (`check.sh` does this itself): one `lockf -k` lock (`LOOM_BUILD_LOCK`, default `~/Library/Caches/loom-run1/build-slot.lock`, never under `~/Documents`), waits up to `LOOM_SLOT_TIMEOUT` seconds (3600), exit 3 when the slot stayed busy, `<lock>.holder` names the current holder.
- Full suite (checkpoint close or large combined change): `scripts/check.sh --full --idle` (D-119: the checks above, the staged release-tree build, then `swift test -c release` over T1 and T2, which is the release test build, then T3 in a `swift test -c release` of its own: beside the offscreen suites' windows its clicks, keys and focus do not land; without `--idle` it exits 2). There is no plain `swift build -c release`: packaging builds its products by name, and the release test build compiles everything the gate runs. TF is not part of it.
- Release flavor: `scripts/check.sh --release-tree` exports the promote allowlist from the checked-out tree into `<scratch>-release-stage` with `Package.release.swift` as the manifest, builds it with `swift build -c release`, and fails when the `loom-app` binary carries development-evidence symbols or strings (`LOOM_EVIDENCE` code, §5). `--full` includes it. Tests that open a real window fail with a locked screen.
- A regression test must fail without the fix. Test success is not proof of UI or real-provider behavior.
- The chat budget tests (`ChatDeltaBudgetTests`, `ChatBudgetTests`, LoomFrozenTests: `--frozen`) print `BUDGET …` lines in the check log. Debug builds can verify the stream's rows after every rebuild (`ChatPresentation.verifiesRows`; costly, tests only).
- Shared fixtures live in the `LoomTestSupport` target (`Tests/LoomTestSupport/`, product-free): the bounded waits (`waitFor`, `holds`), `Products.directory` for the built executables, `TemporaryRoot`, the window host (`host(_:size:key:)`, not key unless asked), the accessibility readers (`InkAX`, `axTree`, `accessibilityElements`) and the `.processHeavy` trait. Fixtures that need a product's internals and serve more than one test target live in their area's rig, a plain target that `@testable import`s the products (`LoomCoreTestRigs`, `LoomChatTestRigs`, `LoomRemoraTestRigs`, `LoomCatalogUITestRigs` under `Tests/`); the test files `@testable import` the rig. A suite split across tiers keeps one copy of its fixtures there: its statics and nested types in an enum, its instance helpers in a protocol extension both halves adopt. Only test targets depend on a rig or the support, no product lists one, and `Package.release.swift` names none (`check-tests.py`, rule `targets`). A suite nests only in a type of its own target: a type from another module would put that module's name in the test's id, out of its tier's filter (the Chat-hosted suites' `ChatHosted` namespace is declared in each target that has them). Process-heavy suites (supervisor, runtime, run scope, shutdown, session deletion, launch choices, the Chat driver and its view) carry `.processHeavy`: a lock file named after the test process, so these suites run one at a time within a target (SwiftPM runs each target in a process of its own, one after another); others still run side by side.
- The fake provider's Chat mode (`loom-fake-provider`, `ChatEngine.swift`) reads `LOOM_FAKE_CHAT_DELAY_MS`, `LOOM_FAKE_CHAT_CAPABILITIES`, `LOOM_FAKE_CHAT_INIT` (`silent`: never answers `initialize`; `exit`: one stderr line and exit 1; `exit-on-resume`: only a resume does that) and `LOOM_FAKE_CHAT_IGNORE_INTERRUPT=1` (an interrupt is answered, the turn goes on). `rewind_files` (V21) follows per-message file checkpoints (`ChatCheckpoints.swift`) when `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=true` is in its environment (the Chat spawn sets it): the files its Write tool touched are restored to before the chosen message, and `LOOM_FAKE_CHAT_CHECKPOINTS=off` or `fail` makes the dry run say "File rewinding is not enabled." or a real run answer an error frame; `die` makes a real run restore the files and exit without an answer. The quick question's answer (V22) is scripted by `LOOM_FAKE_CHAT_SIDE_ANSWER` (its text), `LOOM_FAKE_CHAT_SIDE_DELAY_MS` and `LOOM_FAKE_CHAT_SIDE` (`error`: an error frame; `unsupported`: the error of a CLI without the request; `silent`: no answer). The fork route (V22 part 2) is `--resume <parent> --fork-session --session-id <new>` (the help text of a test rig must list `--fork-session`): the fake takes `<new>` as its session id from the first line, copies the parent's uuid-bearing transcript records into `<new>.jsonl` under that id after a `{"type":"mode"}` line, and sends its SessionStart hook with source `fork`. A side chat sends no text that starts with a slash, so a message that starts with `~scenario` is read as `/scenario` (`~scenario approval write` asks for a Write, `~scenario run cut -c1-3 a` for a Bash the fake asks about but `ReadOnlyCommand` allows). So are V23's (`AgentsLiveRealTests.v23ASubagentsRequestNamesTheSubagentAndTheHubCarriesItsAgentId`, and Release C's `v23ForegroundSubagentCarriesItsWordsAndItsAgentIdWhileItsCardWaitsAndItsFolderListsItDone`, whose prompt asks for a foreground subagent; opt-in with `LOOM_V23_REAL=1`, `LOOM_V23_CLAUDE_CONFIG`, `LOOM_V23_WORK`, `LOOM_V23_DIR`, and `LOOM_V23_CLAUDE` for the binary); in the fake, a subagent's request comes from `/scenario subagent [ms] approval`. The fake's `--help` lists `--forward-subagent-text` and, as the CLI does, sends a subagent's text and thinking records (those with `parent_tool_use_id`) on stdout only when it was launched with that flag; it writes them to the subagent's transcript either way and always sends the subagent's tool_use and tool_result records. A test rig with its own fake help text lists the flag where a test needs a subagent's words: the driver tests' `Rig.make(listsForwardSubagentText:)` lists it by default (`LiveRig.make` does not, and no test of it needs the words yet). Scenarios are sent as `/scenario <name>`; `api-retry [n] [error]` writes `n` (default 2) `system/api_retry` records, error `overloaded` by default, then an answer. Request scenarios (V18): `approval <variant>` (`edit`, `write`, `web`, `mcp`, `redirect`, `bare`, `long`), `approvals [n]` and `orphan [resolve]`. The fake accepts a live change to `bypassPermissions` only when launched with `--allow-dangerously-skip-permissions`, as the CLI does. It mirrors the CLI's permission layers (V24, `ChatPermissions.swift`: `set_permission_mode`, `apply_flag_settings`, `list_permission_rules`, `dontAsk` refusals) and refuses an `outputStyle` that no `--plugin-dir` provides. More scenarios: `file <name> <text>` (a Write), `run <command>` (a Bash call; `mkdir` and `touch` take effect), `web WebFetch|WebSearch` and `bg-agent [ms]` (a background Agent whose end starts a turn that tries to write), each decided by the rules in force. `flood [n]` sends n small assistant rows at once (default 1,000) with no transcript, then an answer. `stream <seconds> <chars/s> [fence300|nested-fence]` (`ChatStreamScenario.swift`) is the Chat stream cost cells' load: Markdown text deltas at that rate for that time (a fixed seed, paced by the clock; paragraphs, headings, lists, fenced code), a Read or Bash tool call every 3–5 s of text, then a normal result. A variant puts a long block after every third ordinary one, so the open tail stays one block for long stretches: `fence300` a fenced code block of 300 lines, `nested-fence` a four-backtick fence holding three-backtick fences and paragraphs. The fence still open when the time ends is closed by its own opener (a four-backtick fence by four backticks); `scripts/perf/chat_stream_rate_check.py --fixtures <dir> [--variant fence300|nested-fence]` checks its rate without the app. More environment: `LOOM_FAKE_CHAT_USER_RULES` (a JSON list of `{behavior, source, rule}` the user's own settings hold), `LOOM_FAKE_CHAT_FAIL_MODE` (a comma list of modes `set_permission_mode` refuses), `LOOM_FAKE_CHAT_FAIL_ASK_RULES=1`, `LOOM_FAKE_CHAT_RESET_FORGETS_SETTINGS=1`, `LOOM_FAKE_CHAT_FAIL_PICKS` (a comma list of `model` and `effort`: those live picks are refused; `title` fails `generate_session_title` and `titlenull` answers it with no title. Otherwise the fake answers "Fake title: <first three words>" and writes an `ai-title` record when `persist` is true, after `LOOM_FAKE_CHAT_CONTROL_DELAY_MS`), `LOOM_FAKE_CHAT_RESET_ORDER=init-first` (on `/clear` the init comes before the SessionStart hook; by default the fake sends the real CLI's order, with a decoy `new_conversation_id` in the reset as the CLI does), `LOOM_FAKE_CHAT_INIT_DELAY_MS` and `LOOM_FAKE_CHAT_CONTROL_DELAY_MS` (slow answers, for races), `LOOM_FAKE_CHAT_TITLE_DEFER=reset` (the first `generate_session_title` is answered only after a `/clear`, right before the next message is taken) and `LOOM_FAKE_CHAT_TITLE_LOG` (a file that gets one line per title request: the subtype, then a JSON object with the description's `length` and the `description` the host sent) and `LOOM_FAKE_CHAT_REQUEST_LOG` (a file that gets one line per `control_request`, its subtype; `ChatModelCallTests` uses it to pin that a Chat session's life makes one model-call request per card, the title). The fake's terminal mode answers `/idle-prompt` with a turn and then Claude's own `idle_prompt` reminder: the session rests at its prompt and asks for nothing.

## 3. Test and heat policy (user decision 6 Oct 2026, renewing 4 Oct)

The Mac is fanless and overheats. Therefore:
- No parallel builds or tests. Exactly one agent owns and runs the full suite for a combined change; separately passing slices prove nothing about integration.
- Implementers run only `scripts/check.sh` (build and whitespace/syntax checks) and short narrow tests (`--suite`). A test run that ends without its passing summary fails (1.6.1): `swift test` can exit 0 when its test process ends in the middle of a test, so `check.sh` reads the output after an exit 0, and every `Test run started.` must be followed by its `Test run with N tests … passed`, with one at least, or the step fails with one line.
- Heavy measurements, release suite runs and screen-flashing UI/window tests only when the user says the computer is idle and the Loom window may stay on screen. Screen unlocked, no concurrent build, Terminal windows out of the way, power adapter plugged in.
- 90 s cooldown between heavy cells.

### 3.1 Test cadence: slices, one pooled batch, fixes, scoped re-checks (D-90, 22 Oct 2026)

Testing must not block development. Comprehensive tests and the optimizer run only when they are needed and enough has collected to be worth the screen time and the heat. The work moves in four steps:

1. **Feature slices.** A slice runs only its own narrow, off-screen checks: `scripts/check.sh --suite <the suites it touches>` and a regression test shown to fail without the fix. What it cannot prove off screen (window tests, visual pairs, hover/focus/VoiceOver passes, app smokes, measurements, real-Claude checks) goes into the test pool as a named item, not into a run of its own: the slice's Report lists it under **Unverified**, and the planner appends it to the pool (the End Batch runbook and the evening queue, [plans/ACTIVE-PLAN.md §4](plans/archive/ACTIVE-PLAN-1.6.0-to-1.7.2.md#4-complete-end-batch-runbook-d-87)). The next slice starts right after review; it does not wait for a heavy run.
2. **Pooled batch.** The pool runs once, as one batch on the integrated head (`v2`), in an idle window the user has given (§3): when several integrated slices have collected, at a milestone or release candidate, or for a concrete risk the narrow checks cannot reach. The full gate (`--full --idle`) is one item of the batch, not a separate run. A failure is recorded with its log and is not chased during the batch; the batch runs on.
3. **Fix slices.** After the batch, each failure becomes a bounded fix slice with its own regression test that fails without the fix.
4. **Scoped verification.** After a fix, only what failed and the fix's own suites run again, never the whole pool. The whole pool or the full gate runs again only for a new release candidate, or when a fix touched shared ground (process ownership, lifecycle, deletion, `Package.swift`, the build or packaging).

**What a test is.** Each test protects a behavior or contract someone relies on, durability (processes reaped, locks, cancellation, deletion, restart and crash recovery, bounded resources), or performance (work counted, or a wall-clock bound with at least 1.5× between the right and the broken mechanism). It lives at the lowest layer that owns the behavior, in a file named by feature, never by round. A regression test fails first, and a rewritten test still catches its defect (break the line, see it fail, record it in the commit). Tests never block the cooperative pool (blocking fixtures run through `onOwnThread`), never share process-wide state or read the Mac's real input state (the owner injects a reader), wait for conditions rather than time with a message that names what they saw, inject time rather than wait out product timeouts, reap every child they spawn, and run in parallel unless the suite says `// serialized: <reason>`. No shortcuts: no wider bound without a measured reason, no retries, no `.disabled`, no weakened assertion. An intermittent failure whose cause is measured and is not a product defect may be quarantined with `withKnownIssue(isIntermittent: true)` and `// flake: <id> <date> <cause>` for 14 days at most. `scripts/check-tests.py` counts what the tests still break against `check-tests.allow`; counts only fall.

**Tiers.** A test's tier is its target, so a new test cannot forget it. T0 is the guards (no build). T1, unit, is the area targets: models, reducers, parsers, codecs, view models, layout math and offscreen views; no real process, socket, PTY or ordered-in window (`--unit`, the routine slice check). T2, integration, is LoomIntegrationTests: real children (the fake provider, the test child, the run host, the hook server), PTYs, sockets, run scopes, deletion and shutdown on real processes; a suite with one such test lives there whole, so its fixtures keep one home. T3, window, is LoomWindowTests: key, focus, click, hit-test, accessibility and drawing in a shown window, run alone (`--windows --idle`). TF, frozen, is LoomFrozenTests: tests of code D-100 (the Chat face) and D-102 (the art) left unreachable from the product, kept and compiled, run with `--frozen` by a slice that touches the lane's files, at a release candidate as a report, and before any un-freeze. Opt-in suites (real providers, benchmarks, corpora) stay behind their environment switch where they are until the acceptance tier (M10).

The closing `@optimizer` review ([D-06](DECISIONS.md)) follows the same rule: once, when a release or checkpoint closes or a body of integrated slices has collected for review, or earlier only for a concrete structural or resource problem; never per slice.

## 6. Packaging

`scripts/package-dev-app.sh [output-dir]` (default `Loom-Dev/app`): release-builds the four products with `loom_scratch_path`, assembles `Loom Dev.app` (+ `LoomRunHost.app`) in a temp dir next to the target, signs, verifies (`codesign --verify --deep --strict`, owner requirement), then swaps. Exit 2 if the output is under `~/Documents`; exit 3 if anything runs from the target app (quit it first; never kill the user's app). `CFBundleVersion` is the commit count (`git rev-list --count HEAD`; LaunchServices needs a number) and `LoomRevision` the short commit (shown in About and diagnostics); neither reflects uncommitted changes, so identify packages by SHA of the binary. `LSApplicationCategoryType` is developer tools, as in the release.

Both package flavours copy Claude, Codex (including its template), opencode and agy marks; the release allowlist exports the same PNGs. Pi is drawn as the approved boxed glyph. Source-only asset staging can be checked without building or opening an app; actual package/visual verification stays in the idle-window gate.

- Identity: `LOOM_CODESIGN_IDENTITY` (name or SHA-1, `-` = ad-hoc), else local `Loom Dev Code Signing`, else the first `Apple Development`/`Developer ID Application` identity, else ad-hoc. Ad-hoc loses TCC grants (Documents prompts return) and the run host can only check Loom's identifier. The script prints the chosen signing. Do not create certificates per build; the private key stays out of repo and logs. Signing blocks while the screen is locked.
- Changing bundle id, signer or install path invalidates earlier TCC consent ([evidence](plans/experiments/cp5-stable-signing.json)).

## 7. Measurement method

[SPEC.md §12](SPEC.md#12-resource-performance-subscription--context-budgets-d-07-d-83-c) defines the budgets. Loom, providers and WindowServer are judged separately; CPU says nothing about GPU.
- Load: realistic, repeatable; keep synthetic and real-provider results apart. Record duration, input, warm-up, repetitions, command. Comparative claims need at least five runs, median and spread, in absolute units compared against noise; the 3-run `perf/run-final-matrix.py` is a regression check against the baseline, not a comparative claim.
- CPU: `proc_pid_rusage` (user+system) over the sample window, summed over app, fixture and run-scope hosts (`scripts/cp5-d-measure.py`; an unreadable scope member invalidates the cell). Alternate with a reference package (A/B/A/B), 90 s cooldown, frozen input hashes. Tools: `top -l`, `ps`, `sample`, `vmmap`, `xctrace`.
- Conditions: Loom window visible and not covered (the scripts never raise it), screen unlocked, nothing else building or testing. The visible-window cells of the performance matrix need the window uncovered: during the Release A run the Claude desktop app covered it and made the first attempt invalid. Bring Finder to the front first (`open -a Finder`) and check that the window is not occluded. Known limit: `scripts/perf/indicator_cost.py` launches the app without activating it, so its first cells can run occluded; activate the app first.
- Runners: `scripts/perf/run-final-matrix.py`, `indicator_cost.py`, `claude_real.py` (see scripts/README.md). Output goes to a run dir under `~/Library`.
- Remora off in measured and real runs: every launcher in `scripts/perf/` and `scripts/cp5-d-measure.py` calls `perf_paths.seed_remora_off` on its run's data root right before the app starts. It merges `remora {isOn: false, briefMode: whenIAsk}` into the root's `ui-preferences.json`, keeps every other key, and refuses `~/Documents`, the default data roots and a file that is not a JSON object. The app reads that file before its model exists, and Remora's brief stops at Off first, so no cell and no real run makes a Remora call. There is no launch argument for Remora, and an evidence command comes only after launch.
- Chat stream cost (Release B): `scripts/perf/chat_stream_cost.py` (visible, `--hidden`, `--sessions N`, `--long`, and from 1.6.1 `--variant fence300|nested-fence`: the long-block cells `chat-fence300-<rate>` and `chat-nested-fence-<rate>` (visible, one session, C8 of FB5-10), whose record-gap allowance grows by the block's streaming time) samples a fake-provider Chat stream with the matrix sampler: the app, the total with the Chat sessions' children, idle wakeups and footprint. Its terminal counterpart is `cp5-d-measure.py --scenario stream600|stream6000`. A visible cell brings Finder to the front inside the same build-slot call, so no window covers Loom while the slot waits.
- Judging a matrix run: `scripts/perf/compare_baseline.py <run-dir> [--baseline <json>]` pairs the reference and candidate cells and exits 1 on a regression gate (stream1 total >= 40 %, candidate stream1 app median above the reference median + 1.5 points or, without a reference, above the baseline max + 1.5, spinner1 median above the baseline max + 2.5, hidden stream1 app above the baseline + 1.0, latency p95 median above 25 ms, any invalid cell). The thresholds are this run's regression gates, not product budgets (O-01 is open). `--self-test` checks it on synthetic runs built from the baseline JSON.
- Baseline, package I, Core Graphics, CPU % of one core ([data](plans/experiments/cp5-final-matrix-I-20261006.json)): stream1 1 MiB/s visible app 23.8-24.0 (total 25.4-25.6; CPU40 passes), spinner1 12.6-14.7, stream1 hidden 3.5, input-to-draw p95 about 20 ms, working indicator under reduced motion about 0.005 (idle wakeups near 0), idle observer with one real Claude 0.044.

## 11. Logs and diagnostics

Sphyrna logs through unified logging (`LoomLog`, `Sources/LoomCore/LoomLog.swift`), subsystem `local.loom.desktop`, one category per area:

- `Lifecycle`: runs, with a start line (session, face, new, resume or fork) and an end line (reason, exit), and, at debug, one `Terminal resize source=layout|attach cols=… rows=… run=…` line for each size the terminal asks of the program; an app-owned helper run (the Codex usage probe) reads "Helper run … started (codex app-server, …)" with no session ref;
- `Session`: `SessionService`, the outcome of each start, resume, stop, handover, answer and open request, and side-chat retirement;
- `Chat`: the Chat face's driver and host (ready latency, end causes, requests by kind and answer, undecoded output lines);
- `Remora`: one end line per call (kind, model, duration, tokens, outcome or failure kind), the automatic brief's decision and the day's slot;
- `Deletion`: each deletion's start, failed step and outcome, and the resume of interrupted ones;
- `Catalog`, `ClaudeHooks`, `Registry`, `Toolchain`, `Scope`, `Usage`, `Recovery`, `Quit`, `Diagnostics`, `Sidebar` (also a session drag's debug lines: `beginDrag session <id8>`, `endDrag <why>`; and the project reorder's notice lines: `projectReorder start <id8> place <n>`, `projectReorder gap <id8> <gap>`, `projectReorder end <id8> moved|unchanged|cancelled`; ids only), and `HookClient` (the `loom-hook` helper).

The rules, kept by every call site:

- **Levels.** Notice is a state transition or an outcome, error a failure, debug per-event detail. There are no info lines.
- **No content.** Entries carry ids, counts, durations, kinds, outcomes and error categories (`LoomLog.category(of:)`), never a prompt, message, title, question, answer, transcript, tool input, stderr or an error's description. User paths go through `path:` and stay private.
- **Refs.** A line about a session carries `s:` and the first 8 hex digits of its id (`LoomLog.ref(_:)`), and its face where known. Run lines also carry the run's 8-character prefix, and an agent's open request is `r:`. The journal's `chat.*` events carry the same `session` ref, so one `grep s:7c41e0d2` follows a session through an export.
- **Volume.** Nothing is logged per output chunk, frame or keystroke, and nothing above debug per Home show. A failure that can repeat goes through `LoomLog.error(_:key:_:)`, at most once a minute per key.

`LoggingAndJournalTests` guards them: the category list, no `Logger(subsystem:` outside `LoomLog` and the signposts, and no error description or `.detail` inside a log message.

```
/usr/bin/log show --last 1h --info --debug --predicate 'subsystem == "local.loom.desktop"'
/usr/bin/log show --last 1h --predicate 'subsystem == "local.loom.desktop" && category == "Session"'
/usr/bin/log stream --level debug --predicate 'subsystem == "local.loom.desktop" && category == "Chat"'
```

**Retention.**

- **The unified log.** macOS owns it: it keeps notice and error entries in its own store, which is capped by size and rotated by the system. Debug entries are not stored at all. An app cannot give its entries a time limit: Info.plist's `OSLogPreferences` has no such key (`man 5 os_log`).
- **Sphyrna's own files** are kept 3 days (`DiagnosticRetention.maximumAge`, 72 h):
  - the journal drops older entries the first time it is used after launch, and when it rotates;
  - exports older than 3 days are removed at that same first use and at every new export.

Rare events also go to `<data root>/diagnostics/journal.jsonl`:

- launch and quit summaries;
- `claude_cli` (version, detected options) and `cli_compat_warning`;
- `hook_silence`, recovery, and catalog backup and restore;
- the Chat face's `chat.*` events.

It is rotated at 512 KB to `journal.1.jsonl`; two files are kept, and no entry older than 3 days. One JSON object per line, so `jq -c . <data root>/diagnostics/journal.jsonl` reads it.

"Collect Diagnostics…" (the Help menu, or Settings → About) runs `SessionRuntime.collectDiagnostics(to:)`. It writes `<data root>/diagnostics/exports/sphyrna-diagnostics-<stamp>/` (folders of 1.7.0, `loom-diagnostics-…`, are still pruned and aged out), then shows it in Finder. The folder holds:

- `summary.json`;
- the journal files;
- `log.ndjson`: the subsystem's last 72 h at notice and up, from processes inside the running app's bundle only, with a 30 s timeout. Past 5 MB only the newest 5 MB are kept, from a whole entry on: `log show` writes the oldest first, and a report is about the newest.

It is built for sending to the developer: no session content, home paths shortened to `~`. At most 3 exports are kept, none older than 3 days.

Tests use temporary data roots only. They never run the real `log show` (a stand-in executable does). Two read-back tests read the test process's own entries through `OSLogStore(scope: .currentProcessIdentifier)`:

- a failed `SessionService` start writes one `Session` error with its ref;
- a Remora call writes one `Remora` notice at its end.
