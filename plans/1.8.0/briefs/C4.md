# C4: the harness-neutral draft

**Goal.** A new-session draft knows its harness. Its model, effort and mode are a `HarnessLaunchChoices` that every harness
can fill. The last-used store and project presets keep them per harness, and an opened session (`open`) carries them too.
Picking another harness's model switches the draft's harness. This is the data under FEEDBACK-6 FB6-7/8 and FB6-14 step 2;
the panel that edits it is B4.

**Starts after** C2.

**Read.**
- FEEDBACK-6 "FB6-7 and FB6-8 (1.8.0)" ("Beneath it") and FB6-15 (the `open` flags, Full access never an agent's).
- In `v2`:
  - `Sources/LoomCore/NewSessionLaunch.swift` (`ClaudeLaunchChoices`), `ProviderLaunchProfile.swift`;
  - `OpenSessionProtocol.swift`, `OpenSessionCoordinator.swift`, `SessionCatalog+Launch.swift`;
  - `Sources/LoomCatalogUI/NewSessionDraft.swift` (`SessionDraft`), `NewSessionStore.swift`, `DraftPresets.swift`,
    `CatalogModel+NewSession.swift`, `NewSessionComposer.swift`;
  - the mode list (`Chat/LoomTheme+Composer.swift`'s `ModeTone`, DESIGN §3 "Mode tones").
- `grep -rln ClaudeLaunchChoices Sources` lists every user. The frozen Chat code (`LoomChat/Driver/*`) must keep compiling.

**Write set.**
- The `LoomCore` and `LoomCatalogUI` files above, and new `HarnessLaunchChoices.swift` and `HarnessModes.swift`.
- The frozen Chat files only where a type rename forces it.
- `CatalogModel.swift` (the draft region only); their tests; SPEC §3 and §6.5.

**Approach.**
1. **`HarnessLaunchChoices`:** `harness: HarnessID`, `model: String?`, `effort: String?`, `mode: HarnessMode?`. It validates
   against the harness's descriptor: the model a safe token, the effort among the model's `efforts` from C2, the mode among the
   harness's modes.
2. **`HarnessMode`:** Sphyrna's mode names (ask before edits, accept edits, plan, auto, full access) with a per-harness mapping
   in the descriptor. The mapping to flags is D1's and E's; here only which modes exist per harness. A harness without a mode
   offers none.
3. **`SessionDraft`** gets `harness` and `choices: HarnessLaunchChoices`. A draft starts with the project's last-used harness,
   or Claude.
4. **Changing the model** to another harness's model switches `draft.harness`. The effort is retained when the new model offers that level, otherwise it takes that model's valid default or none
   (approved DESIGN §0.5 / D-106; B4 step 4). The mode maps to the harness's supported equivalent or safe default; a cross-harness
   model pick never carries Full access.
5. **Last used and presets** store choices per harness. Migrate stored values:
   - a stored `ClaudeLaunchChoices` reads as Claude's choices;
   - a preset without a harness is Claude's;
   - a file written now still opens in 1.7.2's build (write the old keys beside the new ones, or check that the old reader
     ignores unknown keys, and say which).
6. **`open`** (`OpenSessionInput`) accepts `--harness` beside `--model`, `--effort` and `--mode`. Full access is refused for an
   agent, as today, and the approval card shows the harness.
7. **`ClaudeLaunchChoices`** remains only as the Claude launch profile's internal input, built from `HarnessLaunchChoices`. If
   nothing else needs it, it goes.

**Done when.**
- A draft can hold Claude or Codex choices, and switching the model across harnesses switches the harness with valid effort
  and mode.
- Presets and last-used survive the migration and still open in the old build.
- `open --harness codex --mode bypassPermissions` is refused, and `open` without `--mode` takes the default mode.
- Starting a Claude session from a draft passes the same flags as today (a launch-argument test pins it).

**Checks.** `NewSessionStore` and draft tests, `OpenSession*Tests`, `LaunchContractTests`, `ProviderProfileTests`, new
`HarnessLaunchChoicesTests` (validation, cross-harness switch, migration both ways); then `--tests`.
