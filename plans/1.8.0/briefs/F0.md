# F0: cross-harness child contract (D-111)

Goal: settle the provider-neutral parent/child task contract before expanding F1, using the user's required native-like, multi-round workflow and the T3/Orca evidence.

Owner: planner for the contract; core implementer for the new durable task types/store/coordinator foundation (D-112/D-114). There is no new provider daemon, scheduler or background polling service. Read SPEC9/12, F1, D-111/D-114 and `evidence/r9/reference-harnesses/` reports. The capability ships with1.8.0; D1 supplies verified launch/native identity, D2 supplies provider-reader/deletion parity, and F1 wires the existing runtime/CLI and UI to the task foundation.

Required flow:
1. An explicitly approved delegation creates a stable parent/child task binding with separate application and provider-native identities, selected target harness/model/effort and effective permissions. No parent history is copied implicitly.
2. The parent can query child status on demand, wait for a relevant event, and read the latest bounded completed result/attention request with source turn/run identity. Read-only access is limited to the caller's task; unrelated session history stays outside it.
3. Second and third messages reach the same child session. A retry/delayed receipt cannot create another child, duplicate a turn, answer a stale request or resurrect cancelled work.
4. Completion, failure or parent-input need produces a bounded event/nudge. Define separately the app notification, queued mailbox ownership and any provider turn consuming it. Event-driven wait and explicit reads replace background polling. A wake must stay inside explicit delegation/delivery authority and SPEC12's declared context/call budget.
5. Parent/child permission ceilings and Full-access provenance remain explicit. The initial delegation card approves a named bounded task grant: default3 child input rounds and6 automatic parent wake submissions for1h, with visible limits and explicit renewal. Ordinary peer sends still require approval each time. Read/status/wait/report and app-only notices make no model input; provider consumption has its own receipt. Native permission approvals remain user-only.
6. Task/turn completion and verified process shutdown are separate. Stop, Quit, deletion, /new and provider reconnect revoke/fence the appropriate input/result authority; unresolved ownership/delivery remains visible and retryable.

Done: exact command/wire/receipt shapes and bounds; ownership/provenance and lifecycle state table; safe default for follow-up/wake approval; tests/real acceptance plan for Claude→Codex and Codex→Claude including2–3 turns, status/read/wait, attention, duplicate/late result, cancellation and restart. Keep CLI discovery inside the existing tiny skill/context budget; do not copy multi-KB reference prompts, a shared daemon or general workflow scheduler.

Apply this to F1's implementation brief once D1/D2's actual interfaces are stable. A live model call is not authorized by this plan; parent must reserve every acceptance input in the shared ledger. Current evidence is source-level, not live proof of both directions.

## Reference verdict (29 Oct)

The planner checked the decisive source anchors in `evidence/r9/reference-harnesses/multi-round/REPORT.md`. T3 `recordSubagentFollowup` retains the app child thread and creates a fresh delegated task/run with pending completion delivery for each later attempt. Its result finalizer and question reactor repeatedly notify the parent, with source-run and request deduplication. Orca reuses a terminal/chat through a fresh Task/Dispatch and requires the new IDs for `worker_done` or supervised `ask`. Both support the requested relationship in source; neither report proves a live two-direction, three-round flow or installed/source parity.

Take the stable child and separate round identities. Status/read receipts must name the requested round and may separately report the child's current round; an old result cannot masquerade as the latest one. Completion and parent-input events repeat for later rounds. A provider restart may change PID; recovery must verify the recorded provider-native session rather than silently start another one. Do not promise process retention as session continuity.

Keep cancellation scopes explicit: cancel-round addresses that round and returns already-settled for a completed round; stop-child targets the current child binding and its verified owned run. T3's observed old-task cancellation stops later work on the same child, while Orca's settled-Dispatch stop does not. Add a fake regression where a delayed first-round cancel/result arrives during round two and cannot stop it, overwrite its result, or consume its attention request. Restart/reconnect must also fence old run/request authority.

The source map is complete in `evidence/r9/f0/seam-map/REPORT.md`. Existing global control-token/openedBy metadata is insufficient task-content authority; F1 supplies launch-local scoped caller proofs. Explicit child report/question/reply payloads are authoritative for the round, rather than attributing the latest unrelated transcript answer. Native status, a reported task outcome and verified process shutdown remain distinct. Durable intent/unknown-delivery receipts precede effects and prevent blind retry after restart. The core foundation uses a private indexed store and one actor with bounded event-driven waits; F1 owns wire shapes, discovery and the existing runtime bridge. This introduces no shared daemon, profile edits or unbounded automatic work.
