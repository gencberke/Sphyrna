# F0: cross-harness child contract (D-111)

Goal: settle the provider-neutral parent/child task contract before expanding F1, using the user's required native-like, multi-round workflow and the T3/Orca evidence.

Owner: planner. This is a contract/planning slice, no runtime broker or new background service. Read SPEC9/12, the F1 brief, D-111, and `evidence/r9/reference-harnesses/` reports. The completed capability must ship with1.8.0; D1/D2 provide verified launch/identity and bounded provider-result reads. F1 implements transport and follow-up/wake delivery under the settled contract.

Required flow:
1. An explicitly approved delegation creates a stable parent/child task binding with separate application and provider-native identities, selected target harness/model/effort and effective permissions. No parent history is copied implicitly.
2. The parent can query child status on demand, wait for a relevant event, and read the latest bounded completed result/attention request with source turn/run identity. Read-only access is limited to the caller's task; unrelated session history stays outside it.
3. Second and third messages reach the same child session. A retry/delayed receipt cannot create another child, duplicate a turn, answer a stale request or resurrect cancelled work.
4. Completion, failure or parent-input need produces a bounded event/nudge. Define separately the app notification, queued mailbox ownership and any provider turn consuming it. Event-driven wait and explicit reads replace background polling. A wake must stay inside explicit delegation/delivery authority and SPEC12's declared context/call budget.
5. Parent/child permission ceilings, Full-access provenance and existing open/send confirmation rules remain explicit. Define any task-scoped preauthorization concretely before broadening per-send approval; D-111 alone is not a blanket permission for arbitrary messages or model calls.
6. Task/turn completion and verified process shutdown are separate. Stop, Quit, deletion, /new and provider reconnect revoke/fence the appropriate input/result authority; unresolved ownership/delivery remains visible and retryable.

Done: exact command/wire/receipt shapes and bounds; ownership/provenance and lifecycle state table; safe default for follow-up/wake approval; tests/real acceptance plan for Claude→Codex and Codex→Claude including2–3 turns, status/read/wait, attention, duplicate/late result, cancellation and restart. Keep CLI discovery inside the existing tiny skill/context budget; do not copy multi-KB reference prompts, a shared daemon or general workflow scheduler.

Apply this to F1's implementation brief once D1/D2's actual interfaces are stable. A live model call is not authorized by this plan; parent must reserve every acceptance input in the shared ledger. Current evidence is source-level, not live proof of both directions.
