# C1: the harness catalogue

**Goal.** One place in `LoomCore` describes every harness Sphyrna knows: Claude, Codex, opencode, agy and pi. It says what
each harness is, where it is installed, whether it is On, Off or Not found, and what it can do. Every gate asks it instead of
`switch provider` tables. This is FEEDBACK-6 FB6-13 steps 1–4 and 6 and the optimizer's items 6 and 11. The consumers move in C2.

**Read.**
- FEEDBACK-6 "FB6-13 (1.8.0): the harness catalogue" and "What the code says" for FB6-13; FEEDBACK-7 Q8 of FEEDBACK-6 (Claude
  and Codex on when found, the others off until switched on).
- In `v2`, `Sources/LoomCore/`:
  - `ManagedSession.swift` (the `Provider` enum);
  - `Harness.swift` and `HarnessRegistry`;
  - `HarnessCapabilities.swift`, `HarnessConnections.swift`, `HarnessHealth.swift`, `HarnessSetup.swift`;
  - `ProviderToolchain.swift` (`ProviderToolchainProbe.find`).
- `Tests/LoomCoreTests/HarnessCapabilitiesTests.swift` (the source guard, `dispatchFiles`), `HarnessRegistryTests.swift`.
- `evidence/r6/optimizer/REPORT.md` items 6 and 11.
- For reference: T3 Code `packages/provider-*/src/server/status.ts` (one status module per provider; "not installed or not on
  PATH").
- P1's `SPIKE.md` if it exists (commands, install and sign-in lines for opencode, agy, pi). If not, take those lines from each
  CLI's `--help` and mark them "to confirm".

**Write set.**
- New `Sources/LoomCore/HarnessID.swift`, `HarnessDescriptor.swift`, `HarnessCatalogue.swift`, `HarnessAvailability.swift`.

- The preferences type that stores the connect switch.
- Their tests and the guard test; SPEC §6.7 and ARCHITECTURE's harness section.

Not yours: UI files, `ModelCatalog`, usage, probes and launch profiles (C2, C4, D1).

**Approach.**
1. **`HarnessID`:** a struct backed by a string with static members `.claude`, `.codex`, `.opencode`, `.agy`, `.pi`.
   - An unknown stored value decodes as an unknown harness instead of failing, so a catalog written by a newer build still opens.
   - The stored `ManagedSession.Provider` values (`claude`, `codex`, `synthetic`) keep decoding. Migrate through `HarnessID`, or
     keep `Provider` as a thin alias; pick the smaller change and say which in the report.
2. **`HarnessDescriptor`** (values, no behaviour):
   - id, display name, command name, mark asset name;
   - install, sign-in and doctor commands with a docs URL;
   - the profile folder and its environment variable;
   - the version table (minimum, recommended);
   - capabilities;
   - `onWhenFound` (Claude and Codex true, the others false);
   - `startable` (Claude true; Codex as the build gate says today, opened in D1; the others false until E1–E3).
3. **`HarnessCatalogue.all`** in Connections' order: Claude, Codex, opencode, agy, pi.
4. **`HarnessAvailability`:**
   - found or not by a PATH lookup on the cached terminal environment (`ProviderToolchainProbe.find`); no `--version` run;
   - the three states On, Off and Not found. Not found is Off with the switch disabled;
   - preferences store an explicit map `harness → on/off`; a harness absent from the map takes `onWhenFound`.
5. **Per-harness facts** (optimizer 6) sit beside the capability table in the descriptor. `claudeVersion` becomes `cliVersion`
   (optimizer 11) wherever it is read.
6. **The guard:** widen `HarnessCapabilitiesTests`' source guard to refuse:
   - `provider == .<any>`;
   - `? "codex" : "claude"`-style literals;
   - `HarnessID` comparisons outside the descriptor and dispatch files.

   List the dispatch files the guard allows.

**Done when.**
- The catalogue lists five harnesses with their descriptors. Availability reports On, Off or Not found per harness from PATH
  and preferences.
- A catalog written today opens unchanged; an unknown harness value opens as unknown; a value written now opens in 1.7.2's
  build. Say how you checked going back.
- Behaviour visible today is unchanged: Claude starts; Codex is read only in production.
- The widened guard passes.

**Checks.** `--suite HarnessCapabilitiesTests HarnessRegistryTests` plus new `HarnessCatalogueTests` and
`HarnessAvailabilityTests`:
- found or not, with a fake PATH;
- the switch map and its default;
- Not found disabling On;
- decoding an unknown id.

Then `--tests` per COMMON §4.
