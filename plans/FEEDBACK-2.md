## Research: sessions starting sessions, subagents (12 Oct)

Read-only investigation plus 2 short real-Claude turns (haiku, isolated profile, CLI 2.1.293); notes and payloads in `~/Library/Caches/loom-run1/feedback2/research/` (`NOTES.md`, `t1/`, `t2g/`). The planner checked the captured hook payloads and `meta.json` files.

**Sessions starting sessions.** Claude's own paths do not fit Loom: Agent View (`--bg`, `/bg`, `claude agents`) moves sessions under a launchd supervisor and is refused under `CLAUDE_CODE_DISABLE_AGENT_VIEW` (verified); cross-session messaging only reaches existing sessions; agent teams are experimental and use tmux/iTerm panes; `claude -p` from Bash is headless and invisible. A nested `claude` inherits `LOOM_HOOK_SOCKET`/`LOOM_HOOK_TOKEN` and the run ids but not Loom's `--settings` (hooks, `crossSessionInbound`). The hook socket has one token per app run and no reply channel. An interactive start with a name and a first prompt works: `claude --session-id <uuid> -n "<title>" "<prompt>"` (verified; the title reaches Loom through the terminal title). Candidate: a `loom` command (next to `loom-hook`) with a request/response channel; Loom shows a confirmation (project, title, prompt preview) and starts the session through its own start path, so ownership, hooks and the card stay Loom's. Contract §7: a spawn is new work and needs the user's authorization; a token in the environment is no control (an injected agent can read it), only a decision inside Loom is.

**Subagents.** `SubagentStart` carries `agent_id`, `agent_type` (no description); `SubagentStop` adds `agent_transcript_path` (no success/failure, no tokens); Claude's internal agents arrive with an empty `agent_type` and must be ignored. `<session>/subagents/agent-<id>.meta.json` holds `agentType`, `description`, `requestShape` (foreground/background), `spawnDepth`, `toolUseId` (written about 25 ms after `SubagentStart`); the `.jsonl` holds per-message usage and model. `Stop.background_tasks[]` lists running background subagents with description and type. Loom today drops every event with an `agent_id` (`ClaudeHook.swift:567`, `.childAgent`), does not register the two subagent events, and reduces `background_tasks` to a count. Not available: the parent agent id, the current tool, success versus failure. Unverified: nested subagent layout, hooks fired inside a subagent, a background subagent's permission prompts.

## Plan: a session opens a session (D-40)

Goal: from a Loom Claude session, an agent asks Loom to open a new Claude session (project, title, optional ticket key, first message); the user approves inside Loom; the session is a normal Loom session (own card, terminal, hooks, Stop/Resume) whose card shows its origin (S2). Out: delivering a message into an existing session, queues, MCP, Codex.

Planner decisions (routine, reversible):
- **Command.** No new product: `loom-hook` gains an `open` subcommand. Loom sets `LOOM_CLI` (absolute path of the bundled `loom-hook`) in Claude sessions it starts; outside Loom the variable is absent, so an agent can say the tool is unavailable. Usage: `"$LOOM_CLI" open --title <t> [--ticket <key>] [--project <name|path>] (--message-file <path> | --message -)`. Default project: the requester's.
- **Transport.** A separate request/response control socket next to the hook socket, authenticated with the run token and the caller's `LOOM_SESSION_ID`/`LOOM_MANAGED_RUN_ID`, accepted only for a live run (same rule as hook `staleRun`); message cap 64 KiB; one pending request per requesting session; no retries.
- **Flow.** Validate (existing Loom project; title 1–160 characters). Same project and ticket already has a session (`ticket_key`, else a title starting with the ticket key): reply `exists` (id, title, running or stopped) at once, and Loom shows a card "<ticket> already has a session" with Show Session / Dismiss; nothing is selected without the user. Otherwise Loom shows a confirmation (requesting session, project, title, ticket, message preview) with Open Session / Deny, neither the default action; the command waits up to 90 s and replies `started` (session id), `denied`, or `pending` (the card stays; a later approval still opens it).
- **Launch.** Claude gets `-n <title>` and the message as the first prompt (after the options, guarded against a leading `-`); the catalog title is set to the requested title (automatic, so a rename still wins). `sessions.ticket_key` and `sessions.opened_by` are added inside schema v3 like `last_activity_at`, so 0.3.0 still opens the catalog.
- **Origin (S2).** The card's meta row shows an arrow and "from <requester title>" in place of the branch when both sessions are on the same branch; otherwise the branch stays and the origin is in the tooltip; the detail facts gain "Opened by".
- **Discovery.** After acceptance the planner adds one usage line to the edd and enmusait project cards in the vault (reading the vault's AGENTS.md first).

Slices, in order after item 5 (shared files: `ClaudeHook.swift`, `ProviderLaunchProfile.swift`, `SidebarView.swift`): P1 core (transport, `loom-hook open`, catalog columns, launch arguments, lookup; LoomCore, loom-hook, LaunchEnvironment), P2 UI and wiring (confirmation and exists cards, origin line, detail fact; LoomCatalogUI, loom-app). Acceptance: tests per rule (auth, stale run, size cap, lookup, launch argv, migration with 0.3.0's schema, pending/deny/approve), then 1–2 short real-Claude turns on a dev package with an idle Mac.

## Flaky terminal test (12 Oct, at the user's request)

`TerminalRunControllerTests.repeatedRequestsStartAtMostOneRun(2)` waits on the MainActor with a wall-clock 5 s deadline while other suites of the target run in parallel. Cause this time: `TerminalPartialDrawTests` and `TerminalDirectGlyphTests` compared ~2 MB bitmaps with `zip(...).reduce` on the MainActor in a debug build (~0.25 s per call, every step), holding the MainActor for seconds (`incrementalDrawEqualsFullRedraw` 8.8 s, `identicalRewritesAreNotInvalidated` 2.9 s); the controller test's launch hop waited behind them. Same symptom as CP5 §20.3, different code. Fix, tests only: `Tests/LoomTerminalTests/PixelDifference.swift` (`differingBytes`: `memcmp` fast path, raw-buffer count, a size mismatch counts as different instead of being truncated by `zip`), used at the six call sites; assertions, time limits and the known issue in `droppedDirtyRowIsDetected` unchanged. Evidence: before, a full target run failed 37/38 (log `check-20261012T095849-36786.log`) and the PartialDraw pair slowed the controller test to 12.5 s; after, the pair 0.55 s and 6 consecutive full-target runs 38/38, target time 31 s → about 11.8 s. Not shown: a reliable fail-before/pass-after pairing (the failure reproduced 1 of 1 full runs only). Rule for test authors: no long synchronous loops over large buffers on the MainActor in LoomTerminalTests.
