# Loom v2 directions

Appendix of [V2-BRAINSTORM.md](V2-BRAINSTORM.md). Three independent designers each built one coherent v2 from the [idea catalog](IDEAS.md) under a different stance; a judge scored them and a completeness critic checked the result (17 Oct 2026). These are proposals, not decisions; the planner's own reading is in the main document.

## Loom Cockpit (`cockpit`)

**Thesis.** The real Claude Code terminal stays the centre of Loom. Loom v2 makes everything around it the best attention, context and review instrument for a person who runs 3-6 CLI sessions across two work projects. Every session answers four questions without being opened: Does it need me? Why, in one line? What did it change and what state is it in (context size, branch, PR/CI, plan pace)? What is the one key that acts on it? Loom stays a native host that owns the process, proves outcomes and draws nothing it does not need. It adds read-only views (a Conversation view, a Changes view, the existing subagent panel) and a very small, verified, draft-first send path. It does not add a chat engine, a worktree orchestrator, a browser or a daemon. Anthropic is absorbing the breadth (Desktop diff, side chat, agent view); a light local app can only win on triage, truth and cost. The product rule is: terminal for doing, Loom for knowing, one key to get from knowing to doing. Chat-style rendering is used only where it is read-only or clearly cheaper than a live terminal (idle, stopped and catch-up reading, search results, side questions). Evidence-led escape valve: if the Conversation view becomes the way the user reads most of the time, a composer-led direction is reconsidered in a later round with data, not now.

**A day in the user's life.** 08:40 Berke opens Loom on the Mac. A banner row in the Active area says 'Ended with Loom: 3. Reopen all / Dismiss' (I-21). He reopens the two EDDP-* sessions and dismisses the experiment. The sidebar shows the In work list (I-18) with yesterday's four tickets; two cards carry a ticket chip (EDDP-412, EDDP-415). The footer shows '1.1M today, 5h 22%' with no pace warning.

09:05 He presses Option+Cmd+N, the new-session sheet appears (I-33), the EDDP-415 chip is already offered from recents, preset 'plan + high' is selected, he types the first message and presses Return. The session starts in plan mode. He continues in the real terminal. Keep-awake (I-20) is on, so the Mac does not sleep while it works.

10:30 He is deep in a terminal reviewing a plan. The menu bar badge turns orange. The card of EDDP-412 says under its title 'Bash: git push origin feature/EDDP-412' (I-14) and the Dock badge says 1. He ignores it until his thought ends, presses Cmd+J (next session that needs me), lands in that terminal, reads the real dialog and answers it with the CLI's own keys. The banner for an approval carried the command text too, so he knew it was safe before switching. A second card turns blue: 'Finished, unviewed'. Its second line shows the tail of the last message: '...want me to keep the old endpoint, or remove it?'. He knows it needs a decision, not a read.

11:10 A third session, EDDP-415, is Working for a long run. He opens the right inspector with Cmd+Opt+S and types a question into Ask Aside (I-09): the real CLI forked from that session in plan mode, nested under the card, nothing enters the main thread. While it answers, a long answer is catching up: the header shows 'ctx 412k' and the state pill says 'Working, 2 subagents'. He clicks a subagent row: the existing read-only transcript replaces the terminal in place (unchanged).

12:20 EDDP-412 finishes. The card shows '+120 -8 in 5 files' and a PR token '#482, checks running' (I-28, I-31). He presses the header Changes chip, reads the diff in the right inspector, selects two hunks, writes two comments and presses 'Stage in prompt'. Loom pastes one structured block into the session prompt without pressing Return (I-29 over I-01 draft-only). He looks at the terminal, edits one word and presses Return himself; the card then says 'Delivered' once the hook confirms. He did not use a chat composer; the CLI prompt is still where he types.

14:00 He quits for lunch with two sessions mid-run. Quit stops everything, verified. At 15:00 reopening shows 'Ended with Loom: 2'. A stopped session opens in the Conversation view (I-05): rendered markdown, folded tool rows, readable without a process or live terminal; Resume is one click. He searches 'idempotency' in the sidebar and a section 'In conversations' lists three sessions with a snippet (I-41).

17:40 The footer chip turns orange: 'at this pace the 5-hour window ends around 18:30, resets 20:15' (I-25). He parks the lowest-priority work: Mark Done on two In work items. Cmd+Q: the quit sheet names the Working sessions (I-17). Nothing leaks, nothing polls.

**Design rules and decisions it changes.**

- D-34 (no right sidebar): lifted for exactly one purpose, a collapsed-by-default right inspector hosting side session, Changes and read-only Conversation. Still no left rail. Why: the user wanted this panel since Herdr Desktop and a fork/diff needs a place that does not replace the terminal.
- Contract/DESIGN 2.6 'terminal is never replaced by a custom chat UI' is reworded to 'the live session is always the real terminal; Loom adds read-only views and a draft-first send path'. Why: allows the Conversation view for stopped/idle sessions and the live catch-up toggle without making chat the primary surface. UI-MAP 'No chat UI' changes in the same way.
- D-54 point 3 (stopped session shows the last terminal screen, ~4 MiB snapshot): the Conversation view replaces the static ended-screen snapshot for sessions without a terminal, if the user agrees, with the snapshot kept only if it proves useful for pending dialogs. Why: searchable, lighter, no snapshot held in memory.
- DESIGN section 2.4 two-row card: kept, except a conditional third line on attention-state cards only (asking / last said). Why: 'who needs me and why' is the product; the row is drawn only while the state holds, so a quiet list stays exactly two rows. The never-drawn status label rule is unchanged.
- D-53 header fixed places: header keeps its fixed places for pill/chip/controls but gains conditional chips (changes, PR, context) with a strict drop order, rather than new always-visible controls.
- D-52 (banners only for approvals): approval banners gain tool and command text; an opt-in, default-off 'finished or failed' banner when away. Why: reason in the banner is triage; opt-in keeps it quiet.
- D-38 (idle sessions never stop): unchanged by default; an opt-in 'Sleep' for idle sessions (I-19) is added only after the resume-fidelity spike, with the setting off.
- PermissionRequest hook stays decision-free in Phase 1-2. In Phase 3 it may change to a held, decision-returning hook (I-15) only if the hook/dialog race spike passes; this needs a new DECISIONS entry and an amendment to the CP2 text in the contract. Otherwise approvals stay answered in the CLI.
- D-43/D-46 (cross-session channel wanted, undated): given a date only for the read side (I-36) and user-initiated send (I-37 slice 1) in Phase 4, and only after the I-01 spike; agent-initiated sends stay behind a per-message approval card.
- D-20/D-32 wording: the per-session --settings may later carry more than hooks only if a statusLine bridge is adopted; not planned here (I-24 excluded).
- Header 'Stop' stays the only Loom-originated process action; no new action may report success without a verified outcome (send uses queued/pasted/delivered/outcome unknown vocabulary; never retried).
- Resource rules gain a budget table (I-44): every per-card or per-panel datum must pass a 1/10/100-card render test and a hidden-means-zero check before it ships.

**Risks.**

- The send path (I-01) is the shared foundation of P3-P4 and rests on undocumented TUI behaviour (paste, delay, modal visibility). If the spike fails, the cockpit still works as a read/triage product but the review loop becomes copy-patch only. Mitigation: draft-only default and P0 first.
- Anthropic keeps absorbing features (Desktop diff and side chat, agent view, Remote Control); the defensible core is cross-project triage and truth, not any single feature. Keep the plan to what a light local app does better and drop items Claude's CLI ships well (/diff, /btw, /goal).
- Header and card crowding: conditional chips plus a third attention line push against the two-row contract. Needs a design preview round and strict drop order; if it fails, move the data to tooltips and the inspector.
- Reason lines expose commands and paths on a locked screen and in notifications. Needs Settings switches and bounded memory-only text; never persisted.
- Right inspector narrows the PTY and the Claude TUI reflows (SIGWINCH). Mitigation: collapsed default, one coalesced resize, auto-collapse sidebar; a slide-over or tab fallback if it feels bad.
- Hook drift: status accuracy depends on documented but subtle hook semantics (Stop vs interrupt, idle_prompt, background_tasks). Mitigation: fixtures per CLI version, drift advisory, never pin.
- Scope creep from the Conversation view into a chat product (markdown, diffs, composer pressure). Keep it read-only and gated by evidence of use.
- Several ideas depend on the user's unanswered facts: GitHub vs GitLab, tickets and worktree habits, permission mode used, whether they hand-type /goal. Wrong guesses waste M-sized items; ask before P2.
- Resource creep: gh, git and transcript scans are the first work Loom does off its own files. Each must be event-driven, bounded, cancelled on Quit and visible-only, with a render and CPU test.
- Reopening D-38 or the contract's chat rule requires the user's explicit decision, not an agent's.

**Effort.** Roughly 3.5-4.5 months of solo agentic work, mostly S/M items. P0: ~1 week and some real-turn spend; P1: ~3 weeks (nine S/M items, mostly pure state and hook fields already received); P2: ~5-6 weeks (I-05 is the only L, with I-28 chip, I-31, I-41 as M); P3: ~4 weeks (I-01/I-02 M, I-15 M if it passes); P4: ~5 weeks (I-09 and I-10 are L, I-29 is L). Each phase ships on its own and P1 alone changes daily use.

**Identity.** Orca, cmux, Conductor, T3 Code and Claude Desktop are workspaces that own the agent: a worktree orchestrator with embedded diff and browser (Orca, Conductor), a terminal multiplexer with browser panes (cmux), a chat shell over the SDK or ACP (T3 Code, Conductor), or the vendor's own engine and cloud (Claude Desktop). Loom Cockpit owns only the process and the truth. It hosts the unmodified CLI in a verified run scope, reads the documented hook, registry and usage surfaces, and presents attention, reason, change, cost and context across projects on one screen, with outcomes it can prove (delivered, stopped, deleted) instead of optimistic UI. No daemon, no worktree manager, no embedded browser, no model call of its own, nothing drawn while hidden. Where the others render the conversation, Loom keeps the CLI and adds an instrument panel and a draft-first, never-retried send path. Its edge is being the light, native, always-correct second brain for several sessions, not a better IDE or chat window."

## Loom Lens (conversation-first hybrid) (`conversation`)

**Thesis.** The conversation is the front door, the real terminal is the engine room. Every session opens as a native, readable conversation rendered from the transcript of the SAME real Claude CLI process Loom already owns (no second engine, no SDK, no Node), with a composer, approval and question cards, and a right panel for side chat and subagents. One click switches the centre to the real PTY, which stays authoritative for everything Loom does not model (slash menus, pickers, dialogs, skills, MCP). The bet is that most of the user's day is reading, triaging and giving short follow-ups, which a chat view does better than a terminal, while the 'real CLI is always there' fallback keeps update resilience and the billing/policy posture intact. The chat default for LIVE sessions is earned, not assumed: it ships behind spike results (send fidelity, dialog discrimination, hook race). If those fail, the product degrades gracefully to 'excellent reader + draft-only composer + terminal for dialogs', which is still a better Loom than today.

**Design rules and decisions it changes.**

- DESIGN section 1 item 6 / UI-MAP 'No chat UI' / contract core-experience row: 'the terminal text is the real CLI, never replaced by a custom chat UI' becomes 'the live session is always the real CLI process in a PTY Loom owns; Loom adds views of it. Loom never emulates CLI features (slash menus, pickers, plan/model switchers) and never scrapes the TUI.' Why: the user is now open to a chat-centred UI, and a lens over the same process keeps update resilience, ownership and billing posture.
- D-34 (no right sidebar): lifted for exactly one collapsed-by-default right inspector with two tenants (Side chat, Subagent transcript). No left rail is added. Why: the user's long-standing wish, and the chat-centred centre is native so opening the panel does not SIGWINCH a running TUI.
- D-54 P1 (subagent click replaces the terminal in place): the transcript opens in the right panel beside the main conversation; in Terminal mode it still opens in place or the panel auto-collapses. Why: P1 existed to avoid resizing the PTY; a native centre removes that constraint.
- D-54 point 3 (stopped session shows its last terminal screen): superseded by the Chat view as the default for sessions with no process; the static snapshot (~4 MiB in memory) is dropped after one release unless the user misses it. Why: reads better, is searchable, and reduces memory for idle records.
- D-53 header fixed places: two new fixed slots (Chat|Terminal segment, panel toggle); state pill may become a popover trigger ('why this status', I-12). Header remains one control group.

**Risks.**

- TRANSCRIPT FORMAT: the main-session JSONL is CLI-internal (the SDK typings say so), not a documented interface. A CLI update can change record types, ordering, branches after rewind, resume/clear id changes. Mitigation: tolerant decoder, unknown rows shown raw, fixtures per CLI version, drift notice, Terminal always works. Residual: Chat view can be wrong or empty after an update while status (hooks) is still right.
- LIVE FEEL: the lens updates per content block with a ~100 ms flush lag and no token streaming; it will feel less alive than T3 Code or Claude Desktop. Only an opt-in stream-json mode fixes that, and it carries policy exposure. If the user's expectation is a streaming chat, Phase 1-3 will disappoint.
- WRITE PATH UNVERIFIED: 'never press Enter into a dialog' is not documented anywhere. Loom's 'Waiting for you' cannot tell an idle prompt from a question dialog; a composer Enter can approve a highlighted option. Mitigation: draft-only default, hook gate, user-keystroke epoch, auto-degrade, 99% bar. If the bar fails, the composer is only 'Place in Prompt' and the user must switch to the terminal to press Enter, which weakens the chat-first claim.
- APPROVALS: whether a held PermissionRequest hook races the CLI dialog, whether a terminal answer cancels the hook, and whether AskUserQuestion/ExitPlanMode are hookable are all unmeasured. If they fail, approvals stay in the terminal and live sessions should default to Terminal; the Chat view then mostly serves reading, queued follow-ups and side chat.
- DUAL SURFACE CONFUSION: two places to type (composer and the TUI draft box). A half-typed TUI draft or an open picker can be overwritten or mis-targeted. Mitigation: composer disabled with a reason when the terminal is dirty or in a modal; one writer per run through the existing input queue.
- POLICY/BILLING: the PTY path is on the safe side (unmodified CLI, user's own login). Anthropic's metering and SDK/headless policy changed several times in ten months; Chat mode and any headless side chat are exposed. The existing 1 s headless get_usage call is already a small instance of this. Re-read the support article before each release; keep Chat mode killable.
- FORKS: a fork re-reads the whole context (cache-cold cost), shares the working tree (plan mode is CLI-enforced but some read-only Bash will prompt), only sees flushed turns, may pollute the resume picker, can double-count usage, and mid-turn forks may carry a dangling tool_use. All unverified until the Phase 0 fork spike.
- RESOURCES: markdown/diff rendering of long sessions, backwards paging with variable-height rows and prepend scroll stability are real SwiftUI/AppKit risks; a visible Chat view plus a visible right panel plus live terminal surfaces for many sessions can break the CPU gate. Mitigation: render budget table, bounded reads, hidden = zero, no snapshot memory, reuse of the existing per-file vnode feed instead of new FSEvents streams.
- IDENTITY DRIFT: one Loom session can span several conversation ids/files (resume, /clear, fork, rewind branches). The view must follow Loom's adoptConversation logic or it will show a stale thread.
- SCOPE CREEP AGAINST ANTHROPIC: Claude Desktop already ships diff, side chat, preview, PR monitor and Routines. Building a Changes pane, PR dashboard or scheduler makes Loom a worse copy. Mitigation: keep to chips, links and triage; leave review comments and worktrees as user decisions.
- EVIDENCE QUALITY: much of the research is single-user anecdote and several mechanisms are explicitly unverified. The plan therefore front-loads spikes and gates phases; a failed spike changes the product shape, not just the schedule.
- TWO-PHASE DECISION DEBT: this direction needs user decisions recorded in DECISIONS (contract wording, D-34, D-54, hook decision-making, default view for live sessions, naming of the toggle, Return semantics, whether prompt text may be stored). Building before those are recorded would repeat the old pattern of design drift.

**Effort.** XL overall. Rough single-developer, heavily agentic estimates: Phase 0 S-M (about 1.5-2 weeks, mostly spikes); Phase 1 L (4-5 weeks, decoder + markdown rendering + paging + search); Phase 2 L (4-6 weeks, send primitive, queue, approval cards, conditional hook channel); Phase 3 L (4-5 weeks, inspector shell, fork lifecycle, cascade deletion, bring-back); Phase 4 M-L (3-4 weeks); Phase 5 M (3-4 weeks across many small items); Phase 6 XL and optional (6-8+ weeks if Chat mode proceeds). About 4-5 calendar months for Phases 0-5 if each phase's gate passes; Phases 1 and 3 are independently shippable, so the first useful release is the end of Phase 1.

**Identity.** Loom Lens renders the user's real Claude session instead of replacing it. T3 Code, Conductor and Zed-style chat UIs drive the model through an SDK or ACP engine and re-implement the CLI's features, so they lag the CLI (hidden slash commands, pinned or bundled CLI versions) and carry SDK billing exposure; Loom's chat is a lens over the unmodified CLI in a PTY, so every skill, MCP server, plugin and dialog works on day one via one click to Terminal, and it never pins a CLI version. Orca, cmux and Warp-style hosts show terminals and worktrees but write to the PTY without proof (Orca/Superset report 'delivered' blindly); Loom's edge is verified outcomes (delivered only on the UserPromptSubmit hook, Stop and delete verified, 'outcome unknown' stated) and run-scope process ownership with no daemon. Orca and Superset pay for daemons, polling and Electron; Loom stays a light native Swift app where hidden means zero work and idle records cost nothing. Conductor and Claude Desktop centre on one workspace, diff and PR flow (Desktop in Anthropic's environment); Loom centres on triage across many local sessions and two or three projects: status accuracy, attention routing, the subagent tree, ticket-keyed sessions, a side chat that is a real forked card with verified discard, and a user-authorized cross-session channel. It does not try to be an IDE, diff reviewer or scheduler; it hands those to the user's IDE, GitLab/GitHub and Claude itself.

## Loom v2 "Lean Cockpit": the terminal is the engine, Loom is the instrument panel (`lean`)

**Thesis.** Loom v2 does not become a second agent client. It stays a light native host over the unmodified Claude CLI and gets better at the three things only a host that owns the process can do: (1) tell the truth about each session (status, what it is asking, usage pace), (2) let the user catch up on any session without a live terminal (read-only Chat view of the same session, a one-click 'reopen what was running'), and (3) give the user the side thread they have wanted for months by forking a real session, not by building a chat engine. Every feature either surfaces something the CLI already ships (hook fields Loom already receives, /btw, --fork-session, transcripts, get_usage) or reads a file Loom already knows how to tail. Nothing in v2 holds a new standing authority, adds a runtime, or watches anything while hidden. Three small releases (0.5 Trust the dot, 0.6 Read it without the terminal, 0.7 Ask aside); each ends with a measured CPU/render gate and each later release is gated by evidence from the earlier one. The highest-risk write-path ideas (submit-into-PTY composer, answering approvals from Loom, cross-session send) are deliberately not in v2; they are replaced by draft-only paste, which the user confirms with Return.

**A day in the user's life.** 08:40. The user opens Loom. Quit stopped everything yesterday, so Active is empty, but above the day headings a quiet row reads 'Ended with Loom - 4  Reopen all  Dismiss' (I-21, derived from the catalog: runs that ended at the last Quit or crash, no new state). They press Reopen all for EDDP-412 and the api session; the other two they ignore. Cards go Working; Cmd+J still jumps to whatever needs them.

09:15. Needs-approval banner (as today) now says 'api - Bash: git push origin EDDP-412' (I-14) instead of just 'needs approval'. They glance, know it is the push they expected, switch with Cmd+J and answer in the real terminal. The pill's three-dot menu has 'Why this status?' when a dot looks wrong; Failed cards no longer turn into 'Waiting for you' 60 s later (I-12). Footer chip: '1.2M today - 5h 62% - ~2h left at this pace' turns orange only when the pace will run out before reset (I-25).

10:30. Mid-task in EDDP-412 they wonder whether the retry should be idempotent. Cmd+; opens 'Ask aside' (R3): a plan-mode fork of the session appears nested under the parent card as 'Aside: retry idempotent?', the detail swaps to its terminal (parent header status stays visible, parent is not resized). They talk with it for six turns. 'Bring back' pastes a short summary into the parent's prompt as an unsent draft; they edit and press Return. They discard the aside; its data is verifiably deleted. Before R3 existed, the same moment was a one-key /btw (I-08).

11:45. They run a long test suite session and close the lid for lunch; with 'Keep the Mac awake while sessions work' (I-20) the run finishes, and the menu bar item shows one blue Finished. The Mac holds only while Working; it let go when the session went to Waiting.

13:30. A teammate asks what was decided about pagination last week. They open the ended session; it opens in the Chat view (I-05 slice A: rendered turns, folded tool calls, nothing running, no process, no live terminal) rather than a frozen screenshot. In R3, sidebar search for 'pagination' also lists 'In conversations' hits with a snippet (I-41, budgeted scan, no index).

15:10. A multi-agent workflow runs. The subagent row that is blocked on a permission prompt shows the attention glyph and its name, so they know which of the five is asking (I-11 tier 1); a finished subagent never sticks on 'running'.

18:00. They Quit. Loom lists the two Working sessions by name in the quit sheet (I-17), Quit stops everything as always, and tomorrow's 'Ended with Loom' row will offer them back. The day used no extra process, no daemon, no new watcher while the window was hidden.

**Risks.**

- I-05 is the long pole and is honestly L: main-session JSONL is CLI-internal and undocumented (record types, branches after rewind, compaction, resume spanning ids), markdown rendering and prepend-scrolling are easy to get wrong. - Privacy of surfaced text: last message and command text can contain secrets or work-project content on a locked screen or in screenshots. Mitigation: memory-only, bounded, cleared with the state, banner details behind an off-by-default switch, excluded from diagnostics exports.
- Keep-awake and 'Reopen all' touch battery and plan budget: staggered resume of several large contexts re-reads caches; keep-awake can pin the Mac. Mitigation: caps, Low Power Mode pause, release on Waiting, stagger and count limit on Reopen all, off by default.

Mitigation: the exclusion list with named revisit conditions; compete on triage, accuracy, idle-zero cost and verified outcomes.

- The user may not feel the pain assumed by some R2/R3 items (context figure, search). Mitigation: I-23 and I-41 are explicitly conditional and drop out without hurting the thesis.

**Effort.** Overall roughly 9-12 weeks of agent-assisted work, no XL item. 0.5: about 2 weeks (all S, plus one recording day and one idle-Mac checklist; I-14 and I-17 are the largest at S/M). 0.6: about 4-5 weeks (I-05 slice A is the long pole at L; I-21 M, I-11 tier 1 M, I-23 tokens-only S-M; live toggle slice B is an extra 1 week only if used). 0.7: about 3-4 weeks including the fork spike (I-09 L, draft-only paste S, I-41 stage 1 M). Real-Claude spend: about 100-150 short turns in isolated profiles across the three recording/spike days, inside D-04. Each release runs the full suite and the CPU/render gates once, only when the user says the computer is idle.

**Identity.** The competitors are all workspace managers that grow upward into orchestration: Orca, Conductor, T3 Code and cmux centre on worktree-per-task, a diff/review loop and (for Conductor and T3) a bundled or SDK-driven agent; Claude's own Desktop app is the vendor's full client with side chat, diff and routines. Loom v2 is the opposite bet: the lightest native cockpit over the unmodified CLI, competing on trust rather than breadth. What is distinct and kept: (1) verified, honest status and outcomes (hook-driven state with watchdog and drift detection, sticky Failed, 'why this status', verified Stop/Quit/delete; the others write to a PTY or show a dot without proof); (2) process ownership with idle cost near zero (run scopes, Quit stops everything, no daemon, nothing drawn or watched while hidden, a CPU gate in the contract; the others carry resident daemons, pollers or Electron); (3) a read-only Chat view of the same session plus 'reopen what was running', so catching up never needs a live process; (4) a side thread that is a real forked session with plan mode and verified discard, not a second engine or a billing-exposed headless child; (5) honest usage (plan pace, stale marked) and never reading credentials; (6) the user's own authority stays in front: Loom never answers an approval or sends text into another session for them. It deliberately does not try to be an IDE, a worktree manager or an orchestrator."

## Completeness critic

### Dropped ideas that matter

- Hibernation by count or memory pressure, and a manual Sleep, are absent from the plan and the question list (cmux, supacode, orca, conductor, persistence-remote-orchestration). The cmux fact-check says its hibernation is not an idle timer: it only evicts the oldest idle background agents above 12 live terminals. Supacode keeps the 3 most recent live and sweeps on memory pressure. Both avoid the D-38 surprise of a 60-minute auto-stop. The catalog's I-19 is time-based and opt-in only, and the synthesis puts it in 'later' behind a resume-fidelity spike that is not in spikes_first. No user question asks about it, although 'idle sessions cost nothing' is a stated long-standing wish and five sources converge on it. A manual Sleep (a Stop that keeps the tab) needs no D-38 change.
- Memory-pressure and recency policy for hidden-but-Working sessions (supacode TerminalsFeature). Loom keeps one TerminalSurface per live run, selected or not (I-13 facts in the catalog). The plan only discusses idle records. Hidden Working sessions still hold renderers and scrollback, and nothing in the plan or in I-44's budget table covers them.
- Documented `http` hook handler (attention-surfaces and persistence-remote-orchestration, 'Missed by the report'). A hook that POSTs to Loom's local endpoint would remove the per-event loom-hook helper spawn (about 4 ms CPU each). It would also avoid holding one helper process per pending PermissionRequest, which I-15 needs. The catalog only measures helper latency (I-44) and never proposes this. It fits the CPU and process principles better than the I-44 budget work alone.
- Claude Channels `claude/channel/permission` is a documented, build-your-own approval relay (persistence fact-check 'Missed'). It is a research preview that needs the dev flag or an allowlist and costs one MCP process per session. The synthesis files Channels under 'standing skips/gated' and makes Allow/Deny depend on an unverified hook race. The research corrects the 'undocumented' framing, so the I-15 decision should at least name Channels as the documented alternative.
- The idle_prompt semantics decision (I-17 decision 1) is missing from the plan and the questions. The cmux fact-check says cmux HEAD maps idle_prompt to a reminder and suppresses needs-input for completed or background-pending sessions. The catalog says this one choice 'matters more for badge trust than any ordering change'. Today, about 60 s after a turn you already viewed, Loom shows an orange 'Waiting for you' that counts in the Dock badge, the menu bar, the project dot and Cmd+J. I-17-light and the 13 user questions omit it. S-2, the idle_prompt reality check, is also not in spikes_first.
- Cache-cold hint and prompt-cache countdown (usage-tools, orca CacheTimer, t3code). I-25 splits it out as 'a separate spike', and the spike is not in spikes_first. The plan adds I-21 'Reopen all', which resumes N cold sessions. It also never mentions the silent idle-compaction token spend at 54 min on 200K+ contexts, or the `idleCompaction:false` switch (claude-official fact-check). Users get no cost warning before the first prompt of a resumed session.
- A per-turn approvals counter and Enter/Esc approve/deny (codex-app, 'Keyboard approval and per-turn circuit breaker') were dropped without a word. The judge's skip list says 'A per-turn approvals counter (I-15) is the cheap substitute' for the auto-reviewer, but I-15 contains no counter. The Enter-approves part conflicts with DESIGN.md 'Return never approves while a live terminal is shown', so dropping it is defensible but should be stated. The counter is a cheap, no-model-call piece that does not depend on the hook race.
- Fork-from-here and rewind points (happy, 'listClaudeRewindPoints' and 'forkAndTruncateSession' with a hard-fail rule). Not in the catalog and not in the skips. It is only a possible future use of the --fork-session work in I-09, but it is the research's cheapest alternative to a checkpoint UI.
- `claude agents --json` as a documented cross-check source (claude-official, zed, cursor 'Missed'). It gives state working|blocked|done|failed|stopped, status and a waitingFor enum, and lists kind:interactive rows. Loom's status relies on the registry file `sessions/<pid>.json`, which the code comment calls 'a private CLI capability'. The principle says documented interfaces are preferred. I-22 dismisses the idea as a visibility lane and never evaluates it as a drift cross-check. The cheap test (does it work with CLAUDE_CODE_DISABLE_AGENT_VIEW=1, which Loom sets) is only inside I-22's E1.
- Per-type filtering of Stop.background_tasks (superset fact-check: PR #8114 counts only subagent and workflow tasks because shells and monitors can run indefinitely; conductor 'waiting on background task' with a timer). The catalog never proposes filtering by task type, a visible 'waiting on background work' wording, or a timer. See the principle_violations entry on the same point.
- The outbound cross-session gap named in the contract (LOOM-PRODUCT-CONTRACT.md section 7): `crossSessionInbound: refuse` blocks only incoming messages, so a Loom session can still SendMessage to non-Loom sessions. The catalog has it as I-37 S4, but it is in neither spikes_first nor the plan nor the user questions. Q10 treats the channel purely as a future feature.

### Claims the fact-checks weakened

- 'Delivered only after UserPromptSubmit' and 'prompt digest/hash match' (I-01, I-02 S1, I-03, the judge's send path). The review-git-loop and warp fact-checks weaken this in four ways. (1) The hook's `prompt` has pastes expanded or wrapped in <pasted_content>, and invisible Unicode is stripped on Enter, so exact hash equality is overstated. (2) Loom does not retain prompt text. (3) UserPromptSubmit also fires for turns Claude starts on its own, so it proves 'some prompt', not 'my prompt'; a nonce or normalisation is needed. (4) Slash commands are swallowed by autocomplete even when sent as short constants. The '50 ms' delay is only Orca's renderer note path; the main path uses 500 ms plus a size term. The catalog sometimes says 'digest compare' without the caveat.
- 'Draft-only Place in Prompt' is called the zero-risk mode, and 0.7 reports 'placed or not placed with reason'. Nothing in the research gives Loom a way to verify placement. The contract (section 7) says bracketed paste does not prove the target field accepted the text, and chat-ui-paths rejects screen scraping. Until the user presses Return there is no UserPromptSubmit to confirm anything, so 'placed' is only 'bytes accepted by TerminalInputQueue', which is 'sent, unconfirmed'. Whether a paste into an AskUserQuestion or permission dialog is inert depends on whether the TUI keeps bracketed paste mode on there. That is I-01 E2, which is unrun. A paste of numbers or newlines into a dialog is not obviously harmless.
- 'Loom's defensible edge is cross-project triage.' The power-user and cursor fact-checks say Agent View already has `--cwd` project filtering, grouped states, a Ready-for-review group, PR/CI labels, PR-number search and peek/reply. Cursor adds that Claude's agent view 'overlaps Loom's sidebar and was not discussed'. The edge that holds up is status truth, verified outcomes, idle-zero cost and the subagent tree. The judge's wording is stronger than the evidence.
- 'The /btw week is the baseline for the I-09 go/no-go.' /btw is a single-answer, no-tools, in-memory answer in the TUI (chat-ui-paths fact-check). SubagentStop also fires for it (claude-official). It cannot measure demand for the user's actual wish: a persistent, multi-turn thread that 'can do most things except spawn subagents'. A week of /btw can show how often side questions happen. It cannot show that a tool-enabled persistent thread is unnecessary.
- Hook-only status is presented as the stable base. The herdr fact-check says herdr moved away from hook-driven state for Claude after stale-hook bugs and now strips its hooks. Supacode and Paseo conflate permission_prompt (about 6 s delay, only when the user seems away) with idle_prompt (about 60 s after finishing). Per-session --settings mitigates the herdr failure mode, but the new items (I-12, I-14, I-20) depend more on Stop, background_tasks and Notification semantics. Several of those are unobserved on the installed CLI, and the unrun recording day is the only verification.
- I-05's 'Stop-hook-to-JSONL about 100 ms' and the live-view plan. The warp fact-check quotes the hooks docs: the transcript file 'isn't guaranteed to include the final message at Stop time on all versions', which is why last_assistant_message exists. This does not hurt slice A (stopped records) but it does affect slice B and any transcript-based confirmation. The plan should say the live view needs Stop.last_assistant_message to reconcile with the file.
- Allow/Deny and the AskUserQuestion/ExitPlanMode cards (I-15/I-16, listed as 'later, if the race spike passes'). The attention-surfaces fact-check shows that answering these by hook in an interactive session is an inference. The docs frame it for -p and PreToolUse only. 'The CLI does not reap the pending hook when you answer in the terminal' rests on one user's report (Vibe Island #245). CLI 2.1.300 now drops unknown updatedInput keys, so older CodeIsland-style answers fail. The synthesis gates these correctly, but the I-14-light banner already assumes PermissionRequest carries tool_input for AskUserQuestion and ExitPlanMode, which is unverified. The permission-mode question also stays open: auto mode (2.1.283+) makes approvals rarer than the older statistics suggest.
- 'The CLI waits and continues by itself at a usage limit (2.1.234+), so drop Continue-at-reset and the Limit-reached state' (I-25). The same item says the hook order and Loom's state during that wait are unobserved. The simplification rests on docs, not on a recorded sequence, and the sequence spike is missing from spikes_first.
- 'Prompt-cache TTL tier readable from transcripts' and 'idle compaction fires SessionStart(source=compact)' are both unverified (usage-tools, claude-official). The synthesis ships the context figure in 0.6 with 'reset on SessionStart(compact)'. The I-23 E2 spike is listed, but the I-25 TTL spike is not. The statusLine `context_window_size` field is documented, so the 200K-versus-1M uncertainty exists only on the transcript route. The tokens-only fallback is sound, but 'reset on compact' is not yet shown to work for idle compaction.

### Principle risks

- Accurate status and predictable behaviour: I-12 pins 'background-task Stop keeps Working' as a regression sequence, and I-20 holds the Mac awake on 'background tasks counted'. Loom's ClaudeHook.swift counts every entry of Stop.background_tasks with no type filter (collectionCount). A background dev-server shell or monitor can run indefinitely, so the card stays Working forever and the idle-sleep assertion is held up to the 6-8 h cap (battery). Superset deliberately counts only subagent and workflow tasks (superset fact-check, PR #8114). The tasks have a type (shell, subagent, monitor, workflow) per the cmux fact-check. The plan should filter by type, or show a distinct 'waiting on background work' wording, before building the assertion on it. I-20's own Cron check does not cover the shell case.
- Verified outcomes: 'placed in prompt' (I-01 draft-only, 0.7) and 'Bring back' report a result that no documented signal confirms (see shaky_claims). Without a screen-state check or the later UserPromptSubmit, the honest vocabulary is 'sent, unconfirmed' (the research's own wording for the part of Orca not to copy).
- Process ownership and verified deletion in I-09: 'Discard' may skip the confirmation, children are cascade-deleted with the parent, and persistent forks accumulate. Contract section 8 requires a dry run and a verified result for permanent deletion. The fork child also holds a copy of the parent's history, so an unconfirmed Discard can destroy a promoted or edited side session. This is only a user question, not a design rule.
- Low resource use: I-41 stage 1 scans up to 512 MiB of transcripts per query (14-day window) after the 120 ms debounce, on a 'budgeted scan, no index' design. It is bounded and user-triggered, so it is not polling, but each new character starts another scan and the first gate is S2, which needs an idle Mac. Snippets can also surface secrets pasted into prompts, and the scan reads transcripts of sessions beyond the catalog. The plan adds it to 0.7 only 'if the corpus measurement says so', which is fine, but the privacy side has no setting yet.
- Privacy at the card level: I-14-light puts the last assistant message and the tool+command in tooltips and (after a design preview) a third card line, and only the banner has an off-by-default switch. Screen sharing and a locked screen can still show card text. The privacy question in Q7 covers banners only.
- Cross-session actions under the user's authority: the known outbound gap (Loom session to non-Loom session through the native SendMessage) is documented in the contract but nowhere in the plan, spikes or questions. The plan adds 'Reopen all', batch open and a future send path while the existing open gap stays unmitigated.
