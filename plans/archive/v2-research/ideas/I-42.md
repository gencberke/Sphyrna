# I-42: Away from the Mac: Remote Control toggle, presence file, optional content-free push

Card from the [Loom v2 idea catalog](../IDEAS.md). **Away from the Mac: Remote Control toggle, presence file, optional content-free push** · verdict **spike-first** · cost M · value 3/5 · proposed by 7 reports: [claude-official](../products/claude-official.md), [happy](../products/happy.md), [persistence-remote-orchestration](../products/persistence-remote-orchestration.md), [cursor](../products/cursor.md), [warp](../products/warp.md), [paseo](../products/paseo.md), [attention-surfaces](../products/attention-surfaces.md).

> Keep only the launch flag, the presence file and a hook-proven badge, and cut the push and the preflight process; run one throwaway-profile spike first, because Loom's verified-Stop promise and its CLAUDE_CODE_DISABLE_AGENT_VIEW=1 launch env are untested against `--remote-control`.

## What the user gets

For sessions that already run in Loom PTYs, a 'Reachable from phone' toggle (and a Settings default) so approvals, answers and nudges can be done from the phone, with an RC badge on the card; Claude's own phone pushes are suppressed while you are at the Mac; optionally a content-free 'session X needs you' push. No Loom server, relay or app.

## Mechanisms found in the research

1) [Documented, `--remote-control [name]` present in `claude --help` 2.1.300] Launch with `--remote-control "<title>"` (or send /remote-control later); badge from CLAUDE_CODE_BRIDGE_SESSION_ID in hook payloads (v2.1.199) once connected; preflight with `claude auth status` and explain why unavailable (API-key auth, Bedrock/Vertex, custom ANTHROPIC_BASE_URL, CLAUDE_CODE_OAUTH_TOKEN/setup-token, ZDR/HIPAA, Team/Enterprise owner toggle, disableRemoteControl, Trusted Devices). 2) [documented on the RC page] write/delete the CLAUDE_CLIENT_PRESENCE_FILE on screen lock/unlock (NSDistributedNotificationCenter) so CLI pushes happen only when away; env is read at CLI start, so it only affects sessions started afterwards. 3) Optional webhook/ntfy/Shortcuts push, off by default, fixed string + session title only, no approve-from-phone; likely redundant because RC already sends documented mobile pushes for finished and needs-permission.

## Debates and fact-check corrections

Corrections: DISABLE_TELEMETRY / DO_NOT_TRACK no longer block RC since 2.1.283 (unless Trusted Devices required); the 'Mac must stay awake' claim is overstated (a sleeping laptop reconnects; server mode gives up after about 10 min); Remote Control sessions can pick Auto mode; truncated-approval-card evidence is a ~5-month-old comment. Privacy: transcript is stored on Anthropic servers while connected, so default off with plain wording; Quit still stops the session, so the phone loses it (say so). Unresolved tests needed with a throwaway CLAUDE_CONFIG_DIR: does --remote-control start a long-lived daemon outliving Loom's scope on macOS, and does RC work with CLAUDE_CODE_DISABLE_AGENT_VIEW=1 (Loom sets it). Loom can claim only 'requested' unless RC state is visible to hooks/registry (unverified; /rc active indicator exists in the TUI). Mobile reality: value is attention (push, approve/deny, short result, one follow-up), not deep review. Paseo's loopback web page over Tailscale/SSH is the heaviest acceptable variant and persistence-remote-orchestration ranks any Loom-owned relay/web/app as skip.

## Design in Loom


BASELINE FACTS (observed)
- Loom runs Claude in the user's real default profile (ClaudeProfileLayout, SessionRuntime+Claude.claudeProfile only overrides CLAUDE_CONFIG_DIR when given). So `remoteControlAtStartup=true` or typing `/remote-control` already works in Loom today, with no Loom code. Loom's added value is only (a) a per-session start switch, (b) the presence file, (c) an honest badge.
- `claude --help` 2.1.300 lists `--remote-control [name]` and `--remote-control-session-name-prefix <prefix>`. The RC docs say `claude --remote-control` with no eligible login still starts an interactive session and shows a failure notification in the TUI. So an unavailable RC is not fatal and needs no gating preflight.
- CORRECTION to the idea text: CLAUDE_CODE_BRIDGE_SESSION_ID is an ENVIRONMENT variable of hook-command and Bash subprocesses, set while RC is connected and removed when it ends (env-vars page, hooks page; v2.1.199+). It is NOT a field in the hook JSON payload. Today `loom-hook` (Sources/loom-hook/main.swift) forwards only stdin plus LOOM_* env, and ClaudeHookEvent.init reads only payload keys. The helper therefore has to read that env var itself.
- CLAUDE_CLIENT_PRESENCE_FILE (v2.1.181+) is checked once per push-triggering event, not polled. File exists means pushes are skipped. It is read from the CLI's start environment.

DESIGN (smallest version; cost M, not S)
A. Start switch (LoomCore).
   - `ProviderCapabilities.supportsRemoteControl = help.contains("--remote-control")`, added to `detectedClaudeOptions` like the other flags (ProviderLaunchProfile.swift).
   - `ProviderLaunchProfile.claude(route:...)` gets an optional `remoteControl: String?` (the name). It emits `--remote-control=<name>` before the `openingArguments` and before the trailing `--` prompt. Use the `=` form because the argument is optional-valued and the title can start with `-`.
   - Unlike `--settings` and `--session-id`, which are passed even when `--help` does not list them, this flag is gated on detection. It is an opt-in convenience and must not stop a session from starting. When it is missing the UI says "this Claude has no Remote Control option".
   - The name is built from the project name and the ticket key (the catalog has both), so two EDDP sessions can be told apart on the phone. Otherwise the CLI invents "host-graceful-unicorn".
   - Per-session intent is one nullable catalog column `sessions.remote_requested`, added the same way as `ticket_key` and `opened_by` (CatalogDatabase, no `user_version` bump), so Resume repeats the choice. The Settings default (UIPreferences) applies only to new sessions. D-20 is met because both are explicit user switches and the default is off.
B. Presence file (loom-app, beside ApprovalNotifier and SystemServices).
   - A `PresenceService` protocol with a system implementation and a recording fake for `--evidence`, like NotificationService.
   - Events: `com.apple.screenIsLocked` and `com.apple.screenIsUnlocked` on DistributedNotificationCenter (undocumented names, so verify on macOS 27 or fall back to CGSessionCopyCurrentDictionary read at the event), NSWorkspace.screensDidSleep and screensDidWake, and the screensaver start and stop notifications. There are no timers. One atomic create or delete per event, a re-sync at launch, and delete at Quit.
   - The file lives at `<data root>/presence/at-mac`, so the dev app and the daily app never share it. Loom exports `CLAUDE_CLIENT_PRESENCE_FILE` into the launch env only when the user's Phone switch is on; it is inert unless RC is active.
   - Limitation to state: the env is fixed at CLI start, so a session that began before the setting existed is not affected.
C. Honest badge (hook path).
   - `loom-hook` adds an optional `bridgeConnected: Bool?` to ClaudeHookEnvelope. It reads only whether the env var is present and never stores or logs the value, because it equals the claude.ai/code session id in the URL. An old envelope still decodes.
   - The adapter publishes a new `.remote(RemoteState)` change through SessionEventHub, the same shape as `.subagents`. SessionViewState holds it and it is cleared on run start, detach and end.
   - Card states: none, Requested (flag passed, not yet seen), Connected (as of the last turn event), Not connected (requested, but the var was absent at the first UserPromptSubmit or Stop, or it disappeared). The last state reuses SessionIssueNotice: "Phone access did not start, see the terminal footer".
   - Wording never says "connected" without hook proof.
D. Cut from this idea.
   - Mechanism 3 (webhook, ntfy, Shortcuts push). RC already sends documented finished and needs-permission pushes, but only if the user has enabled them once in `/config`. Loom must not change those CLI settings (D-20). A second channel adds a network dependency and a settings surface for no gain.
   - A `claude auth status` preflight process. Loom reads nothing of the account today (ClaudePlanLimits keeps only the two windows). Use a pure, process-free hint from `toolchain.environment`: ANTHROPIC_BASE_URL, CLAUDE_CODE_USE_BEDROCK or VERTEX or FOUNDRY, CLAUDE_CODE_OAUTH_TOKEN, CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC, DISABLE_GROWTHBOOK. Word it as "may not work", because settings.json env, Trusted Devices, the Team owner toggle and ZDR/HIPAA are invisible to Loom.
   - Injecting `/remote-control` into a running PTY. Loom has no programmatic input path; D-43 and D-46 leave "deliver into a session" for the cross-session channel. The menu item for a running session only shows the hint "type /remote-control".
   - `claude remote-control` server mode. It spawns sessions outside Loom's run scopes, which breaks process ownership.
   - A Loom power assertion. The CLI handles idle sleep itself while working (2.1.287 fix). The gap is a session that is waiting for approval while the Mac sleeps. That belongs to the persistence idea's stay-awake option as a separate user decision.
E. Triggers and bounds.
   - Everything is event-driven: lock and sleep notifications, hook events that already fire, and the user's click. Nothing polls and nothing is drawn when hidden.
   - Memory is one Bool per live session plus one file.
   - Cost: M. Flag and capability about S; presence service S to M; hook, envelope, hub and badge M; Settings and menu M; tests M. The flag-only version is S but gives an unprovable badge and no quiet pushes.


## Where it shows


- Settings → General gets a "Phone" group.
  - Switch 1: "Start new sessions reachable from my phone", off by default. Caption in plain words: "Uses Claude's Remote Control. The conversation is stored on Anthropic's servers while connected. The session ends when you stop it or quit Loom, so the phone loses it. Needs a claude.ai login."
  - Switch 2: "Skip phone pushes while I'm at the Mac", on once Switch 1 is on. Caption: "Applies to sessions started afterwards. Push types are set once in Claude's /config."
  - A short grey line shows the env-derived hint when something would block RC.
- Session ⋯ menu, with no confirmation dialog:
  - Stopped or new session: a checkable "Reachable from phone".
  - Running session: a disabled item "Reachable from phone: type /remote-control in the terminal".
  - Later, once the badge is proven: "Copy phone link", with the id kept in memory only.
- Card, bottom row: a small monochrome `iphone` symbol left of the provider icon, in text.secondary. An outline means requested, filled means connected at the last turn, and a struck-through look means not connected. No status words, so DESIGN.md §4 and the three-status-hue rule are untouched. The tooltip and accessibility label carry the words.
- Header: no new chip. A failed request reuses the existing issue notice. Stop and Quit text gains one line when a phone-reachable session is running: "The phone loses it."


## Principle check


- Resources: PASS. No polling, a handful of OS notifications, one file write per lock event, one Bool per session. Fail condition: periodic `claude auth status`, registry polling for RC, or a standing helper. The design avoids all three. There is no Loom network code at all.
- Predictability: PASS if default off, the flag is gated on detection, and sessions started before a setting change are not affected (stated in the caption). RISK: RC makes sessions depend on network, the account and Anthropic's pairing, and it can fail silently (#34255 and #35637 open, per the persistence note). Loom must not hide that.
- Accurate status: RISK, managed. The badge is proven only by the hook env, and only as of the last turn event. SessionStart probably fires before the bridge connects, so a fresh idle session stays "Requested" until its first prompt (to be measured). Never show "Connected" from the flag alone. When a phone answers an approval, the hook sequence is the same as for the terminal, and the registry busy sample returns the state, so no new status bug is expected (to be confirmed in the spike).
- Fluency: PASS. One switch and one menu item, no modal, no startup wait. First-use text sits inline in Settings.
- Modularity: PASS. Launch rule in ProviderLaunchProfile, an OS service in loom-app behind a protocol with a fake, state through the existing hub path. LoomCore stays UI-free.
- CLI-update resilience: PASS. Only documented surfaces are used: `--remote-control`, the hook env var, CLAUDE_CLIENT_PRESENCE_FILE. All are version-tagged in the docs and degrade to "absent". Capability detection joins the drift list. Never pins a CLI version.
- Process ownership: UNPROVEN, and the decisive risk. If an RC session leaves a bridge or daemon process that survives Loom's Stop or scope kill (the Windows report #101118), the phone could show the session online after Loom said "Stopped". That is a false success. The spike must prove that Stop and Quit leave nothing and that the phone sees the session go offline. Fail condition: any survivor means do not ship, or ship only after tearing it down inside the scope.
- User authority: PASS with a caveat. A phone approval comes from the user's own claude.ai account, not from another session, so it is not a cross-session action. It is still an extra control surface, so it is opt-in per session, shown on the card, and never turned on silently. Loom's own cross-session channel (D-43) stays unrelated, and `crossSessionInbound=refuse` is unchanged.
- Privacy: transcripts are stored server-side while connected. Work projects (EDDP) may be under company or Team policy. Default off, plain wording, and no per-project auto-enable.


## Value for the user (3/5)

The use is real. Several long multi-agent runs blocked on approval, with the user away from the Mac, is exactly the case RC serves, and Anthropic's own pushes and approval UI already exist. But the user's own wish list (side chat, right panel, usage, reliable delete, idle cost) never mentions a phone, and the bare benefit is already available for free through `remoteControlAtStartup` or typing `/remote-control`. Loom's increment is convenience, the quiet-push presence file and an honest badge. Reliability caveats (open silent-disconnect and approval-not-reaching-host issues, a Mac that sleeps while a session waits for approval, server-side transcript storage) cap the value until the user confirms they want it.

## Experiments before building

- S1 Ownership and daemon (decides ship or no-ship). Needs a one-time `/login` by the user in an isolated profile (CLAUDE_CONFIG_DIR=/tmp/loom-rc-spike), because CLAUDE_CODE_OAUTH_TOKEN cannot establish RC and the real ~/.claude is off limits. Launch `claude --remote-control=x` with CLAUDE_CODE_DISABLE_AGENT_VIEW=1, the way the launch profile does, inside a throwaway Loom run scope. Decide by three checks: (a) it connects (the TUI footer shows the indicator and the phone lists the session); (b) the process tree before and after shows no `claude daemon`, supervisor or bridge process outside the scope; (c) after Stop and after Quit the phone shows the session offline and `ps` finds no survivor. If it needs AGENT_VIEW enabled, or a daemon escapes, the idea is dropped or becomes a user decision under D-20.
- S2 Hook env timing. Use a tiny test hook that records only whether CLAUDE_CODE_BRIDGE_SESSION_ID is set, for SessionStart, UserPromptSubmit, Stop, Notification and SubagentStart, in these cases: RC from launch, RC turned on mid-session, RC turned off, resume with the flag, after /clear. Decides whether 'Connected' can ever show before the first prompt, and whether subagent hooks carry it. If SessionStart never has it, the badge copy must say 'after your first message'.
- S3 Presence file. With the phone app registered and `/config` pushes enabled in the spike profile, check that pushes still arrive with the file absent and stop while it exists, both when the Loom-like terminal has focus and when it does not. Also check whether the CLI's own 'focused terminal' suppression works at all in Loom's PTY (SwiftTerm has DECSET 1004 support but I did not confirm Loom forwards window focus). Separately verify on macOS 27 that the lock, unlock and display-sleep notifications actually fire.
- S4 Naming and resume. Check how `--remote-control=<name>` interacts with `-n <title>`, whether the phone title follows later auto-titles, and whether `--resume <id> --remote-control` creates a duplicate stale entry in the phone list each time.
- S5 Phone approval round trip. Approve a Bash permission prompt from the phone and watch Loom's state (PermissionRequest hook, then the registry busy sample) for a stuck 'Needs approval'. Optionally record `pmset -g assertions` while working versus waiting for approval, to see whether the CLI holds the Mac awake in the waiting case.

## Questions for the user

- Do you actually want phone access? Your notes do not list it. If you only want to be told when a session needs you, the presence file alone is the whole value.
- Which login do the work projects (EDDP-*) use: a personal Pro/Max account, or a company Team/Enterprise one? Server-side transcript storage and the owner toggle or ZDR/HIPAA restrictions apply there. Should RC be allowed for those projects at all?
- Is `remoteControlAtStartup` already on in your own Claude settings? If so, the start switch is moot and only the badge and presence file remain.
- Are you willing to do the one-time `/login` in a throwaway profile for the spike? It signs a session into your real claude.ai account.
- Keep-awake: should Loom ever hold an idle-sleep assertion for phone-reachable sessions? This is a battery and predictability trade-off and it overlaps the persistence idea.
- Default for the Settings switch: off (recommended, because of D-20 and privacy), or on for personal projects only?
