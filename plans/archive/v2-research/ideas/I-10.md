# I-10: Right-hand context panel (subagents, side chat, changes, notes)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Right-hand context panel (subagents, side chat, changes, notes)** · verdict **spike-first** · cost L · value 4/5 · proposed by 6 reports: [t3code](../products/t3code.md), [paseo](../products/paseo.md), [openchamber](../products/openchamber.md), [codex-app](../products/codex-app.md), [happy](../products/happy.md), [chat-ui-paths](../products/chat-ui-paths.md).

> Build only a one-tenant right pane for a real forked side session (not a generic tabbed panel), but first run a CLI fork/hook/cache/resize spike, because the pane is the cheap part and the child-session plumbing is the risk.

## What the user gets

A collapsible right panel (the user's long-standing wish) that hosts the secondary threads of the selected session: subagents/subtasks, the side chat, later Changes and an agent note. Nothing is drawn or watched when it is collapsed; closing a tab stops what it owns.

## Mechanisms found in the research

Shell first (M): a per-window collapsible pane with tabs, one owner process per tab, lifetime = panel open. T3 puts side chat in a right-panel tab sharing the composer (Esc returns to main), OpenChamber uses a slide-over above the composer collapsible to a chip, Paseo/Codex use a right-hand pane, Zed a side panel. Lighter alternative that needs no new rail: reuse Loom's existing 'click a subagent = read-only live transcript in place of the terminal' pattern and let a side-chat child open the same way. Collapsed panel must still surface a pending approval of the parent (OpenChamber v2.4.0 fix for a parent stuck on an unseen request).

## Debates and fact-check corrections

Standing decision D-34 (no left rail; right sidebar deferred, 'ideas such as a side chat come later') must be revisited with the user. In-place vs side-by-side is a UX decision; a side panel competes for width on a laptop and with the terminal's column count. No report measured the panel's idle cost; the design rule is that an unopened panel costs nothing.

## Design in Loom

SCOPE CUT. Subagents are already solved: the sidebar tree plus the in-place read-only transcript (CatalogModel+Subagents.swift, SubagentTranscriptView/Model, D-54 P1, chosen days ago, "terminal is not resized"). Changes and note tabs are separate ideas (checkpoint diff L, vault notes). So I-10 reduces to: a collapsible right pane whose first and only tenant is a side chat. Add a tab or enum host only when a second tenant exists (YAGNI). Possible second tenant later: "show this subagent beside" reusing SubagentTranscriptView unchanged.

1) SHELL (S-M). MainSplitViewController.swift already is an NSSplitViewController with sidebarItem + contentItem (detail min 480). Add a third NSSplitViewItem(inspectorWithViewController:), collapsed by default. Mirror SidebarCollapseSync/SplitViewItemCollapse for collapse truth and persist width/open flag in UIPreferences (sidebarWidth/sidebarCollapsed pattern, new optional keys decoded with decodeIfPresent so old files load). Mount its SwiftUI content lazily: the hosting controller's rootView is an empty placeholder while collapsed, real content only while open, so a collapsed pane observes nothing and draws nothing (NSSplitViewItem collapse only hides the view; it does not stop SwiftUI observation). New view files only: LoomCatalogUI/SidePanelView.swift, SidePanelHeader (parent state pill reused from StatePill, child state, Stop, Promote, Discard, Close), CatalogModel+SidePanel.swift (keep out of the 1,612-line CatalogModel.swift). Pane chrome follows DetailView panel rules (10 pt radius, hairline, panel fill); all values via LoomTheme (scripts/check-theme-literals.sh).

2) SIDE SESSION = a normal Loom session, not a new runtime. Path already exists: approveOpen / startConversation(opening:) start a session without moving selection, in its own run scope (RunScopeLauncher), with openedBy. Add: ClaudeRoute.fork(parentProviderID, newID) in ProviderLaunchProfile.claude(route:...) producing `--resume <parent> --fork-session --session-id <newID>` (verify combination in the spike), keep `--settings`/hooks/--plugin-dir exactly as for any run; `ProviderCapabilities.supportsForkSession = help.contains("--fork-session")` and add it to detectedClaudeOptions/missingRequiredClaudeOptions like the other options (drift is journaled once, the start still proceeds, per the existing rule). New SessionRuntime+SideSessions.swift: startSideSession(of:question:mode:) -> reuses createSession/launch; a new nullable catalog column sessions.side_of added by the same ensureOriginColumns/ensureActivityColumn pattern (no schema bump, 0.2.1/0.3.0 still open the catalog). No JSONL copying (reject Happy's copyFile approach; it breaks on format drift).

3) ASK-FIRST LAUNCH, zero idle cost. Opening the pane shows a SwiftUI composer only (no process). On Enter, Loom starts the fork with the boundary text and the question as the Claude positional prompt (the existing `trailingArguments` after `--`, as ClaudeOpening does): "Everything above is reference only; do not continue its plans or tool calls; no subagents; no edits unless asked here. Question: ...". Boundary goes in the message, not the system prompt, to keep the cached prefix. After that the pane swaps to the child's live TerminalContainerView (model.terminalView(for:) already returns it; TerminalContainerView.viewDidMoveToWindow steals first responder, so focus must be made explicit for the pane). Read-only default via --permission-mode plan (cache-friendly: mode text lives in messages) with an "Allow edits" toggle (T3 PR #18243); do NOT use --tools to restrict (changes tool definitions, would miss the cache) unless the spike shows otherwise.

4) LISTS AND ATTENTION. Child is hidden from lists by `AND s.side_of IS NULL` in SessionCatalog+Paging.swift (sessionPage, searchSessions window query), SessionCatalog+Projects.swift sessionCounts, classifyStale/oldestStaleCandidate, and the CatalogModel+Patching listedSession path; it is NOT hidden from attention: its hook state still feeds SessionEventHub, so approvals/notifications/menu bar/Dock badge/Cmd+J (AttentionOrder) work unchanged and the pane toggle shows an attention dot when the child needs approval or finished. The parent's approval is already always visible because the parent terminal and RequestList stay on screen beside the pane (this is the OpenChamber v2.4.0 failure the split layout avoids by construction; with a slide-over it would have to be re-solved). Under the parent card show a one-line child row like SubagentTree, or only a small glyph.

5) LIFECYCLE (all event-driven, no polling). Open pane: nothing runs. Send: start child (state Starting until SessionStart/registry confirms; failure shown, never reported as started). Close pane while child Working: keep running, pane toggle shows Working; when child is idle/finished and the pane is closed, optional one-shot timer armed from the Stop hook stops it (SessionLifecycleController idle machinery exists; stopsIdleRuns is false in the app, D-38, so this needs the user's OK). Stop = existing verified ProcessSupervisor.stop; Quit already stops all runs. The record survives (hidden, reachable from the parent's menu "Side chats"); Promote = clear side_of (one UPDATE + hub frame); Discard = existing ConversationDeletion flow (dry run, verified). Usage is already deduped by message.id (ClaudeUsageIndex), so the fork's copied history is not double-counted.

6) BOUNDS. At most one live side child per parent and (say) 2 live globally; no auto-open ever; a context-size hint before the first send ("re-reads ~N tokens; cache may be cold"). Fork sees only what the parent has flushed to its transcript (say so in the UI).

HONEST COST. Shell alone S-M. The real work is the child-session plumbing (fork route, side_of column and 4-5 query filters, lifecycle/Promote/Discard, focus, tests with loom-fake-provider, ARCHITECTURE/UI-MAP/DECISIONS updates): whole thing L (the research's M is right for the pane, not for the feature). No new polling, no new process type, no new socket.

## Where it shows

Default: no pane; a `sidebar.right` toggle sits at the right end of the session header group (and Cmd+Opt+S, Codex's chord, opens it straight into the ask box); the toggle carries a small status dot when the child needs the user. Open: the detail panel narrows and a second rounded panel appears on the right (default 420 pt, draggable 340-640, remembered). Top of the pane: "Side chat" title, parent's state pill ("main: needs approval / working / finished", the Codex SideParentStatus idea, from liveStates), child's state pill, Allow-edits toggle, Stop, and a menu (Promote to session, Copy last answer to main prompt, Discard, Close). Body: before the first send a text box "Ask something about this session" with the context-size hint; after it, the live terminal of the forked Claude. Esc in the box or a click on the main terminal returns focus to main. Width warning: at the default 1220 pt window, sidebar 300 plus a 420 pt pane leaves roughly 55 columns for main and 44 for the pane, so opening the pane should offer to collapse the sidebar (or stay a slide-over), and it is comfortable only from about 1450 pt (full screen on a 14-inch laptop).

## Principle check

Resources: PASS if the pane mounts content lazily and the child exists only after Send (collapsed pane = no SwiftUI observation, no process, no vnode source; hidden terminals already suspend rendering via suspendsRenderingWhenNotVisible); RISK: a second live Claude is a few hundred MB RSS and a fork re-reads the whole context (cache reuse across sessions unverified), so show the hint and cap live children. A violation would be a persistent hidden child, a poll of the parent's transcript, or an always-mounted SwiftUI pane. Predictable: PASS (user-initiated only, never auto-open). Accurate status: PASS with care (started only after SessionStart/registry confirmation, stop and delete use the existing verified paths, "sees only flushed transcript" disclosed); RISK: PTY resize mid-turn of the main Claude (Ink reflow artifacts) has not been measured. Fluency: PASS (ask-first launch, no confirms except Discard). Modularity: PASS if kept in new files and a CatalogModel extension; RISK: the side_of filter must be applied in every list query or hidden children leak into counts and search. CLI-update resilience: PASS (documented flags --resume/--fork-session/--session-id/--permission-mode, feature-detected from help, drift journaled, no private-file copying); RISK: --fork-session with --session-id and the hook's SessionStart source are inferred, not verified here (`claude --help` 2.1.300 confirms --fork-session and --session-id exist separately). Ownership: PASS (child in its own run scope, Stop/Quit verified, deletion via ConversationDeletion). User authority: PASS (user opens it; the child inherits LOOM_CLI so it could still raise an open-session request, which keeps its approval card). Contract: the child IS the real CLI in a PTY, so the "terminal is never replaced by a custom chat UI" rule is not touched; D-34 ("no right sidebar now, side chat later") is what must be lifted; contract section 13 already lists "side chat and right panel" as an unscoped wish.

## Value for the user (4/5)

The side chat is the user's oldest wish and fits a heavy multi-agent workflow (ask "why did you do that" without derailing a long turn, with tools and a persistent thread, which native /btw lacks), but the generic panel with subagents, changes and notes tabs adds little: subagents are already served by the sidebar tree and transcript panel, and the others are separate ideas, so the whole of I-10 as written is about a 3 and the side-chat core is a 4.

## Depends on

- D-34 must be lifted by the user (right pane allowed); contract section 13 moved into scope
- Loom 0.4.4 existing parts: startConversation(opening:) start path, SessionEventHub hook state, ConversationDeletion, SubagentTranscriptView (only if a subagent-beside tenant is added)
- Optional later pairing: a usage-by-source line so side chats appear in the Usage page

## Experiments before building

- E1 fork launch, isolated CLAUDE_CONFIG_DIR, loom-fake-provider for plumbing then 2-3 short real turns (D-04): does `claude --resume <id> --fork-session --session-id <new-uuid> --settings <hooks> -n <title> -- <prompt>` start, create a new transcript, leave the parent untouched, and deliver SessionStart (which source value) plus a registry entry for the new id? Decides whether the route can reuse the `.new(uuid)` identity path or needs adoptConversation(.bind). Fails -> use `--resume --fork-session` without --session-id and bind from SessionStart.
- E2 prompt cache: start the fork inside the cache TTL and read cache_read_input_tokens versus fresh input in the fork's first assistant usage record; repeat with --permission-mode plan, with --disallowedTools, and with --tools restricted. Decides the read-only mechanism and the cost hint. A low hit ratio is not a blocker, it just means the hint must be honest.
- E3 fork while the parent is mid-turn (tool call in flight) and just after a Stop: does resume load cleanly, and what does the fork see? Decides whether to fork only from the last finished turn or accept a half-written tail.
- E4 resize and width, user machine idle: one SIGWINCH of the main Claude during a streaming turn when the pane opens/closes, and a Claude TUI at 44-56 columns. Decides split vs slide-over vs auto-collapse-sidebar. Measure by screenshot of scrollback artifacts and by SwiftTerm resize counters; also confirm the coalesced resize task (TerminalSurface.resizeTask) sends one resize per drag settle.
- E5 no-code baseline for the user: use native /btw (no tools, no history, works mid-turn) for a week; if it covers most side questions, shrink this to a keyboard shortcut or defer the fork pane.

## Questions for the user

- Lift D-34 for a right pane, and is a side-by-side split acceptable even though it narrows the main terminal and resizes its PTY (P1 deliberately avoided resizing), versus a slide-over that covers terminal columns, versus a plain extra tab (D-33 tabs) with no layout change?
- When the pane opens at the default 1220 pt window, may Loom collapse the sidebar automatically?
- Side session permissions: read-only by default with an Allow edits toggle (plan mode), or full tools; and forbid subagents by boundary text only?
- Should a side session stop itself after N idle minutes (the user's own 'goes inactive after a while'), given D-38 says running sessions are never stopped for inactivity?
- On close: keep the hidden record (reachable from the parent, promotable) or delete it; and does a side session count toward Cmd+J, the Dock badge and the menu bar when it needs approval?
- Is native /btw enough for most side questions, i.e. does the user really need tools and a persistent thread, which is what justifies the fork pane?
- Is there any appetite for the other tabs (Changes, agent note), or is the pane only for side chat; if only side chat, skip all tab machinery?
