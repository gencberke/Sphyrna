# I-38: Handoff and session reference (bounded digest, fresh session, fresh reviewer)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Handoff and session reference (bounded digest, fresh session, fresh reviewer)** · verdict **adopt-light** · cost M · value 3/5 · proposed by 5 reports: [t3code](../products/t3code.md), [power-user-workflows](../products/power-user-workflows.md), [zed](../products/zed.md), [vibe-kanban](../products/vibe-kanban.md), [persistence-remote-orchestration](../products/persistence-remote-orchestration.md).

> Build a token-free, user-initiated, bounded session digest (snapshot file in a Loom-owned cache, pasted unsent into a live prompt or used to seed a fresh handoff/reviewer session) and skip the agent-driven /handoff automation and any live or agent-initiated reading, because the digest layer is cheap and fits every principle while the automation adds state machines for little gain over the user's own skill.

## What the user gets

Feed one session's work into another without a messaging channel: drag a card into another session or use 'Reference session' to paste a small bounded reference (transcript path plus a generated markdown digest of title, last N turns, truncated tool bodies, files touched); a 'start fresh session with a handoff note' action when context is heavy (via the user's own skill / Obsidian); a user-initiated fresh reviewer (second-opinion) session. Costs no tokens until the agent reads it.

## Mechanisms found in the research

Digest written under a Loom-owned cache from the incremental transcript reader; only an id/path goes in the prompt and the agent reads on demand (T3 @thread chips + t3_thread_read); preview what will be referenced (secret-leak risk across projects); handoff brief template with zero-context assumptions (Paseo); handoff delivery via the open-session flow with verified delivery; Zed 'New From Summary' as the UX precedent; the compact/new-session hint tied to I-23.

## Debates and fact-check corrections

Handoff vs /compact: the compaction-threshold advice in the research varies (35-40%, 50%, 100-120k, 500k, 700k clusters; the cited 40-50% is one of several). User-initiated, read-only and bounded keeps cross-session authority clean. Skip T3's cross-environment export complexity.

## Design in Loom


DESIGN IN THREE LAYERS (each shippable alone; L0+L1 are the "light" core, L2 is optional in the same slice).

Layer A, core, no UI (LoomCore, new `SessionDigest.swift` + `SessionDigestStore.swift`):
- Trigger: only a user action (menu item, drag start, or "Start fresh session" sheet). No watcher, no timer, no hook subscription. Nothing runs when nobody asks.
- Locating the source: the Claude conversation id of the card (the same id `row.claudeSessionID` feeds "Copy Claude Session ID") is resolved to `<projects>/<encoded cwd>/<id>.jsonl` with the existing by-name finder `ClaudeTranscriptEffort.transcript(conversationID:projectsDirectory:)` and `SessionRuntime.claudeProjectsDirectory()`; then the same safety rules as `SubagentTranscriptLocation.resolve` (realpath inside the profile's `projects` folder, `O_NOFOLLOW`, regular file of this user). Today `SubagentTranscriptLocation` only accepts `…/subagents/agent-<id>.jsonl`, so a sibling `SessionTranscriptLocation` (main file shape `projects/<folder>/<id>.jsonl`) is needed; the open-descriptor code in `SubagentTranscriptFile.openDescriptor()` can be shared.
- Reading: one cold read, bounded. `SubagentTranscriptTail` already does "last 512 KiB from a line start plus the first line, only whole lines, lines over 128 KiB skipped, shrink/inode replace handled"; use it once (no feed, no `SubagentTranscriptFeed`), with a larger cold window for a main transcript (about 1 MiB, tunable). The first line is delivered too, which for a main session is not the goal (see E2), so the digest also takes the first real user prompt from the head. Reading runs on a utility queue, never MainActor, and the read is a `pread` loop, so it holds no lock on Claude's file and cannot disturb the running CLI.
- Parsing: reuse the `SubagentTranscriptParser` shape (memmem gate before decode, narrow Decodable that never decodes `toolUseResult`, strings clipped at 4 KiB, tool results reduced to first line + line count + isError, tool calls reduced to the main argument). It must be extended or sibling-ed for the main file: it has no `isMeta` / `isCompactSummary` / `isSidechain` fields and treats every user text as `.brief`, so system reminders, slash-command echoes and the compaction summary would leak in as "user prompts". Those line kinds are hypotheses from the format, not verified here (see E2). Anything unknown yields nothing, as the existing parser does.
- Output (versioned markdown, hard cap about 16 KiB, about 4-5k tokens): header (source title, project, branch, ticket key if any, Claude session id, transcript path, snapshot time, state at snapshot, "last N of M turns", "turn in progress: yes/no"), the first user prompt (goal), the last N turns (default 8) as user text / assistant text / one-line tool calls / truncated tool results, the last assistant message in full up to 3 KiB, and "Files touched" (unique paths of Edit/Write/MultiEdit/NotebookEdit calls, max 30, separate from "files read"). A compaction summary, if found in range, is quoted once and labelled. Parse yields zero turns -> no file is written and the UI says "Loom could not read this session's transcript format" (journal `cli_compat_warning`), never an empty reference.
- Secret hygiene: best-effort redaction of common token shapes in tool-call arguments and text (sk-, ghp_/github_pat_, AKIA, "Bearer ", PEM headers, password=/token= values), stated as best-effort in the preview. The main leak surface is the Bash command first line in `toolCall` arguments; tool bodies are already reduced to first line + count by design.
- Store: `<data root>/handoffs/` (data root is `~/.loom` or `~/.loom-dev`; the same root as `<data root>/claude-plugin`), dir 0700, files 0600, name `<source short id>-<yyyyMMdd-HHmmss>.md`, written atomically (as `ClaudeLoomPlugin.install` does). Bounds: 32 KiB per file, at most 24 files, 7-day age, pruned on write and at launch. It is a derived, bounded digest, not a second copy of the transcript (contract section 7: "a second copy of the transcripts must not be kept"; this is the sentence to confirm with the user).
- Deletion: register with `ConversationForgetters.shared` (`ConversationForgetting.forget(sessionID:providerIDs:)`, called in the verifying step of `ConversationDeletion`) so permanently deleting the source session removes every digest made from it, idempotently, and a failure keeps the deletion open like other registered components. Digests record the Loom session id in a sidecar-free way (filename prefix), so no new catalog table is needed. Content already pasted or read into another session's transcript is outside deletion scope by contract section 8 ("Content sent to another session ... not deleted"); the preview says so in one line.

Layer B, reference into a live session (LoomCatalogUI + LoomTerminal, thin):
- Entry points: (1) "Reference in Prompt" and "Copy Reference" items in the card context menu and the detail header actions menu, next to the existing `SessionLocationMenuItems` group (Reveal in Finder, Copy Claude Session ID, Copy Resume Command); (2) dragging a card onto the terminal. For (2) the card supplies the digest as a lazily produced FILE URL, so the existing `TerminalSurface` drop path (`registerForDraggedTypes([.fileURL])`, `performDragOperation` -> `insertDroppedFiles` -> `pasteText`) inserts the path with no new drop code and no custom pasteboard type crossing the SwiftUI/AppKit boundary. The digest is only generated when the drop is accepted (NSItemProvider file representation), not at drag start.
- What goes into the prompt: one line, unsent, for example `Context from session "<title>" (snapshot 14:32, <project>): <digest path>`. The user finishes the sentence and presses Enter. Loom never writes a carriage return. This is deliberate: the contract says "Bracketed paste does not prove that the target is in the right prompt field or that it accepted the task", so Loom only claims "inserted into the prompt, not sent"; delivery is proven the way it already is, by the next UserPromptSubmit hook turning the card to Working.
- Target gating (the important safety rule): paste only into a live run whose indicator is at a prompt (Ready, Waiting for you, Finished; `SessionIndicator` in `SessionDisplay.swift`). Refuse for Needs approval (a dialog with numbered choices is listening: pasted characters could answer it), Failed, Problem, State unknown, Identity unclear and any session without a live terminal (ended screen, stopped, idle record). Never resume a stopped session just to receive a reference (no live terminal for idle records). Working is allowed because Claude queues typed text; the text still needs the user's Enter.
- Preview: a small popover (not a modal) before the first insert/copy of each digest shows the first 25 lines, byte size, "from project A into project B" when the projects differ, "snapshot; the source may have moved on", and Insert / Copy / Reveal buttons. This is the secret-leak check the idea asks for.

Layer C, fresh session seeded from a session (optional, same slice if cheap): "Start Fresh Session From This..." and "Start Fresh Reviewer..." in the same menus, one sheet with an editable title, an editable first-message template and the preview. It starts through the existing start path: a user-initiated sibling of `approveOpen` that calls `SessionRuntime.startConversation(provider: .claude, projectID: <same project>, opening: SessionOpening(...))` -> `ProviderLaunchProfile.claude(... opening:)` -> `-n <title> ... -- <message>`. `SessionOpening.openedBy` is the source session, so the card's existing origin line ("from <session>", D-39 S2) shows the lineage with no new UI. The message is short and zero-context: goal, "read <digest path>", "the source session's work is in this folder; run git status/diff yourself", plus an optional line the user types or a note path the user's own skill produced. Delivery is verified by the normal hook/state path (SessionStart then UserPromptSubmit/Working); a failed start is reported by the existing `RuntimeLaunch` error path and never retried.
- Reviewer variant: same folder, fresh context, template says "review, do not edit"; optional launch flags from `claude --help` 2.1.300 (verified present in help): `--permission-mode plan` for CLI-enforced read-only and `--add-dir <digest dir>` so the new session can read the digest outside its cwd without a prompt. Both are gated on the help text like the other capabilities (`ProviderCapabilities`), passed anyway if help drifts, journaled by the existing `missingRequiredClaudeOptions` pattern. Both change CLI behaviour, so they are user decisions (D-20 class), default off until decided.
- Not built: typing `/handoff` into the old session and waiting for Stop to harvest a path. Loom would have to parse model prose for a path (a guess presented as a verified outcome) and run a delivery-then-completion state machine across two sessions. The user's own skill already writes the note; the sheet just lets the user attach that path or text in one field.

Cost accounting for the idea as written (M stays honest): digest builder + location + parser extension + tests on fixture lines about 40 percent, store + forgetter + cleanup about 15 percent, menus/popover/drag provider/paste gating about 25 percent, fresh-session sheet + start path + templates about 20 percent. Layer A+B alone is S-M; the research's "S" for the reference alone is right only if the digest quality is accepted as is.


## Where it shows


- Card context menu and detail header actions menu get a "Reference" group right after the location group: "Reference in Prompt" (disabled with a tooltip when the target session is not at a prompt), "Copy Reference", then "Start Fresh Session From This...", "Start Fresh Reviewer...". "Reference in Prompt" targets the session currently shown; from a card of another session it targets the selected session; a card's own menu on the selected session offers only Copy and Start items.
- Drag: pick up a sidebar card, drop it on the terminal. The terminal highlights as for a file drop and the one-line reference appears in the prompt, unsent. Dropping on a Needs-approval or ended terminal shows no drop target.
- Preview popover anchored to the menu origin: title row (source title, project chip, snapshot time), 25 lines of the digest in monospace secondary text, a cross-project notice line in attention orange only when projects differ, buttons Insert / Copy (accent filled is Insert) and a quiet "Reveal". Copy in DESIGN section 6 voice: sentence case, "Inserted into the prompt. Not sent." / "Could not read this session's transcript."
- Fresh-session sheet: title field, first-message text editor (template filled in, editable), a "Digest" disclosure with the same preview, optional "Your handoff note" path field, for the reviewer two checkboxes (Read-only, Allow reading the digest folder), Cancel / Start Session. Return does not start it (same rule as the open-session box). The new session appears as a normal card with the origin line.
- No new persistent surface, no badge, no sidebar section, no animation, theme tokens only (checked by scripts/check-theme-literals.sh and check-user-wording.sh: "session", never "conversation").


## Principle check


- Resources: PASS. On-demand only; one bounded pread (about 1 MiB cold window, 128 KiB per-line cap, 16 KiB output); no watcher, timer, poll or process; nothing drawn when hidden; idle cost is zero. RISK: a per-card `.draggable` modifier on every sidebar card could add body evaluations to the list, which Loom guards with counters (`SidebarRenderProbe`, H1-D card-invalidation work); measure card body counts before and after, and attach the provider lazily.
- Predictability: PASS. Explicit gestures only, versioned digest format, deterministic caps, snapshot semantics stated in the file header ("snapshot at 14:32, turn in progress: yes"). Never changes the meaning of Enter (T3's default-on Compact chip backlash, #17467, is the cautionary tale in plans/v2-research/products/t3code.md fact-check).
- Accurate status: PASS if worded strictly. Outcomes are "copied", "inserted into the prompt, not sent", "digest written" and for a fresh session the normal verified start/Working state; never "delivered" or "handed off". A transcript that cannot be parsed produces an error, not an empty digest. RISK: transcript lines flush asynchronously (the tail comment says every 100 ms, and the power-user note says the hook's transcript_path can lag memory), so a Working source yields a stale tail; the header flags "turn in progress" and the UI says so.
- Fluency: PASS with one friction to measure. No confirmation dialogs; the popover is the only step and is dismissible. RISK: a live session reading a file outside its cwd may raise a permission prompt (to be tested in E1); fresh sessions can avoid it with `--add-dir`, live ones cannot without changing settings.
- Modularity: PASS. LoomCore holds a UI-free `SessionDigest` + `SessionDigestStore`; LoomCatalogUI adds views and the controller intents; no new target, no upward dependency; the start path is the existing `startConversation(opening:)`. If v2 becomes chat-centred, the digest layer is reused unchanged and only the menu/drag layer is replaced by composer chips (T3 pattern).
- CLI-update resilience: PASS with discipline. The transcript format is private and drifts: defensive parser (unknown -> nothing, zero turns -> visible error + `cli_compat_warning` journal), no field is required except what the digest degrades without. Launch flags used (`-n`, `--`, optionally `--add-dir`, `--permission-mode`) are in `claude --help` 2.1.300 and follow the existing help-text gating; nothing pinned. The idle-compaction toggle (v2.1.302) means a source may contain a compaction summary the parser must label, not choke on.
- Ownership: PASS. No process spawned or adopted; files only in Loom's data root, removed on source deletion through `ConversationForgetting`, aged out otherwise. The files are readable by any same-user agent that knows the path, which is not new exposure (the transcripts themselves are). Contract section 7 "second copy of the transcripts must not be kept" is the sentence to settle: the digest is capped, derived and expiring, but it is a content copy, so it needs the user's explicit nod (user_decisions).
- User authority: PASS and this is the idea's main merit. Every reference is a user click or drag; read-only; no agent can ask for another session's content in this design; a pasted line is inert until the user presses Enter. Agent-initiated or standing access is exactly what contract section 7 reserves for the CP3 channel and is not smuggled in. Cross-project note shown in the preview.
WHAT WOULD MAKE IT A VIOLATION, AND THE AVOIDANCE: (1) a live or auto-refreshing reference (continuous tailing of the source) -> snapshot only; (2) model-written summaries (Zed's New From Summary and Agent view's row summaries cost tokens/quota and are not the user's choice) -> mechanical digest only; (3) typing into other sessions or pressing Enter for the user -> paste unsent, at-prompt states only; (4) answering a pending approval by accident -> refuse Needs approval; (5) an agent-callable read tool without per-grant approval -> out of scope here; (6) harvesting the handoff note path by parsing prose -> user supplies it; (7) unbounded cache or surviving deletion -> caps, TTL, forgetter.


## Value for the user (3/5)

Real but second-order for this user. Multi-session, multi-project work with ticket keys makes planner-to-implementer and writer-to-reviewer handoffs common, the official Writer/Reviewer pattern is endorsed in the research, and drag-a-card is a delightful, token-free gesture that also becomes the seed of the CP3 channel (D-43/D-46). But a mechanical digest (last N turns, truncated tools) is a worse handoff than the note the user's own skill and Obsidian vault already produce ("things not to redo", decisions), loom:open-session already covers agent-initiated handoff with user approval, and a fresh reviewer is about three clicks today (New session, type the skill). The unique value is the zero-typing reference/seed and the lineage line, not the digest quality. The compaction-threshold advice in the research varies (35-40%, 50%, 100-120k, 500k, 700k), so no threshold-based nudging is encoded here.

## Experiments before building

- E1 permission friction (isolated CLAUDE_CONFIG_DIR, temp project, short real turns allowed by D-04): ask a session to read a markdown file that lies outside its cwd. Observe (a) whether a read prompt appears, (b) whether launching with `--add-dir <that folder>` removes it, (c) whether an `@path` mention or a bare pasted path behaves differently. Decides: whether live-session references need a documented 'approve once' note, whether fresh sessions get `--add-dir` (a user decision), and whether the data-root location is acceptable or the digest must live somewhere else.
- E2 main-transcript line shapes (isolated profile, a handful of real turns including a tool turn, a slash command, /clear, /compact, a subagent, an error turn; dump line types and key names only, never user data and never the real ~/.claude): confirm whether isMeta, isCompactSummary, isSidechain, a 'summary' line type and system/attachment lines exist and what a genuine user prompt looks like versus injected text; also check how far the file lags a Working session. Decides: filter rules, whether `SubagentTranscriptParser` can be extended with a few optional fields or needs a sibling, and the 'turn in progress' warning.
- E3 digest usefulness (cheap, human-judged): build digests by hand from 3 representative finished sessions (ticket work in a work project, a planner session, a long debugging session), start a fresh session with only the digest path, and see whether it continues or reviews without re-asking basics; compare with pointing it at the raw transcript path and with the user's own /handoff note. Decides whether Layer C (fresh handoff session) ships or only Layers A+B (reference/reviewer), and the right N and byte caps. If the user's skill-based note clearly wins, drop the handoff template and keep the reviewer and reference only.

## Questions for the user

- Is a bounded content digest under Loom's data folder acceptable given contract section 7's sentence that a second copy of the transcripts must not be kept (capped at 16 KiB, 24 files, 7 days, deleted with the source session)? If not, the fallback is path-only references (transcript path plus session id) with no digest file, which is weaker and exposes raw jsonl.
- May fresh handoff and reviewer sessions start with `--add-dir <Loom digest folder>` and the reviewer with `--permission-mode plan`? Both change CLI behaviour (D-20 class); the plan-mode default and the 'read-only' wording are the user's call.
- Should a fresh handoff successor inherit the source's ticket key? (Ticket de-dup picks the oldest match, so the source stays the target of `loom:open-session`; the reviewer probably should not carry the key.)
- How much does the user trust a mechanical digest versus their own /handoff skill note? Decide after E3: keep Layer C, or reduce it to 'open a fresh session with this note path'.
- Should an agent-readable `$LOOM_CLI read` verb (user grants access per reference, expires) be the follow-up that turns this into the first CP3 slice, or stay file-based?
- If v2 moves to a chat-centred UI, are references expected to become composer chips (T3 style)? The design keeps the digest layer UI-free for that reason.
