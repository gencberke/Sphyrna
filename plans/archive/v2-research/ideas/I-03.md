# I-03: Native composer overlay with per-session drafts and delivery receipt

Card from the [Loom v2 idea catalog](../IDEAS.md). **Native composer overlay with per-session drafts and delivery receipt** · verdict **spike-first** · cost M · value 3/5 · proposed by 3 reports: [superset](../products/superset.md), [warp](../products/warp.md), [codex-app](../products/codex-app.md).

> Worth building only as a small, optional helper on a verified send path (paste with a bracketed-paste gate, separate Enter, a UserPromptSubmit receipt), and two real-CLI spikes must first decide the shape: Claude's documented Ctrl+G external-editor hook that nobody in the research saw, versus direct PTY injection. Drop @file, images, persisted drafts and auto-open.

## What the user gets

A native multi-line editor (shortcut) for long structured prompts: @file completion from the session cwd, pasted images saved to a file and referenced by path, a draft per session, optional auto-open when a session finishes. The card says 'submitted' only when the hook arrives, else 'not submitted yet, press Enter' with the draft kept.

## Mechanisms found in the research

NSTextView overlay that exists only while open; plain text only; send = I-01 (bracketed paste + separate Enter); drafts in memory, optionally persisted on quit; never opens or sends while Needs approval; receipt from UserPromptSubmit within a window, never auto-retry Enter. Image paste = file path (clipboard + Ctrl+V into the TUI is hacky). Warp auto-opens its rich input on InProgress/Success/Failed/Cancelled and closes it on Blocked.

## Debates and fact-check corrections

Contract tension: the user's rule that the terminal is never replaced; the overlay loses CLI vim mode and slash-command completion, so keep it optional. Claude input changes (mode-switch prefixes ! and &, paste-burst heuristics) forced Warp special cases. power-user-workflows lists 'a custom composer that replaces the CLI prompt' under do-not-build; this is the lighter helper variant. Confirmation timeout can false-alarm on slow hooks (UserPromptSubmit default timeout 30 s).

## Design in Loom

FACTS FROM THE CODE AND DOCS (observed)
- Loom has no way yet to put app-originated text into a session. The only app-side write is the evidence hook `ConversationController.typeForEvidence`, which calls `TerminalSurface.send` (Sources/LoomCatalogUI/ConversationController.swift). Every write goes through one ordered `TerminalInputQueue` (4 MiB cap, visible rejection, no silent drops; Sources/LoomCore/TerminalInputQueue.swift). `TerminalInputGate` closes it for a deleting or stopping run, so a late composer send is refused visibly.
- Image paste is already handled. `LoomTerminalView.paste` forwards an image-only clipboard as Ctrl+V, and dropped files insert quoted paths (Sources/LoomTerminal/TerminalSurface.swift ~l.362-452). Claude documents Ctrl+V as inserting an `[Image #N]` chip. The overlay's "image becomes a file path" feature adds almost nothing on top of that.
- Receipt plumbing half exists. `ClaudeHookEvent` parses UserPromptSubmit, `prompt_id` and a `promptIsSynthetic` flag, but it throws the prompt text away (Sources/LoomCore/ClaudeHook.swift). `ClaudeSessionAdapter` handles `.userPromptSubmit` (ProviderSessionAdapters.swift ~l.268). `ClaudeHookStateTracker.receive` sets Working. `SessionViewState` and `SessionEventChange` (SessionEventHub.swift) carry no "a prompt was accepted" signal.
- The hook helper runs with `timeout: 1` and is synchronous (ProviderLaunchProfile.claudeSettings), not the 30 s default in the debate note. UserPromptSubmit fires before Claude processes the prompt, so on an idle session the latency is tens of ms. The risk is not a slow hook but the session state at send time.
- "Waiting for you" cannot tell a prompt apart from a dialog. `ClaudeHookStateTracker.notificationActivity` maps idle_prompt, agent_needs_input and elicitation_dialog all to `.waitingForInput`. Only `.atPrompt` (SessionStart) and `.turnComplete` (Stop) reliably mean the input box is up. A paste plus Enter into an AskUserQuestion or plan dialog could answer it wrongly. That is worse than an unsent draft.
- SwiftTerm `pasteText` only wraps the text in 200~/201~ when the program has enabled mode 2004 (`Terminal.bracketedPasteMode`). Without it, newlines go out as `\r`, which submits every line. The composer must refuse to send unless `bracketedPasteMode` is true, and must sanitise its own text rather than rely on `pasteText`'s `allowUnsafe` fallback (AppleKittyClipboard.swift l.136-144).
- Claude 2.1.300 docs (code.claude.com/docs/en/interactive-mode, fetched via tinyfish): Ctrl+G or Ctrl+X Ctrl+E "opens in default text editor"; the `v` key in the transcript viewer opens `$VISUAL` or `$EDITOR`. Messages typed while Claude works are queued and shown grey until sent; Ctrl+Enter sends them at once. Multi-line paste is a documented input method. Issue #18990 (closed) showed Ctrl+G once auto-detected IDEs and ignored `$EDITOR`; current behaviour is unverified.
- Slash commands that Claude runs locally (/clear, /model, ...) fire no UserPromptSubmit. A receipt timer on such a draft would false-alarm.

DESIGN (lightest version)
1. Draft store. `ComposerDrafts` in LoomCatalogUI, in memory only: `[sessionID: String]`, each draft capped at about 100 KB, at most 32 drafts, least recently used evicted. Plain text. Dropped by the existing `ConversationForgetting` hook on deletion (ConversationDeletion.swift) and on Quit. Keep it memory-only because a persisted draft is conversation content that contract §8 deletion would then have to purge and verify. Extend `QuitConfirmation` (SessionNavigation.swift) with "N unsent drafts" so a quit cannot silently lose text.
2. Overlay. A ZStack child in `DetailContent`, floating over the bottom of `TerminalHost`, with opacity-only appearance (DESIGN.md Motion row: a height change would resize the PTY). It is an `NSTextView` wrapper that exists only while open: no timers, nothing drawn when closed or hidden. State is `CatalogModel.composer: ComposerState?` plus a menu item in the Edit or Session menu (a free key such as Cmd+E; check the menu table in UI-MAP.md l.85). Esc closes and keeps the draft. It can open at any state, because writing a draft during Needs approval is useful. Only Send and Insert are gated.
3. Two actions, to keep the zero-risk mode first-class:
   - Insert: bracketed paste only, no Enter; the user reads it in the TUI and presses Enter. Allowed whenever a live run owns the terminal and `bracketedPasteMode` is true.
   - Send: paste, then a single-shot `Task.sleep` (about 150-300 ms, to be set by the spike), then one `\r`, all through the run's `TerminalInputQueue` so order against keystrokes is preserved. Allowed only when activity is `.atPrompt` or `.turnComplete`, hooks are reliable (`providerWorkStateIsReliable`), no approval is pending and `bracketedPasteMode` is true. A draft starting with `!`, `&` or `/` is Insert-only: `!` and `&` switch Claude's input mode, and `/` commands may produce no hook. While the session is Working, Send is disabled; do not claim a receipt for Claude's own queue, whose UserPromptSubmit timing is unknown. This is where I-01 (the shared send primitive) and the Loom-side queue idea connect.
   - Sanitiser: strip ESC and all C0 controls except LF and TAB, normalise CR to LF, remove any 201~ sequence.
4. Receipt, event-driven. Extend `ClaudeHookEvent` to keep a bounded digest of the prompt (SHA-256 of the first and last 256 characters plus the length), never the text. Publish a new `SessionEventChange.promptSubmitted(PromptReceipt)` from `ClaudeSessionAdapter` next to `markProviderUsed`. The change is state-light: `SessionViewState` gets only `lastPrompt: (sequence, digest, at)`. Mind the hub's equal-frame suppression and the SidebarRenderTests hot path: do not feed this into card rows. The composer arms a single 5 s timer at the Enter write. Digest match gives "Submitted". Timer expiry gives "Not confirmed yet - your text may be in the prompt; press Enter in the terminal", with the draft kept. A late match upgrades that to Submitted, so slow hooks never leave a permanent false alarm. Never auto-retry the Enter. A second Enter on an already-submitted, now-empty prompt is harmless. No polling anywhere.
5. Where the receipt shows. Inside the overlay and as transient header text in the existing fixed-height row (like `PreparingNotice` in DetailView.swift), so no layout shift. Not on sidebar cards.

PREFERRED SHAPE IF SPIKE 1 PASSES: a "compose bridge" through the documented Ctrl+G
Set `VISUAL` and `EDITOR` in the run's env (ProviderLaunchProfile.swift ~l.145-153 already sets CLAUDE_CONFIG_DIR, LOOM_HOOK_*, LOOM_CLI) to a small subcommand of loom-hook: `$LOOM_CLI compose <file>`. This follows the existing split in Sources/loom-hook/main.swift, where arguments mean the agent-facing command. The helper connects to the authenticated control socket (the `loom-hook open` pattern, OpenSessionControlServer) and blocks. Loom shows the overlay bound to that file with the CLI's current prompt prefilled. Done writes the file and exits 0, and Claude loads it back into its own input. There is no PTY injection, no readiness guess, and the CLI itself decides whether it is at a prompt. Vim mode, slash completion and queueing stay in the CLI. The helper is a child of claude inside the run scope, so Stop and Quit already own and kill it. Guard against the helper capturing unrelated `$EDITOR` calls (an agent's `git commit` in a Bash tool inherits the env): recognise Claude's prompt temp file, else exec the user's original editor, passed as `LOOM_ORIGINAL_EDITOR`. Make this an opt-in Setting because it changes what Ctrl+G does.

BOUNDS: draft 100 KB x 32, one overlay at a time, one 5 s single-shot timer per send, digest not text, hook payload already capped at 1 MiB (ClaudeHookClient.maximumPayloadByteCount). Idle or stopped records have no terminal, so the composer is unavailable there; a later "Resume with this prompt" can reuse the documented launch path that takes the prompt after the options (open-session flow in ARCHITECTURE.md ~l.168).

WHAT WOULD MAKE IT A PRINCIPLE VIOLATION, AND THE AVOIDANCE
- False success: reporting "submitted" on a PTY write. Avoided by the digest receipt and a neutral "not confirmed" wording.
- Predictability: Enter landing in a dialog. Avoided by the Insert/Send split, the `.atPrompt`/`.turnComplete`-only gate and the bracketed-paste check.
- Resources: a resident editor, a file index or a draft timer. Avoided: the editor exists only while open, no index, no timers beyond the single shot.
- Fluency: auto-opening on Stop would steal focus, and keystrokes meant for another terminal would land in the overlay. Recommend never auto-focusing. At most offer a passive affordance.
- CLI resilience: per-version delay tables as Warp has. Avoided: one delay, plus the receipt as the drift signal (receipts that stop arriving surface as a diagnostics note, like the existing hook-silence watchdog).
- Contract: the terminal stays the real CLI and the overlay is optional. This is the "light helper" variant, not the do-not-build replacement composer in power-user-workflows.md. It needs the user's explicit acknowledgement, because the contract text says the terminal is never replaced.
- Deletion: persisted drafts or saved images would add a deletion obligation. Avoided by memory-only drafts and no image files.

COST (honest for this codebase)
- Light version (overlay, Insert/Send, sanitiser, draft store, receipt, tests, doc updates): M (about 1 slice). Pieces: TerminalSurface paste/send API plus sanitiser, S. Hook digest, hub change and adapter publish, S-M. Overlay, model state, menu item, header text, M. The repo's tests, evidence run and doc requirements (ARCHITECTURE, UI-MAP, DESIGN) add a meaningful share.
- Compose bridge on top of the light version: +M (helper subcommand, control-socket request type, env wiring, setting, EDITOR fallback).
- Full original idea (@file completion, image files, persisted drafts, auto-open): L, and several of those parts break the principles above.

## Where it shows

Shortcut (for example Cmd+E) opens a bottom-anchored panel over the selected session's terminal. It is a rounded Surface.panel card, about 30-40 % of the terminal height, 12 pt inset, fade-in only, no resize of the PTY. Contents: a plain multi-line mono NSTextView, a footer with a character count, an Insert button, a primary Send button, and a one-line state text.

State text, in order of precedence:
- "Waiting for approval - Insert or Send is off"
- "Working - Insert only"
- "Sent - waiting for Claude" (neutral, no spinner)
- "Submitted" (fades after a few seconds)
- "Not confirmed yet - press Enter in the terminal; your text is kept"

Esc closes the panel and keeps the draft. A small "Draft" dot sits in the header chip row of that session only, not on sidebar cards. Return does nothing special: Cmd+Return sends and Return inserts a newline. A `!`, `&` or `/` first character shows "Insert only" with a one-clause reason.

If the compose bridge passes the spike, Ctrl+G in the terminal (or a Loom menu item that sends ^G) opens the same panel prefilled from the CLI's prompt file, with a single Done button in place of Insert and Send.

## Principle check

Resources (pass): memory-only drafts, NSTextView only while open, a single-shot timer, no index, no polling. The hook already arrives, so the digest costs one hash per prompt.
Predictability (risk, mitigated): the TUI input state is not directly observable. Gate on `.atPrompt`/`.turnComplete`, hooks reliable and `bracketedPasteMode`; Insert is the zero-risk default; Needs approval and Working disable Send.
Accurate status (pass, if the digest receipt is implemented): "submitted" only on a matching UserPromptSubmit; the neutral "not confirmed" and the late upgrade avoid false alarms. A digest mismatch or a hook-silence state is shown as unconfirmed, never as failure.
Fluency (risk): no auto-open and no confirmations; the optional overlay adds one shortcut. Auto-open on Stop is a focus-steal hazard.
Modularity (pass): the send/receipt primitive is shared with I-01 and the queue and diff-comment ideas; the overlay is a thin UI on it; the helper subcommand follows the existing loom-hook split.
CLI-update resilience (risk, bounded): bracketed paste, mode 2004 and `!`/`&`/`/` input behaviour are TUI behaviours, not a contract. The receipt turns breakage into a visible signal. The Ctrl+G route uses a documented key and `$VISUAL`, but its IDE auto-detection history needs verification.
Process ownership (pass): writes go to the Loom-owned PTY only; the compose helper lives in the run scope.
User authority (pass): every send is the user's own action in the focused app; nothing crosses sessions.
Contract: the "terminal never replaced" rule is only touched by an optional helper; keep it opt-in and say so.
Deletion contract: pass only with memory-only drafts and no saved images.

## Value for the user (3/5)

Real but modest for this user. They write long ticket prompts across several sessions, and a multi-line editor with per-session drafts is a comfort gain. But the CLI already offers Ctrl+G, multi-line paste, Ctrl+V images and message queueing, so the new value is mostly Loom-side (a draft that survives a session switch, and a verified receipt). The receipt matters more as foundation for non-focused sends (queue, cross-session, side-chat or diff comments) than for a focused overlay where the user sees the TUI react. If v2 becomes chat-centred, the composer is rebuilt as the main input, so the reusable asset is the send primitive plus receipt, not the overlay. Not on the user's stated wish list; the research's "wish list" claim in warp.md is the researcher's inference.

## Experiments before building

- SPIKE 1, Ctrl+G bridge (decides Variant A). In an isolated CLAUDE_CONFIG_DIR with a throwaway project, run Claude 2.1.300 in a PTY (loom-probe pattern: Sources/loom-probe/ClaudeQ1Experiment.swift) with VISUAL and EDITOR pointing at a script that logs argv, cwd and the file contents, then rewrites the file. Questions: (a) does Ctrl+G honour VISUAL/EDITOR or pick an IDE; (b) what is in the temp file; (c) is the edited text loaded into the input box or auto-submitted; (d) does the TUI use the alternate screen, and does Loom's screen capture and resize cope; (e) does the editor child land in the run scope; (f) do Bash-tool subprocesses inherit the env and call the editor (git commit without -m). Decides: if (a) and (c) pass, build Variant A and make direct injection optional; if Ctrl+G ignores the env, fall back to Variant B.
- SPIKE 2, direct paste plus delayed Enter with receipt (decides the Send delay and gates). Same isolated setup with real Claude, driving `TerminalInputQueue` bytes. Matrix: idle at prompt and just after Stop; a 100 KB multi-line text; text beginning with `!`, `&` and `/`; while Working (what does Claude's own queue do, and when does UserPromptSubmit fire for a queued message); with a permission dialog; with an AskUserQuestion or plan dialog (does `.waitingForInput` plus bracketed paste plus Enter answer it); right after SessionStart before mode 2004 is on (does `bracketedPasteMode` flip as the gate expects). Measure the minimum safe gap between the paste and Enter and the hook latency distribution. Decides: the delay constant, whether `.waitingForInput` is Insert-only, and whether Working may Send at all. Both spikes follow DEVELOPMENT.md rules: isolated config dir, never the real ~/.claude, light runs unless the user says the computer is idle.
- Check that the digest approach works with the real payload: confirm the UserPromptSubmit `prompt` field is the exact text Claude received after paste expansion ([Pasted text #N] placeholders, trailing newline handling); otherwise match on length plus a prefix hash only.

## Questions for the user

- Is the contract exception acceptable: an optional native editor over the live terminal, never replacing the prompt, even though the user is open to a chat-centred UI? If v2 goes chat-centred, should the composer wait and be built as that UI's input instead?
- Should Ctrl+G be allowed to open Loom's editor (the compose bridge changes the user's EDITOR/VISUAL behaviour inside Loom sessions), or should Loom only inject text?
- Is losing unsent drafts on Quit acceptable with a warning (memory-only), or should drafts persist (which adds a deletion-contract obligation)?
- Drop @file completion, image saving and auto-open from v1? Recommended: yes, since Claude's own @ completion and Ctrl+V images already exist, and auto-open risks stealing keystrokes.
