# I-28: Read-only diff / Changes pane per session

Card from the [Loom v2 idea catalog](../IDEAS.md). **Read-only diff / Changes pane per session** · verdict **adopt-light** · cost M · value 3/5 · proposed by 14 reports: [orca](../products/orca.md), [conductor](../products/conductor.md), [claude-official](../products/claude-official.md), [codex-app](../products/codex-app.md), [superset](../products/superset.md), [paseo](../products/paseo.md), [warp](../products/warp.md), [zed](../products/zed.md), [cursor](../products/cursor.md), [emdash](../products/emdash.md), [vibe-kanban](../products/vibe-kanban.md), [t3code](../products/t3code.md), [review-git-loop](../products/review-git-loop.md), [power-user-workflows](../products/power-user-workflows.md).

> Build the cheap half now (an owned, bounded `git` read that gives a '+N -M, K files' chip on the card and header plus Copy patch / Open in editor), and keep the full in-app Changes pane behind an experiment, because Claude's own /diff already overlaps it and the chip is where Loom's unique triage value is.

## What the user gets

See what the agent changed without leaving Loom: a Changes pane for the session's cwd/branch (Unstaged, Staged, Branch vs base, Last turn), '+N -M in K files' on the card so you triage which finished session to open first, and 'Open in editor' / 'Copy patch'. No accept/reject, no editing.

## Mechanisms found in the research

Lightest: diff-stat chip + open-in-editor/GitLab, a files-changed list (from PostToolUse Edit|Write|MultiEdit payloads per turn and `git diff --stat`). Pane: git CLI plumbing only (`git --no-optional-locks diff --no-ext-diff --no-textconv --no-color -z`, against HEAD or merge-base; never -uall, Superset #6004), run on demand when the pane opens and once after Stop/UserPromptSubmit, FSEvents only on the visible worktree with a debounce (Claude's own /diff mod: 150 ms debounce, 2 s HEAD poll only while seen, 5 s git timeout, 10 redraws/s; Emdash moved to 1 s; Orca 125 ms), hard caps on files/lines, cancel on leave, virtualized native text rendering, skip binary/generated, renames/quoting handled (Paseo's long diff-fix list shows parsing is hard). Syntax highlighting adds a dependency. Claude's built-in terminal /diff panel (2.1.287+, fullscreen, 110+ columns) already has per-turn source picker T1/T2 and an 'ask' button that attaches a file diff to the next prompt, so overlap is real.

## Debates and fact-check corrections

Most-proposed capability and the user's largest gap, but power-user-workflows argues AGAINST a diff viewer (Anthropic Desktop already ships diff, preview, PR monitor; generation is no longer the constraint, human review is, so build light aids only: diff-stat chip, tests-changed flag, open in IDE/GitLab, user-started fresh reviewer session). Competitors converge on 'git CLI, on demand, bounded'; their CPU pain came from watchers and polling (Superset per-workspace watchers/git fan-out and -uall; Emdash 250 ms full scan; Orca). Scope creep toward commit/PR/CI is the named risk; Zed/Cursor/Paseo keep it read-only. Hardest parts: large repos, submodules, line drift after agent edits.

## Design in Loom


FACT BASE (read in the tree)
- Loom spawns no git per card today: `GitBranch.read` is pure file reads, run through `BranchCache` (actor, injectable `Reader`), refreshed on a `turnComplete` frame and on window activation (`CatalogModel.apply` ~l.1360, `setWindowActive` ~l.1026). Only the cleanup review runs git, through `CleanupWorktreeProtection.live` -> `ProcessSupervisor.captureHelper("/usr/bin/git", ..., GIT_OPTIONAL_LOCKS=0)`.
- `captureHelper` is the wrong runner for a per-turn read. `runOwnedJob(scope: .perCall)` opens a whole run scope (LaunchServices `open -n LoomRunHost.app`, coalition, handshake) for every call, polls every 20 ms, and throws (not truncates) over 4 MiB (`LaunchEnvironment.capture`). Right precedent: `ClaudePlanLimitsFetcher`'s `LimitsExchange` (plain `Process`, `CancelFlag`, 4 MiB cap, SIGTERM then SIGKILL by pid).
- `ProviderLaunchProfile.claudeSettings` registers no per-tool hooks on purpose ('each hook spawns a helper'). The idea's 'files-changed from PostToolUse Edit|Write|MultiEdit' therefore contradicts a standing Loom choice. Do not add PostToolUse.
- The hook payload already carries `cwd` and `transcript_path` (`ClaudeHookEvent.workingDirectory/transcriptPath`, ClaudeHook.swift ~l.442). The detail pane already has an 'in place of the terminal' pattern (`viewedSubagent`, `SubagentTranscriptView`, `SessionBackControl`, D-54 P1) that leaves the PTY running and un-resized.

DESIGN (two phases)

Phase 1 (adopt, M): the chip and the exports.
1. New `LoomCore/GitChanges` (no UI): `GitRunner` (plain `Process`, absolute git path, env `GIT_OPTIONAL_LOCKS=0 GIT_TERMINAL_PROMPT=0 LC_ALL=C`, args `--no-optional-locks -c core.quotepath=false -c core.fsmonitor=false`, 5 s timeout, 1 MiB stdout cap that truncates and flags, cancel flag checked in a poll(2) loop, killed on Quit via the runtime shutdown path). Probes, all `-z` plumbing, so no patch-header parsing (this avoids Paseo's quoting/rename bug class): `diff --numstat -z --no-ext-diff --no-textconv --ignore-submodules=all -M HEAD` (tracked, vs HEAD; unborn HEAD falls back to `--cached`), `status --porcelain=v2 -z -unormal --branch --ignore-submodules=all` (never -uall, Superset #6004). Untracked files are counted as 'new' entries without line counts in the chip (cheap, honest); line counts for untracked are read in-process only when the pane opens, capped (<=200 files, <=256 KiB each, NUL sniff = binary).
2. `ChangesStat { added, deleted, files, newFiles, truncated, computedAt, headShort }` or `.unknown` (timeout, not a repo, error). A timeout or failure is shown as no chip or a dim em dash, never as 0 (accurate-status rule).
3. `CatalogModel+Changes` (same shape as `BranchCache`/`refreshBranches`): a `ChangesCache` actor keyed by working directory with in-flight de-duplication and a 1 s minimum gap per folder; an injectable reader for tests. Triggers, all existing events: (a) `turnComplete` frame for that session, (b) selecting a session or opening the pane, (c) window activation for the selected session's folder only. No timer, no FSEvents in phase 1. While the window is hidden, events only mark folders dirty (same collect-while-hidden pattern as `UsageModel`); the next activation reads the selected/visible one. Launch runs no git. `retain()` drops folders no card shows.
4. UI hooks: a `changes` value on `SessionRowModel` (not a shared dict read by every card, which would re-evaluate all cards; the card hot path has render-probe tests, `SidebarRenderTests`). Card: a small secondary '+120 -8' after the branch label in the existing meta row (`SessionCardView`, SidebarView.swift ~l.462-480), shown only when a stat exists and the session is not Working. Header: a `changes` slot in `HeaderFlow` that drops before the branch (`HeaderFlowPlan`). Menu (`SessionLocationMenuItems`, SessionMenuItems.swift l.26): 'Copy Patch' (runs `git diff --no-ext-diff --no-textconv HEAD`, capped, to the pasteboard) and 'Open Changed File...' / 'Open in Editor' (needs the editor decision below).
5. Attribution caveat is part of the design: the number is the FOLDER's uncommitted state, not 'what this session changed'. Two sessions in one folder show the same chip. The tooltip says 'Uncommitted changes in <folder>, as of 14:32', and it is shown for sessions with a live run (a stopped session's folder moves without it).

Phase 2 (spike-first, L): the Changes view.
- In-place swap like the subagent panel (`viewedChanges` next to `viewedSubagent` in `DetailContent`; Esc and the Session control go back). No split, so no PTY resize and no collision with D-34 (right sidebar deferred); the view model is placement-agnostic so it can become a tab of a later right panel.
- Scopes v1: Unstaged, Staged, Branch vs base (merge-base with `refs/remotes/origin/HEAD`, else hidden). Skip 'Last turn' in v1 (see below).
- File list from the -z plumbing above; per-file body fetched lazily on expand: `git --literal-pathspecs diff --no-color --no-ext-diff --no-textconv -U3 <base> -- <path>` (for a rename pass both paths). The body is treated as opaque text and classified by first character, so no `diff --git` header parsing. Caps: 1,000 files listed, 5,000 lines and 256 KiB per file body, 5,000 chars per line (Warp's limits are 4.375 MB / 5,000 / 10,000); binary (`-\t-`) shown as one row; lockfiles, `*.min.*`, `vendor/` collapsed by default.
- Rendering: a read-only `NSTextView` with an attributed string like `EndedScreenView` (selection, copy and find free, no timer), one text view per expanded file section or one capped document. No syntax highlighting (a dependency); line washes only.
- Live while Working: no. The view says 'as of 14:32; refreshes when the turn ends' with a Refresh button. Optional later (separate spike): an FSEvents stream on `.git/{HEAD,index,refs}` only while the view is visible, 300 ms+ debounce, mirroring `UsageTranscriptWatcher`; a worktree-wide stream only if measured cheap on a node_modules/target-heavy repo.
- Snapshot lifetime: only the viewed session's snapshot is held; dropped on leave (cancel in-flight job, free text). Nothing cached for idle records.

'LAST TURN' WITHOUT POSTTOOLUSE (deferred, three options, none for v1)
(a) per-file numstat delta between a baseline taken at UserPromptSubmit and one at Stop (in memory, no repo writes, file-level only); (b) T3/Conductor private git refs via temp index + write-tree + commit-tree + update-ref (writes objects/refs into the user's repo, sparse-checkout and racy-index handling; reject for now); (c) the Edit/Write tool_use entries from the main transcript tail (Loom has `SubagentTranscriptTail`/`Parser`), but the research fact-check says `transcript_path` can lag the hook, and Bash edits are missed (same gap as Claude's own T1/T2, which come from Claude's file checkpoints, not git).

WHAT WOULD BE A PRINCIPLE VIOLATION, AND THE GUARD
- A watcher or timer per session/worktree (Superset #6729/#8108, Emdash 250 ms scan): none in phase 1; phase 2 watch only when visible.
- `git status -uall` or an unbounded diff: forbidden; `-unormal`, caps, 5 s timeout.
- A git process per card on a list reload: git runs only on a turn-complete event or on selection, for one folder, de-duplicated.
- Work while hidden: marked dirty only.
- A git call through `captureHelper` per refresh (a run scope each time): use the plain owned runner.
- Writing into the user's repo (index refresh, refs): `--no-optional-locks`, no snapshots, read-only.
- Scope creep to stage/revert/commit/PR/line-comments-to-PTY: out. Those are separate ideas and carry authority/delivery questions.


## Where it shows


Card (activity and project view): meta row reads `branch-icon main  +120 -8` (secondary text, caption size, monochrome, no new colour), only for a live, not-Working session with a known stat; tooltip 'Uncommitted changes in <folder>, 5 files, 2 new, as of 14:32'. Detail header: a clickable chip `+120 -8 · 5` before the rule; it is the first thing to drop when the header is narrow. Header actions menu gains 'Show Changes', 'Copy Patch', 'Open in Editor'. Phase 2: choosing Show Changes replaces the terminal area (terminal keeps running underneath, no resize); header becomes `Session > Changes` with a segmented scope control (Unstaged | Staged | vs main), a file list on top or left with per-file `+a -d`, expandable unified diff below in the terminal font on the panel colour, add/remove lines marked by a sign column and a very light wash. Esc or the Session control returns. The wash tones are a new colour class and need the user's acceptance (DESIGN §6 allows only one accent, three status hues, one project class).


## Principle check


- Resources: PASS for phase 1 (event-driven, one short git per finished turn or selection, de-duplicated, deferred while hidden, no timer, nothing held for idle records). RISK for phase 2 (rendering large diffs; must keep the caps and per-file lazy bodies; T3 shows the failure mode: 228% CPU / 10 GB GPU with a closed preview panel). Must pass the 'nothing drawn or watched when hidden' check and be measured on the user's two real work repos.
- Predictability: PASS if the chip always says 'folder, as of <time>'. RISK: a folder shared by two sessions shows the same number on both cards.
- Accurate status: RISK, handled by design: stale chip (no watcher), timeout or truncation must show unknown / '2,000+' and never 0; untracked files need an explicit 'new' count or the chip understates agent work; a stopped session's chip must not claim the session did it.
- Fluency: PASS. No confirmation, no waiting; the chip is the triage cue; Esc returns.
- Modularity: PASS. GitChanges in LoomCore (no UI, injectable runner like `BranchCache`/`CleanupWorktreeProtection.Capture`), CatalogModel+Changes, a view; dependency direction unchanged. Placement-agnostic so a later right panel can host it.
- CLI-update resilience: STRONG. Git plumbing does not depend on the Claude version. The in-terminal /diff mod, PostToolUse payloads and mods API all do; avoiding them is the resilient choice.
- Process ownership: PASS with one required item: the git child must be cancellable and killed on Quit (CancelFlag + shutdown hook, as the plan-limits fetch). Note `core.fsmonitor`, `diff.external`, textconv in a repo config can run programs; pass `--no-ext-diff --no-textconv -c core.fsmonitor=false`, and measure the fsmonitor trade-off on the big repos.
- User authority: PASS. Read-only; Copy Patch and Open in Editor are user clicks; nothing is sent to a session or the PTY. (Line comments back to the agent would be a different, authority-carrying feature.)
- Contract: no conflict. Terminal stays the real CLI; D-34 not touched (in-place view, not a right sidebar).


## Value for the user (3/5)

The research calls it the field's most-proposed capability, but this user's own long-standing wishes (side chat, right panel, usage, deletion, idle cost) do not include a diff viewer, they review in an IDE and GitLab MRs, and Anthropic ships a /diff pane plus a Desktop diff view; the power-user note argues review capacity, not tooling, is the bottleneck. The part with real, unique value for several concurrent sessions is the cross-session triage cue ('+N -M in K files' on the card of a finished session) and one-click Copy patch / open in editor, both cheap. The full pane is worth about 2, so the blend is 3. Honest cost: chip + exports M (runner, parsers with temp-repo tests for rename, quoting, binary, unborn HEAD, worktree, submodule; cache and triggers; card/header wiring with render-probe tests; DESIGN and UI-MAP updates); read-only pane L; adding a live watcher or per-turn snapshots makes it XL.

## Depends on

- No hard dependency. Soft: the user's answer on worktrees vs shared folders (decides whether a folder-level chip is misleading).
- An owned plain-Process git runner is new shared plumbing; it could also replace the per-call run scope that the cleanup worktree check pays today.
- If the user later wants line comments sent back to the agent: the 'send primitive' / verified prompt delivery ideas (a separate idea with its own authority questions).
- If a right panel is built (D-34 later), Changes should become a tab of it; the view model is written placement-agnostic for that.

## Experiments before building

- E1, zero code: in a Loom Dev session with an isolated CLAUDE_CONFIG_DIR, run Claude's built-in /diff (2.1.287+; installed CLI is 2.1.300) in Loom's terminal at the default window and at a widened one. Decides the pane: it needs the fullscreen renderer and 110+ columns, and at the default 1220 pt window with a 300 pt sidebar the terminal is probably near that limit (inference, not measured). If /diff works well inside Loom, the in-app pane becomes later/skip and only the chip and exports are built. If it opens only when widened, a one-line hint may be enough.
- E2, git cost on real repos (read-only commands only): time `git --no-optional-locks diff --numstat -z HEAD` and `git --no-optional-locks status --porcelain=v2 -z -unormal --ignore-submodules=all` cold and warm on the user's two work repos and the largest repo they use, with and without core.fsmonitor/untrackedCache. Decides the 5 s timeout, the caps, whether `-c core.fsmonitor=false` is acceptable, and whether the chip needs a per-folder size guard (skip the chip above a file-count threshold).
- E3, runner latency: measure `captureHelper` per-call latency (scope open) against a plain Process runner on the same git command. Expected to confirm that the plain runner is needed; also settles the Quit-cancel wiring.
- E4, only if phase 2 proceeds: an NSTextView diff of 5,000 lines and 256 KiB, expanded/collapsed, scrolled, while the window is visible vs hidden; check the CPU and memory against the 40%/1 MiB/s gate and the render-probe style counters. Also a worktree-wide FSEvents stream cost on a node_modules/target-heavy repo, only if live refresh is wanted.

## Questions for the user

- Do you normally run several sessions in the same folder, or one worktree per session? Same folder means the chip is folder-level and the tooltip wording matters more; worktrees make it close to per-session.
- Which editor should 'Open in Editor' use (a Settings choice of app, `$EDITOR`, or the system default for the file type), and is opening the changed file enough or do you want the repo root?
- May the diff view use add/remove tones (a new colour class, like project colours in D-48), or should the chip and the diff stay monochrome with +/- signs only?
- Should cards show the chip only for live sessions after a finished turn (recommended), or for every session including stopped ones (then it is the folder's current state, not the session's)?
- Is the in-app pane worth building at all if Claude's /diff works inside Loom's terminal (E1), or is the chip plus Copy patch plus your IDE and GitLab enough?
- Base for 'Branch vs base': origin's default branch is the proposed default; do your work repos have a different base convention (develop, a release branch)?
- Is an optional FSEvents live refresh while a session is Working wanted later, knowing it is the main source of competitors' CPU complaints?
