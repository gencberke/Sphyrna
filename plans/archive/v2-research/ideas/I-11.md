# I-11: Subagent tree upgrades (who is asking, per-subagent cost, no stuck 'running')

Card from the [Loom v2 idea catalog](../IDEAS.md). **Subagent tree upgrades (who is asking, per-subagent cost, no stuck 'running')** · verdict **adopt-light** · cost M · value 3/5 · proposed by 4 reports: [zed](../products/zed.md), [claude-official](../products/claude-official.md), [usage-tools](../products/usage-tools.md), [power-user-workflows](../products/power-user-workflows.md).

> Adopt the verified half now (name the subagent that asked, using the agent_id Loom already receives, plus deterministic closure rules so no record stays 'running'); defer live per-subagent cost/context, which needs the subagentStatusLine bridge (I-24) and a tick-rate spike.

## What the user gets

Attribute a 'waiting for you' state and its approval box to the specific subagent that asked, show per-subagent tokens/tool counts/context, and guarantee finished subagents never stay 'running'.

## Mechanisms found in the research

Add agent id/type from hook payloads on PreToolUse/permission events if present (unverified for the interactive CLI; degrade to session-level state); optional subagentStatusLine for per-subagent tokens/context (documented; agentType needs 2.1.293+; needs the I-24 bridge); fixtures from claude-hud's agent-tracking bug history (background agents whose completion appears only as a queue-operation enqueue or queued_command attachment, notices with <task-id> but no <tool-use-id>, forked/resumed sessions, usage logged several times per response). Do not promise per-subagent Stop: ACP does it via SDK Query.stopTask and no safe TUI equivalent is confirmed.

## Debates and fact-check corrections

Hook fields for agent identity are unverified for the current CLI (the ACP adapter gets agentID from canUseTool, not necessarily hooks). Needs real transcripts of forked/resumed background-agent sessions that the explorer did not have. SubagentStop also fires for internal agents (prompt suggestions, /btw).

## Design in Loom

KEY CORRECTION TO THE RESEARCH: the 'agent id on permission events is unverified' debate is already settled in Loom. Hooks docs list agent_id/agent_type as common input fields on every hook fired inside a subagent, and FB2-6 (plans/FEEDBACK-2.md, real Claude, 12 Oct) observed PermissionRequest and permission_prompt Notification events carrying agent_id, which ClaudeHookEvent.isSubagentPermissionPrompt already uses. Loom just throws the identity away: ClaudeHookStateTracker.receive only sets .waitingForApproval plus subagentApprovalReturn, and ClaudeHookEvent.permissionRequest keeps toolName only. No new hook event is needed. Do NOT add PreToolUse/PostToolUse: ProviderLaunchProfile.claudeSettings deliberately registers no per-tool hooks because each fires a loom-hook process; that would break the resource principle.

TIER 1 (adopt): attribution.
- SubagentRecord (SubagentLedger.swift) gains `approval: SubagentApproval?` (toolName, since). SubagentLedger gets noteApproval(agentID:toolName:at:) and clearApprovals(). If the prompt arrives before its SubagentStart (hooks are separate processes), keep a small bounded pending-ask map keyed by agent id and attach it when the record appears.
- ClaudeHookStateTracker.receive, in the existing isSubagentPermissionPrompt branch, calls noteApproval. It clears on exactly the existing clear points: the registry's next accepted idle/busy sample (receiveRegistry, where subagentApprovalReturn is cleared), any main-thread event (where subagentApprovalReturn = nil), that agent's SubagentStop, beginRun, and a new SessionStart. ProviderSessionAdapters.receive must also call publishSubagents for permission events that carry an agent_id, and after a registry sample that clears an ask. Today it publishes only on lifecycle, sessionStart, userPromptSubmit and stop. The existing .subagents hub change carries the data, so there is no new channel or watcher.
- Only the tool NAME is kept, never tool_input (a command line can hold secrets).

TIER 1b (adopt, after a small spike): never stuck 'running'. Loom's tree is hook-fed (SubagentStart/Stop plus Stop.background_tasks), not transcript-fed, so claude-hud's queue-operation / queued_command / task-id-only fixtures map only loosely. The real stuck cases here are:
 (1) a background subagent whose SubagentStop is lost. The helper has a 1 s timeout, and the ledger keeps an unlisted known-background record running because 'what an unlisted background subagent means is not verified' (SubagentLedger.turnEnded).
 (2) a foreground subagent when the user interrupts the turn. Docs: Stop does not run on a user interrupt, so turnEnded never fires, and the row reads 'Running 40m' until the next Stop.
 (3) kill or failure of a background task, which the hooks do not report.
 Event-driven closure rules, each added only after the spike confirms it:
 - An accepted registry sample 'idle' (receiveRegistry already reads it by vnode, no polling) ends all running records, because the code comments say Claude reports 'busy' while a background subagent runs.
 - A Stop whose background_tasks key is PRESENT ends known-background records it does not list. This needs ClaudeHookEvent to tell an absent key from an empty list, since BackgroundSubagentTask.parse(nil) and [] look the same today. Docs: the arrays are present when the task registry is reachable.
 - The synthetic UserPromptSubmit that ClaudeHookEvent already detects (promptIsSynthetic, '<\task-notification') may carry <task-id> and a status. If a spike shows it does, parse it to end that record and show 'Failed' or 'Stopped' as a verified outcome. Otherwise keep 'Finished' only.
 Never add a time-based guess: a long-running subagent is legitimate. The honest fallback is the elapsed time that the row already shows.
 Fixtures (Tests/LoomCoreTests/SubagentTests.swift style, plus the loom-fake-provider scripted subagents): lost background stop, interrupted turn, kill, prompt-before-start race, two simultaneous askers, /clear and fork and resume mid-run, a duplicated Start after Stop, and Claude's internal agents (SubagentStop with empty agent_type from prompt suggestions and /btw, which the ledger already ignores via !type.isEmpty).

TIER 2 (later, light): per-subagent tokens without any new I/O. ClaudeUsageIndex already indexes subagents/agent-<id>.jsonl (UsageTranscriptWalker.session maps subagent files to their owning session), keyed per file (msg.file_id) with dedupe by message id (which covers 'usage logged several times per response'). Add one query, tokens (and the last request's input as context fill) for a path. Call it only when a subagent panel is open (shown in the SubagentHeaderRow pill, e.g. 'Running 4m · 38k') and once when a record finishes (shown in the row's .help tooltip). Do not live-publish counts to every card: the card re-render and CatalogHotPathTests budgets would pay for it. Tool counts have no cheap live source. PostToolUse(Agent) only reports totalToolUseCount for foreground agents and gives no usage for background ones, which are the default. The alternative is one bounded SubagentTranscriptParser pass at SubagentStop, counting .toolCall entries with a size cap. Context PERCENT needs contextWindowSize, which is not in the transcript (200k vs 1M variants), so show absolute tokens only until the bridge exists.

TIER 3 (later, behind I-24, needs spike E2): subagentStatusLine via the per-session --settings JSON. Documented fields per task: status (running/completed/failed/killed, ground truth including failures and kills), tokenCount, contextWindowSize, model, effort, label, agentType (2.1.293+). It runs a command 'once per refresh tick' with all visible rows, so the process-spawn rate is the risk. Emit nothing to keep Claude's default row. A loom-hook sub-mode would forward the JSON over the existing authenticated hook socket as a new envelope kind.

Per-subagent Stop is not promised: no confirmed safe TUI equivalent of the SDK's Query.stopTask.

## Where it shows

Sidebar subagent row (SubagentTree.swift, SubagentTreeContent / SubagentRowView): a running row whose record has an approval swaps its ChaseDots for the attention glyph (exclamationmark.circle.fill in Status.attention, as SubagentApprovalNotice uses) and sets the type text to the attention colour. The elapsed time on the right stays. The accessibility label becomes 'Subagent Explore, Find login handlers, waiting for approval of Bash'. No new text on the 22 pt row. Cap rule: a row with an approval must never hide behind '+N more' (maximumRunningRows = 3), so asking rows are pulled into the visible set first.

Detail pane (SubagentPanelViews.swift SubagentApprovalNotice): 'Explore · Find login handlers wants to run Bash: answer it in the session's terminal [Show Session]'. When the open panel is a different subagent from the asker, it names the asker instead. Panel header pill (SubagentPillContent): 'Running 4m · 38k' once Tier 2 lands, and 'Failed' or 'Stopped' only if the spike proves a verified source.

Approval notification (ApprovalNotificationPlanner.body, ApprovalNotifier.swift): '<project> · Explore is waiting for your approval (Bash)', read from the live subagent state when the banner posts. Loom has no approval box of its own today (the dialog lives in the terminal; RequestList is for open-session requests), so 'attribute the box' means the row marker, notice and banner. The same record.approval would feed a future chat-style approval card if v2 adds one.

## Principle check

Resources: PASS for Tier 1 and 2. No new hook events, watchers, timers or processes. It rides the registry vnode and hook events already received, plus the existing FSEvents usage watcher. RISK for the idea as written: PreToolUse for agent_id would spawn a helper per tool call (refused in ProviderLaunchProfile). subagentStatusLine spawns a process per tick, so it needs the E2 measurement before any adoption.
Predictability: PASS. Fixed rules and bounded state: asks bounded by the ledger caps (50 running, 20 finished) and by the 200-id ended list.
Accurate status: PASS only with discipline. Attribution is verified (hook payload). Do not infer 'failed' or 'killed' without a verified source, since the contract requires started/stopped/delivered/deleted to be verified outcomes. Do not close records on a timeout. Each closure rule must be proven by the spike. Today's unlisted-background rule is explicitly marked unverified in the code, so this idea reduces the false-status risk.
Fluency: PASS. Faster triage of which subagent is blocking. No new prompts or waits.
Modularity: PASS. The change lives in LoomCore (ledger, tracker, adapter publish) plus pure value types in LoomCatalogUI (SubagentTreeContent is already unit-tested as a plain value). No new layer.
CLI-update resilience: PASS. agent_id and agent_type are documented common hook fields. If absent, the row degrades to today's session-level state (no ask is noted, nothing breaks). Registry statuses are already handled with unknown-value diagnostics. Transcript fields are not a contract, so Tier 2 must show 'unknown' on drift. Never pin the CLI.
Ownership: PASS. Read-only; nothing started or stopped.
User authority: PASS. No cross-session actions, and no per-subagent Stop is promised (no confirmed safe equivalent).
Contract/decisions: consistent with D-39 (the tree) and FB4-5 (the read-only panel). It touches no D-34 or terminal-is-real-CLI rule.

## Value for the user (3/5)

The user runs many sessions and many background workflows, so knowing which subagent blocks on approval saves a hunt through the terminal, and a stuck 'Running 2h' row erodes trust in every other indicator. But session-level Needs approval plus Cmd+J already gets them to the right terminal, so the gain is triage speed, not a new capability. Per-subagent cost and context is a nice-to-have next to the usage chip and Settings Usage page they already have.

## Experiments before building

- E1, hook and registry truth (decides which Tier 1b closure rules ship). In Loom Dev with the isolated CLAUDE_CONFIG_DIR (DEVELOPMENT.md §2, probe/claude-config) and the loom-probe HookRecorder, record the timeline of hook events plus registry samples for: (a) 2 background agents and 1 foreground agent; (b) Esc during a foreground agent; (c) killing a background task through /tasks; (d) a subagent hitting a permission prompt, foreground and background, and two askers at once. Decide: whether SubagentStop fires on interrupt or kill; whether registry 'idle' ever coincides with a live background agent (if never, the idle-closes-all rule ships); whether Stop.background_tasks omits a finished background agent and its key is present when empty (if yes, the unlisted rule ships); whether PermissionRequest and permission_prompt agent_id equals the SubagentStart id and whether a prompt can precede its Start; whether the synthetic '<\task-notification' UserPromptSubmit carries <task-id> and a status (completed/failed/killed).
- E2, subagentStatusLine cost (decides Tier 3 go or no-go). A recording script as subagentStatusLine in the isolated profile, with 5 concurrent agents: invocations per minute, stdin size, and whether empty stdout keeps the default row. Measure Loom CPU and process spawns with the CPU40 tooling. No-go if more than about 1 invocation per second per session, or if the user's own subagentStatusLine would be overridden.
- E3, token definition. Compare the CLI's tokenCount (E2 output, or the agent panel row) with ClaudeUsageIndex's per-file sum for finished agents. Decide the wording ('tokens' vs 'approx.') and whether the figure goes on a row at all.
- Needs a logged-in isolated Claude profile; the real ~/.claude must not be used.

## Questions for the user

- Should clicking a row that is asking for approval open the transcript panel (shows what it was about to do, notice says answer in the terminal) or go straight to the session terminal where the dialog is?
- If E1 proves a verified source for failed/killed (task-notification status or statusline status), do you want 'Failed' and 'Stopped' subagent states, which departs from today's 'Claude reports no failure' rule? Or keep 'Finished' only?
- Per-subagent tokens: only in the subagent panel header and a tooltip (recommended, cheapest), or visibly on every sidebar row?
- OK to take the subagentStatusLine slot in Loom's per-session --settings later (it would shadow your own subagentStatusLine, if you have one)?
- OK to provision a logged-in isolated CLAUDE_CONFIG_DIR for the E1 spike (real Claude calls, some token use)?
