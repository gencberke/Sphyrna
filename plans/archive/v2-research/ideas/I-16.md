# I-16: Rich approval content: real preview, question card, plan review panel

Card from the [Loom v2 idea catalog](../IDEAS.md). **Rich approval content: real preview, question card, plan review panel** · verdict **spike-first** · cost L · value 4/5 · proposed by 5 reports: [attention-surfaces](../products/attention-surfaces.md), [power-user-workflows](../products/power-user-workflows.md), [happy](../products/happy.md), [cursor](../products/cursor.md), [chat-ui-paths](../products/chat-ui-paths.md).

> Worth building for the AskUserQuestion card and the plan panel (the structured interactions that stall unattended sessions, and the first honest step toward a chat-centred UI), but only after a live spike pins the hook form and the plan-approval semantics; the Bash/Edit/Write diff preview alone is a cheap, separable add-on whose value is mostly triage in notifications and the menu bar.

## What the user gets

Approve confidently without opening files or scrolling: the full Bash command, Edit/MultiEdit as a unified diff from old/new strings, Write as head + size, MCP as server + args; a card for AskUserQuestion (1-4 questions, single/multi-select, free text); and a rendered plan with Approve / Revise-with-feedback for ExitPlanMode. Always with 'answer in the terminal' as fallback.

## Mechanisms found in the research

(a) Preview purely from the hook payload already in memory, size-capped with 'show more', rendered only when visible; a lazy file read for true line numbers later. (b) AskUserQuestion: PreToolUse allow + updatedInput {questions echoed, answers keyed by exact question text} (documented, but framed for -p/permission-host flows; the interactive case is an inference). CC 2.1.300 validates updatedInput: unknown keys are dropped and input the tool rejects denies the call, so a schema slip denies instead of crashing. Pick one hook form (PreToolUse vs PermissionRequest; CodeIsland uses the undocumented PermissionRequest form, Notchi implements both) and pin it with a live-captured contract test. Documented headless alternative: `defer`. (c) ExitPlanMode is a tool name matched under PreToolUse/PostToolUse (not a separate event); plan and planFilePath are injected into tool_input; Revise = deny + message is unverified (does deny keep the CLI in plan mode?).

## Debates and fact-check corrections

Only one commercial product (Vibe Island, closed) ships plan review, so reception is unproven. Duplicating Claude's permission policy is a drift trap (Happy lesson): relay the CLI's own prompt. Diff without file context shows only the replaced fragment. Depends on I-15's request/response channel.

## Design in Loom


## What Loom has today (observed in code)
- The PermissionRequest hook is registered per session in `ProviderLaunchProfile.claudeSettings` (Sources/LoomCore/ProviderLaunchProfile.swift:~185-200) as the same `bounded` fire-and-forget helper as the other events: `{type: command, command: helperPath, args: [], timeout: 1}`. The comment there says "helpers return no provider decision" and "No per-tool hooks: each hook spawns a helper".
- `loom-hook` (Sources/loom-hook/main.swift) sends one envelope over `ClaudeHookClient.send` and exits. `ClaudeHookServer` (Sources/LoomCore/ClaudeHook.swift) is one-way: 1 s receive deadline, no reply, serial queue. `ClaudeHookEvent.init(payload:)` reads PermissionRequest only as `.permissionRequest(toolName:)`; `tool_input` and `permission_suggestions` are never parsed or kept (the full payload, up to 1 MiB, is in `ClaudeHookEnvelope.payload` in memory).
- The tracker turns PermissionRequest into `.waitingForApproval` (`ClaudeHookStateTracker.receive`, ClaudeHook.swift:~733/762) and then lets the registry's "idle/busy" samples move it on (`receiveRegistry`, ~l.590-620). Interrupting or denying in the terminal fires no Stop and no PermissionDenied (plans/experiments/cp5-claude-native-denial-research.json), so the registry sample is the only "card is stale" signal.
- A request/response channel already exists: `OpenSessionControlServer` (Sources/LoomCore/OpenSessionProtocol.swift) on `c-<8>.sock`, same token, holds a connection open per request (max 32 in flight, `Task.detached` so no thread is blocked while waiting), answered later by `OpenSessionCoordinator` (actor, in-memory entries, `updates()` AsyncStream, replyDelay 85 s, Quit answers everyone `unavailable`). `SessionRuntime+OpenRequests.swift` is the UI-facing approve/deny API and `OpenRequestBox` (Sources/LoomCatalogUI/OpenRequestViews.swift) is a ready template: bounded preview, "Show full message" scroll, no default action so Return stays with the terminal, `fadesIn()` opacity only.
- There is NO Claude-side approval box with content today. `RequestList` (DetailView.swift:443) renders `SessionViewState.userRequests`, which only the frozen Codex path fills. For Claude the user sees "Needs approval", a fixed banner "Claude is waiting for your approval." (`ApprovalNotificationPlanner.body`) and `SubagentApprovalNotice` ("answer it in the session's terminal"). So the brief's "approval box" for Claude does not exist yet.
- No Markdown renderer in the repo; `SubagentTranscriptView` is explicitly plain text.

## Proposed split (three separable stages, each shippable alone)

### Stage 0: content line from the payload already received (S, no new hook, no blocking)
- Extend `ClaudeHookEvent` (LoomCore) with a bounded `ToolPreview` parsed only for `.permissionRequest` and only fields it needs: tool name, Bash `command`+`description`, Edit/MultiEdit `file_path` and old/new strings, Write `file_path`+size+head, MCP `mcp_server`+top-level arg keys. Cap each string at parse time (for example 8 KiB, with "N more bytes"), so the 1 MiB payload never travels further.
- Keep it OUT of `SessionViewState` (that struct is diffed per frame in the sidebar hot path; see CatalogHotPathTests/SidebarRenderTests). Publish it on a separate small stream like `openRequestUpdates()`: a `PendingInteraction` store in the adapter keyed by session, set by the PermissionRequest event and cleared when the tracker leaves `.waitingForApproval` (registry sample, UserPromptSubmit, Stop, run end). Event-driven, no timers.
- Consumers: (1) `ApprovalNotificationPlanner.body` gets a second line "Bash: git push --force origin main" (setting-gated because banners show on a locked screen), (2) menu bar row subtitle (MenuBarRowText), (3) a content line/box in the detail pane. For a selected live terminal the box adds little (the CLI dialog shows the same and a better diff), so keep it one or two lines there; the real gain is triage across sessions you are not looking at, and the subagent panel and ended-screen views where the terminal is not showing.
- Edit preview is old_string/new_string only (fragment diff, no true line numbers). Lazy file read for line numbers is a later, optional step (bounded read, only when the box is visible).

### Stage 1: decision channel for AskUserQuestion and ExitPlanMode only (M)
- Do NOT start with Bash/Edit allow/deny. Answering a question is not a permission decision, so Loom duplicates no policy (the Happy drift lesson) and never sits in front of the CLI's own permission logic. Allow/Deny for ordinary tools can reuse the same channel later (PermissionRequest allow/deny; "always allow" only with `destination: session`, never echoing a `localSettings` suggestion) but is a separate decision.
- New blocking hook entry per session in `claudeSettings`, scoped by matcher so it spawns only for the rare tools: either `PermissionRequest` with `matcher: "AskUserQuestion|ExitPlanMode"` or `PreToolUse` with the same matcher (the spike picks; see experiments). Command: the same `loom-hook` with a new first argument (for example `decide`), timeout about 600 s. Needs a branch in `LoomHook.main` before the `OpenSessionCommand` dispatch, which today treats any argument as the open command.
- The helper sends one request (token, session id, run id, stdin payload) to the existing control socket and waits. Generalise `OpenSessionControlServer`'s wire request with a `kind` field (or add a sibling server on the same socket directory with the same `LocalSocket` rules) rather than a third IPC mechanism. A new actor `HookDecisionCoordinator` (LoomCore, sibling of `OpenSessionCoordinator`) keeps pending decisions in memory keyed by (sessionID, runID, tool_use_id or invocation id), exposes `updates()`, and offers `answer(id, ...)`, `handBack(id)`. Reply shapes: hand back = exit 0 with empty stdout (the CLI then shows its own dialog); answer = the documented JSON on stdout.
- AskUserQuestion answer: echo the ORIGINAL `questions` value verbatim from the payload (keep it as the parsed JSON object, never re-encode through a typed model) and add only `answers` keyed by the exact question text (multi-select labels joined with commas). Loom reads just `question`, `options[].label/description`, `multiSelect`; every other field passes through untouched, so new CLI fields cannot cause a schema slip. Hand back instead of rendering when: questions is not 1-4 dictionaries, a question text repeats, the payload has an `agent_id` (subagent), or parsing fails (journal a `cli_compat_warning`).
- ExitPlanMode: render `tool_input.plan` (injected, documented), show `planFilePath`; Approve = allow (+ `updatedInput` echo); Revise = deny with the user's feedback as `message`; "Use terminal" = hand back. If the PermissionRequest form is chosen, Approve can carry `updatedPermissions: [{type: setMode, mode, destination: "session"}]` to mirror the CLI's "approve and auto-accept edits" choice (documented), which the PreToolUse form cannot do.
- Hold rule, no polling: the helper and socket stay open while the card is pending. Loom hands back at its own deadline (stay under the helper's 600 s timeout; a timed-out hook does not block per docs, so the CLI falls back to its dialog either way), on Quit, on run end, when the tracker leaves the waiting state, and when the user clicks "Use terminal". A visible "Handed back to the terminal" state replaces silent loss. Timeouts hand back, never decide.
- State accuracy: while a decision is pending the tracker must keep the card in Needs approval / Waiting for you. Risk: a blocking hook may make the registry report "busy", and `receiveRegistry` would then flip the card to Working under the pending card. Add a tracker input "interaction pending" that the registry samples cannot override until the coordinator resolves it. This is the most invasive code change in the idea (ClaudeHook.swift, ~900 lines of watermark logic).
- Verified outcome: register `PostToolUse` with the same matcher (rare tools, so near-zero spawn cost) and show "Answered" only when it arrives for that tool_use_id; a write to a dead helper, or no PostToolUse and a state change, shows "Claude moved on; answer was not used". The 2.1.300 behaviour (invalid `updatedInput` denies the call) makes this check necessary, not decorative.
- Authority: every action is an explicit click bound to the card's request id, no default/Return action (same rule as `OpenRequestBox`); stale card actions are discarded and logged (CodeIsland #308 lesson). Never log question or plan text (LoomLog is content-free); evidence export honours `redactsContent`.

### Stage 2: plan panel and question card UI
- Panels replace the terminal view while pending, like the subagent panel (`DetailContent`, DetailView.swift:~236-247: terminal keeps running at the same size, only not shown; a card above the terminal would resize the PTY, which DESIGN.md forbids except opacity-only fades). Always a visible "Use terminal" button and Esc returns to the terminal.
- Plan rendering needs a small bounded Markdown renderer (headings, lists, fenced code, inline emphasis through `AttributedString(markdown:)`, lazy blocks), cached by request id, drawn only while visible, cap about 256 KiB with "Show more". This is new code (no renderer exists) and the main reason the cost is above M for plans.
- Cmd+J (next session that needs you) lands on the panel; the notification action can open it. Notification buttons that answer are a later add-on.

## Triggers and bounds (summary)
Triggers: hook events, the coordinator's AsyncStream, user clicks, registry change notifications. Nothing polls. Bounds: payload 1 MiB (existing), preview strings 8 KiB at parse, plan 256 KiB, at most 32 held connections (existing `maximumInFlight`) and a small per-session pending queue (parallel tool calls, subagents), everything in memory only and dropped at Quit.


## Where it shows


- Stage 0: a one- or two-line tool summary on the orange "Needs approval" surface: notification body "Project · Bash: git push --force origin main", menu bar row subtitle, and a slim tinted box above the terminal (opacity fade, bounded, "Show full command" scroll like `OpenRequestBox`). Edit shows "src/Foo.swift  -3 +5" with a small red/green fragment; Write shows path, size, first lines; MCP shows server plus argument keys.
- Question card (Stage 2): replaces the terminal in the detail pane while pending. One block per question (1-4): header chip, question text, option rows with label+description, radio for single-select, checkboxes for multi-select, a free-text "Other" field; a Send button enabled when every question has an answer; "Use terminal" secondary button; no default action. After sending: "Answered" appears only after the PostToolUse confirmation, otherwise "Claude moved on".
- Plan panel: header "Plan ready for review" with the plan file path (Reveal / Copy path), the rendered Markdown in a scroll area, footer with Approve (and a mode menu if the PermissionRequest form works), "Revise..." opening a feedback text field that sends deny + message, and "Use terminal".
- Sidebar and menu bar need no new shapes: the existing orange Needs approval / Waiting for you dot and Cmd+J keep working; the card subtitle can show "Question" or "Plan" instead of a generic state when the interaction is known.


## Principle check


Resources: PASS if scoped. Stage 0 adds one bounded parse per PermissionRequest and no new process. Stage 1 spawns a helper only for the matcher-scoped rare tools (AskUserQuestion, ExitPlanMode), holds a socket and a suspended Task while pending (no thread, no timer), renders only when visible, and keeps nothing for idle sessions. RISK if someone registers a blocking hook on every PreToolUse or every PermissionRequest (a spawn per tool call, which the existing comment in ProviderLaunchProfile.swift rules out) or puts the preview strings into the per-frame `SessionViewState`.
Predictability: RISK, the main one. A blocking hook means the CLI's own dialog is not on screen until the hook returns, so a user who types into the terminal while Loom holds the request sees only a spinner. Mitigations: a visible card/panel with "Use terminal", a hand-back deadline, a Settings choice (answer in Loom / in the terminal; read per request, default is the user's call), and consistent behaviour (always hold for these two tools when the setting says Loom).
Accurate status: RISK, manageable. A held hook may make the registry say busy and flip the card to Working; needs the tracker "interaction pending" input. Delivered/answered must be verified (PostToolUse for the same tool_use_id), never inferred from the write; hand-back, timeout and stale card are shown states. The interrupted-in-terminal case sends no Stop, so cancellation relies on the registry sample and the helper-connection failure.
Fluency: PASS, one click or a few keystrokes from the card or Cmd+J instead of find-pane, scroll, press 1/2; no new confirmation steps. Return is deliberately not a default action.
Modularity: PASS. New `ToolPreview` parse in LoomCore, a `HookDecisionCoordinator` beside `OpenSessionCoordinator`, one `loom-hook decide` subcommand, one detail-pane view and a Markdown renderer; hot paths (sidebar frames, tracker watermarks) are touched only by the one tracker input.
CLI-update resilience: PASS with discipline. Uses documented hook fields (tool_input, plan, planFilePath, decision JSON, matcher); echoes the original `questions` verbatim; any shape mismatch hands back to the terminal and journals `cli_compat_warning`; no pinned versions; pin the chosen hook form with a payload captured from a live session (not hand-written) and keep it as a contract test fixture. Not documented for the interactive case: AskUserQuestion answering via hook is documented and framed for `-p`/permission hosts (the permissions page does document that an ExitPlanMode `allow`+`updatedInput` runs without a prompt in plan mode), so treat the interactive AskUserQuestion path as inferred until the spike confirms it. `defer` is -p only and ignored in interactive sessions, so it is not an option for a PTY host.
Process ownership: PASS. The helper is a child of the CLI inside the run scope; Stop/Quit tear everything down; Quit answers waiting clients and drops the in-memory requests.
User authority: PASS only if every decision is an explicit click bound to the request id, nothing answers on timeout, nothing is stored, and the user can switch the feature off. Contract section 9 says provider permission checks must not be bypassed and "multiple approvals not explained to the user" are unacceptable: answering a question or plan on the user's click is not a bypass, but the first time Loom answers on the CLI's behalf deserves its own DECISIONS entry. Stage 1 also changes the invariant "helpers return no provider decision" (ProviderLaunchProfile.swift comment), which must be updated in the docs.
Contract/decisions: the contract keeps the terminal as the real CLI; panels that replace the terminal temporarily (subagent panel precedent, D-54) with an always-visible way back stay inside it, and the user has said they are open to a chat-centred direction. D-34 (no right sidebar) is not touched because the panel lives in the detail pane. D-43/D-46 (cross-session channel) is untouched: this is intra-session.


## Value for the user (4/5)

For this user (several sessions, spec/interview loops with ticket keys, plan-first habits) AskUserQuestion and ExitPlanMode are where unattended sessions stall and where a human decision matters most, and answering from a rendered card is a real fluency win plus the first reusable piece of a chat-centred UI. Discounts: auto mode is now the default starting mode (v2.1.283+, per the power-user fact-check), so ordinary Bash/Edit approvals are rarer and the plain diff preview is the weakest part (the CLI dialog already shows a better diff for the selected session); only one closed product ships plan review, so reception is unproven; and the hook-held dialog trade-off needs the user's buy-in.

## Depends on

- I-15 (request/response decision channel): not a hard prerequisite, because the existing control socket and a coordinator pattern already hold requests, but Stage 1 should be built as the first user of whatever generalised channel I-15 defines, not as a parallel one
- Stage 0 (content line) is independent of I-15 and of any blocking hook
- A Markdown renderer for the plan panel (new; shared with any later chat-centred/transcript view)

## Experiments before building

- E1, hook form (decides PermissionRequest vs PreToolUse): in an isolated CLAUDE_CONFIG_DIR with Haiku at low effort via loom-probe's HookRecorder, capture live payloads for a Bash prompt, an AskUserQuestion and an ExitPlanMode, with both a PermissionRequest and a PreToolUse (matcher AskUserQuestion|ExitPlanMode) hook that blocks and answers. Decide by: (a) does PermissionRequest fire for AskUserQuestion and ExitPlanMode in an interactive session and carry the injected `plan`/`planFilePath`; (b) does allow + updatedInput suppress the TUI dialog and does the model's tool result show the chosen answers (single, multi-select, free text) in the transcript; (c) which form leaves the cleanest state flow. Prefer PermissionRequest if both work, because it keeps today's state machine and allows `updatedPermissions` setMode. Keep the captured payloads as test fixtures.
- E2, plan semantics: does `deny` + message on ExitPlanMode keep the session in plan mode and does Claude then revise the plan using the message (unverified)? Does `allow` leave plan mode, and into which permission mode (with and without `updatedPermissions` setMode)? Decides whether Revise and Approve can be offered at all, or whether the plan panel stays display-only with approval in the terminal.
- E3, registry/state while a hook blocks: while a PermissionRequest or PreToolUse hook is held, what does the registry (`claude agents --json` / ClaudeRegistry) report (busy, waiting, idle), does the CLI draw its dialog meanwhile, and what happens to the pending helper on Esc/Ctrl+C in the terminal (killed? orphaned? does the socket close so Loom can see it)? Decides how much tracker change Stage 1 needs and how stale cards are cancelled.
- E4, timeout and fail-open: with timeout 600 and with Loom not running, confirm the CLI falls back to its normal dialog (docs say a timed-out hook does not block) and that two hooks on one event (Loom's forwarder plus a user's own PermissionRequest hook from settings) do not produce duplicate or conflicting decisions (the Vibe Island #245 failure mode).
- E5 (cheap, Stage 0 only): record real PermissionRequest payloads for Bash, Edit, MultiEdit, Write and an MCP tool to confirm field names and size, and check how often the user's real flow produces them under their usual permission mode.

## Questions for the user

- Which permission mode do you normally run (auto, acceptEdits, manual)? It decides whether Bash/Edit approval content is worth building at all, versus only AskUserQuestion and plans.
- When Loom holds a question or plan, the CLI's own dialog stays hidden until you answer in Loom or click Use terminal. Is that acceptable as the default, or should the default be terminal-first with the Loom card as an opt-in per Settings?
- Should Loom be allowed to answer on the CLI's behalf at all (a new DECISIONS entry, since today Loom's hooks never return a decision)? And should Allow/Deny for ordinary tool permissions ever be included, or only questions and plans?
- Should the Needs-approval banner show command text (visible on a locked screen), or only a tool name such as Bash/Edit/Question/Plan?
- If E2 shows that Approve cannot choose the follow-up mode, is a plan panel that is display-only (read plan, approve in the terminal) still worth shipping?
