# I-26: Usage rollups per project, per ticket and by source

Card from the [Loom v2 idea catalog](../IDEAS.md). **Usage rollups per project, per ticket and by source** · verdict **adopt-light** · cost M · value 3/5 · proposed by 3 reports: [usage-tools](../products/usage-tools.md), [codex-app](../products/codex-app.md), [power-user-workflows](../products/power-user-workflows.md).

> Adopt a smaller version: the existing usage index already has the dedupe, the sidechain flag and a delete rule, so build only a by-session query, "By project / By source / By ticket" cards in the Usage page, and a Usage fact in the idle session's record view; drop the separate rollup file and the "unusually large" alert.

## What the user gets

Answers 'what did EDDP-1234 cost across five sessions and two subagent workflows' and 'which project eats my quota', plus attribution of tokens to main thread vs subagents vs side chats (and later scheduled runs), per session and per day, with an 'unusually large share' hint.

## Mechanisms found in the research

Group the existing incremental usage reader's data by project colour, ticket key and sidechain marker; demand-driven per-row detail for the selected/expanded card (Codex discipline); label estimates as API-equivalent as today; dedupe by message id + request id with fixtures for resume/fork replay; optional numbers-only daily rollup file (day, project, model, tokens, estimated cost) that survives transcript cleanup.

## Debates and fact-check corrections

Open user decision: Loom's permanent delete removes a session's Claude data, so a rollup that outlives it needs a rule (content-free totals may stay, or deletion also subtracts). cleanupPeriodDays (default 30) is documented and configurable, so do not assume 30 days. Over-counting on resume/fork replay is the classic bug (Usage Monitor #158, CodexBar #2037). If the transcript drops its subagent marker, show 'unattributed' rather than guess. Becomes essential once side chats exist.

## Design in Loom

WHAT ALREADY EXISTS (observed, not assumed): ClaudeUsageIndex (Sources/LoomCore/ClaudeUsageIndex.swift) is already a durable, content-free, per-message SQLite ledger (usage-index.sqlite3 in the data root, table msg: key, file_id, ts_ms, session, model, input/output/cw5/cw1/cr/web, flags, total, cost; index msg_session). Its header says "Rows are history: a transcript Claude deletes later never lowers totals" and test aVanishedFileNeverReducesTotals pins it, so the idea's "numbers-only daily rollup file that survives transcript cleanup" already exists at message granularity and must NOT be built a second time. Dedupe is already by message.id alone (key "m|<id>", fallback request+session+timestamp), keeping the non-sidechain row, then the larger total; fixtures exist for cross-file duplicates, sidechain replays (sidechainFilesCountAndReplaysDoNotDoubleCount, sidechainReplayAfterTheParentIsDropped) and resume. flags bit 0 already stores isSidechain (ClaudeUsageParser reads it). Subagent file lines carry sessionId = parent (plans/experiments/run1-planning-scans/U-usage-data.md line 40), UsageTranscriptWalker.session() maps subagents/ files to the parent session, and resume appends to the same file. Delete rule is already decided in code: ConversationForgetters -> ClaudeUsageIndex.forget(sessionIDs:) keeps tokens in the totals and only nulls msg.session, removes file/symbol rows and keeps a SHA-256 digest (tests forgetKeepsTokensAndDropsTheSessionLink, aForgottenSessionLeavesNoIdBytesInTheIndexFiles). So the idea's open delete question is "extend the existing rule", not "invent one".

SMALLEST DESIGN (3 parts, no schema change, no new watcher, no new process):
1. LoomCore, ClaudeUsageIndex: one new read, e.g. sessionTotals(range:) = SELECT session, flags & 1, model, SUM(...) FROM msg WHERE ts_ms in range GROUP BY 1,2,3 (join symbol for the session text), plus a per-session variant using the existing msg_session index. Prices applied at query time exactly like snapshotOnce (UsagePricing, Self.cost) so cost stays an "API-equivalent estimate" and unknown models stay "-". Rows with session NULL (deleted via forget) or unmatched become explicit buckets. Add the method to the UsageIndexing protocol with a default for test fakes, as the file already does for summary/buckets.
2. LoomCatalogUI: a pure grouping function (new file, e.g. UsageRollup.swift) takes the index rows plus a snapshot of catalog facts [providerConversationID -> projectID, ticketKey/title] and returns buckets: by project (Loom CatalogProject id, name, tone), by source (main thread vs subagents, from the sidechain flag), by ticket (ticket_key, else the leading key of the title using the same fold/prefix rule as SessionCatalog.session(projectID:ticket:) in SessionCatalog+Sessions.swift; no new Jira concept). Buckets: "Outside Loom" (sessions the catalog does not know, e.g. plain CLI use) and "Deleted sessions" (session link cut by forget) and "Unattributed" (no sessionId or no sidechain marker); invariant tested: sum of buckets == snapshot total for the same range. The catalog facts come through an injected closure (SessionCatalog.sessions() is public) so UsageModel does not import the catalog.
3. Events: reuse UsageModel's existing gating. The rollup is computed only inside loadAfterScan/buildReport when usagePageVisible (UsageModel.swift), never for the footer chip, and recomputed only by the events that already rebuild the report (launch scan, watcher change, Settings opening, period switch, manual refresh). The record view (ConversationDetail in DetailView.swift, the Facts grid) gets one Fact "Usage" ("2.1M tokens, 31% in subagents, about $3.20 estimated"), fetched once when an idle/ended session record is selected (single indexed query on msg_session, same discipline as Codex's selected-row-only usage in agents_overview_usage.rs); live terminal sessions show nothing new.
Bounds: every query is limited to a UsageRange (24 h to 90 d, already offered), runs on the index's utility serial queue, returns at most (sessions x models x 2) rows, and nothing runs while the Settings window or main window is hidden.

WHAT TO CUT OR DEFER: (a) no separate daily rollup file (duplicates msg); (b) no "unusually large share" alert: thresholds are arbitrary and tokens overstate cost because cache reads dominate (the research fact-check on the Guardian numbers: 81-96% cached), so show plain shares ranked by estimated cost with tokens beside, like the existing By model card; (c) the side-chat and scheduled-run sources do not exist yet: add them later from Loom's own catalog relation (a child/parent link on the session row), not by guessing from transcript files; (d) per-subagent rows belong to the subagent tree idea, not here; (e) persisting a project key on each message (additive nullable column, version stays 2 so the index is not discarded; a schema bump would DELETE history that can no longer be rebuilt, see openDatabase -> removeDatabaseFiles on schema mismatch) only if the user wants deleted sessions to stay in project totals.

TICKET CAVEAT (observed): a ticket is known only for sessions opened through loom:open-session (sessions.ticket_key) or whose title starts with the key (Claude titles a session after its first prompt). Sessions the user types by hand without the key at the start of the title fall under "No ticket". The card must say "tickets found from titles" rather than imply completeness.

## Where it shows

Settings > Usage (the fixed 680x520 window, UsageReportView with its four SettingsCard-style cards): add two cards that copy the "By model" grid (UsageReportCards.modelsCard: name, Tokens, Share bar, Est. cost, thin dividers), shown under the existing four and respecting the selected period (24 h / 7 d / 30 d / 90 d). "By project": one row per Loom project with its colour stripe, plus "Outside Loom" and "Deleted sessions" rows; meta text "N sessions". "By source": two or three rows, "Main thread", "Subagents", "Unattributed" (hidden when 0). A small segmented control or a second pane in the same card switches "Project | Ticket"; the ticket view lists keys such as EDDP-1234 with session count and cost, a footnote "Tickets are read from session titles", and the existing line "API-equivalent estimate — subscriptions are not billed per token." stays. Idle/ended session record view (ConversationDetail Facts grid): one extra row "Usage" with total, subagent share and estimated cost, "estimated" in the tooltip. Nothing is added to the sidebar cards, the footer chip, the header or the menu bar (cards stay two rows; nothing animates; nothing redraws when hidden). This needs a design preview in the repo's usual way (design/feedback-N-preview.html) before code, per design/DESIGN.md.

## Principle check

resources: PASS. No polling, no new FS stream, no new process, no extra transcript reads; queries run only while the Usage page is visible (UsageModel.usagePageVisible) or an idle record is selected, are range-bounded and on the index's utility queue. RISK to measure: GROUP BY session over 90 days of msg rows; check on the opt-in ClaudeUsageCorpusTests corpus (1 GiB) that it stays in the tens of milliseconds. predictability: PASS if shares are plain, ranked, and the bucket sums reconcile to the period total; RISK if a hint/alert with thresholds is added (cut). accurate status: PASS with labels: "estimated, API-equivalent", "history starts when Loom first indexed" (cold-start window is 90 days and Claude's cleanupPeriodDays is configurable, default 30, so older data may be absent), explicit Outside Loom / Deleted sessions / Unattributed buckets, never a guessed attribution. A project/ticket share is NOT plan-quota share (Anthropic does not expose the weights); say "estimated cost", not "quota". fluency: PASS, no prompts, no waits, no new surface in the working flow. modularity: PASS if the grouping is a pure function in its own file and the new cards live beside, not inside, UsageReportCards.swift (already 506 lines). CLI-update resilience: PASS, only fields the parser already depends on (sessionId, isSidechain, message.id); a vanished marker degrades to "Unattributed", and the existing "N lines not understood" notice stays; no CLI version pinned. RISK: workflow-agent files (subagents/workflows/<run>/agent-*.jsonl) and forked sessions have unverified sessionId behaviour (see experiments). ownership: not touched (read-only on Loom's own index). user authority: PASS, no cross-session action. Standing decisions: no conflict with D-34, the terminal contract or D-43/D-46; it extends D-32 ("lightweight usage and cost view") and D-37 (current usage page), so the user should confirm the rollups are within that spirit. Delete: extends the existing forget rule (tokens stay in totals, link goes), and the index must keep leaving no session id bytes.

## Value for the user (3/5)

Real but periodic value: the user has two ticket-based work projects, a quota ceiling and heavy subagent/workflow use, so "which project and which source eats my quota" and "what did this ticket cost" are useful decisions about workflow style and effort reporting. But the daily flow is not changed, the totals/model/plan-limit views already exist, ticket attribution is only as good as the titles, and the figure is an API-equivalent estimate, not quota. Low risk and cheap because the ledger, dedupe and delete rule are already built, which is why it is worth doing small rather than skipping.

## Experiments before building

- E1 transcript facts spike, in an isolated CLAUDE_CONFIG_DIR (never the real ~/.claude), with Loom's fake or a throwaway profile: run one main turn with a Task subagent, one multi-agent workflow (subagents/workflows/<run>/), one resume, one claude --resume --fork-session, and one /clear; inspect only the usage lines' sessionId, isSidechain, cwd, message.id, requestId. What decides it: (1) if workflow-agent lines carry the parent sessionId, per-session and per-ticket totals include workflows; if not, attribute by the owning session directory (UsageTranscriptWalker already derives it from the path) or label them Unattributed; (2) if a forked file replays the parent's history under the same message.id, totals stay right (message-id dedupe) but per-session attribution depends on which file is scanned first (ties never update the row), so either make the rule deterministic (earliest file wins) or show per-session numbers as approximate for forks; add each case as a fixture in ClaudeUsageFixtures/ClaudeUsageIndexTests.
- E2 volume check on the existing opt-in ClaudeUsageCorpusTests corpus (LOOM_USAGE_CORPUS, never ~/Documents): time the new by-session query for 24 h, 30 d and 90 d. Decision: if a 90 d query exceeds roughly 100 ms, keep it behind the card being visible and cache the result per refresh generation; if it is tens of milliseconds, compute it eagerly with the period report.
- E3 (one question to the user, no code): how many of their recent sessions have the ticket key at the start of the title? Decides whether title-derived tickets are good enough or the ticket-centred-sessions idea must come first.

## Questions for the user

- Deleted sessions: keep the current rule (tokens stay in the period, model and day totals; the session link is cut), so a deleted session moves from its project or ticket row into a 'Deleted sessions' row (recommended, no schema change, no path left behind), OR persist a project key on every message so project totals survive deletion (additive column, one-time backfill from transcripts that still exist, and the deleted session's project path stays in the index)?
- Ticket source: only sessions whose ticket_key is set or whose title starts with the key (the D-40 rule), or also a key anywhere in the title or the branch name? And should the same key across the two work projects roll up together?
- Ranking number: estimated cost (recommended, because cache reads dominate raw tokens) or total tokens, and is a plain share list enough with no 'unusually large' alert?
- Should usage by project also include Claude sessions run outside Loom whose folder matches a Loom project (needs the per-line cwd field and a persisted project key), or only sessions Loom knows, with the rest under 'Outside Loom'?
- Are these cards within the 'lightweight usage view' the user approved in D-32, and is the Usage page plus the idle record view the right (only) place, with nothing added to the sidebar cards or the footer?
