# I-27: Multiple Claude accounts via user-managed config dirs

Card from the [Loom v2 idea catalog](../IDEAS.md). **Multiple Claude accounts via user-managed config dirs** · verdict **later** · cost M · value 2/5 · proposed by 2 reports: [orca](../products/orca.md), [superset](../products/superset.md).

> Technically feasible and safe if kept to "per-project account, new launches only, per-profile plan meters", but nothing in the user's notes says they have two Claude accounts, and the real cost is the per-session profile plumbing (resume, delete, usage, subagent reads), not the env var, so build it only once the user confirms two plans.

## What the user gets

A label and a CLAUDE_CONFIG_DIR per account: new sessions (and 'restart on account B when idle') launch with that env, and the new-session picker/footer shows each account's limit headroom, so two-plan users stop logging out and in and can start the long run on the account with room.

## Mechanisms found in the research

Env-at-launch (already a Loom strength) with per-profile meters from the CLI's own get_usage control request (documented-ish; shape flagged experimental); profile switch applies to new launches only; show 'unknown' for plans that do not expose limits. Cross-account resume by symlinking history dirs (projects, session-env, todos...) depends on internal CLI layout and breaks 'never pin the CLI', so keep v1 to new sessions/restarts. Each config dir is a separate plugin/skill/settings set and a separate supervisor instance.

## Debates and fact-check corrections

Orca reads the Keychain OAuth token and calls undocumented /api/oauth/usage (skip: legal page says third parties may not collect/store/intermediate Claude.ai credentials). Superset notes one conversation history is shared across accounts. Recurring support surface (two settings/plugin sets); ToS sensitivity. T3 supports multiple Claude provider instances through CLAUDE_CONFIG_DIR as a design reference. Real demand: a Reddit user alternates two Max 20 plans.

## Design in Loom

FACTS FROM THE CODE. (1) The launch env is already per launch: ProviderLaunchProfile.claude(...) sets CLAUDE_CONFIG_DIR = config.path (ProviderLaunchProfile.swift:146), and SessionRuntime.claudeProfile (SessionRuntime+Claude.swift:~90-115) pins it only when toolchain.profileDirectory != nil (acceptance runs); otherwise it passes the login shell's value and never pins ~/.claude. launchClaude builds the ClaudeRegistryReader from profile.environment, so the registry follows a per-launch dir for free. (2) Loom's hooks, socket env and skill reach the CLI by flags and env (--settings with hooks, --plugin-dir from ClaudeLoomPlugin, LOOM_HOOK_*/LOOM_CLI), written into Loom's data folder, so NOTHING Loom-owned has to be installed into a second config dir. This contradicts the idea's "separate plugin/skill set and separate supervisor instance": one ProcessSupervisor and one run scope can launch with any env. What does differ per dir is the USER's own CLAUDE.md, agents, skills, settings, MCP and plugins (this user's heavy setup lives in ~/.claude), so a fresh second dir starts bare; Loom must not manage that (user symlinks or copies it).
WHAT IS SINGLE-PROFILE TODAY AND MUST BECOME PER-SESSION (this is the real cost): (a) the catalog has no profile per session: sessions has no config column (only deletions.config_dir, CatalogDatabase.swift:190) and SessionCatalog.schemaVersion = 3; resume (resumeConversation, SessionRuntime.swift:446) must launch with the dir the conversation was created under or the CLI says "No conversation found". Needs schema 4: sessions.profile_id (nullable = default) and projects.profile_id, plus a small accounts list in app_state or a new table (label, absolute dir). (b) SystemProviderToolchains caches one ProviderToolchain per provider with one profileDirectory (ProviderToolchain.swift); key the cache by (provider, profile) or, lighter, keep the one toolchain and apply the profile at claudeProfile() time (capabilities come from --help, which does not depend on the dir). (c) claudeConfigDirectory() (SessionRuntime.swift:631) feeds deletion (ConversationDeletion.swift:199), claudeProjectsDirectory() for the subagent panel (ConversationController.swift:358) and ClaudeTranscriptEffort at resume; all must take the session's profile. Deletion is the accuracy trap: deleting a profile-B conversation by scanning the default dir would report success while the files remain. Rule: the deletion candidate resolves the dir from the stored session profile, and refuses (deletionRefused) if the profile is unknown or its folder missing. (d) The usage index and watcher are one-profile by construction (ClaudeUsageIndex(profile:), UsageTranscriptWatcher on one projects dir, AppDelegate+Usage.swift; STAGE-U already notes "index is not partitioned per profile"). Light version: leave tokens-today for the default profile only (label it), do not build a second index/FSEvents stream. (e) ClaudePlanLimitsFetcher is already parameterised by ClaudeProfileLayout (init takes profile; environment() pins non-default dirs), so a second fetcher per account is a few lines; its 2-minute / window-visible / never-two-at-once gating lives in UsageModel and would need to loop over accounts.
LIGHTEST VERSION (adopt-light shape, if/when wanted): 1. Accounts: label + absolute CLAUDE_CONFIG_DIR, stored in Loom's catalog app_state; added/removed in Settings (new "Accounts" block on General or a small section on Usage). Default = "the CLI's own default" (today's behaviour, no pinning). 2. Binding is per project, not a per-launch picker: projects.profile_id. A project (e.g. an EDDP work project) always starts on its account, so Cmd+N and the menu bar "New Claude Session" stay one action (fluency); sessions copy the project's profile into sessions.profile_id at creation and keep it forever (resume, delete, subagent reads, "a session opens a session" inherit the parent's profile via OpenSessionCoordinator). Projectless sessions use the default. A secondary "New Session on <account>" appears only in the right-click/context menu. 3. Switching an account on a project affects only new sessions; existing stopped sessions resume on their stored profile; no "restart on account B when idle" in v1 (cross-account resume needs Orca's symlinked history dirs, claude-profile-history.ts: internal layout, breaks "never pin the CLI"). 4. Meters: per account, get_usage via ClaudePlanLimitsFetcher(profile:), asked only on events already used: first window shows, Usage page opens, the new-session menu/popover opening, a window showing again after 5 min; at most one process at a time, ~1 s each, never with no window visible, result cached with fetchedAt. Plans without limits (API-key / Console login, `rate_limits_available == false`) render "limits unknown", never a number. 5. Login state: do not read credentials. The documented `claude auth status --json` (exists in 2.1.300) can say loggedIn once when an account is added or when a launch fails; an account that is not logged in just shows the CLI's own sign-in prompt in the terminal (a new dir also triggers onboarding screens). 6. Drift: nothing here reads the dir layout beyond what Loom already reads (projects/<project>/<id>.jsonl for usage/effort/subagents, which ClaudeProfileLayout already encodes); CLAUDE_CONFIG_DIR itself is a documented env var (code.claude.com env-vars page). Bounds: accounts list capped (say 4), one fetch at a time, no timers, no extra watcher, no extra index.
WHAT IT WOULD TAKE TO VIOLATE PRINCIPLES AND HOW THE DESIGN AVOIDS IT: polling quotas on a timer (Orca's 15-min OAuth poll that 429s) -> event-gated ask only; reading the Keychain OAuth token or calling /api/oauth/usage -> never, only the CLI's own get_usage (the legal page forbids third parties collecting/storing/intermediating claude.ai credentials); one usage index per profile with its own FSEvents stream -> not built; symlinking history dirs -> not done; false "deleted" or "resumed" on the wrong dir -> profile stored per session and verified before delete/resume; cross-session authority -> the open-session channel inherits the parent's account and still needs user approval, and an agent can never choose another account.
REESTIMATE: the idea says M. For this codebase the env-at-launch part is S; the correct per-session profile plumbing (schema 4 migration + backup/downgrade guard, resume, deletion, subagent panel, effort lookup, open-request inheritance, accounts model, Settings UI, card badge, header chip, per-account meters, failing-first tests with isolated CLAUDE_CONFIG_DIR fixtures; the fake provider already honours CLAUDE_CONFIG_DIR) is M-L. Light version above: M. Full version with a per-profile usage index and cross-account resume: XL and not recommended.

## Where it shows

Settings > General gets a small "Accounts" card: rows of label + folder path + a light status ("signed in" / "limits unknown" / "folder missing"), Add/Remove, and a one-line hint that the folder must hold its own login and any agents or skills the user wants there. Project right-click (and the project colour menu neighbourhood) gets "Account: Default / Work" as a single choice. Cards and the detail header chip show the account label only when the user has more than one account (a quiet secondary-text suffix after the branch, so a single-account user sees no change). The footer chip stays as is (default account, bottleneck window); its popover or the Usage page's Plan limits card gains one extra row per account ("Work  5h 38% left, resets 16:40  Wk 71% left") using existing PlanLimitWindow formatting, and an account whose plan exposes no limits reads "limits unknown". New session stays Cmd+N and uses the project's account; the sidebar's context menu offers "New Session on Personal". No new pane, no modal picker.

## Principle check

Resources: pass if meters are event-gated (no timer, one ~1 s headless claude at a time per account, only with a window visible, same gating as ClaudePlanLimitsFetcher) and no second usage index or FSEvents stream; risk if someone adds a refresh timer or per-profile index. Predictability: pass with binding per project and a profile frozen on the session; risk if a global "active account" toggle silently changes where Cmd+N goes. Accurate status: pass only if resume and delete use the stored profile and refuse when it is unknown; this is the main failure mode (delete or resume scanning the wrong dir and claiming success), and the meters must show unknown rather than a guess. Fluency: pass with project binding (no extra step per session); risk with a mandatory per-launch picker. Modularity: pass if the profile is data on the session/project and ClaudeProfileLayout stays the single resolver; risk of touching SessionRuntime, catalog schema, deletion, usage and UI at once, so slice it. CLI-update resilience: pass; CLAUDE_CONFIG_DIR is a documented env var, get_usage already has drift handling (shape flagged experimental, unavailable -> hidden), no layout beyond what Loom already reads; risk only if cross-account resume or settings copying were added. Ownership: pass; one supervisor and run scope own all processes, the headless get_usage child is Loom-spawned and short-lived. User authority: pass if an agent-opened session inherits the parent's account and never selects one; ToS: ordinary per-account use of the CLI with its own login is fine, but whether alternating two paid plans to get around limits is acceptable is for the user to judge (Orca's token reading is explicitly out).

## Value for the user (2/5)

The user's notes ask for remaining usage on (singular) Claude, which Loom already ships (footer chip, Plan limits card). The demand evidence is a Reddit user with two Max 20 plans; there is no sign this user has two accounts. If they do (work vs personal, or two plans), value jumps to 4: the work projects bind to a work account once and logout/login disappears. A second dir also starts without their agents, CLAUDE.md, skills and MCP, which is a recurring setup cost for a heavy-config user.

## Depends on

- User confirms they have, or will soon have, two Claude accounts
- Per-session profile persistence (catalog schema 4) is a prerequisite for any account feature and also fixes the long-standing 'config dir not stored per conversation' gap noted in plans/experiments/run1-planning-scans/CP4-deletion.md
- Footer/Usage plan-limits surface (exists) for the per-account meter rows

## Experiments before building

- Isolated-dir launch spike (CLAUDE_CONFIG_DIR under Loom-Dev/probe, never the real dirs): start a Loom-hosted session with a fresh dir and confirm hooks via --settings, --plugin-dir skill, the loom-hook socket and status events all work unchanged and that onboarding/login screens do not break the hook-silence watchdog or state. Decides: whether 'no per-profile install' really holds.
- Resume-mismatch probe: `claude --resume <id>` under the wrong dir; capture the exact failure so Loom can refuse before launch from the stored profile instead of after. Decides: whether a pre-check is needed or the CLI error is clean enough.
- get_usage per profile: run ClaudePlanLimitsFetcher against two isolated logins (and one API-key/Console login) and confirm distinct answers, the rate_limits_available=false shape, and that a not-logged-in dir yields a clean .notAvailable/failure category. Decides: the 'limits unknown' rule and the exact unsigned-in state.
- `claude auth status --json` shape (field names only, no account data stored) to decide whether the Accounts card can show signed in / not signed in without touching credentials.

## Questions for the user

- Do you have (or plan to have) two Claude accounts or plans? If not, skip this; if yes, is it work vs personal (bind by project) or two plans of the same person (bind by headroom)?
- Is binding an account per project enough, or do you want a per-session choice at start (adds a step)?
- Are you comfortable with a second config dir starting without your ~/.claude agents, CLAUDE.md, skills and MCP (you would symlink or copy them yourself), given Loom will not manage or copy settings?
- Is alternating two paid plans to get around limits acceptable to you under Anthropic's terms? (Loom would only read each account's own get_usage and never touch credentials.)
- Should tokens-today in the footer stay default-account only in v1, with per-account plan limits as the only multi-account meter?
