# I-30: Per-turn checkpoints and last-turn change chip

Card from the [Loom v2 idea catalog](../IDEAS.md). **Per-turn checkpoints and last-turn change chip** · verdict **spike-first** · cost L · value 3/5 · proposed by 8 reports: [t3code](../products/t3code.md), [codex-app](../products/codex-app.md), [zed](../products/zed.md), [cursor](../products/cursor.md), [emdash](../products/emdash.md), [vibe-kanban](../products/vibe-kanban.md), [review-git-loop](../products/review-git-loop.md), [claude-official](../products/claude-official.md).

> Worth building as a thin, view-only, event-driven layer (a chip plus a per-turn changed-file list, no restore, no diff renderer), but only after a spike settles four unknowns: where the snapshots live, git cost per hook on the user's real repos, the hook race at prompt time, and the cost of a run scope per git call.

## What the user gets

'What did this turn change' per prompt, correct regardless of which tool the agent used: a chip on the card, a per-turn file list/diff in the detail pane, and a trustworthy 'since I last looked' marker. Restore is deferred.

## Mechanisms found in the research

Lightest: record HEAD and `git diff --stat` at UserPromptSubmit and Stop (hook events, no polling). Fuller: a hidden snapshot ref per turn built with a temporary index (write-tree / commit-tree / update-ref into refs/loom/checkpoints/<session>/<n>) so the user's index and worktree are untouched, then diff consecutive refs (T3 CheckpointStore handles sparse checkout, racy index timestamps and fsync of refs; budget for them or limit to simple repos). `git stash create` skips untracked files (needs testing). Fall back to 'since session start' and say so when the baseline hook is missing. Restore/rewind stays with Claude's own /rewind; no auto-commit per turn.

## Debates and fact-check corrections

Claude's /rewind restores only edits made through Claude's file tools (misses Bash, subagent and outside changes) and cannot be driven in a TUI session, which is the case for snapshot refs; Vibe Kanban's auto-commit rewrites branch history and its reset engine depends on drifting flags (--resume-session-at), so skip both. Concurrent sessions in one checkout make 'last turn' include other edits: label scope honestly ('changes since the prompt was sent'). Hidden refs in the user's repo need a cleanup policy; size/time caps, skip non-git and giant repos, run off the main thread. review-git-loop: do after the diff view, or skip if 'commit first' plus /rewind is enough.

## Design in Loom

FACTS FROM THE CODE (read)
- Both triggers already arrive. `ClaudeHookEvent` (Sources/LoomCore/ClaudeHook.swift) parses `userPromptSubmit`, `stop`, `stopFailure`, and also `cwd` (`workingDirectory`), `prompt_id` (`promptID`) and `promptIsSynthetic`. `ClaudeSessionAdapter.receive` (ProviderSessionAdapters.swift ~205-300) is the one place where a turn start (non-synthetic UserPromptSubmit) and a turn end (Stop/StopFailure) are known, ordered, after the tracker has accepted them.
- Loom registers no PostToolUse hook on purpose: ProviderLaunchProfile.claudeSettings says "No per-tool hooks: each hook spawns a helper". So Loom cannot know which files the agent touched, and a git-level snapshot is the only way to be correct for Bash, subagent and outside edits.
- Loom has no git runner in the production path today. `GitBranch.read` / `BranchCache` only read files. The one git user is `CleanupWorktreeProtection.live` (CleanupCoordinator.swift), which calls `ProcessSupervisor.captureHelper("/usr/bin/git", ...)`, and the cleanup review is dev-build only (ARCHITECTURE section 2, Retention). The owned helper path exists, with a ledger entry, a deadline, a 4 MiB output cap and a cancel on Quit (ProcessSupervisor+EnvironmentJobs.swift, LaunchEnvironment.runHelper/capture).
- IMPORTANT cost fact: `captureHelper` uses `runOwnedJob(scope: .perCall)`, which opens a fresh LoomRunHost scope through LaunchServices (`open -n -g -j`) for EVERY call and releases it after. One call per git command would be heavy, so a snapshot must be ONE call (a `/bin/sh -c` script that runs the whole recipe), and probably should reuse a shared scope kind like `.environment` when snapshots overlap. The scope-launch latency is not measured anywhere in the repo that I could find (the cp5 runscope-latency file measures terminal echo, not scope open).

DESIGN (smallest version that is correct)
1. New LoomCore type `TurnSnapshotStore` (actor, same shape as `BranchCache`; no UI imports). Input: (loomSessionID, workingDirectory, kind: base|end, promptID). It runs one owned helper job per snapshot.
2. Where the snapshots live. Preferred: a Loom-owned shadow git dir under the data root (`<data root>/turn-snapshots/<hash of repo toplevel>.git`) used as `GIT_DIR=... GIT_WORK_TREE=<toplevel>`, with its own index. This is better than refs in the user's repo (T3's `refs/t3/...` and the idea's `refs/loom/checkpoints/...`) because: no ref or object is written into the user's repo; no exposure to `git push --mirror`; Loom's own index means no copy of the user's index and no racy-index trouble with the user's index; cleanup and size are one directory (rmdir plus verify), which fits the deletion contract and 'verified outcomes'; the user's `git gc` cannot race it. Cost: the first snapshot of a repo copies all non-ignored content (blobs) once, then it is incremental through the shadow index. Fallback within the spike: temp-index refs in the user's repo (the T3 recipe: copy index to a temp GIT_INDEX_FILE, `git add -A`, `write-tree`, `commit-tree`, `update-ref`). Honour `.gitignore`, pass `-c core.fsmonitor=false` (never start a git daemon in Loom's scope), `-c commit.gpgsign=false`, fixed GIT_AUTHOR/COMMITTER env, `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0` (same env pattern as CleanupWorktreeProtection.live), and fsync the ref/loose objects (T3 saw 0-byte refs after unclean restarts).
3. Triggers (no polling, no watcher). (a) non-synthetic UserPromptSubmit: take 'base', detached from the hook path so it never blocks the adapter's `transitioningRuns` lock or Claude (the hook helper has timeout 1 and is synchronous). (b) Stop and StopFailure: take 'end', then `git diff --numstat -z base end` (object-only, no work-tree scan) in the same script; the result is path, +, -, status for at most 200 paths plus totals. A later Stop in the same turn (background subagents, synthetic hand-back prompts) overwrites 'end'. An interrupted turn has no Stop: the next real prompt's 'base' doubles as the previous turn's 'end', marked 'ended by interrupt'. Also record HEAD at both ends; if HEAD moved say 'commits/pull/checkout included' (the worktree diff itself is still right when the agent commits its own edits).
4. Bounds. One snapshot at a time per repo toplevel, at most 2 repos at once, a pending 'end' coalesces, 8 s deadline, outputs capped. A repo that blows the deadline is marked 'too slow' for this app run and shows 'tracking off for this repo', never retried in a loop. Skip non-git folders, bare/other-owner repos, folders where `git` is not usable. Per-session cap of 100 turns and 30 days (matches Claude's own /rewind retention), pruned in the same script at snapshot time (event-driven, no timer). Do nothing for idle/stopped sessions (no run, no hook, no git).
5. State. Memory only: `SessionViewState` gains `lastTurnChange: TurnChangeSummary?` (turn index, file count, +/-, state running/ended/interrupted/unavailable, scope text), carried by a new `SessionEventChange.turnChanges(...)` case, published by the adapter like `.subagents`. No catalog migration. The shadow repo is the durable truth: after a relaunch the detail pane re-derives a turn's list lazily from stored commit messages (prompt id, HEAD, timestamps) with one bounded `git diff`, only while that pane is open. 'Since you last looked': no extra snapshot; the unseen range is base(first turn after the last `setViewed`) to end(latest) and is one object-only `git diff`.
6. Deletion and honesty. Register a `ConversationForgetting` hook (as the usage index does in AppDelegate+Usage) that removes the session's snapshot refs from the shadow repo; the shadow repo itself is dropped when no session refers to it. Add one line to the deletion dry run ('N turn snapshots, X MB in Loom's data folder'). Restore stays out; the UI offers 'Copy patch' and 'Open in editor' only, and for a real revert points at /rewind or git.
7. Minimal UI hook: nothing runs in the view layer; `CatalogModel.apply` stores the summary on `SessionRowModel.live` like the other frame fields (statistics and render probes cover it).

## Where it shows

Card (two-row card, design/DESIGN.md section 3 item 4): in the bottom row after the branch, a small tertiary-to-secondary 'Δ 4 files +120 -18' text only when the last turn ended with changes, only on live/Active sessions; blue/neutral, no new status hue, never colour-only (text carries it). Nothing is drawn for 0 changes or when tracking is unavailable. Header (SessionHeaderViews, next to the project/branch chip, D-53 fixed places): the same chip is a button that opens a popover (not a new pane) with: scope line ('Changes since the prompt was sent, 14:02 - 14:09; other edits in this folder are included' and, when it applies, 'HEAD moved: commits or a pull are included'), the turn picker (last turn, since you last looked, turn N), a file list with status and +/-, and Copy patch / Open in editor / Reveal. A Settings switch 'Track changes per turn' (Settings > General). Full diff rendering, line comments and restore are deliberately not part of this idea (they belong to the review-pane idea, which this feeds).

## Principle check

Resources: RISK, manageable. Event-driven, two git jobs per turn only for live sessions, nothing when idle or hidden. The risks are `git add -A` on a large tree and one run-scope launch per helper call (unmeasured); both are why this is spike-first. Predictability: PASS with a switch, and with a fixed scope label. Accurate status: PASS only with honest labels ('changes since the prompt was sent'; 'unavailable' when the base is missing, the repo is too slow or git is unusable; never an invented '0 changes'). The race at prompt time (the base snapshot runs after the hook returns; a first edit in the first few hundred ms would be missing) must be shown to be negligible or labelled. Concurrent sessions in one checkout: 'last turn' includes the others' edits, say so. Fluency: PASS if it never blocks the hook helper, the adapter lock or the UI. Modularity: PASS (LoomCore actor plus one hub case plus a chip; no new target). CLI-update resilience: PASS, it uses only documented hooks (UserPromptSubmit, Stop, StopFailure, cwd, prompt_id) and git; it does not depend on /rewind internals, `--resume-session-at` or the transcript format. Ownership: PASS only if every git process goes through the owned helper path (never `Process()` in the app), with fsmonitor disabled so no daemon outlives the scope. User authority: RISK for the refs-in-user-repo variant (Loom writes into the user's repository); the shadow store avoids it, and a switch gives the user control. New dependency: the production app would run /usr/bin/git for the first time; the Apple shim can pop an Xcode CLT installer dialog if the tools are missing, so check the toolchain before spawning (the cleanup review, dev-only today, already assumes it). Privacy: snapshots copy untracked, non-ignored files (for example an un-ignored .env) into Loom's data folder or the repo's objects.

## Value for the user (3/5)

The unique value is cross-session triage that Claude's own /diff (fullscreen TUI, per-turn T1/T2 from Claude's file-edit checkpoints, misses Bash) cannot give: with several sessions and subagent workflows, a card chip says which finished session actually changed code and how much, and 'since you last looked' makes the blue Finished dot more meaningful. The per-turn file list itself is a convenience, since the user can already press /diff or run git. Without a diff view (a separate idea) it is a data layer with a thin view, so the daily payoff is moderate; with that view it becomes the core of a review loop.

## Depends on

- a review/diff pane idea (the chip is useful alone, but 'Copy patch' and 'Open in editor' are the only drill-down without it)
- Settings switch plumbing (UIPreferences) for 'Track changes per turn'
- a shared-scope option in ProcessSupervisor+EnvironmentJobs if the per-call scope launch proves too slow

## Experiments before building

- E1 snapshot cost and correctness (isolated CLAUDE_CONFIG_DIR / fixture data root, loom-fake-provider, no real ~/.claude): on 3 repos (small, the user's two work-project sizes, one large/monorepo-like), time the one-script recipe through `captureHelper`: cold first snapshot, warm incremental, 1 changed file, 100 changed files, one large untracked file, a repo with a sparse checkout and a linked worktree, and a user with fsmonitor/untrackedCache on. Compare shadow-GIT_DIR vs temp-index-in-user-repo. Decide: warm p95 <= ~300 ms and cold <= ~3 s on the work repos; shadow disk growth small (a few percent of the repo for typical turns); CPU well inside the 40 % gate; user's `git status`/index untouched (index mtime and bytes unchanged, no index.lock). Anything above the thresholds means 'limit to simple/small repos' or skip.
- E2 hook facts (fake provider plus a short real-Claude run in an isolated profile, D-04 allows it): (a) does UserPromptSubmit fire for a message queued mid-turn and for synthetic hand-back prompts (promptIsSynthetic), (b) is Stop skipped on Esc interrupt, (c) measure the gap between the UserPromptSubmit hook arriving and the first file change by the agent, versus the time to finish the base snapshot (the race window). Decide: if the base snapshot loses the race in more than a trivial share of turns, base on the previous turn's end snapshot instead and relabel the scope ('since the last turn ended').
- E3 helper cost: measure `runOwnedJob(.perCall)` end to end (scope open, spawn, release) for a no-op `/bin/true` and for the snapshot script, 20 runs each, with 1 and 5 concurrent. Decide: per-call scope is acceptable only if its added median is small next to the git work; otherwise add a shared scope kind.
- E4 'git stash create' claim from the idea: it takes no -u / --include-untracked option and works from the real index, so it misses untracked files and can contend with the user's index lock; confirm in one throw-away repo and drop it for good. Also confirm that `git add -A` against a copied or shadow index honours .gitignore, .git/info/exclude, nested repos and submodules as expected.
- E5 safety and platform checks: with the Xcode CLT absent (or `xcode-select -p` failing) the /usr/bin/git shim must not open an installer dialog; and a project under ~/Documents must be readable by git inside the LoomRunHost scope (the host is its own TCC-responsible app, DEVELOPMENT.md section 2), as Claude's PTY child already is.

## Questions for the user

- Where may snapshots live: Loom's data folder (shadow git dir, recommended) or hidden refs in the project repos (T3 style)? The first never touches the repo; the second needs a documented ref prefix and cleanup.
- On by default, or opt-in per project/Settings? It stores copies of non-ignored files (including un-ignored secrets) for 30 days or 100 turns and runs git twice per turn.
- Accept the honest scope label 'changes since the prompt was sent' (other sessions or you editing the same folder are included), or require a one-session-per-checkout rule or worktrees before showing a chip?
- Is a chip plus a per-turn file list (no diff rendering) worth it before the review/diff pane exists, or should this wait and ship together with that pane?
- Must deleting a session also delete its turn snapshots and show them in the dry run (recommended), and may the cleanup review later list orphaned snapshot stores?
- Is the first production dependency on /usr/bin/git (Xcode command line tools) acceptable for this Mac, with a quiet 'unavailable' state when it is missing?
