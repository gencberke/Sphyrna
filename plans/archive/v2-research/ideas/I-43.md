# I-43: Process-tree view: listening ports / dev-server pill and on-demand resource inspector

Card from the [Loom v2 idea catalog](../IDEAS.md). **Process-tree view: listening ports / dev-server pill and on-demand resource inspector** · verdict **adopt-light** · cost M · value 3/5 · proposed by 5 reports: [cursor](../products/cursor.md), [superset](../products/superset.md), [conductor](../products/conductor.md), [vibe-kanban](../products/vibe-kanban.md), [openchamber](../products/openchamber.md).

> Adopt a light version: an event-driven "what is this session running and listening on" popover and a conditional port segment, read from the run scope Loom already owns; skip the embedded WKWebView and the LOOM_PORT range.

## What the user gets

An 'Open localhost:PORT' pill on a card when its own process tree is listening (default browser; an embedded WKWebView only on request), and an on-demand popover with per-session process-tree memory/CPU and the top 3 child processes, so a leaked dev server or runaway test run is visible and feeds the park decision.

## Mechanisms found in the research

Enumerate sockets and resource totals of the run scope's pids via libproc only when the card is visible, on the Stop hook, on click or while the popover is open (never a scanner: Superset's lsof scan every 2.5 s / 30 s idle was a CPU/lag source); name only what Loom started; show 'sampled at'; optional LOOM_PORT range env for per-worktree ports (Conductor gives 10 ports per workspace). Nothing drawn when hidden.

## Debates and fact-check corrections

Per-process attribution on macOS (shared coalitions, helpers) is easy to overstate; Conductor fixed wrong memory totals twice. An embedded browser is the heaviest component Loom would own and contradicts 'idle costs nothing' if left open (cmux and Superset pay in memory). Backend-focused user: low payoff for annotated-browser/design-mode work (see skips).

## Design in Loom

DESIGN
Why Loom can do this better than Cursor, Superset or Conductor: a session's run scope (coalition of a LoomRunHost, `RunScope.forkedMembers()` in Sources/LoomCore/RunScope.swift) is an exact, unforgeable member list of everything the session forked, including detached and reparented work. Attribution is membership, not a ppid walk, so the "shared coalition / helpers" worry in the idea's debate section mostly does not apply. Launchd-spawned members are already filtered out (`launchdSpawned`). Most primitives already exist: `ProcessTable.resourceUsage(pid:)` and `physicalFootprint(pid:)` (ProcessTable.swift, `loom_process_resource_usage` in CLoomPOSIX.c, rusage V4 with Mach tick conversion), `RunScopeTable.members(coalitionIDs:)` (one pass for many scopes), `ProcessTable.executablePath`. The dev-only `scopeAccounting` in Sources/loom-app/Evidence/EvidenceResourcePool.swift is already this inspector minus the UI and the sockets. The only genuinely new low-level piece is listening sockets: public libproc (`proc_pidinfo(PROC_PIDLISTFDS)`, then `proc_pidfdinfo(PROC_PIDFDSOCKETINFO)`, keep SOCKINFO_TCP with `tcpsi_state == TSI_S_LISTEN`, port from `insi_lport`). I confirmed these symbols exist in the local SDK headers (sys/proc_info.h, libproc.h). Nothing in the repo uses them for sockets today (the only proc_pidfdinfo use is a vnode-path test in SessionRuntimeTests.swift:858).

Pieces
1. CLoomPOSIX: one function, `loom_tcp_listeners(pid, out[], cap, &count)` returning port, family and loopback-or-any. It reads fds with a hard cap (for example 4096 fds per process and 32 listeners), fails closed with errno, and checks the reply size. It uses a public flavor, so there is no new private-ABI risk.
2. LoomCore, new file `ScopeInspector.swift` (value types plus one function), no UI import. `ProcessSupervisor` gets a small accessor that returns the session's `RunScope` handle (like `scopeWork(sessionID:)` in ProcessSupervisor+Sampling.swift). The heavy reads then run off the supervisor actor, because `loom_scopes_members` can sleep up to 50 ms per unreadable pid (RunScope.c). The result is a `ScopeInspection { sessionID, runID, sampledAt, members:[name,pid,footprint,cpuNs,listeners], totalFootprint, unreadableCount }`. Any unreadable member that cannot be ruled out makes the inspection "unavailable", never a partial total, as with the existing fail-closed membership read.
3. LoomCatalogUI: `ConversationIntents.processInspection(sessionID:) async -> ScopeInspection?` (same shape as `subagentTranscript(path:agentID:)`, with a default of nil), implemented in ConversationController via SessionRuntime. A small `ProcessInspectorModel` (like `SubagentTranscriptModel`) owns the popover: it samples once on open, then every 2 s while the popover is open AND `windowIsVisible` (the plumbing used in CatalogModel+Subagents.swift), and cancels on close. CPU % is the delta of cumulative user+system ns between two samples, so the first frame shows memory and "CPU --".
4. Pill state: a tiny `ListenerBook` in CatalogModel (not in SessionEventHub frames, so no per-card re-render churn) holds the last known listeners per live session. It is refreshed only at events Loom already handles for the branch cache (BranchCache precedent: CatalogModel.apply on `.turnComplete`, line ~1362, and `setWindowActive`, line ~1020): the Stop hook of that session, window becoming active (one pass covers all live scopes), popover open, click. There is NO sampling for "card visible". A card merely scrolling into view triggers nothing, which is the Superset lesson. To avoid a stale pill (an accuracy problem), each listener pid known to the book gets a kqueue/DispatchSource `.exit` watch (event-driven, zero polling); the entry is dropped on exit. The pill therefore only claims "was listening at last check and that process is still alive", and the popover shows the sample time.
5. "Open localhost:PORT" calls `NSWorkspace.open("http://localhost:PORT")` (localhost, not 127.0.0.1, per the Conductor note), after a single-pid re-check that the listener still exists. If it is gone the UI says "No longer listening" instead of opening a dead URL (no false success). Open is per row and never guessed from process names: ports can be Postgres, JDWP or Redis, not HTTP. Loom never probes ports.
6. Bounds: one coalition pass (~700 pids, 2 proc_pidinfo each, a few ms) plus about N members x (rusage + fd list) per sample. Max 10 live sessions x ~10 members. Memory is a handful of structs. No timer exists unless the popover is open and the window visible.

What would make it a principle violation, and how the design avoids it: (a) a periodic scanner or a per-card-visibility sampler is the Superset failure (lsof every 2.5 s, 19 short-lived processes per tick, issue #6717): no timer outside the open popover. (b) Sampling inside the supervisor actor could stall stop/launch paths for tens of ms: run reads in a detached utility task off the RunScope handle. (c) A stale "listening" pill is false status: the pid exit watch plus the 'as of' stamp. (d) Overstated totals: label as "memory footprint, approx." (contract §10 already warns summing child memory can double count shared pages) and show only scope members, never "whole machine". (e) An embedded WKWebView is the heaviest thing Loom would own: not built; default browser only.

Scope limits to state honestly in UI copy and docs: Docker, Homebrew services and anything launched through launchd/LaunchServices is outside the scope by construction (contract §6 "Out of scope"). For this backend user a Docker Postgres or Redis will NOT show, only what the agent forked (Spring Boot, node, test runners). The view must say "in this session", not "on this Mac".

Cost re-estimate: M, as the idea says, but only with the light scope. About S for the C function and ScopeInspector with a fixture test (extend loom-test-child to bind a port; RunScopeTests already assembles real scopes), S-M for the popover, model, header wiring and pill, plus docs (ARCHITECTURE, UI-MAP, DESIGN). The embedded WebView would be XL by itself (entitlements, cookies and logins state, teardown when hidden). The LOOM_PORT range is a separate S-M item (allocation persistence, resume stability, and agents only use it if told).

Tests (behaviour, not mirrors): (1) spawn a fixture in a real run scope that binds an ephemeral port and a detached grandchild that also binds one; the inspection lists both and the totals are non-zero. (2) After the scope stops, the inspection is empty and the pill is gone. (3) An unreadable member makes the whole inspection 'unavailable'. (4) The popover model starts no sampling when the window is hidden and stops on close (a counter, like CatalogHotPathTests). (5) No sample is taken on a plain list scroll or card render (statistics counter stays 0).

## Where it shows

Primary surface is the detail header, because the two-row sidebar card is a fixed contract (DESIGN §2 item 4: status, title, time over branch, project, provider icon), and its second row is already full.

1. Header control group (HeaderControlGroup in Sources/LoomCatalogUI/SessionHeaderViews.swift): when a live listener is known, a conditional segment appears before Stop, with the same hairline separation Stop already uses: a small network glyph plus ":3000" (or "2 ports"). The group already adds and removes the Stop segment, so a conditional segment follows the same pattern. Click opens a popover; there is no auto-open. This is a small deviation from D-53's "fixed places", so it needs the user's okay (see decisions).
2. Popover "Processes in this session": a header line "Sampled 12:04:31 - memory approx. 1.8 GB" and a refresh icon; then up to 3 top rows by footprint (name, footprint, CPU %) and a collapsed "N more"; then a "Listening" section: each row is "node  localhost:5173" or "java  all interfaces :8080" with a trailing Open button (the all-interfaces tag is free security info). Footer: "Only what this session started. Docker and services are not included." Text only, no charts, no animation, secondary text tiers from LoomTheme.
3. Entry points that need no layout change: the actions menu (the three-dot menu in the header and the card context menu in SidebarView.swift ~line 500) gets "Processes and Ports...". It opens the same popover, and works with no known listeners.
4. Sidebar card: no pill in v1. Optional later: one 10 pt glyph at the end of the second row, drawn only when a listener is known for a session that is Finished or Waiting (the leaked-dev-server case), as the cheap answer to "which stopped-looking session still holds my port". Recommend this only after the header version is used for a week.
5. Ended or stopped sessions: nothing, since the scope is verified empty after Stop. Never drawn when the window is hidden.

## Principle check

Resources: PASS with the design above. Event-driven only (Stop hook, window activation, popover open, click), one coalition pass for all scopes, a 2 s tick only while the popover is open and the window is visible, nothing when hidden. RISK if implemented as "sample when card visible" (reject that part of the idea). Predictability: PASS. The same click always shows the same sampled-at snapshot; the pill never appears or disappears from a hidden poll. Accurate status: PASS if the pill is dropped on process exit (kqueue exit watch) and the open action re-checks the listener; totals say "approx." and any unreadable member makes the sample 'unavailable' rather than a partial number (matches the fail-closed style of RunScopeTable and contract §3 "not counted as success"). RISK: private coalition flavors are already in use; this adds only public libproc flavors. Fluency: PASS. No confirmation or wait; Open is one click. Modularity: PASS. A C function, one LoomCore value-type file, one UI model and view; LoomCore stays UI-free, and the dev-only EvidenceResourcePool can later reuse ScopeInspector. CLI-update resilience: PASS, the best of any v2 idea. It depends on macOS libproc, not on any Claude CLI output, hook or file format, and needs no drift detector. Process ownership: PASS and a strength. Naming only scope members is exactly 'name only what Loom started'; scope boundaries (launchd and Docker excluded) must be stated honestly in the copy. User authority: PASS. Read-only; an 'End this process' action is deliberately not included (it would be a user-initiated, verified signal via RunScopeTable.signal and is a separate decision). The contract's terminal-is-the-real-CLI rule and D-34 (no right rail) are untouched, since this is a popover, not a sidebar. D-20 is not triggered (no CLI behaviour changes). A LOOM_PORT env would be a launch-environment change; it is deferred.

## Value for the user (3/5)

Real but not a daily driver. Several concurrent sessions with JVM or node plus test runs make 'which session holds the RAM / who owns :8080' a genuine question, and it feeds the manual Stop decision (Loom has no auto-park; D-38 turned idle stop off). But the user is backend-focused, so an 'Open localhost' browser pill has low payoff (APIs, and Docker-hosted databases are invisible by construction); the useful backend case is port-conflict and leaked-process visibility, which the popover covers. The big productivity levers in the research (side chat, verified send, hibernate, transcript search) are worth more; this is a cheap, safe secondary feature that reuses existing primitives.

## Depends on

- none hard. Soft: an idle-hibernate/park idea (this feeds that decision); a verified 'End this process' action would build on it; LOOM_PORT belongs with any worktree/env-injection idea.

## Experiments before building

- Listener-read spike with loom-probe or a throwaway Swift script inside an isolated CLAUDE_CONFIG_DIR and a real Loom run scope (never the user's real ~/.claude): run listeners as an Apple binary (/usr/bin/python3 -m http.server), a node server bound to localhost (::1 only), a JVM (java -jar or Spring Boot-like) and a reparented/double-forked listener. Decide: does PROC_PIDLISTFDS plus PROC_PIDFDSOCKETINFO work unprivileged for same-uid processes of all four kinds (Apple/hardened-runtime binaries are the doubt), and do IPv6 dual-stack sockets report a usable port and address? Pass: all four listed, no EPERM on same-uid processes.
- Cost spike on the same setup, only when the user says the computer is idle (D-13): time one full inspection of 10 scopes x ~10 processes, and the popover's 2 s tick for 60 s. Pass: a sample well under 20 ms and under 1% of a core average during the open popover, nothing measurable otherwise; also confirm the CPU gate (40% at 1 MiB/s, contract §10) is unchanged. If `loom_scopes_members` shows >50 ms stalls from its retry sleeps, make the inspector tolerate that off-actor rather than change the stop path.
- Memory-number sanity check: compare the summed `ri_phys_footprint` of a scope against Activity Monitor's Memory column and `footprint` for the same processes. Decide the label ('approx.') and whether to show only the total or per process. Do not claim better than approximate (Conductor had to fix wrong totals twice).

## Questions for the user

- Is a conditional port segment in the header control group acceptable (a small deviation from D-53's fixed-places rule), or should v1 be menu-only ('Processes and Ports...' in the three-dot menu) with no pill at all?
- Should the popover offer 'End process' for a leaked dev server, a verified signal to one scope member that the user clicks, or stay read-only and leave stopping to the existing whole-session Stop? Read-only is the lighter default.
- Is 'Open localhost:PORT' in the default browser enough, or do you really want an embedded WKWebView? Recommendation: no WebView; it is the heaviest component and contradicts 'idle costs nothing'.
- Is a LOOM_PORT range per session wanted at all? It only helps if your project scripts read it (for example server.port=${LOOM_PORT:8080}) or agents are told to; if yes it belongs with a worktree/env idea, not here.
- Do you want the optional sidebar-card glyph for 'finished but still listening' sessions after trying the header version, given it touches the fixed two-row card contract?
