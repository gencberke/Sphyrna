# I-07: Optional 'Chat mode': Loom-owned stream-json child per session (no Node, SDK or ACP)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Optional 'Chat mode': Loom-owned stream-json child per session (no Node, SDK or ACP)** · verdict **spike-first** · cost XL · value 3/5 · proposed by 1 reports: [chat-ui-paths](../products/chat-ui-paths.md).

> Technically the right engine for a chat-centred Loom and it fits the run-scope and ownership model better than the research assumes, but it is an unbounded XL build with a headless-billing exposure and an unanswered replace-vs-convenience question, so run a recorded capture spike and gate the build on I-05 proving use.

## What the user gets

A true structured chat session with typed events, authoritative state, tool/permission cards and side questions, chosen per session as an explicit mode, with the PTY as default and fallback. Mode switch = stop plus --resume; exactly one process owns a session id.

## Mechanisms found in the research

[Semi-documented] `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --replay-user-messages --permission-prompts host|none (2.1.259+) --include-hook-events --fork-session ...`; wire protocol typed only in the published SDK typings (about 38-40 control request subtypes; system/init carries `capabilities` for feature detection; unknown types pass through). Loom already sends one get_usage control_request this way (Sources/LoomCore/ClaudePlanLimits.swift), but only as a short-lived probe: no session-lifecycle code exists to reuse. Status: session_state_changed is OPT-IN via CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1 (not on by default). Side questions via the undocumented `side_question` control request (shape unknown, needs a recorded capture). Alternatives: documented `defer` PreToolUse flow; request_user_dialog for tool dialogs.

## Debates and fact-check corrections

Only chat-ui-paths proposes it; Conductor, T3, Zed, Paseo, Emdash and Orca all pay for SDK/ACP-class approaches (feature lag, pinned CLIs, billing exposure, plus adapter trees). Billing: support article 15036540 (Oct 7 2026) says -p/SDK/third-party apps still draw subscription limits; the May 13 metering change was paused June 15 'for now'; April 4 policy said it 'applies to all third-party harnesses'; the legal page says products using the Agent SDK should use API keys and allows the unmodified binary with the user's own login, so headless is where policy moved four times in ten months. Corrections: 230-260 MB is a parked spare's floor, not a measured chat-process cost; AoE is not a 'stop plus --resume' precedent; --bare is recommended for scripts and may become -p's default (skips OAuth, hooks, skills, MCP); plain -p runs project hooks and .mcp.json without a trust dialog; sdk-cli entrypoint sessions are hidden from terminal /resume. User question open: does Chat mode REPLACE the terminal in daily use (then needs parity) or is it a convenience view (then I-05 + I-09 may suffice)? Defer until I-05 proves use.

## Design in Loom


FACTS FROM THE CODE (what makes it cheaper or dearer than the idea text says)
- Run-scope pipes already exist. RunScope.Stdio has `.descriptors(input:output:error:)` (Sources/LoomCore/RunScope.swift ~l.355-437) and loom-run-host supports SPAWN_STDIO (Sources/loom-run-host/main.c l.31, 81). It is used by LaunchEnvironment.swift:397 (the environment-capture helper) and tested in Tests/LoomCoreTests/RunScopeTests.swift. So a pipe child can live in the same fresh coalition and be stopped and verified like a PTY child. The research note's "no session-lifecycle code exists" is true for the stream-json client but not for the process-ownership half.
- But ProcessSupervisor.launch (Sources/LoomCore/ProcessSupervisor.swift l.282-450) is PTY-shaped end to end: rows/columns, spawnInScope returns a PTYProcess, Runtime.terminal is a TerminalEndpoint, ManagedSessionLaunch carries a TerminalEndpoint, and SessionRuntime.register (l.687-692) wraps it. The only stop-path use of the endpoint is `runtime.terminal.finish()` (ProcessSupervisor+Stop.swift:223). A small transport protocol (pid, finish(), exitStatus) over {PTY endpoint, pipe endpoint} is the minimum supervisor change; everything else (ledger, scope release, stop report, catalog finishRun, Quit) is already transport-agnostic.
- "Exactly one process owns a session id" is already enforced: launch refuses `conversationAlreadyRunning(provider:conversationID:)` for a second live run on the same provider conversation id (ProcessSupervisor.swift ~l.292-300). Mode switch = ProcessSupervisor.stop (verified) then resume in the other transport; ProviderResume/`--resume` already exists. The resume path also restores effort from the transcript (ClaudeTranscriptEffort).
- Status can stay hook-driven. ProviderLaunchProfile.claudeSettings (l.~170-200) injects per-session --settings hooks (SessionStart, UserPromptSubmit, Stop, StopFailure, Notification, PermissionRequest, SessionEnd, SubagentStart/Stop) and the loom-hook env (LOOM_HOOK_SOCKET/TOKEN, LOOM_MANAGED_RUN_ID). If hooks fire in `-p` (documented: plain -p runs settings hooks), ClaudeSessionAdapter and ClaudeHookStateTracker work unchanged, Needs approval/Waiting/Finished/Failed and the subagent ledger stay one code path, and session_state_changed (opt-in via CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1) is only a cross-check, not the authority. That is the biggest design simplification and it removes the "status from an opt-in event" fragility. Unknown to verify: ClaudeRegistryReader reads <config>/sessions/<pid>.json (ClaudeRegistry.swift l.66); whether a -p process writes it is unverified, and the hook-silence watchdog (ClaudeSessionAdapter.armSilenceWatchdog) keys off the registry saying busy, so an absent file must read as "unavailable", not as a fault.
- Existing wire code is a probe only: ClaudePlanLimitsFetcher (ClaudePlanLimits.swift) uses Foundation Process, not the run scope, one request, 4 MiB output cap, 1 MiB line cap, blocking poll() loop on a detached task. It deliberately passes --settings {"disableAllHooks":true} --strict-mcp-config --no-session-persistence, i.e. it already learned that plain -p runs user hooks and MCP (seen on 2.1.293). It is a framing/parsing precedent (PlanLimitsWire) but its blocking poll loop must NOT be copied; a resident child needs a DispatchSourceRead like EventDrivenPTYProcess. Note the same plain-`-p` exposure applies to it: if -p ever defaults to --bare (headless.md), both the usage chip's plan windows and any chat child lose OAuth.

LIGHTEST VERSION THAT STILL IS "CHAT MODE" (v1 scope)
1. New LoomCore group `ClaudeChat` (no UI imports, off MainActor): `StreamJSONFraming` (NDJSON, 1 MiB line cap, tolerant: unknown `type`/`subtype` becomes `.unknown(raw prefix)` and is counted, never fatal), `ChatEvent` (assistant text blocks, tool_use, tool_result, can_use_tool request, control_response, system/init with capabilities + claude_code_version, result with error category), `ChatSessionProcess` (spawn through RunScope `.descriptors`, pipe read via DispatchSourceRead, bounded write queue like TerminalInputQueue, SIGINT/`interrupt` for stop-turn, close stdin then verified stop for exit).
2. Supervisor: add the transport protocol above and a `launchPiped` that shares the pre-spawn checks (markers, deletion fence, one-owner check, ledger/scope registration) by extracting them from `launch`. Do not copy 170 lines; factor.
3. Catalog: `sessions.mode` ('terminal' default | 'chat') added on open without a version bump, exactly as ensureActivityColumn/ensureOriginColumns do, so 0.4.x can still open the catalog. Mode only changes on a verified stop.
4. Render model: reuse the shape of SubagentTranscriptEntry/Model (last 400 entries, strings clipped at 4 KiB, one batch = one update, coalesced to at most 5 updates/s, same Feed pattern). Start WITHOUT --include-partial-messages: message-level rendering, no per-token deltas. This removes the biggest CPU/redraw risk and a large share of the parser; token streaming is a later opt-in that is coalesced and dropped while hidden.
5. Approvals: PermissionRequest hook already reaches Loom (status). The decision itself needs `--permission-prompts host` plus the can_use_tool control_request answered by a user click on an approval card; the SDK-internal `--permission-prompt-tool stdio` value is the fragile part and is exactly what the spike must pin down (documented fallbacks: MCP permission tool in Loom's plugin dir, or `defer`). Never auto-allow; deny on timeout/disconnect.
6. Triggers (all event-driven): pipe readability, process exit via the run host's EXITED frame, user send, hook frames, FSEvents already watching projects/ for usage. No timers, nothing drawn when the chat view or window is hidden (keep the parsed entries, drop deltas).
7. Idle: a chat child is a full claude process exactly like the TUI process Loom already keeps resident under D-38 (no idle stop). So the idle-memory story is the same as today; the PTY terminal buffer is the only thing saved. Optional stop-after-result and `--resume` on next send is a user decision (it conflicts with D-38 and costs a cold start per message); default off.
8. Deletion and usage need nothing new for a plain chat session (same JSONL under projects/, ClaudeDataInventory plans it; UsageTranscriptWatcher sees the writes). A fork-based side chat (separate idea) would need its copies added to the inventory and the Loom-owned cleanup.
9. Safety: flags come from `claude --help` detection (ProviderCapabilities pattern) and missing ones are reported through reportCompatibility/journal `cli_compat_warning` instead of pinning; init `capabilities` is stored in the journal summary (version + capability names, no content); chat sessions refuse to open for a folder the user has not added as a project, because plain -p skips the workspace-trust dialog (headless.md).

WHAT WOULD MAKE IT A PRINCIPLE VIOLATION AND THE AVOIDANCE
- Resource: per-token stream_event churn redrawing a SwiftUI list; avoid by message-level v1 and coalescing. Unbounded transcript in memory; avoid by the 400-entry/4 KiB model. A second resident process per mode switch; avoid by one-owner rule plus verified stop.
- Accurate status: deriving Working/Needs approval from the new stream would fork the state machine; avoid by keeping hooks as authority. A write that is not verified delivered (user message sent while the child is dead) must not show as sent; use --replay-user-messages as the delivery receipt (a message is "sent" only when echoed back), otherwise show failed.
- CLI resilience: a hand-rolled client over a protocol typed only in the SDK .d.ts is exactly where drift bites (about 26 CLI releases a month). Avoid by: unknown-passthrough decoding, init capability detection, a recorded-fixture suite per CLI version in loom-fake-provider, and a kill switch that falls back to the terminal for the same session.
- Billing/policy: headless is the surface policy moved on four times; keep PTY default, per-session explicit mode, no --bare, no token handling, surface billing_error/oauth/authentication categories as a visible notice, one Settings switch that disables Chat mode globally.
- Contract: "the real CLI/terminal experience is preserved" (LOOM-PRODUCT-CONTRACT.md §3 Core experience) and the user's "no custom chat UI replacing the terminal" rule are changed only for sessions that explicitly choose Chat mode. That is a user-authority decision, not mine.
- Ownership: do not spawn through Foundation Process like the plan-limits probe; chat children must be run-scope members.

COST (honest, for this codebase)
- Wire client + process + fake-provider fixtures + tests: M (about 1.5-2k lines).
- Supervisor transport factoring, catalog mode column, SessionRuntime/ConversationController wiring for a non-terminal run (ConversationController is built around TerminalSurface creation/reconcile, 474 lines), mode-switch flow with verified stop and failure states: M-L.
- Chat UI: transcript with markdown, code and diffs, tool cards, approval and AskUserQuestion cards, composer with multi-line, image paste, @-file and slash-command completion, model/effort/permission-mode controls, stop-turn, ended-state: L, and the long tail is open-ended because TUI dialog commands (/permissions, /config, /mcp, /agents) and agent teams do not exist in headless.
- Total XL confirmed. A "convenience view" scope (text, tools, approve/deny, stop, switch) is L; "daily driver with parity" is XL and not boundable.


## Where it shows


Detail pane gets a third content branch beside terminal and ended screen (DetailContent in Sources/LoomCatalogUI/DetailView.swift l.228-292 already switches among dev terminal, subagent panel, live terminal, ended screen): when row.mode == chat and a chat run is live or the session is stopped, show ChatView in place of TerminalHost, under the same RequestList/SessionIssueNotice. Header is unchanged (state pill, project+branch chip, Stop); add a small segmented 'Terminal | Chat' control or a header action 'Switch to Terminal' that runs the verified stop-and-resume with a short 'Switching…' busy state (ConversationBusy-style) and keeps the draft. New-session menu gets 'New Claude Session' (terminal, default) and 'New Chat Session' (explicit, labelled as experimental until the spike passes). Sidebar cards are unchanged apart from a tiny mode glyph beside the provider icon. Chat view: bubble-free column in the terminal's background, assistant text, collapsed tool cards (name + main argument, same fields SubagentTranscriptParser already extracts), an inline approval card with Allow/Deny that also drives the existing needs-approval indicator, a composer pinned at the bottom (Return sends, Shift+Return newline, Esc stops the turn). The subagent panel and its click-through keep working (hooks-fed ledger). No right panel in v1; a side-chat panel is the separate idea that would plug in later.


## Principle check


Resources: RISK, bounded by design. A chat child is the same claude process the PTY mode keeps resident under D-38, so memory is roughly equal (the 230-260 MB figure is a parked spare's floor, unmeasured for a live session either way); the saving is the terminal buffer, the cost is a Swift render model. Pass if v1 is message-level, coalesced to 5 updates/s, entries capped, nothing drawn when hidden, no polling (pipe readability, exit frame, hooks, FSEvents). Not measured: stream-json child CPU while a turn runs with partial messages; must clear the 40%-of-a-core gate in the spike.
Predictability: PASS if the mode is explicit per session, PTY is default and fallback, and a switch is a visible verified stop plus resume.
Accurate status: PASS only if hooks stay the authority and a message is 'sent' only on --replay-user-messages echo; RISK if status is derived from the opt-in session_state_changed.
Fluency: RISK. Cold resume per switch and per optional stop-after-result costs seconds; headless has no TUI dialogs or agent teams, which this user uses heavily (multi-agent workflows), so chat mode would be a worse tool for those sessions.
Modularity: PASS with care. New ClaudeChat group in LoomCore with no UI imports; the supervisor needs a transport abstraction, which touches the central, well-tested ProcessSupervisor and is the main regression surface.
CLI-update resilience: RISK, the central risk. The protocol is typed only in SDK typings and moves with about 26 CLI releases a month; --permission-prompt-tool stdio is SDK-internal; -p may become --bare by default; session_state_changed is opt-in. Mitigated by capability detection, passthrough decoding, recorded fixtures and the terminal fallback, never by pinning.
Ownership: PASS. Pipes through the existing run host and coalition, one-owner check already in launch, verified stop; plain Foundation Process (as the plan-limits probe does) would NOT pass and must not be used.
User authority: PASS if every approval is a user click on a card, no auto-allow, deny on disconnect, and no cross-session action is introduced. New risk: plain -p skips the trust dialog and runs project hooks and .mcp.json, so restrict to folders the user added as projects.
Billing/policy (outside the list but decisive): RISK. Support article 15036540 still allows subscription use, but the May 13 metering of claude -p was only paused and the Apr 4 policy covered all third-party harnesses; unmodified binary with the user's own login is permitted. Needs a kill switch and a re-read before releases.


## Value for the user (3/5)

It is the only path to the chat-centred, typed, tool-card and side-question UI the user asked about, and Loom's ownership layer makes it safer here than in Conductor/T3/Zed. But the user's real workflow (many sessions, subagents and multi-agent workflows, skills, MCP, TUI dialogs) is best served today by the PTY, most of the near-term wins (readable ended sessions, side chat, approvals in the panel) can come from lighter ideas, and the value jumps to 4-5 only if the user decides Chat mode replaces the terminal, which also makes the unbounded parity work and the billing exposure the price.

## Experiments before building

- S-07a Recorded capture (isolated CLAUDE_CONFIG_DIR, loom-probe style, fake or throwaway project, never the real ~/.claude): run `claude -p --input-format stream-json --output-format stream-json --verbose --replay-user-messages --permission-prompts host --settings <Loom's per-session hooks JSON> --session-id <uuid>` inside a RunScope with `.descriptors`, with and without CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1 and --include-partial-messages. Record: system/init (capabilities, claude_code_version, slash_commands, plugin/skill list), the exact can_use_tool request/response envelope and AskUserQuestion/ExitPlanMode path, whether loom-hook events fire with the right LOOM_MANAGED_RUN_ID, whether <config>/sessions/<pid>.json appears, the entrypoint stamped in the JSONL, line counts and bytes per turn. Decides: whether hooks stay the status authority (go) or the stream must be (no-go unless the opt-in event is trustworthy), and whether approvals work without --permission-prompt-tool stdio.
- S-07b Round trip (same sandbox): create a session in the PTY (loom-fake-provider cannot prove this, needs a real CLI in the sandbox), stop it verified, resume it in chat mode, send a turn, stop, resume in the PTY with `claude --resume`, and the reverse. Decides: lossless history, no duplicate/forked session id, whether the programmatic entrypoint hides it from the terminal /resume picker and whether that matters (Loom resumes by id), and that `conversationAlreadyRunning` plus verified stop leave exactly one owner. A failure here kills the 'mode switch = stop plus --resume' premise.
- S-07c Resource and latency: RSS and CPU of a resident chat child through a 20-turn session with and without partial messages, versus the TUI child of the same session, idle CPU at the prompt, time from resume spawn to first event (cold start), under the 40%-of-a-core gate. Decides message-level vs token streaming and whether stop-after-result is tolerable.
- S-07d Parity probe: do the user's real kinds of setup load in -p (project CLAUDE.md, skills, plugin-dir `loom:open-session`, MCP servers, subagents with forwarded text, background tasks)? Run with a synthetic project containing each. Decides whether Chat mode can be anything more than a convenience view for this user.
- S-07e Side question capture (optional, belongs to the side-chat idea): record the side_question control_request/response shape and whether init advertises it. Not needed for Chat mode v1.

## Questions for the user

- Is Chat mode meant to REPLACE the terminal for your daily work (then it needs parity with skills, MCP, hooks, plugins, slash-command menus and you accept losing TUI-only dialogs and agent teams in those sessions), or is it a convenience view you switch into for reading and quick replies (then I-05 plus a side-chat idea may be enough and this one should wait)?
- May the product contract's 'real CLI/terminal is preserved' rule be amended to 'preserved by default; Chat mode is an explicit per-session alternative'?
- Billing tolerance: if Anthropic revives metering for `claude -p`/SDK-class use, should Chat mode be switched off automatically (kill switch), stay on at your cost, or be removed?
- Should a chat session stop itself after a finished turn and resume on the next message (saves memory, costs a cold start each time and reverses D-38's 'never stop for inactivity'), or stay resident like terminal sessions do today?
- Is message-level rendering (no token streaming) acceptable for the first version?
- Should Chat mode be limited to folders already added as projects (needed because plain -p skips the workspace-trust dialog)?
