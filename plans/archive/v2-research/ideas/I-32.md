# I-32: Worktree-backed sessions (parallel agents on one repo)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Worktree-backed sessions (parallel agents on one repo)** · verdict **adopt-light** · cost M · value 3/5 · proposed by 10 reports: [herdr](../products/herdr.md), [conductor](../products/conductor.md), [codex-app](../products/codex-app.md), [superset](../products/superset.md), [paseo](../products/paseo.md), [warp](../products/warp.md), [cursor](../products/cursor.md), [emdash](../products/emdash.md), [vibe-kanban](../products/vibe-kanban.md), [supacode](../products/supacode.md).

> Build a thin Loom-owned "New session in worktree" (one plain `git worktree add -b <ticket key>`, session opens with cwd = worktree, glyph on the card) plus a dry-run-guarded "Remove worktree", reusing the catalog's per-session working_directory and the existing CP4-G worktree check; do not delegate to `claude -w`, and skip the pool, registry, storage list, setup scripts and port ranges for now.

## What the user gets

'New session in worktree' for a project or ticket: branch named from the ticket key, the session opens there with worktree provenance on the card, environment files copied, and cleanup is a verified action, so two agents on the same repo stop colliding.

## Mechanisms found in the research

Lightest, documented: delegate to Claude's own `claude --worktree <name>` and .worktreeinclude (plus WorktreeCreate/WorktreeRemove hooks, keep/remove prompt, cleanup sweep); Loom launches, labels and reaps; add env LOOM_SESSION_ID and a reserved port range (Conductor: 10 ports) for the user's own scripts. Heavier: a small Loom module around plain `git worktree add --no-track -b <ticket-branch>` (Emdash final design: inspect, resolve base, add, verify; never fetch if the base resolves locally; APFS-clone preserved ignored files in a background step), a registry of what Loom created, removal only through a verified dry-run delete that refuses dirty or unpushed work (or snapshots to a branch/patch), a storage list with keep-N cleanup that never touches a running or pinned session, linked worktrees treated as one project by reading .git (no exec), per-project setup commands from a committed file with per-project approval showing the command. No pre-warmed pool.

## Debates and fact-check corrections

Polarising: power-user-workflows says skip a worktree manager (Desktop and `claude --worktree` already ship it; realistic parallelism is 2-3 sessions) while ten reports ask for it; HN: worktrees do not isolate ports, DBs, .env and add a layer, review is the bottleneck. Deletion is the data-loss risk (Cursor forum data-loss report; Supacode data-loss bugs on creation failure; Agent View deletes uncommitted changes and a second delete drops commits); dependency installs per worktree are slow/large (about 200 MB+); detached-HEAD default (Codex) to avoid; claude --worktree cleanup semantics must be re-verified against the installed CLI; refuse two sessions on the same branch; setup scripts execute arbitrary commands. Scope creep into a git client (Supacode: process storms, rate limits).

## Design in Loom

**Why this is lighter than it looks.** `sessions.working_directory` is already per session and separate from `sessions.project_id` (CatalogDatabase schema; `SessionRuntime.workingDirectory(projectID:)` only supplies the default). A session with project_id = the main repo's project and working_directory = a worktree path therefore gets, with no change: grouping under the parent project, a correct branch chip (`GitBranch.read` already follows a `.git` pointer file to the worktree's own HEAD), Reveal in Finder and Copy Resume Command (`SessionMenuItems`), resume in the right folder (`resumeConversation`), ticket de-duplication (`SessionCatalog.session(projectID:ticket:)`), and usage/deletion (both walk the config dir by session id, not by cwd: `ClaudeDataInventory`, `ClaudeUsageIndex`). No schema change.

**Decision: Loom runs git itself, not `claude --worktree`.** Facts from `claude --help` (2.1.300) and code.claude.com/docs/en/worktrees: `-w` makes `.claude/worktrees/<name>` on branch `worktree-<name>` (the branch cannot be named from the ticket key), branches from the remote default branch ("fresh"), may fetch for up to 5 s, shows its own keep/remove prompt on /exit, and moves the session's cwd itself. For Loom that means: the catalog still holds the project root, so the branch label and Reveal point at the wrong place until a new hook-cwd plumbing and a catalog write are added; two owners of the worktree lifecycle (Loom Stop kills the CLI so no exit prompt ever runs, orphans stay); and the semantics changed several times (v2.1.208 reuse, 2.1.212 resume), which is exactly the drift the principles warn about. A Loom-run `git worktree add` depends only on git, which does not drift. The cost is that Loom must copy `.worktreeinclude` files itself (below).

**Module and triggers (event-driven, no polling).**
1. New `Sources/LoomCore/WorktreeProvisioner.swift`: pure name/path planning plus an injected `Capture` (same shape as `CleanupWorktreeProtection.Capture`, production = `ProcessSupervisor.captureHelper("/usr/bin/git", ..., timeout 10-15 s)`, owned, bounded, cancelled at shutdown). Steps, only on an explicit user action: (a) inspect: project path is inside a git work tree (reuse the `.git` walk of `GitBranch`/`isLinkedWorktree`), branch name and path valid and not existing, branch not checked out elsewhere; (b) resolve base without network: `origin/HEAD` target if it resolves locally, else the main checkout's HEAD (never fetch; show the chosen base in the sheet); (c) `git worktree add --no-track -b <branch> <path> <base>` (named branch, never detached HEAD); (d) verify: `GitBranch.read(directory: path) == .named(branch)` and the path exists; (e) one-shot `.worktreeinclude` copy (below). Result is a typed outcome: created / created-with-warnings (n files not copied) / failed(stage, message). No rollback by deleting anything: on any failure after (c) Loom leaves the worktree and says so (Supacode #878 deleted a pre-existing folder when creation failed; never `rm -rf`, never `--force`).
2. `SessionRuntime.startConversation(provider:projectID:...)` gets an optional `directory:` override (validated: exists, is a linked worktree whose common git dir belongs to the project path). `ManagedSession.workingDirectory` = worktree, `projectID` = the main project. Launch profile, hooks, registry reader (`observeRegistry` takes the directory) and `--session-id` are unchanged: zero new Claude flags.
3. `.worktreeinclude` copy (Claude's documented file, same semantics: listed AND gitignored): `git ls-files -z -o --exclude-from=.worktreeinclude` then `git check-ignore -z --stdin` to keep only ignored files, copied with `copyfile(COPYFILE_CLONE)` (APFS clone) in one background step, caps on file count and bytes (for example 500 files / 50 MB), symlinks and paths escaping the repo skipped, existing targets never overwritten. This is a bounded one-shot, not a watcher. Fidelity with Claude's `**/` corner case is unverified (experiment 2).
4. Provenance: extend the branch read (`BranchCache`, already keyed per folder and refreshed at turn boundaries and activation) to also return "linked worktree" and the worktree name from the same `.git` file it already opens (no extra I/O, no exec). `SessionCardView` second row and the `SessionHeaderChip` show a small worktree glyph before the branch, tooltip with the path.
5. Removal ("Remove Worktree..." in the card context menu and the header ⋯ menu, a separate explicit action; contract §5 says worktrees are not an automatic side effect of chat deletion, and `CatalogModel+Deletion` already tells the user the worktree stays). Ownership rule without a registry: only a path that equals the working_directory of at least one catalog session, lies under the configured Loom worktree root, is a linked worktree, and has no live run in it (supervisor knows). Dry run reuses `CleanupWorktreeProtection.verdict` (uncommitted, unpushed, stash) but reports counts and file names instead of a bare "protected"; refuses on dirty or unpushed (no force in the UI; user uses git in the terminal, or commits/pushes first). Execution: `git worktree remove <path>` without `--force`, then verify the directory is gone and `<commondir>/worktrees/<name>` no longer exists (file reads). The branch is never deleted by Loom in v1 (herdr and Codex also keep it). The dialog lists the sessions that ran there and says they stay readable (ended screen, transcript) but cannot be resumed from Loom (`requireDirectory` refuses a missing folder); deleting them is the user's separate action. Note: the existing stash rule is repository-wide (stash refs are shared by all worktrees), so for removal it should be dropped or labelled, otherwise any stash blocks every removal.
6. Agent path (optional follow-up, S): `loom:open-session` (`OpenSessionInput`, `ClaudeLoomPlugin` skill text, `OpenRequestBoxContent`) gets `--worktree`; the approval box shows "in a new worktree EDDP-123 from main"; the ticket de-dup already runs first, so an agent cannot create two worktrees for one ticket; there is no agent command to remove a worktree (user authority).
7. Optional S add-on that is useful even without this idea: when Claude enters a worktree itself (EnterWorktree, doc says hook `cwd` follows it), the card keeps showing the main checkout's branch because the catalog holds the launch folder. `ClaudeHookEvent.workingDirectory` is parsed but unused; keep an in-memory observed cwd per run and feed it to `BranchCache.refresh` at turn boundaries. Not persisted.

**What is deliberately not built now:** the reserve pool (Emdash built it in Jan 2026 and removed it in Apr 2026 for stale bases and orphans), a registry table or a hard-coded directory scan (ownership comes from catalog rows plus path containment), a storage list with keep-N cleanup (Cursor's cleanup deletes worktrees it did not create; Vibe Kanban's GC removed active ones; revisit only if disk becomes a real problem at 2-3 parallel sessions), per-project setup/run/archive scripts (arbitrary command execution; Cursor gates it behind workspace trust; if wanted later it needs per-project approval showing the literal command, run in a visible Loom-owned session, never hidden), a reserved port range (`LOOM_PORT_BASE`-style env is a one-line addition to `ProviderLaunchProfile.claude` but only helps scripts the user parameterises; add when asked), grouping of manually made linked worktrees by reading `.git` (today's workaround: Add Project on the worktree folder), diff/PR/merge UI (git-client creep).

**Bounds.** Git execs: only on user action, one owned helper at a time, 10-15 s timeout, bounded output (`LaunchEnvironment.runHelper`). Copy: caps above. No git run on list load, selection or idle. Sidebar cost: none beyond the existing branch read.

## Where it shows

Entry points: (1) project header "+" gets a context menu / long press with "New Session in Worktree..." (the plain click still starts a normal session at once, D-10 stays); the File menu and palette-less app get "New Session in Worktree..." (Shift+Cmd+N is taken by Codex, so a different key, decided later). (2) A small sheet (420 pt like RenameSheet): one field "Ticket or branch name" (prefilled from a ticket key if the sidebar search holds one), a read-only line "Branch EDDP-123 from origin/main (not fetched)", a line "Will copy N files from .worktreeinclude" when the file exists, Create (default action). Errors inline in the sheet; no second confirmation. While git runs the sheet shows a spinner (3-14 s possible on big repos, Emdash baseline) and the session opens in the project's group when done. (3) The card's second row shows a worktree glyph before the branch (same monochrome symbol class, no new colour); the header chip does the same, tooltip = path. (4) Remove: "Remove Worktree..." in the card and header menus opens a sheet in the style of `DeleteConversationSheet`: path, branch, which sessions ran there, "Clean: nothing uncommitted, all commits pushed" or the refusal with counts and the first file names, Remove (disabled when refused). Result banner states what is verified ("Worktree removed; branch EDDP-123 kept").

## Principle check

Resources: pass. Git only on explicit actions through the owned, timed `captureHelper`; no watchers, no polling, no pool; badge reads the file the branch read already opens. Risk: the copy step on a huge ignored tree, bounded by caps; dependency installs per worktree (~200 MB each in one Codex user's report, single post) are the user's, Loom adds none. Predictable: pass if the base is shown and never fetched, a name/path collision is refused (no silent reuse, unlike Claude's reopen-by-name), and creation never rolls back by deleting. Accurate status: pass only if 'created' means git exit 0 plus `GitBranch.read == named(branch)`, and 'removed' means exit 0 plus the directory and the admin folder gone; partial states (created with copy warnings, created but launch failed) are named, not hidden. Fluency: pass for create (one field, Enter), the only confirmation is the destructive removal. Modularity: pass; one new core file with an injected capture (testable on real temp repos like `CleanupCoordinatorTests`), one runtime parameter, two small UI files; no change to the hook state machine or schema. CLI-update resilience: pass, and the main reason not to use `claude -w`: no new Claude flag, nothing to pin; the only Claude coupling is `.worktreeinclude`, a documented file. Ownership: pass with the rule 'only a path a Loom session ran in, under Loom's root, with no live run'; weak point is a worktree whose last session was deleted (not removable from Loom). User authority: pass; agents can only ask (approval box) to open a session in a worktree and cannot remove anything. Violations to avoid: becoming a git client (no fetch, no status polling, no PR/merge), silent GC, `--force`, hidden setup commands, a second lifecycle owner next to Claude's sweep (worktrees Loom creates carry no Claude marker, so Claude's sweep keeps them). Standing decisions: D-34 and the 'terminal is the real CLI' contract rule are untouched; contract §5/§12 'worktrees are not a side effect of chat deletion' is respected by making removal separate; D-26 cleanup already protects dirty/unpushed worktrees.

## Value for the user (3/5)

It removes a real ritual for the EDDP ticket-per-session flow (git worktree add, copy .env, Add Project, later clean up) and keeps the user inside Loom, which a "main app" needs, and Loom's existing per-session cwd, ticket de-dup and worktree check make it cheap. But it is not daily: the field data says realistic interactive parallelism is 2-3 sessions across projects, review is the bottleneck, worktrees do not isolate ports/DBs/.env state, Claude Desktop and `claude -w` already cover the basic case, and the same-repo collision frequency for this user is unknown, so 3 rather than 4.

## Experiments before building

- E1 trust dialog and prompt delivery (isolated CLAUDE_CONFIG_DIR, temp repo, real Claude, a few short turns): start `claude --session-id <uuid> --settings <loom hooks> -- "msg"` with cwd = (a) sibling folder worktree, (b) <repo>/.claude/worktrees/<key>, (c) a folder under Loom's data root. Decides the default worktree root and whether the first message survives a workspace-trust dialog (if every new path shows the dialog, prefer (b) or tell the user once). Also record the hook `cwd` and the transcript's encoded folder.
- E2 .worktreeinclude fidelity: on a fixture repo with .env, config/secrets.json, a gitignored build directory and a `**/` pattern, compare `git ls-files -z -o --exclude-from=.worktreeinclude` + `git check-ignore --stdin` against what `claude -w` copies; decides reimplement-as-is versus a documented deviation, and the file/byte caps.
- E3 resume and removal edge cases: `claude --resume <id>` from the worktree folder (Loom's way), the same after `git worktree remove` (expected: Loom refuses via requireDirectory; check what Claude itself does and whether a transcript from a removed folder still reads in the ended screen and the usage index), and `git rev-list --count HEAD --branches --not --remotes` on a never-pushed zero-commit ticket branch (expected 0, so a clean new worktree is removable).
- E4 creation time on the user's largest work repo (the user runs one `git worktree add --no-track -b` and reports seconds): decides whether the foreground spinner is enough or creation must become a visible background step like Emdash's Activity badge.

## Questions for the user

- How often do two sessions really need the same repo at once, and is the pain file collisions or shared ports/DB/docker state (worktrees fix only the first)? This decides value 3 versus 4 and whether the port env is worth adding.
- Branch convention: the bare ticket key (EDDP-123), or key plus slug, and which base (origin/main, develop, current HEAD)? Loom would show the base and never fetch.
- Where may worktrees live: <repo>/.claude/worktrees/<key> (Claude's own layout, needs a gitignore entry, trust likely inherited), a sibling folder, or under Loom's data folder? E1 informs this.
- Is guarded removal wanted in the first slice, or is `git worktree remove` in the terminal (git itself refuses dirty trees) enough at first? May Loom ever delete the branch (only when merged), or never?
- Should an agent be able to ask for a worktree through `loom:open-session --worktree` (approval box as today), and should the stash rule block removal even though stashes are repo-wide?
- Setup commands (npm/mvn install, docker) per worktree: skip and let the first prompt or Claude do it, or build a per-project approved command later?
