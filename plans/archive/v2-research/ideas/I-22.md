# I-22: Claude supervisor integration: 'Background' visibility lane, then optional 'Run detached'

Card from the [Loom v2 idea catalog](../IDEAS.md). **Claude supervisor integration: 'Background' visibility lane, then optional 'Run detached'** · verdict **later** · cost XL · value 2/5 · proposed by 3 reports: [claude-official](../products/claude-official.md), [persistence-remote-orchestration](../products/persistence-remote-orchestration.md), [supacode](../products/supacode.md).

> Do not build now: the read-only lane is low-value for someone whose sessions live in Loom and carries an unmeasured side effect (`claude agents --json` may start Anthropic's supervisor outside Loom's scope), and 'Run detached' breaks Loom's hook-status channel across a Quit and contradicts D-40, while a small resume-interrupted feature gives most of the benefit.

## What the user gets

Sessions started elsewhere (terminal, Desktop, agent view) become visible in Loom's list and openable; later, an explicit per-session 'Run detached' so a long turn survives a Loom Quit and costs nothing when idle, using Anthropic's supervisor instead of a Loom daemon.

## Mechanisms found in the research

1) [Documented 'supported way to read session state'] Visibility only: `claude agents --json --all` on window focus, after a hook event or manual refresh (never on a timer; the doc itself says poll, there is no push); fields state working|blocked|done|failed|stopped, status busy|waiting|idle, waitingFor enum, kind interactive|background; open with `claude attach <id>` inside a Loom PTY; Loom stops only what Loom launched; dedupe Loom's own interactive rows by sessionId/pid. 2) Later `claude --bg --name ...` as a third, explicitly labelled process class hosted by the supervisor (PPID 1; idle unattached sessions stopped after about an hour; `claude daemon status|logs|stop`; isolated worktree under .claude/worktrees when dispatched from agent view or --bg, which changes cwd/branch; a machine restart stops background sessions). 3) If ever built, Supacode's two-button Quit dialog (Quit / Quit and Terminate Sessions) with an orphan sweep.

## Debates and fact-check corrections

The biggest philosophical decision in the research. Conflicts with 'Quit stops all sessions', process ownership and 'no polling'. Loom currently disables the supervisor with CLAUDE_CODE_DISABLE_AGENT_VIEW=1 (Sources/LoomCore/ProviderLaunchProfile.swift:147), and the env-vars page says that variable disables the on-demand supervisor itself; supervisor state is per CLAUDE_CONFIG_DIR. Anthropic's own daemon bugs are open: #87891 (64 leaked processes, 7.1 GB after six weeks), #65051, #88307 (symlinked settings.json deleted), #98208 (TCC re-prompts), #66402. persistence-remote-orchestration: run Option B only as a clearly labelled spike (hooks, env identity via --settings env, session ids, run-scope capture must all behave) and keep a Loom-owned PTY host (Option C) skipped. Agent view's Delete discards the worktree including uncommitted changes (second delete drops commits). agent_needs_input/agent_completed hooks fire only while agent view is open in a terminal. Haiku-class row summaries are extra billed requests. Agent view criticisms 'no project filter / no branch status' are stale (--cwd, PR/CI labels exist).

## Design in Loom

SPLIT THE IDEA. The three mechanisms have very different costs.

PART 1, 'Elsewhere' lane (read-only visibility). Lightest version, if the user ever wants it:
- Source. Prefer the sessions folder Loom already reads over a CLI spawn. `ClaudeRegistryReader` (Sources/LoomCore/ClaudeRegistry.swift) already opens `<config>/sessions/<pid>.json` with O_NOFOLLOW, uid/mode checks and a 16 KiB cap, and `ClaudeDataInventory.liveSession` (line ~376) already scans `sessions/*.json`. A new sibling reader, `ClaudeExternalSessions`, would list that folder (bounded count and bytes), keep only files whose pid is alive with matching `procStart`, and drop Loom's own rows by leader pid or `sessionId` against `ProcessSupervisor` runs and `ManagedSession.providerConversationID`. No process is started and the supervisor is never touched. Cost: it is the 'private CLI capability' the registry file already is, so it needs the same drift handling (unknown kind or status becomes a visible but inert row; `ClaudeRegistryDiagnostics.noteUnknownStatus` pattern). Note `decode` today demands `kind == "interactive"`, so background rows need a new decode path.
- Documented alternative: `claude agents --json --all` (docs call it 'the supported way to read session state'). Loom's `ProviderToolchain.capture` (Sources/LoomCore/ProviderToolchain.swift:175) already runs `claude --help` in a bounded way, so a bounded capture of `agents --json` has a pattern. But it is a Node CLI start (hundreds of ms and a CPU burst), and whether it starts the supervisor is unknown (docs: the supervisor starts 'the first time you background a session or open agent view'; env page says CLAUDE_CODE_DISABLE_AGENT_VIEW also disables the 'on-demand supervisor'). Loom must keep passing DISABLE_AGENT_VIEW=1 for this call (ProviderLaunchProfile.swift:147 sets it only for hosted sessions; the app-side capture would have to set it too) and the spike must show the call still works with it and spawns nothing.
- Trigger (events only): window activation (the hook `CatalogModel.setWindowActive`, CatalogModel.swift:1022, where branch refresh already runs), a manual Refresh button, and the lane being expanded. No timer. A view-model `ElsewhereModel` in LoomCatalogUI holds at most ~50 rows, nothing observed while the lane is collapsed or the window hidden.
- What it can honestly do: list `cwd` (mapped to a Loom project by path), name, state/status, `waitingFor`, age. Open: ONLY a `kind: background` row can be opened with `claude attach <id>`; a plain interactive session running in another terminal cannot be attached (it is tied to that terminal), and `claude --resume <id>` on a live conversation would create a second writer on one transcript, so interactive rows stay read-only ('Copy session id', 'Reveal cwd'). That removes most of the 'openable' promise.
- Never a Stop on these rows. Contract §6: 'user sessions outside Loom are not touched'.

PART 2, 'Run detached' (explicit per-session supervisor hosting). Requires all of:
- A third process class beside 'Loom run in a scope' and 'ended'. New `RunKind.detached` in the catalog `runs` table (schema bump; note v3 No-downgrade policy DP-CP4-4), `ProcessSupervisor` registry entry that is NOT a scope member, a `DetachedSessionController` in LoomCore that shells `claude --bg --name`, `claude attach|stop|logs <id>` and verifies by reading `agents --json` after each action.
- Env. Loom sets CLAUDE_CODE_DISABLE_AGENT_VIEW=1 on every hosted Claude so that `<-` on an empty prompt cannot background a session out of the scope (agent-view doc: `leftArrowOpensAgents` is on by default). The detached class must be launched by Loom's own process (not from inside a hosted session) with the variable unset, and every normal session keeps it set.
- Status channel breaks. Hook sockets and tokens are per app run: `SessionRuntime.ensureHooks` (SessionRuntime+Claude.swift:9-49) names `h-<8 hex of ownershipRunID>.sock` and mints a fresh token per run. A detached session keeps the settings it was spawned with, so after Loom quits and relaunches its hooks point at a dead socket for good, and `claude attach` runs the client in Loom's PTY while the actual `claude` process is under the supervisor with the supervisor's environment (open issues #98872, #102949), not Loom's `LOOM_*` variables. `ClaudeRegistryReader` keys on the leader pid (`sessions/<leader.pid>.json`), and the leader would be the attach client, so the existing tracker identity (pid + procStart + startedAt + sessionId) does not apply. Status for the detached class would have to come from `agents --json`, which is a poll: the only documented source. That contradicts 'no polling' and 'accurate status' unless limited to focus/manual refresh (stale between), which is a visibly weaker Working indicator.
- Quit. Add Supacode's two-button dialog (Quit / Quit and Terminate Sessions) in `AppDelegate.applicationShouldTerminate` and `AppShutdownCoordinator`, amend contract §6 ('no running work started and owned by Loom remains') and D-40 ('Claude's own background sessions ... stay off'), and add an orphan sweep for detached sessions Loom launched.
- Deletion. `ClaudeDataInventory.liveSession` correctly sees a detached session as live, so the deletion flow's 'stopping' step (`stopConversation`, requires report.succeeded) needs a detached branch that calls `claude stop` and verifies; and the delete dry run must warn about worktrees (agent view Delete discards a worktree including uncommitted changes; second delete drops commits).
- cwd semantics. Dispatch through `--bg` moves the session into `.claude/worktrees/...`, changing the card's cwd and branch chip (`GitBranch`/`BranchCache` read by folder). `/bg` or `<-` skip isolation but are blocked by our env var and have the open new-session-id bug (#87984).
- Run-scope capture of the supervisor is unknown: started from a hosted session it may be killed by Stop (taking every detached session with it) or escape unowned.

CHEAPER SUBSTITUTE for the same user need (survive a Quit): 'N interrupted' marker plus one-click Resume interrupted on the existing resume path (`ProviderResumePlanner.claude`, ProviderResume.swift), power assertion while Working (persistence note option A, cost S). It does not keep an in-flight turn alive, which is the only thing Part 2 adds.

Bounds if ever built: row cap ~50, 16 KiB per file, one capture in flight with a 5 s timeout, no capture while the window is hidden, output parse that never decodes content fields, unknown values shown but inert.

## Where it shows

Part 1: a collapsed 'Elsewhere (N)' section at the foot of the activity list, below the day sections in SidebarView's ActivityList (SidebarView.swift:171). Rows are single-line and visibly different from owned cards: no status dot animation, a small 'external' glyph, name, project stripe if cwd matches a Loom project, 'blocked: permission prompt' text from `waitingFor`, relative age. Context menu: Copy session id, Reveal cwd; for kind background also 'Open in Loom' (claude attach in a PTY). No Stop, no Delete. A refresh affordance in the section header and activation-time refresh; a 'last checked 2 min ago' label because the data is not live.
Part 2 (not recommended now): a card marker 'Detached, hosted by Claude' with its own pill colour, a header action 'Run detached' beside Stop, and the two-button Quit dialog.

## Principle check

Resources: Part 1 pass if sessions-folder reader with focus/manual triggers (a few small file reads); risk if `agents --json` is used (Node start per call) or polled. Part 2 risk: supervisor plus a PTY host and CLI process per detached session, plus Anthropic's open leaks (#87891: 64 processes, 7.1 GB). Predictability: risk (Part 2 changes what Quit and Stop mean for one class). Accurate status: Part 1 pass if labelled 'last checked'; Part 2 RISK/likely fail: hooks die after a Loom relaunch, the tracker cannot key on the attach client's pid, and `done` collapses idle and finished in `agents --json` ('Idle' is not a JSON state); `agent_needs_input/agent_completed` hooks fire only while agent view is open. Fluency: pass for Part 1, neutral for Part 2. Modularity: Part 1 pass (one reader plus one model); Part 2 touches ProcessSupervisor, catalog schema, deletion, Quit, hooks, launch profile. CLI-update resilience: risk. Documented `agents --json` is the better surface but is a research preview ('interface may change') and `claude agents --help` shows flags still moving; the sessions-folder route is private and already carries drift handling. Process ownership: Part 2 is the direct conflict; acceptable only as a labelled third class. User authority: pass for read-only; for detached, `--bg` sessions keep running with the user's credentials and a possible bypass-permissions mode while Loom is closed, so it must be an explicit per-session action. Principle violations to avoid: (1) a timer-based poll; (2) starting the supervisor as a side effect of listing; (3) a Stop button that kills things Loom did not start; (4) a silent change of the Quit contract; (5) showing the `Working` indicator for a detached session from stale data.

## Value for the user (2/5)

Lane: the user wants Loom to be the main development app, so sessions started elsewhere shrink over time, interactive external sessions are not openable, and Loom already surfaces what matters for its own sessions. Detached: the only unique gain is a turn surviving a Loom Quit (the idle-costs-nothing goal is already met by the ended screen plus resume; sleep does not stop Loom sessions either), and a machine restart still ends the supervisor sessions. A Quit confirmation already exists for working sessions (D-45). Value becomes 4 only if the user routinely runs `claude --bg`/agent view or wants overnight unattended runs, which this brief does not show. Cost-benefit is poor: roughly XL plus a contract change for a narrow gain.

## Experiments before building

- E1 (decides the lane, ~1 h, isolated CLAUDE_CONFIG_DIR, no real ~/.claude): run `claude agents --json --all` with and without CLAUDE_CODE_DISABLE_AGENT_VIEW=1 and check `claude daemon status`, `ps` and `~/<tmp-config>/daemon*` before and after. Decision: if listing starts a supervisor or fails with the variable set, the lane must use the sessions-folder reader only; if it is clean, `agents --json` is a safe documented source.
- E2 (decides the lane's value, no code): with the user's Claude Desktop and one plain terminal session running, list `<config>/sessions/*.json` file names and `kind` values only (not content) to see whether Desktop-started sessions appear and which `kind` values exist. Decision: if Desktop and `--bg` sessions are absent or look different, the lane covers only terminal sessions the user can already see.
- E3 (decides Part 2, throwaway config): `claude --bg` started from (a) the Loom app process and (b) a process inside a LoomRunHost scope; check whether the supervisor and workers land in Loom's coalition (killed by Stop) or escape, and what the supervisor's PPID and environment are.
- E4 (decides hooks): a `--bg` session started with the same `--settings` JSON Loom uses, with LOOM_* values only in a settings `env` block; confirm hooks arrive, then quit and relaunch the fake Loom (new socket and token) and confirm what the session does (expected: hooks fail silently). Also check whether `claude attach` in a PTY gets a `sessions/<pid>.json` for the attach client (expected: no), which breaks `ClaudeRegistryReader`.
- E5 (decides Quit value): measure how often the user quits Loom (or Loom Dev updates) during a Working turn; if rare, skip Part 2 permanently.

## Questions for the user

- Do you still run Claude sessions outside Loom (terminal, Desktop, `claude agents`/`--bg`) in daily work, and would you want to see them in Loom? If not, skip the lane.
- Is surviving a Loom Quit during a long turn worth changing the Quit contract (§6) and reversing D-40's 'Claude's own background sessions stay off' for an opt-in class, or is 'Resume interrupted' enough?
- If a detached class exists, should its status be allowed to be 'checked on focus/refresh' (stale between) instead of live?
- Do you accept that detached sessions move into `.claude/worktrees` and that Claude's own Delete discards that worktree?
