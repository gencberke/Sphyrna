# I-06: Chat lens with composer over the live PTY (terminal and chat as two views of one process)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Chat lens with composer over the live PTY (terminal and chat as two views of one process)** · verdict **spike-first** · cost XL · value 4/5 · proposed by 8 reports: [orca](../products/orca.md), [herdr](../products/herdr.md), [cmux](../products/cmux.md), [t3code](../products/t3code.md), [conductor](../products/conductor.md), [paseo](../products/paseo.md), [zed](../products/zed.md), [chat-ui-paths](../products/chat-ui-paths.md).

> The read-only half (a Chat lens over the main session's transcript) fits Loom and is adopt-light via I-05, but the composer-over-PTY and hook-approval half rests on unverified TUI behaviour (a stray Enter can approve a dialog; Loom's "Waiting for you" cannot tell a prompt from a question dialog), so prove the write path in three isolated spikes before committing to the XL whole.

## What the user gets

Toggle Terminal <-> Chat on the same live session: rendered markdown, collapsed tool calls, approvals as cards, a real multi-line composer, history, Esc to interrupt; the real CLI (slash commands, skills, MCP, hooks, subagents, resume) stays authoritative and one click away. Gives the chat-centred feel the user is now open to without an SDK.

## Mechanisms found in the research

I-05 for reading, plus a composer that writes through I-01 (bracketed paste + submit) and enabled only in Ready/Idle; disabled in permission prompts, pickers and slash dialogs; Esc sends an interrupt; approvals and questions via documented hooks (I-15/I-16). Reject screen-scraping of dialogs (Ghostex-style: ~5.2k lines, comments pinned to CLI versions 2.1.268/2.1.280/2.1.284). chat-ui-paths 'A2' = acceptable only for a bounded subset (plain-text send, approve/deny, AskUserQuestion).

## Debates and fact-check corrections

Strongest convergence for 'chat but keep the real CLI'. Risks named by all: two input surfaces ('which has focus'), composer text lost or misdelivered when the TUI is modal, transcript lag for partial output, mode disagreement (plan/permission/dialog). Orca's two-architecture split (terminal + structured chat) is the cautionary tale; Agent of Empires (structured view is DEFAULT, ACP-based, tmux terminal) is not evidence for a stop-and-resume pattern. Ghostex README: raw CLI one hotkey away and your draft comes with you.

## Design in Loom


SHAPE: a second VIEW of the one PTY process Loom already owns. No new process, no stream-json, no SDK, no Node. Billing/ToS posture stays "hosts the unmodified interactive CLI". Staged so each stage is shippable and the next is gated by evidence.

STAGE 0 - spikes (see experiments). Nothing is built until S1-S3 answer.

STAGE 1 - Chat lens, read-only (this is I-05 for the main session; cost L). 
Plug-in points:
- Transcript identity. `ClaudeHookEvent.transcriptPath` (ClaudeHook.swift:383/442, documented `transcript_path` on every hook) is parsed but only used for the subagent ledger (ProviderSessionAdapters.swift:328). Keep the main conversation's path on the live state (new field beside `SessionViewState.subagents`, SessionEventHub.swift:46) from SessionStart/UserPromptSubmit/Stop. For records with no live run (idle, stopped, after relaunch) resolve it by id with the existing `ClaudeTranscriptEffort.transcript(conversationID:projectsDirectory:)` and the same realpath-inside-projects, O_NOFOLLOW, regular-file, own-uid rules as `SubagentTranscriptLocation`.
- Reader (LoomCore, new `ConversationTranscript*`): generalise the proven trio instead of inventing one. `SubagentTranscriptTail` (whole lines only, partial last line held back, cold window = last 512 KiB from a line start, shrink/replaced-inode restart), `SubagentTranscriptFeed` (one vnode source, 200 ms coalescing so at most 5 reads/s, started only while on screen and window visible, `stop()` returns at once). Required changes: (a) the 128 KiB line cap must stop silently dropping lines - a big tool-result line must surface as a "Large record, N KB" placeholder with its byte offset; (b) page backwards on demand in 512 KiB windows ("Earlier" row) - never read a whole file (Paseo #6669 OOM is the cautionary tale); (c) no watcher at all for a record with no live writer - one bounded cold read, then zero cost.
- Parser (new, richer than `SubagentTranscriptParser`, which is a deliberate lossy digest: 4 KiB string clip, first line of tool results, no markdown, `toolUseResult` never decoded): keeps assistant text up to a per-block cap (~64 KiB) for markdown, tool_use name plus input summary, tool_result head plus size, thinking duration, compaction/summary boundary, image placeholders, unknown record types as a collapsed "Unrecognized record (type)" row. Same defensive rules: memmem byte gates before decode, lenient `Lossy<>` blocks, never decode bulky duplicates; heavy bodies (Edit diffs in `toolUseResult`, long tool output) are NOT held - each row keeps its file offset and re-reads that single record when the user expands it. Group by `message.id` (Claude writes one assistant line per content block - ClaudeUsageIndex.swift:16 - so text arrives per completed block, not per token). Order by transcript sequence plus hook timestamps, never insertion time (Orca #23851 showed prompts rendered after responses). Follow the `parentUuid` chain to the active leaf so rewound/abandoned branches are not shown (hypothesis, verify in S3).
- Model/UI (LoomCatalogUI): `ChatLensModel` modelled on `SubagentTranscriptModel` (ring, one observable update per batch, feed alive only while the view is on screen and `windowIsVisible`), `ChatLensView` as a third content branch in `DetailContent` next to the subagent panel and the terminal (DetailView.swift:225 area). The terminal stays with `ConversationController`, running and drained; it is only not in the view hierarchy, exactly the P1 mechanism (D-54) the subagent panel already uses. Per-session mode lives in `CatalogModel` like `viewedSubagent`; last-used mode may go into `UIPreferences`. Markdown without a new dependency: `AttributedString(markdown:, interpretedSyntax: .full)` presentation intents mapped to SwiftUI blocks (paragraph, heading, list, quote, fenced code, table), built on the utility queue and stored immutable on the item; no syntax highlighting in v1. For an ended/idle record the lens replaces `EndedScreenView` as the real history (it survives relaunch, which the memory-only ended screen does not), with the existing Resume notice slot.
- Hard bounds: ring ~400-1000 items, <= ~8 MiB per open lens, released when the session is deselected; only the selected session has a lens; nothing reads when hidden; no timers except the existing 200 ms coalesce.

STAGE 2 - Composer over the PTY (cost M, only if S1 passes). 
- Pure LoomCore function `PromptSubmission` (testable without UI): validates length (<= 64 KiB like OpenSessionInput), refuses leading `/ ! & #` (a leading `!` can run a shell command in the TUI; built-ins like /model open dialogs and fire no UserPromptSubmit so they cannot be verified), wraps in ESC[200~ ... ESC[201~. Single choke point `ConversationController` intent `sendPrompt(text, sessionID)` -> `TerminalSurface.submit` -> the run's existing `TerminalInputQueue.enqueue` (ordered with the user's own keystrokes, 4 MiB bound, closed by `TerminalInputGate` on stop/delete). No second write path.
- Preconditions evaluated at the choke point, from Loom-owned facts only: run live; no `SessionViewState.issue` (hook-silence watchdog quiet); no pending userRequests or open-session wait; activity is atPrompt/turnComplete, or waitingForInput only when the retained Notification type is `idle_prompt` or the registry says idle (today `ClaudeHookStateTracker.notificationActivity` folds idle_prompt, agent_needs_input and elicitation_dialog into one `.waitingForInput`, so the tracker must keep the notification type); the emulator reports bracketed paste on (`Terminal.bracketedPasteMode`, Vendor SwiftTerm Terminal.swift:681 - a standard terminal mode of Loom's own engine, not scraping; if off, refuse, otherwise embedded newlines would submit line by line); and a new "terminal dirty" flag is clear: `TerminalInputQueue` counts non-Enter bytes the user typed since the last UserPromptSubmit/Stop/SessionStart, so a half-typed line or an open slash dialog in the TUI makes the composer say "The terminal has unsent input" instead of pasting into it (the Ghostex "your draft comes with you" case, solved with bytes Loom itself wrote).
- Enter is a separate write after a short gap (Loom's own CP2 experiment plans/experiments/claude-approval.json writes text, waits 0.3 s, then \r), and state is re-checked immediately before the \r: if the session left the promptable state during the gap, the Enter is NOT sent and the UI says so.
- Verified delivery: add a digest (length + hash, not the text) of the documented `prompt` field of UserPromptSubmit to the hook event/tracker (`promptIsSynthetic` already reads that field). Optimistic bubble is styled "Sending" until a UserPromptSubmit whose prompt matches (pasted placeholders arrive expanded, possibly wrapped in <pasted_content> marker lines, and /loop, background-subagent hand-backs and cross-session messages also fire the hook, so match content, never the mere event) or the transcript echoes the user record; one single-shot 3 s timeout (no polling) then "Sent to the terminal, not confirmed" - never a retry, never "Sent". 
- Interrupt: a single ESC byte, only while activity == working, at most once per working period and never twice within 2 s (the 800 ms double-Escape rewind window Ghostex pins to 2.1.280). Stop hook does not fire on a user interrupt (hooks doc), so confirmation is the registry's idle sample (already watched by a vnode source).
- Drafts per session in memory; Up-arrow history from the lens's own user entries. Explicitly out of v1: slash menu, @ mentions, attachments (terminal drop/paste stays), model/effort/plan pills, type-ahead while Working (the CLI has a native queue; could be added later as "queued, unconfirmed" until its UserPromptSubmit arrives).
- Fallback if S1 fails the delivery or stray-Enter bar: "Send as draft" - paste without Enter, switch to Terminal, user presses Enter. Zero approval risk, still removes the multi-line/IME editing pain.

STAGE 3 - Approvals and questions as cards (cost M-L, only if S2 passes). Extend `ProviderLaunchProfile.claudeSettings` (today every hook is `timeout: 1`, advisory, returns no decision): for PermissionRequest, and PreToolUse with matcher `AskUserQuestion|ExitPlanMode` (matcher keeps it off the per-tool spawn path the code deliberately avoids), run `loom-hook` in a blocking mode that follows the existing `OpenSessionControlServer` request/response pattern (held connection, token, 90 s precedent). The helper first reports the event as today (status unchanged), then asks Loom "is a Chat lens showing this session?" - if not, or Loom is unreachable, it returns nothing at once and the TUI dialog appears as today; if yes it waits up to a bounded time for the user's click and returns the documented decision JSON (allow/deny; updatedInput for questions). Timeout falls through to the TUI (cmux "soft wait"), never auto-denies. Only allow-once/deny and plain AskUserQuestion options; "always allow", plan-mode choices and everything else stay "Answer in Terminal". Card style = existing orange `RequestList` callout; Return never approves (DESIGN rule kept). "Approved" is shown only after the tool_use's tool_result appears in the transcript.

DATA FLOW / TRIGGERS (all event-driven): hook event -> tracker/registry vnode sample -> SessionEventHub frame -> CatalogModel -> lens state line; transcript vnode write -> 200 ms coalesce -> utility-queue parse -> one batch -> ring; user action -> choke point -> input queue; one single-shot timer per send for the delivery timeout. No polling anywhere.

COST RE-ESTIMATE for this codebase: whole idea stays XL (rough order 6-9k lines with tests). Stage 1 L (scaffolding reuse saves a lot, but markdown blocks, expand-on-demand, backwards paging and scroll-position stability with variable-height rows are the real work; the existing subagent panel is ~1k lines with tests and is plain text). Stage 2 M (extra work is the fake provider: `loom-fake-provider` must emulate bracketed paste, UserPromptSubmit with prompt, dialogs). Stage 3 M-L. Not counting spikes.


## Where it shows


Header control group (DESIGN section 6, D-53): add a Terminal | Chat segment beside Stop and the three-dot menu; keyboard toggle (shortcut to be chosen in the design round, must not steal Return from the terminal). State is per session and remembered; default for live sessions is a user decision.

Chat view in the detail panel, same panel colour and 6 pt inset rules, a readable centred column (not edge to edge like the terminal). Rows reuse the subagent panel's glyph language so the look is continuous: user prompts as plain blocks, assistant markdown rendered, tool calls collapsed to one line "Bash(npm test)  24 lines" and grouped per turn ("Ran 5 commands, edited 2 files"), thinking as "Thought for 12s", unknown records as one muted row. Tap a tool row to expand the single record on demand. Earlier history behind an "Earlier" row (backwards page read). Follows the tail only while the reader is at the bottom (existing logic).

Bottom composer (Stage 2): 1-8 line auto-growing NSTextView, Return = newline or send per a setting (Cmd+Return the other), a one-line state chip above it: "Ready", "Claude is working - Esc to interrupt", "Needs approval - answer below or in Terminal", "The terminal has unsent input - open Terminal", "Not confirmed - check Terminal". Disabled with the reason spelled out, never silently. Sent messages show "Sending" until verified. Approval/question cards (Stage 3) sit above the composer in the existing orange callout; Allow/Deny are buttons, neither is the default action.

Ended or idle record: the same view without composer, with the existing Resume notice on top, replacing the static ended screen as the readable history; no process, no watcher.


## Principle check


Resources - pass if disciplined: lens exists only for the selected, visible session; feed and vnode source only while on screen and window visible (SubagentTranscriptModel pattern), at most 5 reads/s, cold open = last 512 KiB, ring and per-item caps, heavy bodies re-read on expand, no watcher for records without a writer, no new process. Terminal parsing cost is unchanged (the PTY keeps draining; it is just not drawn). Risk: markdown/AttributedString on very long messages and variable-height SwiftUI rows - must be built off-main, cached immutable, and measured against the 40% CPU gate.
Predictability - pass: one toggle, one send path, one meaning for Return; composer disabled with an explicit reason. Risk: two input surfaces, resolved by visibility (only one is in the hierarchy) plus the dirty-terminal rule.
Accurate status - the central risk, passable only with proof: "Sending" becomes "Delivered" only on a matching UserPromptSubmit prompt (documented field) or a transcript echo; otherwise "not confirmed", never retried. Interrupt is confirmed by the registry idle sample, approval by the tool_result. Risk: the status model cannot yet tell a prompt from a question dialog (waitingForInput merges idle_prompt, agent_needs_input, elicitation_dialog), and a composer Enter that lands in a permission dialog can approve it (Herdr #5263 is the real incident). Mitigated by gating, dirty-terminal accounting and re-check before Enter, not eliminated - that residual risk needs the user's explicit acceptance, or the Send-as-draft fallback.
Fluency - pass: toggle is instant (cold tail read on a utility queue); composer adds one short gap before Enter; no confirmations. Cost: text shows per completed content block, not per token, so live token streaming stays a Terminal-view benefit.
Modularity - pass: reader and parser in LoomCore with no UI import, `PromptSubmission` pure and testable, UI in new ChatLens files, small touches to `DetailContent`, `ConversationIntents`, `ClaudeHookEvent`, `TerminalInputQueue`; dependency direction preserved. Risk: scope creep toward Orca's ~120 native-chat component files; the bounded-subset list is the guard.
CLI-update resilience - risk, contained: the JSONL schema is declared CLI-internal, so lenient decode, unknown records shown (never dropped or faked), recorded-fixture tests per CLI version, drift journaling reusing the `cli_compat_warning` mechanism, and the terminal always one click away. Write-path coupling points are named and each fails closed: bracketed-paste mode, Enter timing, leading-character modes, Esc semantics. No screen scraping (Ghostex needed ~5.2k lines pinned to 2.1.268/2.1.280/2.1.284). `--prefill` is hidden/undocumented and is not used.
Ownership - pass: no new process; input goes through the run's own PTY and queue, closed by `TerminalInputGate` on stop/delete; Quit and verified Stop unchanged. (Alternatives B/C/D in chat-ui-paths would add a second owner.)
User authority - pass with care: every send, interrupt and approval is an explicit user click or keystroke; nothing auto-approves; Return never approves; the hook wait times out into the TUI dialog, not into a denial; the lens only holds a hook when it is actually showing that session.


## Value for the user (4/5)

High for the reading half: a heavy multi-session, multi-subagent user gets rendered markdown, folded tool noise, catch-up on finished sessions and, for idle/ended records, real history that costs no process and survives relaunch (the static ended screen does not). It is also the foundation the user's side chat and right panel need, with no SDK or billing exposure. The composer adds less (multi-line editing, native IME/Turkish-layout input that the terminal handled badly in D-36) while carrying the only real hazards, so the value drops to about 3 if the user is happy typing in the terminal; the approval cards overlap what I-15/I-16 notifications already give.

## Experiments before building

- S1 write-path fidelity on a real Claude CLI in a throwaway CLAUDE_CONFIG_DIR (never ~/.claude), Haiku, low effort, driven through Loom's own PTY test harness like plans/experiments/claude-approval.json. Matrix: single-line, 5/50-line, Turkish-character, 20 KB and 64 KB text; bracketed paste then \r after 0/50/150/300 ms; N=30 per cell. Record UserPromptSubmit.prompt equality (expanded placeholders / <pasted_content> markers) and misses. Also leading / ! & # behaviour via paste, and Esc: single Esc while Working (does registry go idle, does Stop fire) and single/double Esc at idle. Decides: gap length, size cap, whether leading characters must be refused, whether Stage 2 may auto-submit. Bar: >= 99% verified delivery and zero unexplained results; otherwise ship only Send-as-draft.
- S2 dialog and state discrimination plus hook concurrency, same isolated setup. For each of: idle prompt, Bash permission dialog, ExitPlanMode, AskUserQuestion, MCP elicitation, /model picker, folder-trust, feedback survey, record hook events (including Notification type) and registry status before/after a composer-style paste+Enter, and what a stray Enter does (does it approve the highlighted option). Separately, a blocking PermissionRequest hook and a PreToolUse(AskUserQuestion) hook returning updatedInput in an INTERACTIVE session: does the dialog render while the hook waits, does answering in the TUI cancel the hook, does timeout fall through to the dialog. Decides: whether 'promptable' can be derived from hook+registry+dirty-terminal rules alone, and whether Stage 3 exists at all.
- S3 transcript fidelity on recorded fixtures from the same throwaway profile: latency from hook (Stop, PostToolUse) to the JSONL line (expect the documented ~100 ms flush), granularity (one line per content block), ordering of the user record vs UserPromptSubmit, parentUuid branches after /rewind, /compact, /clear and resume, isMeta/sidechain lines in the main file, largest single-line sizes. Decides: ordering rule, branch-following rule, line cap and placeholder behaviour, and whether the 'Earlier' backwards page is enough. Keep the fixtures as per-CLI-version tests.
- S4 (cheap, during Stage 1, not a go/no-go) render cost: 400-1000 long markdown items with large code blocks in the evidence harness, CPU against the 40% gate and scroll-position stability when prepending an older page.

## Questions for the user

- Is the lens a second view of the same process (terminal stays authoritative, default view per session chosen by you), or do you want Chat to become the default for live sessions? Either needs a new DECISIONS entry amending DESIGN section 2.6 ('never replaced by a custom chat UI') and UI-MAP.
- Do you actually feel pain typing in the terminal (multi-line, Turkish layout, IME), or is the want mostly reading and catching up? That decides whether the composer (Stage 2-3) is worth its risk, or whether Stage 1 plus Send-as-draft is enough.
- Accept the bounded composer (plain text only; no slash commands, @ mentions, attachments, model/plan pickers; leading / ! & # refused) and the residual, mitigated-not-zero risk that a composer Enter lands in an approval dialog and approves it? Or prefer the zero-risk Send-as-draft?
- Should a lens-visible session hold a blocking PermissionRequest hook (answer in the card, soft-timeout into the TUI dialog), or should approvals stay in the terminal and the notifications of I-15?
- Should the lens replace the static ended screen for stopped sessions (it would supersede part of D-54 point 3: 'a stopped session shows its last terminal screen')?
- Keys: does Return send or insert a newline in the composer, and which shortcut toggles Terminal/Chat?
- Order against side chat: build the lens first so a right-panel side chat can reuse it, or side chat first as a plain forked PTY?
