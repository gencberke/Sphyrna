# I-09: Side chat as a forked real CLI session (the user's ChatGPT-style side thread)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Side chat as a forked real CLI session (the user's ChatGPT-style side thread)** · verdict **spike-first** · cost L · value 5/5 · proposed by 14 reports: [cmux](../products/cmux.md), [t3code](../products/t3code.md), [conductor](../products/conductor.md), [codex-app](../products/codex-app.md), [superset](../products/superset.md), [paseo](../products/paseo.md), [zed](../products/zed.md), [cursor](../products/cursor.md), [emdash](../products/emdash.md), [openchamber](../products/openchamber.md), [happy](../products/happy.md), [claude-official](../products/claude-official.md), [chat-ui-paths](../products/chat-ui-paths.md), [power-user-workflows](../products/power-user-workflows.md).

> Build it as a hidden child card whose run is `claude --resume <parent> --fork-session` in a plan-mode PTY (the only mechanism that keeps the real CLI, has no billing exposure and reuses Loom's start, stop and verified-delete machinery), but run a one-day isolated-profile spike first, because the card-identity, cache and mid-turn-fork behaviour of the flag are unverified and decide the design.

## What the user gets

Ask about the current work without polluting or blocking the main thread: a child of the parent card (nested like subagents, hidden from the normal list), seeded with the parent's context, multi-turn, with 'promote to normal session', 'bring the answer back' (a user click pastes a summary into the main prompt) and 'discard' (verified deletion). Closed = nothing running.

## Mechanisms found in the research

1) [Documented flags; verified in `claude --help` 2.1.300: --resume, --fork-session] A second Loom-owned PTY running `claude --resume <id> --fork-session` in its own run scope, started only on demand and stopped when the panel closes or the parent ends; ended-screen/transcript view when closed; feature-detect the flag and degrade with a drift notice. Fork from the last COMPLETED turn (T3, OpenChamber, Codex: a fork only sees what is flushed). Prefix the first message with a boundary instruction (OpenChamber BTW_BOUNDARY: inherited history is reference only, no subagents, no file changes unless asked; Codex SIDE_BOUNDARY_PROMPT) and default to plan/read-only permission mode or a restricted tool allowlist (Loom's own design; Codex enforces only at prompt level and permits user-requested mutation). Mark lineage in Loom's own store. 2) [headless variant, needs I-05/I-07 renderer] `claude -p --resume <id> --fork-session` with --permission-prompts none; deleted on close; forks are tagged programmatic so they stay out of /resume. 3) [undocumented] side_question control request on a Chat-mode process, feature-detected, falling back to 2. 4) Reject: copying the JSONL under a new id (Happy's forkSession) breaks on schema change.

## Debates and fact-check corrections

Highest-convergence idea AND the user's long-standing wish. Debates: PTY child (cheap, honest, no billing exposure, terminal UI) vs headless fork rendered in a chat panel (better look, multi-turn with read-only tools, billing exposure and needs a renderer); persistent child (Codex users ask for persistence, #26227; Cursor durable child) vs ephemeral (Desktop side chat is unsaved, Codex /side is ephemeral). Experiments chat-ui-paths wants before committing: does --fork-session work while the parent is mid-turn in another process; combine with --no-session-persistence; does the fork reuse the parent's prompt cache (cache_read_input_tokens); what junk is left under ~/.claude/projects for the deletion path to clean. Costs: a fork re-reads the full context (tokens, cache), double usage while both run; usage must be tagged to avoid double-counting; fork pollutes the registry and `claude --resume` lists unless grouped under the parent and cleaned by Loom's verified permanent delete; shares the working tree so only guidance or tool limits keep it read-only; do not fork mid-approval; users may expect the answer to flow back (it will not). T3's side chat is only an open PR (#18243), not shipped; OpenChamber #3755 (/btw fork inherited an active goal) is reported on 1.24.2 and likely mitigated, but shows metadata must be stripped. Fork-from-an-earlier-prompt (Happy) belongs here only if a documented CLI option exists; otherwise skip.

## Design in Loom


PLAN: a side chat is a NORMAL Loom Claude session (own card, own run scope, own hooks) with one extra catalog link, `side_of = parent card id`. Almost nothing new at runtime. Mechanism 1 only; mechanisms 2 and 3 wait for the I-05/I-07 renderer; mechanism 4 stays rejected.

CORE (LoomCore, no UI):
1. Launch profile. `ProviderLaunchProfile.swift`: add `ClaudeRoute.fork(parent:String, child:UUID)` -> `--resume <parent> --fork-session --session-id <child> --permission-mode plan -n <title>` plus the boundary and question as the trailing positional prompt (the same trailing-prompt slot D-40's `ClaudeOpening` uses; today it is refused for non-`.new` routes, so that guard is relaxed for `.fork`). Add `ProviderCapabilities.supportsForkSession = help.contains("--fork-session")` next to the other substring checks and include it in `detectedClaudeOptions`. Unlike `--settings`/`--session-id` (which the code deliberately passes anyway, ProviderLaunchProfile.swift:111 comment), a missing `--fork-session` REFUSES the side start with a drift notice (`reportCompatibility` + `cli_compat_warning` journal): a launch that silently lacks the flag would be `--resume <parent>`, i.e. a second process writing into the main conversation, the exact pollution the feature exists to avoid. Effort is carried from the parent id through `ClaudeTranscriptEffort.last` as `.resume` does (SessionRuntime+Claude.swift `claudeProfile`).
2. Runtime entry. New `SessionRuntime+SideSession.swift`: `startSideSession(parent:, question:, rows:, columns:, outputSink:)` modelled on `startConversation(opening:)` (SessionRuntime.swift:371-410): refuse unless the parent is Claude, has a `providerConversationID`, is not pending deletion, and its folder exists; same working directory, project and toolchain as the parent (resume looks the transcript up by folder); `supervisor.createSession(...)` with an automatic title (`Aside: <question head>`), `side_of`, and, critically, `providerConversationID = child` PRESET. Reason (read in code): `ProcessSupervisor.adoptConversation` (ProcessSupervisor.swift ~454-585) returns the same card only when `current.providerConversationID == conversationID`; with a nil id and `SessionStart.source == "resume"` (mapped to `.resume` in ProviderSessionAdapters.swift:241-243) it mints a SECOND card and leaves the launch card as an empty orphan. Then `launchClaude(...)` unchanged. Bounds: at most 1 live side run per parent and 2 live overall (refusal text like the tab-strip's "Close one to open another").
3. Verified outcome. `ClaudeSessionAdapter.receive` (ProviderSessionAdapters.swift ~204-255) gets a per-run expectation for side runs: the first SessionStart must report `child`; anything else (equal to parent, or different) stops that run at once and publishes `.issue("Side chat did not fork; stopped")`. 'Started' is therefore never reported for a fork that did not fork. The existing `conversationAlreadyRunning` guard in `adoptConversation` is a second net if the CLI ever reported the parent's id.
4. Catalog. `sessions.side_of TEXT` added by an ensure-on-open step beside `ensureOriginColumns` (CatalogDatabase.swift:247-260), no schema bump, so 0.4.x still opens the catalog. Add to `SessionCatalog.sessionColumns` / `CatalogSession` (SessionCatalog.swift:194-196, 352). Add `s.side_of IS NULL` to the shared `conditions(for:)` in SessionCatalog+Paging.swift (pages, search, counts) and to stale/cleanup classification; new `sideSessions(of: [UUID])` read (one query per visible parents, like `ensureOrigins`, CatalogModel.swift:735) and `promoteSide(id)` (sets NULL, publishes a frame; the transcript keeps the boundary text, so promotion also changes nothing in Claude).
5. Close = Stop. Closing a side chat is the existing verified `stopConversation`; the ended-screen snapshot (EndedScreens, 16 screens / 4 MiB LRU) then shows it, and reopening is a normal `resumeConversation` (cold-cache re-read, see cost). No new lifecycle, no idle timer (D-38), and no auto-stop when the parent ends (a surprise stop; Quit already stops everything).
6. Discard = existing permanent delete. `SessionRuntime.deleteConversation` already does stop -> files -> catalog -> verify (ConversationDeletion.swift; ClaudeDataInventory plans by session id, so the fork's own `<child>.jsonl` and companions are found like any session). Two additions: (a) deleting a PARENT must cascade to its side chats, because each child transcript holds a verbatim copy of the parent's history; otherwise 'permanently deleted' is false (contract §8). The dry-run preview lists '+N side chats' (ClaudeDataInventory.plan takes multiple ids). (b) no confirm dialog on Discard of an unpromoted side chat is the proposal; user decision.
7. Bring the answer back. On click only: read the last assistant text of the CHILD transcript with the existing bounded tail reader (SubagentTranscriptTail 512 KiB cold open + SubagentTranscriptParser narrow decode, no feed, no watcher), then write it as a bracketed paste (NOT Enter) into the PARENT's terminal through `TerminalInputQueue`, only when the parent shows Ready or Waiting for you (never Working / Needs approval, where the paste would land in a permission prompt). Status text is honest: 'Inserted in the prompt, not sent'. If the transcript cannot be parsed (format drift) say so and offer Copy from the side terminal. This is the only place a side chat touches the parent, and it is a user click (D-43/D-46 authority rule).
8. Read-only guard. `--permission-mode plan` is CLI-enforced (stronger than Codex's prompt-only boundary), plus the boundary text as the FIRST user message (inherited history is reference only; do not continue its plans or tool calls; no subagents; no file changes). Do not pin tool names (`--disallowedTools Agent` would be a drift hazard: the tool was renamed Task -> Agent over time). `--system-prompt-snapshot on` is the default in 2.1.300 and, per `claude --help`, resumes send the recorded system prompt 'as-is' even if a later launch passes different text: so `--append-system-prompt` for the boundary would likely be ignored, and also should not be used because it would be a cache-prefix change if honoured; the boundary goes in the message (matches chat-ui-paths SC2).
9. Fork point. The CLI has no documented `--up-to-message`; only the SDK `forkSession` has one. The fork sees whatever the parent has flushed to its transcript, so a mid-turn fork may contain an assistant tool_use without its tool_result. Loom cannot fork 'before the last completed turn' (OpenChamber's rule) with documented options; the boundary message says the last step may be incomplete, and the UI says 'sees up to the last saved message'. Do not fall back to copying the JSONL (Happy).
10. Hook/usage/other fan-out: hooks are keyed by run id, so side status is isolated from the parent. `AttentionOrder`, Dock badge, menu bar and Quit confirmation iterate `liveStates` + `liveRecords` (CatalogModel+Navigation.swift:13-22) and `liveRecords` lazy-loads unknown live ids (CatalogModel.swift:539), so a side chat that needs approval counts without extra code; titles prefixed 'Aside:' keep it readable. Usage: `ClaudeUsageIndex` keys by `message.id` (ClaudeUsageIndex.swift:269), so copied parent lines should dedupe and only the fork's new turns add; verify in the spike. All event-driven (hook frames, vnode watchers already present); no polling, nothing runs when closed.

SMALLEST SHIPPABLE SLICE (the 'M' core): items 1-5 + sidebar child row + header Close/Discard/Promote. Bring-back (7), cascade preview (6a) and the parent-state pill can follow as an S+S.


## Where it shows


ENTRY: header Session menu item 'Ask Aside' and Cmd+; (parity with Claude Desktop) on a live Claude session that has a conversation id. A small popover (one text field, Enter) takes the first question; empty Enter opens the side session with only the boundary. The popover is the only new composer; every later turn is typed in the side terminal itself (the real CLI), so there is no custom chat UI and D-34/contract 'terminal is the CLI' stay intact.
SIDEBAR: under the parent card, in the same guide-line tree as the subagents (SubagentTree.swift, SidebarView.swift SessionListEntry), a row 'Aside · <question head>' with the chase when Working, dot when Needs approval/Waiting, check when stopped. Hidden from the activity list, project list, Active section and search; one click selects it. Up to a few shown, rest folded like 'N finished'.
DETAIL: selecting it swaps it in place of the parent in the detail pane (same mechanism as any session; the parent terminal keeps running and is never resized). Header variant like SubagentHeaderRow: crumb 'Parent title › Aside', its own state pill, a small 'Main: Working / Needs approval / Waiting for you' pill (Codex's SideParentStatus idea, so a blocked parent is never forgotten), then Bring Back, Promote, and a group with Close (Stop) and Discard. Cmd+; or a 'Main' control goes back to the parent. Not Esc: Esc belongs to the Claude TUI here (the subagent panel could use Esc because it has no terminal).
PROMOTE: drops `side_of`; the card joins the normal lists and loses the 'Aside' prefix; a note that the boundary text stays in its transcript.
CLOSED: ended-screen snapshot in memory, record view after relaunch; nothing running. An optional later v2 is a right-hand split (resizes the parent's TUI, see decisions).


## Principle check


- Resources: PASS. Closed = no process, no terminal, no watcher; open = exactly one more Claude + one LoomRunHost, bounded 1 per parent / 2 live. The ended-screen cache is already bounded (16 / 4 MiB). No polling. Honest cost is TOKENS, not CPU: a fork re-reads the whole parent context (warm cache cheap, cold cache = full cache write), every reopen of a stopped side chat likewise. RISK: plan-window burn on 150k+ token contexts; mitigated by the unmeasured cache behaviour in E4.
- Predictability: PASS if behaviour is fixed: Close stops, Discard deletes, Promote unhides, nothing stops on a timer, nothing flows back without a click. RISK: users expecting the answer to flow back (labelled 'Inserted in prompt, not sent'); the fork being a snapshot (does not see later main work).
- Accurate status: PASS with the added first-SessionStart check (item 3) so 'started' means a different conversation id actually started; delete reports only after ClaudeDataDeleter.verify; Bring Back reports 'inserted' not 'delivered'. RISK: a mid-turn fork carrying a dangling tool_use (spike E3); any state shown for the side chat is its own hooks, never inferred from the parent.
- Fluency: PASS. One shortcut and one field; no confirmation on ask; Discard of an unpromoted side chat proposed without a dialog. RISK: the fork's first turn on a cold cache can take seconds; the prompt is accepted before that.
- Modularity: PASS. One new Core file, one profile route, one nullable column, one hidden-filter condition, one child-row view next to SubagentTree; no new protocol or daemon. RISK: `side_of IS NULL` must be added everywhere lists/counts/cleanup read sessions (tests: CatalogHotPathTests, SessionCatalogSearchTests).
- CLI-update resilience: PASS. Only documented flags (`--resume`, `--fork-session`, `--session-id`, `--permission-mode plan`, `-n`), detected from `claude --help` through the existing capabilities struct, no version pin, refusal with drift notice if the flag is gone. RISK: help text shape change causes a false refusal (feature off until fixed; acceptable); `--session-id` combined with `--fork-session` is unverified (E1). The Happy approach (copy the JSONL) is rejected, as is any undocumented `side_question` use in v1.
- Ownership: PASS. Own run scope through the normal launch path; Stop/Quit verified; Discard stops before deleting. No second ownership model.
- User authority: PASS. Everything is user-initiated; the side session cannot write to the main thread; Bring Back is a click that only pastes into an idle prompt; boundary text forbids subagents; `$LOOM_CLI open` from the side session still needs the existing approval box.
- Contract/decisions: D-34 (no right sidebar now) is respected by the in-place v1; contract §13 lists this as an unscoped user wish, so it needs the user's go; contract 'terminal is the real CLI' holds. No billing exposure (interactive PTY, not `-p`/SDK, unlike mechanism 2).


## Value for the user (5/5)

It is the user's longest-standing wish and the top-converging idea (14 sources); a heavy agentic user running multi-hour agents on EDDP-style tickets repeatedly needs 'why did you do that?' / 'what does this file do?' without derailing or blocking the main run, and today's alternatives (type /btw, which is single-answer, tool-less and ephemeral, or open a new session and re-explain) are worse. A PTY fork is not the ChatGPT-style chat look, which costs it a little, but it is multi-turn, can read files, persists, and arrives with no renderer work.

## Experiments before building

- E1 flag combination (decides the card-identity design): in an ISOLATED CLAUDE_CONFIG_DIR (the repo's existing isolated real-Claude method; never ~/.claude), run `claude --resume P --fork-session --session-id C --permission-mode plan -n x -- '<boundary> hi'` against a seeded 2-turn parent. Decide: does it accept `--session-id` with `--fork-session`, honour C, and take a positional prompt together with --resume? If it refuses, fall back to a per-run 'expects fork' flag in the adapter that binds the first reported id (still verify id != parent).
- E2 hook payload: with a logging SessionStart hook, record `source` and `session_id` of the fork. Decides whether `ProviderSessionAdapters.swift:241` (clear/fork -> .new, resume -> .resume) needs a side-run special case, and whether presetting `providerConversationID` fully prevents the duplicate-card path in ProcessSupervisor.adoptConversation.
- E3 mid-turn fork: fork while the parent PTY is mid-turn and while it waits on a permission prompt. Look at the child's transcript for a dangling tool_use, whether the child tries to continue the parent's plan despite the boundary, and whether plan mode really blocks edits. Decides whether Ask Aside is allowed during Working / Needs approval or only at the prompt.
- E4 cache and cost: read `cache_read_input_tokens` / `cache_creation_input_tokens` of the fork's first assistant usage line (it is in the child's own JSONL, no API instrumentation) warm (<5 min after parent's turn) and cold, with default `--system-prompt-snapshot`. Decides the cost hint, whether to warn on large contexts, and whether the same-prefix claim in claude-official holds.
- E5 residue: diff the isolated config tree before/after a fork and after a Loom-style delete by child id; check `ClaudeDataInventory.plan([child])` leaves `residual` empty and that the parent's data is untouched. Also check the child JSONL keeps the parent's `message.id`s so ClaudeUsageIndex dedupe (key 'm|'+id) does not double count: run the usage scan on the temp profile before and after.
- E6 listing pollution: does the interactive fork show in `claude --resume` and `claude agents`? (chat-ui-paths says only headless forks are tagged programmatic.) Decides whether 'Aside:' naming is enough or the picker pollution is a reason to default to auto-discard of empty side chats.
- Pass/stop criteria: build if E1+E2 give a verifiable child id without duplicate cards, E3 shows plan mode holds, and E5 residue is covered by the existing deleter; accept a weaker cost story if E4 is poor, but then show the context size before the first ask.

## Questions for the user

- Layout: v1 swaps the side chat into the detail pane in place (parent never resized, but you cannot watch the main run at the same time), or a right-hand split now? A split narrows the parent's Claude TUI (SIGWINCH reflow, 480 pt detail minimum, D-34 says no right sidebar yet).
- Read-only strictness: `--permission-mode plan` (CLI-enforced; some read-only Bash will prompt) vs prompt-only boundary like Codex vs an 'Allow edits' toggle like T3. Recommendation: plan by default, promote to edit.
- Persistence: persistent child with explicit Discard (recommended, matches the Codex #26227/#40854 demand) vs ephemeral auto-delete on close like Claude Desktop and Codex /side. And: may Discard of an unpromoted side chat skip the confirmation dialog?
- Cascade: deleting a parent also deletes its side chats (they hold a copy of its history). Confirm.
- Do you accept that a fork is a snapshot of what Claude has saved (a running step is not included), and that Bring Back only pastes into the main prompt and you press Enter?
- Cost: a fork and every reopen re-read the whole context; is spending plan window on that acceptable by default, and do you want a context-size hint before the first ask?
- Should side runs ever stop on their own (idle, or when the parent ends)? D-38 says no idle stops; the recommendation is no timers at all.
- Entry: a one-field question popover plus Cmd+; (recommended), or open an empty side terminal only?
- Scope: contract §13 lists the side chat as an idea without a scope decision, so it needs your explicit go before it enters a plan. Also confirm that the PTY child (not a chat-style renderer) is acceptable for the first version.
