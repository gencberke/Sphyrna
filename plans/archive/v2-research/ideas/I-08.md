# I-08: /btw side-question shortcut (lightest side chat)

Card from the [Loom v2 idea catalog](../IDEAS.md). **/btw side-question shortcut (lightest side chat)** · verdict **adopt-light** · cost S · value 3/5 · proposed by 6 reports: [claude-official](../products/claude-official.md), [conductor](../products/conductor.md), [happy](../products/happy.md), [t3code](../products/t3code.md), [zed](../products/zed.md), [power-user-workflows](../products/power-user-workflows.md).

> Adopt a menu item plus one key that types '/btw ' into the live terminal (real CLI, nothing new owned), guarded by a short isolated hook/registry observation; it is cheap and fits every principle, but it only saves about five keystrokes and does not deliver the persistent side chat the user wants.

## What the user gets

One key (e.g. Cmd+;) that focuses the composer and inserts the CLI's own /btw flow: a one-shot question with the full conversation as context, no tools, nothing written to the main thread, works while the main turn is running, cache-cheap.

## Mechanisms found in the research

[Documented in interactive-mode docs] /btw replays the newest 20 exchanges, no tool access, never enters history, terminal keeps it in memory, available mid-turn, 'f' forks it to a background subagent. Loom only binds the shortcut, types '/btw ' into the focused composer when the prompt is empty/idle, and keeps the overlay readable. Even lighter: no shortcut, just document it.

## Debates and fact-check corrections

chat-ui-paths rejects 'type /btw into the PTY' (SC3) because Loom gets no structured answer (overlay only, screen scraping to capture) and holds it as inferior to a Loom-owned fork; the other six reports treat it as the free step 1. Unverified: whether /btw writes to the JSONL or registry on disk. SubagentStop fires for Claude's internal agents including /btw side questions (hooks doc), so the subagent tracker must ignore those. /btw persists in the VS Code panel but not in the terminal or Desktop side chat. Cursor's 'side chat' also uses /btw as an alias but is a durable child conversation, a different behaviour.

## Design in Loom

PLUG-IN POINTS (all follow existing patterns, no new subsystem):
1. Intent: add `askSideQuestion(sessionID:)` to `ConversationIntents` (Sources/LoomCatalogUI/CatalogModel.swift:31) with a default no-op (like approveOpen/closeEndedScreen), implemented in `ConversationController` (ConversationController.swift:177 area). It finds the entry whose `owner == id` (same lookup as `typeForEvidence`, line ~146 and `terminalView(sessionID:)`, line 346), calls `container.focusTerminal()` (line 27) and writes the 5 bytes "/btw " through `surface.send(source:data:)` (TerminalSurface.swift:274) so they take the normal ordered path `TerminalInputQueue` (4 MiB, bounded) -> `TerminalEndpoint.write`. Do not press Enter: the user types the question. Prefer raw keystrokes over `pasteText` (the path `insertDroppedFiles` uses, TerminalSurface.swift:436) so the CLI shows its normal slash-command menu and treats '/' at prompt start like real typing; spike item below decides.
2. Model: `CatalogModel.canAskSideQuestion` (like `canStop`, CatalogModel.swift:1506): selected row has a live terminal owned by a run, activity is not Needs approval (typed letters would hit a dialog), no ended-screen, no open subagent panel (if `viewedSubagent` is set, call `closeSubagent()` first, CatalogModel+Subagents.swift:41, then focus the terminal; or disable). Statuses Working, Waiting for you, Ready, Finished unviewed are all allowed: /btw is documented to work mid-turn.
3. Menu/key: one `NSMenuItem` "Ask a Side Question (/btw)" in `installMenus` (AppDelegate.swift:~735, next to the SessionShortcut items) plus a `SessionShortcut` entry (SessionNavigation.swift:85) so title/key live in one tested place, and a `validateMenuItem` case (AppDelegate.swift:537). Key equivalents reach the menu before the focused terminal (comment at AppDelegate.swift:745), so no change to `LoomTerminalView.keyDown`. Key choice matters: Claude Desktop uses Cmd+; but the user has a Turkish Q layout (the code already special-cases it, TerminalSurface.swift:362) where ';' is not a free key; pick a letter chord (for example Cmd+Shift+B) or let the user choose.
4. Trigger = one user key press, event-driven. No timer, no polling, no new file watcher, no process, no state; nothing is drawn or watched when hidden. The overlay is the CLI's own TUI inside the existing terminal pane, so Loom has nothing to render or keep readable beyond not stealing its keys (Esc/Space/Enter dismiss; Shift+Left/Right, [ ], Tab step older answers; c copy; f fork; x clear). Check that none of these chords is bound in Loom's menus (Cmd+Option arrows and Cmd+Shift+[ ] are, but those carry Cmd).
5. Hardening that the shortcut makes more frequent (internal agents already exist today via prompt suggestions): hooks doc says SubagentStop fires for /btw side questions with `agent_type` = the agent name the session runs as, empty when no --agent/`agent` setting. `SubagentLedger.apply` (SubagentLedger.swift ~lines 150-165) drops an unknown stop only when `type.isEmpty` (comment line 187). If the user runs with an `agent` setting, each /btw would add a finished phantom row to the subagent tree (ClaudeHook.disposition lets agent_id lifecycle events through, ClaudeHook.swift:662). Fix only if the spike shows it: ignore a stop with no earlier start AND no meta.json (internal agents have none, real ones get `agent-<id>.meta.json` ~25 ms after start) or a stop whose agent_transcript_path is absent.
6. Status accuracy: Claude may write the registry `status` busy/idle around a side question. Loom reads the registry (ClaudeRegistryWatch vnode, ProviderSessionAdapters.swift:60) and `receiveRegistry` (ClaudeHook.swift:574) accepts any sample newer than the last hook, so a mid-turn /btw that flips the registry to idle on completion could show 'Waiting for you' while the main turn still works until the next hook, and a /btw at an idle prompt could show 'Working' briefly. This already happens if the user types /btw by hand; the shortcut only makes it more frequent. Observe first, fix in the tracker only if it happens (for example do not trust an 'idle' sample newer than the last hook while a turn is known active, which needs a design check against D-45).
7. Usage: ClaudeUsageIndex already attributes `subagents/agent-*.jsonl` to the parent session (ClaudeUsageIndex.swift:635-665), so if /btw writes a subagent transcript its tokens are counted for free; if it writes nothing, the chip undercounts slightly. Note, do not build.
8. Tests: a controller/model test that the intent writes exactly "/btw " in order through the queue and is refused for Needs approval / ended / no run (mirror TerminalSurfaceTests.swift:125 style); validateMenuItem rules; SessionShortcut table. No e2e needed beyond one fake-provider check that the bytes arrive.
9. Docs: one line in Help or the shortcut list and in LOOM-PRODUCT-CONTRACT section 13 ('side chat' stays an idea without a scope decision) so the shortcut is not mistaken for the side-chat feature.
BOUNDED: 5 bytes per press, rate limited by the user's hand. NOT built: no capture of the answer, no screen scraping, no Loom UI for the overlay (chat-ui-paths SC3 rejects exactly that as a destination, and that is right for the full feature; as a step 1 it is fine because it promises nothing structured).

## Where it shows

No new surface. Window menu (or a Session menu) gets 'Ask a Side Question (/btw)' with a key chord, enabled when the selected session has a live terminal and is not waiting on an approval. Press: focus goes to the terminal and '/btw ' appears at the CLI's prompt; the user types the question and presses Enter; the CLI draws its own dismissible overlay over the prompt area (Space/Enter/Esc dismiss, Shift+Left/Right older answers, c copy, f fork to a background subagent, which then shows in Loom's subagent tree as a real subagent). Optional tiny polish: the menu item's help text or the Help menu says 'Answers are not saved; closing the overlay forgets them' so nobody expects history. If a draft is already in the prompt the text lands at the cursor exactly like typing; Ctrl+U clears it (a documented limit, not detected).

## Principle check

Resources: pass (event-driven, 5 bytes, zero idle cost, no watcher). Predictability: pass with one risk; the CLI cannot report prompt contents, so with an existing draft or vim NORMAL mode the inserted text may land wrongly; mitigated by doing exactly what typing does and by not auto-submitting. Accurate status: RISK until observed; /btw may move the registry status or fire SubagentStop with a non-empty agent_type (phantom subagent row); both are tracker issues that already exist for by-hand /btw and prompt suggestions, so run the spike and harden the ledger/registry rule if needed. Fluency: pass (no confirmations, works mid-turn, saves about five keystrokes plus the need to remember the command). Modularity: pass (one intent, one model predicate, one shortcut entry; LoomCore untouched unless the ledger fix is needed). CLI-update resilience: pass; relies on a documented slash command, no flags, no file format, nothing pinned; if a future CLI renames or removes /btw the user sees the CLI's own 'unknown command' and nothing in Loom breaks. Ownership: pass (no new process; the side question is a model call inside the existing Claude run, covered by Stop and Quit). User authority: pass (no cross-session action; the user types and submits). Contract/decisions: pass; the terminal stays the real CLI (DESIGN.md line 20), D-34 is not touched (no right sidebar); section 13 side-chat item remains open. Would become a violation if: Loom auto-submitted or auto-typed without a key press, scraped the screen for the answer, polled for the overlay, or stored the answer (new durable data, deletion scope, and a CLI-internal rendering dependency).

## Value for the user (3/5)

Real for this user: long multi-agent turns are exactly where a no-tools, cache-cheap question while the main turn runs helps, it needs no new process, and it ships the first slice of a long-standing wish for almost nothing. But the keystroke saving is tiny (typing '/btw ' is five keys), the answer is single-response, in-memory, tool-less and unreachable by Loom, so the wished-for persistent ChatGPT-style side thread in a right panel is not served. The real value is discoverability and a consistent menu entry; it should not be mistaken for, or delay, a Loom-owned side thread decision.

## Depends on

- Independent of every other idea; the optional fork-to-subagent step ('f') relies on the existing subagent tree and transcript panel (SubagentLedger, SubagentTranscript*) and needs nothing new
- Feeds the later decision on a Loom-owned side thread (chat-ui-paths candidates, a --fork-session PTY or stream-json child): a month of using /btw shows whether single-answer is enough

## Experiments before building

- Hook and registry observation (isolated CLAUDE_CONFIG_DIR under ~/Library/Application Support/Loom-Dev/probe/claude-config, the existing loom-probe HookRecorder, installed CLI 2.1.300, never the real ~/.claude): in a Loom-managed fake-or-real session run /btw (a) at an idle prompt, (b) mid-turn while a long tool call runs, (c) with and without an `agent` setting, and record every hook event (SubagentStart/SubagentStop/Stop/UserPromptSubmit, their agent_type and agent_transcript_path), every change of sessions/<pid>.json status, and any new file under projects/<slug>/<session>/ (including subagents/agent-*.jsonl) and the main transcript. DECIDES: if no hook other than an empty-agent_type SubagentStop and no registry status change occurs, ship as is; if the registry flips idle/busy, add the tracker guard; if a non-empty agent_type or no meta.json stop appears, add the ledger guard; if a transcript is written, record that deletion and usage already cover it (subagents/ folder).
- Input fidelity check: with the real TUI confirm that raw keystrokes '/btw ' show the slash menu and run the command, that a bracketed paste of '/btw ' also works (decides send vs pasteText), and what happens with an existing draft, in vim NORMAL mode, and while an approval dialog is open (the dialog case is guarded by state; the others are documented limits).
- Key choice: confirm which chord works on the user's Turkish Q layout through NSMenuItem key equivalents (Cmd+; versus a letter chord); AppDelegate.swift:745 shows the Shift+Cmd+J case-matching trap to check for.

## Questions for the user

- Which key: a letter chord that works on the Turkish layout, or Cmd+; for parity with Claude Desktop (may not be typeable as a plain chord on Turkish Q)?
- Is typing only '/btw ' (user types and sends the question) acceptable, or should the shortcut open and also submit when the prompt holds text (not possible to detect reliably, so the answer is almost certainly 'type only')?
- Should this stay a thin shortcut while a Loom-owned persistent side thread is evaluated separately, or does the user want the side-chat work to start now and skip this step?
