# I-21: Crash-safe state and 'Resume interrupted' after Quit or crash

Card from the [Loom v2 idea catalog](../IDEAS.md). **Crash-safe state and 'Resume interrupted' after Quit or crash** · verdict **adopt-light** · cost M · value 3/5 · proposed by 2 reports: [herdr](../products/herdr.md), [persistence-remote-orchestration](../products/persistence-remote-orchestration.md).

> Most of the 'crash-safe state' half already exists in Loom (SQLite catalog with WAL, daily backups, damaged-catalog prompt, atomic prefs, system-quit handling, abandoned-run closing), so adopt only the missing half: a launch-time, derived 'Reopen what was running' offer (with an optional 'was mid-turn' tag), no snapshots and no new write path.

## What the user gets

A reboot, crash or update never loses the layout or the resume handles; after a Quit or crash a one-click 'Resume interrupted' (or resume-all) reopens the sessions that were mid-work.

## Mechanisms found in the research

Atomic state writes, a few rolling snapshots (about 15-minute throttle), back up an unreadable state file before overwriting, persist on NSWorkspace will-power-off; mark sessions 'interrupted' (not Failed) when the previous run ended by Quit/crash; validate saved resume references against Claude's own registry on restore instead of trusting them (herdr bugs #5261, #5348 show stale/missing references). Keep any pane screen history opt-in and out of scope (secrets).

## Debates and fact-check corrections

Honours the contract (Quit stops everything, verified) while softening its cost; persistence-remote-orchestration ranks it option A of 'keep the contract, add cheap resilience'. Low risk; part may already exist in Loom.

## Design in Loom

WHAT ALREADY EXISTS (observed in code/docs, so the stated mechanisms are mostly moot):
- Durable state is not a layout file. Loom has no pane layout; the only 'layout' is UIPreferences {selectedSessionID, openTabs (max 8), windowFrame, viewMode, sidebar width} in ui-preferences.json (Sources/LoomCatalogUI/UIPreferences.swift). UIPreferencesStore.flush already writes with .atomic, writes only on change, renames an unreadable file to ui-preferences.unreadable-<ts>.json, tabs are written immediately, selection/frame coalesce for 300 ms (CatalogModel.preferenceWriteDelay) and flush on Quit (AppDelegate.applicationWillTerminate -> flushPreferences). Resume handles (sessions.provider_conversation_id, working_directory, provider_identity_changes) live in catalog.sqlite3: WAL, quick_check, per-event transactions, daily VACUUM INTO backups (3 kept, CatalogBackupStore), launch prompt Restore Backup / Start Fresh for a damaged catalog (AppDelegate+Diagnostics.offerCatalogRecovery, CatalogRecoveryPrompt), migrations in one transaction (docs/ARCHITECTURE.md section 5).
- Reboot/logout/update: macOS sends the quit Apple event; QuitConfirmation.isSystemInitiated reads keyAEQuitReason (logo/rlgo/rrst/rest/rsdn/shut), never asks, shuts down through AppShutdownCoordinator, and replies terminate even if the shutdown is unverified (AppDelegate.quitFinished). An NSWorkspace.willPowerOff observer would only duplicate this path.
- Crash/Force Quit: SessionCatalog.closeAbandonedRuns (SessionRuntime.start, line ~340) ends runs whose leader is dead with reason applicationQuit and no exit status; PreviousRunRecovery drains run scopes; StaleSocketSweep removes sockets; the run host stops forked work if Loom dies (contract section 6).
- 'Not Failed': after Quit/crash no live state exists, so a mid-work session already shows Ended/Idle/Stale (SessionIndicator.init in SessionDisplay.swift), never Failed. What is missing is only the knowledge 'this one was running'.
- Stale resume reference validation: Loom does not scrape references. It launches new chats with --session-id and resumes with --resume (contract line ~258); /clear, fork and resume are tracked by adoptConversation + provider_identity_changes. So herdr bugs #5261 (daemon session recorded as another pane's) and #5348 (hook silently inert without python3) have no direct analogue. SessionRuntime.resumeConversation already refuses cleanly (noProviderIdentity, requireDirectory, deletionPending, unverifiedStop) and ProviderResumeDiagnostics maps 'No conversation found' to providerHistoryUnavailable. Missing: a pre-check before offering resume.

WHAT TO BUILD (lightest version):
1. Derived set, no new schema, no hot-path write. 'Ended with the app' = sessions whose latest run (via run_sessions.unlinked_at IS NULL, so a /clear that moved the run counts the card the run ended on) has runs.end_reason = 'applicationQuit' AND runs.ended_at is newer than the previous launch (CleanupCoordinator already keeps last_launch_at, app_state key, and reads the previous value before overwriting; capture it once at start) AND no later run exists for that session. This covers clean Quit (supervisor stop paths use applicationQuit, ProcessSupervisor+CatalogCommits.swift:32, ProcessSupervisor.swift:437/445, +Shutdown.swift:197) and crash (closeAbandonedRuns). A user Stop (.requested) and a CLI that exited by itself (.processExited) are excluded automatically. The set lives for exactly one launch generation, so it is bounded and needs no cleanup job. Implement as one catalog read in a new small extension (SessionCatalog+Runs.swift neighbour), returning ids, evaluated once after closeAbandonedRuns at runtime start and again only on explicit refresh.
2. Filter: provider == claude (Codex frozen, startableProviders), providerConversationID non-empty, not isDeletionPending, working directory exists (requireDirectory), and the Claude transcript for that id still exists under the profile projects folder (one stat per candidate, off MainActor; helper next to SubagentTranscriptLocation / ClaudeDataInventory which already know the layout). A candidate that fails is dropped from the offer (and could show 'cannot resume: history missing' on its card). This is the 'validate against Claude's own data instead of trusting' part, at zero cost.
3. Optional mid-turn tag (second step, still no hot path): at the start of SessionRuntime.shutdown, before ProcessSupervisor.shutdown, write one app_state row (e.g. quit_busy_sessions, JSON of ids) from the same busy predicate QuitConfirmation.busyCount uses (Working or Needs approval). Hooks are already stopped before the supervisor stops (ARCHITECTURE Quit section), so no late Stop hook can disturb it. For a crash this is unknown, and the UI says only 'was running', never claims mid-turn. The heavier alternative (a sessions.busy_since column set on the busy edge in ProcessSupervisor.updateProviderWorkState and cleared when a non-quit run end is recorded) gives crash-accurate mid-turn tags, costs 2 UPDATEs per turn (same cadence as existing markProviderUsed/markProviderActivity in ProviderSessionAdapters.swift ~273/287), needs the ensureOriginColumns-style add-on-open migration, and has an accuracy trap: Esc-interrupt does not fire Stop, so the flag must follow the effective status, not raw hooks. Not recommended for v2 first cut.
4. Action: CatalogModel gets 'reopenCandidates' (ids) and 'reopenAll()' which calls the existing intents.resume(sessionID:) for each, staggered (sequential with a small delay, concurrency capped at 2-3) so N Claude processes and N terminals do not start in the same instant; each failure surfaces through the existing per-card problem text. Dismiss stores nothing durable beyond an in-memory flag (the set expires at next launch anyway); optionally app_state key reopen_dismissed_at.
5. Never automatic (user authority, tokens, process count): offer, do not act. No auto-resume on launch. No screen history persistence (secrets; the in-memory ended-screen snapshot, max 16 / 4 MiB in ConversationController, stays memory-only).

PRINCIPLE VIOLATIONS TO AVOID: polling for 'what is running' (do it at launch and at shutdown only); writing per hook event; auto-launching Claude processes; claiming 'interrupted/mid-turn' when only 'was running' is known; resuming Codex; reading the user's transcripts beyond a stat; adding a periodic snapshot timer (the herdr 15-minute/48-snapshot machinery solves a problem Loom does not have because its state is a transactional DB plus an 8-field JSON).

## Where it shows

Activity view, only when the offer is non-empty and not searching: a banner row in the existing Banners stack in the detail pane (UI-MAP 'Banners', info style) or, better for discoverability at launch with nothing selected, a heading-style row above Active in ActivityList: 'Ended with Loom · 4' with trailing text buttons 'Reopen all' and 'Dismiss'. Cards keep their normal look (they are ordinary ended rows, loaded by id because paging may not have them; Active has the same 'loaded rows only' constraint, so use a small sessions(ids:) load, not a page). Cards from the offer may carry a muted suffix 'was working' (only when the Quit-time tag knows). The section disappears when the set is empty (all reopened, dismissed, or next launch). Menu bar item/Dock badge unchanged; Cmd+J unchanged (these rows are not 'needs you'). Optional File menu item 'Reopen Sessions From Last Time (N)'. No new indicator state is needed in SessionIndicator (avoid adding an 'Interrupted' state that looks like a verified status). Docs impact: UI-MAP (activity list), ARCHITECTURE (catalog read, shutdown tag), DECISIONS (new D entry), design/DESIGN.md if a heading action style is new.

## Principle check

Resources: pass. Two catalog reads (launch, optional refresh), one app_state write at Quit, N stat calls; nothing watched, no timers, nothing drawn when hidden. Staggered resume bounds simultaneous process starts; the user's click is the spend authorization. Predictability: pass if the set is exactly 'runs that ended with the app during the previous generation and were not reopened since', documented, and expires at next launch. Accurate status: risk if labelled 'interrupted'/'mid-turn' for a crash (unknown) or when hooks were unreliable (providerWorkStateIsReliable false); wording must be 'ended with Loom' and 'was working' only when the Quit-time snapshot says so. Esc-interrupt/Stop-hook gap makes the column variant inaccurate; the derived variant avoids it. Fluency: pass, one click instead of remembering and clicking each card; no new confirmation (Quit prompt already exists, D-45). Modularity: pass, a read-only catalog extension plus a model property; core knows nothing about UI; Codex excluded. CLI-update resilience: pass, uses only --resume which Loom already depends on; transcript existence check is a stat of a path layout Loom already assumes (ClaudeDataInventory, SubagentTranscriptLocation), failure degrades to 'not offered'. Ownership: pass, resumed sessions go through the normal launch and run scope; nothing outlives Quit. User authority: pass, offer only, no automatic resume; unaffected contract rule 'Quit stops everything' (contract section 6; D-38). Contract/decisions touched: none violated (D-34 right sidebar untouched; terminal stays the real CLI). Note a new DECISIONS entry is advisable because it adds startup behaviour.

## Value for the user (3/5)

The user installs and restarts Loom often (0.4.x cadence, plus macOS restarts) and runs several live sessions across projects; after any Quit the sidebar cannot tell which cards were running, so restoring that set in one click is real but occasional value. The headline 'never lose layout or resume handles' is already true (transactional catalog, atomic prefs, backups, system-quit path), so the rest of I-21 adds nothing. Value rises to 4 only if the spike shows the CLI continues an interrupted turn on resume.

## Depends on

- Existing resume path (SessionRuntime.resumeConversation / CatalogModel.resumeConversation); no dependency on other v2 ideas
- Optional pairing with any stay-awake/power-assertion idea from the same theme (separate, not required)

## Experiments before building

- Spike 1 (decides whether the button is 'reopen' or 'reopen and continue'): in an isolated CLAUDE_CONFIG_DIR with its own login, start a Claude session through a Loom-Dev-like launch, kill it mid-turn (SIGTERM and SIGKILL), then claude --resume <id>. Observe: does the CLI detect the interrupted turn and continue by itself, show a 'resume from summary / full' choice, or sit at an empty prompt; does the Loom hook state read Waiting for you / Working / Ready afterwards; does it spend tokens before any user input. Decides: resume-only versus offering a 'Continue' text injection (which needs TerminalInputQueue and the user-authority rules) and how the card state looks right after resume-all. Needs the user's say-so for token spend and a logged-in isolated dir.
- Spike 2 (resource, only when the user says the computer is idle): resume 5 realistic sessions with the staggered loop and measure CPU/RSS and time to Ready against the 40%-of-a-core gate; decides the concurrency cap and whether a 'Reopen all' needs a count limit.
- Check 3 (no spend, read-only): confirm at which point SessionRuntime.start/CleanupCoordinator overwrite last_launch_at relative to closeAbandonedRuns, so the 'newer than previous launch' boundary is read before it is overwritten; write the catalog test (crash-closed run, Quit-closed run, user-Stop run, run followed by a later run) before the UI.

## Questions for the user

- Scope: is 'reopen everything that was running (including sessions at the prompt)' what you want, or only sessions that were mid-turn? The derived design gives the first cheaply; the second needs the Quit-time tag (clean Quit only) or the heavier per-turn column (crash-accurate).
- Offer location: a heading row above Active in the sidebar (more visible, needs rows loaded by id) or an info banner in the detail pane (cheaper, only visible when a session is selected/pane shown)?
- If the CLI does not continue an interrupted turn by itself, do you want a separate opt-in 'Reopen and continue' that types a prompt into the PTY (touches the input-injection rules), or reopen only?
- Should the offer survive a second launch if you ignore it, or expire after one launch as proposed (bounded, predictable)?
