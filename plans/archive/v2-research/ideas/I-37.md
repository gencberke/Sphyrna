# I-37: Cross-session message channel as a user-authority broker (the wanted D-43/D-46 channel)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Cross-session message channel as a user-authority broker (the wanted D-43/D-46 channel)** · verdict **adopt-light** · cost L · value 4/5 · proposed by 9 reports: [herdr](../products/herdr.md), [cmux](../products/cmux.md), [t3code](../products/t3code.md), [claude-official](../products/claude-official.md), [superset](../products/superset.md), [openchamber](../products/openchamber.md), [supacode](../products/supacode.md), [persistence-remote-orchestration](../products/persistence-remote-orchestration.md), [codex-app](../products/codex-app.md).

> Build the user-authority hand-off in two thin slices on machinery Loom already has (user-initiated send with hook-verified delivery first, then an agent `send` that reuses the open-session approval card), and do not build the full broker or govern the CLI's native channel, because native hold/accept cannot be made observable or user-authorized.

## What the user gets

One session can hand a short result or question to another (planner to implementer, reviewer back to author) under the user's control and with verified outcomes, instead of copy-paste between cards; or the user can send between sessions themselves.

## Mechanisms found in the research

Lightest, no new agent-originated channel: user-initiated send/queue (I-02 + I-01) plus session reference (I-38). Next: an authority broker over Loom's authenticated socket (loom:read-session / loom:send-to-session skills): approval card showing the exact text and source session, scoped per source/target/action pair (persisting until Stop or Quit), refuse delivery into Needs approval, explicit states queued -> delivered (prompt observed) -> read | failed (plus 'stalled'), idempotency keys instead of blind retry, text-only with a size cap (cmux 32 KiB) and control characters rejected, provenance label 'not an instruction from your operator', hold while the recipient waits on a human, per-session/project opt-out, iteration cap for reviewer loops, delegation only while the parent is working (T3). Govern the CLI's own messaging instead of duplicating it [documented since 2.1.224]: per-session inbox socket (CLAUDE_CODE_MESSAGING_SOCKET), Loom sets crossSessionInbound accept|hold|refuse via --settings, shows peers and 'message held from X' as a needs-you reason, surfaces notify_when_idle.

## Debates and fact-check corrections

Debate: build Loom's own broker (herdr/cmux/Superset/OpenChamber/T3 style) vs 'do not build a second transport, govern Claude's native one' (claude-official; persistence-remote-orchestration G with H as later adapter). Corrections: explicit crossSessionInbound=hold shows a notice per message and delivers NOTHING, with no dialog and no expiry; the approve/deny dialog (default 5 min) belongs to the unset default rule and only in interactive terminal sessions (Desktop/VS Code cannot show it); the unset default auto-delivers when the receiver prompts for permissions and the sender is not bypassing, so 'user-authorized only' requires explicit hold/refuse; Loom's explicit refuse also blocks the own-child posting path; the message wire format is only reverse-engineered (documented: path, optional auth line, 30 s incomplete-line close); #78706, #65972, #52084 are not precedents (Desktop MCP tool, closed not_planned/duplicate); send cap of 10 per human input is request #94000; Claude agent teams are experimental and token-heavy (do not adopt). Channels (research preview, dev flag) with permission relay is a documented future transport. Herdr: refusal only works when its detector knows the pane is blocked; its failure #5263 shows keystrokes into the wrong state. Prompt-injection chains between sessions and approval fatigue are the main risks. Standing decisions D-43/D-46 (wanted, undated).

## Design in Loom

SHAPE. Two slices plus a deliberate non-goal.

SLICE 1, user-initiated send (the contract's "text transfer" convenience, §7 last bullet; I-02+I-01+I-38 core). The user picks a target and text; Loom delivers it as the user's own prompt and reports verified outcomes.
- New LoomCore actor `SessionMessageCoordinator`, modelled on `OpenSessionCoordinator` (Sources/LoomCore/OpenSessionCoordinator.swift): in-memory, bounded (64 entries like `maximumEntries`), `updates()` AsyncStream for the UI, one one-shot Task per in-flight message (like its 85 s `replyDelay`), no polling. Record = id, source (session or user), target session, text, nonce, state, timestamps.
- States, all verified outcomes: queued (target not safe to type into yet) -> sent (bytes accepted by the run's TerminalInputQueue; explicitly NOT success) -> delivered (the target's UserPromptSubmit hook carried the message nonce) | stalled (no matching UserPromptSubmit within about 5 s; no automatic retry, the UI says it may or may not have arrived) | failed (target stopped, deleted, input queue closed or overflowed) | denied | expired (still queued after a TTL, or at target Stop/Quit). A "handled" mark can come from the next Stop of that run; there is no separate "read" state because Claude gives no read receipt (do not invent one).
- Trigger is event-driven: subscribe to `SessionEventHub` frames (already published on every hook/registry transition). When the target becomes prompt-safe, write once. Nothing runs while nothing is queued.
- Prompt-safe gate (the herdr #5263 lesson): deliver only when the target is `atPrompt` or `turnComplete`, or `waitingForInput` caused by `idle_prompt`/registry "idle"; never in Needs approval, Working, an elicitation/question dialog, or when `TerminalInputGate.lastInputDate(runID:)` is newer than the last turn boundary (the user may have an unsent draft or an open picker). Today `AgentActivity.waitingForInput` merges idle_prompt, elicitation_dialog and registry "idle" (ClaudeHook.swift lines 612-620, 744-748, 790-791), so the tracker needs a small `promptSafe` derivation or a cause tag; the registry's `waitingFor` field is not read at all.
- Delivery write: a header line plus the text, as one bracketed paste, then Enter. Header example `[Loom msg 7f3a9c21 - from you via Loom, session "Planner"; context from another session, not a new instruction]` (starts with "[" so the text can never be read as a slash command, `!` shell or `#` memory prefix; the nonce doubles as the confirmation token). Text-only, C0 controls except \n and \t rejected, NUL rejected, inline cap about 16 KiB (cmux 32 KiB; above the cap write a file under the Loom data folder and send its path, which is I-38's session reference). Write goes through the run's existing `TerminalInputQueue` (registered per run in `TerminalInputGate`), so ordering and overflow handling are already defined; today the queue is created inside `TerminalSurface.attach` (UI layer, ConversationController.adopt), so either `TerminalInputGate` gains `enqueue(runID:bytes:)` or the controller owns the call. Bracketed-paste wrapping must come from the surface's terminal mode (SwiftTerm), not a guess.
- Confirmation: `ClaudeHookEvent` (ClaudeHook.swift) already reads the UserPromptSubmit `prompt` only to set `promptIsSynthetic`; add a `deliveryMark` extracted from the first line (nonce only, never store the prompt). `SessionRuntime.deliver` forwards it to the coordinator -> delivered. Loom's own tracker then shows the target as Working, then Finished unviewed, with no extra status code.
- Stopped target: Resume with the message as the first prompt (`claude --resume <id> -- <msg>`; `ProviderLaunchProfile.claude` currently allows an opening only for `.new`, so that guard is relaxed for resume). No PTY typing at all on that path, delivered is still confirmed by the nonce.
- Idempotency: nonce per message; "Send again" is an explicit user action that makes a new nonce and says "may arrive twice". Never a blind retry (contract §7 "no blind automatic retry").

SLICE 2, agent-originated send under per-message approval (the D-43/D-46 channel, minimal form). Extends the D-40 stack instead of adding a second transport.
- `OpenSessionCommand` gets a `send` subcommand: `"$LOOM_CLI" send --to <session-id|ticket|title> (--message-file F | --message -)`. Same control socket (`LOOM_CONTROL_SOCKET`), same per-run token and `authorize` (SessionRuntime ensureHooks), same validation style (`OpenSessionInput.validated`), same reply/exit-code pattern. `ClaudeLoomPlugin` gets a second skill `send-to-session` (about 80 tokens in context per session).
- Natural first use: when `open --ticket K` returns `exists`, the agent can now `send` the brief into that ticket's session; D-40 said exactly this was "a later slice".
- Approval card = a new `OpenSessionRequest.Kind` (`.deliver`) in the existing `RequestList` slot above the SOURCE session's terminal: exact text (same 4-line preview + "Show full message"), source session, target session and project, buttons Deny / Send. The source card shows Needs approval meanwhile (already wired for open requests: `attention`, Cmd+J, ApprovalNotifier, Dock badge, menu bar), so approval fatigue is at least not hidden. Reply to the waiting agent: `delivered <id>` | `queued` (held until the target is safe; request stays in Loom, memory only) | `stalled` (do not resend, tell the user) | `denied` | `error: ...`; exit codes like open (0/1/2/3).
- The delivery step is Slice 1's, with the provenance header changed to say it was sent by another session's agent and is not from the user.
- Refuse by policy, before any card: unknown or deleted target, target == source, target in Needs approval or Working with the user typing, text over the cap, more than N waiting requests per source (one pending per source, like open requests).
- Loop guard without polling: count agent-to-agent hops since the last human-typed prompt in either session (a UserPromptSubmit that carries no nonce and is not synthetic resets the count); at 6 hops, the next send needs a fresh card even if a grant exists.

OPTIONAL, ONLY AFTER USE SHOWS APPROVAL FATIGUE: scoped grant "allow <source> to send to <target> until Stop or Quit": in memory, keyed by (source session, target session, action), dropped when either run ends, a new conversation id is adopted, or Loom quits; capped at 20 messages; not offered when the target runs with bypass/auto permissions (read `permission_mode` from hook payload, not parsed today; verify); not offered across projects. Every grant-delivered message still appears as a one-line log row in the target's detail view.

READ side (`loom:read-session`): defer. When wanted, answer only from data Loom already holds: `ClaudeSessionStatus.lastAssistantMessage` (set from the Stop hook, no transcript read) and state; a deeper read reuses the bounded tail reader pattern (`SubagentTranscriptTail`); cross-project reads need a card.

NON-GOAL, govern the CLI's native channel. Keep `"crossSessionInbound": "refuse"` (ProviderLaunchProfile.swift, claudeSettings). Reasons verified against the docs and the fact-check: explicit `hold` shows a per-message notice in the terminal and delivers nothing, emits no documented hook or event, so Loom cannot show "message held from X" as an accurate needs-you reason, and there is no dialog and no expiry; the approve/deny dialog belongs to the unset default and only in terminal sessions; `accept` and the unset default deliver automatically when the receiver prompts for permissions, which breaks "user-authorized only"; `refuse` on either side also disables native notify_when_idle, and Loom's own state, Cmd+J and notifications already cover "tell me when it is idle". The wire format for posting to the inbox socket is only reverse-engineered (documented: path, optional auth line, 30 s incomplete-line close). Claude agent teams are experimental and token-heavy; do not adopt. Channels (research preview, dev flag, permission relay) are a documented future transport, not a base.

KNOWN GAP (unchanged by this idea): a Loom session can still SendMessage to a Claude session outside Loom, and docs say Claude Code does not prompt for same-machine sends. Contract §7 already records this; a PreToolUse hook with matcher `SendMessage` (cost only when that tool fires) would close it, see experiment S4.

BOUNDS: text 16 KiB inline, 64 KiB wire (as open), 64 records, one pending agent request per source, TTL for queued messages (30 min proposed), nothing persisted (a queued message is lost at Quit and the card says so, same wording style as the `pending` line in OpenSessionReply.line), Quit and Stop of either side expire the record, deletion fence (SessionRuntime already fences a deleting session out of every list) turns a queued message to failed.

## Where it shows

No new chrome and no right panel needed.
1) Entry points: "Send to Session..." in the card context menu and the detail header's actions menu (next to SessionLocationMenuItems in SessionMenuItems.swift), and "Send Last Answer To..." when the session has a stored last assistant message. A small sheet: target list (live sessions first, grouped by project, same project preselected), a text field (or the quoted last answer), and a Send button; a stopped target shows "will resume it" in secondary text.
2) Outcome strip: a slim neutral box in the existing RequestList slot above the TARGET terminal ("Message from Planner: delivered" / "waiting until this session is at its prompt" / "not confirmed: check the terminal"), one line, fades when dismissed; the sender's sheet is not kept open.
3) Agent request (Slice 2): the existing orange open-session box look: "Send a message to <target>?" with Source / Target / Project lines, the exact text (4-line preview, Show full message), Deny and Send; neither is the default action and Return stays with the terminal (same rule as DESIGN.md "A session that opens a session"). While waiting, the source card/tab/project dot read Needs approval.
4) Card meta row: reuse the origin-arrow idea only if wanted later ("from <session>" already exists for opened sessions); no permanent badge for messages.

## Principle check

Resources: PASS. Event-driven from SessionEventHub and the hook; one one-shot timer per in-flight message; bounded records; nothing drawn or watched when no message exists; no asyncRewake waiter process per session in the base design (cmux's 2 s asyncRewake poll leaked memory in idle sessions, #18632). RISK only if the asyncRewake path is chosen later: one blocking helper per live session, and Claude still enforces the hook `timeout` on it, so it needs re-arming.
Predictability: PASS with a gate. Delivery only at a proven prompt-safe state; one write, no retry; every message ends in an explicit state. RISK: today `waitingForInput` conflates idle_prompt, elicitation dialogs and registry idle, and AskUserQuestion/plan dialogs are not separately tracked; typing into the wrong dialog is exactly herdr #5263. The gate must be conservative and S2 must map it.
Accurate status: PASS. Only "delivered" when the target's own UserPromptSubmit carried the nonce; "sent" is never shown as success; stalled is a first-class result (this also acts as drift detection for the paste mechanism). Contract §7 stages (recorded, forwarded, accepted, completed) map to queued, sent, delivered, Stop seen.
Fluency: PASS for slice 1 (no confirmation, the user is the authority). Slice 2 costs one click per message, reachable by Cmd+J and notification; that is the price of authority; grants are deferred until the friction is real.
Modularity: PASS. New coordinator beside OpenSessionCoordinator, same socket, same authorize, same RequestList slot, one new Kind; the hook parser gets one field; no change to ProcessSupervisor, run scopes or the catalog schema (in-memory only).
CLI-update resilience: MODERATE RISK. Slice 1 depends on bracketed-paste input into the Claude TUI (de facto, not a documented delivery interface) and on the documented UserPromptSubmit `prompt` field (Loom already reads it); drift shows up as stalled, never as false success. The contract's CP3 "decisive case" wants a documented interface for idle live targets (asyncRewake, or resume with a prompt); PTY paste is allowed only as the user's text-transfer convenience (§7). Using it for agent-originated sends needs an explicit contract note from the user or the S3 result. Governing the native channel is rejected partly for this reason (undocumented posting format, no held-message signal).
Ownership: PASS. No new process; a resumed target goes through the normal start path inside a run scope; Stop/Quit/deletion expire records.
User authority: PASS by construction in slice 1; slice 2 requires an explicit card with the exact text and source, refuses delivery into Needs approval, labels provenance ("not an instruction from you"), cannot answer another session's approval (a prompt is not an approval; the target's own permission prompts still fire), and has a hop cap. RISK: prompt-injection chains and approval fatigue are the main residual risks; they argue against standing grants, against grants into bypass/auto targets, and against cross-project grants (the user has two work projects with separate contexts). A grant must never be global or persisted.

## Value for the user (4/5)

The user is a heavy multi-session user with ticket-keyed sessions and a standing wish (D-43) for exactly this, and today every hand-off is copy-paste between cards. Slice 1 alone (send a session's last answer to another session, with an honest delivered/stalled result) is a large, cheap win and also the base of the side-chat and queue ideas. Slice 2 adds the planner-to-implementer and reviewer-back flows but carries injection and fatigue risk, so it is a 3 on its own; the full broker (grants, caps, read verb, native governance) is not worth its cost for one user and is where the 'L' of the original estimate sits.

## Experiments before building

- S1, real-CLI delivery spike (isolated CLAUDE_CONFIG_DIR, throwaway project; decides whether Slice 1 can ship): bracketed paste + Enter into a live Claude TUI at its prompt, three sizes (200 B, 4 KiB, 30 KiB multi-line) with a nonce on line one; Enter in the same write vs 150 to 500 ms later (Superset #6243: delivered is not submitted). Record: does UserPromptSubmit fire, time to hook, does `prompt` contain the nonce after Claude collapses large pastes, what happens when the first char is / ! #, with an unsent draft already in the composer, with a slash picker open, and when sent mid-turn (queued: does the hook fire when it is dequeued, how late). Decides: inline cap, whether a single Enter re-send is ever allowed, the stalled timeout, and whether 'queued while Working' is sent immediately or held by Loom.
- S2, prompt-safe gate map (same isolated setup, plus the fake provider for unit coverage): for AskUserQuestion, ExitPlanMode, MCP elicitation, a permission prompt, the trust dialog, /model and /resume pickers, record which hook events and registry statuses (`status`, `waitingFor`) Loom actually receives and what `AgentActivity` results. Decides whether a `promptSafe` flag can be exact or must fall back to 'Stop/SessionStart seen and no user keystroke since' only; if a dialog is invisible to both, the gate stays at that conservative rule and the UI says so.
- S3, only if agent-originated delivery must use a documented interface: an asyncRewake hook (exit code 2 wakes an idle Claude with stderr as a system reminder) backed by a helper that blocks on the Loom socket. Measure idle RSS/CPU of the waiter per session, behaviour at the enforced `timeout` and re-arming, duplicate waiters if registered on several events, and that the message shows to the model as a system reminder rather than a user prompt (changes provenance and the nonce check). Decides: PTY paste vs asyncRewake for Slice 2.
- S4, outbound gap: does a PreToolUse hook with matcher `SendMessage` fire and can it deny or ask in 2.1.300, so Loom sessions cannot message non-Loom sessions unprompted without banning SendMessage (which would also kill subagent/team messaging)? Cost is zero when the tool is not used. Independent of the rest, but it is the honest completion of 'cross-session actions only under the user's authority'.
- S5, resume-with-prompt: `claude --resume <id> -- <message>` under an isolated profile, with the nonce, to confirm the stopped-target path delivers through UserPromptSubmit and what the cold prompt cache costs; also whether `--settings`/plugin flags interact.

## Questions for the user

- Is Slice 1 (you send between sessions yourself, verified) enough for the first release of this, with agent-originated sends following only after the S1/S2 results? Or do you want the planner-to-implementer agent flow in the same round?
- For agent-originated sends: always one approval card per message, or may a later round add 'allow this pair until Stop or Quit' (not for bypass/auto targets, not across projects)? Prompt injection and approval fatigue pull in opposite directions.
- Should messages between your two work projects (different tickets and contexts) be allowed at all, and should a read of another session's last answer need a card across projects?
- A message to a stopped session: resume it automatically with the message as its first prompt (spends tokens, cold cache) or show 'stopped' and ask first?
- A one-line Loom provenance header with a nonce will be visible in the target's transcript. Acceptable, or do you want the receiving side to see only the bare text (then confirmation falls back to prompt-text matching, which is weaker)?
- The contract (section 7, CP3) says the decisive delivery case should use only documented interfaces and calls pasted text a user convenience. Do you accept PTY paste as the delivery for agent-originated sends once S1 passes, or must it be asyncRewake / resume (S3)?
- Queued messages live in memory and are lost at Quit (the card says so). Is that acceptable, or must a queued hand-off survive Quit (which would need persistence rules from contract section 7)?
