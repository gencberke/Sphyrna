# I-31: PR / CI chip and canned git actions

Card from the [Loom v2 idea catalog](../IDEAS.md). **PR / CI chip and canned git actions** · verdict **adopt-light** · cost M · value 3/5 · proposed by 7 reports: [conductor](../products/conductor.md), [emdash](../products/emdash.md), [supacode](../products/supacode.md), [claude-official](../products/claude-official.md), [review-git-loop](../products/review-git-loop.md), [vibe-kanban](../products/vibe-kanban.md), [power-user-workflows](../products/power-user-workflows.md).

> Adopt a read-only, GitHub-only PR/checks chip fed by one bounded `gh pr list --json` call at the events Loom already has (turn end, window activation, manual refresh), and leave the canned Create PR / Fix CI / Resolve conflicts actions, ETag, merge-tree and "CI failure becomes needs-you" out, because the chip pays for itself only if the work repos are on GitHub and the actions only make sense once the I-01 send primitive exists.

## What the user gets

PR number, merge state and check state on the card ('CI failing' next to the branch, surfacing in the Active list), and one-keystroke Create PR / Fix CI / Resolve conflicts as short prompts to the session; fits the ticket-key workflow.

## Mechanisms found in the research

Event-driven only: refresh on Stop hook, app activation, a visible card's push and a manual refresh; while checks are pending and the card is visible back off (30 s, 60 s, 2 min) and stop when settled; `gh pr view --json statusCheckRollup,mergeStateStatus` through the installed gh (no tokens stored), ETag/conditional requests, label 'checked at <time>', never a false green when gh is missing/logged out; a failed check can move the session to needs-you. Alternative: pr.number / pr.review_state from the I-24 statusLine JSON (no gh), GitHub only. Canned actions are constant slash commands or editable templates sent through I-01 (review-git-loop 'lightest git write path'); merge-tree conflict preview cached by OID pair is optional (OIDs come from PR data and the base ref is fetched, so it is not network-free).

## Debates and fact-check corrections

Competitors poll: Superset PR status every 10 s and comments every 30 s, Orca 120 s stale, Emdash per-repo each minute, Supacode GraphQL storms and rate limits (#830, #844); the research insists on event-driven only. The user's work repos may be GitLab (power-user-workflows), where gh gives nothing. Skip merge buttons, stacks, auto-merge, auto-fix loops unless asked (agent can run gh itself).

## Design in Loom

PLUG-IN POINTS (all verified in code). Loom already refreshes the card's Git branch at exactly the events the idea wants: `CatalogModel.apply(frame)` calls `refreshBranches([workingDirectory])` on a `.turnComplete` status frame, `setWindowActive(true)` calls `refreshBranches(Set(branches.keys))`, and `BranchCache` (actor, one read per folder, publishes only changed values, `retain()` prunes to shown folders, `pruneBranches()` ties lifetime to cards/selection/tabs). The PR status should be a sibling of that path, not a new scheduler: new `PullRequestCache` actor (LoomCatalogUI, same shape as `BranchCache`) keyed by (folder, branch), `CatalogModel.pullRequests: [PRKey: PullRequestStatus]` (in memory only, no catalog schema change, pruned with `pruneBranches`), `CatalogModel+PullRequests.swift` for triggers, same serialized-publish trick as `branchTask`.

NEW CORE PIECES (LoomCore, no UI imports, per ARCHITECTURE layer rule): (1) `PullRequestFetcher`, modelled on `LimitsExchange` in `ClaudePlanLimits.swift` (Foundation `Process`, poll with short steps so a cancel is noticed, 15 s timeout, 1 MiB output cap, SIGTERM then SIGKILL, stderr to null, cancelled on Quit). It runs `gh pr list --head <branch> --state all --limit 1 --json number,url,state,isDraft,headRefOid,mergeStateStatus,reviewDecision,statusCheckRollup,updatedAt` in the card's folder, with env from the resolved `ProviderToolchain.environment` (the user's login-shell PATH, because a LaunchServices-started Loom has no /opt/homebrew/bin) and `GH_PROMPT_DISABLED=1 GH_NO_UPDATE_NOTIFIER=1 NO_COLOR=1`. Use `pr list --head` rather than `pr view`: it returns `[]` with exit 0 when the branch has no PR, so "no PR" is a verified outcome and no stderr text is ever parsed. Exit 4 (documented in `gh help exit-codes`) = not logged in; exit 1 / timeout / spawn failure = could not check. (2) `PullRequestStatus` pure value + parser/classifier (unit-testable with canned JSON): outcome is one of noPullRequest (verified), open/draft/merged/closed with `checks` in {none, pending, failing(n of m), passing} and `merge` in {clean, behind, blocked, conflicts, checking}, or `unavailable(reason: ghMissing | notLoggedIn | notGitHubRemote | failed | outputNotUnderstood)`. statusCheckRollup mixes CheckRun (status/conclusion) and StatusContext (state) entries; any unknown enum value is classified unknown, never passing; an EMPTY rollup is "no checks", never "passing"; `mergeStateStatus == UNKNOWN` (GitHub computes mergeability lazily after a push) is "checking", never "conflicts". (3) Forge gate without a process: read the remote URL from `.git/config` (same small bounded file reads as `GitBranch.read`, worktree `commondir` aware); if the host is not github.com or a host `gh` knows, show nothing and spawn nothing. This is also how a GitLab repo degrades quietly instead of showing a gh error on every card.

TRIGGERS (events only): (a) turn complete of a session, (b) window becomes active, (c) a card's first appearance when it has a live run and no cached value, (d) manual 'Refresh PR Status' in the session menu / chip context menu. NOT triggers: FSEvents on refs/remotes (the agent's push happens inside a turn so the Stop edge already catches it, and a push from another terminal is caught by activation; dropping the watcher removes a per-card file watcher), hooks per tool call (Loom registers no per-tool hooks on purpose, `claudeSettings` comment), any timer for settled PRs.

BOUNDS: refresh only for sessions that have a live run, plus the selected session and tab sessions (ended cards show their last cached value dimmed, or nothing); one gh child at a time (serial queue, like the ordered `branchTask`); at most one refresh per (folder, branch) per 30 s except manual; dedupe sessions sharing a folder; results below the 1 MiB cap only. The single deliberate exception to no-polling: while the last result is `checks: pending` (or just pushed and the rollup is still empty) AND the window is active AND the session is selected/tabbed/live, re-arm ONE cancellable one-shot task at 30 s, 60 s, 120 s, 120 s, ... capped at about 10 minutes total (7 calls), cancelled on window deactivate and on settle. After the cap the chip says 'pending, checked 14:41' and waits for the next event or a manual refresh. This is bounded and visible, and should be presented to the user as a decision, not hidden. GraphQL cost is about 1 point per call, so no ETag/`gh api -i` layer is needed at this call volume; the Supacode storms (#830, #844) came from timers over every worktree, which this design never does.

VERIFIED OUTCOMES: the chip carries `checkedAt` (shown in tooltip and header, 'checked 14:32') and, optionally, compares the PR's `headRefOid` with the local branch tip read from the ref file: if they differ the header says 'checks are for an older commit' (unpushed work), which stops a green PR from hiding local changes. 'merged' / 'closed' come only from gh's `state`, never from the agent saying so (contract: 'the agent saying done is not proof'). On failure the last known value stays but is dimmed with its time and the reason; it is never refreshed to green by a failed call.

DRIFT: gh's `--json` field list is documented (`gh pr list --help`). A removed field makes gh exit 1 with an unknown-field error; map that to `outputNotUnderstood` and journal one `cli_compat_warning` per app run, same pattern as `ClaudeRegistryDiagnostics` / `reportCompatibility` (D-45). No GitHub API versions, no tokens stored, no OAuth, uses the user's own gh login.

NOT IN THE LIGHT VERSION (and why): (1) 'failed check moves the session to needs-you': `SessionIndicator` derives from provider state (`SessionDisplay.swift`), `AttentionOrder.rank`, the Dock badge, the menu bar item, Cmd+J and the Active section's `activePhase` (set in `SessionEventHub.publish`) all share that one meaning ('Claude is waiting for you'); a red CI is a fact about a PR, not about the session, and mixing them breaks 'accurate status'. Show it as a chip tint only; revisit as a separate, opt-in 'CI failed' notification if the user asks. (2) Canned actions: Loom has no send-to-session path today (grep finds only the evidence-only `typeForEvidence`); they depend on the I-01 verified-send primitive. Until then the cheapest honest version is 'Copy Fix-CI Prompt' (with failing check names filled in) in the chip's context menu. Once I-01 exists, add constant or user-editable templates sent as a draft (not auto-submitted), refused while the session is Needs approval. (3) merge-tree conflict preview: not network-free (OIDs from PR data, base ref must be fetched, per the review-git-loop fact-check) and `mergeStateStatus` already says DIRTY/BEHIND/BLOCKED. (4) merge button, stacks, auto-merge, auto-fix loops: the agent can run gh itself, and auto loops spend tokens without the user.

GITLAB: Claude Code's statusLine JSON does carry `pr.number/url/review_state` and, for a GitLab remote, the merge request (`pr.kind: mr`, v2.1.234+), but only number and a coarse review state, no pipeline status, and getting it needs the I-24 statusLine bridge, which the usage-tools digest rates the weakest fit (per-update process spawn, an inline `--settings` statusLine replaces the user's own and hides CLI footer hints; D-32 forbids a process per update). So the I-24 route is not the cheap alternative the idea implies. If the work repos are GitLab, the honest options are a second forge adapter (`glab mr list --source-branch ... --output json`, +M, glab is not installed on this machine, gh is) or no chip for those projects.

COST (honest re-estimate): idea says M. Chip only: M at the low end (about 600-800 lines incl. tests): fetcher ~200, status parser/classifier ~150, cache + model ~200, card/header/menu views ~120, Settings switch + docs ~60; tests are cheap because a fake `gh` script on PATH and canned JSON cover parsing, tri-state, throttle, cancel-on-quit and prune. Full idea as written (ETag layer, FSEvents push watcher, merge-tree with fetch, canned actions with delivery verification, needs-you promotion) is L-XL and drags in I-01 and the Active/attention pipeline.

## Where it shows

CARD (SessionCardView, `SidebarView.swift` ~line 463): the existing second row `branch ... [pin] ... project  provider-icon` gets a compact PR token right after the branch: `⎇ EDDP-123-fix-x  #482 ✕`. Caption type (11 pt), monochrome SF Symbol, branch label truncates first (`layoutPriority`), the token never truncates. Glyphs, all static (no new animation, per DESIGN §4): passing = checkmark in secondary text (no green: DESIGN has exactly three status hues and 'never a false green' is easier when passing is neutral), failing = xmark in the existing failure red, pending = `circle.dotted` secondary, conflicts/blocked = triangle in attention orange, draft = dashed circle, merged = merge glyph, closed = neutral, unavailable = nothing on the card (reason in header/tooltip), stale-after-failed-refresh = dimmed. Tooltip: 'PR #482, 2 of 9 checks failing, mergeable state: blocked. Checked 14:32'. It rides on whatever cards the Active section already shows (working or unread), so a failing PR is visible there without changing Active membership.

HEADER (`SessionHeaderViews.swift`): a small 22 pt capsule next to the project chip: `#482 · 2 failing · checked 14:32`, clicking opens the PR URL in the default browser (validate https, NSWorkspace). It is the first item to drop when the row is narrow (the title already gives way first, D-53). If the PR head differs from the local tip: 'older commit'.

MENU: session context menu and header ⋯ get 'Open Pull Request', 'Refresh PR Status', 'Copy PR URL', and (until I-01) 'Copy Fix-CI Prompt'. After I-01: 'Fix CI', 'Create PR', 'Resolve conflicts' as drafted-not-submitted prompts, disabled with a reason while the session is Needs approval.

SETTINGS: Settings → General 'Show pull request status (uses the GitHub CLI)', default off, with one line that says whether gh was found and logged in ('gh not found', 'gh is not logged in: run gh auth login in a terminal'). Off means no process ever spawns.

## Principle check

RESOURCES: pass with the light design (event-driven, serial, one short child per refresh for live/selected sessions only, 15 s timeout, 1 MiB cap, no watcher, nothing when the window is hidden, nothing when the setting is off). RISK: the pending back-off is a timer; keep it capped at about 10 min, window-active only, cancelled on hide and settle, and present it to the user as an explicit exception. Principle violations would be: a repeating interval over all cards (Superset 10 s, Emdash 1 min, Supacode #830/#844), a FSEvents watcher per card, fetching for every loaded or ended card, retry loops after errors, or `gh pr checks --watch` as a long-lived child.
PREDICTABILITY: pass if the trigger list is fixed and documented (turn end, activation, first appearance of a live card, manual); risk if the back-off feels like magic, so label it ('pending, will recheck') and show 'checked <time>'.
ACCURATE STATUS: pass only with the discipline above: tri-state results, no-PR distinguished from gh-missing/not-logged-in/failed, empty rollup is not green, unknown enum is not green, UNKNOWN mergeability is 'checking', failed refresh keeps a dimmed stale value, merged/closed only from gh. Hard risk: promoting CI failure into the session's own status (indicator, pill, Dock badge, Cmd+J, menu bar, Active) conflates two meanings; kept out. A false green is the worst failure of this feature.
FLUENCY: pass; read-only, no confirmation, click opens the PR. Canned actions are one keystroke only after I-01; they should draft, not submit.
MODULARITY: pass; core fetcher/parser in LoomCore with no UI imports, cache/model beside `BranchCache`, views in LoomCatalogUI, forge gate pure and testable; a GitLab adapter would slot behind the same `PullRequestStatus` type.
CLI-UPDATE RESILIENCE: pass; uses only the user's installed gh and its documented `--json` fields and exit codes (0/1/4), no stderr text parsing, no GitHub API versioning, no tokens; drift becomes a journaled `cli_compat_warning` plus an 'output not understood' chip state, never a crash or a pin. It does not touch the Claude CLI at all (the I-24 route would).
OWNERSHIP: pass with a caveat; gh (and the git it may call) are short-lived children of the Loom app, started by Loom and killed by it on timeout, cancel and Quit, the same precedent as `ClaudePlanLimitsFetcher` (D-37), not run-scope members. They must be cancelled in `SessionRuntime.shutdown` so Quit stays clean. Spike: confirm no leftover child after a forced cancel.
USER AUTHORITY: pass; read-only chip, user's own gh login, the network call is to the user's own forge. Any prompt sent to a session must be user-initiated (and via I-01's gating); no auto-fix, no auto-merge, no cross-session send. Privacy: repo and branch names go to GitHub exactly as `git push` already does; default-off setting makes the new network behaviour opt-in.

## Value for the user (3/5)

It removes a real context switch at the end of every agentic task (push, PR, wait for CI) for GitHub repos, and fits the ticket-key workflow because branch and PR title carry EDDP-*, but it is only informational: Claude Code already shows its own PR badge in the terminal footer, the user types prompts fluently so canned actions save little ('fix CI' is a few words and the agent runs `gh pr checks` itself), and the research notes say the user's backend work flows through GitLab/IntelliJ review, which a gh chip does not cover (glab is not even installed here). Value is 3 if the work repos are on GitHub, about 2 if they are GitLab.

## Experiments before building

- gh contract spike (isolated scratch repo plus one read-only run by the user on a real repo, no Loom app needed): run the exact `gh pr list --head <branch> --state all --limit 1 --json ...` from a Loom-like minimal environment (PATH from the resolved ProviderToolchain, no TTY, GH_PROMPT_DISABLED=1). Decide: (a) exit codes and output for no PR (expect exit 0 and `[]`), logged out (expect exit 4), non-GitHub remote and no remote (expect exit 1), offline; (b) p50/p95 latency (adopt if p95 is under about 2 s; if much slower, lengthen the throttle); (c) that statusCheckRollup shapes (CheckRun vs StatusContext) all map to the classifier, including a repo with no checks; (d) mergeStateStatus right after a push (UNKNOWN flapping) so 'checking' is correct and the pending back-off covers it.
- Post-push timing spike: push a trivial commit to a scratch repo with a workflow and record what the rollup looks like at +0 s, +10 s, +30 s, +60 s (empty vs queued vs in_progress). Decides whether the 30/60/120 s back-off schedule and the 'waiting for checks to start' wording are right, or whether a different first delay is needed.
- Ownership and environment spike (dev build, isolated data root): spawn the fetcher from a LaunchServices-started Loom Dev (not from a terminal) to confirm gh is found via the resolved toolchain PATH, that a repo under ~/Documents does not raise an extra TCC prompt for the child, and that cancelling mid-run and Quit leave no gh/git child behind.
- Render-cost check using the existing counters: with 30 loaded cards, confirm the PR token adds no card body evaluations beyond the changed row (SidebarRenderProbe / CatalogHotPathTests pattern), i.e. PR updates patch one row via the same equality-guarded publish as `branches`.

## Questions for the user

- Where do the EDDP-* work repos live: GitHub or GitLab? This decides everything: GitHub means the gh chip is worth building; GitLab means either a second adapter (glab, not installed here), a link-out only, or skipping the idea.
- Should a failing CI ever alert you (a notification, or Needs-you), or is a red chip on the card enough? The recommendation is chip only, because session status means 'Claude is waiting for you'; a separate opt-in 'CI failed' notification could come later.
- Accept the single bounded exception to no-polling (re-check at 30 s, 60 s, 2 min, capped at about 10 minutes, only while the window is active and the session is live, selected or in a tab), or insist on strictly event-only with a manual refresh?
- Default off with a Settings switch (recommended, since it is Loom's first network-touching feature), or on whenever gh is found and logged in?
- Do you want canned Create PR / Fix CI / Resolve conflicts prompts at all, given you can type them quickly and the agent can run gh itself? If yes: editable templates, drafted but not submitted, and only after the I-01 send primitive exists.
- Should the chip show on every card or only on live, selected and Active cards (recommended, to keep gh calls proportional to the sessions you are actually working with)?
