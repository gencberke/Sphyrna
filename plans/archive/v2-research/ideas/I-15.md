# I-15: Answer approvals from Loom's own surfaces via the documented hook decision

Card from the [Loom v2 idea catalog](../IDEAS.md). **Answer approvals from Loom's own surfaces via the documented hook decision** · verdict **spike-first** · cost M · value 3/5 · proposed by 6 reports: [cmux](../products/cmux.md), [attention-surfaces](../products/attention-surfaces.md), [happy](../products/happy.md), [codex-app](../products/codex-app.md), [chat-ui-paths](../products/chat-ui-paths.md), [power-user-workflows](../products/power-user-workflows.md).

> Loom is already 80% wired for it (per-session `--settings` PermissionRequest hook, authenticated sockets, a Codex-era approval box), but the one fact that decides safety (does the CLI dialog wait for or race the hook, and does a terminal answer cancel it) is unmeasured, so run a half-day hook-race spike, then build a small first slice (box + banner buttons + menu rows, no hotkey, no Always/Bypass).

## What the user gets

Allow / Deny (and later pick-an-option) directly from the approval box, the menu-bar popover, the notification buttons or a hotkey, without switching to the session: one fewer context switch per approval with 3-6 parallel sessions. Verified outcome = the CLI continues.

## Mechanisms found in the research

[Documented] A per-session PermissionRequest hook injected with `claude --settings <inline JSON>` (or the existing Loom plugin), never the user's global settings.json, blocking on Loom's authenticated socket; the approval box, popover and notification resolve the same (session id, request id, kind); stale actions are discarded and logged; fail open if Loom is gone; advisory soft-wait (cmux 120 s) then hand back to the CLI prompt with a visible 'handed back' state; cancel the card on PostToolUse/Stop/SessionEnd/PID exit (kernel process-exit events, no polling). Keep 'Always' and 'Bypass' out of banners; notification actions = UNNotificationAction (banner must be expanded; Focus modes delay) and an optional Carbon global hotkey bound to the single visible request. Enter/Esc keyboard approve/decline on a focused box plus a per-turn approvals counter (Codex) to hint when to change permission mode. Do not answer by injecting keystrokes (fragile, layout-dependent).

## Debates and fact-check corrections

Unverified for interactive sessions: whether the TUI dialog and the hook race or the hook runs first, and whether answering in the terminal cancels the pending hook (one Vibe Island report says it does not, but the reporter also blamed the app's own self-healing; chat-ui-paths lists it as open question #3, decisive for safety). Hook timeouts differ (command/http/mcp_tool default 600 s, UserPromptSubmit 30 s, SessionEnd 1.5 s). Auto mode is now the starting permission mode for interactive sessions (2.1.283+), so approvals are rarer than the '93% rubber-stamped' framing suggests: re-weigh the value. CodeIsland idled about 5.3% CPU even after gating its animations, and Open Island #377 (kernel exit) and #517 are unmerged proposals. Channels (research preview) permission relay is the cleanest future input path to watch.

## Design in Loom

OBSERVED STARTING POINT. (1) ProviderLaunchProfile.claudeSettings already injects a per-session inline `--settings` JSON whose hooks include PermissionRequest, but as a fire-and-forget `loom-hook` command with `timeout: 1` and the comment "helpers return no provider decision"; nothing goes to the user's settings.json (contract section 9 says the same). (2) ClaudeHookServer is one-shot: it reads one message under a 1 s deadline, closes, and never answers, so the decision channel cannot reuse it. (3) The control socket (OpenSessionControlServer, `c-<8>.sock`, same token, LocalSocket, up to 32 held connections, `Task.detached` handler, `finish()` replies on the held connection) is the existing request/response-with-hold pattern, built for D-40. (4) A provider-approval box already exists: `ProviderUserRequest` (id, kind, summary, failure, isAnswerable) published via `SessionEventHub.Change.userRequests`, reset on runStarted/runEnded, drawn by `RequestList` in DetailView (Approve/Deny, `returnApproves:false` over a live terminal so Return stays with the CLI), answered through `CatalogModel.answerRequest` to `intents.answer`. Today only the Codex path fills it (SessionRuntime+Codex.publishRequests); Claude's Needs approval is a state with no card, banner text "Claude is waiting for your approval." with click-to-jump only (ApprovalNotifier, UserNotificationService: no actions), and the subagent panel says "answer it in the session's terminal" (SubagentApprovalNotice). (5) Answered-in-terminal is already detectable without polling: ClaudeRegistryReader watches the registry file (status idle/busy/waiting) and ClaudeHookStateTracker returns from Needs approval on the next registry sample.

DESIGN (lightest). (a) Wire: add a `decide` mode to loom-hook, selected by the payload's hook_event_name == PermissionRequest (no new argument needed; the existing entry stays one entry, its `timeout` raised from 1 to about 125 s). The helper first sends the normal state envelope on the hook socket exactly as today (so status/identity ordering is unchanged), then opens a framed request on the control socket (length-prefixed or newline frame, NOT half-close, so EOF means the helper died) carrying token, session id, run id, the payload (tool_name, tool_input, permission_suggestions, agent_id, cwd) capped at 64 KiB, and waits. Every failure path (no socket, refused, token rejected, cap exceeded, timeout, Loom quit, unknown reply) exits 0 with empty stdout = CLI prompt untouched (fail open; never exit 2 and never allow by default). A reply `allow` prints `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}` with no updatedInput and no updatedPermissions; `deny` prints behavior deny with message "Denied from Loom" and interrupt false; `pass` prints nothing. (b) Loom side: a `ClaudeApprovalCoordinator` actor beside OpenSessionCoordinator: authorize (live run, launch card == LOOM_SESSION_ID, as OpenSessionCoordinator does), assign a Loom request id per connection (PermissionRequest has no tool_use_id, so never hash input), keep an in-memory per-session queue (cap about 8; overflow answered `pass` at once), publish `.userRequests` with a richer summary (tool, full command or file path plus old/new text). Tool names AskUserQuestion and ExitPlanMode are answered `pass` immediately (an allow without answers would break them; they belong to separate ideas). A DispatchSourceRead on each held connection reports helper death. (c) Cancel/hand-back triggers, all event-driven: registry sample waiting->busy/idle, Stop, SessionEnd, StopFailure, runEnded/runDetached (leader exit is already tracked by ProcessSupervisor), Loom quit (reply `unavailable`), and one one-shot Task.sleep soft-wait (about 120 s, below the 600 s default) that exists only while a request is pending and hands back with a visible `handed back to the terminal` state. Timeouts hand back, never decide. (d) Surfaces all resolve the same (session id, request id, kind): RequestList box (extend `answerRequest` to route Claude vs Codex); ApprovalNotifier posts one banner per request (identifier = request id) with a UNNotificationCategory of Allow and Deny actions (no `.foreground`, no Always, no Bypass), the delegate calls the model with the ids; MenuBarController rows get an Allow/Deny submenu (the NSMenu is rebuilt on open, so it never shows stale rows). A stale or unknown id is discarded and logged once (LoomLog ClaudeHooks category), never applied to the head of a queue. (e) Verified outcome has two honest stages: `sent to the CLI` (helper reports it wrote the decision and exited) and `continued` (registry busy or a later hook event); if the second does not arrive the card says so rather than claiming success. (f) Smart hold policy chosen after the spike: if the dialog is NOT gated by the hook, always hold; if it is gated, hold only when the user is not looking at that session's live terminal (app inactive or another session selected) and release on focus, because a gated dialog would otherwise be delayed by the hold. (g) Safety: the preview is bounded plain text and never silently truncated; if the command or diff exceeds the cap, Allow is disabled (Deny and Open session remain). Hook allow cannot override deny rules and updatedInput is not used, so Loom cannot widen what the CLI would allow. Per-session scope also means subagent requests (agent_id present) become answerable from the same card, which today is impossible without leaving the transcript panel. (h) Skip in v1: Carbon hotkey, Enter/Esc beyond the focused box (keep `returnApproves:false` over a live terminal), the Codex per-turn approvals counter, Always-allow (later: only the CLI-suggested session-scoped entry), AskUserQuestion and plan cards. Tests: reuse loom-fake-provider/loom-test-child to emit PermissionRequest and hold; contract tests from payloads captured from a live CLI; coordinator tests for stale id, cancel races, overflow, quit.

## Where it shows

Detail pane: above the live terminal (same slot as RequestList), a callout card "Bash wants to run" with the full command in a monospaced selectable block (or Edit as old/new lines), a source line (session, subagent name if any), and Deny / Allow buttons (neither is the Return default over a terminal). A "+2 more" line when several are queued. After a decision the card turns into a one-line status: "Sent, waiting for Claude to continue", then disappears on continue; or "Handed back to the terminal" when the soft-wait expired or the terminal answered first. Sidebar card keeps the existing Needs approval pill; its second line can show the tool name (shares work with the card-line idea). Notification banner: title = session, body = tool plus first line of the command, buttons Allow and Deny (visible on hover or expansion; with Alerts style always visible). Menu bar menu: a Needs you row with approval gets a submenu Allow / Deny / Show Session. No popover, no notch overlay, no always-on window; nothing is drawn when hidden.

## Principle check

Resources: pass. Event-driven only (socket reads, registry vnode samples that already exist, kernel-tracked leader exit, one one-shot sleep per pending request); no polling, no new visible window, no animation; one helper process per pending request, and Loom already spawns one per PermissionRequest today, now held longer; held sockets cost a file descriptor, not a thread (hard cap 32 in flight, per-session cap about 8). Risk: CodeIsland still idles at about 5.3% CPU, but that is its notch overlay, which this design does not have. Predictability: risk until the spike, because raising the hook timeout from 1 s to about 125 s changes worst-case behaviour if the CLI gates its dialog on hooks; the spike and the smart-hold policy bound it. Accurate status: pass if two-stage outcome is kept (`sent` versus `continued`), cards removed on registry/Stop/SessionEnd/run end, `handed back` shown rather than silent loss, and stale ids discarded and logged; the failure to avoid is the CodeIsland 308 bug (answering the head of the queue) and reporting Allowed because a button was pressed. Fluency: pass, one fewer window switch per approval; Allow stays disabled on a truncated preview, a small intentional friction. Modularity: pass; one coordinator plus one protocol file, reuse of ProviderUserRequest/RequestList/answerRequest, no TerminalSurface or renderer change. CLI-update resilience: acceptable but is the biggest ongoing cost; PermissionRequest decision control is documented (hooks reference, v2.1.300 checked), `--settings` is already used and drift-checked, but the interactive ordering semantics are not documented, so ship a captured-payload contract test, a drift journal entry if the helper sees an unexpected payload shape, and fail open on anything unknown. Never pin. Ownership: pass, per-session scope, no global settings.json writes (counter-example: Vibe Island hook self-healing, #245), fully owned by the run scope; Quit answers every waiting helper and drops requests (memory only, like open requests). User authority: pass only because every decision is the user's own click on a visible, session-labelled card; no automatic allow, no timeout-allow, no agent-to-agent answers (contract section 7 forbids an agent message answering another session's approval; this path has no such route). Contract: the terminal stays the real CLI; no keystroke injection; no CUI replacement; but "multiple approvals not explained to the user" (section 9) means the settings text must say that Loom can answer from banners. Conflicts with a user's own PermissionRequest hook run in parallel and first decision wins; document it.

## Value for the user (3/5)

Real but frequency-bound: auto mode is the starting mode from 2.1.283 (installed CLI is 2.1.300), so the prompts that remain are the risky or unusual ones, where blind one-click approval is least wise, and the 93% rubber-stamp figure describes the older default. It pays most for this user because of parallel sessions and many subagents (a subagent prompt today forces leaving the transcript panel to answer in the terminal), and approvals while Loom is in the background. The cheaper stage 0, putting the tool and command from the payload Loom already receives into the banner body and card line (no hook blocking, no race risk), captures much of the benefit and should ship regardless.

## Experiments before building

- E1 hook/dialog race (S, half day, decisive). Use the isolated profile CLAUDE_CONFIG_DIR=~/Library/Application Support/Loom-Dev/probe/claude-config (never the real ~/.claude), an interactive claude 2.1.300 in a PTY harness, and a plain shell-script PermissionRequest hook passed via inline --settings (not Loom). Matrix: (1) hook sleeps 30 s and prints nothing: does the TUI dialog render at once or only after the hook returns? (2) answer in the TUI at 5 s: is the hook process killed, does it linger, does its late output get ignored, does the next tool call behave normally? (3) hook prints allow at 5 s while the dialog is up: does the dialog dismiss and the tool run with no extra keypress? (4) hook prints deny with message, and exit 2 without a decision. (5) two parallel tool calls and one queued dialog: do hooks fire together or one by one? (6) a subagent's request (agent_id present) answered by the hook. (7) registry file status values during the wait and after an answer (is waiting/busy transition reliable enough to verify the outcome and cancel the card). (8) the user's own PermissionRequest hook in the profile alongside the --settings one. (9) a sandboxed Bash command and an MCP tool that requires user interaction (documented as not hookable). Decide: dialog immediate and decision cleanly dismisses it and a terminal answer is harmless -> build with always-hold; dialog gated by the hook -> build only with hold-when-away, short soft-wait, release-on-focus, or skip; decision does not dismiss the dialog or leaves it needing another key -> skip this idea and wait for Channels. Save captured payloads as the contract-test fixtures.
- E2 macOS 27 notification actions (S, dev app only with the dev bundle id): do Allow/Deny buttons appear for a banner without expansion, how do Alerts versus Banners style and Focus modes change delivery, does the action run while Loom is in the background, and does removeDeliveredNotifications remove a banner already expanded. Decides whether banner buttons are a primary or a secondary surface.
- E3 cost check with loom-fake-provider (optional): 8 held requests across 4 sessions, confirm CPU is flat and fds/helpers return to baseline after hand-back, Quit, and killing the CLI mid-wait.

## Questions for the user

- How often do you actually see permission prompts today (auto mode, manual, or bypass)? If rarely, stage 0 only (context in the banner) may be enough.
- Is one-click Allow from a banner acceptable, given a small preview, or should banners offer only Deny and Open, with Allow only in the in-app card where the full command is visible?
- Soft-wait length before handing back to the terminal: about 120 s (cmux), or shorter, for example 45 to 60 s?
- Allow raising the PermissionRequest hook timeout from 1 s to about 125 s and recording that the hook now returns a decision (DECISIONS.md amendment)?
- Do you want 'Always allow for this session' in the card (CLI-suggested, session-scoped only), or none in v1?
- Global hotkey: wanted, or is Cmd+J plus the box enough?
