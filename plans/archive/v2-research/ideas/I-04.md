# I-04: Input fidelity audit (image paste, drag-drop paths, dictation)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Input fidelity audit (image paste, drag-drop paths, dictation)** · verdict **adopt-light** · cost S · value 3/5 · proposed by 2 reports: [power-user-workflows](../products/power-user-workflows.md), [warp](../products/warp.md).

> Most of this is already built (Ctrl+V on an image-only clipboard, quoted-path drops via bracketed paste, a text-input client for dictation), so adopt only a one-time hands-on checklist plus the small fixes it finds, and treat /voice microphone attribution as the one real unknown.

## What the user gets

Invisible correctness work: screenshots and files dropped or pasted into a Loom terminal reach Claude correctly; macOS system dictation works in the terminal and composer; no voice stack needed.

## Mechanisms found in the research

Audit-only first: check image paste, Finder drag-drop path quoting, dictation insertion and large-paste behaviour in the SwiftTerm view. System dictation instead of a hosted voice dependency (Happy's voice agent costs about $0.01/min via ElevenLabs and a hosted dependency).

## Debates and fact-check corrections

Low controversy. Whether Loom already handles all of it is unknown (reports did not read Loom code); treat as a check, not a build.

## Design in Loom

OBSERVED STATE (code, not inference). The audit is not a blank slate; Loom already has the three mechanisms, in LoomTerminalView (Sources/LoomTerminal/TerminalSurface.swift, ~L362-452):
1) Image paste: `paste(_:)` checks `NSPasteboard.general`; if there is no `.string` and `canReadObject(forClasses:[NSImage.self])`, it does `send(data:[0x16])` (Ctrl+V), else falls to SwiftTerm `super.paste`. Claude Code's documented image-paste binding is Ctrl+V on macOS (Cmd+V only in iTerm2), so Loom matches the docs. Menu path: Edit > Paste uses `NSText.paste(_:)` (AppDelegate.swift:702), which reaches the first responder.
2) Drag-drop: `registerForDraggedTypes([.fileURL])` (TerminalSurface.init, L168), `draggingEntered` accepts only when file URLs exist, `performDragOperation` -> `insertDroppedFiles` -> `quotedPaths` (POSIX single-quote quoting, control bytes escaped) -> `pasteText` (bracketed paste when the app enabled ?2004h, no Enter). Pinned by `Tests/LoomTerminalTests/TerminalSurfaceTests.swift` `finderDropUsesBracketedPasteQueueWithoutEnter` and `TerminalProductTests.multipleDroppedPathsAreShellQuotedWithoutEnter`. Documented in design/UI-MAP.md:77 and docs/ARCHITECTURE.md:39.
3) Dictation: the vendored SwiftTerm TerminalView conforms to NSTextInputClient (Vendor/SwiftTerm/Sources/SwiftTerm/Mac/MacTerminalView.swift: insertText L2447, setMarkedText L2557 with a marked-text overlay whose comment names "dictation hypotheses", hasMarkedText/selectedRange/firstRect L3128-3200, `extension TerminalView: NSTextInputClient`). So system dictation (Fn-Fn) and third-party dictation that inserts through the input system should land as committed text via the same path as typing. Not yet confirmed on screen in Loom.
4) Large paste: `pasteText` goes through the single ordered TerminalInputQueue (LoomCore/TerminalInputQueue.swift) capped at `TerminalSurfaceLimits.pendingInputBytes` = 4 MiB, with visible `onInputError` on overflow (never silent loss).
WHAT IS GENUINELY UNVERIFIED (this is the audit's real content):
a) Mixed clipboards: a Finder-copied image file or a browser/Preview "Copy Image" carries a string flavour (filename or URL) next to the image, so `pasteboard.string(forType:.string) == nil` is false and Loom pastes text, not Ctrl+V. Whether Claude Code would have accepted the image in that case is the test. If yes and it matters, widen the rule to "has image data and the string is only a filename or URL" (a few lines in `paste`).
b) Image-file paths: Claude Code recognises a pasted image path as an attachment; whether it does so for Loom's single-quoted form (vs backslash-escaped, Terminal.app style) is untested. If not, change `quotedPaths` to the CLI's preferred escaping for Claude sessions only (a one-function change, existing test updated).
c) Non-file drags (browser image drag, Mail attachment promises) are refused (`draggingEntered` returns []), so the drop bounces. Fixing this means writing temp files, which is a new feature with cleanup and ownership cost; recommend NOT doing it, only documenting it.
d) /voice (documented: hold/tap Space after enabling; native mic capture by the claude process). Neither Info.plist from scripts/package-dev-app.sh (app L107-126, LoomRunHost.app L86-100, LSBackgroundOnly) has NSMicrophoneUsageDescription, and a grep finds no microphone or entitlement strings anywhere in Sources/scripts. The claude process runs as a descendant of the bundled LoomRunHost.app inside Loom's run scope, so which bundle TCC treats as responsible for the microphone request, and whether the missing usage string makes the prompt fail silently, is unknown. This is the only item that could need a packaging change (add NSMicrophoneUsageDescription to one or both plists; maybe the audio-input entitlement under hardened runtime, `--options runtime` is used at package-dev-app.sh:130-143).
DESIGN: no new runtime component. Deliverable = (i) a short manual checklist (screenshot Cmd+Ctrl+Shift+4 then Cmd+V; Finder copy of a PNG then Cmd+V; drag a file with spaces/apostrophes/Turkish characters; drag a screenshot thumbnail; 200 KB and 3 MB text paste; Fn-Fn dictation including a Turkish phrase; /voice) recorded as an evidence note, run once per Claude Code minor release only if drift is suspected; (ii) only the fixes (a), (b), (d) the checklist proves necessary; (iii) one regression test per fix in the existing LoomTerminalTests suites (the test harness already injects bytes and hashes the child's input, so fidelity is checkable without UI). Triggers: user events only (paste, drop, key); no polling, no new watchers, nothing drawn or kept when hidden. Bounds: unchanged 4 MiB input queue, visible error on overflow. 'Verified' status: do not add 'image attached' indicators; Claude Code's own [Image #N] chip is the receipt, Loom claims nothing.
PRINCIPLE VIOLATIONS TO AVOID: a Loom-side image/clipboard watcher or thumbnail strip (resource use, duplicate of the CLI chip); temp-file creation for non-file drags (ownership, cleanup, deletion dry-run scope); an embedded voice/ASR stack or hosted dependency (Happy's voice agent at ~$0.01/min via ElevenLabs is exactly what to avoid); pinning behaviour to one CLI version (keep keystroke Ctrl+V, which is the documented binding, and verify by hands-on check instead of a version table).

## Where it shows

None. No new UI. At most, if /voice needs a plist change, one line in docs/Help or Settings notes that microphone access is granted to Loom (macOS shows its own system prompt). Dictation and paste keep looking like typing in the terminal; Claude Code's own [Image #N] chip is the only feedback.

## Principle check

resources: pass (zero new runtime cost, event-driven only). predictability: pass, the rules are already deterministic and pinned by tests; risk only if the mixed-clipboard rule gets clever. accurate status: pass, Loom claims nothing about attachment; the CLI chip is the receipt. fluency: pass, this removes friction (silent text paste instead of image). modularity: pass, all changes stay inside LoomTerminalView/quotedPaths and, if needed, two plist templates in package-dev-app.sh. CLI-update resilience: pass with care; relies on the documented Ctrl+V binding, no version pins; risk that Claude Code changes the image-paste key or path-detection, so the checklist (not a table) is the guard. ownership: pass; no new processes or files; temp-file drag support would break this, so excluded. user authority: pass; nothing cross-session. Contract: terminal remains the real CLI; no custom composer.

## Value for the user (3/5)

Screenshots into Claude are a daily habit for a heavy agentic developer (UI bugs, error dialogs, ticket screenshots), so a silent text-instead-of-image failure would be costly, but the common case (image-only screenshot clipboard, Finder drag) is already handled and tested; the remaining payoff is edge cases plus a possible /voice unlock, and the user's notes mention neither voice nor image paste as a wish. Value is correctness insurance, not a new capability.

## Experiments before building

- Hands-on checklist on an isolated dev build (isolated CLAUDE_CONFIG_DIR, not the daily Loom.app, run only when the user says the computer is idle): (1) screenshot to clipboard then Cmd+V gives [Image #1] in Claude Code; decides whether the existing 0x16 rule works end to end. (2) Finder Cmd+C on a PNG, and Safari/Preview 'Copy Image', then Cmd+V; decides whether the string-nil condition in LoomTerminalView.paste must be widened.
- Drag a PNG, a file with spaces/apostrophes/Turkish characters, and a screenshot thumbnail into the terminal; check whether Claude Code attaches the image from the single-quoted bracketed paste; decides whether quotedPaths needs the backslash-escaped form for Claude sessions.
- Fn-Fn system dictation in an idle Claude prompt (English and Turkish), watching the marked-text overlay then commit; decides whether SwiftTerm's NSTextInputClient is enough (expected yes) or needs a patch under patches/.
- /voice in a Loom Claude session on a throwaway config dir: does macOS show a microphone prompt, and for which app name (Loom vs Loom Run Host), or does capture fail silently; decides whether to add NSMicrophoneUsageDescription (and possibly the audio-input entitlement) to the app and/or LoomRunHost.app Info.plist in scripts/package-dev-app.sh. Also confirm /voice exists and is enabled on the installed CLI (claude 2.1.300 here; --help does not list it).
- Large paste: 3 MB text paste into an idle session; confirm no UI stall and that overflow past the 4 MiB queue shows the visible input error (existing behaviour, only a confirmation).

## Questions for the user

- Is /voice something you would actually use (Turkish speech?), or is macOS system dictation (Fn-Fn) enough? That decides whether microphone attribution in the run scope is worth any packaging change.
- If a browser-image or Mail-attachment drag is refused today, do you accept 'documented, not supported' rather than Loom writing temp files for it?
- May the checklist run on the dev build when you next say the machine is idle (it needs a GUI, a real clipboard and a microphone)?
