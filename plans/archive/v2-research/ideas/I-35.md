# I-35: Extend 'a session opens a session' (parent/child, batch fan-out, narrow always-allow, ceilings)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Extend 'a session opens a session' (parent/child, batch fan-out, narrow always-allow, ceilings)** · verdict **adopt-light** · cost M · value 3/5 · proposed by 5 reports: [paseo](../products/paseo.md), [vibe-kanban](../products/vibe-kanban.md), [supacode](../products/supacode.md), [t3code](../products/t3code.md), [openchamber](../products/openchamber.md).

> Adopt a smaller version (a click-through roll-up row of opened sessions under the parent card, a capped batch open with one approval, and a deny cool-down); put per-project always-allow, the permission ceiling and the worktree field behind a spike or later, because they are the only parts that widen standing authority and need CLI facts Loom does not read today.

## What the user gets

The shipped open-session flow becomes legible and quicker: the opened session nests under its parent with one 'child finished / needs you' signal on the parent card; an agent can propose several sessions and the user approves them in one sheet; trusted cases ask once per project; results return to the asking agent as session id + verified outcome.

## Mechanisms found in the research

Parent link + nesting; a single UI event on the parent card (never a prompt injected into the parent's PTY); detach and cascade-stop only as explicit gestures (Paseo cascades archive by default; do not copy); batch sheet with a cap and cost note; literal-action confirmation and a revocable per-project + action-type 'always allow' (never for delete or send-to-session unless opted in); a child may not get a broader permission mode than its caller (T3 ceiling); optional worktree field; rate-limited prompts and de-duplication by ticket key.

## Debates and fact-check corrections

Supacode's 'Always allow' flips a GLOBAL automatedActionPolicy to .always (all CLI/deeplink actions incl. destructive), so Loom's narrow scope is a deliberate improvement, not a Supacode feature; its socket auth is only 0700 permissions (Loom's authenticated socket is stronger). OpenChamber's agent tool is on by default with no per-action approval (do not copy); Vibe Kanban's MCP has no approval step. Stale parent links after deletion; orphan handling.

## Design in Loom

WHAT ALREADY SHIPS (so I-35 is smaller than it reads): sessions.opened_by and ticket_key exist in the catalog (CatalogDatabase.ensureOriginColumns; SessionRuntime.startConversation(opening:) -> ProcessSupervisor.createSession(openedBy:)). The card shows 'from <requester>' (SessionOrigin in OpenRequestDisplay.swift; CatalogModel.origin(of:), ensureOrigins/pruneOrigins; stale or deleted parent reads 'another session' via missingOrigins) and the detail view has an 'Opened by' fact (DetailView.swift:403). The approval box is already literal (project, title, ticket, 4-line message preview plus full text; OpenRequestBoxContent) and neither button is the default so Return stays with the terminal. The requester's card already goes to 'Needs approval' through awaitingOpenApproval (CatalogModel.setOpenRequests -> SessionIndicator), so it feeds Active, Dock badge, menu bar and Cmd+J. Ticket de-duplication, one waiting request per requester, a 32 waiting cap, and a 64 entry cap are in OpenSessionCoordinator. The agent already gets 'started <id> "<title>"', 'exists', 'denied', 'pending' or 'error' (OpenSessionReply.line). Starting only reports started after launchClaude succeeds, so 'session id + verified outcome' is already true for one session.

PIECE 1 - PARENT ROLL-UP (the 'nesting' + 'one signal'). Do NOT re-parent cards in the list: the activity view is day-grouped with an Active section and paged, and a child may sit in another project (--project), so a real tree would break ordering and paging. Instead add a reference row under the parent card in the exact slot where SessionListEntry (SidebarView.swift ~line 375) already draws SubagentTreeView: a pure value 'OpenedSessionsContent' modelled on SubagentTreeContent (max 3 rows, '+N more', rows = child title + SessionIndicator label, click = select child). The child keeps its own normal card. The parent's own indicator is NOT changed by a child (accurate status: the parent is not 'Needs approval' because a child is). Data: one new catalog read 'children(of: [UUID])' (SELECT ... WHERE opened_by IN (...), chunked, bounded) run when a list reload loads rows, kept in a CatalogModel map next to origins (new file CatalogModel+OpenedSessions.swift, not CatalogModel.swift which is already 1612 lines), plus a partial index CREATE INDEX IF NOT EXISTS sessions_opened_by ON sessions(opened_by) WHERE opened_by IS NOT NULL added the same additive way as the other columns (no user_version bump; older builds ignore it). Child state comes from liveStates/rowModels that the hub already delivers; no new hook, timer or event. The only live observation is up to 3 child row models per visible parent. Distinguish Finished (unviewedCompletion), Needs approval/Waiting, Failed, Stopped/Ended (Paseo's 0.12 changelog fixed 'parent told finished when child was merely stopped'; Loom's SessionIndicator already separates these, so reuse it). Deleted child: absent from the query. Deleted parent: children keep the existing 'another session' origin; the roll-up simply has no card to sit under. /clear: requesterID is the card the run is on at ask time, so the link follows that card (documented limitation). Optional explicit gestures only: context-menu 'Stop opened sessions (N)...' that loops the existing verified stop per child with a count confirmation; 'Remove link' sets opened_by NULL. No cascade by default, no cascade on Stop of the parent, no cascade on delete (contract §8/§234: deleting a chat is not a side effect on others).

PIECE 2 - BATCH OPEN. The single-request protocol cannot just be called N times: the agent's calls are sequential and each blocks up to 85 s, then gets 'pending - do not ask again' (OpenSessionLimits.serverReplyDelay), and the coordinator rejects a second undecided request from the same requester. So add one batch call: '"$LOOM_CLI" open-batch --file plan.json' where plan.json is a JSON array of {title, ticket?, message|messageFile} (OpenSessionCommand parse; OpenSessionInput.validated per item). Wire: optional 'items' array on OpenSessionWireRequest (decodeIfPresent; loom-hook and the app are one bundle, so there is no CLI-version skew on this socket; keep protocolVersion handling). Caps: at most 5 items (constant OpenSessionLimits.maximumBatch), per-item rules unchanged (64 KiB), wireByteLimit raised to ~1 MiB, duplicate ticket keys inside a batch rejected, items whose ticket already has a session answered 'exists' at submit and not shown for approval. Coordinator: a batch is one Entry holding N request items that share a batch id and one waiter; the UI shows one sheet/box in the requester's detail pane listing every item literally (project, title, ticket, message preview each expandable) with per-item Skip and two buttons 'Open N sessions' / 'Deny all', plus a cost note: 'N more live Claude sessions will start (M are running now)' - a count only, no invented RAM figure. Approval must start items strictly one after another (startConversation guards (provider, project) with startingNew -> alreadyStarting, and each start needs its own TerminalSurface from ConversationController.approveOpen), and each item reports its own outcome. Reply is one line per item in order ('started <id> "<title>"', 'exists ...', 'skipped', 'error: ...'); exit 0 only when every non-skipped item started or exists, 1 otherwise. Partial failure is reported per item and never retried (contract §7: no blind retry). If the 85 s wait lapses first the agent gets one 'pending' and learns no ids - state this plainly in the skill text; see experiment 2 for lifting the wait. Update ClaudeLoomPlugin.skill (it is written from source into <data root>/claude-plugin, so it follows the app version) and the OpenRequestEvidence rows.

PIECE 3 - RATE LIMIT. In-memory per requester: after a Deny (or 3 requests in 10 min), the coordinator answers 'denied: the user declined recently, do not ask again' without drawing a new box for a cool-down; the box count and 32-waiting cap stay as the hard bound. No persistence, no timer: the cool-down is a timestamp compared on the next submit.

DEFERRED PIECE 4 - ALWAYS-ALLOW + CEILING (spike-first, ship only together). A pure LoomCore struct OpenSessionPolicy (project id + action 'open') stored in Loom's own preferences/app_state (never in ~/.claude), evaluated event-driven in CatalogModel.setOpenRequests when a request arrives (the UI layer must call approveOpenRequest because the start needs a TerminalSurface), listed and revocable in Settings, with a per-start 'auto-approved' mark in the child's Opened-by fact. Hard limits if built: same project as the requester only (--project elsewhere always asks), only requests whose requester was not itself auto-opened (depth 1, because every session has $LOOM_CLI and a chain would otherwise self-propagate, contract §7 'a chain beyond the user's task is not authorized'), at most 3 auto-opens per requester per 10 min, a global live-session cap, never batches, never delete/send-to-session. Ceiling: Loom passes no --permission-mode today (ProviderLaunchProfile.claude builds only --session-id/--resume, effort, --settings with hooks and crossSessionInbound:refuse, --plugin-dir, -n and the prompt), so a child silently gets the user's settings default, which can be broader than a caller the user toggled to plan mode. To enforce 'child <= caller' Loom would parse the documented common hook field permission_mode (ClaudeHookEvent in ClaudeHook.swift currently ignores it), keep the latest value per run in ClaudeHookStateTracker, and launch the child with the documented --permission-mode <same>. If the value is unknown/unmappable or --permission-mode is missing from claude --help (same pattern as ProviderLaunchProfile.missingRequiredClaudeOptions), always-allow is simply unavailable and the box asks as today.

DEFERRED PIECE 5 - WORKTREE FIELD. Loom has no worktree code at all (grep: only cleanup-planner mentions); the field belongs to the separate 'new session in worktree' idea. Do not couple it here.

WHAT THE IDEA TEXT CLAIMS BUT ALREADY EXISTS OR BELONGS ELSEWHERE: 'results return as session id + verified outcome' exists for one session; 'child finished' as a return value to the agent (wait verb) is the separate read-only orchestration idea (T3) and must be event-driven from hook transitions, not polled.

## Where it shows

Sidebar: the parent's card is unchanged. Directly under it (same guide-line style as the subagent tree, same slot in SessionListEntry) a small block: '↳ EDDP-412 migration   Working', '↳ EDDP-413 api   Finished', '↳ +2 more'. Row text uses the existing state words and colours; a row that needs the user uses the same attention dot, so the parent shows ONE glance 'a child needs you' without its own state lying. Click a row = select that child session. Project view: same row. Context menu on the parent adds 'Stop opened sessions (3)...' (confirm with the count; explicit, never automatic).
Detail pane of the asking session: when the agent calls open-batch, one amber callout box (same style as OpenRequestBox) titled 'Open 4 new sessions?' with a list of rows (checkbox, project, title, ticket, first lines of the message, 'Show full message'), a footnote 'This starts 4 more live Claude sessions (2 running now). Nothing starts until you press Open.', buttons Deny all / Open 4 sessions (neither is the default key). While starting each row shows Opening..., then Opened / Failed: <text> / Skipped, and the finished box stays until dismissed like failed requests today. Settings (only if piece 4 ships): Automation list 'Always open without asking in: <project> [Revoke]'.

## Principle check

Resources: PASS for pieces 1-3 - no timer, no polling, no new hook events; one bounded catalog read per list reload and at most 3 child observations per visible parent; the batch cost is N real live CLIs, so it is capped (5) and the live count is shown; nothing is drawn when the window is hidden because the roll-up is ordinary sidebar content. The CPU gate is unaffected (no PTY output path touched), though a 5-session start burst should be measured once on an idle machine. RISK: unbounded child lookup (avoid by chunked IN with a cap) and reading child state for off-screen parents (avoid: only visible entries observe).
Predictability: PASS if the batch box shows every item literally and nothing starts without the press; RISK: a batch approved as a blob hides what each session will be told - hence per-item preview and Skip, cap 5, no always-allow on batches.
Accurate status: PASS - per-item verified outcomes (started only after launchClaude succeeds, 'exists' never counted as started), partial failure per item, no retry, parent never inherits a child's state, stopped is not finished. RISK: the 85 s reply window (an approval after it leaves the agent with only 'pending'); the skill must say so and experiment 2 may remove it. RISK: roll-up uses opened_by which is attribution not liveness - a child whose parent card was /cleared points at the old card.
Fluency: PASS - one approval instead of N, one-click jump to a child, no prompt injected into the parent's PTY. RISK: approval still lives in the requester's detail pane (the user must go there; Cmd+J and the Needs-approval indicator already lead there).
Modularity: PASS - batch grouping in the coordinator, roll-up as a pure content struct plus new extension file, policy as a pure LoomCore struct; LoomCore stays UI-free and nothing moves up the dependency graph.
CLI-update resilience: PASS for 1-3 (only Loom's own socket, command and skill; the plugin is a documented --plugin-dir mechanism written from app source). Piece 4 RISK: depends on the documented permission_mode hook field and --permission-mode choices (help lists acceptEdits, auto, bypassPermissions, manual, dontAsk, plan, which are not guaranteed to equal the hook's strings, e.g. 'default' vs 'manual'); designed to disable itself on drift, never to pin.
Ownership: PASS - children are ordinary Loom-started runs in their own run scopes; cascade-stop is a loop of the existing verified stop per child and only as an explicit gesture; no process is ever started or stopped by the link itself.
User authority: PASS for 1-3 (approval per request or per batch, as D-40 and contract §7 require). Piece 4 is a standing authorization that amends D-40 ('starts only after the user approves') and §7, and a prompt-injected parent could use it to start an agent with an arbitrary first message with no human gate; Supacode's 'Always allow' is global and unscoped (fact-check), OpenChamber's tool is on by default with no per-action approval (partly: OpenCode's own tool permissions still apply), Vibe Kanban's MCP has no approval step - none of that may be copied. Paseo's default cascade-archive of children is likewise not copied.

## Value for the user (3/5)

The user runs several sessions and ticket-keyed multi-agent flows, which is exactly why D-40 was built, so a legible parent-to-children view and one approval for a multi-ticket plan are real wins. But the single-session flow already approves in one click with a literal box, the 'from <parent>' origin already exists, and the finish/needs-you of any child already reaches Active, the Dock badge, the menu bar and Cmd+J. The remaining gain is mostly the batch and the glanceable roll-up; the high-risk part (always-allow) buys one saved click on a rare action. Unknown: how often the user's agents actually call open-session today (no usage data in the repo).

## Depends on

- D-40/D-42 shipped open-session flow (no dependency on new work)
- Piece 5 (worktree field) depends on the separate 'new session in worktree' idea; Loom has no worktree code
- 'child finished returned to the asking agent' (a wait verb) belongs to the separate read-only orchestration verbs idea (T3-style) and needs its own approval model

## Experiments before building

- E1 permission-ceiling spike (isolated CLAUDE_CONFIG_DIR, no real ~/.claude): run claude 2.1.300 with a temp --settings hook that logs the raw payload, once per --permission-mode choice, plus a Shift+Tab toggle mid-turn. Decides: do the hook's permission_mode strings map 1:1 onto the --permission-mode choices (manual vs default naming), is the last event's value fresh enough when 'open' runs inside a turn, and is there a defensible ordering for 'not broader than' given auto and dontAsk. If any answer is no, piece 4 is dropped, not approximated.
- E2 late-approval return: with the fake provider or an isolated Claude, test whether the open command can safely wait well beyond 85 s (Claude's Bash tool default timeout is about 2 min; background execution exists). Decides whether the 85 s pending-and-forget limit can be lifted so the agent always gets session ids after a slow approval, or whether the skill should instruct run-in-background. Pure protocol test, no real approvals needed.
- E3 start-burst cost: start 5 sessions through the batch path against the fake provider first, then once with real Claude on an idle machine (only when the user says it is idle), reading Loom's existing process sampling. Decides the default cap (5 vs 3) and whether the cost note needs a measured memory figure.
- E4 reverse-lookup cost: with a large fixture catalog (loom-catalog-fixture), time children(of:) for a 100-row page with and without the partial index. Decides whether the index is needed or the query can stay unindexed.

## Questions for the user

- How often do your agents call open-session today, and how many sessions would a typical fan-out contain? (decides the batch cap and whether piece 2 is worth building before piece 1)
- Do you accept a roll-up row under the parent card that links to children (cards stay where they are), or do you want true tree nesting in the sidebar with the cost of reordering the day/Active/project lists?
- Do you want any standing authorization at all (per-project always-allow)? It amends D-40 and contract §7 and exposes a prompt-injection path; recommended answer for now is no, revisit after the ceiling spike.
- Is an explicit 'Stop opened sessions (N)' gesture wanted, or is stopping each child by hand enough?
- Should the worktree field wait for the separate worktree idea, or do you want open-session to accept a plain target folder/project now (already possible with --project)?
- Should approval of an agent's open request also be possible from the menu bar item or a notification instead of only inside the requester's detail pane (a larger fluency gain than always-allow, separate idea)?
