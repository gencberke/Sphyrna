# I-18: Park / snooze / In-work: user-owned lifecycle flags for sessions

Card from the [Loom v2 idea catalog](../IDEAS.md). **Park / snooze / In-work: user-owned lifecycle flags for sessions** · verdict **adopt-light** · cost M · value 4/5 · proposed by 2 reports: [t3code](../products/t3code.md), [openchamber](../products/openchamber.md).

> Adopt only the "In work" half (one persisted per-session flag, opened by the user's own prompt, closed only by one-key Done, 15-day stale falloff, no model call), and drop the Park shelf, timed snooze and auto-settle timers, because Loom's Active section is live-only and forgets everything at Quit, while Mark as Read and the stale lifecycle already cover most of what Park would do.

## What the user gets

A cheap, reversible 'I am done with this for now' (Park, optionally snooze until a time or until the plan limit resets) and an explicit 'In work' list of sessions you are still responsible for, so the Active list equals 'things that need or may need me'. 5-second Undo toast; 'park and go to the next session needing me'.

## Mechanisms found in the research

Loom-owned metadata only (pinned, parked, snoozed-until, work=open|done), a Parked shelf in the activity view; snooze-until-limit reuses the reset time from get_usage; auto-settle by age evaluated lazily when the sidebar is shown or by one one-shot timer to the next due time, never for a session with a pending approval, running subagent or live process (T3 isAutoSettlementCandidate checklist). OpenChamber 'In work': a sent message only opens, only the user closes (Done is one click/key), a message newer than doneAt reopens, a section above Active; define precedence so a session is listed once; no classifier ('looks done' hint costs a model call per turn).

## Debates and fact-check corrections

T3's docs say pinning does not prevent automatic settlement while the code excludes pinned threads (docs and code disagree). OpenChamber had to fix a pinned session appearing twice (v2.4.0). Two overlapping lists (Active vs In work) can confuse; skip PR-merge auto-settle until Loom knows PR state (I-31). Useful for the user's two work projects with many half-finished tickets.

## Design in Loom


Finding that changes the idea: Loom's Active section is live-only. `CatalogModel+Active.updateActive` admits a session only when `live?.runID != nil` and `SessionViewState.activePhase != .inactive`, and that state is in-memory hub state (`SessionEventHub.publish`: cleared on runEnded/runDetached). Quit stops everything (contract), so after every restart Active is empty and the user falls back to day headings. A persisted In-work list therefore fills a real gap. Park fills a smaller one: viewing a session already ends "Finished unviewed" and `markRead` acknowledges "Waiting for you" (SessionEventHub.markRead), so Park only adds suppression for sessions that are still working or waiting on approval, and those should not be hidden anyway (accurate status).

Design (light):
1. State = ONE nullable column, not several flags. `sessions.work_state TEXT` (NULL | 'work'), plus `work_state_at REAL` if a "since" is wanted. Add it on open with the existing no-version-bump pattern (`CatalogDatabase.ensureOriginColumns` / `ensureProjectColors`: nullable ALTER under the write lock, older builds still open the file). One column means a session cannot be in two lists by construction, which removes the OpenChamber v2.4.0 "listed twice" bug class. Extend `SessionCatalog.sessionColumns` (SessionCatalog.swift ~L195), the row decoder (~L345) and `CatalogSession` (init has defaults, so call sites survive).
2. Triggers (all existing events, no new timer):
 - Open: the user's own prompt. `ProcessSupervisor.markProviderUsed` -> `SessionCatalog.markUsed(reactivate: true)` is already called on `UserPromptSubmit` (ProviderSessionAdapters.swift ~L268). Set `work_state='work'` inside that same UPDATE (one SQL statement, no extra write) only when `movesActivity` is true, so a resume (`SessionLifecycleController.reactivate`, movesActivity false) does not open it. The sent-message-opens, only-user-closes invariant is thereby a SQL rule. A new session's first prompt opens it too.
 - Close: user command only, `SessionCatalog.setWorkState(nil, for:)` modelled on `setPinned` (SessionCatalog+Sessions.swift L242) and `CatalogModel.setPinned` (CatalogModel+Cleanup.swift L10: write, then `refreshRow`; a failed write reports an error, never a false success). Done on a live session also calls `markRead` (display-only acknowledgement), and never stops anything (Stop stays a separate verified action).
 - Reopen: the next prompt (same rule as Open). No `doneAt` comparison needed.
 - Falloff (auto-settle by age, for free): the shelf excludes `lifecycle = 'stale'`. Stale is already classified by `SessionLifecycleController.classifyStale` on its existing one-shot timer chain (15 days unused, contract section 5), which publishes `.catalogLifecycle`. No new timer or scheduler. A stale row keeps its flag; a new prompt reactivates it.
3. Sidebar: add `CatalogScope.inWork` (one more `conditions(for:)` branch in SessionCatalog+Paging.swift: `s.work_state = 'work' AND s.lifecycle != 'stale'`) and `CatalogListKey.inWork` (CatalogModel.swift L7), loaded with the first page, capped at one page (100, `CatalogQuery.maxPageSize`) so it is bounded. A dedicated query is needed because the activity list is keyset-paged: deriving the shelf from loaded rows (as `activeRows` does) would miss In-work sessions older than the loaded range. `ActivityLayout` gains `inWork`; `daySections`/`activeRows` already take an exclusion set keyed by `activeRevision`, so the same mechanism excludes In-work IDs (single partition function = single place that decides precedence).
4. Precedence (listed once): Active (live, needs or is doing work) > In work > day sections. An In-work session that is live and under way shows in Active only, with the In-work glyph on its card; when it is read it drops into In work, not into the day list. While searching, no sections (existing rule). Project view is untouched (creation order never moves, D-39); there In work is only a card glyph.
5. Row patching: the new list joins `CatalogModel+Patching` (which already decides per list whether a patched record belongs) so a flag flip is one row read, not a full refresh.
6. Keyboard/Undo: File or Window menu command "Mark Done" / "Put Back in Work" (toggle, one chord; pick a free one, none of Cmd+J, Cmd+1/2, Cmd+Delete, Cmd+. is used by it) next to the Cmd+J items in `AppDelegate.installMenus`; context-menu item beside Pin/Mark as Read (SidebarView.swift ~L506). Reversible by the same toggle; plus an "Undo Mark Done" menu title valid until the next flag action, which costs no timer and no surface. "Done and go to the next session that needs me" = `markDone` then `jumpToAttention(.next)`; since the current session leaves the set or never was in it, `AttentionOrder.neighbor` already starts the walk at the first entry.
7. Retention: In-work sessions should be exempt from cleanup like pinned ones (`CleanupPlanner.classify`, `CleanupCandidate.pinned` / `taskLink`): a one-line exclusion reason. Cleanup review is dev-only and automatic deletion is off, so this is low risk; it needs a DECISIONS entry because contract section 5 lists the exceptions.
8. Left out on purpose: Parked shelf, snooze-until-time, snooze-until-plan-reset, T3 PR-merge settle, pending-approval/subagent auto-settle checklist (not needed: nothing auto-settles except the existing stale rule, which already skips running sessions via `oldestStaleCandidate(excluding: running)`), the "looks done" classifier, agents setting the flag over the control socket (user authority). Snooze-until-limit-reset belongs with the separate usage-limit idea: `ClaudePlanLimits.PlanLimitWindow.resetsAt` exists, but Loom only knows a reset when the CLI answered `get_usage`, and `UsageModel` asks only on events (afterShown 300 s, afterTurn 120 s), and nothing today links a session stopping on `StopFailure` to a limit.

Check before building: `markProviderUsed` runs for every `UserPromptSubmit`, including synthetic ones (`promptIsSynthetic`, ClaudeHook.swift L395: subagent hand-backs and task notifications), because the adapter at ProviderSessionAdapters.swift ~L268 does not test it. Opening In work from there would reopen a Done session when a background subagent reports back. Gate the open on `!promptIsSynthetic` (pass a flag into `markProviderUsed`), with a test.


## Where it shows


Activity view, top to bottom: Active (n) as today, then a new heading "In work  n" in the day-heading style (`ActivityHeading`, 11 pt semibold secondary, same paddings; not drawn when empty or while searching), then the day sections without those rows. Cards in In work are the normal two-row cards; a small "work" glyph (same slot and size as the pin glyph, theme tokens only) marks In-work membership on cards that appear in Active or in the project view. Context menu: "Mark Done" (In-work card) / "Put in Work" (any other), next to Pin and Mark as Read. One menu command with a chord does the same for the selected row. Feedback for Done: the card simply leaves the section; an "Undo Mark Done" Edit-menu title carries the 5-second-Undo promise without a toast. If a toast is wanted later, draw it as an overlay: the existing `Banners` stack in DetailView changes layout and would resize the terminal (PTY resize), which its own comment forbids. No Parked shelf and no snooze picker in v1.


## Principle check


Resources: pass. One nullable column; one bounded query (cap 100) at list load; no timer, no polling, no watcher; the falloff reuses the stale classifier's existing one-shot chain; nothing drawn when the section is empty. Risk if built the heavy way: a lazy-evaluated or timer-driven snooze/auto-settle scheduler, or a classifier per turn.
Predictability: pass if precedence is one partition function and the state is one column (a session is in exactly one of Active / In work / day). Risk: auto-open on every prompt makes the list long and the user must learn Done; the rule stays simple (prompt opens, user closes, 15 days unused falls off) but must be shown in a tooltip.
Accurate status: pass with care. In work is user intent, not a verified provider outcome, so it must not share the status indicator (contract section 4: agent states are a separate field from active/idle/stale; keep this a third, orthogonal field). Done must never read as stopped or deleted; no suppression of Needs approval, Failed or Cmd+J/Dock badge in v1 (that is why Park is dropped: hiding a working or approval-blocked session would make the badge lie).
Fluency: pass: one key, no confirmation, same toggle undoes it. No wait added.
Modularity: pass: column in LoomCore catalog, scope/query in the paging file, list/partition in CatalogModel+Active-style extension, view in SidebarView; LoomCore stays UI-free.
CLI-update resilience: pass: uses only the UserPromptSubmit event Loom already consumes; no new hook, flag or CLI parse.
Ownership: pass: no process is started, stopped or touched; Done does not stop a run.
User authority: pass: only the user closes; no agent, hook or socket path can set the flag (explicitly not added to the open-session control socket).
Older builds: pass: nullable column added on open without a version bump (three precedents), older builds ignore it.


## Value for the user (4/5)

For someone running several sessions over two work projects with ticket keys, a persisted "what am I in the middle of" list directly fixes the empty-Active-after-restart gap, and it costs no resources. The full Park/snooze half scores about 2: Mark as Read and viewing already clear the noisy states, and hiding approval or working sessions conflicts with accurate attention counts.

## Depends on

- I-31 (PR state) only for a later PR-merge auto-close; not needed for the light version
- usage-limit actions idea (Continue/Snooze at reset) for snooze-until-limit, kept separate

## Experiments before building

- No spike needed for feasibility. One cheap code check decides a detail: confirm in a fixture test that a synthetic UserPromptSubmit (subagent hand-back) reaches markProviderUsed today, then gate the open on !promptIsSynthetic; the test must fail without the gate.
- Optional decision aid before building (one week, no code): the user lists by hand how many sessions they prompt in a typical week that they would want in an In-work list; if auto-open would put more than about 15 items there, switch to manual 'Put in Work' plus auto-open only for sessions with a ticket key or project.

## Questions for the user

- Should a prompt auto-open In work (OpenChamber v2.3.0 choice, no forgetting but a Done ritual) or should In work be opt-in per session?
- Is dropping the Parked shelf and timed snooze acceptable for v1, given Mark as Read already clears Finished/Waiting and parking a working session would hide it from the badge?
- Should In-work sessions fall off the shelf at Loom's existing 15-day stale rule, or never until Done?
- Should In work also exempt a session from stale cleanup (a small contract section 5 / DECISIONS change)?
- Should the existing Pin (today only a retention exception shown as a glyph) stay as is, or be reused/renamed? It is a different meaning from T3's keep-on-top pin.
