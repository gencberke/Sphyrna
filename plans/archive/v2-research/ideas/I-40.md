# I-40: Scheduled runs with a triage inbox (later)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Scheduled runs with a triage inbox (later)** · verdict **later** · cost XL · value 2/5 · proposed by 4 reports: [codex-app](../products/codex-app.md), [emdash](../products/emdash.md), [superset](../products/superset.md), [claude-official](../products/claude-official.md).

> Technically a clean fit if cut down to read-only recipes plus one armed timer that runs only while Loom is open, but for this user it mostly duplicates Claude skills and /loop, the unique unattended value costs plan budget, and the full version (worktrees, budgets, return-to-session) is XL, not L, so park it behind the worktree and usage-by-source work.

## What the user gets

A Scheduled section whose runs (daily repo brief, CI-failure triage, stale-docs sweep) arrive as ordinary sessions in the existing Active/Finished-unviewed machinery, with 'nothing to report' runs auto-marked viewed.

## Mechanisms found in the research

One armed timer for the next due run; works only while Loom runs and says missed runs were skipped (Codex needs the app running too); each run in an isolated worktree; standalone vs 'return to this session'; per-task budget; scheduled prompts authored by the user, agents cannot create schedules without approval; build only after worktrees and usage-by-source exist. Recipe-only variant (no scheduler) from Emdash; if true background runs are wanted, delegate to Claude's own Routines (research preview, min 1 h) / Desktop scheduled tasks or launchd rather than keeping Loom alive.

## Debates and fact-check corrections

Superset and Emdash both advise against a Loom-style cron daemon (contradicts Quit stops everything / no daemon); the real-value version is unattended runs, which needs a different ownership model and a tight permission mode. Anthropic already ships Routines and Desktop scheduled tasks (min 1 min, while the app is open, one catch-up within 7 days).

## Design in Loom

CORRECTIONS TO THE IDEA FIRST. (1) The "debates" line says Superset and Emdash advise against a cron daemon. The notes say otherwise: both SHIP schedulers (Emdash runtimes/automations: one upcoming run per automation, only fires while the app runs, recovers interrupted runs; Superset Pro automations are cloud-dispatched, at-least-once, and 'created' only means the workspace exists, not that the agent succeeded, issue #7941/#6243). The "no daemon" advice is the digest authors', and Superset's own pty-daemon problems (#7977, #5792, #8029) are the real cautionary tale. (2) Loom's own contract already says a closed app does not pick up work (LOOM-PRODUCT-CONTRACT.md section 7 last paragraph), so "runs only while Loom runs" is consistent, not a compromise. (3) 'Return to this session' is already free: Claude's /loop and cron are session-scoped, and Loom already counts them as pending work (ClaudeHook.swift reads Stop.session_crons; ProviderSessionAdapters.swift adds scheduledTaskCount to pendingProviderWorkCount, so a looping session shows under way in the Active section). Do not build that variant.

SMALLEST VERSION THAT FITS (call it 'Recipes'): read-only prompts per project, run on a timer while Loom is open, results arrive as ordinary cards.
1. Store (LoomCore, new file e.g. ScheduledRecipe.swift): recipes {id, name, projectID, prompt, schedule (daily/weekly time or interval >= 1 h), enabled, lastRun, nextDue}. Persist as a small JSON beside ui-preferences.json (UIPreferencesStore pattern, unreadable file renamed aside) or an additive table opened like ensureProjectColors. Authored only from a Loom Settings page. No verb in loom-hook/OpenSessionProtocol or the loom:open-session skill can create or edit one, so agents cannot schedule (contract section 7). Honest caveat: an agent with Bash can edit a file in Application Support, so the real guard is that a recipe's permission mode is fixed in code (read-only), not user-chosen text.
2. Trigger, no polling: one armed Task per runtime (SessionRuntime owns it, like SessionLifecycleController.reschedule/timerFired with a single Task.sleep to the earliest deadline; CatalogModel.sleepUntil is the existing wall-clock sleep seam). Re-arm only on: recipe edit, runtime start, NSWorkspace.didWakeNotification, NSSystemClockDidChange (the last two forwarded from loom-app, event-driven). On fire, recompute from the wall clock (never trust the sleep), because ContinuousClock sleeps through machine sleep. Nothing runs between events; with no enabled recipes there is no timer at all.
3. Missed runs: at runtime start and on wake compute due-but-unrun slots. Policy (user decision): run ONE catch-up if the slot is within a grace window (default 12 h for daily), otherwise record 'skipped' with a reason. Settings shows 'Skipped 2 runs while Loom was closed' plainly (Desktop scheduled tasks do one catch-up within 7 days and log skip reasons; copy the honesty, not the 7 days).
4. Start path: reuse SessionRuntime.startConversation(opening:) / ProviderLaunchProfile.claude(route: .new, opening:) exactly like an approved open-session request (SessionRuntime+OpenRequests.approveOpenRequest). The user's creating and enabling the recipe is the authorization, so no per-run prompt; the approve box (OpenRequestViews) is not used. Add to the launch profile (capability-detected from claude --help like supportsEffort, drift-journaled by missingRequiredClaudeOptions, never pinned): '--permission-mode dontAsk' plus '--allowedTools' with a read-only list (Read, Grep, Glob, Bash(git log/diff/status:*), Bash(gh pr/run list/view:*)). claude --help 2.1.300 lists dontAsk, plan, auto, bypassPermissions. The scheduled run gets hooks but NO control socket and NO plugin dir (ClaudeHookLaunchConfiguration already allows controlSocketPath nil), so an unattended session cannot file open-session requests; crossSessionInbound is already 'refuse' in claudeSettings. A needs-approval stall still surfaces through the existing path (Needs approval, banner, Cmd+J).
5. Launch needs a TerminalSurface (rows/cols, ended-screen snapshot), so the UI-layer ConversationController gets a start(scheduled:) beside approveOpen (it creates the surface the same way; selection does not move, no window opens, no sound).
6. Origin and unread: add a nullable origin column (e.g. scheduled:<recipeID>) next to ticket_key/opened_by with the ensure*Columns 'added on open, no version bump' pattern, so older builds still open the catalog. Card shows a clock glyph and 'scheduled · Daily brief' in the meta row (S2 'from <session>' precedent, D-39).
7. Run end (this is the part the idea glosses over): SessionEventHub.runEnded sets activePhase to .inactive and clears status, and unviewedCompletion lives in memory only, so a stopped run today shows NO blue 'Finished' dot and nothing survives a relaunch. For an inbox the result must stay unread across the stop. Two options: (a) keep the TUI alive at its prompt until viewed (zero new state, but a ~230 MB class Claude process per unread run sits idle all day, against 'idle records cost nothing'; D-38 forbids auto idle stop but a scheduled run is a different case); (b) preferred: when the Stop hook arrives with pendingProviderWorkCount == 0, Loom runs its normal verified stopConversation, EndedScreenStore keeps the snapshot, and a persisted sessions.unread_result flag (catalog, cleared by the first deliberate view via markViewed/viewRecorded) drives a new 'unread result' indicator on an ended card. That is a real catalog + SessionIndicator + sidebar change (M), not 'reuse the machinery'.
8. 'Nothing to report' auto-viewed: do not judge text. The recipe wrapper appends 'If there is nothing to report, reply with exactly NOTHING_TO_REPORT'. Loom already parses Stop.last_assistant_message (ClaudeHook.swift lines 387/445/768) but never publishes it (ProviderWorkState carries only activity + pending count), so plumb one bounded comparison (exact match after trim) in the adapter; on match, mark read and stop. A miss errs toward showing the card unread. Label it agent-reported, never as verified status. Verify the Stop payload field against the installed CLI before relying on it (the research notes document background_tasks/session_crons for Stop but not this field).
9. Bounds: concurrency 1 (queue, drop duplicates of the same recipe); wall-clock cap per run (default 15 min) enforced by Loom's verified Stop. A token budget cannot use the CLI: --max-budget-usd works only with --print, which this design avoids. Per-session token caps need a session sum over ClaudeUsageIndex (messages are keyed by session, but no per-session query or usage-by-source exists yet), so defer them to that work. Floor: skip a run (log 'skipped: plan window under 20%') when the plan share Loom already reads from get_usage is low, reusing the footer chip's orange threshold.
10. Status honesty (Superset lesson): 'running' only after the first UserPromptSubmit hook of that run; a run that never reaches it within ~60 s is marked Problem 'did not start' (reuse the hook-silence watchdog idea; a folder-trust dialog runs no hooks, see experiment 2); 'done' is the Stop hook plus a verified stop; 'skipped' and 'missed' are first-class rows, never silent.
11. Quit/ownership: runs live in normal run scopes; Quit stops them and QuitConfirmation counts them as Working (correct). No launchd, no helper that outlives Quit. If the user ever wants truly unattended runs, delegate to Claude Desktop scheduled tasks, cloud Routines (min 1 h, research preview, GitHub-hosted repos) or their own launchd job; those results will not appear as Loom cards, and sessions started outside Loom are not Loom-owned (contract section 6).
12. Codex: frozen (D-28); recipes are Claude-only until it returns.

WHAT IS DEFERRED FROM THE IDEA'S FULL FORM: worktree isolation (Loom has no worktree code; CleanupCoordinator only protects existing linked worktrees). Read-only recipes need none, which removes the idea's main prerequisite. Edit-capable recipes (stale-docs sweep that writes) must wait for the worktree work and for experiment 2.

## Where it shows

No new sidebar section and no left rail (D-34). Management is Settings > Scheduled: a list of recipes (name, project colour stripe, schedule, next run, last result, enable switch), Run now, Edit (prompt, project, time), and a plain line 'Runs only while Loom is open' plus any 'Skipped N runs while Loom was closed'. Results are ordinary cards in the activity view (Active while running, then the day heading) with a small clock glyph and 'scheduled · <recipe>' in the meta row; an unread result shows the existing blue Finished dot even though the process has ended; a 'nothing to report' run is already read and just sits under its day. Menu bar menu gets one line 'Next: Daily brief 09:00'. No sound, no window focus, no selection change when a run starts. A later optional filter chip 'Scheduled' in search is enough; a dedicated inbox view is not needed because Cmd+J already jumps to the next unread item.

## Principle check

Resources: PASS if built as designed (one armed Task, none with zero recipes, no polling, nothing drawn when hidden; a run is a normal working session, concurrency 1, 15 min cap, stopped at Stop so no idle process per unread result). RISK: each run spends plan tokens and a Claude process; the plan-window floor and the cap are mandatory, not optional. Predictability: RISK, an unattended start while the user works; mitigate with no focus/sound/selection change, fixed read-only mode, visible next-run line. Accurate status: PASS only with the Superset lesson applied (started = UserPromptSubmit seen, skipped/missed recorded, 'nothing to report' labelled agent-reported); FAIL if 'created' were shown as 'ran'. Fluency: PASS (no per-run confirmation; creating the recipe is the authorization). Modularity: PASS, scheduler is a small LoomCore actor over existing start/stop paths; the unread-after-stop change touches catalog + SessionIndicator + sidebar (the costly part). CLI-update resilience: PASS for --permission-mode/--allowedTools via help detection and drift journal, never pinned; RISK that dontAsk or Stop payload fields change, and that a billing-policy change hits headless use (the Oct 7 support article says claude -p still uses subscription limits but a June change was paused), which is why the design stays on the interactive TUI. Ownership: PASS (run scope, Quit stops it, no daemon, no launchd); a design with a surviving runner would FAIL. User authority: PASS (schedules authored only in Loom UI, no agent verb, no control socket or plugin in scheduled runs, tight mode, Desktop precedent of no cross-session sends from unattended sessions); residual: a Bash-capable agent can edit the recipe file, bounded by the fixed read-only mode. Principle violations to avoid: a timer that keeps Loom alive or relaunches it, polling every minute (Desktop does; Loom must not), unattended edit-capable runs without worktrees, sleeping idle TUIs per unread result, token-judging 'nothing to report' with another model call.

## Value for the user (2/5)

The user's stated wishes are side chat, right panel, usage, reliable deletion and free idle sessions; scheduling is not among them. Reusable prompts are already Claude skills or slash commands (a brief is Cmd+N plus a skill), in-session repeats are /loop, and the only unique value is unattended timing, which spends the plan window the user watches and runs only while Loom is open and the Mac awake. Read-only brief/triage runs on two work projects are pleasant but not a productivity step change; the high-value form (editing runs in worktrees with budgets) is the XL part.

## Depends on

- Worktree-backed sessions (digest 'idea 5'; needed only for edit-capable recipes, not for read-only ones)
- Usage by source / per-session token query over ClaudeUsageIndex (needed for token budgets and the 'scheduled' attribution line)
- Persisted unread-result flag for ended sessions (new, part of this idea's own cost)
- Cross-session channel decision (D-43/D-46) so the 'agents cannot create schedules' rule is designed once with the rest of the authority model

## Experiments before building

- E1 interactive dontAsk run: in an isolated CLAUDE_CONFIG_DIR and a throwaway repo, start claude with --permission-mode dontAsk --allowedTools <read-only list> and a positional prompt through Loom's launch profile (loom-fake-provider is not enough, this needs the real CLI). Decides: does it reach Stop with no prompt, do denied tools end the turn instead of hanging, do the hooks Loom needs fire. If it hangs or prompts, the design needs --print and its billing exposure, which changes the verdict toward skip.
- E2 trust dialog and worktrees: a fresh directory and a claude -w worktree under an already-trusted repo, launched unattended. Decides: whether an untrusted path blocks on the folder-trust question (which runs no hooks, per ARCHITECTURE watchdog notes) and therefore whether worktree-based recipes are allowed in v1 or the 'did not start' detector is mandatory.
- E3 Stop payload: confirm last_assistant_message is present in the Stop hook input of the installed CLI (claude --version here is 2.1.300) and that a NOTHING_TO_REPORT sentinel is returned exactly in about 10 runs of a quiet repo. Decides: whether auto-marking viewed is safe or the feature ships without it.
- E4 cost of a typical brief: run the daily-brief prompt on one real project twice in an isolated profile and read tokens via the usage index. Decides the default cap and whether the plan-window floor is enough, or whether the feature is too expensive for the user's plan.
- E5 wake behaviour: in a spike with the armed Task, sleep the Mac across the due time and change the clock. Decides that the wake and NSSystemClockDidChange re-arm is enough and no periodic safety tick is needed.

## Questions for the user

- Do you want unattended output at all, or only one-click saved prompts? (If only the latter, Claude skills already cover it and this idea should be skipped.)
- Is it acceptable that scheduled runs happen only while Loom is open and the Mac is awake (use Open at login and the menu bar item), or do you want them when Loom is closed, which means using Claude's own Routines, Desktop scheduled tasks or launchd outside Loom?
- Missed-run policy: one catch-up within a window (how long?) or skip with a note?
- Read-only recipes only in v1, or do you need editing recipes, which forces the worktree work first?
- Default per-run cap (time) and a plan-window floor under which scheduled runs are skipped, given you watch the plan limits?
- Are cloud Routines acceptable for the two work repos (employer policy), since they would solve the closed-laptop case without any Loom code?
- Should a finished scheduled run stop its process and stay unread (recommended), or stay alive at its prompt like other sessions today?
