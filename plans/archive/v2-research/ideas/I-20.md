# I-20: Keep the Mac awake while a session is Working

Card from the [Loom v2 idea catalog](../IDEAS.md). **Keep the Mac awake while a session is Working** · verdict **adopt-light** · cost S · value 4/5 · proposed by 5 reports: [orca](../products/orca.md), [zed](../products/zed.md), [supacode](../products/supacode.md), [persistence-remote-orchestration](../products/persistence-remote-orchestration.md), [power-user-workflows](../products/power-user-workflows.md).

> Adopt a trimmed version: one on/off setting "Keep the Mac awake while sessions work", one idle-system-sleep assertion driven by the existing live-state fan-out (the same path as the menu bar item), with background tasks counted, scheduled crons excluded, a one-shot cap and a visible indicator. Drop "Always" and the "tied to the watchdog" claim, because Loom's Working is already registry-corrected and the watchdog only covers a run with zero hooks.

## What the user gets

Long runs (tests, multi-agent workflows) survive idle sleep and screen lock without a side-terminal `caffeinate`; Off / While working / Always, with a small indicator and release on the last Finished.

## Mechanisms found in the research

One IOKit PreventUserIdleSystemSleep assertion taken on the first Working transition and released when none remain (not during Needs approval, matching Zed), tied to the hook-silence watchdog so a stale Working expires the lease (Orca uses a stale-timeout lease); indicator in footer/menu bar; display sleep still allowed; release on Quit/crash is automatic; default off or only on power.

## Debates and fact-check corrections

Easiest high-convergence win; Conductor's setting went from experimental (0.50) to General (0.51). Risks: battery drain if status is falsely Working, clamshell/closed-lid limits, managed Macs. Relevant documented signals: quota_auto_resume_fired/stale/disabled Notification types (v2.1.234+) mean a 'Working' state may really be a quota wait, and after sleeping >30 min across the reset Claude waits for Enter; Desktop sessions survive sleep only while the process survives.

## Design in Loom

PLUG-IN POINT (verified). `CatalogModel.updateAttentionCount()` (Sources/LoomCatalogUI/CatalogModel+Navigation.swift:43) already runs on every live-state or record change and never on a timer. It derives `MenuBarSummary` and fires `onMenuBarChange`, which `AppDelegate.installSystemIntegration` (Sources/loom-app/AppDelegate+System.swift:35) wires to `MenuBarController` and `ApprovalNotifier`. The keep-awake feature is a third consumer of the same pass. The model keeps `liveStates` current whether or not the window is visible, so no new subscription, watcher or timer is needed. This is the ApprovalNotifier pattern, which only hears a changed set (ApprovalNotifier.swift).

PIECES.
(1) `KeepAwakeRule` (pure, LoomCatalogUI, next to MenuBarState/SessionNavigation). Input is `liveStates` (SessionViewState). A session counts when `runID != nil`, no `stopFailure`, no `issue`, identity is not ambiguous, and either `status.activity == .working` or (`.turnComplete` with background work > 0). It does NOT count `.waitingForApproval`, which matches Zed and what the user asked for. It does NOT count scheduled crons.
   - Why not reuse `MenuBarSummary.working` or `SessionIndicator.working`? `SessionIndicator.init` (SessionDisplay.swift:58-60) maps `.turnComplete` with `pendingProviderWorkCount > 0` to Working. That count is `backgroundTaskCount + scheduledTaskCount` (ProviderSessionAdapters.swift:84 and :301). `scheduledTaskCount` is `Stop.session_crons`, so a session with a /loop or cron looks Working forever and would pin the Mac awake. This is the real false-Working source in Loom, and it is not the stale-hook case the research feared.
   - Fix: add an additive `scheduledWorkCount` (default 0) to `ProviderWorkState` (SessionLifecycleController.swift:3), set only by the Claude adapter's two construction sites. `pendingProviderWorkCount` stays the sum, so the idle blockers (SessionLifecycleController.swift:441) and the Active section (SessionEventHub.swift:338) do not change. The rule then uses `pending - scheduled`. The smaller fallback is `activity == .working` only, which misses the case where Claude ends its turn and waits for a background test run.
(2) `PowerAssertionService` protocol in Sources/loom-app/SystemServices.swift, beside NotificationService and LoginItemService, with the live implementation and a recording fake under `--evidence`. The live version calls `IOPMAssertionCreateWithName(kIOPMAssertionTypePreventUserIdleSystemSleep, level on, "Loom: a session is working")` and `IOPMAssertionRelease`. It reports the IOReturn so the indicator only shows when creation succeeded. `ProcessInfo.beginActivity(.idleSystemSleepDisabled)` is the Foundation alternative, but IOKit is more exact. Do not use `.userInitiated`, which also changes App Nap and sudden-termination behaviour. Display sleep is not asserted, so the screen still sleeps and locks.
(3) `KeepAwakeController` (loom-app, @MainActor, ~60 lines). It takes `count` from the model and `model.keepAwake` from preferences. Count goes from 0 to >0: take the assertion and arm a single one-shot cap (suggest 6-8 h of continuous hold, then release until the next fresh transition from zero). Count goes to 0: release after a short grace (suggest 30 s, one-shot) so turn handoffs and quick follow-up prompts do not flap the assertion. Setting off, `applicationWillTerminate` (AppDelegate.swift:374) and Low Power Mode on also release (`NSProcessInfoPowerStateDidChange`, event-driven). A crash or kill releases automatically, because the kernel drops assertions with the process, so nothing outlives Loom (process ownership and the Quit contract hold). Exposed `isHolding` goes to the model for the indicator.
(4) Preference: `UIPreferences.keepAwake: Bool` (UIPreferences.swift:48-112, absent in an old file decodes to the default), `CatalogModel.setKeepAwake` with an `onKeepAwakeChange` closure, copying `setNotifyApprovals` (CatalogModel.swift:1189). Settings row in `SystemSettingsCard` (SettingsView.swift:~150), same `SettingsRow` + switch as "Notify when a session needs approval".
(5) Trigger plumbing: `updateAttentionCount` computes the keep-awake count in the same pass and calls the closure only when the boolean-relevant value changes (count 0 vs >0), as it does for `menuBarSummary`.

BOUNDS. No polling. At most two one-shot timers (grace and cap), both armed only on state edges. One assertion, one tiny object. Nothing is drawn while hidden (the indicator is state-driven). No new file watchers, no reads.

VERIFIED OUTCOME. The indicator shows only when `IOPMAssertionCreate` returned success. Evidence check: `pmset -g assertions` lists a PreventUserIdleSystemSleep entry named for Loom while a fake-provider session (Sources/loom-fake-provider) is Working and none after it finishes. Run this in the dev flavor with an isolated data root and a throwaway CLAUDE_CONFIG_DIR, never the real app.

CLI-UPDATE RESILIENCE. It reads only state Loom already derives. Hook and registry drift is already detected (D-45), and the feature degrades safely: unknown state means no hold.

TESTS. Pure `KeepAwakeRule` cases: working, approval, ready, cron-only, background-only, problem/issue, stopUnverified. `KeepAwakeController` with the fake service: edges, grace, cap, setting off, Low Power Mode, quit. Reuse the SystemServices fake seam. One integration check with the fake provider.

## Where it shows

Settings > General > the system card (SystemSettingsCard), one new row: title "Keep the Mac awake while sessions work", detail "Stops idle sleep while a session is working or waiting on background tasks. The screen can still sleep and lock. Closing the lid still sleeps the Mac." Switch only, and a notice line when Low Power Mode pauses it.

Indicator, shown only while actually holding (state-driven, no animation, monochrome SF Symbol per DESIGN 'Iconography'):
- The menu bar menu gets a disabled info line "Keeping this Mac awake" above the separator (MenuBarMenu.items). It also goes in the status item's accessibility label ("Loom, 2 sessions working, keeping the Mac awake").
- The sidebar footer gets a small 13 pt glyph (e.g. a sun/moon-slash or bolt style symbol) left of the usage chip, with a tooltip "Keeping this Mac awake while sessions work. Click to change." The click opens Settings > General. No layout shift: it is drawn only while holding, and the chip is the one flexible element in the footer (SidebarFooter.swift:11), so it absorbs the 28 pt.

No Dock badge change. Off by default or on by default is the user's call (see decisions).

## Principle check

Resources: pass. It runs on edges of existing state, with no polling, no watcher and no draw while hidden. The IOKit assertion costs nothing while held. Risk: only battery drain from a false hold, mitigated below.

Predictable: pass if it is a visible setting plus a visible indicator, and a hold is only for 'turn under way or background tasks'. Risks: (a) cron-only sessions look Working in Loom today and would hold forever, so exclude them as designed. (b) A genuinely stuck Working. Loom's Working is registry-backed in both directions: `ClaudeRegistryWatch` (vnode, no timer) turns an 'idle' sample back into waitingForInput, so an Esc interrupt or a lost Stop hook corrects itself. Remaining stuck cases get the one-shot cap, a process-end release, and the visible indicator. Do NOT add an inactivity lease like Orca's stale timeout: a 40-minute test run emits no hooks and would be released wrongly.

Accurate status: pass. 'Holding' means creation succeeded, it is released on every exit path, and nothing is shown as success otherwise. Caveats to state plainly in the UI copy: lid-close on battery still sleeps, and a Working session that Loom flags as Problem (hook silence) does not hold even if Claude is really busy.

Fluency: pass. No prompts, and it removes the side-terminal caffeinate habit.

Modularity: pass. A pure rule in LoomCatalogUI, a service protocol and controller in loom-app (as for notifications and login item), one additive field in LoomCore, and no dependency pointing up.

CLI-update resilience: pass. Documented hook and registry state only, nothing pinned, and unknown state means no hold. Quota auto-resume Notification types are currently ignored by `notificationActivity` (ClaudeHook.swift:788). Whether a quota wait shows as Working is unverified (see experiments).

Ownership: pass. The assertion belongs to the Loom process, so Quit or a crash releases it. No daemon, no change to 'Quit stops everything'.

User authority: pass. It is an explicit setting touching only this Mac's idle sleep, with no cross-session action. 'Always' is not recommended because it contradicts 'idle sessions cost nothing'.

## Value for the user (4/5)

This user runs several long agentic sessions and multi-agent workflows and often walks away. A run that sleeps silently mid-turn, or a background test that freezes after Claude ends its turn, costs real time and tokens. The feature is small, invisible when working and removes a manual caffeinate habit. The ceiling is limited: lid-close still sleeps, and it does not give 'sessions run while the Mac is closed', which is the cloud or Remote Control domain. A student laptop on battery makes the default and Low Power Mode behaviour matter. Docs note Desktop sessions survive sleep only while the process survives, and it helps quota auto-resume, which waits for Enter if the Mac slept more than about 30 minutes across the reset.

## Experiments before building

- Assertion spike (small, no real Claude): in a dev build with an isolated data root and the fake provider, take and release IOPMAssertionCreateWithName(PreventUserIdleSystemSleep) on a Working edge and confirm via `pmset -g assertions` that it appears and disappears, the display still sleeps, and no entry survives a force-quit of Loom. Decides IOKit vs ProcessInfo.beginActivity, and confirms 'no App Nap side effects'.
- Cron false-Working check (pure state, can be a unit test plus a throwaway real session in an isolated CLAUDE_CONFIG_DIR): confirm a session with `/loop` or a session_cron shows indicator Working today via pendingProviderWorkCount, and that `Stop.background_tasks` counts background bash tasks as well as subagents and workflows. Decides whether the scheduledWorkCount split is needed and whether background shells count.
- Quota-wait state (unknown): observe which registry status and Notification type a Claude session shows while paused for a usage limit (quota_auto_resume_fired/stale/disabled, autoContinueAtUsageLimit, CLI 2.1.234+). Needs a real limit hit or the user's word; do not provoke it on the real account. Decides whether a quota wait should hold the Mac (probably yes if it shows Working and the cap bounds it) or be excluded.
- Clamshell reality check on the user's own Mac: confirm what happens with the lid closed, on power with and without an external display, so the Settings copy is accurate.

## Questions for the user

- Default: off (predictable, user opts in) or on while working (Zed's default)? A MacBook on battery argues for off, or on only on power.
- Should it pause on battery or in Low Power Mode (proposed: pause in Low Power Mode only), or ignore the power source entirely?
- Hold while a turn has background tasks (a test running in the background after Claude ends its turn)? Proposed yes. Cron or /loop sessions are excluded.
- Hold while Needs approval? Proposed no (matches Zed), so an unattended session blocked on you stops pinning the Mac awake.
- Cap on one continuous hold (proposed 6-8 h) and release grace (proposed 30 s): acceptable?
- Indicator placement: menu bar menu line only, or also a footer glyph?
