# I-29: Review comments batched back into the session

Card from the [Loom v2 idea catalog](../IDEAS.md). **Review comments batched back into the session** · verdict **adopt-light** · cost L · value 4/5 · proposed by 10 reports: [orca](../products/orca.md), [conductor](../products/conductor.md), [claude-official](../products/claude-official.md), [codex-app](../products/codex-app.md), [superset](../products/superset.md), [paseo](../products/paseo.md), [warp](../products/warp.md), [emdash](../products/emdash.md), [vibe-kanban](../products/vibe-kanban.md), [review-git-loop](../products/review-git-loop.md).

> Adopt a light version: comments stored in Loom's catalog and staged as a draft (bracketed paste, no Enter) in the pane's own session, with delivery confirmed by a marker in the UserPromptSubmit hook. Auto-send, the skill pull and the mod path are left out. It only exists on top of a Changes pane that Loom does not have today.

## What the user gets

Select lines in the Changes pane, write comments, and send them as ONE structured prompt to the right session (or keep them pending until the turn ends). Review feedback is the step done most after an agent finishes; one batched message with file, line and quoted code cuts round trips.

## Mechanisms found in the research

Comments live in Loom's store as the system of record with sent/unsent state and staleness anchors (store diffIdentity and mark 'outdated' rather than moving them); a batch is always one message, plain text 'File / Lines / User comment' (Orca) or Warp's build_review_prompt style ('run git diff yourself'). Delivery order from review-git-loop: (A) status-gated, hook-verified PTY paste with a 'draft only' default and explicit 'send now' via I-01; (B) pull-at-skill (`/loom:review` constant command + !`cmd` export; export call is Loom's proof of handover); (C) mods $.prompt.submit later; (D) hold pending and deliver at Stop for busy sessions. States: queued / handed over / delivered / outcome unknown; hash mismatch shows truncated/modified. 'Ask about this file' attaches a diff.

## Debates and fact-check corrections

Where the research most disagrees is the transport. review-git-loop prefers B over A; its own fact-check weakens B (injected !`cmd` needs pre-approved commands or the skill aborts; slash commands are exactly what autocomplete swallowed in #15553) and A (Claude needs a typed lead line, pasted text may get <pasted_content> wrapping, invisible-char stripping leaves a draft, long input bursts truncate). Orca's evidence and re-send behaviour are inconsistent (code removes delivered notes, docs say unresolved return). Emdash notes with a real PTY Loom cannot verify acceptance of a paste, but Loom's UserPromptSubmit hook can (with normalization). Mods path may be blocked on managed machines (sec-default mod, allowManagedModsOnly).

## Design in Loom


PREREQUISITE (observed): Loom has no diff or git-status code. `GitBranch.swift` and `BranchCache.swift` only read `.git/HEAD` and never launch git. I-29 therefore needs a read-only Changes view first. The cheapest shape follows the precedent of `EndedScreenView` and the subagent transcript panel. It is shown in place of the terminal (same slot as `model.viewedSubagent` in `DetailView.swift`; Esc goes back). It is a selectable read-only NSTextView with the diff as attributed text, so line selection comes free and there is no custom Core Text renderer. The diff is per file and lazy, because only the selected file's diff is ever fetched. Short-lived git child processes (the `ClaudePlanLimits`/`DiagnosticsExport` `Process()` precedent) use `--no-optional-locks --no-ext-diff --no-textconv`, a 5 s timeout, and an output cap of about 1-2 MiB with the child killed at the cap. Triggers: pane opens, the Stop hook of this session while the pane is visible, window activation while visible, manual refresh. No FSEvents and no timers in v1.

1) STORE (LoomCore, SessionCatalog). New tables `review_comments` and `review_batches`, created on open like the other post-schema-3 additions (no `user_version` bump). Comment fields: session_id, path, new-side start/end line, quote (at most 6 lines, 200 characters per line, invisible Unicode removed), quote_hash, file diffIdentity (hash of that file's diff), head OID, body, state, batch_id.
 - Staleness: do not move comments. On each refresh, compare the quote hash at the stored range. A mismatch marks the comment `outdated`: shown dimmed, left out of the next batch unless the user ticks 'include anyway'. A sent and outdated comment reads as probably addressed.
 - `SessionCatalog+Deletions` must delete these rows, and the delete sheet's dry run should count them. The quotes are the user's work code and are personal data under contract section 8.
 - Quotes and comments are stored; diffs never are.

2) FORMAT (pure function in LoomCore, unit-testable). Merge Orca's File/Lines/Comment blocks, Vibe Kanban's quoted code and Warp's 'run git diff yourself' pointer.
 - First line: 'Review comments (N) on <branch> [loom-review <id4>]'.
 - Then numbered 'path Lstart-end' blocks with a '>' quote and 'Comment: ...'.
 - Then 'Full context: git diff HEAD.' and an end marker '[/loom-review <id4>]'.
 - Markers are ASCII only, because Claude strips invisible characters on Enter. The batch cap is about 12 KiB: beyond that, quotes drop and only the path and line range stay. Turkish characters and prompt-trigger characters (leading '!', '/', '@') must survive; E1 checks this.

3) STAGE (LoomTerminal + ConversationController). Add `TerminalSurface.stageDraft(_:)`, reached through a new `ConversationIntents.stageDraft(sessionID:text:)`, which returns an outcome enum (see 3a). It reuses SwiftTerm's `pasteText`, the same path `insertDroppedFiles` already uses, so it goes through TerminalInputQueue and its single ordered writer. It never sends Enter.
 3a) Refusals, checked against the run's state: no live run (the ended screen or record view keeps the comments pending and offers Resume); `waitingForApproval` or `waitingForInput` ('Needs approval: answer it first'); an `issue` on the session (hook silence); and the engine's `bracketedPasteMode == false`. The last one matters: without bracketed paste, embedded newlines would act as Enter. If E3 shows Claude drops DECSET 2004 in dialogs, this flag is also a free dialog detector. Pasting while Working is allowed, because typing ahead is documented to queue.
 3b) After a successful stage: focus the terminal and show 'Staged in prompt. Press Return to send.' No auto-send in v1: an auto Enter is I-01's job, and its failure modes (autocomplete swallowing Enter, #15553; a draft left behind) are what the draft-only default avoids.

4) VERIFY (LoomCore/ClaudeHook.swift + the Claude adapter). `ClaudeHookEvent` currently keeps only `promptIsSynthetic` and discards the prompt text. Extend it with a bounded scan for the `[loom-review <id>]` start and end markers, parsed at init like `promptIsSynthetic`, without retaining the prompt. The payload cap is 1 MiB, so a 12 KiB prompt is no problem. The adapter publishes a `reviewBatch(id, outcome)` event on the SessionEventHub, and the catalog updates the batch. States, all event-driven:
 - draft: in Loom only.
 - staged: bytes accepted by the input queue. This is not shown as delivered.
 - delivered: a non-synthetic UserPromptSubmit contains both markers. Comments become sent and are kept.
 - delivered, truncated: start marker only (#90910 truncates the start, so the end marker is the check).
 - not submitted: a later non-synthetic UserPromptSubmit has no marker, or the run ended. The comments return to draft. No automatic re-stage.
 Staged is a legitimate resting state while the user thinks. There is no timer.

5) SKIPPED (kept as notes). B (`/loom:review` skill with !`cmd`): its own fact-check says injected commands need a pre-approved allowed-tools rule or the skill aborts, and whether a rule can match `$LOOM_CLI` is unknown. Slash commands are the cases autocomplete swallowed in #15553. Its handover proof is the export call, not the user's prompt. It is only a fallback if E1 shows big pastes are unreliable. C (mods): young API, unsandboxed, blocked on managed machines, and a code-execution surface inside the CLI. D (additionalContext at Stop): it is a system reminder, not a user message, and it does not wake an idle session. E (cross-session inbox, channels): no user authority, contradicts `crossSessionInbound: refuse` in `ProviderLaunchProfile`, and belongs to D-43.

6) ROUTING. Target session = the session whose Changes pane it is. Per-session routing removes the Orca-style 'send to which agent' picker and keeps the action inside the user's own click: no cross-session authority question. The same worktree shared by two sessions is a known ambiguity; the comment belongs to the session where it was written.

## Where it shows


Where it appears:
 - Header: the control group gets a 'Changes' segment with +N -M and a small badge for pending comments.
 - Pane: it opens in place of the terminal (Esc returns), like the subagent panel. A narrow file list sits on the left (status letter, path, +/-) and the selected file's unified diff on the right in the terminal font, without syntax highlighting. Whether it is a right panel instead (D-34) is the user's call.

Making a comment:
 - Select lines, then press 'c' or the margin '+' to get a one-field editor under the selection.
 - Comments appear as cards under their lines, and as a list at the bottom or side: path, L12-15, body, with edit, delete and an 'outdated' badge.

Sending:
 - The bottom bar says '3 comments (1 outdated)' with a 'Stage in prompt' button (Cmd+Return).
 - Staging switches back to the terminal, with focus in it and the text in the prompt box as '[Pasted text +N lines]', plus a one-line notice 'Staged review (3) - press Return'.

State line:
 - The notice is a slim line like `SessionIssueNotice`, with no height animation, going staged, then 'Delivered' when the hook confirms.
 - If delivery cannot be confirmed it reads 'Not submitted' or 'Delivered, possibly cut off (end marker missing)'.

Disabled states:
 - The button is disabled with a reason when the session needs approval, is stopped ('Resume to stage'), or has no live terminal.


## Principle check


- Resources: PASS. Nothing runs while the pane is hidden. Git runs only on pane open, the Stop hook while visible, window activation while visible, or a manual refresh. It is one bounded read of a single file's diff, with a 5 s timeout and a size cap. No watchers and no polling in v1. Comments are small SQLite rows. RISK: `git status` on a huge work repo with ignored build output; mitigate with `--untracked-files=normal` and the timeout.
- Predictability: PASS. Nothing is sent without a click, and nothing is sent without the user pressing Return. Auto-send would break this, which is why it is out.
- Accurate status: PASS and an improvement. 'Delivered' means the hook saw the markers in a real UserPromptSubmit. 'Staged' is never shown as delivered. Truncation is detected through the end marker. A failed or unknown outcome is shown honestly, with no retry. RISK: the markers might not survive some future CLI prompt normalization; the failure mode is a visible 'not confirmed', not a false success.
- Fluency: RISK, accepted. The cost is one Return keypress and a terminal focus switch per batch. This is the trade for removing the Enter-swallow and draft-left-behind failure modes, and is still far fewer round trips than retyping paths and lines.
- Modularity: PASS. The format is a pure function. The store is one catalog extension. The stage API is a narrow intent. The marker is a hook-event field. The Changes pane is a separate component, and review never enters `ProcessSupervisor`.
- CLI-update resilience: PASS. It relies only on the documented `prompt` field of UserPromptSubmit (already registered in `ProviderLaunchProfile`) and on ordinary bracketed paste into the prompt, which a terminal user does constantly. It adds no CLI flag, no skill permission rule, no mods API, and does not pin a version. The stage refusal when 2004 is off is a safety check, not a version assumption.
- Process ownership: PASS. Git children are short-lived and bounded and have no run scope, like the plan-limits child. No daemon.
- User authority: PASS. The target is the pane's own session, chosen by the user, and the user presses Return. This is not the D-43 cross-session channel.
- Contract: the terminal stays the real CLI and no chat UI is introduced. The Changes view temporarily takes the terminal's slot, as the subagent transcript panel already does.
- Data: RISK. Code quotes from the work projects (EDDP) now live in the catalog. They need deletion coverage (`SessionCatalog+Deletions`, the dry run's counts) and should be excluded from the diagnostics export.


## Value for the user (4/5)


The user runs several sessions and many subagents and reviews agent output constantly. Review is the step done most after a turn ends, and it is Loom's biggest gap relative to Claude Desktop, Conductor, Codex, Warp and Orca, all of which ship this loop.
 - Loom's catalog and hook knowledge give it a verified delivery state that none of the PTY-based competitors have.
 - The value is conditional. It only exists if the Changes pane is good enough that the user actually reviews in Loom instead of their IDE.
 - The pane has no syntax highlighting in v1 and is a bigger build than the comment layer.
 - Claude Code's own /diff panel (2.1.287+, with `ask`) already covers viewing diffs, so Loom's differentiator is the comment loop plus the cross-session overview.
 - The draft-only default costs one Return key, so it is slightly less automatic than Desktop's Cmd+Enter.
 - Score 4 only if the Changes pane is built; as a standalone idea it is worth 0.


## Depends on

- The Changes/diff pane idea in the review-git area (git runner, file list, diff text, caps). I-29 cannot ship without it, so the two should be decided together.
- I-01 (verified 'send to session' primitive) is optional and later. It would add an explicit 'Send now' (gated Enter) on top of the same store and format; v1 does not need it.
- SessionCatalog schema addition and deletion coverage (contract section 8, ConversationDeletion).

## Experiments before building

- E1, staging fidelity (isolated CLAUDE_CONFIG_DIR, a throwaway repo, the real CLI; no touching ~/.claude): use the existing `pasteText` path to stage blocks of 1, 4, 12 and 32 KB. The blocks contain Turkish characters, tabs, backticks, quote lines starting with '!', '/' or '@', and a zero-width space. Then press Return and compare the hook's `prompt` field with what was staged. Decides the batch size cap, whether markers survive and in which order (start and end), whether `<pasted_content>` wrapping appears, and whether a typed single-line lead is needed. The question is whether Claude acts on a pasted-only review block or treats it as data, which Orca's pasteNeedsTypedRequest hints at. If big pastes truncate, fall back to a smaller cap with a git-diff pointer, then to option B as a spike.
- E2, state gating: stage while Working (does the prompt queue as documented?), while a permission dialog is open, during an AskUserQuestion, in vim mode, and with the rewind menu open. Decides which refusals are needed on top of the hook state.
- E3, bracketed-paste flag as a detector: does Claude enable DECSET 2004 only while the prompt box is focused and drop it in dialogs? If yes, `Terminal.bracketedPasteMode` is a free dialog detector. If no, rely on hook state alone.
- E4 (cheap, offline): measure `git diff HEAD --no-ext-diff` plus `git status --porcelain=v2 --untracked-files=normal` time on the user's largest work repo to set the cap and timeout. Run only when the computer is idle.

## Questions for the user

- Should the Changes view replace the terminal in place (like the subagent panel, fits D-34 now) or wait for the right panel the user has wished for (subagents, side chat, Changes)?
- Is draft-only (the user presses Return) acceptable as the permanent default, with auto-send only through I-01 later? Or is a one-click send required from day one?
- Is Loom meant to replace the IDE diff view for review? That decides how much polish (syntax highlighting, side-by-side, hunk navigation) the pane needs before the comment loop is worth using.
- May the catalog store code quotes from the work projects (EDDP), with deletion coverage and exclusion from diagnostics exports?
- Should a stopped session keep pending comments and stage them after Resume, or should comments only be allowed on live sessions?
