# I-05: Read-only conversation view of the SAME session (chat-looking transcript, no new engine)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Read-only conversation view of the SAME session (chat-looking transcript, no new engine)** · verdict **adopt-light** · cost L · value 4/5 · proposed by 11 reports: [orca](../products/orca.md), [herdr](../products/herdr.md), [cmux](../products/cmux.md), [t3code](../products/t3code.md), [conductor](../products/conductor.md), [paseo](../products/paseo.md), [zed](../products/zed.md), [emdash](../products/emdash.md), [openchamber](../products/openchamber.md), [chat-ui-paths](../products/chat-ui-paths.md), [power-user-workflows](../products/power-user-workflows.md).

> Build it as a read-only transcript view that reuses the subagent panel's tail/feed/model machinery, shipped first for sessions with no terminal (stopped, stale, after relaunch) and then live, with no composer, no cross-session search and no hook-text dependency. The plumbing is mostly there; the real cost is a faithful main-session decoder, markdown/diff rendering and backward paging, so L stays honest.

## What the user gets

A 'Conversation' tab or panel that renders Claude's own transcript as readable turns (markdown, tool calls folded per turn with expandable rows, diffs, questions), next to the terminal. Ended, stopped and idle records become readable and searchable without a live terminal or process, replacing the static ended-screen snapshot; it is the first safe step toward a chat-centred UI and the base for side chat, right panel and search.

## Mechanisms found in the research

Extend the existing read-only subagent transcript panel to the main session. Incremental FSEvents tail by byte offset + inode (already how Usage reads), bounded cold open (T3: about 75 rows / 1 MiB), windowed/virtualized rows, raw tool bodies loaded only when a row is expanded, render nothing when hidden, never mount all history (OpenChamber lesson), 'latest N steps' while a turn runs. [Transcript JSONL is CLI-internal per SDK typings: lenient decoder, unknown records shown as raw collapsed blocks, recorded fixtures per CLI version, drift detection, fall back to the terminal.] Final text of a turn should come from the Stop hook's last_assistant_message (documented) because transcript_path is written asynchronously and can lag. Order by hook timestamps + transcript sequence, not insertion time. Sending from an ended view = resume the real CLI session.

## Debates and fact-check corrections

Every chat proposal in the research starts here; chat-ui-paths ranks it A1, cheapest big win with zero billing/ownership risk; power-user-workflows calls it the safest chat-UI step. Debate is about WHEN (power-user says only after measuring) and how far a live session goes. Transcript lag means partial streaming output is unavailable (use 'last complete message'). Cost depends on a lenient decoder; Ghostex spends about 5.2k lines of Rust on Claude alone, Conductor/T3/Orca show ordering and scroll polish absorbs effort. Contract rule about never replacing the CLI is kept because it is a view.

## Design in Loom

FIT: the subagent panel (FB4-5) already is the pattern. SubagentTranscriptLocation (realpath inside projects, O_NOFOLLOW, regular file of this user), SubagentTranscriptTail (offset+inode, whole lines only, partial line held back, shrink/replace restarts, cold window), SubagentTranscriptFeed (one vnode source, 200 ms coalescing = at most 5 reads/s, utility queue, AsyncStream, stop() returns at once), SubagentTranscriptModel (feed exists only while onScreen && windowVisible, generation counters, ring), and DetailContent swapping the terminal for the transcript in place. I-05 generalises these to the main session. CORRECTION to the idea text: Usage uses one directory-level FSEvents stream (UsageTranscriptWatcher); for one visible file the per-file vnode feed is lighter than a second FSEvents stream, so reuse the feed, add no stream.

NEW OR CHANGED PIECES (no new target, no schema change, no new dependency):
1. LoomCore, locate: generalise SubagentTranscriptLocation to also accept projects/<folder>/<uuid>.jsonl. The main session's path is not stored anywhere today (ClaudeHookEvent.transcriptPath is parsed at ClaudeHook.swift:442 but only used for subagent meta). Resolve on open, off the main actor: prefer the hook path while a run is live, else ClaudeTranscriptEffort.transcript(conversationID:projectsDirectory:) (folder scan by name, newest mtime wins), with SessionRuntime.claudeProjectsDirectory() as the root. The path is derived, never persisted, so there is nothing to purge on permanent deletion.
2. LoomCore, reader: generalise SubagentTranscriptTail into a TranscriptTail (keep the subagent API as a thin wrapper so its 27 tests stay). Add readBackward(maxBytes) (chunked reverse newline scan from a known offset) for "Earlier turns". Raise the main-session line cap (128 KiB is too small for tool results and Writes), and replace today's silent skip with a counted placeholder (skipped record, N KiB, offset), because a faithful view must not drop turns silently. Cold open reads about 1 MiB from the end (T3's bounded cold open is about 75 rows / 1 MiB), never the whole file.
3. LoomCore, decoder: ConversationParser beside SubagentTranscriptParser. Same technique: memmem gate (attachments and other bulky record types never decoded), a narrow lenient Decodable that never names toolUseResult, and per-block Lossy decoding. Emits records with timestamp, uuid/parentUuid, message.id, stop_reason and a source locator (offset, length). Kinds: userPrompt (+ image count, no base64), assistantText (full text, larger clip than 4 KiB, with a "show more" fetched on demand), toolUse (name, main argument; inline payload kept only for Edit/MultiEdit/Write diffs, AskUserQuestion and ExitPlanMode), toolResult (first lines, line count, byte count, isError), thought(ms) (the existing parser already relies on the CLI writing only a duration), system notes (compact boundary, API error, local command) and subagent calls (Agent/Task). Anything unrecognised becomes .unknown(type, bytes): a collapsed raw row whose bytes are fetched on expand. First sighting of an unknown type or shape is reported once through the existing ClaudeRegistryDiagnostics-style path (log notice + cli_compat_warning journal event), and a count shows in the view the way the Usage page shows "N usage records could not be understood".
4. LoomCore, turn builder (pure, fixture-tested per CLI version): folds records into turns (user prompt, steps, final text), pairs tool_use with tool_result by tool_use_id, groups runs of tool rows ("Ran 4 commands, read 3 files", "Worked for 22s" from first/last timestamps). Order is file order plus parentUuid/timestamps, never insertion time (Orca's #23851 "prompt after response" came from optimistic inserts; a read-only view has none). Whether abandoned rewind branches need a parentUuid leaf-chain walk is decided by the spike.
5. LoomCore, raw bodies: ConversationBodyReader preads one line by (offset, length), re-parses only the wanted block, clips at 256 KiB and marks truncation. Expand = one bounded read; the ring holds only clipped summaries. Never expand-all by default (OpenChamber #2267/#4607).
6. LoomCatalogUI: ConversationViewModel copies SubagentTranscriptModel's gating exactly (feed only while onScreen && windowVisible, stop on selection change/hide/deletion, drop batches from a stale generation). Memory bound: last ~60 turns plus a byte cap per view, one view live at a time, older turns prepended via readBackward. CatalogModel gets a memory-only per-session mode (.terminal/.conversation), like viewedSubagent. DetailContent gets a branch beside the subagent-panel and ended-screen branches, and ConversationDetail (the facts-only record view) is replaced by the transcript with the facts demoted. The live terminal stays with its controller, running, only not shown, so nothing above it resizes.
7. Rendering: LazyVStack of turn rows (or an NSTableView host if the prototype shows SwiftUI cannot prepend rows without a scroll jump; the app already hosts AppKit views, EndedScreenView is an NSTextView). Markdown: Claude answers are lists, fences and tables, which Text(AttributedString(markdown:)) does not render as blocks, so write a small block parser (paragraph, list, heading, quote, fence, table) with inline spans through AttributedString, cached per record and built only for visible rows. Do not add swift-markdown/cmark-gfm for v1. Edit/Write diffs are computed from the tool_use input (old_string/new_string), not from toolUseResult.structuredPatch, which the lean decoder deliberately never reads. Links are never opened and images never loaded (the subagent panel's rule). Selection is per row only, as in the subagent panel; add a Copy turn action.

TRIGGERS (events only): user switches the mode, selects an ended or stale session in conversation mode, a run starts/ends (liveStates), the vnode event on the open file, window visibility. One cold read, then the feed runs only while the view is on screen and the file can still grow. A stopped session's file is read once and its feed stopped; a Resume that appends to the file restarts the feed from the run-start edge. No timer, no poll.

STATUS AUTHORITY: the header pill and cards stay hook/registry driven (D-45). The view never infers Working or Finished from the file. "Working…" renders only when row.indicator says so, and the running turn collapses to the latest ~5 steps plus "+N more" (OpenChamber). JSONL is written per content block or message rather than per token (granularity still to confirm), so there is no partial streaming text; say so in the UI.

HOOK TEXT: Stop.last_assistant_message is parsed (ClaudeHook.swift:445) and kept in ClaudeSessionStatus.lastAssistantMessage (:768), but it is not on the SessionViewState/hub path. With a continuous tail, the vnode event delivers the final text a few ms after Stop, so it is NOT needed for v1. It is useful only as a bounded fallback ("transcript is behind", shown marked after ~2 s) and as the sidebar-subtitle source, which is a different idea. The idea's rule "final text from the hook" fits a poll-at-Stop design, not a tail.

SLICES: A) locate + backward-capable tail + parser + turn builder + read-only view for sessions with no terminal, with fixtures (this is where the value is highest: today the ended screen is memory-only, 16 screens and 4 MiB, and after a relaunch a stopped session shows only the facts grid). B) live tail + the Terminal/Chat toggle for running sessions + diffs/questions + Earlier turns. C) later and out of the light scope: ended-record composer (Resume with the message as the first prompt via the existing startConversation(opening:)/ProviderResume path, confirmed by the first UserPromptSubmit hook), in-view find, FTS cross-session search, unify the subagent panel onto the new engine.

COST RE-ESTIMATE: L, not M. Reuse removes most plumbing (location, tail core, feed, model gating, panel swap, tests' patterns), but still new: a main-session decoder with fixtures (M), turn model (S-M), backward paging (S-M), markdown block renderer plus diff rows (M), list scroll/prepend behaviour (M with risk), mode/header/deletion/resume wiring (S-M), and acceptance scripts (S). Ghostex spends about 5.2k Rust lines on Claude chat, but that includes TUI scraping, which this design omits; Orca and Conductor show that ordering and scroll polish dominate the issues.

## Where it shows

Where: the detail panel, in place of the terminal (the P1 pattern from D-54), using the existing panel chrome and LoomTheme.Typography.transcript tokens, with no new colour classes.

Switch: a two-state control "Terminal | Chat" (label is a user decision; see below) in the session header's control area as a new fixed slot, shown only when a transcript resolves, plus a keyboard toggle. Sessions with no live terminal (stopped, stale, after relaunch) open in the chat view by default. The "This session is not running" notice with Resume stays above it. The memory-only last-screen snapshot stays one click away as "Last screen" for the moment of stopping, or is dropped later (user decision).

Layout: a readable column (about 720-780 pt max) scrolling to the bottom and following the tail only while the reader is at the bottom (same rule as SubagentTranscriptView). Top: an "Earlier turns" row that loads another ~1 MiB backward.

Per turn:
- the user prompt as a quiet block;
- assistant text as rendered markdown;
- a single folded step row between them: "Worked for 22s · 3 commands · 2 edits" with a chevron. Expanded, it lists the Claude-style rows already used in the subagent panel (⏺ Bash(first line), ⎿ first line and "+N lines"). An Edit row shows "file +12 -3" and expands to a bounded diff, and a result row expands to the bounded raw body via one pread.
- AskUserQuestion shows as a read-only card (question and chosen answer); the actual answering stays in the terminal or the existing approval boxes.
- Unknown or skipped records are dim one-line rows ("1 record not shown, 212 KiB") with a raw expand.

Running turn: the current turn shows only the latest ~5 steps ("+14 earlier") and "Working…" only while the hook state is Working. A "Jump to latest" pill appears when scrolled up. Esc and Cmd+F are not needed in v1; find over the loaded turns can come later, stating its scope.

States: "Reading the transcript…", "The transcript is not available" (file gone or drift), and always a fallback hint to switch to the terminal.

## Principle check

RESOURCES: pass if the bounds hold. The feed exists only while the view is on screen and the window visible (copied gating); a stopped file is read once; cold open about 1 MiB; at most 5 reads/s while a turn runs; the ring is capped by turns and bytes; markdown is built for visible rows only and cached; one live view at a time; raw bodies load on expand only. It becomes a violation if history is all mounted, expand-all is the default, the whole file is parsed on open, the feed runs for a hidden or stopped view, or a second always-on watcher is added. The terminal underneath keeps parsing PTY output while hidden (same as the subagent panel today); that cost is already accepted and measured under CPU40, but re-measure it with a visible chat view during a 1 MiB/s run.

PREDICTABLE: pass with a label. It is the same session read two ways. Mode is explicit and per session, read-only is stated, and nothing in it sends input.

ACCURATE STATUS: the main risk. The view must never be the source of Working/Finished/Needs approval (hooks and registry stay authoritative), and it must never drop content silently: oversize, unknown and unreadable records show as rows and counts, and the end of file is shown honestly ("transcript is behind" instead of a guessed final message). It would violate the principle if it showed "Finished" from file contents, or hid skipped records so a turn looks complete.

FLUENCY: pass. Switching is local; cold open is one bounded read; no confirmations. Watch the first-paint time of markdown for long answers.

MODULARITY: pass. The decoder, turn builder and reader live in LoomCore (UI-free, testable with recorded fixtures); the model/view in LoomCatalogUI mirror the subagent files; no new target. It also gives one transcript engine that the future side-chat panel (forked session file) and the subagent panel can share.

CLI-UPDATE RESILIENCE: moderate risk, designed for. The JSONL is declared CLI-internal in the SDK typings and the CLI shipped 26 releases in 30 days. Mitigations: a lenient narrow decoder; unknown records shown as collapsed raw rows; recorded golden fixtures per CLI version (run through loom-fake-provider and an isolated profile); drift reported once through the existing cli_compat_warning journal path; never pin; a graceful fallback to the terminal. Hook payload fields (transcript_path, last_assistant_message) are documented; the file contents are not.

OWNERSHIP: pass. No process is started; read-only O_NOFOLLOW descriptors, closed on hide/stop. Teardown on deletion is required: an fd left open on a deleted file keeps the content readable until it closes, so the view must close on the deletion request and on the .conversationDeleted frame, and write nothing to disk (no cache, no index in the light version), so verified deletion stays true.

USER AUTHORITY: pass. Read-only, with no cross-session reads (it shows only this session's own file); a future composer would be an explicit user action confirmed by the first UserPromptSubmit hook, and the contract's "terminal is the real CLI and is never replaced" holds for live sessions, since this is an extra view.

PRIVACY: transcript text is untrusted; render only, open no links, load no remote images.

## Value for the user (4/5)

The user runs several sessions and many subagents, and the real gaps are catching up on what a long run did ("Finished while away"), reading long markdown answers, and reading any stopped session. Today, after a relaunch, a stopped session shows only a facts grid. The ended screen is a memory-only screenshot of at most 16 sessions and 4 MiB, and the terminal scrollback is 2,000 lines. A transcript view fixes that at zero idle cost, fits the stated openness to a chat-centred UI without breaking the contract (it is a view), and is the shared base for side chat (render a forked session's file), the right panel and a later FTS search. It is not a 5 because input, approvals and slash commands stay in the terminal, so the user still lives in the terminal while working, and the biggest chat-UI payoff (composer plus approvals) is explicitly out of the light version.

## Experiments before building

- E1 fixture-capture spike (about half a day, isolated CLAUDE_CONFIG_DIR via the dev --claude-config flag or an extended loom-fake-provider; never the real ~/.claude; a handful of short real turns per D-04/D-30). Record on CLI 2.1.300: every main-session record type and its fields; one turn each with Bash, Edit, Write, MultiEdit, AskUserQuestion, ExitPlanMode, Agent, compact, /clear, a rewind, a queued prompt and a pasted image. Measure the line-size distribution (decides the line cap and whether the 128 KiB skip is acceptable), write granularity per block or message, Stop-hook-to-file-append latency, whether --resume appends to the same file and keeps the session id (Loom's adoptConversation handles resume/fork/clear, so a Loom session may span several ids/files), and whether rewind leaves abandoned branches. What decides: whether the turn builder needs a parentUuid leaf-chain walk, the cold window size, and whether the live 'latest steps' view is good enough without streaming.
- E2 scroll/prepend prototype on a synthetic 2,000-turn fixture: SwiftUI LazyVStack+ScrollPosition versus an NSTableView host with variable-height markdown rows. Decides: whether a prepend causes a scroll jump, row-height measurement cost, and main-thread time per batch. Run with the computer idle (D-13).
- E3 resource check using the ClaudeUsageCorpusTests-style generator: a 50-100 MB synthetic transcript with 150 KiB to 2 MiB lines. Pass if cold open reads at most about 1.5 MiB (TranscriptTail.bytesRead), no whole-file parse occurs, a hidden or stopped view holds no descriptor or watcher (the openDescriptors test pattern), and total Loom CPU stays under CPU40 with the chat view visible during a 1 MiB/s terminal run.
- E4 markdown fidelity sample: render 20 real-looking Claude answers (tables, nested lists, fences, long links) through the block parser versus AttributedString(markdown:) alone, and decide whether an own block parser is enough or the swift-markdown dependency is worth it (a dependency decision for the user).

## Questions for the user

- What should a stopped or ended session show by default: the chat view, or the last-screen snapshot (D-54)? Should the snapshot stay at all once the chat view exists (it holds about 4 MiB in memory and shows what the user saw at Stop, including a pending dialog)?
- Naming: the code and tabs say 'conversation', but D-37 asked for 'session'. Pick the toggle label (Chat / Transcript / Conversation) and the shortcut.
- May the contract and design wording be relaxed from 'No chat UI' / 'terminal is never replaced' to 'the live session is always the real terminal; Loom adds read-only views'? This is the first step toward the chat-centred direction and touches the contract's core-experience row.
- Scope of v1: ship slice A (sessions with no terminal) first and the live toggle after real use, or both together? Include Edit diffs in v1 or only folded tool rows?
- Is an own markdown block renderer acceptable, or is a new dependency (swift-markdown) allowed, given the vendored-only dependency policy?
- Is it acceptable that live text is per message or block and not per token, and that there is no composer in this idea (typing, approvals and slash commands stay in the terminal until a later composer idea)?
