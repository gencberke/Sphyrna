# I-01: Verified send-to-session primitive

Card from the [Loom v2 idea catalog](../IDEAS.md). **Verified send-to-session primitive** · verdict **spike-first** · cost M · value 4/5 · proposed by 12 reports: [orca](../products/orca.md), [herdr](../products/herdr.md), [superset](../products/superset.md), [warp](../products/warp.md), [codex-app](../products/codex-app.md), [paseo](../products/paseo.md), [zed](../products/zed.md), [openchamber](../products/openchamber.md), [vibe-kanban](../products/vibe-kanban.md), [emdash](../products/emdash.md), [conductor](../products/conductor.md), [review-git-loop](../products/review-git-loop.md).

> Worth building as a small LoomCore primitive (hook-gated, draft-only by default, hook-confirmed 'delivered', never retried), but the safety claim 'never press Enter into a dialog' is not documented anywhere, so a one-day real-Claude spike (send matrix + modal visibility) must decide the constants and whether 'submit' ships at all.

## What the user gets

One safe path that puts text into a running Claude session only when Loom knows it is at an idle prompt, and reports the true outcome (queued, pasted, delivered, outcome unknown). It is the shared foundation for queued prompts, the composer, review comments, canned PR/CI actions, side-answer hand-back and any later cross-session send, and it removes the 'switch to the terminal, paste, hope it was not a permission dialog' step.

## Mechanisms found in the research

1) [PTY; TUI input is undocumented but Loom owns the PTY] State-gated bracketed paste with ONE writer per session (Superset serializes sends so a delayed Enter cannot submit another send's text). Refuse in Needs approval or any modal (permission prompt, picker, /resume menu). Offer 'draft only' (paste without Enter) as the zero-risk mode. Confirm delivery with the documented UserPromptSubmit hook; states queued / pasted / delivered (prompt observed) / outcome unknown; never retry blindly. Practical details from Orca: Claude needs a TYPED lead line before the bracketed paste (pasteNeedsTypedRequest), Enter goes in a separate write after a delay (Orca main path ~500 ms plus a size term; the 50 ms figure is only its renderer note path), and sanitize invisible Unicode yourself because Claude strips it on Enter and then sends nothing (leaves a draft). 2) [documented, complement] hook additionalContext at the next prompt/tool boundary/Stop for 'attach to the next turn' when busy; does nothing for an idle session so cannot be the only path. 3) [documented but young: mods 2.1.287+, API churn, unsandboxed, blockable by org policy] a Loom mod calling $.prompt.submit({text, asUser:true}) once idle, as an optional runtime-detected upgrade. 4) [pull-at-skill] paste a short constant slash command (e.g. /loom:review) and let the skill pull content from Loom's socket with !`cmd` (needs allowed-tools pre-approval; fails if disableSkillShellExecution or org policy). 5) [undocumented, avoid] hidden `claude --prefill` flag (absent from docs, launch-time only, same code path had an RCE fixed in 2.1.118).

## Debates and fact-check corrections

Fact-checks: 'exact hash verification' is overstated (hook prompt has pastes expanded or wrapped in <pasted_content id=...>, invisible chars removed; need normalization or a marker, and Loom does not retain prompt text); Orca's turn-start verifier is NOT used on its diff-note path (two terminal.send calls with status gating), and Orca removes delivered notes while its docs say the opposite; herdr's agent_blocked guard only fires when its scraper already classified the pane and its 5 s effect gate runs after the keystrokes are sent; issue #15553 is a feature request and its failing examples are slash commands (/clear, /model) swallowed by autocomplete, which weakens the 'short constant slash command sidesteps paste quirks' argument. Orca's blind write after timeout (onUnconfirmedDelivery) is the part not to copy. review-git-loop recommends pull-at-skill as default and PTY paste as fallback; the product reports mostly propose gated paste. Contract tension is minimal (input aid, not a UI replacement).

## Design in Loom

WHERE IT PLUGS IN (all verified in the tree)
- Core: new `Sources/LoomCore/SessionInputSender.swift` (actor, owned by `SessionRuntime` beside `claudeAdapter`/`inputGate`; ~300 lines) plus a pure `SendReadiness` gate and `PromptText` (sanitize + normalize), ~120 lines. LoomCore stays UI-free: it decides and sequences; it writes through a small `TerminalInputPort` protocol that `TerminalSurface` implements and registers by runID. `TerminalInputGate` (LoomCore, already the runID registry the surface fills in `TerminalSurface.attach`) is the natural place to hold the port next to the `TerminalInputQueue`.
- Write path: reuse the run's existing `TerminalInputQueue` (one ordered, bounded 4 MiB writer per run; user keys and paste already share it, `TerminalSurface.send`). The sender enqueues `ESC[200~ text ESC[201~` as one chunk, waits one delay, then enqueues `\r` as a separate write. Loom already writes a draft without Enter today (`LoomTerminalView.insertDroppedFiles` -> `pasteText`, UI-MAP line 77), so draft-only is an existing behaviour made gated, not a new class of risk.
- One writer per session: at most one in-flight send per run inside the actor; a second request gets `refused(.busy)` (or joins the Loom-side queue). A delayed Enter therefore cannot submit another send's text. The user is a second writer Loom cannot lock out, so the Enter step re-checks (below).
- State source: `ClaudeSessionAdapter.receive` (ProviderSessionAdapters.swift) already sees every hook event in order after `ClaudeHookStateTracker.receive`. Add one call there: after a non-synthetic `.userPromptSubmit` is applied, `sender.promptObserved(runID, promptID, digest)`; after `.stop` applied, `sender.turnEnded(runID)` (fires an armed 'after this turn' send). `ClaudeHookEvent.init` (ClaudeHook.swift ~l.448) already reads `prompt` only for `promptIsSynthetic`; add a content-free `promptDigest` computed from the normalized prompt (SHA-256, not the text), so Loom still retains no prompt text.
- GATE (`SendReadiness`, pure, table-tested), evaluated before the paste and again right before Enter. Inputs: `ProviderWorkState.activity`, `identity`, `issue`, `stopFailure`, `userRequests` / awaiting-open-approval, deletion fence (`TerminalInputQueue.close`), queue open and not draining, subagent-approval state, user-input proof. Rules: submit allowed only for `.atPrompt` and `.turnComplete` with a clean prompt proof; `.waitingForInput` is draft-only (SessionIndicator and the tracker map idle_prompt, elicitation_dialog and agent_needs_input to the same case, so a question dialog is indistinguishable from an idle prompt until E2 shows otherwise); `.working` -> refuse or Loom-side 'after this turn'; `.waitingForApproval`, `.unknown`, `.failed`, problem/identity-unclear/stop-unverified, no live run -> refuse with a reason string. Never auto-resume a stopped session (resume-and-send is a consumer decision).
- Clean-prompt proof (the hard part, honestly): Loom sees every user byte, which competitors do not, but `TerminalSurface.send` also carries terminal replies, so the counter must sit in `LoomTerminalView` (keyDown, paste, insertText, dropped files; already overridden/owned) as `userInputEpoch`. Core marks the prompt 'touched' on the first user input after a baseline (SessionStart or a non-synthetic UserPromptSubmit), ignoring input that arrives while the state is Needs approval (permission answers are not drafts); event-driven (one callback per baseline), no polling. Touched or input in the last ~2 s -> draft-only or refuse. Residual blind spots that no Loom-side signal closes: client-side pickers (/model, /resume, rewind menu) and text typed during a turn then Stop. Hence 'submit' is an opt-in, per-send button, 'draft' is the default.
- Sequence for submit: gate -> sanitize -> (optional typed lead line, raw, single line, constant from the consumer; only if E1 shows Claude needs it) -> bracketed paste -> sleep(delay) -> gate again + `userInputEpoch` unchanged + queue drained -> write `\r` -> arm one confirm timer (5-8 s) -> `promptObserved` resolves it. Delay constants, lead-line rule and size cap live in one `ClaudeInputProfile` value, not scattered.
- Sanitize (your own, because Claude strips invisible characters on Enter and then submits nothing, leaving a draft): drop ESC and C0/C1 controls except LF/TAB, DEL, bidi/zero-width/other Cf characters, any literal `ESC[201~`; normalize line endings; cap at 32 KiB (larger payloads are a consumer problem: write a file and send a short pointer). Reject a body that starts with `/`, `!`, `&`, `@`, `#` unless the consumer declares `kind: .slashCommand` from a constant allowlist (autocomplete swallows programmatic Enter on slash commands, issue #15553 comments; slash commands are out of scope for v1).
- Outcomes (value type returned to the caller as an AsyncStream of at most 3 updates): `refused(reason)`, `queued` (Loom-side, waiting for Stop), `pasted` (written to the terminal, not submitted; label it 'placed in the prompt, not confirmed': drained bytes are not bytes Claude read, see `closeIfIdle` doc comment), `delivered(matched)` (UserPromptSubmit digest equals), `delivered(unmatched)` (a non-synthetic prompt arrived right after our Enter but the text differs: edited or truncated), `outcomeUnknown` (no prompt in the window; late arrival upgrades it while the tombstone lives; no automatic retry, ever). Matching is two-level because 'exact hash' is overstated: normalize pasted_content wrappers, invisible characters and trailing whitespace on both sides, compare digest of the normalized text; fall back to 'a user prompt arrived'. Only the hook can say delivered.
- Drift handling: journal rare events via `DiagnosticJournal` (`send_unconfirmed`, with CLI version, no content), reuse `ProviderToolchain` executable stamp; two consecutive `outcomeUnknown` with a clean prompt degrade the primitive to draft-only for the rest of the app run and show one line saying so (same spirit as `ClaudeSessionAdapter.hookSilenceIssue`). Nothing pins a CLI version; `--prefill` is never used (hidden, absent from `claude --help` 2.1.300, same deeplink path had an RCE fixed in 2.1.118).
- Bounds: one in-flight send per run, optional queue of at most 5 entries per session, memory only (lost on Quit, contract §7 requires queue persistence/cancellation to be defined: say so explicitly in the UI), 32 KiB per item, two one-shot timers only while a send is in flight, all cancelled on run end, Stop, deletion (`TerminalInputQueue.close`) and Quit (`SessionRuntime.shutdown`).
- Authority: `send(origin:)` takes a required origin; only `.user` (an explicit click or shortcut in Loom) is implemented. The D-43 cross-session sender is a later consumer that adds per-target approval; PTY paste does not satisfy contract §11 CP3's 'using only documented interfaces' gate, so I-01 does not close CP3.

OTHER MECHANISMS FROM THE IDEA
- (2) hook additionalContext: separate feature ('attach to the next turn'), not part of this primitive. Loom's helpers are synchronous 1 s `loom-hook` processes that return no provider decision (ProviderLaunchProfile.claudeSettings), so adding stdout JSON means making the hook wait for Loom's reply on the hot path. Later, optional.
- (3) Loom mod (`$.prompt.read/fill/submit({asUser:true})`): the only mechanism that can read the draft and refuse under a dialog, i.e. it closes exactly the two blind spots above. Loom already passes `--plugin-dir` (ClaudeLoomPlugin), so a mod file could ship there, but it is unsandboxed, 15 days old, API-churning, blockable by org policy and unverified end to end (asUser is missing from the repo's d.ts). Treat as a runtime-detected upgrade after the PTY path, behind its own spike (E4).
- (4) pull-at-skill (`/loom:review` + !`$LOOM_CLI ...`): not the default. The pasted payload is a slash command, which is the failing class in #15553; the injected command needs an `allowed-tools`/allow rule in every Loom session's `--settings`, which is a D-20-class change to CLI behaviour (user decision) and fails under disableSkillShellExecution or org policy. Keep as a later option for payloads over 32 KiB.
- (5) `--prefill`: reject.

FIRST CONSUMER (so it is testable and useful): one 'Send to Session...' popover from the header actions menu (see ui_sketch). Queued prompts, composer, review comments and hand-back are later consumers of the same call.

TESTS: `SendReadiness` as a pure table test; sender state machine with an injected fake port and fake clock (refusal matrix, user typed between paste and Enter, run ends mid-send, late hook after timeout, duplicate/synthetic prompts, single-writer); `ClaudeHookTests` for the digest; the fake provider (`loom-fake-provider`, reads lines with readLine) cannot reproduce bracketed paste or Ink behaviour, so real-Claude evidence comes from the spike, not from the suite.

## Where it shows

v1 has no new chrome and nothing in the sidebar. In the detail header's actions menu (the three-dot group, DESIGN §3 item 6) add 'Send Text to Session...' which opens a small popover over the terminal: multi-line text field, a primary button 'Place in Prompt' (draft-only, default), a secondary 'Send' (enabled only when the gate proves a clean prompt; disabled with a one-line reason otherwise) and, while the session is Working, 'Send After This Turn' (Loom-side, shows '1 queued', cancel, and a note that queued text is dropped on Quit). The popover closes on send and the header shows one transient status line near the state pill: 'Placed in the prompt. Press Return in the terminal.' / 'Delivered' / 'Not confirmed. Check the terminal; Loom did not retry.' / 'Not sent: Needs approval'. Nothing is drawn or watched when the popover is closed; the card and menu bar are untouched (no new redraw source in the sidebar hot path). Stopped sessions: the action is disabled with 'Resume to send'.

## Principle check

Resources: PASS if built as designed (no polling; two one-shot timers only during a send; memory-only bounded queue; digest not text; nothing drawn when hidden). RISK: any 'wait until idle' loop, screen scraping for the prompt state, or a persisted queue would violate it; avoided. Predictability: RISK, the central one. Enter into a permission dialog is the herdr #5263 failure; mitigation is double gating (before paste and before Enter), draft-only default, user-input proof, no blind Enter after a timeout. Residual blind spots (client-side pickers, drafts typed during a turn) are only closed by the optional mod path, so 'Send' must stay an explicit, opt-in button. Accurate status: PASS, only a UserPromptSubmit hook upgrades to 'delivered'; 'pasted' is labelled unconfirmed; 'outcome unknown' is never retried or shown as success (do not copy Orca's blind write after timeout, nor herdr's post-write 5 s effect gate). Fluency: PASS with care; refusals must carry a reason and a one-click alternative (draft, queue), otherwise the primitive becomes a nag. CLI-update resilience: PASS/RISK; only documented hooks (UserPromptSubmit prompt/prompt_id) plus terminal-standard bracketed paste, but the Claude TUI's input handling is undocumented, so delay/lead-line/size constants live in one profile, drift is journaled and the primitive self-degrades to draft-only; never pins a version. Modularity: PASS (LoomCore decides behind a port; TerminalSurface only moves bytes; consumers separate; one hook call site in the adapter). Process ownership: PASS, it only writes to a PTY Loom owns, by runID, and refuses for ended or deleting runs. User authority: PASS for `.user` origin; cross-session origin deliberately not implemented (D-43 needs per-target approval and a documented-interface path). Contract: the terminal stays the real CLI (input aid only); contract §7 'Text transfer' says bracketed paste does not prove acceptance, which this design honours by defining delivered as hook-confirmed only.

## Value for the user (4/5)

For a heavy multi-session, multi-agent user it removes the manual switch-paste-hope step and is the common substrate for a queued-prompt list, a composer, review-comment hand-back and side-answer hand-back, and its hook-verified outcomes are something competitors (Superset #6243, Warp, Orca's note path) do not have. Standalone it is nearly invisible (value ~2) until a consumer exists, and the 'submit' half carries real risk, so I rate the foundation 4, not 5. Honest cost: M covers primitive + draft tracker + one popover consumer + tests; the queue/composer/review features built on it are separate (L together).

## Experiments before building

- E1 send matrix (decides constants and whether 'submit' ships): isolated CLAUDE_CONFIG_DIR, current Claude (2.1.300 here; 2.1.302 latest), a throwaway repo, ~30 short turns inside the D-04 isolated-profile allowance. Vary: bracketed paste with and without a typed single-line lead, Enter delay 50/150/500/1000 ms in a separate write, payload 1 line / 10 lines / 5 KB / 30 KB, texts starting with / @ ! #, invisible Unicode. Record the hook `prompt` text per case. DECIDES: is a typed lead needed (does a bare paste get treated as data), the delay constant, the size cap, the normalization rule for pasted_content/placeholder expansion, and whether truncation is detectable by digest. Pass bar: 20/20 exact or normalized-exact deliveries and 0 stuck drafts at the chosen config; otherwise ship draft-only only.
- E2 modal visibility (decides the gate): for permission prompt, AskUserQuestion, plan-approval, folder-trust, /model picker, /resume picker, rewind menu, autocomplete popup, vim mode, an idle_prompt after 60 s: capture which hook events fire, the registry status, whether SwiftTerm `bracketedPasteMode` stays on, and what a bracketed paste (and a bare Enter) does inside each. DECIDES: which states can be proven idle from hooks alone, whether waitingForInput can be split into idle_prompt vs question dialog, whether the user-input epoch proof is necessary, and whether `bracketedPasteMode` is a usable extra signal.
- E3 native queue: send paste+Enter while Working and see whether a queued message later produces its own UserPromptSubmit and whether a dialog appearing in the 500 ms gap eats the Enter. DECIDES: confirms that Working-state sends stay refused (Loom-side queue instead).
- E4 (separate, optional) mods probe: in an isolated profile ship a trivial mod through --plugin-dir and test `$.prompt.read()`, `fill()` under a dialog, `submit({asUser:true})` and the resulting UserPromptSubmit; also whether Loom's per-run --settings and the user's account/org permit mods. DECIDES: whether to add the runtime-detected dialog-safe upgrade; do not start before E1/E2 are read.

## Questions for the user

- Default mode: 'Place in Prompt' (draft, you press Return) with 'Send' as an explicit second button, or submit-by-default once E1/E2 pass? I recommend draft default.
- Is Loom allowed to press Enter on your behalf at all in v1, only on an explicit click, and only when the gate proves a clean idle prompt?
- While a session is Working: Loom-side 'after this turn' queue (memory only, dropped on Quit, editable and cancellable) or refuse with a reason? The Claude TUI's own queue is not used because a permission dialog can appear before the Enter.
- Stopped sessions: refuse, or later offer 'Resume and send' (resume today cannot carry a first message; the launch `--` prompt works only for new sessions)?
- Approve the spike budget (about 30 short real-Claude turns in an isolated profile, E1+E2) before any build.
- Accept automatic degradation to draft-only for the rest of the app run after two consecutive unconfirmed submits?
- Any later change to every session's --settings permissions (allowed-tools for a pull-at-skill command) or loading an unsandboxed mod is a D-20-class decision; not needed for v1.
