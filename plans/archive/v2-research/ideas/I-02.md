# I-02: Per-session prompt queue with verified delivery

Card from the [Loom v2 idea catalog](../IDEAS.md). **Per-session prompt queue with verified delivery** · verdict **spike-first** · cost M · value 4/5 · proposed by 7 reports: [codex-app](../products/codex-app.md), [paseo](../products/paseo.md), [zed](../products/zed.md), [openchamber](../products/openchamber.md), [vibe-kanban](../products/vibe-kanban.md), [warp](../products/warp.md), [orca](../products/orca.md).

> Worth building as a small Loom-held "after this turn" queue (a different semantic from the CLI's mid-turn queue), but only after a one-day spike proves that pasting and submitting into the real CLI and matching the UserPromptSubmit prompt really works, since "verified delivery" is the whole premise and the shared I-01 primitive carries all the risk.

## What the user gets

Line up the next instruction(s) for a session you are not looking at (or that is still working) in a small strip above the terminal; edit, reorder, 'send now'; Loom delivers when the hooks say the session is Ready and shows queued -> delivered -> failed. Also a global quick-capture hotkey that picks a session and queues text. Removes the wait-then-retype loop across 3-5 sessions, and is the safe user-authorized core of any later cross-session send.

## Mechanisms found in the research

Lightest: Loom-owned persisted queue (small file per session; several ordered items, not one slot) delivered by the Working->Ready/Stop hook event through I-01, marked delivered only when UserPromptSubmit shows the text; cancel or ask when the user types in the terminal meanwhile; refuse delivery into Needs approval; dropped or restored as drafts on Quit and said so (no daemon). Add an unsent-draft marker on the card (Conductor). Documented CLI behaviour to know: typed input already queues while Claude works, and Ctrl+Enter / Ctrl+X Ctrl+S (chat:sendNow, v2.1.275+) sends queued messages now (moves backgroundable work to background since 2.1.281). Loom's added value is cross-session/offscreen queuing and editing.

## Debates and fact-check corrections

Overlap with the CLI's own queue. Competitor queues are a bug magnet: OpenChamber 2.3.0 hidden/out-of-order delivery, Vibe Kanban 'never fires, draft not cleared, single slot, lost on restart' (thinly sourced: #3416 has one top-level comment), Paseo's queue is memory-only. Conductor removed the queue setting in 0.86 but kept a 'waiting until Claude reads it' pending state (concept not gone). Needs captured-transcript tests for ordering and Escape/interrupt interplay.

## Design in Loom

FINDINGS THAT SHAPE THE DESIGN (facts, with sources)
- The CLI's own queue is NOT an "after the turn" queue. Documented (code.claude.com/docs/en/interactive-mode, "Queue messages while Claude works"): a message typed while tool calls run is passed to Claude "as soon as those tool calls finish, within the same turn"; only commands and `!` shell lines wait for the turn end. Ctrl+Enter / Ctrl+X Ctrl+S (chat:sendNow, v2.1.275+) sends now; Up takes queued messages back for editing. So Loom's real differentiators are (a) composing for a session you are not looking at, (b) true next-turn semantics ("when this finishes, do X"), (c) edit/remove before delivery with a Loom-side verified outcome. Persistence is a weaker differentiator: Quit stops every session, so a persisted item for a stopped session can only go out after an explicit Resume.
- Pieces Loom already has: (1) an ordered, bounded write path per live run: TerminalInputQueue (4 MiB, ordered, closes atomically), registered by run id in TerminalInputGate (Sources/LoomCore/TerminalInputGate.swift, TerminalInputQueue.swift). Every live run keeps its TerminalSurface and queue even when not selected (ConversationController.entries); ended runs keep only a snapshot. (2) Turn boundaries from hooks: ClaudeHookStateTracker (ClaudeHook.swift ~L540-790) yields atPrompt (SessionStart), working (UserPromptSubmit), turnComplete (Stop, with background_tasks counts), waitingForApproval, waitingForInput (registry "idle", Notification idle_prompt/agent_needs_input/elicitation_dialog), failed. The registry watch (ProviderSessionAdapters.swift receiveRegistry) covers the Esc-interrupt case where Claude fires no Stop. (3) Precedent for programmatic input: ConversationController.typeForEvidence (evidence only) and LoomTerminalView.insertDroppedFiles -> pasteText (bracketed-paste aware). The D-40 start path passes a first message as the documented positional prompt after `--` (ProviderLaunchProfile.ClaudeOpening). (4) Deletion hooks: ConversationForgetters (ConversationDeletion.swift) and TerminalInputGate.close(runID:) at deletion step 1.
- Gaps found in code: (a) ClaudeHookEvent parses `prompt` only to set promptIsSynthetic and keeps nothing, so "delivered when UserPromptSubmit shows the text" needs a small addition: a digest of the normalised prompt (never the text) in the event. (b) The hub stream is bufferingNewest(1) (SessionEventHub.subscribe), so a quick Stop -> UserPromptSubmit pair can be collapsed; the delivery trigger must not ride the UI frame stream. (c) AgentActivity.waitingForInput conflates "idle for a minute" with "Claude asked a question" (notificationActivity maps idle_prompt, agent_needs_input and elicitation_dialog to one case), so it is not a safe delivery signal on its own. (d) The fake provider's UserPromptSubmit hook carries only prompt_id (loom-fake-provider/main.swift ~L221); tests need a `prompt` field. (e) TerminalSurface.send cannot tell keyboard bytes from programmatic ones, and TerminalInputQueue.lastAcceptedInput counts both.

LIGHTEST VERSION THAT FITS (the "adopt-light" shape once the spike passes)
1. Data (LoomCore). A `prompt_queue` table in the catalog, added on open like ensureActivityColumn/ensureOriginColumns (no schema-version bump, so older builds still open the file): (id, session_id, position, text, state, created_at, attempt_at). `secure_delete = ON` is already set per connection, so a deleted session leaves no prompt bytes. Register a ConversationForgetters entry that deletes its rows, and cancel items at deletion step "stopping" (contract section 8, point 2). Bounds: at most 8 items per session, 16 KiB per item, 64 overall; beyond that the add is refused visibly. A memory-only queue is the fallback if the user does not want prompt text in the catalog.
2. Delivery coordinator: a new LoomCore actor `PromptDeliveryCoordinator`, one file, owned by SessionRuntime. It is fed directly from ClaudeSessionAdapter.receive after tracker.receive applied the event (ordered, inside the run's transition, after updateProviderWorkState), NOT from the hub. It reacts to three inputs only: Stop/atPrompt (candidate boundary), UserPromptSubmit (verification), SessionEnd/run end/delete (cancel). No timers except two one-shot tasks per delivering run: a ~400 ms settle after Stop (a CLI-queued message or a background-subagent hand-back may start another turn at once; if a UserPromptSubmit arrives in the window, wait for the next Stop) and an ~8 s verification deadline after the write.
3. State machine per item: queued -> sending (bytes accepted by the run's input queue) -> delivered (a non-synthetic UserPromptSubmit of this run whose prompt digest equals the item's) | not confirmed (deadline passed, no match; NEVER auto-retried; the strip says "Check the terminal" and offers Retry or Discard) | failed (input queue refused: closed/overflow/writeFailed; text kept) | held, with a reason shown ("needs approval", "you are typing here", "session is working", "last turn failed", "session not running"). Only the head item is in flight, and the next goes after the previous is verified, so ordering is Loom's, not the TUI's.
4. Deliverable gate, checked at the Stop event and never by polling: run live and the card's active conversation; provider state reliable; activity is turnComplete with pendingProviderWorkCount == 0 (or atPrompt; waitingForInput only when the tracker records that it came from the registry "idle" or an idle_prompt after a turn, which needs one small field, lastNotificationType, on ClaudeSessionStatus); never waitingForApproval, failed, unknown, or an open-session approval pending; the user has not typed into this terminal since the last turn boundary. In user words: deliver when the card reads Ready/Finished.
5. Typing guard (LoomTerminal). TerminalSurface already sees every user byte in send(source:data:). Add a flag "user bytes other than a bare Return since the last UserPromptSubmit/SessionStart", and make programmatic submission a separate entry point (`TerminalSurface.submitQueuedPrompt(_:)`, using view.pasteText so bracketed paste is honoured, then Return) that does not set it. If the flag is set the item is held with "you are typing here" and the strip offers Send now. It is a heuristic (history recall, Ctrl+U and menus are invisible to it), which is why the hold and the visible not-confirmed outcome both exist.
6. Stopped sessions. A queued item on a session with no live run shows "waits for Resume". "Resume and send" uses the documented positional prompt (the D-40 mechanism), so no paste is involved and the UserPromptSubmit digest still verifies it. It is an explicit user click, never automatic after Quit or relaunch (no daemon, user authority).
7. Send now on a Working session (not approval) pastes and submits at once, which makes it an ordinary CLI type-ahead message (mid-turn delivery, documented). Do not synthesise Ctrl+X Ctrl+S in v1 (it can move work to the background since 2.1.281).
8. Not in v1: the global quick-capture hotkey (Loom has no global hotkey today; it needs Carbon RegisterEventHotKey plus a floating window; a menu bar item entry or Cmd+Shift+Q on the selected card is cheaper), drag reorder (Move up/down in the row menu instead), slash and bang items (UserPromptSubmit may not fire for local commands such as /model, /status, /clear, so "delivered" cannot be proven; refuse them or label them "sent, cannot be confirmed" until measured), attachments and images, per-item model overrides.
9. Where the code goes: LoomCore (SessionCatalog+PromptQueue.swift, PromptDeliveryCoordinator.swift, digest field in ClaudeHookEvent, lastNotificationType); LoomTerminal (TerminalSurface entry point and typing flag, a controller-level submit intent); LoomCatalogUI (PromptQueueStrip.swift, CatalogModel+PromptQueue.swift, a ConversationIntents method, a queue/draft mark on SessionListEntry). Dependencies still point down and LoomCore stays UI-free.

WHAT WOULD BREAK A PRINCIPLE, AND THE GUARD
- Polling: a "retry until Ready" loop or a periodic queue scan. Guard: only hook-path callbacks plus two one-shot tasks; nothing runs while the table is empty.
- Resources: an unbounded queue, or prompt bodies held in memory for every session. Guard: the caps above; bodies are read from SQLite only for the head item at delivery and for a visible strip.
- Accurate status: calling a PTY write "delivered". Guard: delivered only on a matching UserPromptSubmit digest, otherwise "not confirmed"; no blind retry (contract section 7: "on ambiguous delivery, no blind automatic retry").
- Predictability: answering a dialog by accident (plan approval, AskUserQuestion, folder trust, /resume picker, half-typed input). Guard: Stop-edge delivery only, approval/unknown/failed refused, the typing guard, and the not-confirmed outcome that leaves the text visible in the terminal.
- Authority: any agent writing to the queue. Guard: items come only from the user's own composer; this is the safe first half of D-43's channel, but agent-originated items (loom:open-session style) would need a per-send approval and are out of scope.
- CLI-update resilience: depends on bracketed paste and Return semantics of the TUI and on UserPromptSubmit carrying `prompt` (documented in the hooks reference). Guard: verification fails closed to "not confirmed"; a cli_compat_warning-style journal entry when digests never match across several sends; no CLI pinning.
- Ownership: nothing new is spawned and there is no daemon. Quit keeps items as drafts and says so in the existing QuitConfirmation text ("3 queued prompts are kept; sessions stop").

REVISED COST (for this codebase)
Spike: S (about 1 day). Phase 1: M-L, dominated by UI and tests, not core logic. Rough scope: store + migration + forget hook (~250 lines), coordinator + event plumbing + tracker fields (~400), surface entry point and typing flag (~120), strip UI + composer + row menus + card mark + quit text (~500), tests (digest and ordering on the fake provider with scripted hooks, deletion, input-queue refusal, quit/restore, one captured real-CLI transcript for paste/submit) (~500), docs (ARCHITECTURE section 3 flow, contract section 7 note, DECISIONS entry, DESIGN element). If I-01 is not built first, the paste/submit/verify primitive belongs to I-02, so I-01 + I-02 are one L effort. The global hotkey would add another S-M.

## Where it shows

A slim "Queued" strip in DetailContent's VStack, between RequestList/SessionIssueNotice and the terminal, the same place and style as the approval and open-request boxes (it appears and disappears with a 200 ms opacity fade; the PTY resizes once, as with those boxes). It shows only when the session has items. Collapsed: one line, "2 queued · next sends when this finishes", with a chevron. Expanded: up to 8 compact rows, each with a one-line preview, a state tag (Queued / Sending / Delivered / Not confirmed / Held: needs approval, or you are typing here), and a row menu (Edit, Move up, Move down, Send now, Remove, Retry on a not-confirmed item). Delivered rows fade out after a few seconds; not-confirmed and failed rows stay until dismissed. Adding: Cmd+Shift+Q (or "Queue Prompt…" in the card's context menu and the header action menu) opens a small multi-line sheet or popover for the selected or chosen session; Return queues, Shift+Return is a newline, Esc cancels. The sidebar card gets a small queue glyph with a count (and an "unsent draft" mark), and the menu bar menu can list "Queue prompt for…" later. The terminal remains the real CLI; nothing replaces it. A stopped session shows the strip in the record and ended-screen views with "Resume and send". No new surface when the queue is empty.

## Principle check

Resources: PASS (hook-driven only, caps, one-shot tasks, bodies read lazily). Predictability: RISK, mitigated (the TUI is not a stable input interface; Stop-edge delivery, typing guard, approval refusal, fail-closed verification). Accurate status: PASS if delivered means a matching UserPromptSubmit digest, and "not confirmed" is its own state, no blind retry. Fluency: PASS (an explicit queue entry is the authority, no confirmation per send; the cost is that a Finished card flips straight to Working for queued sessions, so the "Finished" signal for that turn is not shown, which should be said in the UI copy). Modularity: PASS (one coordinator, one store extension, one strip; dependencies point down). CLI-update resilience: RISK (bracketed paste, Return timing and the prompt digest depend on TUI behaviour; drift journal entry, no pinning, fail closed). Ownership: PASS (no new processes, no daemon; Quit keeps drafts and states it). User authority: PASS for user-typed items; any future agent-originated item would need its own approval, so keep the table's source column user-only. Contract fit: contract section 7 already requires persistence, cancellation, size/time limits and deleted-target behaviour for any queue, and warns that bracketed paste alone proves nothing; the digest check is the answer to the second point. D-34/D-43/D-46 are not violated; the terminal-is-the-CLI rule is untouched.

## Value for the user (4/5)

The user runs 3-5 sessions and several workflows; "when this finishes, do X" for a session they are not looking at is a recurring, real need, and the CLI's own queue cannot give next-turn semantics (it delivers mid-turn) or offscreen composing. Not a 5: when the session is focused the CLI queue already covers most of it, a persisted queue mostly dies at Quit, and the value depends on the delivery spike.

## Experiments before building

- S1 delivery fidelity, real CLI 2.1.300, isolated CLAUDE_CONFIG_DIR and a throwaway project: with loom-probe's HookRecorder (Sources/loom-probe/HookRecorder.swift, ClaudeQ1Experiment.swift) record what UserPromptSubmit reports when the app pastes text between bracketed-paste markers then Return, for: a one-line prompt; a 20-line prompt; a 15 KiB prompt (does the TUI fold it into "[Pasted text +N lines]" and what does the hook's `prompt` contain?); text with trailing newline or CRLF; non-ASCII (Turkish) text; a prompt starting with "/" (skill) and with "!". Also test Return in the same write versus Return after a short delay. Decides: whether the digest compare works (exact, or only after normalisation), whether a settle delay between paste and Return is needed, and which item kinds v1 may accept. Pass bar: 100% match over about 50 sends per kind, or that kind is refused in v1.
- S2 input-box conflict: with the same recorder, deliver while (a) the user has half-typed text in the TUI, (b) the /resume or /model picker is open, (c) an AskUserQuestion or plan-approval dialog is open, (d) a folder-trust prompt shows. Decides whether the typing flag plus approval refusal is enough, or whether a screen check (SwiftTerm buffer: is the cursor on the prompt line?) is also needed. If a dialog can be written into silently with no hook state, the feature is limited to the Stop edge only.
- S3 boundary behaviour: capture hook order for Stop followed by a queued CLI message, a background-subagent hand-back, an Esc interrupt (no Stop, registry idle only), and rate-limit StopFailure. Decides the settle window (~400 ms guess) and whether waitingForInput may ever count as deliverable.
- S4 (optional, cheap): measure whether the hook's `prompt` field is ever truncated or altered by other UserPromptSubmit hooks, so the digest is not compared against a mutated text.

## Questions for the user

- Is prompt text allowed in the catalog (SQLite, deleted with secure_delete on session deletion), or must the queue be memory-only and discarded at Quit with a warning?
- Delivery rule: strictly after the turn ends (Stop edge, nothing pending in the background), or also deliver while background subagents/workflows still run? The proposal holds until the card reads Ready/Finished.
- Should a queued item for a stopped session offer "Resume and send" (documented positional prompt) in v1, or only deliver to live sessions?
- Are slash commands and `!` lines wanted in the queue (e.g. /compact between tasks)? They cannot be verified through UserPromptSubmit yet, so they would be refused or marked "cannot be confirmed".
- Global quick-capture hotkey now, later, or never? The proposal defers it and uses Cmd+Shift+Q in the window plus a menu bar entry.
- Does the user accept that a queued turn replaces the "Finished" blue state for the previous turn (the card goes Ready -> Working at once)?
- Build I-01 and I-02 together as one effort, or I-01 first?
