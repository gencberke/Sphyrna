# I-23: Per-session context meter on cards and header

Card from the [Loom v2 idea catalog](../IDEAS.md). **Per-session context meter on cards and header** · verdict **adopt-light** · cost M · value 3/5 · proposed by 5 reports: [zed](../products/zed.md), [usage-tools](../products/usage-tools.md), [vibe-kanban](../products/vibe-kanban.md), [power-user-workflows](../products/power-user-workflows.md), [claude-official](../products/claude-official.md).

> Build a tokens-first, live-sessions-only context figure that rides the existing transcript watcher and usage index and resets on a documented compaction hook; add percent and amber/red only where the window is known, because current models run 1M by default, so the transcript route cannot give a trustworthy percent for the common case.

## What the user gets

See which of five sessions is near its context limit (and about to compact) without switching to it and typing /context; a thin bar or number that only appears from about 50% and turns amber at 70, red at 85; optional 'compact' or 'new session from summary' hint (user-triggered, never automatic).

## Mechanisms found in the research

Transcript-derived, from the incremental reader Loom already has: tokens = input + cache_creation + cache_read of the last main-chain assistant record (max per message id; sidechain/subagents separate), reset from compact_boundary.postTokens, labelled 'approx'. Window size (200k vs 1M) is not reliably in the transcript: show tokens only when unsure (heuristic: assume 1M once any record exceeds 200k, or parse the model suffix; unverified). Exact variant via the I-24 statusLine bridge.

## Debates and fact-check corrections

Mismatch with /context is the top complaint of the tools doing this (ccstatusline #109, #233); advisor/multi-iteration turns double count (claude-hud #666, and the stdin field itself had bugs: 'stdin is trustworthy' should read 'documented and mostly correct'). Window size must come from a documented source, not a hardcoded table (drift). Demand evidence: Oct 2026 outcry when Desktop moved its context ring; Anthropic's mods docs use a context-fill chart as the example. Idle compaction (2.1.299) changes the picture while idle.

## Design in Loom

**Key facts I verified (they change the idea)**
- Anthropic's model-config doc (fetched today via tinyfish) says Opus 4.7+, Sonnet 5+, Haiku 5.5 and the Fable models run a native 1M window with no `[1m]` suffix. They auto-compact at about 967K by default. The user can change this with `autoCompactWindow`, `/autocompact`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW` or `CLAUDE_CODE_DISABLE_1M_CONTEXT`, and Loom cannot see any of these. Opus/Sonnet 4.6 reach 1M only through `[1m]`.
- So for this user the common case is a 1M window. A "50/70/85 percent" scale against an assumed 200K would show false amber at 140-199K tokens. The idea's one-way heuristic ("assume 1M once any record exceeds 200K") is right in direction but fails in exactly that common case, because it only helps after the session has already passed 200K.
- The statusLine stdin JSON is the only documented source of `context_window_size`. The doc itself says it counts "from the last API response" while `/context` adds an estimate, so "approx" is honest.
- Compaction already reaches Loom: `SessionStart` is hooked and carries `source` ("startup", "resume", "clear", "compact", "fork"). `ClaudeHookEvent.Kind.sessionStart(source:)` exists and `ClaudeSessionAdapter` currently treats "compact" as `.automatic`. The hooks doc also lists `PostCompact`, which fires after manual, auto and idle compaction. Loom therefore does NOT need `compact_boundary.postTokens` from the transcript (an internal format). The hook is a documented interface.
- Subagent transcripts ARE indexed: `UsageTranscriptWalker.session(forRelativeComponents:)` maps `subagents/agent-*.jsonl` to the parent session id. The query must therefore exclude sidechain rows (`msg.flags & 1`). It should also exclude files whose path contains `/subagents/`, in case a subagent line lacks `isSidechain` (spike E3).

**Where it plugs in (no new watcher, timer or process)**
1. LoomCore `ClaudeUsageIndex`: add `latestContext(forSessions:) -> [String: ContextSample]`.
   - A `ContextSample` holds timestamp, model symbol text and `input + cw5 + cw1 + cr`.
   - It is one indexed read of the `msg` table (columns `input`, `cw5`, `cw1`, `cr`, `ts_ms`, `flags`, `model`; partial index `msg_session`). Per live session: `WHERE session=? AND flags&1=0` joined to `file` with a `NOT LIKE '%/subagents/%'` guard, `ORDER BY ts_ms DESC LIMIT 1`.
   - Output tokens are excluded, matching the documented `used_percentage` formula.
   - The index already dedupes by message id (it keeps the larger total) and records `sidechain`, `model` and `sessionID` per row (`ClaudeUsageParser.ClaudeUsageRecord`, `UsageDatabase.upsert`). No parser change is needed.
   - If a long session makes `ORDER BY` measurable, add `(session, ts_ms)`. The index file is disposable and rebuilt on a schema bump.
   - Window inference, no hardcoded table: `maxContextByModel()` is `SELECT model, MAX(input+cw5+cw1+cr)` over the 90-day history. A model whose maximum ever exceeded 200K is "extended window known". Otherwise the window is unknown and the UI shows tokens only. This is derived from the user's own data and cannot drift like a table.
2. LoomCore `SessionEventHub` / `SessionViewState`: add `compactedAt: Date?`.
   - It is set from `SessionStart(source: "compact")` in `ClaudeSessionAdapter.receive` (the same place `.subagents` is published), and cleared by a new run, as `subagents` is.
   - A sample is valid only if `sample.timestamp > compactedAt`. This fixes the one real accuracy hole: after a manual `/compact` from 90 percent the bar would stay red until the next API call.
   - If spike E2 shows idle compaction does not send `SessionStart(compact)`, add `PostCompact` to the event list in `ProviderLaunchProfile.claudeSettings`. It is a rare event, unlike per-tool hooks, so the one-helper-per-event cost is negligible. `ClaudeHookEvent.Kind` also needs a `.postCompact` case. Today an unknown name becomes `.unknown` and must not be allowed to change status.
3. LoomCatalogUI: a small `ContextReading` value type (pure, unit-tested like `UsageChipContent`) holding tokens, an optional percent and a level (hidden, neutral, amber, red).
   - `UsageModel.run()` ends in `loadAfterScan`. After a scan it asks the index once for the conversation ids of rows that have a live run (`SessionRowModel.live?.runID != nil`, `live.conversationID`). This is at most about 10 ids.
   - `CatalogModel` patches `SessionRowModel.apply(context:)` only when the value changed, using the existing `apply(live:)` pattern. It should round to whole percent or to 5K tokens, so a streaming turn does not redraw cards.
   - Trigger chain, all existing events: FSEvents `UsageTranscriptWatcher` -> `UsageModel.transcriptsChanged` -> 2 s debounce -> index refresh -> one context read. Gating is unchanged: when no window is active the changes are only collected, and coming back reads just those files. Nothing runs when hidden. On activation or a run start, a live row with no reading gets one read with no transcript scan, because the index persists across launches.
4. Not in v1: any statusLine bridge (I-24), any text typed into the PTY, any notification.

**What would violate the principles, and the avoidance**
- A per-session tail reader or timer: avoided, because it reuses the single FSEvents stream and the index.
- A statusLine bridge spawning a process per assistant message: it conflicts with D-32 and D-20, and it overrides the user's own status line. Keep it as the later exact variant, off by default.
- A hardcoded model-to-window table: replaced by history-derived learning.
- Percent shown with an unknown window: replaced by tokens only, in a neutral colour.
- A stale bar after compaction or a long idle: handled by `compactedAt` plus a "as of <time>" tooltip.
- Drawing for ended or idle records: live runs only. An ended card shows nothing, which matches "idle sessions cost nothing".

**Re-estimated cost:** M, not S. Core query plus window learning with fixtures (sidechain, duplicate ids, an advisor/multi-iteration case, compaction) is about 150 lines plus tests. The hub field and hook plumbing are about 60 lines plus `ClaudeHookTests`. The UI model and row patching are about 120 lines plus a render-count test in the style of `SidebarRenderTests` and `CatalogHotPathTests`. Views and docs (card, header slot, a11y, Increase Contrast, UI-MAP/DESIGN) add the rest. The tokens-only core with no colours is a size-S slice if the user wants it first.

## Where it shows

- **Session card, second row:** a small caption figure such as `412k` between the branch/pin group and the project name/provider icon. It appears only for live runs and above a visible threshold (default idea: 100K tokens, or 50 percent once the window is known). It is secondary-coloured while the window is unknown. It turns the attention orange (`LoomTheme.Status.attention`, the same colour the footer chip uses under 20 percent remaining) at roughly 70 percent and the failure tone at roughly 85 percent, only when the window is known. The card row is already tight (branch, pin, project, 14 pt icon), so the figure must be the first thing to drop on a narrow sidebar, like the footer chip's meter. No bar on the card in v1.
- **Detail header:** a `ContextChip` slot next to the project/branch chip in `SessionHeaderViews` (`HeaderFlowPlan` needs one more optional slot with the lowest priority after the branch). It shows the figure plus a 34x4 meter reusing `UsageChipMeter`, only when the window is known. The tooltip reads "About 412K tokens in context, as of the last reply (2m ago). Approximate: /context may differ." and, for a known window, "of 1M". Accessibility label: "Context about 412 thousand tokens, 41 percent, approximate".
- **Hint:** v1 has none beyond the tooltip. A later user-triggered "Compact..." or "New session from summary" must be a deliberate click, and it must go through the existing open-session approval flow rather than typing into the PTY.
- **Nothing moves:** no reordering, no animation, no badge, no notification, no Dock change.

## Principle check

- **Resources: pass.** There is no new watcher, timer or process. It piggybacks on the existing FSEvents stream and the `UsageModel` observing gate. The extra work is one indexed SQL read of at most about 10 rows after a scan that was already happening. A row is redrawn only when its rounded value changes. Risk: the 2 s debounce means a streaming turn triggers a read every few seconds while the window is active, which is the same cadence as the usage chip today.
- **Predictability: pass.** The figure is hidden under a threshold, positions never move, and it appears only for live runs.
- **Accurate status: the main risk, handled by design.**
  - Percent is shown only with a window learned from the user's own history.
  - "Approx" appears in the tooltip, plus the age of the sample.
  - `compactedAt` removes the stale-after-compact case.
  - The residual risks are real: a user-set `autoCompactWindow` or `DISABLE_1M` is invisible to Loom, advisor turns may double-count `cache_read` (claude-hud #666, spike E1), and `/context` can read higher than the last API response.
  - None of these produce a "success" claim, but the tooltip must not read as exact.
- **Fluency: pass.** There are no clicks and no confirmations.
- **Modularity: pass.** A core query, a pure value type, a row patch and two views. `LoomCore` stays UI-free and dependencies point down.
- **CLI-update resilience: mostly pass.**
  - It depends on transcript `usage` fields, but the usage index already depends on them, parses them defensively and counts un-understood lines in `linesNotUnderstood`.
  - The compaction signal uses the documented `SessionStart.source` and `PostCompact`.
  - No version pinning. The window comes from observed history, not a table.
  - Risk: the `msg` row keeps the larger total per message id, which is fine for the input side. A transcript-format change that drops `cache_*` fields would read as small numbers. Fixture tests and the drift counter cover that.
- **Ownership: n/a**, read-only. **User authority: pass**, because nothing acts on a session. Any later compact or handoff is user-triggered, and typing into a PTY remains out of scope.
- **Standing decisions:** no conflict with D-32, D-34 or the contract. It adds no right rail and no chat UI, and it does not replace the terminal. D-20 is touched only if `PostCompact` is added to the hook list. That is an observer hook that returns nothing, like `SubagentStart`/`SubagentStop`, but it should be named to the user.

## Value for the user (3/5)

The user runs several sessions with subagents and hands off by hygiene, and the token figure also feeds the cache-cold and resume-cost decision. So a glanceable per-session size is useful and there is demand evidence (the Oct 2026 Desktop context-ring outcry; Anthropic's mods docs use a context-fill chart as the example). But current models run 1M natively, so "about to compact" at 967K is rare. The real value is a size/cost awareness figure, not a compaction alarm. That is why it is 3 and not 4-5, and why a percent scale would oversell it. The value rises if the same figure also drives a "cache cold, resume re-reads about 400K" hint on return to an idle card.

## Experiments before building

- E1 (window and accuracy; decides whether percent and colours ship). Use an isolated CLAUDE_CONFIG_DIR with Loom's per-session --settings plus a throwaway statusLine that appends stdin JSON to a file. Run 3-4 short turns on the current default model. Then repeat with CLAUDE_CODE_DISABLE_1M_CONTEXT=1, and with `--model opus[1m]` if an Opus 4.6 variant is available. Compare, per turn, the transcript-derived `input+cache_creation+cache_read` of the last main-chain record against `context_window.used_percentage`, `context_window_size` and `current_usage`. Decides: (a) what `message.model` looks like for native-1M versus `[1m]` versus DISABLE_1M (if the transcript cannot tell them apart, percent stays learned-from-history only); (b) whether the figures match within about 1-2 percent. If they do, ship tokens and percent. If there is a constant offset, show tokens only. Include an advisor/multi-iteration turn if the feature is available, to see whether `cache_read` doubles.
- E2 (compaction signals). Same isolated profile with a hook dumper for SessionStart, PreCompact and PostCompact. Use `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000` (documented minimum) for auto-compaction, a manual `/compact`, and for idle compaction `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` set low (documented, needs 2.1.290+) and a wait of about 54 minutes. The check is whether the idle-compaction run emits `SessionStart(source=compact)`, `PostCompact`, both, or neither, and what the `compact_boundary` transcript line contains. Decides: SessionStart(compact) alone versus adding PostCompact to the launch hooks; and, if neither fires on idle compaction, a sample older than the cache TTL must be shown only as 'as of <time>'.
- E3 (subagent attribution). In the E1 profile, run a turn that spawns a subagent. Check that its lines in `subagents/agent-*.jsonl` carry `isSidechain: true` and the parent's `sessionId`. Decides whether the `/subagents/` path guard in the SQL is needed or just belt-and-braces.
- E4 (no API cost, in-repo). A test fixture check with `ClaudeUsageFixtures`: build a main-chain, sidechain, duplicate-message-id and post-compact transcript, and assert `latestContext` returns the right sample. It is the regression test that must fail without the sidechain filter.

## Questions for the user

- Percent or tokens first? Given native 1M windows, the honest default is tokens (for example `412k`) with colour only once the window is learned. Do you want absolute thresholds you set in Settings (for example amber at 150K, red at 300K, matching your own hand-off habit) instead of 70/85 percent of a window?
- Where may it appear: card second row, detail header chip, tab strip? The card row is crowded.
- Should it show only for live runs (recommended, matching 'idle costs nothing') or also a last-known figure on ended cards, useful before a resume?
- If E2 shows SessionStart(compact) is not sent on idle compaction, may Loom add the `PostCompact` observer hook to its per-session settings (D-20: it changes the launch settings but not CLI behaviour)?
- Is a later 'Compact...' or 'New session from summary' hint wanted? If so, it goes through the open-session approval flow, never as text typed into the terminal. Is that the line you want?
- Is the statusLine bridge (I-24) acceptable later as an opt-in exact source? It overrides the user's own statusLine setting for Loom sessions and spawns a helper per assistant message.
