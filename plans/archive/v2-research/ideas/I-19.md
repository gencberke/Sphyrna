# I-19: Idle auto-park (hibernate): stop the process, keep the card, resume on open

Card from the [Loom v2 idea catalog](../IDEAS.md). **Idle auto-park (hibernate): stop the process, keep the card, resume on open** · verdict **spike-first** · cost M · value 3/5 · proposed by 5 reports: [orca](../products/orca.md), [cmux](../products/cmux.md), [conductor](../products/conductor.md), [supacode](../products/supacode.md), [persistence-remote-orchestration](../products/persistence-remote-orchestration.md).

> Most of the machinery already exists in Loom (SessionLifecycleController idle path, verified stopForIdle, ended screen, --resume), but the user switched exactly this off in D-38, so a half-day spike on resume fidelity and on whether the hook signals are trustworthy must precede a strictly opt-in, visible re-enable.

## What the user gets

Directly serves the wish 'sessions that cost nothing when idle': after N minutes of true idleness a session's process is verifiably stopped while the card, ended-screen snapshot and resume handle stay; opening it resumes the same conversation. Ten open sessions stop being ten live Claude processes.

## Mechanisms found in the research

Manual 'Sleep' action first (cmux request #9873), then opt-in auto-park. Eligibility checklist (Orca/cmux/Conductor): Finished/Idle, not visible, untouched, no unsent input, no running subagents, no unfinished background tasks/monitors/wakeups, no pending approval, no unsettled orchestration. Trigger from state-change events plus ONE one-shot timer per idle session (no repeating ticker); mark 'Parked' only after the run scope's process group is verifiably gone; resume with `--resume <id>` and the ended screen shown meanwhile; make the window cache-aware (about one prompt-cache TTL, 5 min / 1 h) and show 'cache cold' as information. Variant B (Supacode): free only the RENDERER/scrollback of hidden-but-working sessions under memory pressure (DispatchSource), recency-exempt the last 3; needs a retained screen model and Supacode needed a per-dormant reader thread (about 5 wakeups/s).

## Debates and fact-check corrections

Convergent: Orca hibernation is experimental/off by default, 30 min default (1 min-24 h), eligibility includes no live subagent roster; Claude's own supervisor stops idle unattached sessions after about an hour; Supacode's is Beta but ON by default (5 min grace, keep 3). Corrections: cmux hibernation is NOT an idle timer, it evicts the oldest idle background agents only when live restorable terminals exceed maxLiveTerminals (12), off by default, so 'idle N minutes then park' is Loom's own design; Orca's resume is 'the same resume flags' (inference: --resume). Risks: Conductor shipped bugs where background tasks and long workflows were killed on idle; cold resume (cache loss, plus 200K+ conversations get idle-compacted at about 54 min since 2.1.299, idleCompaction setting 2.1.290+) can cost more than the RAM saved for short gaps; resume can fail after CLI updates; users surprised by a parked working-looking card.

## Design in Loom

KEY FINDING: this is not a new subsystem. Loom already has an idle auto-stop, switched off by D-38 (8 Oct 2026; FEEDBACK-1 item 1: the 60-minute stop surprised the user). Sources/LoomCore/SessionLifecycleController.swift has SessionIdlePolicy(idleAfter, stopsIdleRuns), ONE event subscription plus ONE timer for the earliest deadline across all sessions (already better than the idea's "one timer per idle session"; reschedule() runs on state-change frames only), evaluateIdle() with a blocker set (unknownAgentState, activeTurn, waitingForApproval, waitingForInput, pendingProviderWork = Stop.background_tasks + session_crons count, pendingPromptDelivery, recentTerminalInput via TerminalInputGate.lastInputDate, nonBaselineDescendants, ambiguousIdentity, deletionPending), then ProcessSupervisor.stopForIdle (endReason .idle, refuses if providerWorkStateIsReliable is false) and catalog lifecycle .idle (contract 4.3 already specifies the transition contract). AppDelegate.swift:493 passes SessionIdlePolicy(stopsIdleRuns: false); the only other reference is Tests/LoomCoreTests/SessionRuntimeTests.swift:620. The UI side also exists: ConversationController.reconcile -> keepEndedScreen captures the ended screen from the live (even hidden) TerminalSurface and releases the surface; EndedScreenNotice offers Resume; runtime.resumeConversation uses the stored provider id, passes --effort back, and never falls back to a new conversation (ProviderResumeDiagnostics).

WHAT TO ADD (smallest version, "adopt-light" shape once the spike passes):
1. Setting: UIPreferences (ui-preferences.json) "Put idle sessions to sleep", OFF by default, window picker (15 min / 30 min / 1 h / 2 h; recommend default 30 min when switched on). SessionRuntime gets a setter that updates the lifecycle controller's policy (today `policy` is a `let`) and calls reschedule(); turning it off cancels the timer. No new timer type.
2. New blockers in evaluateIdle: (a) viewed: SessionEventHub.viewedSessionID is private, so add a read accessor; the session the user is looking at in a visible, active window is never parked; (b) possible draft: TerminalInputGate.lastInputDate(runID) later than the last UserPromptSubmit/Stop means unsent composer text may exist (Loom cannot read the TUI composer, so be conservative: any keystroke after the last submit blocks until the next prompt); (c) a pending open-session request of that run (OpenSessionCoordinator); (d) deletionPending already exists.
3. Fix two signal problems that would make real Claude sessions never park or park wrongly: (i) the .waitingForInput blocker (SessionLifecycleController.swift:438) cannot tell Claude's idle_prompt reminder (about 60 s after every finished turn) or the registry "idle" sample from a real question, because ClaudeHook.swift:791 and :618 map all of them to .waitingForInput. This is cmux bug #14308 in Loom form. SessionEventHub already distinguishes them (activePhase == .underWay with .waitingForInput at lines 249-252 and 342 versus an at-prompt period), so use "waitingForInput while activePhase is not underWay" as parkable. (ii) ClaudeHook.swift collectionCount(object["background_tasks"]) returns 0 when the key is missing, so a future CLI that drops or renames the documented Stop fields (background_tasks, session_crons; documented in code.claude.com hooks reference, in the CLI since about 2.1.145) would read as "no pending work" and park a session with live background tasks. Require the keys to be present (a Stop that lacks them makes the work state unknown, so no park) and log a cli_compat_warning once, in the style of the existing CLI-drift handling.
4. Drop the DescendantRecheckSchedule backoff (5 s to 300 s repeating re-checks) for parking: treat any non-leader descendant as a hard block that is re-evaluated at the next state event. Cheaper, no timer chain, and the false negative (a silently exited helper delays parking) is harmless. This user's three live Claude processes had no child processes at all when checked, so MCP children are not a blocker for them, but a user with stdio MCP servers would simply never park (conservative and acceptable, maybe a one-line reason in the card tooltip).
5. Trigger set stays event-driven: frames (turn complete, prompt, view change) reschedule; one Task.sleep to the earliest deadline; on fire, evaluate only due sessions. Optional later trigger: DispatchSource memory-pressure event parks the oldest eligible sessions early (zero polling, cmux/Supacode precedent). Skip Supacode variant B (renderer-only freeing): Loom's whole process with 3 live terminals was 75 MB RSS while each Claude is 194-324 MB, so the renderer is not where the memory is.
6. Verified outcome and state: "Asleep" is shown only from the existing succeeded SessionStopReport plus companion teardown, as lifecycle .idle with end_reason idle (no schema change). A failed stop stays the existing "Stop not verified" state. Journal a `park` event (counts and blocker names only, no content) like the other rare events in DiagnosticJournal.
7. Manual "Sleep" is already Stop (Cmd+.): same verified stop, same ended screen, same Resume. The only difference worth adding is that Stop closes the tab (ConversationController.stop) while a sleeping session may keep its tab. Do not build a separate manual path first; ship opt-in auto with the manual menu item reusing evaluateIdle's checklist as an explanation ("Asleep when X finishes").
8. Cache awareness is simpler than the idea says: the server-side prompt cache expires with or without the process, so parking after at least one TTL costs no cache that was still warm; a window of 30 min or more means "cache cold" is true by the time a session is parked. Show it as static text on the ended notice (using last_activity_at, assume the 5 min tier; exact tier only exists in statusLine JSON, so word it "probably cold"). No countdown. Idle compaction (2.1.299, 200K+ conversations idle about 54 min) will not fire in a parked session; whether that is a saving or a loss is part of the spike.
9. Out of scope: Variant B, a daemon, per-session timers, transcript scanning for background work (cmux's 32 MiB tail scan), and anything that keeps a process alive after Quit.

BOUNDS: zero extra wakeups while idle (one sleeping Task for all sessions); evaluation reads the process table once per due session at the deadline; no file reads; ended screens stay capped at 16 / 4 MiB (EndedScreens.swift), memory-only, so more than 16 sleeping sessions or a Loom restart fall back to the record view (ConversationDetail) rather than a screen. Note for D-43/D-46: a future cross-session channel must treat an Asleep target as not deliverable (or ask the user to wake it), never wake it silently.

## Where it shows

Settings (General): toggle "Put idle sessions to sleep" (off) with "after 30 min". Card: label "Asleep" (no dot, same quiet treatment as Idle/Ready/ended per DESIGN; the contract word is `idle` but "Idle" collides with Claude's own registry idle, so rename the label) plus the existing relative time; project stripe, branch, subagent tree unchanged. Context menu: "Sleep" (Stop that keeps the tab) next to Resume. Detail: the existing ended-screen view with the slim notice "Asleep since 14:02. The conversation cache is probably cold." and the filled Resume button (existing "Resuming…" state while it starts). Open behaviour is a user decision: either click Resume as today, or a click-selection (not arrow-key browsing) of an Asleep card resumes at once, which would amend D-45's "Return does nothing on an ended screen / opening launches nothing" for this one state. Menu bar and Dock badge need no change (Asleep is not an attention state). Quit confirmation still counts only Working/Needs-approval sessions.

## Principle check

Resources: PASS and the point of the idea. Measured today on the user's daily Loom: three live Claude processes at 194, 262 and 324 MB phys_footprint (208/306/363 MB RSS) on a 16 GB Mac (about 690 MB swap used), the Loom app itself 75 MB; ten live sessions is roughly 2.5-3 GB. Cost of the feature: one sleeping Task, no polling (drop the 5-300 s descendant re-check). Predictability: RISK, the central one. D-38 exists because an automatic stop at 60 min surprised the user; mitigate with opt-in (off), a visible "Asleep" state, a journal line, never parking the viewed session, and by listing blocker reasons. Accurate status: PASS if "Asleep" is shown only from the verified stop report (existing); RISK from the signal gaps found: idle_prompt/registry-idle lumped into waitingForInput (never parks) and missing `background_tasks`/`session_crons` read as 0 (parks wrongly). Fluency: RISK, resume latency and the extra click, plus lost session-local state (see experiments). CLI-update resilience: PASS with the missing-key fix; relies only on documented hook fields and `--resume`, never pins, resume failure is surfaced and never starts a new conversation (ProviderResumeDiagnostics). Modularity: PASS, extends the LoomCore lifecycle controller; UI only gets a setting, a label and notice text. Ownership: PASS, stop goes through the run scope; nothing outlives Quit. User authority: PASS only while opt-in; the same D-38 reversal would be a violation if it came back on by default.

## Value for the user (3/5)

It serves a stated wish ("idle sessions cost nothing") and the memory is real (200-330 MB per live Claude on a 16 GB machine that also runs Claude Desktop, Xcode and builds), but today the user keeps about three sessions live, so the gain is moderate, Stop plus Resume already gives a manual version, and the user turned the automatic version off once after being surprised. Value rises if the user routinely keeps 8-15 sessions open or the Mac is under memory pressure.

## Experiments before building

- Resume fidelity (half day, isolated CLAUDE_CONFIG_DIR, base it on scripts/perf/claude_resume_real.py; never the real ~/.claude). Start a real Claude through Loom's launch profile, set non-default state (shift-tab permission mode such as acceptEdits/plan, /model, a 'don't ask again this session' tool grant, /add-dir, fast mode, output style, a background Bash, a Monitor, a ScheduleWakeup or /loop wakeup, a todo list, /rename), then Stop and --resume. Record what survives. Decision rule: whatever is lost becomes either a restore flag taken from the transcript (as --effort already is, FB1) or an eligibility blocker (do not park a session in a non-default permission mode or with session grants); if the loss is large and cannot be restored or blocked, the feature stays 'manual Stop only' and the verdict becomes later/skip.
- Signal truth: with real hooks, check what Stop.background_tasks and session_crons list for a background Bash, a Monitor, a running workflow, a background subagent and a ScheduleWakeup wakeup, and what happens to the state after an Esc interrupt (Stop does not fire on user interrupt per the hooks doc). Confirm the idle_prompt arrives about 60 s after a finished turn and that the hub's activePhase separates it from an AskUserQuestion/elicitation. Decision: if wakeups are not in session_crons, they need their own blocker or the feature must refuse sessions that ever used /loop or ScheduleWakeup; if the fields are unreliable, do not enable auto-park.
- Resume latency: time from Resume to the SessionStart hook (atPrompt) for conversations of about 20K, 100K and 250K tokens. Decision: under about 3 s allows click-selection resume; much longer keeps an explicit Resume click with the 'Resuming…' notice.
- Benefit check (read-only, 10 minutes): with N sessions live, compare `footprint` per Claude process and system memory pressure/swap against a parked state. Decision: if the user's real working set is 3-4 sessions and memory pressure is low, defer the feature until it hurts and keep Stop as the manual tool.
- Park-before-compaction side effect: confirm whether a 200K+ idle session that is parked before about 54 min avoids the CLI's idle compaction token spend, and whether the cold resume then costs more or less than the compacted one. Informs the default window (30 min versus 1 h).

## Questions for the user

- Is re-enabling automatic stop acceptable at all after D-38, as a strictly opt-in setting that is off by default (recommended), or should only a manual Sleep exist?
- Default window when switched on: 30 min (recommended, past the 5 min cache tier, before the 54 min idle compaction) or 1 h or longer?
- Opening an Asleep session: keep the explicit Resume click, or resume at once on click-selection (amends D-45's 'Return does nothing / opening launches nothing' for this state only)?
- If the fidelity spike shows session-local state is lost (permission mode, session tool grants, model): restore what can be restored and block parking for the rest, or accept the loss with a note on the card?
- Name: 'Asleep' (recommended, avoids confusion with Claude's registry 'idle') or 'Parked' or the contract's 'Idle'?
- Should a session that has an open tab but is not on screen, or the selected session while the window is hidden for hours, be eligible?
- Interest in the later memory-pressure trigger (park the oldest eligible sessions early under pressure), accepting that a park the user did not time themselves is less predictable?
