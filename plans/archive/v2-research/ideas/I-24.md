# I-24: statusLine bridge for 'official numbers' (context %, cache, cost, effort, PR state)

Card from the [Loom v2 idea catalog](../IDEAS.md). **statusLine bridge for 'official numbers' (context %, cache, cost, effort, PR state)** · verdict **spike-first** · cost M · value 3/5 · proposed by 2 reports: [claude-official](../products/claude-official.md), [usage-tools](../products/usage-tools.md).

> The data is documented and event-driven and the spawn cost is small (about 4 ms CPU per loom-hook spawn, measured), so the real risk is the footer hints and the user's own status line; run a half-day spike on those before committing, and ship only an opt-in, no-chaining light version first.

## What the user gets

Exact per-session figures the CLI itself shows: context percentage, prompt-cache warm-until, per-session cost, effort/fast mode, worktree and branch, and pr.number / pr.review_state for a PR chip, plus rate_limits and per-subagent stats, without heuristics or extra git/gh calls.

## Mechanisms found in the research

[Documented statusline JSON] A tiny per-session statusLine command injected via inline `--settings` that copies stdin JSON to Loom's authenticated socket, then runs the user's own statusLine command and returns its output (chaining). CLI-driven events (new assistant message, compaction, permission-mode change, rate-limit reset, cache expiry; 300 ms debounce). Field availability is version-gated (prompt_cache 2.1.251+, last_miss_cause 2.1.260+, subagent agentType 2.1.293+; rate_limits only for Pro/Max after the first response) and degrades to absent.

## Debates and fact-check corrections

Weakest resource/principle fit in usage-tools: a process spawn per assistant message conflicts with D-32 (no process per update) and D-20 (CLI behaviour changes are a user decision); a custom statusLine hides most CLI footer hints (such as 'esc to interrupt'), overrides the user's own status line (Vibe Island #137 / Open Island takeover class) and double-wraps with claude-hud/ccstatusline; npx/bunx cold start per update is costly (the ccstatusline #22 'per subagent' claim was a 1.0.88 CLI bug). claude-official rates it M/good, usage-tools L/defer until I-23 is measured. Orca respects an existing user statusLine and does not reinstall after deletion (marker file). Decision belongs to the user.

## Design in Loom

Facts first. Nothing in Sources/ mentions statusLine today. Loom already injects an inline `--settings` JSON per session (ProviderLaunchProfile.claudeSettings: `crossSessionInbound: refuse` plus 9 hook events, each running the bundled loom-hook with timeout 1). Env carries LOOM_HOOK_SOCKET, LOOM_HOOK_TOKEN, LOOM_CLI (= helper path), LOOM_CONTROL_SOCKET. SessionRuntime+Claude.ensureHooks creates h-<8>.sock and c-<8>.sock. The contract (LOOM-PRODUCT-CONTRACT.md line 258) says `--settings` "carries only this session's hooks and settings", so a statusLine entry is a small text amendment, not a new kind of change. PERF.md T3 measured a loom-hook spawn at about 3.8 ms CPU, 6 ms wall, 6.5 MiB transient (plans/experiments/cp5-perf-claude-hook.json), and the hook set deliberately has no per-tool hooks. A statusLine fires per assistant message (about one per tool step, debounced 300 ms, in-flight run cancelled), so it has per-tool-hook cardinality: roughly 0.1 s CPU for a 30-step turn. That is small in CPU terms. The real conflicts are D-20 (footer hints, an extra row, the user's own status line) and the literal wording of D-32, not CPU.

LIGHT VERSION (what I would build after the spike):
1. Launch. In `claudeSettings`, when the Settings toggle "Live session numbers" is on (default off, D-20 class, `UIPreferences`), add `"statusLine": {"type":"command","command":"\"$LOOM_CLI\" statusline"}`. The CLI runs the command through a shell, so $LOOM_CLI expands and survives the space in "Loom Dev.app" (the shell-expansion and env inheritance are to be verified in the spike). Gate it on `capabilities.supportsSettings` like the rest. No `refreshInterval` (that would be polling). No `subagentStatusLine` (a second spawn per tick and it changes the agent panel; separate idea).
2. Skip, don't chain. Before adding the key, check whether any settings layer already defines `statusLine`: the profile's settings.json, `<cwd>/.claude/settings.json`, `settings.local.json`, and the managed file. This is a key-presence check, not a precedence reimplementation. If one has it, Loom leaves the session alone and the Settings page says "your own status line is kept". Chaining (running the user's command from the wrapper) is phase 2 and only if the user actually runs claude-hud or ccstatusline; it needs the user's command string resolved across layers, which is the drift-prone part.
3. Helper. A `statusline` verb in Sources/loom-hook/main.swift, handled before the OpenSessionCommand dispatch (today any argument means the open command). It reads stdin with a hard cap (16 KiB; the JSON is a few KB), wraps it in an envelope of a new kind with LOOM_SESSION_ID, LOOM_MANAGED_RUN_ID and the token, and sends it over a new third socket n-<8>.sock or a `kind` field on the hook socket. Exit 0 always. It prints nothing, or one fixed short line if the spike shows an empty row is a problem. Without the Loom env it exits silently, so a session started outside Loom is unaffected.
4. Ingest. Do NOT send it through ClaudeHookIngress or ClaudeHookStateTracker. Status must never depend on these numbers (accurate-status principle). Add a small `SessionNumbersStore` in LoomCore, latest-wins per run (no queue). It decodes with a narrow all-optional Decodable (context_window.used_percentage and context_window_size, prompt_cache.warm/expires_at/ttl, pr.number/url/review_state/kind, cost.total_cost_usd, session_id, version) and ignores the rest, the same discipline as SubagentTranscriptParser. It authorises exactly as the hook server does (token + live runContext) and checks that the payload session_id matches the run's conversation.
5. Publish. `SessionViewState` gets `numbers: SessionNumbers?`, cleared by a new run, a detach and the end of the run, exactly like `subagents` (SessionEventHub.swift). To avoid a sidebar redraw per message, the store publishes only when a displayed value changes: context percentage rounded to 5 percent steps, the warm/cold flip, the PR number or state. H1-D2 patching then covers it (one row patch). Rate-limit and cost values are not published per message.
6. Cache-expiry. The CLI itself re-runs the statusLine when prompt_cache.expires_at passes, so "warm until HH:MM" turns into "cold" with no Loom timer; the label reads expires_at at render time (the same minute-tick pattern as CardTimeLabel).
7. Drift. A required-field check (session_id and context_window absent while `version` is present) journals one `cli_compat_warning` per run of the app, in the same style as D-45's hook-silence and unknown-registry reporting. Version-gated fields degrade to absent. Nothing is pinned.
8. Optional resource win. When a fresh `rate_limits` figure has arrived from a live session in the last few minutes, the get_usage headless ask (D-37) can be skipped, which removes a CLI process. get_usage stays the source when no session is live.

Original full version, for comparison: chaining plus subagentStatusLine plus rate_limits plumbing. That is L to XL.

What would make it a principle violation, and how the design avoids it: (a) hiding the CLI's footer hints, or taking over the user's own status line, without a user decision (opt-in, off by default, skip when one exists); (b) a spawn per update becoming a CPU problem (measured about 4 ms, debounced by the CLI, no refreshInterval, and the spike must re-measure a real 30-step turn with 4 sessions); (c) numbers shown as live when stale (cleared at run end, shown only with their source, a 5 percent step, and an "as of" tooltip); (d) a statusline payload moving the Working/Waiting state (separate path, never touches the tracker); (e) a pr.url from CLI JSON opened blindly (open it only on a user click, https only).

## Where it shows

No new panel and no change to the two-row card. Detail header: the existing project+branch chip (SessionHeaderChip / ProjectBranchChip, 22 pt, HeaderFlow) can gain a trailing "#142" PR token coloured by review state (approved / pending / changes requested / draft) when pr.number is present. A click opens pr.url in the browser. It is the first thing HeaderFlow drops when narrow, after the branch. Context: a thin ring or bar appears on the detail header (and on the card's second row) only from about 50 percent, amber at 70, red at 85; the tooltip says "Context 73 percent of 1M, from Claude Code; cache warm until 14:32" (or "cache cold: next message re-reads about N tokens" when recache_tokens_if_cold exists). Cards of sessions below 50 percent look exactly as today. Settings: one switch "Live session numbers" under General with a one-line explanation: "Claude Code reports exact context and PR figures to Loom. It hides Claude's own keyboard hints and cannot be used together with your own status line." Idle and stopped records show no numbers (they cost nothing, so nothing runs). A session whose own status line is kept shows no figures and the toggle's help says why.

## Principle check

Resources: pass with a caveat. About 4 ms CPU per spawn, CLI-debounced, no polling, no work for idle or stopped sessions, one latest-wins record per live run, 16 KiB cap. Risk: it is a per-assistant-message spawn, the per-tool-hook cardinality the hook set deliberately avoided; D-32's wording ("no extra CLI processes") is amended in its spirit, as D-37 did for get_usage, so it needs a decision note. Predictable behaviour: risk until the spike. Footer hints vanish and a row may appear; opt-in with a clear explanation fixes this. Accurate status: pass. A separate path from the hook tracker, numbers labelled as the CLI's own, absent instead of guessed, cleared at run end. Statusline JSON can lag the in-flight response, so say "as of the last message". Fluency: pass. Nothing waits on it; the script never blocks the turn. Modularity: pass for the light version (one verb, one store, one optional field on SessionViewState, one chip). Chaining would not pass: it reimplements settings layering. CLI-update resilience: mostly pass. It is a documented interface with version-gated fields that degrade to absent, plus a drift check. But statusLine is gated by workspace trust, disableAllHooks and allowManagedHooksOnly, and managed settings beat --settings, so absence is normal and must be silent. Ownership: pass. The helper is a child of the CLI inside the Loom run scope; nothing outlives it; the socket is Loom's own. User authority: pass if opt-in; it overrides nothing without consent, and a user's own statusLine is skipped, not replaced (Orca's rule).

## Value for the user (3/5)

Per-session context % across several live sessions is genuinely valuable for this heavy multi-session, multi-agent user. But Loom can already get an approximate figure from transcripts (the context-meter idea, zero CLI change). Branch is already read from git, effort is already read from the transcript, cost is the same list-price estimate Loom computes, and plan limits already come from get_usage. The unique gains are exact context and window size, cache TTL, and the PR chip. The PR chip only helps if the work repos are on GitHub or GitLab, which I could not confirm from the notes. Against that sit a visible CLI change (hints) and a possible conflict with the user's own status line.

## Experiments before building

- S1 footer hints. In an isolated CLAUDE_CONFIG_DIR (never the real ~/.claude), start the real claude 2.1.300 with `--settings` carrying a statusLine whose command prints nothing, then one that prints a short line. Check by screenshot whether `esc to interrupt` and `? for shortcuts` still appear, and whether a blank status row takes a line. Decides: if hints survive an empty bridge, the user-visible cost is nil and the toggle can default on after one release; if they vanish, keep it opt-in with the explanation above, or drop the idea in favour of the transcript meter.
- S2 override and env. With a second statusLine in the isolated user settings, confirm the inline `--settings` one wins (the notes mark this 'not tested in Loom'). Confirm `"$LOOM_CLI" statusline` expands from the hook env (needs LOOM_CLI and the socket variables in the statusLine process) and that a path with a space works. Confirm the trust-dialog gate (blank until accepted) and that `disableAllHooks` silences it. Decides: whether the quoted-env command is viable or the absolute path must be baked in.
- S3 cost. Count real statusLine invocations per turn on a 30-step agentic turn with 4 concurrent sessions, and measure CPU of the helper with the same method as cp5-perf-claude-hook.json. Decides: if it is under about 0.2 s CPU per turn, the spawn concern is closed; if the CLI re-runs it far more often than once per assistant message, drop the idea.
- S4 payload. Capture one real payload (from the S1 run, into a file in the isolated dir) and diff it against the documented fields: used_percentage, context_window_size, prompt_cache.ttl, pr.* on a repo with an open PR. Also compare used_percentage to /context to settle whether the transcript meter (I-23) is already close enough. Decides: whether this idea adds anything beyond PR state and cache TTL.

## Questions for the user

- Do you run your own statusLine (claude-hud, ccstatusline or a script)? If yes, the light version does nothing for you, and chaining becomes necessary and is the expensive part. If no, the light version is the whole thing.
- Would you accept losing Claude's own keyboard hints (`esc to interrupt`, `? for shortcuts`) in Loom sessions in exchange for exact figures? This is a D-20 call; it may be moot if S1 shows the hints survive.
- Are your work repos on GitHub or GitLab (so pr.* is ever present)? If they are on Bitbucket or something else, the PR chip has no value and the idea shrinks to context % plus cache, which the transcript meter mostly covers.
- Should an amendment to D-32 (a Claude-side helper spawn per message, about 4 ms) be recorded, in the way D-37 amended it for get_usage, if the spike passes?
