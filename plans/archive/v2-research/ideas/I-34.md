# I-34: Ticket-centred sessions (new session from ticket, ticket chip/grouping, derived work ledger)

Card from the [Loom v2 idea catalog](../IDEAS.md). **Ticket-centred sessions (new session from ticket, ticket chip/grouping, derived work ledger)** · verdict **adopt-light** · cost M · value 3/5 · proposed by 3 reports: [emdash](../products/emdash.md), [vibe-kanban](../products/vibe-kanban.md), [power-user-workflows](../products/power-user-workflows.md).

> Adopt only the cheap half (ticket chip, search by key, a user-side 'New session from ticket' sheet using variant (b), reusing the shipped de-dup); defer the Work ledger and tracker write-back, because Loom has no per-session branch or PR state to derive them from yet.

## What the user gets

Group sessions, branches and PRs by ticket key (EDDP-123); 'New session from ticket' with the ticket context in a delimited block the user can edit before sending; a computed Work list (Needs you / Working / In review / Merged) answering 'where was I'; optional, user-confirmed suggestions to move the ticket or archive the session when the PR merges.

## Mechanisms found in the research

Variant (b) no tracker code: first message tells Claude to fetch the ticket with the user's own MCP/CLI, shown for editing before send; variant (a) Loom-side fetch from Linear/Jira with a Keychain token, on demand only, refreshed at send. De-duplicate by ticket key (already shipped). Ticket chip and project-view grouping are modest UI; state is derived from session status, branch and PR (I-31), never a manually maintained board. Write-back (Linear/Jira transition) only as a visible suggestion.

## Debates and fact-check corrections

Do not rebuild issue tracking or a kanban (Vibe Kanban's cloud-dependent board died with the company; users in #3424 said keep the ledger, drop the runner); no webhook auto-triggered sessions (needs a daemon). Ticket text is a prompt-injection vector: always show and delimit it. Emdash's ticket write-back is contested (#1930 unconfirmed). The Atlassian Claude Agent for Jira runs on Managed Agents (API-key, GitHub only), not Claude Code, so it is no evidence for the user's GitLab workflow. The ledger duplicates the activity view unless it adds the ticket dimension.

## Design in Loom

WHAT ALREADY EXISTS (read): sessions.ticket_key and opened_by columns (CatalogDatabase.ensureOriginColumns, added on open without a version bump); CatalogSession.ticketKey/openedBy (SessionCatalog.swift:36-47); SessionCatalog.session(projectID:ticket:excluding:) does the de-dup by ticket_key, else a title that starts with the key (SessionCatalog+Sessions.swift:23); OpenSessionInput validates the key (1-40 of [A-Za-z0-9-_.], OpenSessionProtocol.swift:48-57); SessionRuntime.startConversation(opening:) launches Claude with `-n <title> ... -- <message>` through ProviderLaunchProfile.ClaudeOpening, so the first message is argv and needs no PTY injection or delivery verification. GAPS found: (1) ticket_key is only ever set on the agent-initiated path (loom:open-session, D-40); a session the user starts by hand never has one. (2) ticket_key is not shown anywhere in the UI (only OpenRequestDisplay) and search matches only provider, title and project name (SessionCatalog+Paging.swift:44-49). (3) SessionOpening.openedBy is a non-optional UUID (SessionRuntime.swift:160-167), so the user-initiated start needs it made optional (CatalogSession.openedBy is already optional and the sidebar origin line treats nil as 'user started'). (4) Branch is read per working directory (GitBranch.read, BranchCache keyed by path) and Loom sessions run in the project folder; Loom never creates worktrees. Every session of a project shares one branch, so 'ticket -> branch -> PR' per session is not derivable today.

DESIGN, three small slices, all event-driven:
A. Chip + find (no new state). Display key = ticket_key, else a leading key in the title that matches a user-set prefix list (e.g. EDDP); a bare `[A-Z]+-\d+` regex is wrong ('UTF-8', 'GPT-4', 'SHA-256'). A pure function next to SessionDisplay.swift, evaluated on the record already in memory: no IO, no timer. Draw it in card row 2 beside the branch (SidebarView ~l.460-480; collapse it into the branch slot when narrow, like the origin line) and in ProjectBranchChip (SessionHeaderViews.swift). Add `loom_fold(s.ticket_key) LIKE` to the search condition so typing EDDP-123 finds every session of the ticket across projects; this is the 'where was I' answer for the ticket dimension and reuses CatalogModel+Search.swift unchanged. Prefix list lives in UIPreferences (ui-preferences.json) or a nullable projects column added the ensureProjectColors way; the preference file is lighter.
B. New session from ticket (variant (b)). A sheet (no command palette exists in Loom; entry points: the project header '+' menu, File menu item, a shortcut): project, ticket key (validated by OpenSessionInput's rules), title prefilled '<KEY> - ', and a first-message TextEditor prefilled from a template with {key}. Default template tells Claude to fetch the ticket with the user's own Jira/Linear MCP or CLI and to wait for a go-ahead before changing code; the user can replace it with `/their-skill {key}`. The sheet shows exactly what will be sent, editable; nothing is sent until the button is pressed (user is the authority, so no approval box; the agent-opened path keeps its box). On key entry and again at submit, call the shipped catalog.session(projectID:ticket:); if a session exists, show 'EDDP-123 already has a session: Show Session' instead of Start. Start goes through ConversationIntents.start with an opening whose openedBy is nil. Extract the 'validate, re-check ticket, startConversation(opening:)' core now duplicated between OpenSessionCoordinator.approve (~l.330-348) and the new path into one function so there is one launcher.
C. Deferred: Work list and PR/merge suggestions. They need I-31 (PR/MR state: gh or glab on demand at Stop events or window activation, not polling) AND a per-session branch identity (worktrees, or the hook payload's cwd, which ClaudeHook parses at ClaudeHook.swift:444 but nothing stores). Without both, 'In review / Merged' would be a guess, which violates accurate status. 'Needs you / Working' columns are exactly the activity view's Active section, so the ledger adds value only through the ticket dimension, which slice A already gives. Revisit after I-31 and a worktree decision. Project-view grouping by ticket also fights keyset paging (lists page by creation order per project, CatalogModel+Search/Paging), so do not group rows in v1; use the chip and search.

BOUNDS: sheet is on demand; one folded LIKE inside the existing search query; message <= 64 KiB (OpenSessionLimits); template text capped; no network, no Keychain, no tracker SDK, no webhook, no daemon.

VARIANT (a) (Loom-side fetch): not recommended. It adds Keychain tokens, per-tracker REST shapes (Jira ADF descriptions, Linear GraphQL), rate limits, tracker drift (the exact CLI-update-resilience problem Loom avoids for Claude), network access in a 'very low resource' app, and a real prompt-injection channel inside Loom's own UI path. Variant (b) puts ticket text through Claude's normal tool-result path under the user's own MCP auth. If ever added, show and delimit the fetched text and refresh at send, as Emdash does (buildFinalPrompt / refreshLinkedIssueContext).

WRITE-BACK: only ever a visible suggestion after a verified merge; skip in this idea. Emdash #1930 is contested/unconfirmed (emdash.md fact-check) so it is no evidence it works.

## Where it shows

Sidebar card row 2: `[EDDP-123] arrow.triangle.branch feature/x` (key in the secondary text style, same size as the branch; the key replaces nothing, it is dropped first when narrow, after the origin line). Detail header chip: project stripe | EDDP-123 | branch. Search field: typing a key shows all that ticket's sessions in either view. Project header '+' menu gets 'New Session from Ticket...' (and a File menu item): a sheet with Project popup, Ticket field (inline red text if invalid, orange 'already has a session - Show Session' if the key exists in that project), Title field, a monospaced multi-line 'First message' editor prefilled from the template, buttons Cancel / Start Session (Return does not submit from inside the editor). No new sidebar mode, no right rail (D-34 untouched), terminal stays the real CLI (contract untouched).

## Principle check

Resources: pass (chip is pure over in-memory records; one extra folded LIKE in an existing query; sheet on demand; no polling, no network). Predictability: pass, provided the prefix list is explicit; risk if keys were guessed with a loose regex (false chips on UTF-8/GPT-4). Accurate status: pass for slices A/B (start result is the existing verified start path; de-dup is a catalog fact); RISK for slice C: showing In review/Merged without verified per-session branch and PR state would be a false-status surface, hence deferred. Fluency: pass (removes copy-paste of ticket context; the editable-before-send step is one intentional pause the user asked for). Modularity: pass if the open-request launcher is extracted and shared; risk of a second copy of the start logic otherwise. CLI-update resilience: pass (argv `-n`/`--` already used, drift already reported; variant (b) has no tracker API; a skill-name template is user content Loom does not pin). Ownership: pass (session starts in a Loom run scope as usual). User authority: pass (user-initiated, visible message; no auto-triggered sessions, no tracker writes).

## Value for the user (3/5)

Fits the user's two ticketed work projects and the HN-style session-per-ticket workflow in power-user-workflows.md, and de-dup is already built. But the user can already type the prompt or use their own skill, ticket text fetching depends on their MCP, and the high-value half (PR/merge-derived Work list) is blocked on I-31 and worktree identity; the research itself says the ledger duplicates the activity view and that the ceiling is 2-3 parallel sessions, so a ticket board is low leverage for one person.

## Depends on

- I-31 (PR/MR state, glab for GitLab) for any In review / Merged column or merge suggestion
- A per-session branch identity (worktree-per-ticket convention or storing the hook payload cwd) for ticket-to-branch derivation
- Making SessionOpening.openedBy optional and extracting the shared validate/de-dup/start function from OpenSessionCoordinator

## Experiments before building

- Spike 1 (isolated CLAUDE_CONFIG_DIR, a trivial skill): does `claude -n t ... -- "/my-skill EDDP-1"` execute the skill as the first prompt in interactive mode, with Loom's --settings/--plugin-dir flags present? Decides whether the template can be a slash-command invocation (clean, user-owned) or must be plain text.
- Spike 2: with the user's own tracker MCP configured in a throwaway profile (or described by the user), does a Loom-launched session reach the MCP and finish OAuth inside the PTY without a first-run stall that the hook-silence watchdog would flag? Decides whether variant (b) works out of the box.
- Spike 3 (read-only, on the user's catalog copy or by asking): how many existing sessions' titles start with an EDDP-style key versus have ticket_key set? Decides whether the title-prefix derivation in slice A is accurate enough or needs the user to start via the sheet to get real keys.

## Questions for the user

- Which tracker and which key prefixes do the two work projects use (EDDP- only? Jira or Linear?), and does the user already have an MCP or a skill that fetches a ticket?
- Does the user use one git worktree per ticket? If not, a per-ticket branch and PR cannot be derived and the Work list should stay skipped.
- Is a modal sheet from the '+' menu acceptable, or is a keyboard-first quick entry (shortcut, key field only, default template) preferred?
- Default first-message template: 'fetch the ticket and wait', or 'fetch and plan', or a user skill name?
- Should the ledger wait for I-31, or is chip + search by key enough and the Work list dropped?
