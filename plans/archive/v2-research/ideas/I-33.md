# I-33: Fast launch surface: new-session sheet, presets, loom:// URLs, recipes, skills launcher

Card from the [Loom v2 idea catalog](../IDEAS.md). **Fast launch surface: new-session sheet, presets, loom:// URLs, recipes, skills launcher** · verdict **adopt-light** · cost M · value 4/5 · proposed by 5 reports: [cursor](../products/cursor.md), [warp](../products/warp.md), [emdash](../products/emdash.md), [power-user-workflows](../products/power-user-workflows.md), [codex-app](../products/codex-app.md).

> Build the new-session sheet, JSON presets/recipes and a prefill-only URL on Loom's existing launch path, show the permission mode from the documented hook field, and drop the skills browser, hotkey and Loom-side worktree creation (worktrees wait for I-32).

## What the user gets

Starting the third parallel task takes seconds: a palette-style sheet (project, branch or worktree, plan/permission mode, effort, first message) with an empty state listing the two work projects and recent ticket keys; saved presets (and 'Save this session as preset') reachable from a '+' menu, from Raycast or scripts via loom://preset/<name>; reusable prompt recipes; a launcher for the user's skills and commands.

## Mechanisms found in the research

Launch-time only, no live process: documented CLI flags with drift detection (show plan mode/effort only when detected), permission mode shown on the card afterwards; presets as TOML/JSON (project, branch/worktree template, Claude options, first message, colour) built on the existing 'a session opens a session' flow; URL scheme behind the same user-authority gate; worktree presets use verified git calls (I-32); recipes = project + prompt + worktree choice from the palette; skills/commands browser as launcher, not manager; global quick-capture hotkey (Codex).

## Debates and fact-check corrections

Skip Cursor's plan tab / Build in Parallel (Claude's plan lives in its terminal). Branch/worktree choice must not silently switch the user's working tree. URL schemes widen the attack surface. Plan-mode flag availability varies by CLI version.

## Design in Loom

FACTS CHECKED
- Starting a session today is one click and carries no options: CatalogModel.startConversation -> ConversationController.start -> SessionRuntime.startConversation(provider:projectID:opening:) -> claudeProfile -> ProviderLaunchProfile.claude. Only --session-id, --settings, --plugin-dir, resume-time --effort and the D-40 opening (-n title, then "-- message") are passed. Loom passes no permission-mode flag and no model flag.
- The installed CLI (2.1.300 --help) documents --permission-mode <mode> (choices acceptEdits, auto, bypassPermissions, manual, dontAsk, plan), --effort, --model, -n/--name, and -w/--worktree [name]. ProviderCapabilities already parses --help for --effort and --name, and missingRequiredClaudeOptions/reportCompatibility already log drift without refusing a start. "Show plan mode only when detected" therefore needs one more parsed option plus a parsed choices list.
- Claude's docs list permission_mode as a common hook-input field ("manual" arrives as "default"; not every event carries it). Loom's ClaudeHookEvent does not parse it (grep finds no permission_mode in Sources). Showing the mode on the card can come from this documented field, so it stays right after the user presses Shift+Tab, instead of from launch intent.
- There is no URL scheme anywhere (no CFBundleURLTypes in scripts/package-dev-app.sh or scripts/release/build-loom.sh; no application(_:open:) in loom-app). The control socket used by "a session opens a session" is authenticated by a live session's LOOM_HOOK_TOKEN and always ends in the approval box. A URL has no token, so it cannot reuse that gate as it is.
- Catalog sessions already store workingDirectory per session, project, ticket_key (SessionCatalog.session(projectID:ticket:) is the de-dup lookup) and opened_by. SessionOpening.openedBy is a non-optional UUID today; createSession already takes it optional.
- Worktrees: documented claude --worktree creates .claude/worktrees/<name> on branch worktree-<name>, then the session's cwd and transcript move there. Loom's catalog working directory would stay the repo root, so GitBranch.read (card and header branch) would show the wrong branch. CleanupCoordinator's linked-worktree protection and Loom's resume assumptions would not see it. The CLI's own exit prompt (keep or remove) never appears because Stop kills the process. A worktree Loom creates itself (git worktree add, then start with workingDirectory = the worktree) keeps all of that consistent, but it is the worktree-lifecycle work of I-32 and must not be smuggled in here.

LIGHTEST DESIGN (four layers, each independently shippable)
1. Launch options in LoomCore (the base for everything else). New value type ClaudeStartOptions {permissionMode?, effort?, model?} passed into ProviderLaunchProfile.claude(route: .new) next to opening. ProviderCapabilities gains supportsPermissionMode and permissionModes (the choices parsed from the --permission-mode help block). The sheet offers only modes that are both detected and on Loom's allowlist (Manual, Plan, Accept Edits, Auto). bypassPermissions and dontAsk are not offered anywhere in v1 (user authority; the user can still Shift+Tab inside the TUI). Not detected means the control is hidden, and an undetected flag is not passed. SessionOpening becomes "SessionStart intent": title?, firstMessage?, ticketKey?, openedBy: UUID? (nil = the user started it), options. SessionRuntime.startConversation takes it; the D-40 path keeps passing no options, so an agent can never choose a mode (an agent-requested session cannot escalate).
2. New Session sheet (LoomCatalogUI, e.g. NewSessionSheet.swift + NewSessionModel, presented from CatalogModel). Fields: project (defaults to contextProjectID; the two work projects first, then others, plus "No project"), ticket key, title (auto), mode, effort, first message (multi-line; a leading "/skill args" works because that is how the CLI is typed, so no skills browser is needed). Empty state: the project list and "Recent tickets" from one bounded catalog query (DISTINCT sessions.ticket_key by last_activity_at, LIMIT 8) run when the sheet opens. While the user types a ticket key, the sheet does the same de-dup lookup as OpenSessionCoordinator and shows "EDDP-123 already has a session - Show" instead of starting a copy. Return/Cmd+Return starts; Esc closes. Start goes through the same ConversationController.start path, so busy/starting state, startingNew guard and error reporting are unchanged. Cmd+N keeps the instant one-click start; the sheet is a second entry (proposal: Option+Cmd+N, footer + menu "New Session...", project "+" menu).
3. Presets = recipes (one concept, not two). One JSON file per preset in <data root>/presets/<name>.json (Foundation Codable, no TOML dependency; Loom has no TOML parser and SwiftTerm is the only package). Fields: name, project (exact name or path, resolved at use like --project in OpenSessionInput, never created), ticketTemplate?, title template?, permissionMode?, effort?, model?, message template with {ticket}/{title} placeholders. No colour field (projects already carry D-48 colours). PresetStore is a small LoomCore type: read the folder when the + menu or sheet opens (on demand, at most 64 files of at most 64 KiB, lstat/regular-file checks, atomic 0600 write, unknown keys ignored so a newer file does not break an older Loom). No FSEvents watcher in v1. "Save this session as preset" (session context menu, SessionMenuItems) writes a preset from the card's project and the options Loom started it with. A preset chosen in the + menu with a clear, safe summary (e.g. "plan, high, project") starts at once or opens the sheet prefilled when the preset has a {ticket} placeholder.
4. loom:// as a PREFILL-ONLY entry. The handler (AppDelegate application(_:open:), URL parsed by a pure, tested function in LoomLaunchOptions or LoomCatalogUI) only opens the sheet with the preset (or explicit query items project/ticket/title/message) filled in. It never starts a session; the user presses Start in Loom with the full resolved message and options visible. That keeps the same user-authority rule as D-40, defends against any web page or local process firing a URL, and means no new socket or token. Dev builds register a different scheme (BuildIdentity owns production vs development names) so Loom Dev and Loom never fight for the handler. URLs received before the runtime is up are held until startupTask finishes. Raycast calls "open loom://preset/<name>".
Later and optional, on the user's word: a per-preset "start without asking" flag for trusted presets from the + menu only (never from URL).

NOT BUILT (and why)
- Skills/commands browser: the CLI's "/" menu already lists them, and a Loom-side lister must reproduce Claude's resolution rules (user, project, plugin, bundled, skillOverrides, user-invocable false, .claude/commands) and read the user's real ~/.claude. That is the drift and ownership risk the principles warn about. The free-text first message already takes "/skill args". Revisit only if the user later says discovery hurts.
- Global quick-capture hotkey: it is a different feature (queue a prompt to a session) and Raycast + the URL cover launching.
- Cursor plan tab / Build in Parallel: confirmed skip; plan mode is only the --permission-mode plan flag, and the plan stays in the terminal (contract: terminal is the real CLI).
- Loom-created worktrees or claude --worktree: belongs to I-32. Until it lands, a preset may carry an optional absolute directory (resolved and checked like a project) so a worktree the user made by hand can be started; nothing is created or removed here.

WHAT TO SHOW AFTER LAUNCH
Parse permission_mode (and optionally effort.level) from the documented hook JSON in ClaudeHookEvent, keep the latest value in the tracker's view state (only when the field is present; "default" displays as Manual), and show it as a small text chip in the detail header or tooltip, with no new status colour and no new animation. This is observation, not launch intent, so it is accurate after Shift+Tab. It is an independent slice (S) and would also serve other ideas, so it could ship first.

WHERE IT HURTS IF DONE WRONG
Polling/watchers for presets or skills, a permanent socket for URLs, a URL or agent that can start without a click, a bypass mode in one click, a Loom-side worktree that leaves the card showing the wrong branch, an options UI that goes stale when the CLI changes its choices. The design above avoids each by being launch-time only, on-demand reads, detection-gated, and approval-gated at the external boundary.

## Where it shows

Entry points: footer "+" menu gets "New Session..." (Option+Cmd+N) and a "Presets" submenu listing each preset as "Name  -  project, plan, high" (a non-empty first line, since the user must see what a click will do); project header "+" menu gets the same project-scoped; File menu keeps Cmd+N as the instant start. Session context menu: "Save as Preset...".

The sheet is a compact palette-style panel (about 460 pt wide, 10 pt radius, theme tokens, appears with opacity only): row 1 project picker with the project colour stripe (work projects first); row 2 ticket field with a Recent chips line under it (EDDP-142, EDDP-139, ...) and an inline "already has a session - Show" notice when it matches; row 3 title (auto placeholder); row 4 two compact pop-ups, Mode (only detected ones) and Effort (only when --effort is detected); row 5 first message editor (3-8 lines); footer: Presets popup on the left, Cancel / Start (Cmd+Return) on the right. Empty state when no project is selected: the project rows themselves, so the first keystroke picks one. A preset or URL opens it prefilled and the Start button shows the resolved mode and effort in its label. After launch the card behaves as today; the header chip shows the live mode ("Plan") from the hook field. No new window chrome, no animation, no status words on cards (DESIGN section 2.4 holds).

## Principle check

Resources: pass. Everything is launch-time; presets and recent tickets are read on demand (bounded 64 files x 64 KiB; one LIMIT 8 query); no timer, watcher or process is added, and a closed sheet draws nothing. Risk only if someone adds a preset folder watcher or a skills scanner. Predictability: pass. Same start path, same startingNew guard; a preset's resolved options are shown before an external launch; project is resolved by exact name/path, never created. Accurate status: pass with one rule. 'Started' still means the verified scope launch. The permission mode on the card comes from the hook field and is hidden when absent; Loom must not claim a launch-time flag was applied, so a flag it did not detect is never shown or passed. Fluency: pass. One extra keystroke for URL starts is the deliberate cost; the + menu preset start can be one click. Modularity: pass. New code sits in three seams (ClaudeStartOptions/capabilities in LoomCore, PresetStore in LoomCore, sheet in LoomCatalogUI); nothing touches the terminal, supervisor or ledger. CatalogModel is already 1,600+ lines, so the sheet model must live in its own file and extension. CLI-update resilience: pass with a spike. Options are gated on parsed --help text like --effort/--name; the permission choices list is parsed, not hard-coded; unknown choices are ignored and the missing-option notice goes to the journal. The 'manual' versus 'default' naming already differs between flag and hook, which is exactly the drift the parse must tolerate. Process ownership: pass. No new process or socket; worktree creation (which would own files outside the run scope) is deliberately deferred to I-32. User authority: the key risk. The URL is prefill-only, agent-initiated opens (loom-hook open) get no mode or effort argument, bypassPermissions/dontAsk are not offered, and presets are user-authored files that an agent could in principle write, so any preset from outside the + menu goes through the sheet. D-20 (settings that change Claude behaviour are the user's decision) is satisfied because the user picks each option per launch. Contract: pass; the terminal remains the interface and no chat UI is added. D-34 is not touched.

## Value for the user (4/5)

The user already runs about three parallel sessions across two ticket-keyed work projects, and today each start is a bare click followed by retyping the same plan-mode preamble or ticket prompt. The sheet's ticket de-dup, plan mode, effort and first message remove that, and Raycast/URL starts help a backend dev who works across apps. The gain is real but bounded: the instant Cmd+N already exists, plan mode can be reached with Shift+Tab, and the heaviest pieces of the original idea (worktrees, skills browser) are deferred or dropped.

## Depends on

- I-32 (worktree lifecycle) for any worktree field; until then only an optional absolute directory in a preset
- Reuses D-40/D-42 start path and the ticket de-dup in SessionCatalog.session(projectID:ticket:)
- Optional: the permission_mode hook-field chip is an independent slice that other ideas (plan-mode awareness) can share

## Experiments before building

- Isolated-CLAUDE_CONFIG_DIR spike with the real claude binary: start `claude --permission-mode plan --effort high -n T -- "first message"` in a PTY and confirm the TUI starts in plan mode, the message auto-submits, and a first message beginning with "/skillname args" invokes the skill. Decides whether the free-text field can stand in for a skills launcher; fails -> keep the field plain text only.
- Same spike, record the raw hook JSON for SessionStart, UserPromptSubmit and Stop (with and without --permission-mode, and after Shift+Tab): which events carry permission_mode and effort.level, and what string Manual/auto produce. Decides whether the card chip can be hook-derived or needs a fallback (hide when unknown).
- Parse `claude --help` for the --permission-mode choices block in 2.1.300 and in the previous CLI version if available (the doc says 'manual' arrives as 'default'): decides the allowlist mapping and the drift behaviour.
- Check for a `loom` URL scheme collision on the user's Mac (lsregister -dump | grep -i 'loom:' or `open -Ra` with the scheme; another app named Loom may register loom://). If it collides, pick another scheme name; decides the scheme.
- Only if worktrees are pulled into this idea instead of I-32: isolated repo test that `claude --worktree x` started by Loom keeps hook cwd, transcript location, GitBranch label and resume working after Stop and Resume. Expected to fail the branch label unless Loom tracks hook cwd, which is why it is deferred.

## Questions for the user

- Shortcut: keep Cmd+N as the instant start and add Option+Cmd+N for the sheet, or make Cmd+N open the sheet?
- May a preset opt in to 'start without asking' from the + menu (never from a URL)? Default proposed: no, until used for a while.
- Mode allowlist: only Manual, Plan, Accept Edits, Auto in the sheet, with bypassPermissions and dontAsk excluded. Agree, or does the user want bypass available in presets (always behind the sheet)?
- Preset storage: one JSON file per preset in the Loom data root (editable in any editor, Reveal in Finder), with no in-app editor in v1. Acceptable, or is an in-app preset editor wanted from the start?
- URL scheme name (after the collision check) and whether to ship the URL in the same release as the sheet or one release later.
- Are the user's real ticket prefixes (EDDP-*) enough for the Recent-tickets chips, which come from sessions that carry a ticket key, or should the sheet also parse keys from titles and branch names?
