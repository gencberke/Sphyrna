# I-39: User-armed Goal mode driven by the Stop hook

Card from the [Loom v2 idea catalog](../IDEAS.md). **User-armed Goal mode driven by the Stop hook** · verdict **adopt-light** · cost M · value 3/5 · proposed by 1 reports: [openchamber](../products/openchamber.md).

> Skip the idea as written: Claude Code already ships `/goal` (documented, CLI 2.1.300 here) as a session-scoped prompt Stop hook with a Haiku evaluator, so Loom should not build its own checker and Stop-hook loop. Adopt only a light layer that makes Loom aware of a native goal: a card marker, no false "Finished" between goal turns, and one real end signal.

## What the user gets

Arm a goal (objective, token budget, turn cap default 20) and walk away: Loom answers each Stop with a block+reason that continues the work until an independent check says done / needs-you / budget / cap. The blue 'finished unviewed' then fires once at the end. Stop always wins and pauses the goal.

## Mechanisms found in the research

[Documented] Stop hook decision (block + reason); no 15 s quiet-window timer needed because the hook IS the turn-end signal; the check sees only the objective and the last assistant message with three yes/no questions decided in code (OpenChamber audit.js). Arming is an explicit per-session user act, visible on the card; suppress intermediate notifications; metered.

## Debates and fact-check corrections

Single source; Codex ships thread/goal/* in its documented app-server (precedent). Risks: runaway spend, loop fighting the user's own hooks, behaviour of Stop blocks across CLI versions, whether Stop fires separately for subagents (unverified), checker misjudgment (their self-measured lab: about 98%). OpenChamber's public docs are stale (blocked settles on the first auditor answer, now verified in code). HN: walk-away works 'most of the time, not always'. power-user-workflows warns against orchestration/swarm complexity.

## Design in Loom


FINDING THAT CHANGES THE IDEA. The research note leaves one point open ("check first whether Claude Code's native /goal already exists"). It exists. Observed in the docs: code.claude.com/docs/en/goal and the Hooks reference ("The /goal command is a built-in shortcut for a session-scoped prompt-based Stop hook"). Observed in the installed binary (claude 2.1.300): a `goal_status` transcript attachment type and an `active_goal` app state. Native /goal already has:
- a user-set condition of up to 4,000 characters;
- a fresh small-model evaluator after every turn, with three verdicts: not met, met, impossible;
- a turn or time cap, written as a clause inside the condition;
- a token count in `/goal` status;
- deferral of evaluation while subagents or background shells run, plus check-ins at 30 min, 1 h and 2 h;
- clearing on unrecoverable errors (auth, credits, context overflow, model unavailable);
- pausing on rate limits;
- restoring the goal on resume;
- a `◎ /goal active` TUI indicator.
Building Loom's own version would duplicate all of this and keep it in step with CLI changes. That breaks "documented interfaces preferred" and "never pin".

WHAT THE IDEA WOULD COST IN THIS CODEBASE (why the original is not L).
1. The hook path is deliberately one-way. `ProviderLaunchProfile.claudeSettings` registers `loom-hook` for Stop with `timeout: 1`. A comment there says helpers return no provider decision. `ClaudeHookClient.send` sends one message, shuts down the write side, waits at most 0.1 s for a 1-byte NAK, and ignores everything else. A Stop block needs these changes:
   - a reply protocol in the client and `ClaudeHookServer`;
   - `loom-hook` printing `{"decision":"block","reason":...}` on stdout;
   - a much longer Stop timeout for every session, because the settings are inline `--settings` JSON fixed at launch and cannot be changed per armed session;
   - the decision made inside the ordered `ClaudeHookIngress` / `SessionRuntime.deliver` path, or a side path that bypasses it.
2. Loom has no model-call machinery. The only headless Claude use is `ClaudePlanLimitsFetcher`, which makes one `get_usage` call. A checker would be a new `claude -p` process:
   - started inside a run scope, with its own profile, auth, hook-recursion guard and failure modes;
   - with its tokens metered into `ClaudeUsageIndex`;
   - and its transcripts kept out of the catalog and the usage view.
3. Documented loop limits. A Stop hook that blocks hits an 8-consecutive-continuation cap (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`). The count resets whenever Claude calls a tool, and `stop_hook_active` is true during a continuation. A Loom cap of 20 would be shadowed by the CLI's cap on turns that call no tool.
4. It would run in parallel with the user's own Stop hooks and with native /goal, which are the two things most likely to fight a Loom loop.

My honest re-estimate of the original is L to XL plus permanent drift cost. The light layer below is S to M.

THE LIGHT VERSION ("goal awareness"). Three pieces, all reusing existing event paths. Nothing polls.
(a) Detect arming and clearing. `ClaudeHookEvent` already parses the `prompt` field of UserPromptSubmit (`isSyntheticPrompt`). A small `GoalPromptParser` in LoomCore classifies a prompt that starts with `/goal ` as arm, `/goal clear|stop|off|reset|none|cancel` as clear, and a bare `/goal` as a query. It also clears on `SessionStart(source: clear)`, on a run end, and on a new run. Result: `SessionViewState.goal` (nil, or the condition plus a started-at stamp), held in memory only, because the CLI restores a goal on resume and Loom must not own a second copy. UNVERIFIED: whether a built-in slash command fires UserPromptSubmit or only UserPromptExpansion. If it fires neither, the fallback is the `goal_status` attachment in the next piece.
(b) Detect the end. When a session has `goal != nil`, Loom does one bounded tail read of the main transcript (`transcript_path` is in every hook payload). It reads the last 64 KiB from a line start, reusing `SubagentTranscriptTail`, which is the existing bounded line reader. It looks for the newest `attachment.type == "goal_status"` entry (`met`, `failed`, `reason`, `iterations`, `durationMs`, `tokens`). The read runs only on events, and only for goal sessions:
   - triggers: the transcript write notification that `UsageTranscriptWatcher` (FSEvents) already delivers, or the next Stop;
   - timing: the evaluator verdict is written after Loom's own Stop hook fires, because command hooks run in parallel with the prompt hook, so Loom cannot learn "blocked or allowed" from the Stop payload itself.
   This transcript format is undocumented, so it is a drift risk. It needs the same treatment as the registry file: unknown shape leaves the goal marker unchanged and journals once through `ClaudeRegistryDiagnostics`-style reporting. It must never produce a false "met".
(c) Quiet the card while a goal runs. Today a Stop sets `turnComplete`, which raises `unviewedCompletion` (`SessionEventHub.publish`) and ends the Active-section phase (`activePhase`). A registry "busy" sample then flips it back to Working, once per goal turn: a blue flicker, Dock badge and menu-bar churn, and Cmd+J targets a session that is not actually done. The Stop payload does not say whether a goal verdict will continue the turn, so the hold needs the goal flag. With `goal != nil`, extend `activePhase` the way `pendingProviderWorkCount > 0` already does (`case .turnComplete where status.pendingProviderWorkCount > 0: return .underWay`), and do not raise `unviewedCompletion` until (b) reports met, failed or impossible, or until the goal flag clears. The same applies to any Stop that is not followed by a continuation: no continuation, no goal verdict, and the registry reporting "idle" release the hold after one registry sample. This is event-driven; no timer is needed.

ARMING (optional, S). The header ⋯ menu gets "Set Goal..." with a sheet: one text field and a hint ("name one measurable end state and how Claude proves it; add 'or stop after 20 turns'"). It writes `/goal <text>` plus Return through the existing per-run `TerminalInputQueue` (the same one-ordered-write path as keystrokes and paste). It is allowed only at Ready or Waiting for you, never mid-turn, and it checks the state first. Delivery is confirmed by the UserPromptSubmit (or `goal_status`) that follows, not assumed, so no false "armed". The user can already type `/goal` in the terminal, so for this user the sheet is convenience. Build awareness first.

STOP ALWAYS WINS comes for free. Loom's Stop kills the verified run scope. A user interrupt (Esc) fires no Stop hook, and the CLI's own docs say evaluation resumes after the next prompt. After a Loom Stop and Resume the CLI restores the goal but resets its counters, which the marker must not misreport (show the condition only, no turn count).

DO NOT BUILD. A Loom-side checker, a Loom token budget, a Loom turn cap, sentinel strings, suppressing or replacing the CLI's own evaluator, or any Stop-hook decision output. Budget and cap are the CLI's job through the condition clause. Loom can show the tokens the transcript reports in `goal_status`.

## Where it shows


- Card (two-row): a small `◎` glyph in the existing monochrome symbol class (`LoomTheme`; no new hue, per the DESIGN.md three-status-hues rule) sits next to the project/branch row or the status text while a goal is active. The status stays truthful: Working while turns run, with no Waiting or Finished flicker between goal turns.
- Header: beside the state pill, a quiet chip "Goal · 6 turns · 41k tokens" (from `goal_status`, when known). Its tooltip shows the full condition and the latest evaluator reason. A click toggles the condition line, with no extra panel. The ⋯ menu gets "Set Goal..." and "Clear Goal" (which types `/goal clear`).
- End: when the goal resolves, the existing blue "Finished" appears once, and the pill briefly reads "Goal met" or "Goal not reached: <reason>" until the user views the session. This reuses the existing unviewed state and the Dock badge, menu bar and Cmd+J; those are not touched.
- Optional macOS banner "Goal met · <project>" through the existing `ApprovalNotifier` / `NotificationService` seam. Today banners exist only for Needs approval (D-49), so this is a new notification class and the user's call.
- Nothing is drawn or watched for sessions without a goal.

## Principle check


- Resources: PASS for the light version. It is event-driven with no timer or poll. Parsing a prompt string is trivial. The transcript tail read is bounded (64 KiB, line-aligned, O_NOFOLLOW, regular file of this user) and runs only for sessions that have a goal. The original design RISKS this: a Loom-spawned `claude -p` per turn, plus a Stop timeout raised for every session.
- Predictability: PASS. Loom adds no behaviour to the loop. The original adds a second, Loom-owned loop that fights the CLI's 8-continuation cap, the user's own Stop hooks and native /goal.
- Accurate status: the light version IMPROVES it. Between goal turns the card no longer claims "Finished" when the CLI is about to continue. Risks to design against:
  - never show "met" unless the transcript says met;
  - a missing or unreadable `goal_status` leaves the marker unchanged and drops the hold after one idle registry sample;
  - Loom's marker says only that a goal is armed;
  - after a Loom Stop and Resume the counters are reset by the CLI, so Loom shows no counter it cannot verify.
- Fluency: PASS. There is no extra confirmation. Arming is one sheet or typing in the terminal. No new waits.
- Modularity: PASS. It is a parser, an optional tail reader, one `SessionViewState.goal` field and a few lines in `activePhase`. All of it sits beside `SubagentLedger` and `SubagentTranscriptTail`, the existing precedents for hook- and transcript-derived card data.
- CLI-update resilience: the weakest point. Documented: `/goal` itself, the Stop decision semantics, `stop_hook_active`, and the fact that Stop is the main agent only (SubagentStop is the subagents' event; internal agents such as /btw fire SubagentStop, which Loom already ignores as `.childAgent`). Undocumented and so drift-prone: the transcript `goal_status` attachment shape, and whether the slash command surfaces in UserPromptSubmit. Mitigation: parse with a narrow Decodable, treat unknown shapes as "no information", report once, and keep the pre-goal behaviour as the fallback. The `/goal` docs also name versions (v2.1.239, v2.1.246, v2.1.269), so features move; do not branch on versions.
- Ownership: PASS. No new process. The CLI's evaluator runs inside the CLI, inside the run scope Loom already owns and verifies.
- User authority: PASS. The user arms the goal themselves (typing it or using the sheet), and Loom never arms one on its own. No cross-session action is involved.

## Value for the user (3/5)

The walk-away loop the user wants already exists in the CLI and costs Loom nothing. What Loom adds is trust: a visible marker, no false blue between goal turns (which also protects the Dock badge, menu bar and Cmd+J across several parallel sessions), and one real end signal. That matters most for a heavy multi-session user who walks away. The arming sheet is mere convenience. The idea as written, a Loom-owned checker and loop, would add high cost and risk for little over the CLI feature. HN-style "works most of the time, not always" caveats apply to the CLI evaluator and are out of Loom's hands. These are my estimates; the user has not said whether they use /goal today.

## Experiments before building

- E1, hook, registry and transcript trace of a native /goal run. Use an isolated CLAUDE_CONFIG_DIR, never the real ~/.claude. Run a trivial 2 to 3 turn goal such as 'create /tmp/x with one line, then stop' with a hook script that logs every event to JSONL, then read what Claude wrote. Decisions it makes: (1) Does `/goal <text>` fire UserPromptSubmit, UserPromptExpansion or neither, and does the continuation turn fire a UserPromptSubmit? That decides how arming is detected. (2) Does Loom's own Stop command hook fire on every goal turn, including turns that the evaluator then continues? (3) What is the order of the Stop hook, the `goal_status` write to the transcript and the registry 'busy' sample between turns? That decides whether the end signal comes from the transcript or can be inferred, and how long the current Finished flicker lasts. (4) What fields does the `<config>/sessions/<pid>.json` registry hold while a goal is active (is there a goal field)? That would give a documented-ish source. (5) Does `last_assistant_message` plus `stop_hook_active` tell the next Stop anything useful?
- E2, Loom's current behaviour under a goal. Run the same goal inside Loom Dev (not the daily app) with an isolated profile and record the SessionEventHub frames (the `activePhase`, `unviewedCompletion` and `status.activity` sequence per turn). Decides: is the flicker real and long enough to bother the user, or does a registry 'busy' sample arrive within milliseconds? If the flicker is under about a second, piece (c) can shrink to a pure marker and the hold is skipped.
- E3, can Loom type `/goal` safely? Write `/goal <text>` plus Return through TerminalInputQueue to a session at the prompt (bracketed paste versus plain typing; the slash-command menu may intercept the first characters) and confirm acceptance by the resulting hook or transcript entry. Also try `claude -- "/goal ..."` as the first message, since the open-session path (D-40) already starts sessions with a first message. Decides whether the arming sheet is a plain write or needs a verified-delivery wrapper.
- Budget for all three: well inside D-04 (real-provider tests in isolated profiles, a few short turns, small-model evaluator), and the CLAUDE_CODE_GOAL_CHECKIN_MINUTES=0 setting avoids idle check-ins during the trace.

## Questions for the user

- Do you use /goal in the terminal today, and would you arm it from Loom (header sheet) or keep typing it? If you keep typing it, the arming sheet is dropped and only awareness (marker plus quiet status) remains.
- Should Loom send a macOS banner when a goal ends (met, impossible, error)? Today banners exist only for Needs approval (D-49), so this is a new notification class.
- Is a small `◎` goal marker acceptable as a new card/header element, within the DESIGN.md rule of monochrome symbols and the existing three status hues? It is the only UI change in the light version.
- Should the blue 'Finished' be held back for the whole goal and fire once at the end (my recommendation), or show after every goal turn as it does now?
- Does the walk-away value justify any Loom-owned loop at all? I recommend no: if native /goal's evaluator proves too weak for your work (the research cites roughly 98 % agreement for OpenChamber's own lab, and 'not always' from HN users), the better lever is a Stop command hook or a prompt hook you write in your own settings, not a Loom-owned checker.
