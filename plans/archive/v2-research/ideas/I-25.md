# I-25: Usage honesty: plan pace, provenance, cache-cold hint, limit-hit actions

Card from the [Loom v2 idea catalog](../IDEAS.md). **Usage honesty: plan pace, provenance, cache-cold hint, limit-hit actions** · verdict **adopt-light** · cost M · value 4/5 · proposed by 5 reports: [usage-tools](../products/usage-tools.md), [t3code](../products/t3code.md), [orca](../products/orca.md), [power-user-workflows](../products/power-user-workflows.md), [claude-official](../products/claude-official.md).

> Adopt the pure-function core (plan pace on the existing chip, a stale/unknown marker, an honest "usage limit reached" state) as an S job; drop Loom's own "Continue at reset" because Claude Code 2.1.234+ already waits and continues by itself, and make the cache-cold hint a separate spike because the transcript can probably give the TTL tier but nobody has checked.

## What the user gets

Turn the raw plan-window percentage into a decision and make every number trustworthy: 'at this pace the 5-hour window runs out in 1h 40m, reset in 2h 10m' (only when it matters), a tag on each figure (official / estimate / stale), a 'cache likely cold, next message re-reads about 143k tokens' hint before you resume an idle session, and 'Continue at reset' for a session stopped on the limit. (Remaining usage for ChatGPT is a later wish; Codex is frozen.)

## Mechanisms found in the research

Pure functions of data Loom already has: (a) pace from get_usage utilization + resets_at, shown at >=10% used and projected >=90% (amber chip, one-shot notification per window re-armed after reset; weekly bar only at >=80% or bad pace); recompute on get_usage refresh or turn end, never poll; state freshness ('as of 3 min ago'). (b) provenance enum on view models; limit % drops to 'unknown' after now passes resets_at; guard NaN/negative/epoch values. (c) cache-cold: computed at render from the last-assistant timestamp; TTL tier (5 min vs 1 h) is only documented in statusline JSON (prompt_cache.ttl), so say 'probably cold' unless I-24 exists; keep the TTL in one constant. (d) Limit actions: documented Notification types quota_auto_resume_fired/stale/disabled (setting autoContinueAtUsageLimit, v2.1.234+) mean the CLI can continue at reset by itself; otherwise a one-shot timer to the reset time then resume + explicit continue prompt verified by the hook, per-session opt-in, Loom must be running (say so), plus 'Snooze until reset' (I-18). Compact chip is information, never changes Enter.

## Debates and fact-check corrections

Linear projection is rough (burst from parallel subagents, early-window false alarms; hence the 10% floor and 'at this pace' wording); the Oct 2026 outcry about hidden indicators shows demand. Cache TTL tier unverified for transcripts. Orca ships a CacheTimer; T3 a Compact chip (but with compact-on-Enter default, which to avoid). Plan limits via get_usage are flagged experimental (shape may change). Do not read the Keychain OAuth token or call /api/oauth/usage (see skips).

## Design in Loom


FACTS READ
- Plan limits already exist end to end. `ClaudePlanLimitsFetcher` (Sources/LoomCore/ClaudePlanLimits.swift) runs a ~1 s headless `claude -p` with one `get_usage` control request and returns `PlanLimits{fiveHour, weekly: PlanLimitWindow{usedPercent:Int, resetsAt}, fetchedAt}`. `PlanLimitWindow.isCurrent(at:)` and `PlanLimits.current(at:)` already drop a window once `now` passes `resetsAt`. `interpret` already rejects non-finite values and clamps to 0...100. So half of the provenance idea (b) is already done.
- `UsageModel` (Sources/LoomCatalogUI/UsageModel.swift) is event-driven. `fetchLimitsIfDue` asks only while a Loom window or the Usage page is visible, never two at once, with a minimum age (`PlanLimitsCadence`: 300 s after the window is shown, 120 s after a turn ends, 10 s after the page opens). It has no timer. `minuteTick()` (called from CatalogModel.swift:1057 while the window is active) only calls `rebuildChip()`. `rebuildChip()` publishes a new `UsageChipContent` only when it differs, so the footer redraws only when the text changes.
- On a failed ask the chip keeps the last answer. `limitsFailure` only feeds the Usage page card ("not refreshed"). The footer percent therefore carries no age marker.
- The hook layer already receives what (d) needs. `ProviderLaunchProfile.claudeSettings` registers Notification and StopFailure. `ClaudeHookEvent.Kind` has `.notification(type:)` and `.stopFailure(error:details:)`. `notificationActivity` treats `quota_auto_resume_*` as informational, so the state is kept. A rate-limit turn end becomes `AgentActivity.failed("rate_limit")`, shown as red "Failed" (SessionIndicator.failed, ProjectAttention.failure, menu bar failure dot). ClaudeHookTests.swift:363 already has a `rate_limit` / 429 fixture.
- The transcript parser already reads the cache TTL tier. ClaudeUsageParser's `Usage.CacheCreation` decodes `ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`, and the index `msg` table keeps `cw5`, `cw1`, `cr`, `input`, `ts_ms`, `session` and a sidechain flag. Indexes exist on `msg_session` and `msg_ts`. The research's "TTL tier unverified for transcripts" is probably answerable from data Loom already stores.

DOCS I FETCHED, which the research note does not cover
- Interactive-mode docs, "Wait for a usage limit to reset": from v2.1.234, in an interactive session signed in with a claude.ai subscription, automatic continue is ON BY DEFAULT. When a usage limit stops a turn, the open session shows "Continuing automatically at 3:45pm · esc to cancel" and continues at the reset by itself.
- The CLI does not start that wait for Remote Control / teammate sessions, or when the reset is more than 24 h away. For those, the user can pick "Wait here, then continue automatically" from `/rate-limit-options`.
- Exiting Claude, `/resume`, `/clear` or `/login` ends the wait, and it does not restart on resume.
- The continuation passes through `UserPromptSubmit` (a blocking hook ends the wait). Esc / Ctrl+C cancels it, and that cancel fires no hook (`quota_auto_resume_disabled` explicitly does not fire on Esc).
- Hooks docs: `idle_prompt` is not sent while the CLI waits for a limit reset. After a sleep of more than about 30 min across the reset, the CLI sends `quota_auto_resume_stale` and waits for Enter.
- Statusline and costs docs: `prompt_cache.ttl` ("5m" or "1h") is computed by the CLI "from the cache token counts in the API's responses". `/usage` already prints `warm (1h TTL, last activity 40s ago)`. A subscription session normally gets the 1 h tier, so a flat 5-minute "probably cold" would be wrong most of the time for this user.
- The v2.1.299 idle compaction (research note, confirmed by its fact-check): a conversation over about 200k tokens that has been idle about 54 min is compacted just before the 1 h cache expires, unless `idleCompaction` is false. A "re-reads ~N tokens" figure is therefore false for those sessions.

DESIGN, by part

(a) Pace. Add `PlanPace` in LoomCore next to ClaudePlanLimits.swift: a pure function `PlanPace.evaluate(window, kind, fetchedAt)` returning nil or `{projectedPercent, exhaustsAt}`.
- Compute it AT `fetchedAt`, not at `now`, because the utilization was only true then. elapsed = windowLength − (resetsAt − fetchedAt), with fixed lengths 5 h and 7 d.
- Unknown (nil) if resetsAt is missing, elapsed ≤ 0 or elapsed > windowLength.
- Show only when used ≥ 10 %, elapsed ≥ ~30 min for the 5 h window, projected ≥ 90 % and exhaustsAt < resetsAt. The research's 10 % floor alone gives false alarms at the start of a window, for example 10 % after 15 min.
- 5-hour only. A linear weekly projection will cry wolf for a user who does not work seven even days. The weekly bar needs no new rule: `bottleneck` already shows the lowest remaining percent, and the weekly window appears when it is the bottleneck.
- Plug into `UsageChipContent.make` by adding `Limit.pace`. It turns the percent and meter amber, the same attention tone as `isLow`, and the tooltip gets one line: "At this pace the 5-hour limit runs out about 14:20; it resets 15:45 (as of 14:02)".
- Use absolute clock times, not "in 1h 40m". A relative ETA would change the tooltip every minute and make `minuteTick` → `rebuildChip` redraw the footer every minute. The existing equality gating exists to avoid exactly that.
- Triggers are the ones that exist: a successful `fetchLimitsIfDue` and `minuteTick`. Add no fetch and no timer.
- Round-trip `utilization` as a Double inside PlanLimitWindow. The current Int rounding makes the early-window projection jumpy (12 % vs 13 % moves the projection by about 8 %).

(a2) Notification. The research proposes a one-shot macOS notification per window. Under the current cadence it is almost worthless: asks happen only while a Loom window is visible, which is when the user already sees the chip. Making it useful means an ask on turn end while hidden, which is a policy change to D-37 ("a few asks per hour while a window is visible").
- Defer it. If wanted, bound it: ask on turn end while hidden only when the last known utilization is ≥ 50 %, at most once per 120 s.
- `NotificationService.post(id: UUID, …)` and `onActivate: (UUID)` are session-keyed, so a usage notice needs a small protocol addition plus its own Settings switch (default off) beside the existing "Notify when a session needs approval".

(b) Provenance. Replace "nothing" with a three-case enum computed from existing data, shown as one dim glyph plus tooltip text, no extra chrome.
- limit % = official (CLI `get_usage`), with "as of HH:MM".
- Same % when `now − fetchedAt` > ~15 min, or `limitsFailure != nil` and the answer predates it = stale: the glyph "~" and "couldn't refresh since 14:02".
- Tokens today = estimate, from local transcripts. The tooltip already says "approximate" on the Usage page; say it on the chip too.
- The window past `resetsAt` already drops to nothing, so no new "unknown" case is needed there.
- Change the clamp for absurd values: today `utilization` > 100 or negative is clamped, so an epoch-sized garbage value shows "0 % remaining". Reject (treat the window as unavailable) beyond a sane bound such as > 150 or < 0, and keep clamping 100–150.
- Tests: extend ClaudePlanLimitsTests.swift and the UsageChipContent tests with an injected `now`.

(c) Cache-cold hint. This part needs a spike (see experiments).
- Add one method to `UsageIndexing`: `lastMainTurn(sessionID:) -> {timestamp, contextTokens = input+cw5+cw1+cr, lastWriteTier}?`.
  - It is one indexed query: `msg WHERE session=? AND sidechain=0 ORDER BY ts_ms DESC`, plus the latest row with cw5+cw1>0 to get the tier (cw1>0 means 1 h, cw5 only means 5 m).
  - It lives in ClaudeUsageIndex.swift. The fake in UsageModel's protocol extension needs a default (nil), like `diagnostics()`.
- Call it only when the user selects a session that is idle, stopped or Ready (CatalogModel selection event), once per selection. No scan and no background work. Nothing for sessions the user is not looking at.
- Pure `CacheHint.make(turn, now, idleCompactionPossible)` renders only when cold. It stays silent when the tier is unknown, when context > 200k and idle > 54 min (say "may have been compacted" or nothing), and when there is no usage row.
- The TTL constants live in one place. The 1 h / 5 m split comes from the data, not a constant.
- Where it shows:
  - The text of `EndedScreenNotice` (DetailView.swift:294) for a stopped session, the main "resume an idle session" case: "This session is not running. Resume re-reads about 143k tokens (cache expired 3 h ago)". Resume stays a plain button. Nothing changes what Enter or Return does.
  - A slim notice like `SessionIssueNotice` for a live session that sits at its prompt past the TTL.
- Wording "probably cold" only when the tier is unknown. Prefer saying nothing.

(d) Limit state and actions.
- Do NOT build Loom's own timer + resume + continue prompt.
  - The CLI already does it for the 5-hour window in every Loom PTY session, because Loom starts interactive subscription sessions and D-38 never stops them. A second continuation from Loom would be a double execution, which contract §7 forbids ("no blind retry, no double execution").
  - The weekly case (reset > 24 h) and stopped sessions are the only gaps. In both, Loom must be running at reset time anyway (Quit stops everything), so the user can pick "Wait here, then continue automatically" in the terminal themselves.
  - Loom's timer would also need `--resume <id> -- <prompt>`, which `ProviderLaunchProfile` currently refuses (opening only for `.new`), plus a hook-verified UserPromptSubmit. That is a real feature for a rare path.
- DO fix the status. Today a session waiting for a reset shows red "Failed" with the project dot and menu bar failure dot, and when the CLI continues it silently flips to Working.
  - Map `.failed("rate_limit")` in `SessionIndicator.init` (SessionDisplay.swift:56) to a distinct, non-failure indicator. Working name: `.limitReached`; label "Limit reached"; attention or neutral tone, not failure red.
  - The state pill tooltip shows the reset time from `UsageModel.limits` (five_hour `resetsAt`) with hedged wording: "Claude continues on its own after the reset unless it was cancelled". The wording must be hedged, because Esc-cancel fires no hook and Loom cannot know.
  - The informational `quota_auto_resume_fired/stale/disabled` Notification types can refine the tooltip: `stale` means "press Enter in the terminal", `disabled` means "will not continue".
  - Because `UserPromptSubmit` carries the continuation, the existing state tracker returns to Working correctly with no change.
  - This is a user-visible state change: needs the user's OK (see decisions). It also touches ProjectAttention and the menu bar, so it must stay within SessionIndicator's one derivation point so cards, dots and tabs agree.
- "Snooze until reset" stays with I-18.

BOUNDS AND TRIGGERS
- No new process, no timer, no polling, no new file format.
- (a) and (b) are O(1) per fetch result.
- (c) is one indexed SQLite read per selection.
- (d) is a switch on an existing string.
- CLI drift: all inputs are documented (`get_usage` is undocumented in public SDK docs but is already in use since D-37; hook types are documented). A missing field degrades to "no pace / no hint", never to a wrong claim.

COST (honest)
- (a) + (b) + (d) status-only: S, about 1 to 1.5 days including tests and the two real-session checks.
- (c): M. It needs the index method and the fake, selection plumbing, two views, the idle-compaction caveat and fixtures, and it should not start before the spike.
- The Loom-side Continue-at-reset in the original idea would be M to L and is not worth it.
- The bundle as written (S) is understated; the recommended light version is S.


## Where it shows


- Footer chip, same single-line 38 pt bar. It reads "1.2M today · 5h 38%" today. With a bad pace the "5h 38%" part and its meter turn attention-orange (the colour `isLow` already uses under 20 % remaining). Nothing else is added to the line.
- Tooltip, only when the pace is bad: "At this pace the 5-hour limit runs out about 14:20; it resets 15:45 (as of 14:02)."
- A stale answer gets a "~" before the percent and a tooltip line "couldn't refresh since 14:02".
- Weekly appears only as the bottleneck, as now.
- Session card and detail pill: a session whose last turn ended on a rate limit reads "Limit reached" (attention tone) instead of red "Failed". The pill tooltip says when the limit resets and that Claude continues by itself unless cancelled.
- Stopped session, `EndedScreenNotice`: one extra clause on the existing text line, "Resume re-reads about 143k tokens (cache expired 3 h ago)", shown only when cold and only when the tier is known. A live idle session past its TTL gets the same sentence in a slim notice styled like `SessionIssueNotice`. No new button; no change to Enter or Return; no compact action.


## Principle check


- Resources: pass. Pure functions of data already held. No new process, timer or poll. The hint costs one indexed read on selection. Risk: absolute clock times are needed so the tooltip does not change every minute and force a footer redraw on `minuteTick`.
- Predictability: pass. Thresholds are fixed constants. The pace is explicitly "at this pace". The hint never changes Enter and has no compact-on-Enter default (the T3 #17467 regression is avoided).
- Accurate status: the whole point of (b) and (d). The risk is claiming too much.
  - Esc-cancelled auto-continue is invisible to hooks, so "continues at X" must be hedged.
  - A cache hint with a guessed TTL or on a session that was idle-compacted is a false claim, so it stays silent when unsure.
  - Linear pace is a model, not a fact.
- Fluency: pass. No new confirmations or waits. Information appears only when it matters (pace ≥ threshold, cache cold).
- Modularity: pass. `PlanPace` and `CacheHint` are pure types in LoomCore with injected clocks. The UI reads view-model data only. The one cross-layer change is the `UsageIndexing` method.
- CLI-update resilience: mostly pass. Hook notification types and `/usage` fields are documented. `get_usage` is undocumented but already used. Transcript usage fields are not a contract: the cache hint must degrade to silence when `cache_creation` is missing. Never pin; nothing here needs a version gate beyond the existing capability probing.
- Ownership: pass. Loom's own timer is the thing that would have blurred ownership (two continuers on one session). Dropping it keeps the CLI as the sole actor on a Loom-owned PTY.
- User authority: pass for (a)–(c). (d) status mapping changes how a failure looks (a user decision). Any future automatic continue must be per-session opt-in and must not coexist with the CLI's own auto-continue.
- Constraints touched: D-32/D-37 (no polling beyond the visible-window cadence) is kept by adding no ask. The contract's "terminal is the real CLI" is untouched (no composer). D-20 (changing CLI behaviour is a user decision) is respected by not setting `autoContinueAtUsageLimit`. D-34 is unaffected.
- Violations to avoid:
  - a hidden-window fetch for notifications beyond the bounded rule above;
  - a ticking relative ETA in the chip text;
  - sending a prompt from Loom while the CLI's wait is still armed;
  - writing the user's settings.json to turn the CLI setting on or off.


## Value for the user (4/5)

This user runs several sessions plus subagent workflows and reaches the 5-hour window sooner than a single-session user, so "do I slow down?" is a daily decision and the chip already carries the data. The honest limit state also removes a misleading red "Failed" on a session that is just waiting for a reset. The cache-cold hint is a nice-to-have decision aid for resuming large sessions, not essential. The original Continue-at-reset adds little, because Claude Code does it by itself.

## Depends on

- I-24 (statusline bridge) is optional, only if exact TTL, context size or live rate_limits are wanted later; not needed for the light version

## Experiments before building

- TTL tier in transcripts (decides whether the cache hint can ship without I-24): in an isolated CLAUDE_CONFIG_DIR, run one real short Claude turn on the subscription, then compare the last main-chain assistant record's usage.cache_creation.ephemeral_1h/5m_input_tokens with the same session's /usage line 'Prompt cache (main): warm (1h TTL ...)' and, if cheap, a one-off statusLine dump of prompt_cache.ttl. Decides yes if 1h writes show as ephemeral_1h on a subscription and the tier can be read from the latest record with creation>0; if a turn made of cache reads only hides the tier, the lookup must walk back to the last write (already planned). If the tiers disagree, drop the hint or say 'probably cold'.
- Hook order at a real usage limit (decides the (d) status mapping): capture the real event sequence when a session hits the 5-hour limit, using loom-probe's HookRecorder or Loom's own hook log, on a normal dev run. The questions are: does StopFailure(rate_limit) arrive once per hit; does a Stop follow; what do the Notification types do; does a continuation arrive as UserPromptSubmit with a synthetic prompt; and what happens to Loom's state while the CLI waits. The fixture in ClaudeHookTests.swift:363 only proves the StopFailure shape. Do not burn quota to produce it; use the next natural hit, or record from a long-running isolated profile.
- Idle-compaction signature in the transcript (decides how the cache hint stays silent for large idle sessions): find out what a v2.1.299 idle compaction leaves in the transcript (compact_boundary record? usage row?) so the lookup can tell that the context was rewritten, or confirm that the 200k + 54 min rule alone is enough.
- Does `claude --resume <id> -- <prompt>` start a resumed session with a first prompt? Only needed if a Loom-side continue for stopped sessions is ever built; not needed for the light version.

## Questions for the user

- Should a session that is waiting on a usage limit stop being red 'Failed' and become its own 'Limit reached' state in attention tone? It changes how sessions look in the sidebar, project dots and menu bar.
- Is a pace-based macOS notification wanted at all? Without a policy change it fires only while a Loom window is visible, so it is nearly useless; the useful version allows a bounded ask on turn end while Loom is hidden when last known usage is already high. Is that acceptable under D-37, and should the switch default to off?
- Do you want a Loom-side 'Continue at reset' for stopped sessions or the weekly limit at all, knowing the CLI already auto-continues the 5-hour limit in the open session? My recommendation is no for now.
- Should the weekly window get any pace logic, or stay a plain bottleneck percent (my recommendation)?
- If the cache hint ships: show it for live idle sessions as well, or only on the ended-screen notice before Resume (the lighter option)?
