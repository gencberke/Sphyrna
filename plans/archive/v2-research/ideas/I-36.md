# I-36: `loom` CLI + read-only verbs + wait + event hooks (the read side of multi-agent work)

Card from the [Loom v2 idea catalog](../IDEAS.md). **`loom` CLI + read-only verbs + wait + event hooks (the read side of multi-agent work)** · verdict **adopt-light** · cost M · value 3/5 · proposed by 7 reports: [herdr](../products/herdr.md), [t3code](../products/t3code.md), [supacode](../products/supacode.md), [warp](../products/warp.md), [openchamber](../products/openchamber.md), [superset](../products/superset.md), [cmux](../products/cmux.md).

> Build only the in-session read side (sessions, status, wait) as new verbs on the existing authenticated control socket, served from the SessionEventHub with no new UI; leave outside-shell scripting, event hooks, `read` and `--explain` for later, because they are either redundant, unsafe to expose, or have no precedent that fits Loom.

## What the user gets

Agents and the user's own shell/Raycast scripts can address 'this session' and query siblings without polling: `loom sessions --json`, `loom status <id> [--explain]`, `loom wait <id> --until needs-you|finished|failed --timeout`, `loom read <id> --last-turn`; plus a small personal hooks file that runs commands on Loom events (session finished, needs approval, ticket opened, worktree created).

## Mechanisms found in the research

Export LOOM_SESSION_ID/LOOM_PROJECT into every hosted session (Supacode's SUPACODE_* ids are deprecated and its commands default to the FOCUSED target, which must not be copied); read verbs answered from Loom's in-memory hook-derived state over the existing authenticated socket via an event subscription (herdr's 100 ms sleep loop is what not to copy), pinned to session id + run identity so a resumed/replaced process cannot satisfy a wait; reads need no approval, mutating verbs (open, send, stop) keep the approval card; per-session short-lived credentials revoked on stop (T3 McpSessionRegistry); scope to the same project unless the user allows more; skill pattern from herdr (gate on LOOM_SESSION=1, the binary is the syntax authority, never predict ids, trigger only on explicit mention, safety rules). Scripting catalog (list, rename, focus, status, set_title) behind a Settings > Scripting switch (off by default) with an owner-only discovery record and short-lived action-scoped grants (Warp local_control). Event hooks: plain processes with LOOM_* env and bounded timeout/output, failures reported, no marketplace, no sandbox.

## Debates and fact-check corrections

Scope creep into a full orchestration API and a second configuration language; version the API and detect mismatch rather than pin. T3's outside-agent grants last 30 days across all projects (no per-ticket scoping precedent); Warp's warpctrl is dogfood-only at the cloned commit; herdr's marketplace is unreviewed arbitrary code (explicitly not the model). Exposes more session data to agents, so keep it read-only and scoped.

## Design in Loom


WHAT ALREADY EXISTS (observed in code; the idea is smaller than it reads)
- LOOM_SESSION_ID is already exported to every hosted session (LaunchEnvironment.make, Sources/LoomCore/LaunchEnvironment.swift:70). LOOM_MANAGED_RUN_ID is set in ProcessSupervisor.swift:325. LOOM_CLI (the bundled loom-hook binary), LOOM_CONTROL_SOCKET and LOOM_HOOK_TOKEN are set in ProviderLaunchProfile.swift:149-153. LOOM_PROJECT is not needed: the server derives the project from the caller's session, which is one fewer env var to drift. The herdr-style gate already exists as "Only inside Loom, where $LOOM_CLI is set" in ClaudeLoomPlugin.skill.
- The control socket (OpenSessionControlServer in OpenSessionProtocol.swift, c-<8>.sock, token compare, 32 in-flight cap, connection held per request, continuation-based so it holds no thread) and its authorize rule (SessionRuntime.swift:316: supervisor.runContext(runID) live AND launchSessionID == LOOM_SESSION_ID; returns the card the run is on now, so /clear is handled) already give "this session" plus run binding. A run ending makes authorize return nil, which is already the "revoked on stop" behaviour T3's per-session credentials buy, so do not add a second credential system. The token is shared by all sessions of one app run and readable by any same-uid process, so scoping is a guard against mistakes and prompt confusion, not a security boundary; say so in the docs.
- SessionEventHub (actor) already is the event source: subscribe() yields the current snapshot first and then frames, so "snapshot, then wait on events" is race-free by construction (herdr needed an explicit sequence snapshot because it polls at 100 ms). SessionViewState carries runID, status (ProviderWorkState incl. pendingProviderWorkCount), identity, issue, stopFailure, blockers, subagents.

DESIGN (slice 1)
1. Protocol: generalise the open-only wire shape (OpenSessionWireRequest v1) into a verb envelope {version, token, sessionID, managedRunID, verb, args}; keep `open` byte-compatible. Reply is JSON plus a one-line text form for agents. Server answers an explicit "unsupported version, update the Loom skill/app" instead of "malformed" (API versioned, mismatch detected, nothing pinned). Client side: extend OpenSessionCommand.run (191 lines) or add a sibling ControlCommand in LoomCore; loom-hook/main.swift already routes any argument to the agent command, so no new binary.
2. Verbs (4 at most): `sessions [--json] [--limit N]`, `status <id|self> [--json]`, `wait <id> --until needs-you|finished|failed [--timeout S]`, and nothing else. `open` stays as is and keeps its approval card. Ids are read from output, never predicted (`started <id>` from open already returns the child id, which is the main wait target).
3. Scope rule enforced server-side: the target must be in the caller's project, or be a session the caller opened (catalog `opened_by`). `sessions` lists live sessions (hub snapshot, bounded) plus at most N recent catalog rows (default 50, hard cap 200) with id, title, ticket, project, branch only if already cached, status, running. Cross-project only if the user turns it on (a Settings switch is the only UI this ever needs).
4. Status vocabulary lives in LoomCore. SessionIndicator (Sources/LoomCatalogUI/SessionDisplay.swift, 243 lines) is a pure function of CatalogSession and SessionViewState but sits in LoomCatalogUI, and LoomCore may not import UI. Move it (or its derivation core) into LoomCore so the card, the menu bar, Cmd+J and the CLI cannot disagree. That mechanical move is the largest hidden cost. Verb states: working | needs-approval | waiting-input | finished | failed | ready | ended | unknown, plus raw fields. `finished` must NOT depend on the user having viewed it (unviewedCompletion is a display concept).
5. Wait: a WaitRegistry actor in LoomCore. It subscribes to the hub only while at least one waiter exists (nothing watched otherwise), resolves waiters on frames, and cancels its subscription at zero. Pin each waiter to (sessionID, runID captured at start): a runEnded/runDetached/new runID resolves it as `ended` or `replaced`, never as success. Add a per-session `completionSeq` to SessionViewState (incremented on a turnComplete transition; the frame-level turnCompletions counter is global and the stream is bufferingNewest(1), so a fast working->complete->working could be missed). Subscribe with an unbounded or large buffer for the registry; frame rate is one per hook event. `finished` = a turn completion after the wait began, or the session is already turn-complete with pendingProviderWorkCount == 0; atPrompt/Ready (startup, resume, /clear) and unknown never count, and a Stop with background_tasks still pending stays working (the tracker already handles this, ClaudeHook.swift Stop parsing and SessionDisplay `.turnComplete where pending > 0 -> .working`). Distinct outcomes and exit codes: reached, timeout (4), ended/replaced (5), not-found/out-of-scope (2), unavailable at Quit (3, existing pattern). Caps: 16 waiters total, 4 per caller, timeout default 10 min, max 60 min; a separate waiter cap so waits cannot starve `open` of the 32 in-flight slots. Quit resolves every waiter `unavailable` (same path as pending open requests in SessionRuntime shutdown).
6. Agent teaching: extend the single loom plugin skill (ClaudeLoomPlugin.swift) with a short "look at sibling sessions" section; the always-in-context description grows by about one sentence (D-42 budget is about 80 tokens). Rules in the skill: only when the user mentions it or after `loom open`, binary --help is the syntax authority, `finished` is not approval, `unknown` does not prove completion, do not re-open after timeout, long waits run as a background shell task so the coordinator is not blocked.
7. Tests: reuse OpenSessionIntegrationTests/OpenSessionTests/SessionEventHubTests patterns with the fake provider (loom-fake-provider already emits Stop/last_assistant_message and background tasks). Deterministic counters, not timing: waiter resolved exactly once; replaced run cannot satisfy; /clear; background-task Stop does not finish; waiter count returns to zero and the hub subscriber count returns to the baseline.

WHAT TO LEAVE OUT (and why)
- `read --last-turn`: it moves one session's output into another's context (prompt-injection and data exposure), which is a content channel rather than status. If wanted later: only for sessions the caller opened, bounded to the Stop hook's last_assistant_message (already parsed, ClaudeHookEvent.lastAssistantMessage, and kept in ClaudeSessionStatus but not published to the hub, so it needs a small bounded hub field, not a transcript read), labelled as untrusted text. Needs the user's call (D-40 said cross-session messaging stays off).
- Event hooks file: the user can already run commands on "finished" with a plain Claude Stop hook in their own settings (hooks from user settings and Loom's per-session --settings all run; inferred from Claude's hook merging, verify in the spike). Loom-only value would be needs-approval/ticket-opened semantics, which the menu bar and approval notification (D-49/D-52) already cover. "worktree created" does not exist in Loom (no worktree feature). A hook runner would also be a new Loom-spawned process outside any run scope, which needs its own Quit kill and crash story (Process in its own process group, hard timeout, a helper-enforced timeout so a crash cannot leave a long orphan). Later at best.
- Settings > Scripting for the user's own shell/Raycast: any tokenless same-uid endpoint is equally callable by every agent's Bash tool, so the catalog must be read-only to be safe (rename/set_title/focus let a prompt-injected agent deceive the user or steal focus). Warp's broker model (peer-uid check, action-scoped grants) is dogfood-only at the cloned commit, so there is no field evidence. A read-only variant needs a discovery record (data root, owner-only) and a `loom` on PATH, which is an explicit user-initiated install step ("Install Command Line Tool") because it changes the user's environment. Only worth building if the user actually scripts Loom.
- `--explain`: nearly free later because everything it would list (activity, issue, identity, stopFailure, blockers, lastEventAt, hook-silence) is already in SessionViewState; do it as a header-pill popover first, CLI second.
- Per-session short-lived credentials (T3): redundant, see above.
- MCP server instead of a skill: adds a process or config per session and changes the agent's tool set (T3 does this; Loom's D-42 chose a plugin skill on purpose).


## Where it shows


Slice 1 has no new surface: it is a command the agent runs, answered on the existing socket. Optional, only if it proves useful: a quiet "waiting on <session>" line in the coordinator card's meta row (reuse the S2 origin-line style from D-39), shown only while a wait is open. A Settings > General switch "Let sessions see other projects" (default off) is the only setting. Diagnostics export gets request/wait counters like HookDiagnostics. The later outside-shell variant would be a Settings card "Scripting" (off by default) with an "Install Command Line Tool" button and a plain line showing the socket record path; the later `--explain` is a click on the state pill in the detail header showing the signal behind the state.


## Principle check


Resources: PASS if built as designed. No polling or timers: the registry subscribes to the hub only while waiters exist and each waiter is a continuation, not a thread; `sessions` is one bounded catalog query per request; nothing is drawn or watched when no agent calls it. RISK: an agent in a loop calling `sessions` (add a per-caller rate limit) and unbounded waiter or buffer growth (hard caps above).
Predictable: PASS with explicit outcomes (reached/timeout/ended/replaced/not-found/unavailable), no blind retry, wait never auto-restarts.
Accurate status: PASS only if wait reuses the single derivation (move SessionIndicator into LoomCore) and refuses atPrompt/unknown/background-pending as `finished`. This is the main risk of the whole idea; herdr's #5263 shows what a loose notion of idle costs. Never report a missed transient as success (completionSeq).
Fluency: RISK. Every `"$LOOM_CLI" ...` Bash call in a session will hit Claude's own Bash permission prompt unless the user allows it; adding an allow rule in Loom's per-session --settings is a D-20-class change and needs the user. A foreground wait blocks the coordinator for the Bash tool's time limit; the design relies on background shell tasks (unverified, see experiments).
Modularity: PASS if the verb router, WaitRegistry and status derivation sit in LoomCore and the UI only consumes. RISK: scope creep into a full orchestration API and a second configuration language; hold at 4 verbs, no config file.
CLI-update resilience: PASS. Uses only hook-derived state Loom already trusts, a Loom-owned protocol version, no new CLI interface. Skill text is regenerated from source (ClaudeLoomPlugin) each app version. No pinning.
Ownership: PASS for slice 1 (no new process). The deferred event-hook runner would be a new Loom-spawned process family and would need its own Quit and crash handling, which is a reason to defer it.
User authority: PASS for reads of metadata in the same project; mutating verbs keep the approval card (open today; send would need its own card). RISK: `read` (content) and cross-project scope are authority questions for the user, and the shared token plus same-uid readable environment means scope is not a security boundary against a hostile agent. Contract §7 and D-40 ("cross-session messaging stays off") need an explicit new decision row before this is built.


## Value for the user (3/5)

It is the "follow the child" half of D-43 and the user's ticket-session workflow (a session opens an EDDP-* session through loom open and then needs to know when it finished or is blocked, without the user relaying), and it costs nothing at idle. But it only pays when a coordinator agent actually runs several top-level sessions, which is a narrow part of daily use, the human already gets the same signals from Cmd+J, the menu bar and notifications, and the outside-shell, event-hook and read parts that would widen the audience are the weakest or riskiest. Score rises to 4 if the user confirms they run coordinator-style workflows weekly.

## Experiments before building

- E1 Agent ergonomics (isolated CLAUDE_CONFIG_DIR, short real-Claude turns, fake provider for Loom): does a `"$LOOM_CLI" sessions` Bash call prompt every time, and can an allow rule in Loom's per-session --settings match a command that starts with an env-var expansion? Decides whether the verbs are fluent or need a user-approved allow rule (a D-20 decision).
- E2 Wait path: does a `"$LOOM_CLI" wait ... ` started as a background shell task wake an idle coordinator when it exits, does Loom show it as Working through Stop.background_tasks meanwhile, and what happens at the foreground Bash time limit? Decides whether `wait` is practical or only useful for short waits. If background wake does not work, shrink to sessions/status plus a short foreground wait.
- E3 Deterministic counters, no measurement run: with 16 waiters and a fake provider emitting hook frames, hub subscriber count returns to baseline, no timers exist, waiter resolution is exactly-once. Confirms the resource claim without needing the idle computer.
- E4 (only if the outside-shell variant is ever pursued) confirm whether an agent's Bash tool can read the discovery record and reach the socket, i.e. that the catalog must be read-only.

## Questions for the user

- Lift D-46's 'no date' for the first, read-only slice of the cross-session channel, and amend D-40/contract §7 to say read verbs of status are allowed without approval?
- Do you run coordinator-style workflows where one session waits on sessions it opened? How often? (This sets value 3 vs 4.)
- Should an agent be able to read another session's last answer (`read`), or only its status? If yes, only for sessions it opened?
- May Loom add an allow rule for the read-only verbs to the per-session --settings so agents are not prompted for each call (a D-20-class change), or should the prompt stay?
- Do you script Loom from your own shell or Raycast? If not, drop the Scripting switch and the PATH install entirely.
- Is a same-project default scope right for your two work projects, or do you want coordination across projects (e.g. EDDP-* and the other work project)?
