# I-14: Richer card content: what it is asking / last said, peek, agent note, title precedence, notification text

Card from the [Loom v2 idea catalog](../IDEAS.md). **Richer card content: what it is asking / last said, peek, agent note, title precedence, notification text** · verdict **adopt-light** · cost M · value 4/5 · proposed by 6 reports: [cmux](../products/cmux.md), [supacode](../products/supacode.md), [warp](../products/warp.md), [orca](../products/orca.md), [power-user-workflows](../products/power-user-workflows.md), [cursor](../products/cursor.md).

> Adopt a small version: show Stop's last_assistant_message and PermissionRequest's tool_name/tool_input (already in the hook payloads Loom receives) as a bounded, memory-only line that is shown only while the matching state holds, on attention cards (or as a tooltip first), plus a richer approval banner; defer the agent-set note, and treat title precedence as already satisfied.

## What the user gets

The sidebar and notifications answer 'does this need me, and for what' without opening the session: a one-line 'asking / last said' under the title, a peek popover (last message, question or final summary), an optional agent-reported note ('reproduced bug; testing fix'), a stable human title, and notifications whose body is the outcome or approval summary plus branch.

## Mechanisms found in the research

(a) 'Last said' from the Stop hook's last_assistant_message and the Notification message (both documented; Supacode caps about 1000 bytes, Warp about 200 chars), no transcript read; truncate hard, treat as untrusted text, respect a title-only privacy toggle for the lock screen; delete/update the notification when the session resumes, cap simultaneous toasts. (b) Peek = same text in a popover, read-only. (c) Agent-set note: the session updates one line through Loom's authenticated socket and loom skill (Orca `worktree set --comment`), shown with 'agent-reported' styling, capped, rate-limited, cleared on a new prompt, never used as status truth; ship the skill as a thin stub that asks the app for version-matched instructions. (d) Title precedence: user rename in Loom > Claude's own name (/rename or --name) > first/latest prompt; never let a hook or approval summary overwrite a user name (Warp's most repeated complaints); where Claude stores /rename is unknown (read incrementally, treat as drift). (e) One-sentence reason on each approval box (tool + path), from hook payload.

## Debates and fact-check corrections

cmux also runs an async auto-name hook on Stop (timeout 120, may run a summarizer): a model-call cost Loom would not want by default. Privacy: prompt/approval text on a locked screen. Prompt injection via agent-written notes is not a new vector but should be bounded.

## Design in Loom


FACTS FROM THE CODE (what already exists)
- ClaudeHookEvent (Sources/LoomCore/ClaudeHook.swift:364-478) already parses last_assistant_message. ClaudeHookStateTracker.receive copies it into ClaudeSessionStatus.lastAssistantMessage on Stop and StopFailure (lines ~766-776). Nothing outside tests and loom-probe reads it, so it never reaches SessionViewState or the UI. ClaudeSessionAdapter.receive (ProviderSessionAdapters.swift:~260-312) stores the status in lastStatuses and publishes only ProviderWorkState(activity, pendingProviderWorkCount).
- Not parsed today: Notification message/title (Kind is notification(type:)), PermissionRequest tool_input (Kind is permissionRequest(toolName:)), and SessionStart session_title.
- The generated hook settings (ProviderLaunchProfile.claudeSettings, ~180-208) register SessionStart, UserPromptSubmit, Stop, StopFailure, Notification, PermissionRequest, SessionEnd, SubagentStart and SubagentStop, with timeout 1. There is no PreToolUse or PostToolUse, on purpose ("each hook spawns a helper").
- Claude approvals happen in the terminal and the hook returns no decision. Loom has no in-app approval box for Claude. SessionViewState.userRequests is the Codex path (paused) and DetailView's RequestList. The only Claude-side boxes are the open-session request boxes. So part (e) cannot be "a sentence on the approval box"; it becomes the card line, the tooltip and the banner body.
- Approval banners: ApprovalNotificationPlanner posts on the transition into Needs approval while Loom is inactive and removes the banner when the session leaves it. ApprovalNotifier.approvalsChanged is fed by the menu bar summary (AppDelegate+System.swift:35-37). The body is the fixed text "<project> · Claude is waiting for your approval." There is no finished or needs-input banner (D-52 chose approvals only, no sound). Removal on resume and "cap simultaneous toasts" are therefore already covered: Loom has no in-app toasts and macOS does the stacking.
- Titles (part d): SessionCatalog+Titles.swift has title_is_custom. renameSession sets it; recordTerminalTitle (fed only by Claude's OSC title via ConversationController.titleChanged) writes only WHERE title_is_custom = 0. Hooks and approval text never touch the title. The user > Claude's own title ordering therefore already exists and Warp's overwrite bug class cannot happen here. The docs answer the "where is /rename stored" unknown: SessionStart carries a documented session_title (set via --name, /rename, a hook or the SDK; generated titles are excluded), and the statusLine JSON carries session_name. Loom must not use the statusLine (a helper spawn per refresh, and it collides with the user's own statusLine). Whether a mid-session /rename reaches the OSC title is unverified.
- The skill/plugin (part c): ClaudeLoomPlugin.install rewrites its files from the app's source into <data root>/claude-plugin whenever they differ, so the skill is already version-matched. A "thin stub that asks the app for instructions" adds nothing here.
- The control socket (OpenSessionProtocol.swift) is shaped only for `open`: OpenSessionWireRequest has title/ticket/project/message and protocolVersion 1. A note command would need a command discriminator, a new handler, a new CLI verb in OpenSessionCommand and a second skill.

DESIGN (smallest version that pays)
1. Core, pure and tested like ApprovalNotificationPlanner: new `AttentionText` type in LoomCore. It sanitizes (drops control, bidi and zero-width scalars, collapses whitespace, grapheme-safe cut), takes the LAST ~240 characters of last_assistant_message (a question sits at the end; a summary's tail is the outcome) and the first ~160 of a tool summary, and keeps a ~600-byte peek variant. `summary(tool:input:)` covers the documented tool_input shapes: Bash.command, Edit/Write/Read.file_path, WebFetch.url, Grep/Glob.pattern, an MCP tool shown as "server: tool". An unknown tool shows just the tool name.
2. Hook layer: ClaudeHookEvent also reads PermissionRequest tool_input (only the few fields above; Write content is skipped, but the payload is already JSON-decoded today), the Notification message/title (used only for elicitation_dialog; permission_prompt and idle_prompt texts are generic: "Claude needs your permission"), and truncates lastAssistantMessage at parse time. This also removes up to 1 MiB per live session now kept in tracker and lastStatuses.
3. State: add `attention: AttentionNote?` to SessionViewState plus a SessionEventChange case, published beside .status from ClaudeSessionAdapter.receive, in the same serialized transition and BEFORE the status change. That way the Needs-approval set change (which triggers the banner) already sees the text. The note holds (kind: approval | input | finished | failed, text). Memory only: nothing in the catalog and no second copy of the transcript (contract §8 "deleted is not an archive", the "no second copy" rule at contract line 209, schema untouched). SessionEventHub.publish dedupes equal states, the reducer clears the note on working, a new run, a detach and the run's end, and a relaunch shows nothing.
4. Accuracy by construction: the UI shows the note only while SessionIndicator maps to the same kind (waitingForApproval, waitingForInput or unviewedCompletion, failed). A stale note can never appear against a different status. It is never an input to the indicator, the Active section, Cmd+J or the badge counts.
5. Card: the existing two-row card (DESIGN §1 item 4) gains an optional third line only for the four attention kinds, 11 pt secondary (not tertiary), one line, tail-truncated, plain `Text(verbatim:)` (never Markdown or LocalizedStringKey, so agent text cannot render as formatting or links). The same text goes into `.help` (native tooltip, about 600 bytes) as the "peek". Start with the tooltip and decide on the third line with a preview HTML, as the repo does for design changes. Read the note inside the card body only. Do not add a new observed property per card beyond live.attention.
6. Banner: title stays the session title. Add a subtitle "Needs approval · <project>" and a body "Bash: git push origin feature/x" from the note, with an optional "· <branch>" from BranchCache. With no note (older CLI, missing field) the current generic body is used. The id-based remove-on-leave stays.
7. Menu bar rows: the same text as the NSMenuItem tooltip. MenuBarRowText stays unchanged.
8. Title (d): no code change. Add one invariant test (a hook, an approval or an agent note never changes the title or title_is_custom). Optionally read the documented SessionStart.session_title as a provider-title input to the existing recordTerminalTitle path, which keeps the custom-title guard. That is S and only worth doing if the spike below shows /rename does not reach the OSC title.
9. Agent note (c): do not build now. It needs a protocol bump, a handler, a CLI verb, a second skill and about 80 more tokens of skill description in every session. It also depends on the model choosing to call it, and every update is a tool call that costs latency and tokens. For this user, mid-turn Working sessions are the ones that do not need triage; Stop already delivers the agent's own words for free. If it is ever built, reuse the requester check in OpenSessionCoordinator.authorize (run live, launch card == LOOM_SESSION_ID), cap it at 140 characters and 1 write per 10 s, clear it on UserPromptSubmit, render it with an "agent-reported" glyph, and never let it touch status.

TRIGGERS AND BOUNDS: everything is driven by hook events Loom already receives (Stop, StopFailure, PermissionRequest, Notification). There is no timer, no polling and no transcript read. The cost is one capped string per live session. The card line costs nothing when the card is not drawn. The tooltip costs nothing until hover.

WHAT WOULD VIOLATE A PRINCIPLE: reading the transcript for "last said" (undocumented format, and the doc says the transcript lags the hook); adding PreToolUse or PostToolUse hooks for text (a helper spawn per tool); persisting the text; letting the text decide status; rendering it as Markdown; calling a model to summarize (cmux's auto-name hook); adding a card line to every card (density, layout jumps).


## Where it shows


Sidebar card, attention states only (and in practice only the cards in the Active section or "Waiting for you"): the usual two rows, then one 11 pt secondary line under the branch row. Examples:
- Needs approval: "Bash: git push origin feature/EDDP-412"
- Waiting for you / Finished: "...want me to keep the old endpoint, or remove it?" (the tail of the last message)
- Failed: "API error: rate_limit".
A Working, Ready, Idle or ended card is unchanged (exactly two rows). Hovering a card with a note shows a tooltip holding the longer text (~600 bytes) as a read-only peek; a real popover is a later option, only if the tooltip proves too small. Banner: title = session title; subtitle "Needs approval · <project>"; body = tool summary (+ branch). Menu bar rows: the same text as the item tooltip. The detail header and terminal are unchanged. The text needs no "agent-reported" styling, since it is the agent's own message or the CLI's own permission request, not a self-written note.


## Principle check


- Resources: PASS. Event-driven, one capped string per live session, nothing read or drawn when hidden. It reduces memory (truncating the retained 1 MiB message). The risk is a card re-evaluating on every live change, which is already true; SidebarRenderTests/CatalogHotPathTests should gain a case showing that a note change touches only that card.
- Predictability: PASS. The note appears only with its state and follows the same rule everywhere (card, tooltip, banner, menu).
- Accurate status: PASS if the note is gated by the indicator kind and never feeds it. RISK: "waiting for you" text is only the last message, not necessarily a question; label and tooltip must say "last message", not "asking". A second PermissionRequest during an unchanged Needs-approval period updates the card text but not the already-posted banner.
- Fluency: PASS. No confirmations or waits; it removes trips into sessions to find out what they want. RISK: card height changes when a state flips (the list shifts under the pointer). Limit the line to attention states and keep it fixed to one line.
- Modularity: PASS. `AttentionText` is pure in LoomCore; the UI only reads. The change touches ClaudeHook, ProviderSessionAdapters, SessionEventHub, SessionViewState, CatalogModel apply/patching, SidebarView, ApprovalNotifier and the planner.
- CLI-update resilience: PASS. Only documented fields (Stop.last_assistant_message, Notification.message/title, PermissionRequest.tool_name/tool_input). A missing field degrades to today's UI. Do not parse the transcript. The tool_input field names per tool are only partly specified, so fall back to the tool name.
- Ownership: not involved.
- User authority: PASS. Display only. The agent-set note (c) also only labels the caller's own session and needs no cross-session authority, but it is deferred.
- Privacy and security (not on the list but binding): the text is untrusted and is displayed verbatim only (no Markdown or links, bidi and control scalars stripped, hard caps). Commands and paths can contain secrets, and they would appear in banners. macOS already offers Notifications → Loom → Show previews (When Unlocked / Never) for the lock screen. A Loom switch "Show details in banners" is S and covers screen sharing; a user decision.
- Contract: "the terminal is the real CLI" is untouched. D-34 (no right rail) is untouched. "No second copy of transcripts": satisfied by memory-only storage. DESIGN §1 item 4 (two-row card, no status words) needs a design preview and a decision from the user for a third line.


## Value for the user (4/5)

With 3 or more sessions across two EDDP projects, the real cost is deciding which session to open and why. Today the card says only "Waiting for you" or "Needs approval", and the banner is the fixed text "Claude is waiting for your approval". The data is already in the hooks Loom receives and part of it is already parsed, so most of the benefit costs only plumbing. It scores 4 rather than 5 for two reasons. The fact-check says auto mode is now the default starting mode, so approvals are rarer (the banner part matters less than the last-message part). Selecting a live session in Loom is also cheap, since its terminal is already running. The agent note (c) alone would be about 2, so it is not worth its protocol and token cost.

## Experiments before building

- Hook payload recording with an isolated CLAUDE_CONFIG_DIR, using the existing loom-probe HookRecorder (Sources/loom-probe/HookRecorder.swift) against a real current claude. Record Notification payloads for permission_prompt, idle_prompt and elicitation_dialog. What decides it: whether `message` carries anything beyond the generic text (if not, only PermissionRequest and Stop feed the line; if elicitation_dialog carries the MCP prompt, include it).
- Same recording, PermissionRequest tool_input for Bash, Edit, Write, Read, WebFetch and an MCP tool. What decides it: the exact field names used by `AttentionText.summary`, and whether a large Write payload keeps the 1 MiB hook cap safe.
- Same recording, does PermissionRequest fire in an interactive session for AskUserQuestion and ExitPlanMode? Loom has no PreToolUse hook, so if it does not fire, the most useful 'what is it asking' text (a multiple-choice question) is missing. What decides it: whether to leave that gap or register `PreToolUse` with matcher `AskUserQuestion|ExitPlanMode` (matcher-filtered, so there is no helper spawn per ordinary tool; verify that on the real CLI) as a follow-up.
- Stop.last_assistant_message shape: is it the whole final text or just the last text block, and is it empty when the turn ends in a tool call or after a background-task Stop? What decides it: tail-versus-head truncation and the empty-string handling.
- Does a mid-session /rename or --name change reach Claude's OSC title that ConversationController.titleChanged already receives, and does SessionStart (startup, resume, compact) carry session_title? What decides it: whether the optional session_title read is needed or the current terminal-title path already satisfies the precedence rule.

## Questions for the user

- Third line on attention cards (needs a design preview and amends DESIGN §1 item 4 'two-row card'), or tooltip only for now?
- Banner detail: show the tool + command/path in approval banners by default, and add a Settings switch 'Show details in banners' (default on or off), or rely on macOS 'Show previews' alone? The text can contain commands and paths.
- A banner for 'finished / waiting for you' as well, as an opt-in setting? D-52 deliberately chose approvals only with no sound, and the Hashimoto-versus-Cherny notification split is real. The recommendation is not to add it now.
- Agent-set note (part c): confirm deferral. Also, if wanted later, whether agents should learn it from Loom's plugin skill (it works with D-42) at the cost of about 80 context tokens per session?
- Is it acceptable that the line is gone after a Loom relaunch (memory-only, no transcript read), so stopped records show nothing?
