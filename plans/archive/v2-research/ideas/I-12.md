# I-12: Status accuracy hardening and 'Why this status?'

Card from the [Loom v2 idea catalog](../IDEAS.md). **Status accuracy hardening and 'Why this status?'** · verdict **adopt-light** · cost S · value 3/5 · proposed by 9 reports: [herdr](../products/herdr.md), [cmux](../products/cmux.md), [conductor](../products/conductor.md), [superset](../products/superset.md), [warp](../products/warp.md), [supacode](../products/supacode.md), [paseo](../products/paseo.md), [usage-tools](../products/usage-tools.md), [orca](../products/orca.md).

> Most of the idea is already in Loom (background_tasks/session_crons, run+session binding, child-agent drop, interrupt via registry, no stale Working across launches); the real gaps are a sticky Failed, pinned regression sequences, unknown-value drift evidence and a pull-based 'why' readout, so build that small slice and drop the timer-based Interrupted state and the `loom status --explain` flag.

## What the user gets

Fewer wrong dots on the cards the user trusts all day: a session with background work or running subagents never shows Finished/Idle; Failed is not silently downgraded; resume, /clear and compaction never show Finished unviewed; an interrupt does not leave Working stuck; and a pill popover (and `loom status --explain`) says which signal produced the state, when, and what it replaced.

## Mechanisms found in the research

Mostly an audit plus tests of Loom's transition table (reports did not read Loom code, so some cases may already be covered): (a) Stop/SubagentStop hook input has background_tasks (shell/subagent/monitor/workflow) and session_crons (documented in hooks reference; since 2.1.145): derive 'Waiting on background work' with elapsed time instead of Finished; keep a per-session set of unfinished background launch ids, no transcript rescan; (b) bind every hook event to session id + launch identity, ignore nested/foreign sessions that inherit env, keep the hook tiny and a no-op outside Loom (Superset #8120/#8131/#8245/#6243); (c) sticky Failed (Supacode: Notification after Stop-on-error must not downgrade it), compaction (PreCompact -> SessionStart source=compact) as Working, use the documented notification_type (permission_prompt only after ~6 s, idle_prompt ~60 s after finishing; PermissionRequest is the immediate signal) and never treat idle_prompt as 'needs you'; (d) 'Interrupted' state: Stop does not fire on user interrupt and there is no interrupt event (documented), so after Loom writes Esc/Ctrl-C into a Working session and no hook arrives within a short window mark Interrupted until the next UserPromptSubmit, one-shot timer only; (e) completion/state-change sequence guards so restore/resume never counts as a completion (herdr completion_seq), reconcile stale Working at launch from the registry + PID check (Paseo); (f) store the last transition reason (signal, time, previous state) and show it behind a pill click; surface unknown values as drift evidence. Regression tests with exact hook sequences.

## Debates and fact-check corrections

Corrections: Warp does NOT synthesize Cancelled on a local Ctrl-C (only for shared-session/Remote Control viewer writes), so Warp is not precedent for the local case, but the gap is real; cmux #14308 (idle_prompt -> needs-input) and #13024 are historical, at HEAD idle_prompt becomes an idleReminder and is suppressed for completed/background-pending sessions; Orca needs dozens of background-task/child-work tracker files, showing how much state logic this takes. herdr itself moved away from hook-driven state for Claude (stale blocked states, hook removals in users' settings) toward identity-only hooks plus screen manifests, so hook hygiene matters. A Ctrl-C can also just dismiss input, so require Working and no later event; the ~2 s window is a heuristic to tune. Hook field names should be verified against the installed CLI through drift detection.

## Design in Loom

AUDIT RESULT (code read, not run). Already covered: (a) `ClaudeHookEvent` parses `Stop.background_tasks` and `session_crons` into `ClaudeSessionStatus.backgroundTaskCount/scheduledTaskCount`; `ClaudeSessionAdapter` publishes `ProviderWorkState.pendingProviderWorkCount`; `SessionIndicator.init` shows `.working` for `.turnComplete` with pending>0; `SessionEventHub.activePhase` keeps it `.underWay`; synthetic hand-back prompts (`promptIsSynthetic`) do not start a user turn; `SubagentLedger` reconciles background subagents. (b) Hooks are injected only through the per-session `--settings` JSON in `ProviderLaunchProfile.claudeSettings` (nothing written to ~/.claude/settings.json, so no-op outside Loom by construction); `loom-hook` exits unless LOOM_SESSION_ID/LOOM_MANAGED_RUN_ID/token env are present; `ClaudeHookStateTracker.disposition` rejects wrongSession/staleRun/wrongConversation/retiredConversation/duplicateSessionStart and drops `agent_id` payloads as `.childAgent` (test `childAgentPayloadCannotMutateParentStatus`). (c-part) Informational notification types keep the state (`informationalNotificationsKeepTheState`); `idle_prompt` is not treated as a new completion (maps to waitingForInput, acknowledged via `waitingAcknowledged`). (d) Esc interrupt: the registry watch (`ClaudeRegistryWatch`, vnode-driven, no timer) turns Claude's own busy->idle into 'Waiting for you' (test `interruptedWorkingReturnsToInputWhileRealStopRemainsAuthoritative`; FEEDBACK-4 line 101 records the real behaviour). A Loom-side Esc/Ctrl-C timer would need raw key interception in LoomTerminal, add a heuristic, and duplicate a verified signal: skip. (e) `SessionViewState` is in-memory only and `runStarted` resets `unviewedCompletion/activePhase/status`, so no Working survives a launch and resume/clear never set unviewedCompletion (it needs a Stop transition to `.turnComplete`); `PreviousRunRecovery`/`closeAbandonedRuns` handle catalog rows.
REAL GAPS (to build): (1) Sticky Failed. In `ClaudeHookStateTracker.receive`, `.notification` of idle_prompt/agent_needs_input/elicitation_dialog assigns `currentStatus.activity = .waitingForInput` unconditionally, so a `.failed` set by StopFailure is downgraded to 'Waiting for you' when the idle notice arrives (about 60 s later, if Claude sends it after a failed turn: unverified). Fix: a notification with activity .waitingForInput may not replace `.failed`; only UserPromptSubmit, SessionStart (new conversation) or SessionEnd leave it. Registry samples already cannot override it (generation is nil after Stop). Mirror the guard in `receiveRegistry`. (2) Pinned sequences in `ClaudeHookTests`/`SessionEventHubTests`: StopFailure -> idle_prompt; Stop(bg>0) -> idle_prompt -> synthetic UserPromptSubmit -> Stop(bg=0) (one real completion, unviewed set once); SessionStart(compact/resume/clear) after a viewed turn leaves unviewedCompletion false; PreCompact is not registered, so test that SessionStart(source=compact) of the same conversation is a duplicate that keeps Working. Use exact payloads from existing recordings (Claude 2.1.287 sequences in ClaudeRegistryTests). (3) Drift evidence: today only unknown registry statuses are journaled (`noteUnknownRegistryStatus`); add the same once-per-token `cli_compat_warning` for an unknown `notification_type`, an unknown `hook_event_name` (`ClaudeHookEvent.Kind.unknown`) and unexpected Stop field shapes (background_tasks neither array nor dict), through `supervisor.journal` with the existing `ClaudeRegistryDiagnostics.token` sanitising. Note `.unknown` event currently sets activity .unknown; it is unreachable for unregistered events, so leave it. (4) 'Why' readout, pull not push: add to `ClaudeHookStateTracker` a bounded ring (last 8 entries) of {signal name (hook event / notification_type / registry status / watchdog), receivedAt, from, to} recorded only when `activity` actually changes; expose `ClaudeSessionAdapter.explain(sessionID:)` -> `SessionRuntime` -> a `ConversationIntents` closure (same pattern as `subagentTranscript`) -> a pure `StatusExplanation.make(record:live:transitions:)` in LoomCatalogUI that also names the UI-layer cause the tracker cannot know (stopFailure, issue, identityUnclear, open-request approval, waitingAcknowledged, unviewedCompletion, pending work count). Do NOT put the reason into `ProviderWorkState` or `SessionViewState` (extra fields or timestamps would break frame de-duplication in `SessionEventHub.publish` and re-trigger `SessionLifecycleController` evaluations). Also append the last transitions and the existing `HookDiagnostics` drop counts to Collect Diagnostics (`SessionRuntime+Diagnostics`), which is the copy-paste evidence path. (5) Optional later, after the spike: a distinct pill label for 'Background work' (StatePillStyle already accepts a label override, as the subagent panel's 'Running 4m' does).
TRIGGERS/BOUNDS: all event-driven (hook arrival, registry vnode, user click); no timers, no polling, no new hooks (PreCompact/PostToolUse stay unregistered: each hook spawns a helper); memory 8 small entries per live run, freed with the tracker on run end; popover costs one actor call on click.
`loom status --explain` is out of scope: `loom-hook` only has the `open` command and the cross-session channel (D-43/D-46) is undated; revisit when that channel exists, reusing the same explain function.

## Where it shows

Header state pill (StatePill in SessionHeaderViews.swift, DetailView.swift line ~151) becomes clickable only if the user accepts it; popover (about 280 pt, secondary text, no new colours) with 3 lines: 'Finished (unviewed)'; 'Stop hook at 14:03:12, replaced Working'; 'Unviewed because you were not looking; 1 background task still listed'. Failed popover adds 'Stays until your next prompt'. Cheapest variant: no pill change, the same text only in Settings > About > Collect Diagnostics and a new 'Why this status?' item in the three-dot menu (SessionMenuItems), which avoids touching the DESIGN.md pill rules and the focus-ring/hit-area rules. Sidebar cards stay unchanged.

## Principle check

Resources: pass (event-driven, bounded ring, pull on click; the Interrupted one-shot timer is the only piece that adds a heuristic and it is dropped). Predictability: pass with one risk: a sticky Failed needs an explicit clear path (next prompt, resume, SessionEnd) or it nags (project row shows 'A session failed' until then). Accurate status: pass, this is the point; do not add an 'Interrupted' guess since registry idle already reports the verified outcome. Fluency: pass (no confirmations, no new waits). Modularity: pass, changes stay in ClaudeHookStateTracker, a pure explain function and diagnostics. CLI-update resilience: pass and improved by unknown-value journaling; risk: the sticky-Failed rule rests on an assumed idle_prompt-after-StopFailure sequence that must be recorded, and any new reliance on `background_tasks` shapes must degrade to the existing count. Ownership: pass (nothing written to user settings, hooks stay per-session). User authority: pass (read-only display; no cross-session action). Standing decisions: D-45 (watchdog/drift) and D-54 (Active section, known cases) are extended, not reopened; DESIGN.md pill rules only change if the pill becomes clickable.

## Value for the user (3/5)

Status trust is the base of a many-session, subagent-heavy workflow, but the audit shows the headline cases are already handled and tested, so the visible gain is small: one Failed that no longer turns into 'Waiting for you', regression coverage, and a debugging readout that mostly helps the author when a CLI update shifts behaviour. D-54 already accepts that cron/background sessions stay Working in Active.

## Experiments before building

- Hook recording spike with the existing loom-probe HookRecorder against an isolated CLAUDE_CONFIG_DIR (never the real ~/.claude): (a) force a StopFailure (invalid API base URL or key in the isolated profile) and wait 70 s: does Notification idle_prompt follow, and does the registry flip to idle? Decides whether the sticky-Failed guard fixes a real or only a theoretical downgrade (the code change is harmless either way).
- Same recorder with one background shell (`sleep 600` via run_in_background) and one /loop or cron: after the turn's Stop, does Claude emit idle_prompt, what does the registry status say (busy/idle), and does killing the task from /tasks produce any hook? Decides whether 'Working' with pending work ever sticks forever (stale count) and whether a separate 'Background work' label is worth the DESIGN.md change.
- Check `claude --help` and the hooks reference of the installed CLI for field names (background_tasks, session_crons, notification_type values) and record them in CliDriftTests so an update that renames them is caught.

## Questions for the user

- Should Failed be sticky until the next prompt (Supacode rule), or also clear when you view the session or press Mark as Read? Today canMarkRead excludes failures.
- Is a clickable pill with a popover acceptable (changes the DESIGN.md header contract), or do you prefer a 'Why this status?' item in the three-dot menu plus the diagnostics export?
- Do you want a distinct 'Background work' label instead of 'Working' for a parked session (needs the spike first), given D-54 already accepted that such sessions stay in Active?
- Agree to drop the 'Interrupted' state because the registry already reports Esc as 'Waiting for you'?
