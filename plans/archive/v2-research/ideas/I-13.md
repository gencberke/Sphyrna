# I-13: Receive OSC 7501 (Program Status Protocol) as a second in-band state source

Card from the [Loom v2 idea catalog](../IDEAS.md). **Receive OSC 7501 (Program Status Protocol) as a second in-band state source** · verdict **spike-first** · cost M · value 2/5 · proposed by 1 reports: [claude-official](../products/claude-official.md).

> Receiving OSC 7501 fits Loom's principles as a passive, hooks-subordinate cross-check, but most of the promised user gain (reason and message text) is already available from hook fields Loom drops, so run a half-day wire-capture spike first and adopt only a light version if Claude emits 7501 in states hooks miss.

## What the user gets

Faster, more truthful 'which session needs me' with the reason (auth / question / permission) and message text on the card, plus coverage for cases hooks miss (auth expiry, hooks disabled or silent), with no scraping.

## Mechanisms found in the research

[Documented in Claude Code terminal-config docs, 2.1.295+, nothing to enable] In the vendored SwiftTerm answer the `ESC ] 7501 ; ?` probe so Claude starts reporting, parse state/kind/msg/progress/id per PTY, feed as a cross-check next to hooks and the registry. Hooks stay authoritative for identity and transitions (7501 has no session id, no /clear or /resume continuity); disagreement is drift evidence, a missing report after an answered probe is one more drift signal. Mitchell Hashimoto's spec (2026-10-06), at revision 0.4 (a draft).

## Debates and fact-check corrections

tmux, background sessions (even attached) and CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1 send nothing; the probe order and the 'programStatus=no' debug line are user-reported (#101114), not documented; the lifetime rule 'new prompt' means a new SHELL prompt (OSC 133 A), irrelevant to a PTY running claude directly; whether Claude emits ids for subagents is unverified. Receivers disagree on precedence (some let live 7501 override hooks, tuios ranks hooks higher), which supports 'hooks authoritative, 7501 cross-check'. `done` must be mapped carefully to Finished unviewed.

## Design in Loom

FACTS (read in the tree): (1) Each live run has its own TerminalSurface for the whole run, selected or not (ConversationController.adopt/entries/keepEndedScreen); ended runs keep only a snapshot. So a per-surface receiver exists exactly when a PTY exists, with no cost for idle records. (2) SwiftTerm already has a public OSC override, Terminal.registerOscHandler(code:handler:), which runs synchronously inside parser dispatch under the terminal lock, in stream order with the later CSI c reply, and a public observeOscEvents on TerminalView. But TerminalView.terminal is internal, so a surface cannot reach registerOscHandler today. observeOscEvents is asynchronous (private queue) and copies every OSC including the frequent title updates, and its reply would arrive after the DA reply, so Claude would count the terminal as unsupported (spec: if the CSI c reply comes first, unsupported). (3) Claude 2.1.300 is installed here; its bundle contains the probe strings 'probe: no reply to OSC 7501 ; ?' and 'probe: OSC 7501 reply', plus probes for XTVERSION, CSI ? u, DECRPM 2026/1016 and the graphics query. The exact emitted kinds and msg texts cannot be read from the bundle. (4) The spec (revision 0.4, read from superlogical.com) fixes: whole sequence <= 4096 bytes, msg <= 2048 decoded bytes, reply to the probe is `OSC 7501 ; ? ST`, optionally with states= and kinds= lists (omitting them means the five fixed states and three kinds), terminals must refuse a report whose decoded msg or title contains control characters, and 'MUST NOT read meaning into msg'. working and blocked records drop at process exit, done and error persist, no heartbeat.\n\nDESIGN (lightest version, three small pieces):\nA. Vendor patch 15 in Vendor/SwiftTerm (same shape as patch 14, about 10 lines): a nonisolated TerminalView.setOscOverride(code:handler:) that forwards through renderOwner to Terminal.registerOscHandler. Document it in LOOM-VENDOR.md and the Updating list. No other engine change.\nB. LoomTerminal: TerminalSurface installs a handler for code 7501 in init. Handler (feed thread, under the lock) does only: if payload == '?', terminal.sendResponse(ESC ] 7501 ; ? ESC \\) (bare '?', the lowest commitment; the reply goes through the existing TerminalSurface.send -> TerminalInputQueue path, and before attach it is held in the bounded .launching buffer, so it is ordered ahead of the DA reply that the same parse pass produces). Otherwise call a pure parser (new file, e.g. LoomCore/ProgramStatus.swift: ProgramStatusReport, ProgramStatusParser) that enforces the spec limits, drops a whole report on any bad pair or control character, decodes base64, strips bidi and format characters, truncates msg to about 160 characters for display, and keeps at most about 8 records per run (root plus children by id, least recently updated evicted). It yields the changed root/summary into a bufferingNewest(1) AsyncStream, so a burst costs one wake-up. The surface exposes onProgramStatus like onTitle; ConversationController.adopt wires it by runID, resolving the owner when it fires (the existing pattern).\nC. LoomCore: SessionRuntime gets deliverProgramStatus(runID:report:) -> ClaudeSessionAdapter -> ClaudeHookStateTracker as an evidence field only (never writes currentStatus.activity). A small ProgramStatusComparer maps hook activity to the expected 7501 state (working<->working, waitingForApproval<->blocked/permission, waitingForInput<->blocked/question or idle, turnComplete/atPrompt<->done or idle) and, only when they differ, arms ONE one-shot timer per run (about 2 s settle, cancelled on agreement or any hook) because hooks arrive through a spawned loom-hook process after the in-band report. A disagreement that outlives the window is journaled once per kind as cli_compat_warning (same dedupe as ClaudeSessionAdapter.noteUnknownRegistryStatus); nothing is shown. 'Probe answered but no report by the first Stop' is journaled once per app run, with the CLI version from ProviderCapabilities.version and the user's CLAUDE_CODE_DISABLE_TERMINAL_TITLE excluded, as a drift signal.\nD. Optional display step, only after the spike: publish a short SessionViewState.statusDetail (kind plus sanitized msg) through SessionEventHub and show it where the label already lives (detail header state pill or its tooltip, and the menu-bar row), never as new card text and never in notification bodies.\n\nTRIGGERS AND BOUNDS: every step is driven by bytes already arriving on the PTY or by a hook; no polling, no timer except the one-shot above. No work when nothing is reported (Claude sends no heartbeat). Parse is bounded by 4096 bytes per report and 8 records per run, memory is a few KiB per run, the handler never blocks (no actor hop, no allocation beyond the report). Hidden window: PTY feed and parse continue as today, the handler adds no draw. Nothing persists; records vanish with the surface when the run ends.\n\nAUTHORITY RULE (matches contract section on hybrid sources: 'which state comes from which source, and the conflict rule, must be explicit'): hooks own identity, transitions, notifications, Dock badge, Cmd+J order and Finished unviewed. 7501 may only add evidence and a sanitized reason string. 7501 `done` must never create Finished unviewed (that comes from Stop plus Loom's own viewed tracking). The 7501 stream is unauthenticated terminal output (anything printed into the PTY can forge it), unlike the token-checked hook socket, so it must not drive attention state, notifications or any cross-session action.\n\nCHEAPER ALTERNATIVE THAT COVERS MOST OF THE STATED GAIN: Loom already parses PermissionRequest.tool_name (ClaudeHookEvent.Kind.permissionRequest(toolName:)) but drops Notification.message and tool_input. Reading `message` from the Notification hook and showing tool_name in the header gives the 'reason with text' on the authenticated channel with no vendor patch. Do this regardless of the 7501 decision.\n\nRESILIENCE UPSIDE (not a promise): Loom's second status source today is ClaudeRegistry, an undocumented ~/.claude/sessions/<pid>.json file read behind vnode watches and strict identity checks (ClaudeRegistry.swift, ClaudeRegistryReader.decode). 7501 is a documented, generic protocol that gives the same busy/waiting/idle information in-band. If the spike shows it reliable across a few Claude releases, it could later replace or back up the registry watch, which would remove a private-format dependency.

## Where it shows

Phase 1 (passive): no UI. Journal lines in the existing diagnostics export (status_disagreement, no_program_status) so the user and the maintainer can see how often hooks and 7501 differ.\nPhase 2 (only if the spike justifies it): the detail header state pill gets a precise reason word when Claude says so (for example 'Needs approval · Bash', 'Question', 'Sign-in needed') with the sanitized one-line msg as the pill tooltip; the menu-bar row text may show the same words. The sidebar card stays as is: UI-MAP says the label text is shown in the header and the accessibility label, not on the card, and the card is a deliberate dot-only design, so a message line on the card would reverse a design decision and needs the user's say. A startup dialog (folder trust, first-run login) that today reads 'State unknown' could read 'Waiting for you' if the spike shows 7501 covers it. No new panel, no new sidebar element, no animation.

## Principle check

Resources: pass. Event-driven, bounded (4096 B per report, 8 records per run), one-shot timer only on disagreement, nothing when the window is hidden or the run is idle or ended. Risk: a tool-heavy turn could emit many reports; mitigate with a bufferingNewest(1) stream and measure in the spike against the 40% of a core at 1 MiB/s gate. Predictability: pass if 7501 never overrides hooks; risk if a later change lets it set state, because receivers disagree on precedence. Accurate status: pass as evidence-only; `done` mapped to Finished unviewed would be a violation, and so would trusting an unauthenticated PTY stream to raise Needs approval or a notification. Fluency: neutral to small gain; the probe is answered with no prompt or setting. Modularity: pass; parser in LoomCore (pure, testable), surface hook in LoomTerminal, comparer in the adapter; costs one more vendored patch (the 15th) that must be re-applied on every SwiftTerm update. CLI-update resilience: mostly pass (documented in Claude's terminal-config docs, generic protocol, feature-detected, unknown keys and states ignored, never pinned); risks are that the spec is revision 0.4 (a draft), the probe order is user-reported (issue 101114), and answering the probe could change other Claude behaviour, for example the terminal title that Loom stores as the session title (CatalogModel.terminalTitleChanged / recordTerminalTitle); the spike must check this. Ownership: no process or file is created. User authority: nothing cross-session; msg is untrusted text, rendered as plain text, never put in notification bodies, and not interpreted (the spec says terminals must not read meaning into msg). Settings and CLAUDE.md of the user are untouched.\nThings that would make it a violation: polling the registry or screen to compare, letting 7501 set currentStatus.activity, parsing msg for meaning, showing unsanitized msg, or a per-OSC observer that copies every title update (use the synchronous override for code 7501 only).

## Value for the user (2/5)

Hooks plus the registry already give this user Working, Needs approval, Waiting for you, Failed and Finished unviewed, and a hook fires at the same moment as the 7501 report (the spawn latency of loom-hook is tens of milliseconds, not perceptible). The reason text can come from hook fields at near-zero cost. What 7501 adds uniquely is coverage of states with no hook (startup folder-trust or login dialogs, hooks disabled or lost), drift evidence, and a documented replacement path for the private registry file. For a user with 5 to 10 parallel sessions in two projects these are rare edge cases, though they get more valuable if v2 moves toward a chat-centred UI that wants a precise 'needs you because' line, because 7501 is UI-agnostic. Honest re-estimate: cost S holds for the passive receiver (patch, parser, surface hook, journal), but the proposed card reason and disagreement logic make it M.

## Depends on

- Prerequisite: hooks and the registry stay authoritative (D-45 hook-silence and drift work, already shipped in 0.4.x)
- Independent, cheaper sibling worth doing first: show Notification.message and PermissionRequest tool_name from the existing hooks as the reason
- Soft link to any v2 'needs you' surface (menu bar rows, header pill, a future chat-centred view) that would display the reason

## Experiments before building

- E1 wire capture (half a day, read-only for Loom): a throwaway PTY harness (Python pty or loom-probe) runs `claude` 2.1.300 with an isolated CLAUDE_CONFIG_DIR and a temp project folder, answers XTVERSION, CSI ? u and `OSC 7501 ; ?` before CSI c exactly as the spec says, and logs every OSC 7501 with a timestamp next to the JSON of a logging hook (Loom's --settings hook set, writing to a file). Scenarios: untrusted-folder trust dialog, no-credentials login screen (likely the cheapest way to see kind=auth), then with an authenticated isolated profile (the user must supply or approve that login): a plain turn, a tool permission prompt, AskUserQuestion, plan-mode approval, Esc interrupt, API error, /clear, /resume, a foreground subagent and a background subagent, idle for 60 s, exit. Decides: (a) are there reports in states that fire no hook (trust, login, first run)? (b) which kinds and msg texts, and do they carry more than Notification.message; (c) what ends a turn (done or idle) and whether done matches Stop; (d) do subagents get child ids; (e) report rate during a tool-heavy turn; (f) latency versus the hook; (g) is the terminal title (spinner, topic) different when the probe is answered versus unanswered, since Loom stores titles; (h) does the unanswered case emit anything.
- E2 engine check (a short unit-test-sized spike once E1 data exists): replay the E1 capture through TerminalSurface with the vendor override to confirm the reply is written before the DA reply, the handler adds no measurable feed time at 100 reports per second, and the 1 MiB/s CPU gate is unchanged; reuse the loom-test-child terminal-sample pattern in TerminalSurfaceTests.
- Decision rule: adopt-light (phase 1, optionally phase 2) if E1(a) shows real coverage of hook-silent states or E1(b) shows useful kinds, and E1(g) shows no title change; fall back to the hook-field reason only and mark 7501 'later' (revisit when it reaches the stable npm channel, currently 2.1.292 has no sender, and when the spec leaves draft) if Claude only mirrors what hooks already say.

## Questions for the user

- Is a one-line reason in the detail header (not on the card) enough, or do you want text on the sidebar card? That would reverse the dot-only card design.
- May the spike use an isolated Claude profile that you log in once (needed for permission, question, subagent and error scenarios), or should it stay on the no-credentials cases only?
- Are you willing to carry vendor patch 15 (a nonisolated OSC override accessor, about 10 lines) in Vendor/SwiftTerm for this?
- Should 7501 ever be allowed to drive state when the hook-silence watchdog has fired (a fallback for dead hooks), or stay strictly evidence-only? That is the only case where it would raise the value, and it weakens the 'hooks authoritative' rule.
