# I-44: Engineering guardrails: performance budgets, reader regression, contract fixtures, compat advisories

Card from the [Loom v2 idea catalog](../IDEAS.md). **Engineering guardrails: performance budgets, reader regression, contract fixtures, compat advisories** · verdict **adopt-light** · cost S · value 3/5 · proposed by 7 reports: [cmux](../products/cmux.md), [happy](../products/happy.md), [usage-tools](../products/usage-tools.md), [attention-surfaces](../products/attention-surfaces.md), [t3code](../products/t3code.md), [superset](../products/superset.md), [herdr](../products/herdr.md).

> Loom already ships most of this (per-row equality-guarded sidebar with a body-count harness, offset+inode transcript tailing, visibility-gated work, session-scoped 1 s hooks, drift detection), so adopt only the missing slice: a parametrised 1/10/100 render-budget test table that every v2 per-card or per-panel datum must join, value-free hook-payload shape fixtures re-captured on CLI change, and a drift explanation string, with no bundled bad-version JSON and no network fetch.

## What the user gets

Protects the properties that make Loom usable all day (CPU gate, no beachballs with 30+ sessions, accurate status) as v2 adds per-card data, and turns CLI-update surprises into actionable messages.

## Mechanisms found in the research

(a) Sidebar budget as a test: immutable value snapshots plus action closures, Equatable rows with .equatable(), no state writes from body or the ForEach projection, per-card extras via one coalesced equality-guarded projection, hidden means no work, 1/10/100-session synthetic harness without real CLIs, run only when the user says the computer is idle. (b) Transcript reader regression: incremental by byte offset + inode, idle sessions cause zero reads (Happy's 3 s full re-read took 20-40% CPU). (c) No animation or render for hidden panes (herdr: removing the sidebar spinner and skipping hidden-pane renders cut CPU 89-95%). (d) Captured-payload contract tests for hooks and approvals, agent-tracking fixtures. (e) Compatibility advisories: a small JSON of known-bad CLI versions and feature thresholds bundled with each release, optionally one conditional fetch at launch, shown as a non-blocking banner and as the explanation when drift detection fires; never block by version. (f) Hook hygiene: tiny, fast, no-op outside Loom, scoped via --settings, fail-open, short timeouts.

## Debates and fact-check corrections

T3 treats 2.1.111..2.1.280 as 'graceful' and only <2.1.111 as unsupported, and only emits an advisory (the '2.1.280+ hard minimum' is from release notes, not code), so version advisories are compatible with 'never pin' only if advisory. Several resource data points are single-user reports (cmux #2487 not #2586 for the 8.5 h figure; herdr #5289 is a non-default mode; Superset's 12.8 s hook and 50x git status are single measurements); the stable-vs-nightly difference matters (cmux freezes were seen on nightlies). Whether Loom already covers each item is unknown.

## Design in Loom

STATE TODAY (read in code, so most of the idea is already done)
(a) Sidebar budget. SidebarRenderTests (Tests/LoomCatalogUITests/SidebarRenderTests.swift) hosts the real SidebarView in a never-shown 3,200 pt window with 30 cards and counts card and time-label body evaluations through SidebarRenderProbe. It asserts: a selection change evaluates 2 cards; the minute tick evaluates 0 cards and 30 labels and does not regroup the days; an Active-section flip evaluates the moved card at most once and no others. CatalogHotPathTests covers row patches, one search query, and equal-value refresh writing no observed property. CatalogScaleTests measures catalog queries at 1,000 and 10,000 rows. The mechanism differs from cmux's: Loom uses per-row @Observable SessionRowModel with apply(...) equality guards (CatalogModel.swift ~l.101-146), not Equatable value snapshots plus .equatable(). The result is the same invariant (a change evaluates only the affected card), so do NOT rewrite to the cmux pattern.
(b) Reader regression. ClaudeUsageIndex keeps per-file (dev, ino, byte offset, 64-byte guard hash) and reads only appended bytes. SubagentTranscriptTail reads only new whole lines, holds back a partial last line, restarts on a shrink or a new inode, and cold-opens on the last 512 KiB. Tests: ClaudeUsageIndexTests.appendReadsOnlyTheNewBytes, shrinkReparses..., replacedFileWithANewInode..., tamperedBytes...; SubagentTranscriptTests.onlyNewBytesAreRead, anIdleFileDeliversNothing, aBurstOfWritesIsCoalescedIntoFewReads. Wake-ups are event-driven: UsageTranscriptWatcher is FSEvents, and the SubagentTranscriptFeed is one vnode source that runs only while its panel is on screen and the window is visible, capped at 5 reads/s. The Happy failure mode (3 s full re-read) is structurally excluded already.
(c) Hidden means no work. CatalogModel.setWindowVisible (CatalogModel.swift ~l.1034) stops the minute tick and the subagent feed. The working indicator is a Core Animation keyframe animation in the render server (IndicatorView.swift ChaseDots), documented as zero wakeups and zero SwiftUI updates, because a TimelineView re-evaluated the whole graph. SwiftTerm has hidden-window suspension (patch suspended-signal-retention). The usage model collects only changed paths while hidden (ARCHITECTURE.md 'Finished turn and usage'). Measured baseline: working indicator under reduced motion about 0.005% of a core, hidden stream1 3.5%, idle observer with one real Claude 0.044% (DEVELOPMENT.md section 7).
(f) Hook hygiene. ProviderLaunchProfile.claudeSettings puts 9 events in the per-session --settings only (nothing in the user's global settings, contract section 9) with timeout 1, args [], and deliberately no per-tool hooks. loom-hook (Sources/loom-hook/main.swift) exits at once with a log line when LOOM_* env is missing, uses a 0.5 s socket timeout, and a wrong token gets a NAK. HookDiagnostics counts received, applied, malformed, overflow and dropped-by-reason into the diagnostics export. A hook-silence watchdog (3 s, SessionIssueNotice) exists.
(e) Drift. ProviderCapabilities is read from claude --help; ExecutableStamp re-resolves the toolchain after a CLI update; a missing required option never refuses a start (reportCompatibility journals cli_compat_warning once per version and option set); the registry reports unknown statuses once; the journal records claude_cli. This matches contract section 9 and D-45.

WHAT IS MISSING (the adoptable slice)
1. Render-budget table (extend SidebarRenderTests; test-only, no runtime cost). Make host(cards:) parametric over 1/10/100 and add table-driven rows: 'a write to field X of session A evaluates exactly card A'. Seed rows now for fields that exist (live state, subagent list update, pin, rename, title, project tone), and add one row for every v2 per-card datum when its feature lands. Add rows for writes to shared model properties. Hypothesis, not yet measured: SessionCardView.body reads model.projects (through projectName(for:) -> projects.first), model.branches (a whole dictionary) and model.viewMode, and CatalogModel.toggleCollapsed rewrites projects via refreshProjects, so a collapse toggle or rename probably evaluates every loaded card. The first table run will confirm or refute this. Then give the rule in writing: new per-card data lives on SessionRowModel with an equality-guarded apply(...), never in a model-wide dictionary read by every card body.
2. A 'live burst' case: 30 sessions with hub frames (status, subagents, activity stamp) arriving in a burst, asserting body evaluations per frame stay at or below 1 card (the 100 ms patch path, CatalogModel+Patching). SidebarRenderTests uses only idle cards today.
3. Panel gate. When a v2 right panel or chat view arrives it registers with the same visibility edge (setWindowVisible, plus an on-screen flag as SubagentTranscriptModel does: wanted = !closed && onScreen && windowVisible). One test per consumer: hidden means zero timers, zero reads, zero scheduled sleeps. SidebarRenderTests already shows the pattern (gate.requested.count).
4. Hook payload shape fixtures. Today every payload in ClaudeHookTests and SubagentTests is hand-written (SubagentTests says shapes follow 'the 12 Oct 2026 research of Claude 2.1.293'; the CLI is now 2.1.300). Add a capture mode to the existing loom-probe hook-expect experiment (Sources/loom-probe/ProviderExperiment.swift, plans/experiments/claude-hooks.json). It runs a real claude (haiku, low effort, isolated CLAUDE_CONFIG_DIR) through about 4 short turns: a plain turn, a tool needing approval, a subagent, /clear. It dumps value-free shapes per event (key names and JSON types only) to Tests/LoomCoreTests/Fixtures/hook-shapes-<version>.json. A test loads the newest fixture, builds payloads from it and asserts that ClaudeHookEvent and ClaudeHookStateTracker read the fields Loom depends on (session_id, hook_event_name, transcript_path, agent_id, background_tasks[].type/status, last_assistant_message, notification_type, tool_name). A re-capture on a CLI change diffs old vs new shapes, which is the 'CLI-update surprise' detector, and runs only when the user says the Mac is idle (short real-Claude turns are pre-authorized by D-04). Keep it value-free like the other plans/experiments JSON. Approval answering is not in Loom today (PermissionRequest only detects state, the helper returns no decision), so no approval-decision contract is needed yet. If an actionable-approval idea is ever adopted, add the PermissionRequest and AskUserQuestion updatedInput captures first; the research notes that the AskUserQuestion-on-PermissionRequest path is undocumented and that CLI 2.1.300 now validates updatedInput.
5. Drift explanation without a feed. Keep one constant for the CLI version the shipped Loom was last captured against (written by the capture step). When a drift event fires (cli_compat_warning, an unknown registry status, hook_silence), add 'Claude <installed>; this Loom was last checked with <captured>' to the existing issue text and the diagnostics summary. No bundled known-bad JSON (Loom has no list of bad versions to ship, and the owner updates Loom manually, D-47). No launch fetch (it would be Loom's first network code, which D-32/D-37 avoided, and it adds a failure mode). No banner on a merely newer version: the user runs the latest CLI, so it would fire constantly and teach dismissal. T3's 'version gate' is advisory-only in code (the fact-check says it is 'graceful' from 2.1.111 and only below that 'unsupported'), so an advisory is compatible with 'never pin' only when it appears as the explanation for observed drift.
6. Perf scenario (optional, +M, idle Mac only). Add a 'cards30' scenario to scripts/cp5-d-measure.py or scripts/perf/indicator_cost.py using loom-fake-provider: 30 sessions, 5 'working', window visible vs hidden, N hook frames per second; report Loom's own CPU and wakeups and judge them with compare_baseline.py gates. The existing matrix covers terminal streaming (stream1/10, spinner1) but never a crowded sidebar.

SPIKE (decides one number): hook helper latency under load. Run the built loom-hook against a stub listening socket 1,000 times with synthetic stdin, once idle and once while swift build runs, and record p50/p95/max wall time. If p95 is far below the 1 s settings timeout the value stays; if max approaches it, raise it. A killed helper loses an event silently (the watchdog covers only 'no hook ever'), which is the same hazard as Superset's slow UserPromptSubmit (single-machine 12.8 s). Do not move the hooks to async: the code comment says synchronous is chosen so helper racing cannot reorder identity and state.

TRIGGERS AND BOUNDS: everything above is test-time or developer-time; the runtime change is one string constant. Nothing polls, and no runtime reads or timers are added. Window-hosting tests and the perf scenario run only when the user says the Mac is idle (DEVELOPMENT.md section 3); the shape-capture needs 4 short haiku turns in an isolated profile.

## Where it shows

Almost no UI. The only user-visible change is one extra clause in an existing notice: when drift is observed, the SessionIssueNotice line above the terminal, or the Settings > About diagnostics, says 'Claude 2.1.3xx; this Loom was last checked with 2.1.300'. There is no new banner, no new settings page and no new sidebar element. The point is that the future right panel, chat view and richer cards must not make the existing UI heavier.

## Principle check

Resources: pass. These are tests and developer tooling, and the runtime adds nothing (no poll, no read, no timer, no network). A launch-time conditional fetch would be a first network dependency and is rejected. Predictability: pass; body-evaluation counts are deterministic, whereas CPU gates are noisy, so use counts in tests and CPU only in idle-Mac measurements. Accurate status: pass and improved; shape fixtures catch a silent payload change before it makes a status wrong. Risk: a fixture frozen at 2.1.300 can falsely reassure, so the capture date and version must be stored and the test must name them. Fluency: pass; no new prompts or waits. Modularity: pass; the budget table sits beside the existing SidebarRenderProbe and the capture lives in loom-probe, which is dev-only, so nothing lands in the release tree (check.sh --release-tree must still pass). CLI-update resilience: pass if the advisory stays an explanation attached to observed drift. It becomes a violation only if it gates a start by version or ships a hand-maintained known-bad list that Loom then trusts (contract: 'versions not pinned', 'no result inferred from an unknown event'). Ownership: unaffected. User authority: unaffected, because there are no cross-session actions. Risk: the heavy runs (window tests, perf scenario, real turns) must follow the idle-Mac rule or they cause the heat the user's policy forbids. Standing decisions D-34 and the 'terminal is the real CLI' rule are not touched.

## Value for the user (3/5)

It is protective, not a feature. A v2 chat-centred UI, right panel and richer cards are where the daily-use properties (no beachball with 30+ sessions, accurate status, low idle CPU) are most likely to regress, and the shape fixtures plus the table give early warning at low cost. It is not a 4 because Loom already has the hard parts (O(1) card patching, incremental readers, hidden gating), so what remains is mostly discipline and a test table, not new capability. It rises to 4 if the chat-centred UI renders transcripts in SwiftUI, which is the largest new CPU risk.

## Depends on

- Any v2 feature that adds per-card data, a right panel, or a transcript-rendering chat view (each adds one row to the budget table)
- D-04 pre-authorization of short real-Claude turns, and the idle-Mac rule, for the shape capture and the perf scenario

## Experiments before building

- Run the extended SidebarRenderTests (1/10/100 cards, shared-property writes) once with the user's idle-Mac go-ahead. It decides whether a project collapse or rename, or a change to branches, evaluates every loaded card as suspected. If yes, move projectName, tone and branch label onto SessionRowModel as equality-guarded fields. If no, the hypothesis is closed.
- Hook helper latency: 1,000 loom-hook runs against a stub socket, idle vs under a concurrent build, p50/p95/max against the 1 s timeout in ProviderLaunchProfile.claudeSettings. Decides whether timeout 1 stays.
- One real-Claude shape capture on 2.1.300 (about 4 haiku turns, isolated CLAUDE_CONFIG_DIR) diffed against the hand-written payloads in SubagentTests and ClaudeHookTests. Decides whether any assumed field is stale; this is the first value of the fixtures.
- Optional cards30 CPU scenario with loom-fake-provider, window visible vs hidden, to confirm that a crowded sidebar stays well under the 40% gate and that hidden costs about nothing.

## Questions for the user

- Is it acceptable to add a small 'last checked with Claude X' constant that is refreshed whenever the shape capture is re-run, given that the user publishes Loom releases by hand? The alternative is no version text at all.
- Should the capture and the perf scenario be part of the release checklist (run on each CLI minor bump) or stay an on-demand tool the planner runs? The first costs a few real turns per release.
- If the chat-centred UI goes ahead, should its transcript renderer have a hard budget (rows drawn, bytes parsed per second, hidden means zero) written into the contract before the design is chosen?
