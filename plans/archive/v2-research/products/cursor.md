# Cursor 3 Agents Window (Cursor 3.0 to 3.24, April 2 to October 9, 2026)

Research note for the Loom v2 brainstorm ([index](../V2-BRAINSTORM.md)). Written by a research subagent on 2026-10-17 and fact-checked by a second one; the fact-check is at the end and wins over the report where they differ. Raw JSON: `../evidence/deep-dive-20261017.json`.

**In one line:** Cursor's agent-first window: one multi-repo sidebar of local, worktree, SSH and cloud agents with tiled chats, a Changes/PR review tab, side chats, subagent trays and a Dock/menu-bar unread list. It ships roughly weekly and is the most direct commercial analogue of Loom's sidebar, but it owns the agent loop and is a heavy Electron app.

**Category:** hybrid (chat-first agent window on an IDE base; the classic editor remains a separate window)

## Adoption

Cursor's own numbers (blog third-era, Feb 26 2026): agent users are 2x Tab users (it was 2.5x the other way in March 2025); agent usage grew over 15x in a year; over a third of PRs merged inside Cursor come from cloud-VM agents. Press reports (secondary, via getpanto.ai) give ARR above $2B (Feb 2026) and more than 1M daily users. There is NO official figure for how many agents users run at once, so this is unverified. Signals point low: a forum thread (Mar 2026) has users who never needed a herd; a Reddit comment says "I'll rarely run more than two at a time"; the iOS Live Activities show up to eight agents (learncursor.dev, secondary). The Agents Window was made the default window and drew a backlash (forum 160057 and a Reddit thread from Aug 2026; the workaround is the "Window Restoration: Last Used Windows" setting, or `cursor --classic`). Positive reports come mostly from people with many projects or a small laptop screen. Release cadence is about one Agents Window release a week (3.19 on Sep 2, 3.20 on Sep 10, 3.21 on Sep 17, 3.22 on Sep 24, 3.23 on Oct 1, 3.24 on Oct 9), plus Projects, Remote Control (Oct 6), Rollouts and Security Review bots. One changelog snapshot (Oct 16, 2026) mentions an "Origin" code host.

## Architecture

Stack (from forum bug reports with stack traces): an Electron app on a VS Code workbench fork. The Agents Window is a "Glass" layout (bundle `workbench.glass.main.js`; `cursor --classic` bypasses it) with React panels (`useMemo` frames in the AgentPanel error trace, forum 157604). Cursor markets it as "built from scratch"; the traces show it shares the VS Code workbench, file models and extension host.

How it drives the agent: Cursor owns the agent loop. It does not host a third-party CLI in a PTY. Local agents run through Cursor's own harness in an extension host (`anysphere.cursor-always-local`, bundled `cursor-agent-exec`). Cloud agents run in VMs and sync through RPCs such as `aiserver.v1.BackgroundComposerService.ListAgentStoreDirectory` (forum 168692). Because Cursor owns the loop, states (running, waiting for question or approval, error, unread) are first-party events, not inferred. Lifecycle hooks exist in `.cursor/hooks.json` (`beforeSubmitPrompt`, `subagentStart/Stop`, `stop`, `afterAgentResponse` and others; 14 of 20 events also run on cloud). `subagentStop` now carries `child_conversation_id` (3.22). The separate Cursor CLI speaks ACP, with subagents shown as child sessions (CLI v2026.09.15).

Persistence: per-workspace SQLite (`state.vscdb`, `cursorDiskKV` rows such as `inlineDiff:<workspaceId>:<diffId>`) plus server-side state for cloud agents. Pins for cloud agents sync across devices (3.21). Worktrees live under a machine-wide worktree root, with mtime checkpoints for rediscovery at startup (3.5+, docs configuration/worktrees).

Remote Control: one backend serves three surfaces (iOS, web, desktop). A local agent keeps running on your computer and the phone drives it through Cursor's cloud relay. The computer must stay awake (a "Keep this computer awake" setting; plugged in, lid open). Source: learncursor.dev, changelog Oct 6 2026.

Resource notes (heavy): one forum reporter (Windows, 64 cores, 20+ chats open; this is the reporter's measurement and Cursor has not confirmed it) traced multi-day CPU and memory growth in 3.19 and 3.20.0 to three things. (1) Every persisted inline diff is restored eagerly at window start (about 517 text models, 471 MB renderer heap with no chat open); a feature gate `park_inline_diffs` defaults off. (2) A listener leak on `$onAgentExecFileChange`. (3) A store-sync round every 5 s per mounted store plus a 250 ms `checkExclusiveMutationClaim` timer that spawns `whoami` (about 4 spawns per second per chat), which made tool calls take a median of 8.8 s. Another thread reports 22 GB RAM across helper processes. Cursor's fixes in 3.1 to 3.24 are mostly performance work: "avoids expensive updates and fetches unless truly needed", hidden browser tabs no longer render, rust-analyzer starts only when a Rust file opens, and the extension host auto-restarts after 60 s of hang.

## Core loop

1. Open the Agents Window (now often the default). The sidebar lists agents across all repos (local, worktree, SSH, cloud, and those started from phone, web, Slack, GitHub or Linear). It has Pinned (up to 75), per-repo groups, Projects and a Chats group.
2. Start an agent from the empty state: pick the project or repo and branch, then Local, Worktree or Cloud (Cmd+; cycles Cloud). Shift+Tab switches to Plan mode, which asks questions and produces an editable plan tab. "Build" or "Build in Parallel" executes it. /multitask fans out async subagents.
3. While it runs, the user queues or steers messages, opens a /side chat for tangents, or splits the view into tiles to watch several agents. Pills above the prompt show live status first (pending input, Changes, Agents, Terminals, Canvas, Queue) and then actions.
4. When agents finish, the user is pulled back by the unread dot, a chime, and the Dock or menu-bar unread list. An agent that fails gets a red Error status. A blocked agent shows a Questions pill or a yellow dot. The user answers, including questions from subagents, inside the parent chat.
5. Review in the Changes tab (scoped to uncommitted changes or "Last Agent Turn"), stage, commit, open the PR in a PR tab, and use Fix CI, Bugbot or "Fix with Agent". Jump from a diff line to the file for manual edits. Go back to the classic IDE window for per-hunk accept/reject, IntelliSense and extensions.
6. Hand long jobs to the cloud (`/in-cloud`, Move to Cloud, `/babysit` a PR) and supervise from the iOS app. Cmd+K searches agents by transcript content.

## Features

### Multi-workspace agent sidebar, tiles and per-agent tab strip (navigation-ux, confidence high)

- **What the user sees:** A sidebar listing every agent across repos and environments, with pinning (cap raised to 75 in 3.22), a hover card with agent details, and Show > Status filters. Chats open as tabs. Tiled layout (3.1) splits the view into panes; tiles can be dragged, expanded and rearranged, and the layout persists. Each agent gets a tab strip where subagents and side chats open as tabs beside the parent (3.24). Full-screen tabs (3.4, Cmd+Shift+M) maximize the right panel and leave a floating prompt bar. Compact chat density: Compact, Balanced or Detailed tool-call detail (3.4).
- **How it works:** First-party app state in the workbench; not a process or terminal view. Layout persistence is local state. Code paths were not readable because Cursor is closed source; behavior is taken from the release notes.
- **Reception:** Praised by people with many projects or a small laptop screen ('only way to get work done' on a 13-inch laptop, Reddit r/cursor, Aug 2026). Criticized as hard to leave and slow: users resent it being the default window, and the same Reddit thread has complaints about slowness and non-configurable shortcuts that collide with IDE muscle memory (forum 166381, 167129).
- **Evidence:** https://cursor.com/changelog/3-1; https://cursor.com/changelog/3-4; https://cursor.com/docs/release-notes (3.22 Pin up to 75 agents; 3.23 Drag subagents into a split; 3.24 Subagents and side chats open as tabs); https://cursor.com/docs/agent/agents-window

### Attention and status surface (unread, Error, blocked, Dock and menu-bar list) (attention-status, confidence high)

- **What the user sees:** Per-agent unread dot; a 'New Messages' divider and pill that marks where unread replies start inside the chat (3.22); a red Error status with its own Error group and a Show > Status toggle (3.22); a yellow dot on the Agents pill when a subagent waits on a question or MCP sign-in (3.21); the Questions tray collapses into a pill with a count (3.19); right-clicking the Dock icon lists Unread agents (3.19) and the menu bar lists unread agents first with 'N more unread' (3.24); the quit dialog lists still-running agents and clicking one cancels the quit and opens it (3.19); a usage ring appears in the chat status bar past a threshold (3.22). Sound and system notifications exist but are coarse (a settings toggle; users ask for a sound when permission is awaited, forum 171672).
- **How it works:** Status is first-party because Cursor owns the agent loop; no inference from a registry or hooks is needed. Unread is tracked per agent and mirrored to the Dock and menu bar. Not code-read.
- **Reception:** The release notes themselves show how fragile this is: fixes for stale cloud status, agents that flip back to running or unread when a stale update arrives, false 'Done' notifications from cloud agents outside the current workspace, and Dock and menu badge counts that disagreed with the sidebar (3.22 and 3.23). A reminder that status needs a single source of truth.
- **Evidence:** https://cursor.com/docs/release-notes (3.19, 3.21, 3.22, 3.24 sections); https://forum.cursor.com/t/play-a-sound-when-the-agent-is-waiting-for-a-tool-permission/171672

### Side chats (/side, /btw) (chat-input, confidence high)

- **What the user sees:** Type /side (optionally with the question), use the + button at the top of the chat, select text or a diff and choose 'Ask in Side Chat', or press Shift+Cmd+S. A durable child conversation opens next to the main chat. It is seeded with the parent's history, which is hidden from its transcript. It defaults to reading, searching and answering, not editing. Follow-ups stay in the side chat. @-mentioning the side chat in the main thread pulls its context back. Closing archives it. No nesting. The side rail lists the five most recent side chats, the command palette finds them, and they open as a tab on the parent (3.24). Cloud agents got side chats in 3.23, where a side chat runs as its own cloud agent; Projects use threads instead.
- **How it works:** Per Cursor help: 'the parent's conversation history is copied in as reference context for the model', not rendered. It is not a fork (fork copies the transcript). Mechanics beyond the help page are not public. Introduced in 3.11 (Jul 10 2026); cloud support added in 3.23.
- **Reception:** A Reddit commenter singled out side chat as a feature they like even while disliking the Agents Window. Third-party guides frame it as paying a 'context tax' only once. Limits: cannot steer the main run; local-only at launch, which was a complaint until 3.23.
- **Evidence:** https://cursor.com/help/ai-features/side-chats; https://www.digitalapplied.com/blog/cursor-3-11-side-chats-agent-transcript-search-2026; https://aicatchup.com/news/cursor-side-chats-durable-agent-threads (staff forum quote Jul 13 2026); https://cursor.com/docs/release-notes (3.23 Side chats now work on cloud agents; 3.24)

### Worktrees and /best-of-n (parallel-worktrees, confidence high)

- **What the user sees:** Start or move an agent into a worktree from the Agents Window; review, commit or create a PR from it, or bring it back to the main checkout. `.cursor/worktrees.json` holds setup commands (`setup-worktree`, per-OS variants, `$ROOT_WORKTREE_PATH` for copying `.env`). Automatic cleanup keeps the newest N worktrees machine-wide (`cursor.worktreeMaxCount`, default 25; checked every `cursor.worktreeCleanupIntervalHours`, default 6). /best-of-n runs one task across several models, each in its own worktree; it compares but does not merge. Slash forms /worktree, /apply-worktree, /delete-worktree.
- **How it works:** Plain `git worktree` underneath. Startup rediscovery re-scans the worktree root unless mtime checkpoints prove nothing changed. Cleanup also deletes worktrees created outside Cursor, because it rediscovers the root each pass.
- **Reception:** Worst-received part of Cursor 3 at launch: users said the redesign made worktree work 'muddied' (setup config ignored, no Apply Changes button, no worktree icon on the agent, the agent loses track of which checkout it is in, chat history polluted by setup and copy chatter). /best-of-n did not work in the new interface at 3.0.4 and model names were ignored in the classic one. Serious data-loss report on 3.14.7: Cmd+Shift+E (Archive) instantly deleted a dirty worktree with about 60 modified files and no confirmation; unarchive restored the chat but not the files; the user recovered edits from the transcript twice.
- **Evidence:** https://cursor.com/docs/configuration/worktrees; https://forum.cursor.com/t/cursor-3-worktrees-best-of-n/156507; https://forum.cursor.com/t/best-of-n-does-not-run-parallel-model-worktrees-falls-back-to-single-agent/156550; https://forum.cursor.com/t/archiving-an-agent-deletes-its-dirty-worktree-without-confirmation/167129

### Changes tab, PR tab and agent-change review (review-git, confidence high)

- **What the user sees:** A simplified diff view per agent (Changes tab, Ctrl+E) with stage, commit and PR management; a 'Last Agent Turn' scope that shows only the latest turn's edits, reached from Review or from the end-of-turn summary (3.22); a repository and worktree picker in the Changes tab and search in the local file tree (3.20); diff-to-file navigation (3.1); Collapse/Expand-all shortcut (3.19); a PR tab with review state, reviewer threads, CI status groups (Action Required, Ready) and stack navigator; follow-up pills such as Fix CI and Fix Merge Conflicts; /review runs Bugbot and Security Review before pushing, and Bugbot dedupes against the same diff once the PR opens (June 2026). Bugbot posts PR comments, can autofix to a new or existing branch, and has a `.cursor/config/bugbot.yaml` (review effort, incremental, autofix mode).
- **How it works:** Git-based diffs (the Changes tab compares to HEAD) rather than the IDE's per-edit tracking. Bugbot is a cloud service reading PR diffs, with a check status (neutral, success or failure) and an API.
- **Reception:** Cursor staff confirmed in April 2026 that per-hunk accept/reject was missing in the Agents Window, one of the most requested items, with the workaround of opening the classic editor window in parallel. A user said confidence comes from seeing changes and thinking live, and that a Review panel which cannot be undocked or full-screened is painful on a laptop. Bugbot: 80% of its findings resolved by merge (Cursor's May 2026 claim, via augmentcode.com, unverified); the 'Last Agent Turn' scope is the fix for 'too much to review'.
- **Evidence:** https://cursor.com/docs/release-notes (3.19, 3.20, 3.22, 3.23); https://forum.cursor.com/t/agents-window-is-not-good/157226; https://forum.cursor.com/t/diff-iculty-seeing-whats-changing-agent-window/157588; https://cursor.com/docs/bugbot; https://www.gradually.ai/en/changelogs/cursor/ (Bugbot 3x faster, /review, June 10 2026)

### Plan mode, queue and steering, goal pill, composer pills (chat-input, confidence high)

- **What the user sees:** Shift+Tab rotates into Plan Mode: clarifying questions, codebase research, an editable plan opened as a Plan tab with save-to-workspace, then Build or Build in Parallel (independent steps run at once). Messages sent while the agent works are queued, and a Steer New Messages setting sends them mid-run instead. Pills above the prompt (Goal, Queued, Debug, Canvas, Open Browser, plus Changes, Agents, Terminals) open or minimize their panels, and open themselves when something new appears (3.24). /goal gives a chat a completion condition; goal continuations keep the chat's Auto-review setting. Other composer details: '#' references your PRs, '@' references past chats, push-to-talk voice (Ctrl+M), Cmd+Up/Down jumps between your messages (3.23), /summarize on cloud agents, and an edit-and-resubmit dialog 'Revert files to this message?' (3.19).
- **How it works:** Plan is a markdown document in the app with dirty tracking and reload on change (3.1). Queue is client state sent between turns; steering injects into a running turn, falling back to the queue for cloud agents that cannot take it (3.19). Not code-read.
- **Reception:** Plan-first is Cursor's recommended default for complex work. Queued messages being lost at turn end was a bug fixed in 3.22, 3.23 and 3.24, which says how central the queue is. The pills are a deliberate fix for 'the composer shifts around' layout complaints.
- **Evidence:** https://cursor.com/docs/agent/planning; https://cursor.com/help/ai-features/multi-agent; https://cursor.com/docs/release-notes (3.19, 3.21, 3.23, 3.24)

### Subagent tray, cascading stop, answering from the parent, /multitask (orchestration, confidence high)

- **What the user sees:** An Agents pill and tray list a chat's subagents with model and type (3.19). Stop on a subagent now also stops every subagent it started, including unloaded ones (3.19, 3.20). A subagent's question surfaces in the parent chat under 'Question from <name>', and Answer on its row jumps there (3.20). /multitask runs async subagents instead of queuing requests; /in-cloud sends the next task to a cloud subagent with its own VM and branch; /babysit has a cloud subagent shepherd a PR. Drag a subagent into a split pane to watch it (3.23).
- **How it works:** First-party task tree. The `subagentStop` hook now reports `child_conversation_id` to tie audit scripts to a subagent's own conversation (3.22).
- **Reception:** The cascading-stop fix exists because stopping a parent used to leave nested children running; that is a verified-stop bug class Loom also cares about.
- **Evidence:** https://cursor.com/docs/release-notes (3.19, 3.20, 3.22, 3.23); https://www.digitalapplied.com/blog/cursor-3-agents-window-complete-guide; https://www.gradually.ai/en/changelogs/cursor/ (Cloud subagents, June 17 2026)

### Transcript search (Cmd+K) and in-chat find (context-knowledge, confidence medium)

- **What the user sees:** Cmd+K in the Agents Window searches the content of agent conversations, with transcript hits ranked above name or PR-link matches (3.21, 3.22), and finds side chats and PR numbers. Cmd+F searches inside the open chat and matches only visible text; the fullscreen tray has its own find bar. Past chats are @-mentionable.
- **How it works:** A local search index over transcripts that 'scales to thousands of conversations' (3.11 notes via creatorstoolbox.com and digitalapplied.com). Index internals are not public; the bug-report author found a native code chunker for semantic search that can fail to load and disable only semantic search (3.23).
- **Reception:** Quietly useful and widely paired with side chats as 'fleet ergonomics'. No complaints found.
- **Evidence:** https://creatorstoolbox.com/blog/cursor-side-chats-and-conversation-search; https://cursor.com/docs/release-notes (3.21, 3.22, 3.23)

### Integrated browser, Design Mode and canvases (browser-preview, confidence high)

- **What the user sees:** A browser pane the agent drives (screenshots, console, network); browser tabs you open persist per workspace with their own cookies and logins (3.21); agent-opened browsers stay tied to that agent. Design Mode (Cmd+Shift+D) lets you annotate or pick elements on the page and send them to the agent, with keyboard element-tree navigation. An 'Open Browser' pill appears when a local dev server is detected (3.24). Canvases are agent-built interactive reports (/canvas, /visualize charts inline).
- **How it works:** A secure web view controlled by an MCP server running as an extension. Browser logs are written to files that the agent greps rather than summarizing each step, to save tokens; screenshots go through the file-read tool as images; the agent is prompted to detect running dev servers instead of starting duplicates. Tools need approval by default. Hidden tabs stopped rendering in 3.22 after CPU complaints, and web pages can no longer fake element picks.
- **Reception:** Design Mode is the most praised new interaction (precise 'this element' feedback). Security and stability needed repeated fixes (prompt-injection hardening, CPU while hidden).
- **Evidence:** https://cursor.com/docs/agent/browser; https://cursor.com/changelog/3-0; https://cursor.com/docs/release-notes (3.21, 3.22, 3.24)

### Local/cloud handoff, Remote Control and Projects (remote-mobile, confidence medium)

- **What the user sees:** Move to Cloud / Continue on Cloud keeps the conversation and offloads a long run; pull it back to local to iterate. Remote Control (Oct 6 2026, on by default except Enterprise) lets the iOS app list local agents and send them messages; the desktop must stay on, awake and online, and the workspace must be Git-backed. The iOS app gives push notifications, lock-screen Live Activities and merge controls. Projects (beta, Sep 10 2026) add a cloud coordinator agent that delegates to implementer agents and keeps shared context files; local agents can be dragged in as workers over Remote Control. Self-hosted workers (Sep 2026) run tool calls on your own machines.
- **How it works:** One backend, three surfaces (desktop, web, iOS). Remote Control relays through Cursor's cloud; execution stays on the user's computer. The 'Keep this computer awake' toggle exists for this.
- **Reception:** Cloud users say they get no local worktree pain and review PRs in the IDE. Complaint: side chats and some features lagged behind cloud and Remote Control (staff confirmed July 2026 that side chats were not available in cloud or remote-controlled chats; cloud support came in 3.23). Heavy cost: a separate pricing and usage system with credits and weekly allowances.
- **Evidence:** https://cursor.com/changelog (Oct 2026 entries: Remote Control, Projects, Rollouts); https://www.learncursor.dev/guides/cursor-remote-control; https://cursor.com/docs/cloud-agent; https://cursor.com/blog/cursor-3

### Auto-review run mode (automation, confidence medium)

- **What the user sees:** Approvals per run mode: 'Auto-review' (May 29 2026) lets allowlisted shell, MCP and fetch calls run immediately, sandboxes what can be sandboxed, and sends everything else to a classifier subagent that allows, redirects or asks you. You can give the classifier custom block instructions. Approval cards say why they appear ('This edits a file outside your workspace', 3.23) and cannot be dismissed by accident with Escape (3.24). MCP tools that require confirmation always ask (3.23); recursive or ambiguous deletes always ask (3.24).
- **How it works:** A classifier subagent in the agent harness; first-party. It is a model-based decision, so it has had failure modes already (it once approved confirm-required MCP calls such as merges, fixed in 3.23).
- **Reception:** Fewer approval interruptions is the goal; the fixes show the safety edge cases are still being found.
- **Evidence:** https://www.gradually.ai/en/changelogs/cursor/ (Auto-review Run Mode, May 29 2026); https://cursor.com/docs/release-notes (3.22, 3.23, 3.24, Cursor CLI v2026.09.22)

## UX patterns worth borrowing

- Sidebar as the single source of truth, grouped by repo with a Pinned section on top. Status is a filter (Show > Status) and errors are a first-class group, not a decoration.
- Pills above the prompt in a fixed order: live status first (pending input, changes, agents, terminals, canvas, queue), then quick actions. Each pill opens a tray and some trays open themselves when there is something new. Information lives next to the input without moving the transcript.
- Subagents and side chats open as tabs on the parent agent, so the parent stays in view. Back returns to where you were, not to the parent. The same hover card (title, state, branch) appears on the sidebar row, the tab and the tile header.
- Questions from subagents are answered in the parent chat's question tray, which can collapse to a numbered pill. The blocked work is unblocked without leaving the screen you are in.
- Unread inside the chat: a 'New Messages' divider plus a jump pill. Unread outside the app: Dock-menu list and menu-bar list with 'N more unread'; the badge counts only what the menu shows.
- Cmd+K palette with filter pills (All, Agents, Files, Actions) switchable with arrow keys; Cmd+W returns to the previous tab; Cmd+Shift+T reopens what you closed.
- Review scope as a one-click choice: Last Agent Turn versus all uncommitted changes versus branch; Review in the end-of-turn summary opens it pre-scoped.
- Density control for tool calls (Compact, Balanced, Detailed) and an adjustable chat width, instead of one fixed transcript style.
- Approval cards that state their reason in a sentence, and refuse accidental dismissal.
- Edit-and-resubmit asks one explicit question ('Revert files to this message?'), and a failed edit leaves the transcript intact.

## Anti-patterns

- Making the new window the default and hiding the way back. Users filed 'I hate the Agents Window' threads and wrote 'please stop forcing agents mode'; the escape hatches were `cursor --classic` and a Window Restoration setting. Loom should add new surfaces as opt-in.
- Teardown that destroys work without an outcome check. Archive with Cmd+Shift+E removed a dirty worktree with about 60 modified files, with no confirmation and no snapshot (forum 167129). Verified outcomes and a snapshot-before-teardown rule are exactly what Loom's principles demand. The shortcut also collided with another app's meaning for the same keys and could not be remapped.
- Eager restore and polling in a long-lived UI. Reporter-measured (forum 168692, unconfirmed by Cursor): all persisted inline diffs restored at start, a 5-second store-sync round per chat, and a 250 ms timer spawning a process. Multi-day uptime degraded the whole machine. Loom's no-polling and bounded-read rules are the direct opposite.
- Moving the user's mental model of worktrees into chat. In 3.0 worktrees were driven by slash commands inside the transcript, which polluted chat history, hid which agent is in a worktree, and made the agent forget which checkout to edit in. A worktree should be an attribute of the session (a label on the card), not a conversation topic.
- Dropping per-change review in the new surface. The simplified diff view lacked accept/reject and IntelliSense and sent power users back to the IDE for months. Do not ship a thin review view as if it were the review.
- Status that flickers or goes stale: cloud agents stuck on old status, flipping back to running or unread, false 'Done' notifications, badge counts that disagreed with the sidebar. Needs one reducer and one source.
- Features that arrive local-only or cloud-only (side chats, /best-of-n in the new window), then fixed over later releases. Parity gaps between surfaces confuse users.
- Keyboard shortcuts that cannot be configured. Several threads ask for shortcut configuration in the Agents Window because IDE muscle memory triggers destructive actions.
- A classifier-based approval layer that is itself a surface for mistakes (it once auto-approved confirm-required MCP merges). Treat model-based approval as advisory, not as the safety boundary.

## Ideas for Loom

### Side session ('side chat') for a Claude session: a child card under the parent that is a fork seeded from the parent's conversation, read-only by default, never written into the parent. Entry points: a shortcut, a context-menu item, or text selected in the terminal. 'Bring back' is an explicit user action that pastes a summary (or the side chat's last answer) into the parent as a normal message. Closing archives it as an ended screen. (cost M)

- **Inspired by:** Cursor 3.11 /side (help page cursor.com/help/ai-features/side-chats) and the user's own long-standing wish. Claude Code also has /btw (single turn, adds nothing to the conversation; code.claude.com/docs/en/commands) and a documented `claude --resume <id> --fork-session` (code.claude.com/docs/en/cli-reference).
- **Gain:** Asks a question without derailing a 40-minute run and without losing the answer. Removes the context tax of interrupting the main thread, and the retrieval tax of a throwaway chat.
- **Fit:** Fits: it uses a documented CLI flag and a real PTY, so there is no new protocol. It reuses the existing subagent-tree row, the ended screen and the open-session approval path. Idle cost is zero because a closed side session is a snapshot, not a process. Conflicts and lighter variant: the forked session re-reads the whole parent context, so it costs tokens and only partly hits the prompt cache; show that cost on the row. The CLI cannot hide the parent history from the model (Cursor hides it only in the UI), so a read-only mode needs `--permission-mode plan` or a restricted tool list (verify the exact flags against the CLI drift check). Lightest first step: a 'side question' button that sends /btw into the parent's own PTY when the session is at an idle prompt, with no new session at all. Do the fork version second.
- **Risks:** Fork semantics vary with CLI versions (drift check must cover --fork-session). Two sessions sharing one working tree can still edit the same files if the side session is not truly read-only. 'Bring back' must be user-authorized, per the cross-session-actions principle. Cursor itself found side-chat nesting and cloud parity hard.

### Deepen the 'needs you' surface with Cursor's cheap, high-value pieces: (a) a Dock-icon menu that lists unread and needs-approval sessions and opens one on click; (b) the menu-bar list showing blocked sessions first, 'N more' when long, with a badge that counts only what the list shows; (c) a quit dialog that lists Working sessions and lets you jump to one instead of quitting (Loom's Quit stops all sessions, so this protects against a costly mistake); (d) a one-sentence reason on each approval box ('edits a file outside the project'); (e) a blocked-subagent dot on the parent's subagent row. (cost S)

- **Inspired by:** Cursor 3.19 (Dock Unread section, quit dialog that lists running agents), 3.21 (yellow dot for a waiting subagent), 3.22 (Error status group), 3.24 (menu-bar unread ordering and 'N more'), 3.23 (approval cards that state why).
- **Gain:** Time to notice a blocked session drops without opening Loom, and an accidental Quit no longer silently kills several long runs. Small effort for a daily-use gain.
- **Fit:** Strong fit: all of it derives from state Loom already holds (hooks plus registry), is event-driven (no polling), and draws nothing when hidden. The Dock menu is a plain NSApplication dock menu built on demand. It also exercises 'accurate status': badge, Dock list and sidebar must come from one reducer, which is exactly where Cursor's badge-count bugs came from (3.22, 3.23 notes). Skip: a cloud-style 'Listening' pill and Live Activities.
- **Risks:** Need to confirm what a hook or registry tells you about the reason for an approval (tool name and path is probably enough). Quit-time listing must not delay Quit when nothing is running.

### 'Last turn changes' pane per session: a read-only list of files changed in the latest agent turn (path, +/- counts), plus 'open in my diff tool/editor' and 'copy as patch'. Deliberately no accept/reject and no in-app editing. Optional step two: a full uncommitted-changes list per session with a branch/worktree label. (cost M)

- **Inspired by:** Cursor 3.22 Changes tab 'Last Agent Turn' scope and the end-of-turn summary that opens Review pre-scoped; the forum complaint that review of agent output is the bottleneck (forum 157588, 157226).
- **Gain:** Review is where the day goes. Knowing what changed in just this turn, from the sidebar, answers 'is it safe to approve and move on?' without opening an editor or running git by hand.
- **Fit:** Fits if built on turn boundaries Loom already sees: at the Stop hook run one bounded git command in the session's cwd (diff against a tree recorded at turn start, taken with `git stash create` or a temp index so the user's index and working tree are untouched). That makes it event-driven and costs nothing while idle. Keep it deliberately thin: Loom has no editor, and building accept/reject duplicates the user's IDE and Cursor's hardest problem. Open question: untracked and ignored files, binary files, huge diffs (cap output, show stats first), and sessions with several repos.
- **Risks:** Recorded 'tree at turn start' needs a snapshot at UserPromptSubmit; if the hook is missing (drift), fall back to 'since session start' and say so rather than reporting false success. Snapshots add git objects; prune with gc settings or use a ref namespace Loom owns.

### Worktree as a session attribute, with safe lifecycle: create a worktree when starting a session (optionally from a `.loom/worktree.json` with setup commands and a list of files to copy, like `.cursor/worktrees.json`), show a worktree icon and name on the card, and make delete/archive refuse or snapshot when the worktree is dirty or has unpushed commits. Optional machine-wide cap with a cleanup review (never automatic deletion). (cost L)

- **Inspired by:** Cursor worktrees docs (setup file, cap of 25, rediscovery by mtime) and the forum data-loss report (167129) and the 3.0 UX complaints (156507). Claude's own CLI refuses to remove a background session's worktree that has unpushed commits (`claude rm` text in the CLI reference, so a precedent exists).
- **Gain:** Parallel sessions on one repo without file collisions, and no re-explaining setup (npm ci, copy .env) each time. Removes the single most-reported fear with worktrees: losing work.
- **Fit:** Fits 'process ownership' and 'verified outcomes' well: Loom already owns run scopes, so creating a worktree, starting the CLI in it, and stopping both can be one verified action, and 'deleted' can be a checked result (dirty tree = refuse, with a one-click snapshot to a branch or patch). Conflicts: setup scripts execute arbitrary commands, so require explicit per-project approval and show the command; automatic cleanup that deletes work violates 'never report false success', so the lighter variant is a review list only. Skip /best-of-n: it multiplies token cost for a user on a plan limit; if wanted later, it is just N worktree sessions with the same first message.
- **Risks:** Dev-server ports collide across worktrees (a Reddit commenter hit this). Dependency installs per worktree cost disk and time. Interaction with Claude's own worktree features needs checking against the CLI version at run time (documented flags only, with drift detection).

### Cross-session transcript search in the existing search box: match message content (not only titles), rank content hits above loose title matches, show the matching line, and open the session at the right place. Also Cmd+F inside a session's read-only transcript panel. (cost M)

- **Inspired by:** Cursor 3.11 transcript search backed by a local index; 3.21 and 3.22 ranking of transcript matches above name matches; Cmd+F rework in 3.23.
- **Gain:** With many sessions, the question is usually 'where did the agent decide X' or 'which session had that ticket'. This turns hundreds of old sessions into retrievable memory and reduces re-asking.
- **Fit:** Loom already reads Claude's transcripts incrementally via FSEvents for usage, so one pass can also feed an index. The risk is resource use: a persistent index grows and needs updating. Lightest variant, in keeping with 'bounded reads': no index at all. Search the most recent N sessions' JSONL files on demand with a time and byte budget and a streaming matcher, cancel on typing, and add an FTS5 SQLite index only if that proves too slow. If an index is built, store it under Loom's own support directory, cap its size, and rebuild instead of migrating. Deleting a session must delete its index rows (links to the existing deletion dry run).
- **Risks:** Transcripts can hold secrets; an index duplicates them, so deletion and retention must cover it. Claude's transcript format is an internal, unversioned detail, so a parser change should degrade to 'search unavailable' not to wrong results.

### A fast 'New session' sheet (palette-style) instead of only the open-session socket: choose project, branch (or worktree), launch mode (normal, plan mode, with effort), and a first message. It starts the CLI with documented flags and shows the permission mode on the card afterwards. Add an 'empty state' that lists the user's two work projects and recent ticket keys. (cost S)

- **Inspired by:** Cursor's New Agent empty state with branch search and Local/Worktree/Cloud cycling (3.1 Branch selection in empty state), Shift+Tab plan mode (docs agent/planning), and the 'Run on' menu.
- **Gain:** Starting the third parallel task takes seconds and starts in the right branch, so less time is spent cd-ing, remembering flags and typing the same plan-mode preamble. Pairs with 'A session opens a session', which already creates sessions programmatically.
- **Fit:** Fits: it is launch-time only, adds no live process and no chat UI, and it keeps the CLI as the interface. Plan mode and effort must come from documented CLI options with drift detection (the existing missing-option check). Skip the plan tab and Build in Parallel: they are Cursor's own plan objects; Claude Code's plan lives in its terminal, and mirroring it would break 'never replace the CLI interface'.
- **Risks:** Branch/worktree choice must not silently switch the user's working tree. Plan-mode flag availability varies by CLI version, so show it only when detected.

### Dev-server pill: when a session's own process tree is listening on a TCP port, show an 'Open localhost:PORT' pill on its card (opens the default browser; an optional embedded WKWebView only when the user asks). Detect on demand (when the card is visible, on the Stop hook and on click), not by polling. (cost M)

- **Inspired by:** Cursor 3.24 'Open Browser' pill and the browser docs ('Development server awareness'). Idea sparked by a Reddit comment about per-worktree dev-server port collisions.
- **Gain:** Check the thing the agent just built in one click, from the sidebar, in the right worktree and port, with no hunting through terminal output.
- **Fit:** Loom owns the process tree through its run scope, so enumerating the scope's listening sockets is a precise, bounded query and is a better answer than Cursor's heuristic. Nothing is drawn when the card is hidden. Skip a built-in agent-driven browser and Design Mode: Claude Code has its own browser tooling, and a WKWebView with logins is a large state and security surface for a 40%-of-a-core budget. If Design Mode is wanted later, treat it as a separate, explicit project.
- **Risks:** Detecting listening sockets by pid needs libproc or lsof, with some cost per call; do it only on the events above. Sandboxing and entitlements for any embedded web view.

### Optional forward of 'needs you' events to the user's phone through a user-configured webhook or ntfy-style URL, off by default, sending only state and session title. There is no approve-from-phone and no relay. (cost S)

- **Inspired by:** Cursor Remote Control (Oct 6 2026), iOS push and Live Activities. Many Cursor users want completion and permission notifications on a phone (forum 148230 and others).
- **Gain:** Walk away from a long run and still know when a session is blocked or finished. macOS notification mirroring to iPhone already covers part of this for free.
- **Fit:** Full Remote Control conflicts with Loom: Quit stops all sessions and there is no daemon, no relay, and sleep prevention costs battery and violates predictable behavior; Cursor itself requires the computer to stay awake, plugged in with the lid open. A one-way webhook is event-driven and cheap and does not change the process model. If the user wants to answer from the phone, that is a separate decision about authority and a network surface; recommend deferring it.
- **Risks:** Leaking prompts or titles to a third-party service; keep payload minimal and let the user choose the endpoint. Duplicate alerts with macOS notification mirroring.

### Corrections

- Remote Control: do not say execution stays on the user's computer without qualification. Official docs (cursor.com/docs/cloud-agent/mobile) say the agent loop moves to the cloud while tools (terminal, file edits, tests) run on the user's machine. Also Remote Control has been documented since desktop 3.9.8 (July); Oct 6 is the default-on and iOS launch changelog entry.
- The 22 GB RAM thread (forum 158844, Apr 23 2026) is about the classic IDE (3.1.17, 4 workspaces) on macOS, not the Agents Window; do not use it as Agents Window resource evidence.
- The whoami-spawn finding (about 4 per second per chat, 8.8 s median tool call) is Windows-specific (execFileSync whoami /user /fo csv /nh); the reporter is on Windows 11 with 64 cores. Do not generalize to macOS. The eager inline-diff restore and listener leak are renderer-side and platform-neutral but still the reporter's measurement, not Cursor-confirmed.
- /best-of-n and /worktree slash commands are IDE (classic editor) features per docs and staff (forum 156550); they were not in the Glass/Agents Window interface at 3.0.4. The Agents Window has UI-native worktrees. Do not list them as Agents Window features without that caveat.
- The Dock and menu-bar lists show UNREAD (finished) agents only; running agents are excluded. They do not surface needs-approval agents. The yellow dot (3.21) is for CLOUD subagents waiting on a question or MCP sign-in. The report's core loop overstates what flags a blocked local agent.
- Forum 160057 is dated May 8 2026, not August; only the Reddit thread is Aug 22 (and its post is deleted by the author, so the 'I hate the Agents Window' title survives but its text does not). The quote 'I'll rarely run more than two at a time' was not found.
- Staff on forum 171672 say local agents already play the Completion Sound / system notification when an approval needs attention; only a separate toggle is missing. The report's 'coarse' framing should say it is shared with the completion chime.
- Side-chats help page still says local-only, but 3.23 added cloud side chats (not inside Projects); remote-controlled chats were excluded at launch per staff. Cursor's side chats are also called /btw, an alias of Claude Code's /btw name but a different behavior (durable child conversation vs Claude's single-turn no-history /btw).
- 'Git-based diffs (Changes tab compares to HEAD)' and 'status is first-party events, no inference' are inferences, not sourced; mark them as such.
- Cursor already says 'it is only practical to work with a few [synchronous local agents] at a time' (third-era blog); the report's 'no official figure' should note this qualitative statement.

### Missed by the report

- Forum 173963 (Oct 7 2026, 'With six agents running, the slow part was me noticing which one had stopped'): a Cursor user runs 5-6 Claude Code and Codex sessions across 4 Cursor windows, built SessionDeck, a sidebar for Claude Code/Codex/Cursor sessions with a bell for permission prompts, reading transcript tails + process table every 3 s and installing 3 hooks into Claude settings. - Release notes 3.19-3.24: 'Worktree setup respects workspace trust' (setup commands from .cursor/worktrees.json only run after the workspace is trusted; untrusted workspaces skip with a visible notice). Precedent for Loom's approval-before-running-setup idea.
- 3.0 changelog (Apr 2): Agent Tabs in the editor (side-by-side or grid), new /worktree and /best-of-n commands, 'removed cloud agents from the Editor', Await tool for background shells/subagents. Docs agents-window page: Remote Control and cloud/Remote features are 'only available in the Agents Window'.
- Release notes 3.23 (Oct 1): 'Unread badge matches the sidebar' (Dock badge and menu-bar count no longer count cloud agents that are not in the sidebar); 3.24 notes: queued messages, steering falls back to the queue as editable follow-ups when a cloud agent cannot take a steer; 'Steer New Messages?' banner opens Settings instead of flipping the setting (3.21).
- Cursor Origin (git host with its own CLI, stacked PRs, app marketplace, PR tab support) is a large 2026 direction appearing in 160+ places in the release notes, not a passing mention; also Cursor SDK (@cursor/sdk, Agent.create(), run.steer) and self-hosted workers, which make the agent loop programmable outside the desktop app.
- Anthropic-side note for the Claude Code comparisons: code.claude.com/docs/en/cli-reference documents `claude agents`, `claude attach`, background sessions (`/background`), `claude rm` worktree refusal with --discard-unpushed, and `--fork-session` (new session ID when resuming). /btw 'without adding to the conversation' and `--fork-session` are confirmed, but Claude Code now ships its own agent view, which overlaps Loom's sidebar and was not discussed.
