# Supacode (supabitapp/supacode)

Research note for the Loom v2 brainstorm ([index](../V2-BRAINSTORM.md)). Written by a research subagent on 2026-10-17 and fact-checked by a second one; the fact-check is at the end and wins over the report where they differ. Raw JSON: `../evidence/deep-dive-20261017.json`.

**In one line:** A native Swift/TCA macOS "command center" that wraps a patched libghostty terminal around one git worktree per task, hoists agents that need you to the top of the sidebar, and keeps sessions alive across app quit through a bundled per-session daemon (zmx).

**Category:** terminal-first (native terminal app with agent-presence layer, worktree-centred)

## Architecture

STACK. Native macOS 26+, Swift 6, SwiftUI plus AppKit, The Composable Architecture (TCA) for all state/effects, Tuist project generation, Sparkle updates, PostHog and Sentry (AGENTS.md; Project.swift; 242 Swift files under /supacode). Terminal = libghostty (GhosttyKit built from a pinned Ghostty submodule with Zig 0.15.2) with four local patches (patches/ghostty: command-wrapper, osc3008-context-signal, surface-font-size-getter, fractional scroll). This forces a Zig toolchain and an Xcode 26.3 pin on macOS 26.4+ (README; issue #902). It is a real terminal, not a chat UI: tabs, splits, per-pane tabs, Ghostty config reuse.

HOW IT DRIVES THE AGENT. Not stream-json, not SDK, not ACP: it runs the real CLI in a PTY and learns state from hooks it installs into the user's global agent config (for Claude, ~/.claude/settings.json via SupacodeSettingsShared/BusinessLogic/ClaudeSettingsInstaller.swift and ClaudeHookSettings.swift). Each hook is a shell one-liner, guarded by the env var SUPACODE_SURFACE_ID (so it is inert outside Supacode) and tagged with a "# supacode-managed-hook" ownership marker used to prune/replace only its own entries (AgentHookSettingsCommand.swift; AgentHookCommandOwnership.swift). The hook resolves the tty and writes an OSC 3008 escape sequence into the terminal byte stream (SupacodeSettingsShared/BusinessLogic/AgentPresenceOSC.swift: "OSC 3008 ; <action>=<agent> ; event=<event>[ ; pid=<pid>]"). The patched libghostty surfaces it to the app, so attribution is by receiving surface and it works over SSH and through zmx. A second leg, kind=notify, carries base64 title/body (the agent's message/last_assistant_message) for notifications. Signals are explicitly unauthenticated (worst case a spurious badge). A local Unix socket (Infrastructure/AgentHookSocketServer.swift, dir 0700) still exists for CLI and deeplink commands.

STATE DETECTION. Claude hook mapping (ClaudeHookSettings.swift): UserPromptSubmit and PreToolUse -> busy; PostToolUse -> idle (so the shimmer tracks tool execution; a socket-side debounce bridges gaps between tools); Notification, and PreToolUse for AskUserQuestion|ExitPlanMode -> awaitingInput; PreCompact -> compacting; Stop -> error if a shell probe of the transcript finds a current-turn API error, else idle; SessionStart/SessionEnd manage presence. Reducer: Features/AgentPresence/Reducer/AgentPresenceFeature.swift. Activity = awaitingInput|busy|idle|error|compacting. error and awaitingInput are "attention" states: error is sticky (Claude's 60s idle Notification must not downgrade it) and only a new busy, a sessionStart or clearAttention (focusing that surface, AppFeature.swift around line 2119) clears it. Records are keyed (agent, surfaceID) with local pids; a 2-second liveness sweep (livenessSweepInterval, kill(2) off the main actor, only for tracked pids) reaps crashed agents; records are restored after relaunch with a pid liveness check.

SIDEBAR / HOISTING. Per-row state lives in RepositoriesFeature.State.sidebarItems; the reducer's post-reduce hook computes a cached SidebarStructure (Features/Repositories/BusinessLogic/SidebarStructure.swift, 1301 lines) so a per-leaf tick (notification, agent activity) invalidates one row, never siblings (AGENTS.md "Sidebar performance" rule). SidebarActiveClassification (errored first, then unread+awaiting+running ... down to running) decides membership of the global Active section. Rows are hoisted out of their repo section, and a muted "+N active / +N pinned" SidebarHoistSummary stays in the origin repo so the row is still discoverable. Order inside Active is alphabetical by branch (SidebarHighlightOrdering), with unread floated first only if the "prioritize notified" setting is on, so classification gates membership, not recency.

PERSISTENCE. Every terminal surface is launched as "zmx attach supa-<surface-uuid>" via a Ghostty command-wrapper (Clients/Zmx/ZmxClient.swift: ZmxAttach, ZmxSessionID). zmx is a small Zig tool by neurosnap (MIT, 2.2k stars; one session process + unix socket per session, multi-client attach, uses libghostty-vt to restore screen state; no windows/tabs). Supacode vendors a fork (ThirdParty/zmx, one patch). Layout/tab topology is persisted separately (layouts.json v2 with an incremental writer, Features/Terminal/BusinessLogic/Layouts*.swift). On relaunch each surface UUID reattaches to the live session. A launch-time orphan reaper kills supa-* sessions that no persisted layout claims, is attach-aware, and never reaps when the zmx probe result is unknown (WorktreeTerminalManager.reapOrphanSessions). "Quit and terminate" is an explicit option (terminateSessionsOnQuit). A socket-path budget probe silently bypasses zmx if ZMX_DIR makes the path exceed sun_path (issue #554: persistence silently disabled on long-UID corporate Macs).

RESOURCE MODEL. Terminal hibernation (beta flag): a hidden tab's renderer is torn down after a 5-minute grace window, the 3 most recently selected worktrees are exempt, and a DispatchSource memory-pressure event hibernates all hidden tabs immediately (Features/Terminal/Reducer/TerminalsFeature.swift: hibernationGraceWindow, liveWorktreeLimit, reduceMemoryPressureWarning; Clients/AppLifecycle/MemoryPressureClient.swift). Only the renderer goes away; the agent process keeps running inside zmx. Dormant zmx sessions get a passive socket reader thread each, to keep catching OSC signals (Clients/Zmx/ZmxSessionWatcher.swift, poll timeout 200 ms, reconnect backoff 200 ms to 5 s, give up after 6 failed cycles). By my reading that is one thread waking about 5 times per second per dormant session; I did not measure it. Git/PR state: FSEvents per worktree plus .git HEAD file sources, plus timers: 30 s focused / 60 s unfocused refresh, 5 s file-change debounce, 300 s full reconcile (WorktreeInfoWatcherManager.swift init defaults), and gh/GraphQL calls per branch.

AUTOMATION SURFACE. A bundled "supacode" CLI (swift-argument-parser; supacode-cli/) talks to the app over a Unix socket in /tmp/supacode-<uid>/ (named by app pid); inside a session $SUPACODE_SOCKET_PATH plus WORKTREE_ID/TAB_ID/SURFACE_ID env vars make commands default to the caller's own session. Deeplinks (supacode://worktree/<id>/run|stop|archive|pin|tab/new?input=...) mirror it (Clients/Deeplink/DeeplinkClient.swift). Two bundled skills (Resources/Skills/supacode-cli.md, supacode-deeplinks.md) are installed into the agent so it can drive Supacode itself.

## Core loop

Add a repo (or plain folder) once. For each task: create a worktree from the sidebar, a hotkey, the command palette, the CLI or a deeplink (branch and worktree are created together under ~/.supacode/repos/<repo>/, per-repo setup script can start the agent, optionally copy ignored/untracked files into the new tree). Type the prompt in the real agent TUI in that worktree's terminal tab. Switch away; the sidebar row shows an agent badge and a shimmer while busy. When an agent needs you (permission question, plan, API error, finished) the row floats into the global Active section, the menu-bar item shows an unread count, and a system notification carries the agent's last message. Jump with Cmd+P (VS Code-style worktree switcher with MRU), Ctrl+1..9, or by clicking the row; focusing the surface acknowledges the attention state. Inspect the worktree in the right inspector (PR state, CI checks, merge readiness, notifications, file explorer). Run scripts (test, lint, run) in their own tabs, open the PR, merge from the command palette; a "merged worktree" action can archive it automatically. Archive/delete the worktree. Quit freely: sessions keep running in zmx and reattach next launch. There is no built-in diff/review view (only +N/-N line stats; Open-in-editor buttons hand off to Xcode/VS Code etc.), no usage or cost display, and no chat-style UI.

## Features

### Agent presence by hook-to-OSC-3008, installed into the user's global agent config (attention-status, confidence high)

- **What the user sees:** A small avatar badge per agent on each sidebar row and tab; a shimmer on the title while busy, a contrast flip when awaiting input, an error/compaction state, all without any extra windows.
- **How it works:** Shell hooks written to ~/.claude/settings.json (also Codex, Copilot, Kiro, Grok, Pi, OpenCode, etc.) emit 'OSC 3008;...;event=<busy|idle|awaiting_input|error|compacting|session_start|session_end>[;pid=N]' into the tty. A patched Ghostty parses it and the app attributes by receiving surface. Wire format and parser: SupacodeSettingsShared/BusinessLogic/AgentPresenceOSC.swift; per-agent payloads: ClaudeHookSettings.swift (PreToolUse/PostToolUse give tool-level granularity for Claude); reducer: Features/AgentPresence/Reducer/AgentPresenceFeature.swift. Ownership marker '# supacode-managed-hook' lets the installer prune and rewrite only its own hook entries; release notes also mention 'surface unreadable agent integration files instead of reporting them absent', i.e. drift is shown, not hidden.
- **Reception:** Core reason people adopt it (Verdent guide calls the badge 'small feature with outsized value'). Complaints in issues: Codex sessions not appearing in Active (#876, #862 remote), Pi notifications repeating earlier answers (#875), many requests for first-class support of more harnesses (#852 Droid, #815, #871, #602) because each agent needs a bespoke hook installer. Hooks run a process per tool call (PreToolUse and PostToolUse), which is my inference of a cost; the 2 s hook timeout in AgentHookSettingsCommand.timeoutSeconds is there so a wedged PTY cannot stall the agent.
- **Evidence:** supacode/SupacodeSettingsShared/BusinessLogic/AgentPresenceOSC.swift; supacode/SupacodeSettingsShared/BusinessLogic/ClaudeHookSettings.swift; supacode/SupacodeSettingsShared/BusinessLogic/AgentHookSettingsCommand.swift; supacode/supacode/Features/AgentPresence/Reducer/AgentPresenceFeature.swift; https://github.com/supabitapp/supacode/issues/876; https://github.com/supabitapp/supacode/issues/875

### Needs-you hoisting: global Active section with severity classification (attention-status, confidence high)

- **What the user sees:** At the top of the sidebar, an Active (blue dot) section lists every worktree with an agent, unread notification, awaiting input or running script, regardless of repo; an orange Pinned section sits above it. In the origin repo a muted '+2 active' line points back to the hoisted rows (click scrolls to them). Menu-bar dropdown mirrors the same lists.
- **How it works:** SidebarActiveClassification.classify(...) in Features/Repositories/BusinessLogic/SidebarStructure.swift turns four leaf-local flags (unread, awaiting, agent present, script running) into an 11-case severity enum (errored, then unread+awaiting+running, ... running). A non-nil classification means membership. SidebarHighlightOrdering sorts alphabetically by branch (case-insensitive, id tie-break), floating unread rows first only if the prioritizeNotified setting is on. The structure is computed once in the reducer post-reduce hook and cached (SidebarStructure, computeHighlightHoists, SidebarHoistSummary), and the view just lays out ID lists (Views/SidebarHighlightSectionsView.swift). Note: membership includes any row with an agent badge even if idle ('hasAgent keyed off badge presence'), so Active can be broad. Open issues ask for folder grouping inside Pinned/Active (#905) and repo-name search (#903).
- **Reception:** Praised as the thing that makes 5+ parallel agents manageable. Design weakness visible in code: alphabetical order inside Active, not 'most recently needs you' or longest-waiting, so attention order is only partly encoded in position.
- **Evidence:** supacode/supacode/Features/Repositories/BusinessLogic/SidebarStructure.swift (SidebarActiveClassification, SidebarHighlightOrdering, SidebarHoistSummary); supacode/supacode/Features/Repositories/Views/SidebarHighlightSectionsView.swift; https://github.com/supabitapp/supacode (README: 'hoists the worktrees that need you'); https://github.com/supabitapp/supacode/issues/905

### Attention state machine with sticky error and acknowledge-on-focus (attention-status, confidence high)

- **What the user sees:** An errored turn (API error) or a pending question stays visibly flagged until you actually look at that terminal surface or the agent starts again; compaction shows as work, not as a stall.
- **How it works:** AgentPresenceFeature.Activity.isAttention = error or awaitingInput. 'error' is sticky: only busy, sessionStart or clearAttention may leave it; any other event (e.g. Claude's 60 s idle Notification) is dropped so it cannot downgrade the failure. clearAttention is sent when focus moves to that exact surface (AppFeature.swift, .terminalEvent(.focusChanged)), so a broken session in another split keeps its warning. Claude's Stop hook probes the transcript for a current-turn API error because Claude reports API errors through a plain Stop (AgentHookSettingsCommand.claudeStopCommand, AgentPresenceOSC.stopApiErrorProbeShell). Compacting is a transient state cleared by the next event or by the SessionStart(source=compact) Claude fires afterwards; PostCompact is deliberately not mapped.
- **Reception:** No complaints found about this part; the code comments document real Claude behaviours the authors hit (idle Notification at 60 s, Stop-on-error). Useful as a catalogue of hook edge cases.
- **Evidence:** supacode/supacode/Features/AgentPresence/Reducer/AgentPresenceFeature.swift (Activity, clearAttention, normalizeStickyOnRestart); supacode/supacode/Features/App/Reducer/AppFeature.swift (focusChanged -> clearAttention); supacode/SupacodeSettingsShared/BusinessLogic/AgentHookSettingsCommand.swift (claudeStopCommand)

### Background persistence via zmx (per-session daemon), with orphan reaper (other, confidence high)

- **What the user sees:** Quit and relaunch (or app crash) and every terminal, including a Claude session mid-turn, is still there with scrollback; an option 'Quit and terminate' tears all down. Reportedly also survives app updates.
- **How it works:** Each surface launches through 'zmx attach supa-<surface-uuid>' (Ghostty command-wrapper patch). zmx keeps one daemon process per session with a unix socket under ZMX_DIR (default /tmp/zmx-<uid> or $TMPDIR/zmx-<uid>) and restores screen state on attach with libghostty-vt. Supacode keeps layout topology in layouts.json and treats zmx as authoritative for attach-vs-create (ZmxClient is deliberately cache-free). Kill calls have a 5 s timeout; listSessionsWithClients returns nil for 'unknown' and the reaper never reaps on unknown; at launch reapOrphanSessions kills supa-* sessions no persisted layout claims. A socket-path budget probe bypasses zmx if the path would exceed sun_path (104 bytes). Remote SSH repos get a local zmx session wrapping a reconnect loop and, when the host has zmx, host-side persistence.
- **Reception:** Bret Fisher lists ZMX session persistence among the reasons for switching. Pain points: persistence silently disabled with long ZMX_DIR/UIDs (#554), zmx 0.6.0 leaderless-switch teardown killed tabs (#865), remote SSH reconnect loses sessions after Mac sleep (#838), zshrc re-sourced periodically which exhausted a user's process table (#802), orphan host-side sessions have no reaper. It also contradicts a 'nothing survives Quit' guarantee, which is exactly why it is not a free borrow for Loom.
- **Evidence:** supacode/supacode/Clients/Zmx/ZmxClient.swift (ZmxAttach, ZmxSessionID, ZmxSocketBudget); supacode/supacode/Features/Terminal/BusinessLogic/WorktreeTerminalManager.swift (reapOrphanSessions, quit-time orphan sweep); supacode/patches/ghostty/ghostty-command-wrapper.patch; https://github.com/neurosnap/zmx; https://github.com/supabitapp/supacode/issues/554; https://github.com/supabitapp/supacode/issues/865; https://github.com/supabitapp/supacode/issues/838; https://github.com/supabitapp/supacode/issues/802

### Terminal hibernation: free the renderer, keep the process (usage-cost, confidence medium)

- **What the user sees:** (Beta setting) Tabs you have not looked at for a while go dormant; row stays in the sidebar with its last known title/state and wakes when selected. Under memory pressure everything hidden hibernates at once.
- **How it works:** TerminalsFeature arms a per-tab 5-minute grace timer for hidden tabs (hibernationGraceWindow), exempts the 3 most recently selected worktrees (liveWorktreeLimit), re-checks visibility at fire time, defers if a close confirmation is pending, and on a DispatchSource memory-pressure warning/critical sweeps every hidden tab immediately (reduceMemoryPressureWarning, MemoryPressureClient). LayoutFeature.reduceHibernateTab records the frozen grid for persistence. Dormant zmx sessions are still watched by a passive reader thread that feeds an OSC scanner so state/title changes keep arriving (ZmxSessionWatcher, ZmxOSCScanner); the hooks' OSC signal is what keeps the badge accurate while no renderer exists.
- **Reception:** No direct user feedback found. Issue #700 shows the adjacent need: laptop sleeps while agents are busy. Cost: process still alive per dormant session, plus one watcher thread each (about 5 wakeups/s by my reading of the 200 ms poll timeout; not measured), so it is a renderer-memory optimisation, not an 'idle costs nothing' guarantee.
- **Evidence:** supacode/supacode/Features/Terminal/Reducer/TerminalsFeature.swift; supacode/supacode/Clients/AppLifecycle/MemoryPressureClient.swift; supacode/supacode/Clients/Zmx/ZmxSessionWatcher.swift; supacode/supacode/Features/Terminal/Reducer/LayoutFeature.swift (reduceHibernateTab)

### CLI + deeplinks with a user-confirmation policy and completion acks (automation, confidence high)

- **What the user sees:** From any terminal or from the agent itself: supacode worktree/tab/pane/repo commands and supacode:// URLs (create/run/stop/archive/pin/rename tabs, send input into a new tab). Destructive or command-running actions pop a confirmation dialog showing the literal command, with an 'always allow' checkbox; Settings has a policy: CLI & deeplinks / CLI only / Deeplinks only / Never bypass confirmation.
- **How it works:** supacode-cli (swift-argument-parser) -> Unix socket discovered from $SUPACODE_SOCKET_PATH or /tmp/supacode-<uid>/<pid>; env vars SUPACODE_WORKTREE_ID/TAB_ID/SURFACE_ID make commands default to the caller's own session. Deeplink grammar parsed in Clients/Deeplink/DeeplinkClient.swift. SupacodeSettingsShared/Domain/AutomatedActionPolicy.swift decides bypass per ActionSource (.socket vs .urlScheme). Features/App/Reducer/DeeplinkInputConfirmationFeature.swift holds the pending action plus the CLI's response file descriptor, a timeout token and a 'background' flag so a confirmed action re-runs without stealing focus, and the CLI blocks on an ack until the action really completed (AppFeature resolveCommandAcks). Two bundled skills teach agents the CLI and deeplinks; the skill stresses 'capture the UUID printed by tab new/pane split and pass it explicitly' because focused-target defaults point at whatever the user is looking at.
- **Reception:** Positive in the Bret Fisher summary (agents can create worktrees themselves). Open issues: agents trip over CLI behaviours (#884), want 'tab list --json' with titles/surface ids/agent pid (#820). Authentication is only filesystem-level (directory 0700, same-user), no per-request token.
- **Evidence:** supacode/supacode-cli/SupacodeCLI.swift; supacode/supacode-cli/Transport/SocketDiscovery.swift; supacode/supacode/Clients/Deeplink/DeeplinkClient.swift; supacode/SupacodeSettingsShared/Domain/AutomatedActionPolicy.swift; supacode/supacode/Features/App/Reducer/DeeplinkInputConfirmationFeature.swift; supacode/Resources/Skills/supacode-cli.md; https://github.com/supabitapp/supacode/issues/884; https://github.com/supabitapp/supacode/issues/820

### Worktree lifecycle automation (create, setup script, copy ignored files, archive, auto-archive on merge) (parallel-worktrees, confidence high)

- **What the user sees:** One click/hotkey creates branch plus worktree (optionally prompted name, base-ref picker, per-repo base dir); a per-repo setup script runs in a tab and can launch the agent; .env and other ignored/untracked files can be copied into the new tree; archive hides a worktree but keeps it on disk; delete removes dir and optionally local branch; 'merged worktree' action can archive after PR merge; auto-delete after N days; lock against prune.
- **How it works:** Git operations through GitClient with the git-wt helper (patched submodule Resources/git-wt, patches/git-wt); per-repo supacode.json (RepositorySettings: setupScript, archiveScript, deleteScript, scripts[], copyIgnoredOnWorktreeCreate, copyUntrackedOnWorktreeCreate, worktreeBaseRef, pullRequestMergeStrategy, mergedWorktreeAction); WorktreeArtifactCopier copies untracked/ignored files; blocking scripts run via BlockingScriptRunner in their own tab bypassing zmx.
- **Reception:** Main selling point in every review (Verdent, daily.dev, Bret Fisher: one hard-drive location for all worktrees, no git worktree commands to remember). Complaints: failed creation with a branch-prefix name deleted an existing folder of nested worktrees (#878), settings overwrite relative paths (#550, #840), merged PR shown stale on default branch (#695). Verdent warns cleanup is still the human's job: it is easy to accumulate dozens of stale worktrees.
- **Evidence:** supacode/supacode.json; supacode/SupacodeSettingsShared/Models/RepositorySettings.swift; supacode/supacode/Clients/Git/WorktreeArtifactCopier.swift; supacode/supacode/Features/Terminal/BusinessLogic/BlockingScriptRunner.swift; https://docs.supacode.sh/reference/faq; https://github.com/supabitapp/supacode/issues/878

### Right inspector: PR/CI status, notifications pane, file explorer; no diff view (review-git, confidence high)

- **What the user sees:** A per-worktree inspector with a Git/PR pane (PR state, check rows with a progress ring, merge readiness and merge-queue position, actions: open/ready/merge/close, copy failing job URL, copy CI failure logs, re-run failed jobs), a Notifications pane (grouped, filterable, with the agent's message text) and a beta Files pane with git status per file. The sidebar row also shows +N/-N line counts. Review of the actual diff is delegated to an external editor via 'Open in ...' actions.
- **How it works:** Features/Repositories/Views/WorktreeStatusInspector.swift (WorktreeGitInspectorView, PullRequestActionsSection, CheckRow, WorktreeNotificationsInspectorView); forge abstraction in Clients/Forge (GitHub via gh, GitLab, merge queue); the same actions are exposed in the command palette (CommandPaletteItem.Kind: mergePullRequest, copyCiFailureLogs, rerunFailedJobs, openFailingCheckDetails). File explorer is Features/FileExplorer. grep found no usage or token display anywhere in the app.
- **Reception:** The CI-failure-log copy action fits agent loops well (paste into the agent). Cost side: PR/branch state refresh was reported to create gh/git process storms with load average 200+ on 17 repos/105 worktrees (#830), and to burn about 64 GraphQL points/min with 24 repos so a user hit the 5,000/h limit overnight (#844). Release v0.11.4 fixed an idle fsmonitor refresh loop; #783 moved much of it to events 'with a self-healing backstop', but the maintainer said some things stay on timers as a conscious trade-off (#802 thread).
- **Evidence:** supacode/supacode/Features/Repositories/Views/WorktreeStatusInspector.swift; supacode/supacode/Features/CommandPalette/CommandPaletteItem.swift; supacode/supacode/Features/Repositories/BusinessLogic/WorktreeInfoWatcherManager.swift; https://github.com/supabitapp/supacode/issues/830; https://github.com/supabitapp/supacode/issues/844; https://github.com/supabitapp/supacode/releases/tag/v0.11.4

### Keyboard-first navigation: command palette, Cmd+P worktree switcher with MRU, Ctrl+1..9, menu-bar fleet view (navigation-ux, confidence high)

- **What the user sees:** Fuzzy command palette for every action (including PR actions and user scripts); a VS Code-style Cmd+P worktree switcher where Enter on a fresh open lands on the previous worktree (MRU, 'direct beats fuzzy' ranking); Ctrl+1..9 jumps to the Nth row; a menu-bar item (Dock, Dock+Menu bar or Menu-bar-only) with an unread badge and a dropdown of pinned/active/unread worktrees; per-surface bell/notification muting; notified worktree can float to top.
- **How it works:** CommandPaletteItem.priorityTier and isCurrentWorktree (skipped for default selection so Cmd+P Enter is never a no-op); menu bar via Features/App/Views/MenuBarNotificationsMenu.swift and Models/MenuBarNotificationList.swift, which reuses menuBarForcedHoists() from SidebarStructure so the menu always shows the same hoists as the sidebar even when the user has grouping off. Closure-typed focused values are wrapped in FocusedAction to avoid rebuilding the AppKit menu every body run (AGENTS.md).
- **Reception:** The Cmd+P switcher and menu-bar mode were contributed by community members (PR #608 by COCPORN) and released as v0.10.7 'Agents at a glance'. Open requests: Cmd+arrow tab switching (#869), sidebar repo filter (#903).
- **Evidence:** supacode/supacode/Features/CommandPalette/CommandPaletteItem.swift; supacode/supacode/Features/App/Models/MenuBarNotificationList.swift; https://github.com/supabitapp/supacode/releases/tag/v0.10.7; https://github.com/supabitapp/supacode/issues/869

### Notifications that carry the agent's own words (attention-status, confidence medium)

- **What the user sees:** System/in-app notifications titled by worktree/agent whose body is the agent's last message or the Notification text, selectable sound, per-surface muting, and an error notification ('Agent error / Session stopped on an error') distinct from a normal finish.
- **How it works:** The same OSC 3008 channel carries 'kind=notify;title=<b64>;body=<b64>' emitted by the hook; body source keys in precedence message, last_assistant_message, assistant_response (AgentPresenceOSC.notifyBodyKeys), capped to 1000/160 bytes to fit libghostty's 2048-byte OSC buffer (over the cap the whole sequence is dropped). Agent OSC 9/777 notifications are deduped against these (WorktreeContentHost pendingAgentOSCNotifications, lastCustomNotificationAt).
- **Reception:** Bret Fisher highlights agent-aware notifications. Bug class: duplicate/stale bodies (#875).
- **Evidence:** supacode/SupacodeSettingsShared/BusinessLogic/AgentPresenceOSC.swift; supacode/supacode/Features/Terminal/BusinessLogic/WorktreeContentHost.swift; https://github.com/supabitapp/supacode/issues/875

## UX patterns worth borrowing

- Global 'Active' (blue dot) and 'Pinned' (orange dot) sections above per-repo groups, with a muted '+N active/+N pinned' summary line left in the origin repo that scrolls to the hoisted row, so hoisting never makes rows undiscoverable.
- Row identity = worktree/branch (not session title) with repo name as subtitle only inside hoisted sections (SidebarHighlightRepoTag), per-repo colour tint on text, avatar-group of agent badges (awaiting-input badge sorted first, +N overflow), PR icon with check-state badge, +N/-N diff stat, shimmer on the title while busy.
- Cmd+P worktree switcher where the current worktree is shown but skipped for the default selection, so Cmd+P then Enter flips to the previous one (MRU).
- Cmd-held hint overlay: shortcutHintByID shows Ctrl+N numbers in the row's trailing slot only while the modifier is down.
- Right inspector as a switchable pane (Git/PR, Notifications, Files) instead of more sidebar chrome.
- Confirmation dialog for external automation shows the literal command that will run, with 'always allow' and a policy switch by source (CLI vs deeplink).
- Acknowledge-by-focus: attention clears per surface when you look at it, not when the worktree is merely selected.
- Menu-bar-only mode as a true background orchestrator, using the same hoist lists as the sidebar.
- Per-repo committed supacode.json for scripts/setup/archive, with a Script menu, palette entries and deeplinks generated from the same definitions.

## Anti-patterns

- Polling that scales with repo count: PR/branch refresh via many gh/git subprocesses caused load averages of 200+ with 17 repos/105 worktrees (#830) and used about 64 GraphQL points per minute with 24 repos, exhausting the hourly limit overnight (#844). Event-based refresh (#783) helped but timers (30/60 s, 300 s) remain by design.
- Re-sourcing the user's .zshrc for background helper processes so gh/PATH resolve; one user's ssh-agent-in-zshrc exhausted process slots over a night (#802). Never run the user's shell init from background probes.
- Process fan-out per event: Claude hooks run on every PreToolUse and PostToolUse and each spawns a shell (plus tty resolve via ps); a 2 s hook timeout exists because a wedged hook would stall the agent. (The cost estimate is my inference.)
- Persistence that fails silently: zmx wrapping is bypassed without any prominent UI when ZMX_DIR/UID makes the socket path too long (#554); version bumps of the vendored zmx caused teardown bugs that killed tabs (#865). A feature users rely on for 'nothing is lost' must say loudly when it is off.
- Forked dependencies as a maintenance tax: patched Ghostty (4 patches), patched zmx, patched git-wt; Zig 0.15.2 build requires Xcode 26.3 on macOS 26.4+ (#902). Contrast with Loom's rule against pinning CLI versions.
- Hooks injected into the user's global ~/.claude/settings.json: needs ownership markers and pruning logic, and a per-agent installer for each new harness (Codex, Kiro, Grok, Pi, OpenCode...), which is why 'support harness X' requests pile up.
- Active section membership is broad (any agent badge, even idle) and ordered alphabetically by branch, so the list says 'there is activity' more than 'this one needs you first'.
- Unauthenticated in-band status channel (OSC) and filesystem-only socket auth: acceptable for badges, not for cross-session actions; Supacode compensates with a confirmation dialog.
- Maintenance and trust risk of a solo-ish project: slowdown plus a rewrite-in-TypeScript scare (#883), then a paid licence with a hard 5-worktree free limit, announced by release note; users asked for roadmap clarity.
- No built-in diff/review view and no usage/cost display, so the 'main app' still needs an editor and external dashboards.

## Ideas for Loom

### Severity-ordered 'Needs you' hoist with a per-project summary line (cost S)

- **Inspired by:** SidebarActiveClassification + SidebarHoistSummary (Features/Repositories/BusinessLogic/SidebarStructure.swift)
- **Gain:** Loom already has an Active section; two refinements remove scanning: order inside Active by severity and then by how long it has been waiting (Supacode orders alphabetically, which is its visible weakness), and leave a muted '+2 need you' line under a project's header in project view so the row stays discoverable from where the user expects it.
- **Fit:** Pure derivation from state Loom already has (Needs approval, Failed, Finished unviewed, Working); no new IO, no polling. Compute once per state change, not in view bodies (same rule as Supacode's AGENTS.md). Fits 'predictable behavior' if the ordering rule is written down: error > needs approval > finished unviewed > working, ties by waiting-since.
- **Risks:** Rows jumping position while the user is about to click; mitigate by keeping a row stable while hovered or selected and re-sorting on next state change. Over-broad membership (Supacode counts idle agent badges) would dilute the signal; keep Active strictly attention + working.

### Per-surface acknowledge semantics and sticky-failure rules, checked against Loom's status model (cost S)

- **Inspired by:** AgentPresenceFeature (sticky error, clearAttention on focus, compacting as transient work)
- **Gain:** Prevents two classic trust-killers: a Failed state silently downgraded to Idle by Claude's 60 s idle Notification, and a Needs-approval flag that clears just because the session was selected in the background. Compaction shown as Working rather than a stall.
- **Fit:** Direct fit with 'accurate status'. Loom already drives status from hooks plus the session registry; this is an audit of the transition table, not new machinery. Add tests that feed the exact hook sequences Supacode documents (Notification after Stop-on-error, SessionStart(source=compact) after PreCompact).
- **Risks:** Loom already may handle some of these; the work is verification. Over-sticky failure needs an explicit clear path (new turn, resume, focus).

### Notifications and approval cards that quote the agent's own last message (cost S)

- **Inspired by:** kind=notify OSC leg with message/last_assistant_message precedence (AgentPresenceOSC.notifyBodyKeys)
- **Gain:** Lets the user decide from the notification or sidebar tooltip whether to jump in ('Which of the two options do you want?' vs 'Done: 12 tests pass'), cutting context switches to sessions that only needed a yes.
- **Fit:** Loom gets Stop/Notification hook payloads already; reading a short bounded field is free. Truncate hard (Supacode caps at about 1000 bytes), treat as untrusted text, no extra transcript reads. Distinct error notification wording for Failed vs Finished, as Supacode does.
- **Risks:** Leaking sensitive text onto the lock screen; offer a setting to show title only. Payload shape can change with CLI versions, so degrade to the generic text if the field is missing (drift detection, never false success).

### Hold a 'prevent idle sleep' power assertion while any session is Working (cost S)

- **Inspired by:** Supacode issue #700 (users run caffeinate by hand because the laptop sleeps mid-run); Supacode lacks it
- **Gain:** Long agent runs finish while the user is away from the Mac; removes a manual caffeinate habit and a silent failure mode (run paused by sleep).
- **Fit:** Event-driven and cheap: take an IOPMAssertion (PreventUserIdleSystemSleep) on the transition into 'at least one Working', release on the transition out; no polling, no new process. Verifiable and visible: show it in the footer/menu-bar and release it on Stop/Quit so it never outlives Loom (process ownership). Default off or opt-in per the 'predictable behavior' rule.
- **Risks:** Battery drain if status gets stuck on Working; the existing hook-silence watchdog must release the assertion. Display sleep should stay allowed.

### Authorization layer for the cross-session channel: literal-action confirmation, 'always allow for this project', source policy, completion ack (cost M)

- **Inspired by:** AutomatedActionPolicy + DeeplinkInputConfirmationFeature (confirmation shows the literal command, 'always allow', ack returned to the CLI only after the action completes, background flag so confirmation does not steal focus)
- **Gain:** loom:open-session already needs a user approval; making it faster for trusted cases (per-project always-allow, 'open in background', result returned to the asking agent as session id + verified outcome) removes a recurring interruption while keeping the user in charge, and gives the planned cross-session messaging channel a ready-made trust model.
- **Fit:** Matches 'cross-session actions only under the user's authority' and 'verified outcomes'. Supacode's source-policy matrix (CLI vs URL) maps to Loom's socket vs URL-scheme. Keep the always-allow scope narrow (project + action type), revocable in Settings, and never for delete or send-message-to-other-session unless the user opts in per target.
- **Risks:** A broad always-allow quietly widens the blast radius; Supacode's socket auth is only 0700 filesystem permissions, Loom's authenticated socket is already stronger and should stay so. Ack timeouts need explicit 'timed out, outcome unknown' wording, not false success.

### Export the caller's identity into every Loom-hosted session and ship a `loom` CLI/deeplink mirror (cost M)

- **Inspired by:** supacode CLI + SUPACODE_* env vars + bundled supacode-cli skill; wish list #820 ('tab list --json with titles, surface ids, agent pid')
- **Gain:** Lets an agent or script address 'this session' unambiguously (LOOM_SESSION_ID, LOOM_PROJECT) and query siblings (`loom sessions --json`: id, title, state, ticket key, branch), which is the missing read side for multi-agent workflows and for the user's own shell aliases/hotkeys (`loom://session/<id>`).
- **Fit:** Reuses the existing authenticated socket and the loom plugin; a read-only list is cheap and needs no polling. Keep write verbs behind the authorization layer above. Deeplinks should resolve to a verified outcome (opened/not found), and the CLI should refuse to default to the 'focused' session for anything destructive (Supacode's own skill warns about focused-target defaults).
- **Risks:** A second API surface to keep stable; version it and detect mismatch rather than pin. Do not let it grow into an orchestration engine.

### Memory-pressure and recency policy for live terminals of non-idle sessions (cost M)

- **Inspired by:** TerminalsFeature hibernation: 5-minute grace window, keep 3 most recent live, DispatchSource memory-pressure sweep
- **Gain:** With 6+ sessions, hidden Working sessions still hold renderers and scrollback; freeing them under pressure keeps Loom light without losing state, and recent-N exemption keeps flipping between the usual three instant.
- **Fit:** Loom already keeps no live terminal for idle records and draws nothing when hidden; this extends it to hidden-but-working sessions. Memory-pressure DispatchSource is event-driven, zero polling. Supacode's trade-off is keeping the process alive in zmx so the dormant view can be rebuilt; Loom can instead keep the process in its run scope and tear down only the renderer, rebuilding from SwiftTerm buffer or a re-attach snapshot (needs a check of what Loom's PTY layer retains).
- **Risks:** Rebuilding a screen from a dropped renderer requires a retained screen model, which has its own memory cost; Supacode needed a per-dormant-session reader thread (about 5 wakeups/s by my reading) to keep status flowing, which violates Loom's no-polling rule, so Loom should keep status on hooks/registry only.

### Opt-in 'keep sessions running after Quit' (daemon-hosted PTYs) (cost XL)

- **Inspired by:** zmx-based persistence and orphan reaper
- **Gain:** Agent mid-turn survives app crash/update; matches what people praise most in Supacode.
- **Fit:** Conflicts directly with 'Quit stops all sessions / no daemon that survives Quit', 'process ownership', and idle cost. If ever done, the lightest variant is not a third-party multiplexer but an explicit, per-session, user-chosen 'detach on Quit' for Working sessions only, hosted in the existing run-scope helper, with Supacode's reaper rules adopted (reap only what a persisted record claims; unknown probe result reaps nothing) and a hard visible indicator that something outlives the app. Loom's CLI sessions are already resumable from Claude's transcripts, which covers most of the value for idle work.
- **Risks:** Highest: breaks the verified-stop guarantee, doubles lifecycle states, adds a daemon to secure and update. Recommendation: defer/skip; revisit only if crash-loss of in-flight turns becomes a real pain.

### Worktree-per-session lifecycle (create, setup script, copy .env, archive on merge) without a polling PR dashboard (cost L)

- **Inspired by:** Supacode worktree flow + RepositorySettings (setupScript, copyIgnoredOnWorktreeCreate, mergedWorktreeAction)
- **Gain:** The user runs several sessions per project; isolating parallel tasks in worktrees prevents collisions and makes 'delete the session' also clean the checkout. It is the biggest missing piece for using Loom as the main app.
- **Fit:** Use plain git (documented, stable interface) and per-project settings in a small file. For status, borrow Supacode's good part (FSEvents on HEAD/index) and avoid its bad part: no per-repo timers, no per-branch gh queries; fetch PR/CI state on demand for the selected session or after the Stop hook, one batched call, with a concurrency cap of 1-2. Deletion must show a dry run of uncommitted work, consistent with Loom's permanent-deletion dry run.
- **Risks:** Scope creep into git UI (commit, PR, CI). Supacode shows what happens when it scales: process storms (#830), rate-limit exhaustion (#844), stale PR state (#695), and data-loss bugs on creation failure (#878). Treat each as a test case.

### Corrections

- Do not repeat 'a socket-side debounce bridges gaps between tools'. It is a stale comment in ClaudeHookSettings.swift; presence no longer uses the socket and no idle debounce exists in the code. Busy/idle flips on every PreToolUse/PostToolUse.
- Hibernation is Beta but ON by default (terminalHibernationEnabled = true). Do not describe it as opt-in. Persistence is also on by default (terminateSessionsOnQuit = false).
- SUPACODE_WORKTREE_ID/TAB_ID/SURFACE_ID/REPO_ID are documented as deprecated and slated for removal; current pane/tab CLI commands default to the user's FOCUSED target, not the caller's session. The 'caller identity export' idea and the 'commands default to the caller's own session' sentence must not be treated as current Supacode behaviour. (SUPACODE_SURFACE_ID is still used as the hook OSC guard.)
- The #844 numbers (64 GraphQL points/min, 24 repos, 5,000/h) come from a commenter on a feature-request issue, not the report of the issue itself. Attribute as 'user measurement in #844 comments'.
- 'Always allow' in the confirmation dialog flips the global automatedActionPolicy to .always (all CLI and deeplink actions, including destructive ones). Do not present it as a per-project or per-action allowlist; the Loom narrow-scope idea is a deliberate improvement, not a Supacode feature.
- Supacode's Notification->awaitingInput mapping is unfiltered. Per the Claude hooks docs, permission_prompt only fires after ~6 s and, in terminal sessions, only when the user appears away, and idle_prompt fires ~60 s after a finished response. So 'awaiting input' in Supacode conflates real permission questions and idle-after-finish, and permission detection lags. Do not present it as a precise needs-approval signal.
- The transcript-grep for API errors depends on undocumented transcript JSONL keys (isApiErrorMessage, sessionId, type). Classify as reverse-engineered, not a documented interface.
- Report implies hooks are simply 'installed into the global config'. It is an explicit opt-in (sidebar card 'Advanced agent integration' / Developer settings) with install-state and drift reporting, and the target dir can be a custom config folder.

### Missed by the report

- Claude Code has documented hook events that Supacode does not use and that Loom should prefer: PermissionRequest (fires immediately when a tool call needs a decision) and StopFailure (turn ended on an API error; added in Claude Code 2.1.78 per ~/Library/Caches/loom-v2-research/repos/claude-code/CHANGELOG.md and https://code.claude.com/docs/en/hooks). Supacode's Stop-transcript grep is a workaround for the absence of these.
- Notification matcher types (permission_prompt ~6 s delay and only when the user seems away, idle_prompt ~60 s after finish, elicitation_dialog, agent_needs_input, agent_completed, quota_auto_resume_*) are documented; Supacode registers one unmatched Notification hook and maps all to awaitingInput. Source: Claude Code hooks docs.
- Supacode's licensing model is perpetual-for-owned-versions: 365 days of updates included, renewals $59 only for new updates, Standard covers 2 Macs for one person (v0.11.0 release notes).
- Hook install is opt-in, gated on the agent config dir existing, supports custom config folders (#829), and reports unreadable integration files as drift (#779) (AgentIntegrationFactory.swift, CodingAgentsSidebarCardView.swift).
- Ry Walker profile adds adoption data: ~1,000 Homebrew installs in 90 days to June 2026, and 'concentrated maintainership' (khoi ~1,574 commits, sbertix second main contributor). Two maintainers, not solo.
- Maintainer roadmap hint in #883: OSC 7501 support is the next thing to add (long overdue).
- Repository-refresh is user-disableable ('Refresh repository status in the background', default on) and background timers only run while the app is active, per WorktreeInfoWatcherManager.backgroundPollingAllowed; the report implies timers run unconditionally.
- Remote SSH repositories (Beta), plain-folder repos, GitLab forge support, a File Explorer inspector pane, and a global show/hide hotkey are shipped features (README, v0.11.0 notes) not mentioned.
- The zmx daemon dependency has a known upstream hazard: upgrading zmx versions that change IPC kills all running sessions (zmx README 'known issues'); Supacode's vendored zmx lagged upstream (0.6.0 vs 0.8.1) per #865, and zmx attach inside a session switches the caller's terminal because ZMX_SESSION is inherited (zmx README 'nested sessions').
- Issue #878 is a data-loss bug: failed worktree creation with a branch-prefix name permanently deleted a folder of nested worktrees including uncommitted work (not moved to Trash). Report mentions it only in passing as a test case.
- Claude Code 2.1.x hook facts relevant to Loom's own hook design: the hooks docs list PostToolBatch, PostToolUseFailure, PermissionDenied, SessionStart sources (startup/resume/clear/compact/fork); Supacode ignores these.
