# Emdash (General Action, YC W26) - github.com/generalaction/emdash

Research note for the Loom v2 brainstorm ([index](../V2-BRAINSTORM.md)). Written by a research subagent on 2026-10-17 and fact-checked by a second one; the fact-check is at the end and wins over the report where they differ. Raw JSON: `../evidence/deep-dive-20261017.json`.

**In one line:** Open-source Electron "agentic development environment": a task = git worktree + branch + agent conversation(s) + linked ticket + PR, with ticket intake from about 12 trackers, an in-app diff/commit/PR/CI loop, scheduled automations, SSH remotes, and 34 CLI agents, now with an optional ACP chat UI next to the real TUI.

**Category:** hybrid (terminal-first by origin; since v1.1.37 a chat-first ACP mode sits beside the real TUI, selectable per agent)

## Adoption

Repo facts via `gh api` on 2026-10-17: 6,014 stars, 633 forks, 93 open issues, about 131 contributors, created 2025-08-28, Apache-2.0 (the Show HN post said MIT, so the license changed), last push 2026-10-14. Latest stable v1.2.8 (2026-10-10); stable releases arrive about every 1-2 weeks with canary builds in between. The company blog (emdash.com/blog/what-is-emdash, Aug 2026) claims 5.4k stars and "over 1M downloads"; I counted about 2.3M total release-asset downloads, which includes canaries and auto-updates, so it is not unique users. Show HN (2026-02-25, id 47140322): 206 points, 71 comments. A rival's hands-on page (runpane.com/compare/emdash, Oct 2026) names Emdash the more complete tool for ticket intake, automations and a shared prompt/skill/MCP library. Praise on HN: seamless switching between Codex and Claude, "much better than flipping between agents", fast team response. Users say all these worktree apps (Emdash, Conductor, Superset) look the same (r/ClaudeCode).

## Architecture

STACK. Electron app (React renderer with MobX and Monaco; main process; SQLite via Drizzle) in an Nx/pnpm monorepo: apps/emdash-desktop, apps/workspace-server (daemon for SSH hosts), packages/core, wire, plugins, chat-ui (SolidJS), ui, shared. The architecture is heavy on abstractions: a typed "Wire" RPC with live models, host-authoritative inventory with tombstones (docs/adr/0001-0008), and 16 worker-spec.ts files, one per runtime (git, acp, tui-agents, workspace-registry, terminals, files, file-search, lsp, provider-usage, automations, scripts, and so on). Emdash's own diagnosis (.scratch/performance-footprint/assets/diagnosis.md, 2026-08-06) says the app "deliberately spawns ~14 persistent Node worker child processes" and measured 422 MB real memory after a fresh start.

HOW IT DRIVES THE AGENT, two paths per conversation.
(1) TUI path. A real CLI in a node-pty PTY (xterm.js in the renderer; optional tmux wrapper so sessions survive an app restart). Launch uses packages/plugins/src/agents/impl/claude/index.ts buildStandardCommand with --session-id, --resume, --model, --dangerously-skip-permissions and the prompt as argv.
(2) Chat path. A conversation spawns the claude-agent-acp adapter (built on the Claude Agent SDK) as plain Node inside the Electron binary, with CLAUDE_CODE_EXECUTABLE pointing at the installed claude. Provider processes are pooled by provider+cwd+env fingerprint (agents/architecture/acp-runtime.md). The runtime has SessionManager, ConversationHandle, LifecycleCell, SessionCell, a transcript reducer, a permission broker and a prompt queue. Claude-specific enrichment (acp-transform.ts) reads adapter-private _meta.claudeCode.parentToolUseId and parses <\task-notification> XML envelopes to build subagent state.

STATUS DETECTION. Hook-only, never from terminal output (agents/integrations/providers.md: "Emdash does not infer agent status from terminal output"). Claude gets 4 hooks (SessionStart, UserPromptSubmit, Notification, Stop) written into the user-global ~/.claude/settings.json or $CLAUDE_CONFIG_DIR/settings.json, never into the worktree (packages/plugins/src/agents/impl/claude/hooks.ts buildClaudeHookConfig). Each hook is a shell command (packages/core/src/services/agent-plugins/api/plugins/helpers/hooks.ts makeStdinHookCommand): `EMDASH_HOOK_CONFIG_VERSION=1; if [ -z $EMDASH_HOOK_PORT ... EMDASH_HOOK_NONCE ... EMDASH_PTY_ID ]; then exit 0; fi; curl -sf -X POST ... 127.0.0.1:$EMDASH_HOOK_PORT/hook || true`. It posts to a token-protected localhost HTTP server (packages/core/src/runtimes/tui-agents/node/hooks/hook-server.ts TuiHookServer) with headers X-Emdash-Token, X-Emdash-Pty-Id and X-Emdash-Event-Type. Config entries carry a version marker; the installer checks, takes a per-root write lock, and rewrites only when stale; unparseable JSON or TOML is left untouched. Claude's Notification event has no type, so parseClaudeNotification classifies it by regex on the message text (/permission|approval/i gives permission_prompt, anything else gives idle_prompt). Status set is idle | working | awaiting-input | error | completed (core/primitives/agents/api/agent-events.ts), persisted per conversation in SQLite together with a "seen" flag (main/core/agent-status/agent-status-service.ts). For providers without a start hook, pressing Enter infers working, and that inference is dropped on restore (agent-state.ts restore). I found no hook-silence watchdog; a third-party Windows test reported a task stuck on "working" after a failed Codex hook.

PERSISTENCE. SQLite for projects, tasks, conversations, workspaces and the agent_status cache. Durable "session intents" per conversation (provider session pointer, cwd, model/mode/effort, bounded presentation snapshot). Chat sessions are evicted after 60 min idle (SESSION_IDLE_MS in packages/core/src/services/session-lifecycle/api/index.ts) and re-materialized via session/load when the user sends a prompt. TUI sessions opt out of idle eviction. The app keeps running in the tray after the window closes (runpane review).

RESOURCE NOTES. The internal polling inventory is in the diagnosis file: git fetch every 2 min per project, a 250 ms-debounced full git scan per active workspace, a 5-minute PR sync (release notes later say repos are polled every minute), a 60 s idle sweep that spawns tmux, and a 1 s TCP probe per preview URL. The planned fixes lower these (scan debounce 1 s, probe 15 s, scrollback 100k to 10k lines, release the canvas renderer for off-screen terminals). A rival's Windows measurement (runpane, Emdash 1.2.2) shows 2.9 GB idle RAM across 20 processes against 780 MB for their app; that is a competitor's number on Windows and unverified.

## Core loop

A day in Emdash. (1) Cmd+N opens one Create Task dialog: pick a start point (branch, issue from a connected tracker, or an existing PR), a name (auto-generated or the Linear branch name), an agent, auto-approve, Chat UI or TUI, and a first prompt. (2) Emdash creates the worktree, runs the foreground git steps, spawns the agent, and lets setup scripts continue in the background; an Activity badge shows the steps. (3) The user watches a sidebar of tasks grouped by project, each with a status dot or spinner, PR badge and diff stats, and jumps to whichever task asks for them (notifications, "awaiting input"). (4) In the same task window they open the Changes rail, leave line comments on the diff, stage or discard, commit, push, open a PR, watch GitHub check runs and the merge-state banner, and merge. (5) Then archive or delete the task, which runs teardown and removes the worktree. Extra loops: schedule a cron "automation" that creates a task per run; open the in-app browser on a detected dev server; keep a shared library of prompts, skills and MCP servers; run the whole thing against an SSH host.

## Features

### Ticket intake: tracker issue to task to agent prompt (orchestration, confidence high)

- **What the user sees:** Cmd+N, choose From Issue, search the connected tracker (Linear, Jira, GitHub, GitLab, Asana, Monday, Trello, Notion, Plane, Forgejo, Featurebase, Plain, YouTrack). Issues already linked to another task are marked. The task name and branch are filled from Linear's own branchName. An editable "issue context" pill is inserted into the first prompt. In chat, typing @ lets you mention more issues.
- **How it works:** Per-tracker plugins in packages/plugins/src/issues/impl/<tracker>/ expose listIssues, searchIssues and getIssue; the desktop wraps them in features/issues/api/node/plugin-issue-adapter.ts (toLinkedIssue, limits 50/20/500). The result is a LinkedIssue snapshot stored on the task row (tasks.linkedIssue; tasks/node/operations/updateLinkedIssue.ts). Context is flattened to plain text by buildIssueContextText in core/primitives/issues/api/issue-context.ts (Provider, Identifier, Title, URL, Description, Status, Assignees, Project, plus a Context block). For Linear, linear/context.ts hydrates all comments and history (State, Assignee, Priority and other transitions). For PTY agents the text is prepended to the initial prompt as argv (tasks/browser/create-task-modal/initial-conversation-text.ts buildFinalPrompt). For chat agents it travels as hiddenContext inside an <issue_context provider=.. identifier=..> block (build-create-task-params.ts buildInitialQueue). The context is re-fetched at insert time (refreshLinkedIssueContext). The task-name helper getIssueTaskName takes the issue's branchName. The "already linked" marker is a map from issue URL to task (use-linked-issue-urls.ts getLinkedIssueMap). Credentials are API tokens kept in an encrypted secret store with multiple accounts per integration (since 1.2.5).
- **Reception:** The ticket-to-task flow is Emdash's most-cited differentiator (a rival's page lists 12 built-in trackers as a reason to pick it). Gaps users ask for: write status back to the tracker (#1930, still open, one commenter says it is the reason to adopt), start tasks from Linear itself (#1029), GitLab (#1096, the most-discussed open issue). From the code, the Linear list is not limited to issues assigned to me (unverified in the UI), while the Asana docs say assigned-to-you only.
- **Evidence:** apps/emdash-desktop/src/core/features/tasks/browser/create-task-modal/build-create-task-params.ts (buildInitialQueue, hiddenContext); apps/emdash-desktop/src/core/primitives/issues/api/issue-context.ts (buildIssueContextText, buildIssueMentionContextBlock); packages/plugins/src/issues/impl/linear/context.ts, queries.ts (ISSUES_QUERY filter: state not in completed/cancelled, no assignee filter, orderBy updatedAt); apps/emdash-desktop/src/core/features/tasks/browser/components/issue-selector/use-linked-issue-urls.ts; https://emdash.com/docs/issues; https://github.com/generalaction/emdash/issues/1930 (maintainer: no provider updates the ticket status; only a "linked to an agent" indicator exists); https://github.com/generalaction/emdash/issues/1029 (trigger a task from Linear: still open, with discussion about webhooks)

### Reserve worktree pool: built, then removed (parallel-worktrees, confidence high)

- **What the user sees:** Early versions (0.4.x) started a task in about 100 ms to 1 s by claiming a spare worktree. In the current v1.x there is no pool; creation shows an Activity badge with steps, and setup work continues in the background.
- **How it works:** PR #674 (2026-01-24) added WorktreePoolService: it pre-created reserve worktrees in the background and claimed one by `git worktree move` plus `git branch -m`, with background replenishment, a 30-minute max age, a 60 s freshness poll using `git ls-remote`, startup cleanup of orphans scanning hardcoded directories, and direct CLI spawn that skipped shell config loading (saved about 1-2 s). Show HN claimed task start went from 5s+ to about 500-1000 ms. Pool bugs followed: stale reserves starting from outdated code (#867, fix #1403), reserves left behind when a project is deleted (#922), cleanup after restart (#1004). The v1 rewrite removed it (commit 4193beb 2026-04-17 "create branch worktrees directly without reserves"; merge of PR #106). The replacement is packages/core/src/runtimes/workspace-registry/node/create-worktree.ts executeCreateWorktree: a short foreground pipeline inspect, resolve-base, add-worktree, verify, with these rules: stale-is-fine (never fetch when the base ref resolves locally; otherwise a single-ref fetch with --no-tags, --no-write-fetch-head, --no-auto-maintenance), `git worktree add --no-track -b`, retry on transient git lock, rollback on failure, and a separate creation budget tier. Gitignored files (.env and so on) listed in preservePatterns are copied in a background step with copy-on-write (`cp -c` on APFS); pushing the branch and freshening refs are also background steps; `scripts.prepare` blocks, `scripts.setup` and `scripts.run` do not. Their own baseline (apps/emdash-desktop/tooling/prototypes/creation-baseline, 2026-08-06) still measured about 3-5 s creation for a 10k-file repo and 3.6-14 s for VS Code, dominated by fetch, copy and checkout; v1.2.0 then shipped "tasks open faster, with non-blocking setup work in the background".
- **Reception:** Founders presented the pool as a key speed win; it also produced a steady stream of stale or orphaned reserve bugs and was dropped in the v1 rewrite. Task creation is still criticised as slow or silent on large repos (#634, #972, both closed).
- **Evidence:** https://news.ycombinator.com/item?id=47140322 (founders' reserve claim); https://www.codeline.co/thoughts/repo-review/2026/emdash-parallel-coding-agents-with-worktree-isolation (reads src/main/services/WorktreePoolService.ts: FRESHNESS_POLL_INTERVAL_MS 60000, MAX_RESERVE_AGE_MS 30 min, cleanupOrphanedReserves scanning hardcoded dirs); git history via gh api: commit 75396b1 (2026-01-24, #674), 4193beb (2026-04-17), 1b92a1d / PR #106; packages/core/src/runtimes/workspace-registry/node/create-worktree.ts (executeCreateWorktree); agents/workflows/worktrees.md; issues #634, #922, #972

### Hook-based agent status and attention (attention-status, confidence high)

- **What the user sees:** Per-task and per-conversation sidebar indicators (spinner while working, awaiting input, error, completed), unread/seen state, OS notifications and sounds; clicking a notification focuses the right conversation tab.
- **How it works:** See architecture: global Claude hooks that curl a localhost server; the pty id arrives in a header, so no output parsing is needed. Pipeline: hook-server.ts, then tui-agents runtime agent-state.ts (parseHookEvent, setStatus), then main/core/agent-status/tui-agent-status-bridge.ts and agent-status-service.ts, which writes agentStatus and agentStatusSeen to SQLite and publishes a conversation event; services/notifications turns deliverable events into notifications. ACP chat conversations project status from runtime session summaries instead, where a pending permission request sets awaiting-input. Opencode, Codex, Qwen, Kimi, Antigravity, Muse and others each get their own hook or plugin config, with a root-resolution table per provider.
- **Reception:** Dots and spinners per task are what users cite as the overview. Weak points: the Claude Notification classification is a message regex; there is no stale-hook fallback that I found; the sidebar "Active" conversation list follows runtime session state, not open tabs, and one user ended up with a pile of "Active" conversations after two days (#3293, 'closing an agent tab does not kill the agent?'; per a commenter the host's detachSession deliberately does nothing).
- **Evidence:** agents/integrations/providers.md ("Agent Hooks And Notifications"); packages/plugins/src/agents/impl/claude/hooks.ts; packages/core/src/services/agent-plugins/api/plugins/helpers/hooks.ts; apps/emdash-desktop/src/main/core/agent-status/agent-status-service.ts deriveAgentStatus; https://runpane.com/compare/emdash (third-party Windows test: Codex hook failed, task stayed on "working"); https://github.com/generalaction/emdash/issues/3293

### Review loop in-app: diff, line comments to agent, commit, PR, CI checks, merge (review-git, confidence high)

- **What the user sees:** A Changes rail per task (flat or tree), diff tabs with Monaco, stage/discard, commit and Commit and Push, branch-commits list, Create PR modal, a PR entry showing checks, comments, files, and a merge footer with state banners (Ready, Conflicts, Behind, Blocked, Draft). Draft line comments on the diff can be attached to the next chat message through the @ menu ("Diff comments") or inserted into a TUI prompt.
- **How it works:** GitHub is the only PR/CI backend (plugin packages/plugins/src/pull-requests/impl/github/client.ts). It uses the GraphQL statusCheckRollup plus PR check runs per commit, with per-resource RateGate objects for graphql and rest fed from rateLimit and response headers, and ETags for PR reads. A PullRequestEngine in a worker and a SQLite store sit behind it; the release notes say repositories are polled every minute and CI results stay tied to the current commit. The merge banner is a pure function of mergeStateStatus (features/source-control/browser/diff-view/changes-panel/components/pr-entry/merge-ui-state.ts computeMergeUiState; CLEAN, DIRTY, BEHIND, BLOCKED, UNSTABLE and others). Draft comments are formatted into an XML block (<target kind=working-tree|pr|commit path=..><comment line=..>) by core/primitives/line-comments/api; comments are cleared only after confirmed delivery, and failed sends or comments edited mid-send stay pending (v1.2.8 notes). Git state comes from per-worktree checkout resources with watchers and an idle TTL (agents/architecture/git-runtime.md).
- **Reception:** Keeping commit, PR and CI in the same window as the agent is part of the product pitch. Requests: per-turn diff (#1635), local merge without PR (#1269), prompt to delete the worktree after a merge (#1345). A rival review found task creation failing on a repo with no remote because push-on-create is the default.
- **Evidence:** packages/plugins/src/pull-requests/impl/github/client.ts; apps/emdash-desktop/src/core/features/source-control/browser/diff-view/changes-panel/components/pr-entry/merge-ui-state.ts; apps/emdash-desktop/src/core/primitives/line-comments/api/; release notes v1.2.4, v1.2.5, v1.2.8 (gh api repos/generalaction/emdash/releases); https://github.com/generalaction/emdash/issues/1635 (users want "changes since last turn" diff; an outside contributor is implementing it with a git snapshot at each turn boundary); https://runpane.com/compare/emdash (new task branches are pushed by default and creation failed on a repo with no remote)

### Chat UI over ACP, next to the real TUI (chat-input, confidence high)

- **What the user sees:** Per agent, a Chat UI vs TUI choice that is remembered. Chat shows a virtualized transcript with grouped thinking blocks, 'Ran N commands' collapse, mermaid, markdown, file links that open the editor at the line, a composer with model/effort/mode controls from the provider's native config options, @ mentions (files, issues, diff comments), image paste, a prompt queue while the agent is busy, per-conversation drafts that survive tab switches, MCP server list with startup errors, and plan/default mode for Codex.
- **How it works:** Opt-in since v1.1.37-39, enabled for all ACP-capable agents (23 of 37 providers). Transport is the Agent Client Protocol via the claude-agent-acp adapter. packages/chat-ui is a custom SolidJS renderer (ARCHITECTURE.md): off-DOM text measurement with `pretext`, a Fenwick-tree virtualizer, a measure/compose/project pipeline, targeted at 10k+ row streaming transcripts at 60 fps. Hard-won correctness rules are visible in acp-runtime.md and CONTEXT.md: prompts carry client ids, acknowledgement means 'accepted', provider dispatch is a durable boundary, and "outcome unknown" blocks redelivery and is never shown as failed (no silent resend). Permissions are always interactive; no auto-approval for chat. Idle chat sessions are evicted after 60 min and woken on the next prompt.
- **Reception:** The founders say chat gives one intuitive way to interact with many parallel agents. Complaints: chat hides or abstracts harness slash commands such as /settings (#3126, v1.2.3); chat permissions cannot be changed mid-session as in the CLI; chat depends on adapter-private metadata, so each Claude release can break subagent display (the code has explicit guards such as 'Missing or unknown statuses must not default to running'). The rewrite to a typed ACP/Wire stack looks expensive: dozens of release-note lines in July to September 2026 are chat reliability fixes (prompt queue, session restore, history refresh).
- **Evidence:** packages/chat-ui/ARCHITECTURE.md; agents/architecture/acp-runtime.md; CONTEXT.md (Prompt, Provider dispatch, Outcome unknown, Session quiescence); release notes v1.1.37, v1.1.39, v1.2.3, v1.2.4, v1.2.7; https://github.com/generalaction/emdash/issues/3126 (slash commands from the harness are missing in chat mode); https://emdash.com/blog/what-is-emdash

### Task-centred workbench: sidebar, tabs, splits, palette (navigation-ux, confidence medium)

- **What the user sees:** Left sidebar of projects and tasks (sortable by last used or created, pin, archive, colour requests open), each task showing PR badge and line counts; inside a task, a main column with tabs for conversations, terminals, editor files, diffs, browser, and drag-to-split panes; a right rail of conversations/Changes; Cmd+Shift+F content search; a command palette searching commands, files, conversations, projects, tasks; zen mode; Activity badge; a terminal drawer on Cmd+J.
- **How it works:** A Task is the unit: a worktree, a branch, N conversations, a lifecycle status (todo, in_progress, review, done, cancelled, backlog, duplicate, triage in primitives/tasks/api/tasks.ts), an optional linked issue and PR. Feature slices live under apps/emdash-desktop/src/core/features/* with contributions (views, commands, palette providers). Editor state is Monaco plus LSP workers (v1.2.8). Per-pane layout, drafts, selection and scroll are retained per conversation.
- **Reception:** HN founders: the working mode is 'actively on one or two tasks, switching as one runs', with a long sidebar list of explorative tasks; navigating between tasks is the core need. Early HN complaint: 78 tasks made the UI crawl (old version; the later perf work targeted this). Rival review: 'one task is visible at a time; the sidebar is the overview'.
- **Evidence:** apps/emdash-desktop/src/core/primitives/tasks/api/tasks.ts; apps/emdash-desktop/src/core/features/tasks/browser/view/task-sidebar.tsx; release notes v1.2.0, v1.2.3; https://github.com/generalaction/emdash/issues/2124 (tabs as collapsible sub-items under tasks); https://github.com/generalaction/emdash/issues/2123 (auto-generated short task and tab names); https://github.com/generalaction/emdash/issues/2914 (task colours)

### Automations: cron-scheduled tasks with run history (automation, confidence high)

- **What the user sees:** An Automations view: name, project, cron schedule, prompt + provider, workspace choice (new worktree, existing workspace, repo root, sandbox); run now; pause; history of runs with status; convert a run to a regular task. Built-in templates: find critical bugs, daily change summary, vulnerability scan, add test coverage, fix reported bugs, generate docs.
- **How it works:** A dedicated automations runtime (packages/core/src/runtimes/automations) keeps exactly one upcoming scheduled run per enabled automation, recovers runs interrupted by an app restart, and walks a run through queued, creating_task, launching_task, creating_conversation, done/failed/skipped (docs). Runs are real tasks (deployment-builder.ts builds the task/worktree/conversation config). It only fires while the app (or its workspace server host) is running; agents without argv or stdin prompt delivery are excluded unless they support ACP.
- **Reception:** Rival reviews list scheduled runs as a reason to choose Emdash; I found no user complaints. The Monday-10:00 templates read as marketing more than proven workflows (unverified in use).
- **Evidence:** https://emdash.com/docs/automations; apps/emdash-desktop/src/core/features/automations/browser/builtin-catalog.ts; apps/emdash-desktop/src/core/features/automations/node/deployment-builder.ts; agents/integrations/providers.md ('pty-only' prompt delivery)

### Project config: lifecycle scripts, env, ports, preserve patterns (parallel-worktrees, confidence high)

- **What the user sees:** Per project: .emdash.json (shareable) and settings for setup/run/teardown scripts, shell setup, preservePatterns (copy .env into new worktrees), env vars, worktree directory, branch prefix, remotes, and a tmux toggle. Scripts see EMDASH_TASK_ID, EMDASH_TASK_NAME, EMDASH_TASK_PATH, EMDASH_ROOT_PATH, EMDASH_DEFAULT_BRANCH and EMDASH_PORT (a base of 10 ports) so parallel dev servers do not collide. A Storage settings page lists worktree disk use per project and deletes selected tasks.
- **How it works:** packages/core/src/runtimes/scripts runs lifecycle scripts as PTYs with provenance (activation, manual, retry), timeouts and a stop verb; the workspace registry mirrors runs into durable lifecycle steps shown in the Activity badge. Teardown runs on archive/delete when possible (ADR 0003). Deletion intent survives an unreachable host as a tombstone swept later (ADR 0006). Storage page: PR #2686 reuses the canonical deleteTask path.
- **Reception:** The HN question 'every worktree needs its own ports and docker volumes' was answered with these env vars and the commenter said it was exactly what they needed. Known rough edges: preserve patterns are empty by default since workspace-lifecycle-v2 (.env no longer copied automatically), and worktree path or orphan-ref bugs appear in issues (#3247).
- **Evidence:** agents/workflows/worktrees.md; https://emdash.com/docs/project-config; https://news.ycombinator.com/item?id=47140322 (founder answers a ports/docker question with EMDASH_PORT); docs/adr/0003, 0006; PR #2686

### Usage meters, shared prompt/skill/MCP library, in-app browser (usage-cost, confidence high)

- **What the user sees:** A Usage settings page (v1.2.8) with remaining Codex and Claude Code subscription allowances, reset countdowns and refresh controls, shared accounts shown once across machines. A Library of prompts, skills and MCP servers written into every agent's config. An in-app browser tab per task, with dev servers auto-detected from terminal output and forwarded from remote hosts.
- **How it works:** Claude usage is the same control request Loom uses: probeClaudeUsage in packages/plugins/src/agents/impl/claude/usage.ts starts an Agent SDK query() with no prompt, persistSession false, hooks disabled, and calls usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET, with timeouts of 25 s and 5 s, and maps five_hour / seven_day / model_scoped windows; it declares unsupported for API-key auth and signed-out for no login. MCP and skills are read, adapted and merged across provider config formats (agents/integrations/mcp.md). Preview URL detection is regex on PTY output plus a TCP probe (1 s, moving to about 15 s in the planned fix).
- **Reception:** Useful but secondary in reviews. It confirms the get_usage route is a public-but-experimental SDK surface that others also depend on and that Loom's own implementation matches current practice.
- **Evidence:** packages/plugins/src/agents/impl/claude/usage.ts; release notes v1.2.8; agents/integrations/mcp.md; services/preview-detection (url-detector.ts); .scratch/performance-footprint/issues/05-preview-probe-lifecycle.md

## UX patterns worth borrowing

- One "Create Task" dialog that combines start point (branch/issue/PR), name, agent, interface (chat vs TUI), auto-approve and first prompt, and shows the ticket context as an editable pill so the user sees what text the agent will receive.
- Task as the unit: worktree + branch + conversations + ticket + PR + lifecycle status in one sidebar row, with PR badge and line-count diff stats on finished tasks.
- An Activity popover (a single titlebar badge) that lists every background step of a task's setup (create-worktree, copy-artifacts, push-branch, setup/run scripts) with spinner, error emphasis and relative times, so slow background work is visible but not blocking.
- Mark tickets already linked to a task inside the ticket picker, matching by URL, so the user does not start a second agent on the same issue.
- Merge banner as a pure function of mergeStateStatus (Ready / Behind / Blocked / Conflicts / Draft) with a plain-language detail line.
- @ menu in the composer as the single insertion point for context (files, tickets, diff comments, library prompts); comments leave the draft only after confirmed delivery.
- Per-agent Chat UI vs TUI toggle that is remembered across projects and machines, instead of a global mode switch.
- Notification click routes to the exact conversation tab (including other panes) without creating a blank terminal.
- Per-conversation draft, selection, undo history and composer scroll are kept across tab switches.
- Command palette that searches commands, files, conversations, projects and tasks together; Settings has its own search.
- Drag a tab to a pane edge to split.

## Anti-patterns

- A reserve worktree pool: it saved about 4 s on creation at the price of stale-base bugs, orphaned worktrees after crashes or project deletion, hardcoded cleanup directories, and background work on an idle machine; Emdash itself removed it within three months of its first release and moved to a short foreground pipeline plus background steps.
- One worker process per runtime: about 14 to 16 persistent Node workers, plus polling in each (2 min fetch, 250 ms git scan, 1 min PR sync, 1 s preview probes). Their own diagnosis found multi-hundred-MB baselines and later had to cap scrollback, throttle scans and add backoff; a rival measured 2.9 GB across 20 processes on Windows (unverified).
- Status from a message regex: Claude's Notification event is classified permission vs idle by matching /permission|approval/i, and hookless providers get 'working' inferred from the Enter key; a failed hook leaves a task stuck on 'working' with no watchdog.
- A second, SDK-backed agent path for chat: it hides the CLI's own slash commands and settings (#3126), couples display of subagents to adapter-private _meta fields and XML envelopes, and needs a very large reliability effort (typed prompt dispatch, outcome-unknown states, history refresh races).
- Listing every open ticket of a tracker (no 'assigned to me' filter on Linear in the query I read) and stuffing the raw description plus all comments into the first prompt; untrusted ticket text goes into the agent context, so the user needs to see and edit it first (Emdash does show an editable pill).
- Defaults that surprise: push of new task branches on creation (fails on repos without a remote), .env not copied unless configured, closing a tab does not stop the agent so the 'Active' list drifts from what is open (#3293), app stays in the tray after the window closes.
- Writing a version-marked hook block into the user's global ~/.claude/settings.json: it works (guarded by env vars so it is harmless outside Emdash) but spawns curl for each event and makes Emdash an owner of shared user config; breakage after a CLI hook-schema change is invisible to the user.
- Not letting agents drive the app: a rival review states Emdash has no CLI, API or MCP for agents ('by design'), so orchestration stays manual.

## Ideas for Loom

### Ticket-to-session starter built on what Loom already has: a palette action "New session from ticket" (type EDDP-123 or pick from an on-demand list) that opens a session with a title, the ticket key for de-duplication, and a first message containing the ticket context in a delimited block, shown to the user for editing before it is sent. Two lightweight variants: (a) Loom-side fetch from Linear/Jira with a token in Keychain, on demand only; (b) no tracker code at all: the first message tells Claude to read the ticket through the user's own Jira/Linear MCP or CLI, and Loom only manages key, title, worktree and de-dup (preferred). (cost M)

- **Inspired by:** Emdash ticket intake (build-create-task-params.ts hiddenContext, issue-context.ts, use-linked-issue-urls.ts) plus the open requests #1930 and #1029.
- **Gain:** Removes copy-paste of ticket text into a new session, gives a deterministic title and branch name (Linear branchName style), and prevents two agents working the same EDDP key. The user's two work projects use ticket keys, so this is the most direct fit.
- **Fit:** Fits fluency, predictability and cross-session-under-user-authority (the user chooses the ticket and approves the session). Variant (b) adds no credentials, no polling and no tracker API pinning, which is the most resilient to change; variant (a) adds token storage and per-tracker code and should stay optional. Conflict to avoid: auto-triggering sessions from webhooks, which needs a daemon and breaks 'Quit stops all'.
- **Risks:** Prompt injection through ticket text (always show and delimit it); stale snapshot if fetched long before send (refresh at send, as Emdash does); tracker rate limits in variant (a).

### Session worktrees without a pool: "Start in new worktree" when opening a session, using Emdash's final design, not its first. Foreground pipeline of inspect, resolve base, `git worktree add --no-track -b`, verify; never fetch if the base resolves locally; copy preserved ignored files (.env) with APFS clone in a background step; record the worktree Loom created and remove it only through a verified delete path with a dry run (same shape as Loom's session deletion). Add a small storage list of worktrees per project with sizes. (cost M)

- **Inspired by:** Emdash create-worktree.ts executeCreateWorktree, copy-artifacts, the removal of WorktreePoolService (commit 4193beb), and the Storage page (PR #2686).
- **Gain:** Parallel sessions on one repo without manual git commands; a task starts in seconds on most repos; cleanup is no longer manual. Preserved .env saves the most common first-run failure in new worktrees.
- **Fit:** Matches clean ownership (Loom records what it created, deletion verified) and 'nothing runs when idle'. A pool conflicts with the very low idle cost and with accurate state (spare worktrees are state nobody asked for); skip it. Background copy is a bounded one-shot, not a loop.
- **Risks:** Large repos still take 3-14 s (Emdash's own baseline); needs clear failure stages and rollback; branch and worktree naming collisions; worktrees left behind after crashes (use a registry in Loom's own data and a reconcile on launch, not hardcoded directory scans).

### Event-driven PR and CI strip on session cards: show PR number, merge state (Ready / Behind / Blocked / Conflicts) and check-rollup state, refreshed only on events: the Stop hook, app activation, a push noticed by a visible card, and a manual refresh; while checks are pending and the card is visible, back off (30 s, 60 s, 2 min) and stop when settled. A failed check can move the session into Loom's existing red/needs-you state. (cost M)

- **Inspired by:** Emdash PR entry, merge-ui-state.ts computeMergeUiState, github/client.ts statusCheckRollup with rate gates.
- **Gain:** The user no longer opens GitHub to learn whether the agent's PR is green; the sidebar becomes the single place to see 'which session needs me', including for CI.
- **Fit:** Fits only in the event-driven form; Emdash's blanket per-repo polling every minute is exactly what Loom's no-polling rule forbids. Use the already installed `gh` CLI (`gh pr view --json statusCheckRollup,mergeStateStatus`) so Loom stores no tokens and tracks no GitHub API versions. 'Delivered/merged' states must come from the API result, not from the agent saying so.
- **Risks:** gh missing or logged out (show a clear drift-style message, never a false 'green'); GitHub only; multiple accounts; rate limits for many cards (only fetch visible or pending ones).

### Diff and review view with draft line comments that go back to the agent as one structured block, plus a 'since last turn' scope. Per session: working-tree diff, staged files, commit, push, open PR (all through git and gh). Comments are collected in Loom and inserted into the session's prompt box via bracketed paste as an XML-ish block, not auto-submitted. 'Last turn' diff uses a snapshot written at each Stop hook (for example `git write-tree`/`git stash create` into a private ref) as the baseline. (cost L)

- **Inspired by:** Emdash source-control slice, core/primitives/line-comments formatCommentsForAgent, and the heavily requested per-turn diff (#1635).
- **Gain:** Reviewing parallel agents' output is the biggest remaining step outside Loom; per-turn diff and comment-back make the review-correct loop fast without leaving the window.
- **Fit:** Costly but compatible: compute diffs on demand for the visible session only, watch with FSEvents only for the visible worktree, debounce at 1 s (Emdash's 250 ms full scan per active workspace was one of its worst CPU findings and they moved to 1 s with byte budgets). Delivery caveat: with a real PTY Loom cannot verify the CLI accepted a paste, so the UI must say 'pasted into prompt' and let the user press Enter; do not clear comments on a guess. Skip an embedded editor; open files in the user's editor.
- **Risks:** Large diffs; binary files; rendering performance (use a native text view, virtualize); paste behaviour differs across CLI versions.

### Side chat and chat-style view without a second agent stack: render the session's own Claude transcript (already read incrementally for Usage) as a chat-style panel next to the terminal, and implement the long-standing 'side chat' as a forked session (resume of the same conversation with a fork, run in its own Loom-owned PTY) whose result can be pulled back as a summary block. Do NOT add an SDK/ACP path that drives the agent itself. (cost XL)

- **Inspired by:** Emdash chat-ui and ACP runtime (what it cost and what broke: #3126 hidden slash commands, adapter-private metadata, large reliability backlog) and its per-agent Chat UI/TUI toggle.
- **Gain:** Gets the readability of a chat view and the 'does not pollute the main thread' side conversation the user has wanted, while keeping every CLI feature (slash commands, permission modes, hooks).
- **Fit:** A transcript-reading view is read-only, lazy (render only visible rows, nothing when hidden) and does not pin CLI versions beyond the transcript format, which Loom already parses and guards with drift detection; a fork uses a documented CLI resume option (verify the exact flag against current Claude docs before building). An ACP/SDK chat engine would break 'the real CLI is the session' and the resilience rule, and Emdash shows the maintenance bill.
- **Risks:** Transcript format drift (mitigate with the same drift detection as the registry); composer-in-chat would need PTY input injection with unverified delivery; fork semantics and cost doubling for the user.

### Derive and surface task lifecycle from facts instead of a manual kanban: a card shows ticket key, branch, PR state and merge state; 'review' appears when a PR is open, 'done' when merged; offer, under explicit user action, to move the ticket (Linear/Jira transition) or archive the session and remove its worktree when the PR merges. (cost M)

- **Inspired by:** Emdash task lifecycle statuses (primitives/tasks/api/tasks.ts), prompt-to-clean-up after merge (#1345), and ticket write-back (#1930, which Emdash never built).
- **Gain:** Closes the loop that Emdash users are asking for: the ticket and the sidebar stay true without manual status changes, and merged work stops cluttering the sidebar.
- **Fit:** Good: derived (never user-maintained) state is accurate and predictable; every write to a tracker or deletion of a worktree is a visible, user-confirmed action (cross-session and external actions only under the user's authority). Avoid a new manual status field.
- **Risks:** Depends on the PR/CI idea and on ticket access; a wrong auto transition on a real work ticket is costly, so default to suggesting.

### Saved prompt recipes without a scheduler: reusable 'task recipes' (project, prompt, worktree choice) startable from the palette, with an optional 'run when Loom is open at time X, ask me if missed' schedule. Do not build a daemon; if true background runs are wanted later, delegate to Claude's own scheduled routines or launchd rather than keeping Loom alive. (cost S)

- **Inspired by:** Emdash Automations (runtimes/automations, builtin-catalog.ts) and its prompt library.
- **Gain:** Repeated chores (weekly dependency check, triage, 'find critical bugs') become one keystroke.
- **Fit:** A cron runner that keeps firing needs a process that survives Quit, which contradicts 'Quit stops everything Loom started' and 'no daemon'; the recipe-only variant is cheap and consistent. The scheduler part should be skipped in v2.
- **Risks:** Low value without a scheduler; the real-value version (unattended runs) needs a different ownership model.

### Corrections

- Do not repeat 'Claude's Notification event has no type' as a fact about Claude Code. Current official docs (code.claude.com/docs/en/hooks) document a notification_type field (permission_prompt, idle_prompt, auth_success, elicitation_dialog and others) in Notification hook input and as a matcher. Emdash's regex on message text is its own workaround or legacy; a Loom design should use the documented notification_type (and verify against the installed CLI version) rather than copying the regex.
- The 'license changed from MIT to Apache-2.0' is an inference. The only evidence is the HN post saying MIT versus the current repo/blog saying Apache-2.0; the shallow clone cannot show the history.
- The 422 MB figure in Emdash's own diagnosis is framed there as 'unremarkable'; it is not an admission of a heavy baseline. Only the '~14 persistent worker processes' and the polling inventory support the 'heavy' reading. The 2.9 GB / 20 processes number is a competitor's single Windows 11 measurement.
- Tracker count: the plugin directory has 13 trackers (asana, featurebase, forgejo, github, gitlab, jira, linear, monday, notion, plain, plane, trello, youtrack); runpane says 12; the report says 'about 12' while listing 13. Agent counts also disagree across sources (34 in the report, 39 impl directories, 37 in other text, 35 per runpane), so avoid quoting a precise number.
- Issue #1930 is not settled: one contributor says status sync 'should work for Linear already', a collaborator says nothing is updated. Say 'unconfirmed / contested', not 'no provider updates the ticket'.
- Total release-asset downloads counted today are 2,231,970 (report said about 2.3M); still includes canaries and auto-updates, so not unique users.
- Issue #3126 uses Oh My Pi as the example, so it is evidence about the chat UI layer in general, not about Claude Code slash commands specifically.

### Missed by the report

- Claude usage windows also include seven_day_oauth_apps ('Weekly - OAuth apps') in packages/plugins/src/agents/impl/claude/usage.ts; the report lists only five_hour / seven_day / model_scoped.
- TUI runtime has its own 60 s sweep and a tmux keep-alive derived from SESSION_IDLE_MS even though TUI sessions use policy 'always' (packages/core/src/runtimes/tui-agents/node/runtime/runtime.ts ~158-170); relevant if Loom compares idle cost or tmux wrapping.
- Hook command is guarded by env vars set only inside Emdash PTYs, so the global ~/.claude/settings.json entries are no-ops in plain terminals; this mitigates the 'owning shared user config' downside the report raises, and the hook config carries EMDASH_HOOK_CONFIG_VERSION=1 for upgrades (packages/core/src/services/agent-plugins/api/plugins/helpers/hooks.ts). On Windows it uses a PowerShell variant.
- Claude hook payloads carry session_id that changes on /resume inside the TUI; Emdash's parseClaudeHookEvent propagates providerSessionId so the runtime resumes the session Claude is actually in (hooks.ts comment). A Loom session-identity design should account for this.
- Hook server is bound to 127.0.0.1 on an ephemeral port (listen(0)) with a per-run nonce header; this is a concrete model for a local-only status channel (hook-server.ts lines 28, 66).
- The runpane comparison, the main source for the memory number, the 'stuck working' report, the tray behaviour and the no-CLI/MCP claim, is a competing product's marketing page; treat as lower-trust than the repo.
- agents/architecture/acp-runtime.md line 191-192: TUI auto-approve is a launch setting remembered per host/provider/transport and new TUI automations default to no auto-approve; relevant to Loom's permission model.
