# T3 Code (Ping / Theo) - github.com/pingdotgg/t3code, t3.codes

Research note for the Loom v2 brainstorm ([index](../V2-BRAINSTORM.md)). Written by a research subagent on 2026-10-17 and fact-checked by a second one; the fact-check is at the end and wins over the report where they differ. Raw JSON: `../evidence/deep-dive-20261017.json`.

**In one line:** Open-source (MIT) 'agent harness control surface': a Node/Effect WebSocket server drives Claude Code (through the Agent SDK), Codex, Cursor, Grok, OpenCode, Pi and others behind one chat-style UI on Electron desktop, web and iOS/Android. Orchestrator V2 went stable on 2026-10-15 (v0.1.0).

**Category:** chat-first (server-mediated, multi-provider; does not host the CLI's own interface)

## Adoption

Self-reported 'over 500,000 users' on t3.codes and in AGENTS.md (marketing claim, unverified). GitHub API on 2026-10-17: 28,035 stars, 7,504 forks, 473 contributors, 2,933 open issues, MIT, created 2026-02-08, last push hours earlier. Nightly builds several times a day; about 4,000 PRs opened 2026-10-01..2026-10-17 (GitHub search), largely because AGENTS.md says most contributions are made by agents running inside T3 Code itself. Stable cadence: v0.0.34 (2026-08-26) to v0.0.45 (2026-10-02), then v0.1.0 (2026-10-15). iOS App Store and Google Play apps exist; Android 2.0 distribution was rough (issue #14871 comments: Play beta group blocked, APK later attached to the android-nightly release, TestFlight full). Third-party coverage: Flavio Copes deep dive (2026-08-28), Skyflo comparison page (2026-09-18, a competitor, treat with care), a YouTube video 'I Switched From Claude Code to T3 Code' (could not read its transcript). A 7-month-old Reddit thread calls it 'vibe coded' with few tests; the repo now has very large test suites, so that critique is dated.

## Architecture

STACK. TypeScript monorepo, Effect-TS throughout. apps/server = Node WebSocket+HTTP server with event-sourced orchestration persisted in SQLite (statev2.sqlite under ~/.t3/userdata, plus its own copy of messages/timeline). apps/web = React + Tiptap composer + @legendapp/list virtualization. apps/desktop = Electron shell bundling the server. apps/mobile = React Native. native/resource-monitor = Rust sysinfo sidecar that samples only while a diagnostics subscriber exists. Remote: same server reached over LAN/Tailscale pairing links or 'T3 Connect' (Clerk identity + relay brokers a DPoP-bound bootstrap, then traffic goes through a managed tunnel; docs/internals/t3-connect.md).

HOW IT DRIVES CLAUDE (read in code). apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts (9,230 lines) calls the Anthropic Agent SDK (@anthropic-ai/claude-agent-sdk ^0.3.276, apps/server/package.json) query() with a streaming-input prompt queue (Queue.unbounded<SDKUserMessage> turned into an AsyncIterable). The SDK spawns the real 'claude' binary (pathToClaudeCodeExecutable) as a child via a custom spawnClaudeProcessGroup (detached, SIGKILL the whole process group on exit, because plugin MCP wrappers leave orphans; issue #3089). makeClaudeQueryOptions builds: sessionId or resume (native session id), resumeSessionAt (used for rollback), includePartialMessages:true, permissionMode, canUseTool callback, allowedTools/disallowedTools, systemPrompt preset 'claude_code' with an appended T3 instruction block, thinking summaries, settings (e.g. autoCompactWindow), extraArgs from user launch args, and additionalDirectories. MCP servers are NOT passed as --mcp-config argv (readable by any local user); they are registered over the CLI stdin control channel with queryRuntime.setMcpServers() and a 90 s timeout. Sessions are forked with the SDK's forkSession (claudeHistoryWorker.ts runs forkSession/getSessionMessages in a separate worker process to isolate cost).

PERMISSIONS. T3's four modes (Supervised / Auto-accept edits / Auto / Full access) are mapped to SDK permissionMode default / acceptEdits / auto / bypassPermissions in permissionModeForClaudeRuntimePolicy (ClaudeAdapterV2.ts ~L1754); canUseTool is installed only when approval-required or auto-accept-edits (installPermissionCallback). Approvals are therefore answered by T3's own UI through the SDK callback, not through Claude hooks or the CLI's dialog. Open bug evidence of the cost of owning this path: issue #15503 (Auto+Plan silently approves native plan-mode write requests).

STATE DETECTION. Derived from the SDK message stream, not hooks: system init (turn start), result (turn terminal), task_started / task_progress / task_notification (subagents and background shells), background_tasks_changed, api_retry, rate_limit_event, compact_boundary, model_refusal_fallback (ClaudeAdapterV2.ts L6100-8400). Terminal status is rated 'strong' in ClaudeProviderCapabilitiesV2. There is NO hook-silence watchdog: issue #16449 shows a Claude thread stuck 'running' for ~8 hours after a mid-run provider error and unstoppable; #15854 shows Stop before system/init bricks the thread (later turns resume a session that was never created).

LIVE TOOL OUTPUT GAP. The SDK sends no stdout until the tool result, so ClaudeTaskOutputTail.ts polls (250 ms, up to 256 KiB per read) Claude Code's private file <tmp>/claude-<uid>/<project>/<session>/tasks/<task>.output and degrades to 'no live output' if the layout changes. Output is only streamed to a client while the command row is expanded (CommandOutputHub, subscribeCommandOutput; docs/internals/performance-regressions.md).

USAGE. Reads Claude's local JSONL transcripts and de-duplicates per message id (provider/Drivers/claudeUsage.ts notes records repeat usage per content block, overcounting about 2.4x), and uses the SDK's get_usage control response for plan windows (provider/claudeUsageLimits.ts, windows five_hour/seven_day, per-model scoped weekly buckets). This is the same two sources Loom already uses.

PERSISTENCE. Event store + projections in SQLite; commands are idempotent with receipts; Orchestrator V2 doc set in docs/orchestration-v2 (AppThread > Run > RunAttempt > ExecutionNode tree; provider ids are refs, app ids primary). Thread search is SQL LIKE over user messages and final assistant text (orchestration-v2/ThreadSearch.ts), not FTS. Cold open targets ~75 timeline rows / ~1 MiB, bounded paging, raw command output omitted from the wire.

RESOURCES. Scheduler ticks every 5 seconds (scheduling/Scheduler.ts). Process containment exists only on Linux (systemd slice with MemoryHigh/MemoryMax in process/agentScope.ts); on macOS agentScope returns a default no-op (issue #20329: concurrent test runs pushed a 32 GB Mac to ~100 GB memory pressure and crashed it). Electron preview webviews have repeatedly leaked GPU memory (issues #14730 228% CPU/10 GB GPU with the panel closed; #13610 21 GB on a 16 GB Mac).

PROVIDER VERSIONS. Installed 'claude --version' is probed (provider/ClaudeProvider.ts). A compatibility manifest (apps/server/src/provider/model-manifest.json, schema in ModelManifest.ts + providerCompatibility.ts) is bundled and also fetched from raw.githubusercontent.com/pingdotgg/t3code/main/... with a TTL, validated, cached, and only replaces the bundle if newer by updatedAt. Per driver it holds t3CodeRange, recommendedRange/Version and version ranges with status supported / graceful / unsupported / broken (Claude: >=2.1.280 supported, 2.1.111..2.1.280 graceful, <2.1.111 unsupported). Models carry adapter.claudeCode.minVersion so a new model is announced before the CLI supports it ('update required' list in the picker). A separate maintenance runner can run the provider's own update command with progress (provider/providerMaintenanceRunner.ts) and a ProviderLatestVersions check shows 'behind latest'.

## Core loop

Open T3 Code (desktop or phone), pick a project, press New thread, optionally 'New worktree' (branch per thread, setup script from t3.json runs on worktree create), choose provider/model/effort/permission mode in the composer, type the task and send. Cmd+Enter starts it in the background and opens another draft; Shift-click several models to fan the same prompt out to several threads/worktrees. Watch status in the sidebar (working, waiting, approval, input, failed, limited, unread-done), answer approvals/questions in the conversation or from the phone, steer or queue follow-ups while it works, review the per-turn diff, commit/push/open a PR with one button, then Settle the thread (or let the server settle it when the PR merges or after 3 idle days). Agents can themselves delegate to other providers (delegate_task) and spawn/message other threads through the T3 MCP. Scheduled tasks and webhooks start threads unattended.

## Features

### Claude via Agent SDK instead of a terminal (the central design choice) (other, confidence high)

- **What the user sees:** A chat transcript with streaming markdown, collapsible 'Worked for 22s' tool folds, command rows, plan cards, subagent cards, approval panel above the composer. No terminal for the agent; a separate integrated terminal drawer exists for the user's own shell.
- **How it works:** ClaudeAdapterV2.ts: query({prompt: AsyncIterable of SDKUserMessage, options}) with includePartialMessages, canUseTool, resume/sessionId, resumeSessionAt, setMcpServers over the control channel; the SDK spawns the actual claude binary, T3 wraps it in a detached process group and SIGKILLs the group on exit. Messages are normalised into provider-neutral events (docs/orchestration-v2). Skills/plugins/CLAUDE.md parity had to be added after the fact (issue #1283 'Claude integration does not load installed Skills, Slash Commands, or CLAUDE.md', 20 reactions; #5622 plugin skills missing in the $ picker, still open).
- **Reception:** Praised for UI speed and polish ('first coding GUI that did not suck performance wise' appears in the site's own testimonial wall, so treat as marketing). Complaints: feature drift versus the CLI (skills, slash commands, plugins), long-running 'slower than the CLI' reports (issue #695, 31 reactions, open since March: Claude users report 3x slower tasks, no thinking toggle on some models), and no live tool output without polling a private Claude temp file.
- **Evidence:** apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts (query() ~L768, makeClaudeQueryOptions ~L1076, spawnClaudeProcessGroup ~L242); apps/server/package.json: @anthropic-ai/claude-agent-sdk ^0.3.276; https://github.com/pingdotgg/t3code/issues/1283; https://github.com/pingdotgg/t3code/issues/5622; docs/user/providers-claude.md

### Orchestrator V2: delegate_task, child threads, lineage, background work (orchestration, confidence high)

- **What the user sees:** An agent can hand work to a child agent on any provider/model; the child shows as a subagent card/lineage row with model, status, duration and result. Several subagents fold into one card. When background shells/subagents finish the parent agent is woken with a message saying which one finished. Stop also stops delegated children and background work; after a server restart the agent is told which background work died. Subagent threads are read-only (message the parent).
- **How it works:** MCP tool delegate_task (async or wait mode) becomes the V2 command delegated_task.request, creating a child thread with lineage 'subagent' and an app_owned projection on the parent. The child gets only the task prompt (plus optional role), never the parent history. Privilege ceiling: child runtime and interaction mode may equal or narrow the parent's, never escalate. Idempotency via clientRequestId. Native Claude subagents are projected from task_started/task_progress/task_notification SDK messages; Claude 'workflow' tasks (workflow_progress) are mapped to phases/agents (Adapters/claudeWorkflowProgress.ts). A child's pending question wakes the parent with a notification turn. Completion is finalised from the event stream so it also works after a restart.
- **Reception:** Release notes call delegate_task 'the recommended way to combine harnesses'. Open bugs after launch: no token usage or reasoning effort for subagents (#15429, #15214), Claude child task dies after t3_worktree_handoff (#15136), stale 'Waiting on background task' banner (#15993), Claude workflow shown as plain subagent (#15448, closed).
- **Evidence:** docs/orchestration-v2/orchestrator-mcp-server.md; docs/orchestration-v2/README.md (invariants: root-run completion is the only event that completes a turn; child completion never closes the parent); apps/server/src/mcp/OrchestratorMcpService.ts, apps/server/src/mcp/toolkits/orchestrator/; https://github.com/pingdotgg/t3code/releases/tag/v0.1.0; apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts (task_* handling L6298-7110)

### Thread lifecycle: pin, settle, snooze, archive, auto-settle, undo (attention-status, confidence high)

- **What the user sees:** Sidebar sections Pinned / Active / Snoozed shelf / Settled shelf. Settle moves finished work out of the active list without deleting it; Snooze hides a thread until a time (presets or custom) and it wakes early if it needs you; Archive hides; Pin keeps on top. Every one of these shows a 5-second Undo toast (mod+z). Drag rows between sections: the dragged row shows the verb the drop performs (Pin / Unpin / Settle / Un-settle / Wake). Press and drag on a Settle button to settle a whole range. 'Settle and advance' jumps to the next thread. Order of Active threads is stable (new threads on top; activity does not reorder).
- **How it works:** Server-owned (ThreadSettlementService.ts, 637 lines). Defaults: auto-settle after 3 idle days and when the linked PR merges; closed PR can settle an idle thread; never auto-settle when pinned, archived, auto-settle-disabled for that thread, with a pending approval/question, a running run, live background work, or a queued turn start. Only the user's own messages count as resuming. runOnSettle project scripts (e.g. cargo clean) run when a worktree thread settles. The 'woke' state is computed client-side from wokeAt vs lastVisitedAt (Sidebar.tsx ~L1589). Agents can settle threads through the MCP too.
- **Reception:** The ordering/lifecycle is one of the most-documented parts of the product and has a hard design rule (every way in needs a way out). Issue #5534 asked for unsent drafts to be real threads in the sidebar. No major complaints found about the model itself; complexity of the doc page (very long) is a mild signal.
- **Evidence:** docs/user/thread-sidebar.md; apps/server/src/orchestration-v2/ThreadSettlementService.ts (isAutoSettlementCandidate); apps/web/src/components/Sidebar.logic.ts (resolveSidebarThreadStatus L904, resolveSidebarV2TopStatus L936, planSidebarThreadDrop); apps/web/src/settleAndAdvance.ts; AGENTS.md 'Reverse states' rule: snooze needs unsnooze, close needs reopen

### Sidebar status semantics and the 'Working section' ordering (attention-status, confidence high)

- **What the user sees:** Status per thread: working (with elapsed time), waiting, approval, input (question), failed, limited (usage limit), ready/unread-done, woke. Optional beta 'Working section' folds working/monitoring threads into a collapsed group below the active list; a thread returns to the top of the active list when it finishes, fails, or needs approval/answer, ordered by 'when it last came back to you'. In that mode manual drag-reorder is disabled. Threads that are idle and read 'recede' visually; needs-input never recedes.
- **How it works:** resolveSidebarThreadStatus maps pending approvals/user-input (including a subagent's pending request) first, then runtime status; shouldRecedeSidebarThread dims working/read threads; resolveProjectStatusIndicator rolls up the highest-priority status per project. The server holds the authoritative runtime status; 'Working section' is a per-device client setting.
- **Reception:** Release notes: 'Working section (beta): busy threads stay out of the way until they need you.' Bugs about accuracy are the recurring theme: dev server left running made thread look 'waiting' (fixed in #15114), working timers reset on every background wake (#15029), runs stuck (#15048, #16449 still open).
- **Evidence:** docs/user/thread-sidebar.md ('Fold working threads (beta)'); apps/web/src/components/Sidebar.logic.ts L884-960, L1080-1175; apps/web/src/components/ThreadStatusIndicators.tsx

### Per-turn checkpoints, turn diffs, Edit-from-here and rollback (review-git, confidence high)

- **What the user sees:** Each completed turn has a diff of only that turn's own work (merged-in files from pulls/rebases are excluded), a diff panel with find, branch-comparison diff, PR review guide ('stops' with excerpts and attention notes). 'Edit from here' under any sent message rewinds the conversation, optionally also restoring workspace files (offered only for worktree threads, refused when another thread/agent uses the same directory).
- **How it works:** CheckpointStore -> GitVcsDriver.checkpoints.captureCheckpoint writes a hidden commit of the whole working tree (including untracked files) using a temporary index file (GIT_INDEX_FILE under the git common dir), under refs/t3/orchestration-v2/checkpoints, with fsync flags because unclean restarts left 0-byte refs. Handles sparse-checkout and racy-index timestamps (~hundreds of lines). Diff = git diff between two checkpoint refs; listAuthoredPaths filters pulled-in files. Rollback uses provider-native rollback: for Claude, resumeSessionAt a message id (resolveClaudeRollbackResumeSessionAt, ClaudeAdapterV2.ts ~L9018). Checkpoints attach to scopes: root-run checkpoints advance run count; subagent checkpoints are nested.
- **Reception:** Old checkpoints/diffs were NOT migrated from V1 to V2 (issue #14871). No complaints about the git-ref approach itself found; the capture code complexity is the visible cost. Skyflo's comparison page lists 'checkpoints you can rewind' as T3's documented strength.
- **Evidence:** apps/server/src/checkpointing/CheckpointStore.ts; apps/server/src/vcs/GitVcsDriver.ts L765-900; apps/server/src/orchestration-v2/CheckpointService.ts (CHECKPOINT_REFS_PREFIX); docs/user/composer.md ('Edit an earlier prompt'); docs/user/source-control.md ('Review turn changes'); packages/contracts/src/pullRequestReviewGuide.ts

### Fork, merge-back and Side Chat (ask without polluting the main thread) (context-knowledge, confidence medium)

- **What the user sees:** Fork any finished run (including failed/interrupted/limited); forks stay on the same provider by default and use native fork (Codex, Claude, Pi, OpenCode 2); merge a fork's context back into its source. Side chat is NOT in the stable release: community PR #18243 (open) adds /btw and /side, an 'Ask' button next to 'Cite' on selected reply text, a right-panel tab that shares the composer (banner 'Side chat', Esc returns to main), hidden from the sidebar, 'Allow edits' toggle because it shares the worktree, promote to thread, bring answer back to main, discard.
- **How it works:** Fork records app-level lineage first and resolves lazily at first run: native provider fork if same provider (Claude: SDK forkSession(sessionId, {upToMessageId}); ClaudeAdapterV2.ts ~L958/L9070), else portable context transfer (budgeted summary of messages; tool calls/reasoning are lost, release notes warn it is lossy). A side chat per PR #18243 is an ordinary V2 thread with a sideChat flag, forked from the parent's last FINISHED run so it never sees the in-flight run.
- **Reception:** Strong demand (earlier #9274, discussion #7311, PRs #9436/#9437 were closed during the V2 rewrite and re-requested). Maintainers had not merged any side chat as of 2026-10-17 (PR open). Claude Code's own /btw exists in the CLI, which is exactly the point: T3 reimplements it as a UI over fork.
- **Evidence:** docs/orchestration-v2/thread-lineage-and-context-transfer.md, feature-lifecycles.md; https://github.com/pingdotgg/t3code/pull/18243; https://github.com/pingdotgg/t3code/issues/15758 (closed, moved to discussion 18028; 17 reactions, '+1' from several users); apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts

### Composer: steer vs queue, server-side queue, stash, quote-cite, thread-as-context (chat-input, confidence high)

- **What the user sees:** Enter while a turn runs steers or queues according to a setting; Cmd+Enter does the opposite; Cmd+Shift+Enter sends the oldest queued message as a steer. Queued messages sit above the composer and can be edited, reordered by drag, promoted to steer, removed; they survive server restarts (held until you press Resume). Prompt stash (Cmd+S). Select text in a reply -> 'Cite in composer' with a comment. '@' or dragging a sidebar thread onto the composer attaches another thread as a reference chip: only an ID goes in the prompt and the agent reads the history on demand, so it costs nothing until read. /goal <definition of done> keeps the agent working across turns. ArrowUp recalls previous prompts. Slash menu lists skills; '$' picks skills.
- **How it works:** Message dispatch modes steer_active / restart_active / queue_after_active / start_immediately (feature-lifecycles.md); queue persisted server-side with command receipts. Thread references use the t3-thread://v1/<id> link form and the t3_thread_read MCP tool (bounded, incremental via afterPosition). Cross-environment drops export a bounded transcript file.
- **Reception:** Steer/queue is among the most-reacted feature issues (#231). Regression irritation: a default-on 'Compact' chip made Enter run /compact first on stale Claude threads (issue #17467, 14 reactions, closed 2026-10-09; earlier #15769) - a lesson that smart defaults that change what Enter does are resented.
- **Evidence:** docs/user/composer.md; docs/orchestration-v2/feature-lifecycles.md; https://github.com/pingdotgg/t3code/issues/231 (Steer and Queue; 77 reactions); docs/orchestration-v2/orchestrator-mcp-server.md (t3_thread_send auto/queue/steer/restart)

### Provider compatibility advisories and model manifest (other, confidence high)

- **What the user sees:** Settings -> Providers shows per provider: installed version, 'behind latest', and a compatibility advisory (supported / limited / outside supported range / known broken, with a recommended version). The model picker lists models that need a newer CLI with the exact upgrade version. A one-click update action runs the provider's own updater.

### Usage, usage limits and 'Limited' recovery (usage-cost, confidence high)

- **What the user sees:** Usage page across providers (tokens, cache savings, API-equivalent cost by model and speed tier, custom/mapped model prices). Composer shows limit windows. ### Remote and mobile through the same server; outside agents over MCP (remote-mobile, confidence high)

- **What the user sees:** Phone app (iOS/Android) and browser connect to the desktop or a 'service installed' server (t3 service install, launchd/systemd) over Tailscale/LAN pairing links or T3 Connect tunnels; approve, steer, queue offline, voice input, scheduled tasks, push notifications. ### Per-thread worktrees, one-button commit/PR, project scripts (parallel-worktrees, confidence medium)

- **What the user sees:** Each thread can start in a new worktree on a generated branch (prefix t3/, semantic prefix, or custom naming instructions that may include issue IDs), reuse the previous worktree (mod+shift+l), fan one prompt out to several models each in its own worktree, run project scripts (t3.json: runOnWorktreeCreate setup, runOnSettle cleanup), link a PR to the thread, merge controls follow check status. ## UX patterns worth borrowing

- Reverse-state rule: every verb has an inverse and is undoable for 5 seconds with a toast (pin/unpin, settle/un-settle, snooze/wake, archive/unarchive); mod+z triggers the last Undo when no text field is focused (docs/user/thread-sidebar.md, AGENTS.md).
- Drag between sidebar sections performs the state change and the dragged row shows the verb it will perform (Pin, Unpin, Settle, Un-settle, Wake), with labels only while dragging (Sidebar.drag.ts, planSidebarThreadDrop).
- Stable manual order of active threads: new thread on top, activity never reorders; the alternative 'Working section' mode orders by when a thread last came back to you and disables manual order. Two explicit, predictable modes rather than a blended heuristic.
- Status dot vocabulary that distinguishes approval (amber), input/question (indigo), working (sky, pulse + elapsed), limited, failed, woke; project rows roll up the highest-priority child status (THREAD_STATUS_PRIORITY).
- Settle-and-advance: finishing a thread moves selection to the next one (settleAndAdvance.ts) so triage is a keyboard loop; Cmd+1..9 jumps to the first nine displayed threads; Cmd+K palette searches commands, projects and threads (message search from 2 chars).
- Composer as a stack of banners (ComposerBanner slots: approval, user input, plan follow-up, queue, usage-limit recovery, server update, side chat) with priority and dismiss behaviour; approvals appear in the composer position, not as modal dialogs.
- Chips inside the text for context (terminal excerpt, review comment, preview annotation, file, PR, other thread); copy/paste carries chips and what they reference.
- Tool activity folded under 'Worked for <duration>' with summarised tool groups; full command and output only when a row is expanded (and only then does live output stream).
- Thread reference as a link the UI resolves to the current title (t3-thread://v1/<id>), so renames never leave stale references.
- Panel host with tabs on the right (Diff, Files, Preview, thread details, subagents/lineage), a maximize toggle and keyboard focus rules (docs/user/keyboard-focus.md); a 'when' expression language for keybindings (composerFocus, turnRunning, terminalFocus...).
- Hover cards on thread rows (ThreadHoverCard.tsx) and a 'jump hint' overlay after a short delay (THREAD_JUMP_HINT_SHOW_DELAY_MS = 200).

## Anti-patterns

- Reimplementing the CLI over the SDK creates a permanent parity treadmill: skills, slash commands, plugin skills, CLAUDE.md, MCP tool names/icons, workflow tasks, Auto mode, /goal, /compact all needed bespoke work and still show bugs (#1283, #5622, #4544, #2736, #15448). Loom's real-CLI-in-PTY contract avoids this class entirely.
- Owning the permission path means owning its security bugs: Auto+Plan silently approving plan-mode writes (#15503); 'Agents can't approve their own requests' had to be an explicit rule.
- No independent liveness check: runs stuck 'running' for hours (#16449), thread bricked by Stop before init (#15854), 'steers' and 'queues' racing. A hook/registry-based status with a silence watchdog (Loom today) is stronger.
- Process ownership is Linux-only (systemd slice). On macOS there is no containment, and parallel worktree test runs crashed a 32 GB Mac (#20329). Spawned process groups are killed by SIGKILL on CLI exit, a weaker guarantee than Loom's run scope.
- Hidden surfaces that keep working: closed-panel Electron previews burning 228% CPU / 10 GB GPU (#14730), a GPU leak to 21 GB (#13610), a 5-second server scheduler tick, a 250 ms poll of a private Claude temp file, 'idle shells reloading every project once a minute' (fixed in #14893).
- Smart defaults that change what Enter does: default-on Compact chip making Enter run /compact first (#17467, #15769 before it). Users want explicit actions; show information (cache cold, N tokens) but do not change the meaning of send.
- Lock-step upgrades: a V2 server and a V1 app refuse each other; every desktop, server, background service and phone app must be updated; V1 -> V2 is a one-way DB copy and does not carry old checkpoints, diffs, tool activity, approvals or plans (#14871, 60 comments, 77 reactions). Provider minimums are hard (Claude 2.1.280+).
- Own copy of the transcript in a second database (statev2.sqlite) next to Claude's JSONL means two sources of truth, migration pain, bloat (#16428 ACP tool_call_update persisted per delta) and a 'Reclaim database space' repair flow (t3 doctor). I found no code that deletes Claude's own session files when a thread is deleted (unverified).
- Dependency on a policy-volatile path: the Agent SDK and claude -p moved in and out of subscription limits during 2026 (restriction announced for 2026-04-04, a separate monthly API-credit pool planned for 2026-06-15, and an Oct 7 2026 help-center update about monthly API credits for Max/Team that an Anthropic employee on HN says did not remove claude -p from subscriptions). The T3 tracker shows users forking to a PTY adapter in response (issues #2680, #2958). State is still murky as of 2026-10-17 (unverified details).
- Speed reports versus the native CLI (#695: Codex 4m35s vs T3 15+ minutes; Claude users report ~3x slower) persisted for months; a wrapper adds latency and loses model-specific toggles (no thinking option for some models).
- Feature breadth outrunning stability: six providers, two orchestrators, six git hosts, scheduled tasks, voice, previews, T3 Connect; thousands of PRs in 17 days; Plan mode was removed after telemetry showed use fell to 2.5% of sessions (reported by the third-party Skyflo page, unverified).

## Ideas for Loom

### Park / Snooze / Pin lifecycle for sessions with Undo and 'park and go to the next one needing me'. Loom-owned metadata only (pinned, parked, snoozed-until), a Parked shelf in the activity view, 5-second Undo toast, and a keyboard verb that parks the current session and jumps to the next Needs-approval/Finished-unviewed one (Cmd+J exists). Snooze 'until my plan limit resets' reuses the reset time Loom already reads from get_usage. (cost M)

- **Inspired by:** T3 Code thread lifecycle (docs/user/thread-sidebar.md; ThreadSettlementService.ts; settleAndAdvance.ts)
- **Gain:** With 8-15 sessions the Active list fills with 'done but not worth deleting' cards. A cheap, reversible 'I am done with this for now' verb keeps the list equal to 'things that need or may need me', and the undo removes the fear of misclicks.
- **Fit:** Fits: pure local state, no polling. Auto-settle by age should be evaluated lazily when the sidebar is shown or on a single one-shot timer to the next due time, not a ticking scheduler. Never auto-settle a session that has a pending approval, a running subagent or a live process (T3's isAutoSettlementCandidate list is a good checklist). Skip T3's PR-merge auto-settle unless Loom later learns PR state. Keep one stable manual order (T3's 'activity never reorders' rule) and offer the 'Working group' fold as a separate view option.

### Side session ('ask aside') as a real CLI fork in a right panel. A button/shortcut opens a second real Claude CLI with --resume <id> --fork-session in a right-hand pane, attached to the parent card (hidden from the sidebar list, shown as a child row like subagents), closed = process stopped and (optionally) its transcript left to normal retention; actions: promote to normal session, copy answer back to the main prompt, discard (delete its data with the existing permanent-delete dry run). A lighter first step: a one-key 'Ask aside' that types /btw into the main PTY, because Claude Code already ships /btw. (cost M)

- **Inspired by:** T3 Code side chat PR #18243 (forks the parent at its last finished run; 'Allow edits' toggle; promote / bring back / discard) and issue #15758
- **Gain:** Directly delivers the user's long-standing wish (ChatGPT/Claude-style side thread that does not pollute the main context) without changing what the CLI is.
- **Fit:** Fits the process-ownership and fidelity rules if the side session is a Loom-owned PTY in its own run scope that exists only while the panel is open (no idle live terminal, resumable by id). Verified flags: claude --help on 2.1.300 lists --resume and --fork-session. Cautions: a fork only sees what is flushed to the transcript, so a running turn is invisible (same as T3's 'last finished run' rule; say so in the UI); the fork shares the worktree so default it to read-only guidance ('do not edit files') rather than pretending to enforce it; the fork pays prompt-cache cost if the cache is cold.

### Session-as-context reference: drag a session card into another session (or use a 'Reference session' command) to paste a small, bounded reference: the transcript path plus a generated markdown digest (title, last N turns, truncated tool bodies, files touched) written under a Loom-owned cache, never the whole transcript. The receiving agent reads the file on demand. (cost S)

- **Inspired by:** T3 Code '@thread' chips and t3_thread_read (docs/user/composer.md 'Another thread can be context too': only an ID goes in the prompt, the agent reads history on demand)
- **Gain:** Gives the user's multi-session workflows (work project A feeds a fix in project B, a planner session feeds an implementer) a handoff that costs no tokens until used and needs no new messaging channel. It is also the safest first step toward the planned cross-session channel.
- **Fit:** Strong fit: user-initiated and explicit (cross-session action under the user's authority), read-only, bounded, no daemon. Reuse the incremental transcript reader Loom already has. Skip T3's cross-environment export complexity. Risk: leaking secrets from a transcript into another project's context; show a preview of what will be referenced.

### Read-only orchestration verbs plus a privilege ceiling for loom:open-session. Extend the authenticated socket with read verbs (list sessions in this project, status of session X, wait until session X leaves Working) answered from Loom's hook-derived state with no approval prompt, while any mutating verb (open, send message, stop) keeps the user-approval card. Child sessions opened by an agent may not get a broader permission mode than the caller. (cost M)

- **Inspired by:** T3 Code orchestrator MCP: delegate_task, t3_thread_list/read/wait, runtime-mode ceiling, per-session scoped credentials (docs/orchestration-v2/orchestrator-mcp-server.md; outside-agents.md Read-only default)
- **Gain:** Lets a coordinating agent sequence work ('start the migration session, wait for it to finish, then run tests') using Loom's trusted status instead of guessing, which is the part of multi-agent workflows that currently needs the user to babysit.
- **Fit:** Fits if 'wait' is event-driven from hook transitions (no polling) and the credential is per session, short-lived and revoked on stop (T3's McpSessionRegistry model). Conflict: T3 lets agents send/steer other threads with only a mode ceiling; Loom's rule (cross-session actions only under the user's authority) means sends stay behind explicit approval, possibly with an 'allow for this session pair' grant the user can revoke. Do not copy delegate_task's hidden child threads; Loom's children should stay visible sessions.

### Per-turn checkpoints as a read-only 'What did this turn change' view. On the Working -> Idle/Finished transition (hook event, no polling) capture a hidden git ref of the working tree via a temporary index (refs/loom/checkpoints/<session>/<n>), then diff consecutive refs for a per-turn diff and file list in the detail pane. Start view-only; defer restore. (cost L)

- **Inspired by:** T3 Code CheckpointStore / GitVcsDriver.checkpoints.captureCheckpoint (apps/server/src/vcs/GitVcsDriver.ts L765+), listAuthoredPaths, docs/user/source-control.md
- **Gain:** Fills Loom's biggest daily gap (no diff/review view) with the one mechanism that is correct regardless of which tools the agent used, and attributes changes to a turn instead of to the branch.
- **Fit:** Event-driven and bounded: needs a size/time cap, skip non-git directories and giant repos, run off the main thread, and do nothing for idle records. T3's capture handles sparse checkout, racy index timestamps and fsync of refs, which shows the edge cases; budget for them or limit to simple repos first. Restore/rewind should stay with Claude's own /rewind to avoid desyncing the CLI from files. Hidden refs in the user's repo need a documented prefix and cleanup (T3 has deleteCheckpointRefs).

### Compatibility advisories without pinning: a tiny signed 'known-bad CLI versions and feature thresholds' JSON (bundled with each Loom release, optionally refreshed once at launch with a conditional request and a bundled fallback), shown only as a non-blocking banner with a recommended version and as an explanation when drift detection fires. Also show the installed CLI vs latest version. (cost S)

- **Inspired by:** T3 Code ModelManifest.ts + providerCompatibility.ts (statuses supported / graceful / unsupported / broken, recommendedVersion, per-model minVersion)
- **Gain:** Turns the current silent 'missing CLI option' drift detection into an actionable message ('2.1.2xx breaks hook X, use >=2.1.2yy') and avoids hours of debugging a CLI update.
- **Fit:** Compatible with 'never pin' only if it is advisory: never block or disable a session by version, and never claim success from a version number alone (capability checks stay primary). A single conditional fetch at launch is not polling. T3's own use as hard minimums (Claude 2.1.280+) is the pattern to avoid.

### Usage-limit actions on a session: when a session stops on a plan limit, offer 'Continue at reset' (a one-shot timer to the reset time Loom already knows, then resume the same conversation and send an explicit continue prompt) and 'Snooze until reset' (Parked until then). Surface prompt-cache coldness as information only: 'cache likely cold, ~N tokens' on a session idle past the cache TTL, with a one-click /compact the user chooses, never changing what Enter does. (cost M)

- **Inspired by:** T3 Code Limited state with Resume at reset / Snooze until reset / Auto-resume (docs/user/thread-sidebar.md) and the Compact chip (docs/user/providers-claude.md), including the backlash in issue #17467
- **Gain:** Overnight or between-window work resumes by itself under the user's explicit choice; the user stops tracking reset times by hand.
- **Fit:** One timer per scheduled item (no polling) is fine, but a delivered continue must be verified by the prompt-submit hook and Loom must be running at reset time (no daemon after Quit, so say so, as T3 does: 'the environment must be running'). The user opts in per session; no global auto-resume default. Avoid the compact-on-Enter default entirely.

### Chat-style read-only 'Conversation' tab for the main session, built the way the subagent transcript panel already is: render Claude's JSONL as folded turns ('Worked for 22s', tool groups, command rows expanded on demand) next to the terminal, optionally with a composer that submits through the PTY only when hook status says Idle or Waiting. Raw tool bodies are not loaded until a row is expanded; nothing renders while the tab is hidden. (cost XL)

- **Inspired by:** T3 Code MessagesTimeline (fold rows, tool group summaries), expanded-row-only live output (CommandOutputHub), bounded cold open of ~75 rows / ~1 MiB (docs/internals/performance-regressions.md)
- **Gain:** Gives the readability of a chat UI for long agent runs and for catching up on a session that finished while away, while keeping the real CLI as the input and execution engine, and with no Agent SDK dependency.
- **Fit:** Compatible with the contract if the terminal remains the source of truth and the chat view is a lens. Costs: transcript format is Claude's private JSONL (schema drift risk, so parse defensively and degrade to 'cannot render this record'); injecting input into a PTY is only safe in known states, so gate it on hooks and verify delivery. Do NOT drive Claude via stream-json/SDK to get a composer: that is T3's parity treadmill and ties Loom to the SDK's policy volatility.

- Do not attribute the claude -p statement to 'an Anthropic employee': the HN page shows only username luketaylor with no verified affiliation. The Oct 7 2026 monthly API credits item is confirmed on support.claude.com release notes.
- #695 is originally a Codex vs T3 speed report, not Claude; Claude slowness is anecdotal +1 comments from before V2.
- Plan mode was moved to a legacy setting (off by default), not deleted, and the 9%->2.5% figure is a Skyflo secondhand citation of Theo.

### Missed by the report

- Primary policy text the report cites but does not quote: code.claude.com/docs/en/legal-and-compliance says developers building products, including those using the Agent SDK, should use API-key auth; Anthropic does not permit third parties to offer Claude.ai login or route requests via plan credentials on users' behalf or collect/intermediate Claude.ai credentials. It also explicitly allows running the unmodified Claude Code binary where the end user signs in with their own subscription, and forbids modifying the binary or removing/restricting its auth methods. Directly relevant to Loom's real-CLI-in-PTY model (clearly on the permitted side) versus T3's SDK path (gray area in wording, even though T3 uses the user's own local binary/login).
- T3 uses the user's Claude config and login: docs/user/providers-claude.md ('T3 Code uses Claude Code's login and configuration'); multiple Claude provider instances via CLAUDE_CONFIG_DIR per account; conversation state stays isolated per config dir. Useful multi-account design reference. Capabilities probe loads settingSources user/project/local (ClaudeProvider.ts L196-201).
- Permission modes also include 'plan' and 'dontAsk' (read-only sandbox policy) in permissionModeForClaudeRuntimePolicy, and a CLAUDE_READ_ONLY_ALLOWED_TOOLS allowlist; the report only lists the four user-facing modes.
- T3 injects its own MCP server t3-code into every Claude session (allowedTools mcp__t3-code__*) and appends a T3 orchestration instruction block to the claude_code system prompt (L1155-1161): it alters the agent's tool set and system prompt, which a fidelity-first host like Loom would not do.
- Plan mode is now a legacy setting off by default since 2026-08-07 (Skyflo, third party); the docs also say 'Settings > Providers' shows version too old messages.
- Main branch is already at 0.1.1 preview/nightly (2026-10-17); stable v0.1.0 was published on 2026-10-15 so everything about V2 stability has had about 2 days in the field.
- Docs lag code in at least two places (MCP injection docs show query-option mcpServers while code uses setMcpServers; pin vs auto-settle), so docs/user pages alone are not a reliable spec for T3 behavior.
- Anthropic help center (support.claude.com release notes, Oct 7 2026) added monthly API credits for Max ($100 on 5x, $200 on 20x per a Threads post, secondhand) and Team, claimed via a linked Console org; this is the real source of the billing question for SDK-based hosts.
