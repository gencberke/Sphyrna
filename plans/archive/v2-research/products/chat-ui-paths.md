# Theme: Technical paths to a chat-style / structured UI over real Claude Code from a native Swift macOS app (PTY+JSONL, persistent stream-json, Agent SDK, ACP, official attach interfaces, hybrids), plus side-chat mechanics and the 2026 billing/terms situation

Research note for the Loom v2 brainstorm ([index](../V2-BRAINSTORM.md)). Written by a research subagent on 2026-10-17 and fact-checked by a second one; the fact-check is at the end and wins over the report where they differ. Raw JSON: `../evidence/deep-dive-20261017.json`.

## Summary

Researched 2026-10-17 against primary docs, the published SDK typings (@anthropic-ai/claude-agent-sdk 0.3.302 = Claude Code 2.1.302), and shallow clones of claude-agent-acp, Paseo, T3 Code, Orca, Ghostex, Agent of Empires and Codex. Recommendation: stay PTY-first, and add the structured UI in two layers. (1) A read-only structured transcript decoded leniently from Claude's JSONL for every session. (2) An opt-in Chat mode backed by a Loom-owned `claude -p --input-format stream-json --output-format stream-json` child spoken to directly from Swift, with no Node, SDK or ACP. Only one process owns a conversation at a time, so switching modes is stop plus `--resume`. This is the same pattern Anthropic documents for CLI to Desktop handoff and that Agent of Empires uses. Reasons: the stream-json control protocol is the only structured interface that is typed (published in the SDK .d.ts), versioned (init `capabilities`), gives an authoritative `session_state_changed` (idle/running/requires_action), and needs no extra runtime. JSONL is explicitly CLI-internal and unstable per the SDK typings. Screen scraping, as Ghostex does, costs about 5k lines of Rust for Claude alone and is pinned to specific CLI versions. Billing: as of 2026-10-17 Anthropic's support page says the Agent SDK, `claude -p` and third-party apps still draw from subscription limits. The change that would have moved them to a separate metered credit was paused on 2026-06-15 'for now'. The headless path is exactly the surface that change targeted, so keep the interactive PTY as default and fallback and isolate Chat mode behind an explicit switch with error-category detection. Side chat: Claude's own mechanisms are `/btw` (TUI, in-memory, no tools), Desktop side chat (Cmd+;, not saved to disk) and an undocumented `side_question` control request. For Loom, use `side_question` when feature-detected on a Chat-mode process. For PTY sessions, use a Loom-owned ephemeral fork: `claude -p --resume <id> --fork-session` with a Codex-style boundary message, deleted on close. ChatGPT web has no in-thread side chat (only 'Branch in new chat'); Codex has `/side`, an ephemeral fork.

- **Resource and ownership facts for (b). A resident Claude Code process (a prewarmed spare with no session context) holds roughly 230-260 MB, per the official SDK docs; a real session holds more. ## Options

### A1. PTY stays; add a read-only structured transcript view decoded from Claude's JSONL (any session, live or ended) (cost M)

- **How:** Generalize Loom's existing subagent transcript tailer: FSEvents-driven, incremental, bounded reverse-tail read of ~/.claude/projects/<cwd>/<id>.jsonl; lenient decoder that renders known record types (user, assistant text/thinking/tool_use/tool_result, subagent sidechains, compact boundaries, titles) and shows unknown ones as collapsed raw blocks; SDK getSessionMessages semantics as the reference shape. A 'Chat | Terminal' toggle in the detail pane, with the PTY untouched. Input still goes to the terminal.
- **Pros:** No new process, no billing exposure (interactive CLI), preserves 'real CLI, real PTY' contract, works for ended sessions (replaces the static ended-screen with a real transcript), enables cross-session transcript search later, nothing is drawn when hidden, and the decoder degrades gracefully.
- **Cons:** Schema is CLI-internal and can change in any of ~26 releases a month; per-message rather than token streaming is likely (unverified); read-only, so the composer cannot be added without option A2; images/tool results can be large (need lazy loading).
- **Loom fit:** Excellent: reuses existing code, event-driven, bounded, accurate status stays hook/registry-based, update-resilient if decoder is lenient and covered by recorded-fixture tests per CLI version.

### A2. A1 + chat composer that types into the PTY, approvals/questions via documented hooks (Ghostex-style) (cost L)

- **How:** Composer submits via bracketed paste + Enter into the PTY when Loom's own status says idle (or queue). Approval cards answer through a Loom hook command (PermissionRequest allow/deny; PreToolUse allow+updatedInput for AskUserQuestion and ExitPlanMode) that blocks on Loom's authenticated socket. Everything dialog-like that is not covered by hooks is left to the terminal.
- **Pros:** Keeps one live PTY owner, so every TUI feature, slash command and dialog still works; hooks are documented; no billing change.
- **Cons:** Input fidelity is the weak point: busy/dialog/Ink-composer states, multi-line paste, images, double-Escape rewind trap; Ghostex needed ~5k lines of screen scraping for Claude alone. Unverified: hook vs TUI dialog concurrency. /model, plan-mode, effort pickers remain TUI dialogs.
- **Loom fit:** Acceptable only for a bounded subset (text send, approve/deny, AskUserQuestion). Do NOT adopt screen scraping: it violates update-resilience and 'never report false success' (a paste you cannot verify).

### B. Loom-owned persistent `claude -p --input-format stream-json --output-format stream-json` child per Chat-mode session, spoken directly from Swift (cost XL)

- **How:** Spawn the user's installed `claude` in the existing Loom run scope with pipes (no PTY): `-p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --replay-user-messages --forward-subagent-text --include-hook-events --session-id <uuid>` (or `--resume <id>`), no `--bare`. Implement a small Swift NDJSON client + control-protocol state machine from the SDK .d.ts: initialize, can_use_tool (via `--permission-prompt-tool stdio` as the SDK does, or via hooks), interrupt, set_model, set_permission_mode, get_context_usage, rewind_files (checkpoints), stop_task, side_question (feature-detected). Status from `session_state_changed`; drift handled via init `capabilities`/`claude_code_version` and unknown-message passthrough. Stop the process after idle and `--resume` on next send. Switch to terminal = verified stop, then PTY `claude --resume <id>` (and vice versa).
- **Pros:** Typed, versioned, additive protocol (the SDK transport, so Anthropic keeps it stable); true token streaming, tool cards, diffs, images, queued messages, accurate idle/running/requires_action, typed approvals/questions, model/effort/plan switching, usage/cost, checkpoints/rewind, subagent tree with parent ids. No Node. Loom already runs this mode for get_usage and has a fake-provider test harness.
- **Cons:** Headless surface = the one billing policy targeted (paused, not cancelled); sessions are tagged programmatic (hidden from terminal /resume; registry presence unverified); TUI-dialog commands and agent teams unavailable in this mode; ~230-260 MB per resident process (official spare figure); `--permission-prompt-tool stdio` is SDK-internal; `--bare` unusable; two owners must never run on one session id.
- **Loom fit:** Best technical fit for a chat-centred UI that respects lightness (stop-on-idle), process ownership (pipes, same run scope, verified stop), accurate status, and update resilience (capability negotiation + lenient decoding). Contract change: Loom would no longer render the CLI's own interface in this mode, so make it an explicit per-session mode with PTY as default/fallback.

### C. Claude Agent SDK (TypeScript/Python) embedded via a Node/Bun helper (cost M)

- **How:** Bundle a Node/Bun runtime and the SDK package; the SDK spawns the claude binary (bundled or `pathToClaudeCodeExecutable`) and exposes query()/canUseTool/listSessions/forkSession/startup().
- **Pros:** Fastest way to get all protocol features and docs-aligned behavior; TS-only helpers (forkSession file copy, startup/prewarm, SessionStore).
- **Cons:** Adds a runtime and an app-pinned SDK version (SDK/CLI protocol pairing is yours to keep current); duplicates what Swift can do directly; extra process layer complicates verified-stop and the 40%-of-a-core budget; same billing exposure as B.
- **Loom fit:** Poor. If the structured engine is wanted, B reaches the same protocol without the runtime.

### D. ACP via claude-agent-acp (Zed) with a Swift ACP client (swift-acp or own) (cost XL)

- **How:** Spawn the Node adapter, which spawns the Agent SDK/claude; Loom speaks ACP (session/new, prompt, request_permission, session/fork, subagent sessions RFD).
- **Pros:** Open protocol with fork/resume/list RFDs; would give other agents (Codex frozen) a uniform path; Apple's Xcode 27 and Zed use it, so the ecosystem is active.
- **Cons:** Node 22+ and a several-hundred-MB adapter tree; adapter lags CLI features; two translation layers (CLI to SDK to ACP) between Loom and the facts; SDK billing exposure; unverified-stop risk across adapter plus claude children; Claude's CLI has no native ACP.
- **Loom fit:** Poor for Claude-only Loom today; revisit only if multi-provider support returns and a native ACP agent for Claude ships.

### E. Lean on official attach/observe interfaces: `claude agents --json`, hooks, Channels, Remote Control, /desktop (cost S)

- **How:** Use hooks (already used) for status/approvals; optionally cross-check state with `claude agents --json` only on demand; evaluate Channels as a future native input/permission-relay path once custom channels can be allowlisted; hand sessions to Desktop via `claude --desktop --resume <id>` as an escape hatch.
- **Pros:** Documented, Anthropic-owned; Channels would give a typed push path into a live interactive session.
- **Cons:** No local API for attaching to an interactive PTY; Agent view needs a surviving supervisor daemon (violates Quit semantics) and is polling-oriented; Remote Control is claude.ai-only; Channels is research preview and custom channels need a dev flag plus warning dialog each launch.
- **Loom fit:** Supporting role only; not a UI engine. Watch Channels (permission relay) as the cleanest future input path for A.

### SC1. Side chat on a Chat-mode (option B) process via the `side_question` control request (cost S)

- **How:** Send `control_request {subtype: side_question, ...}` to the live stream-json process; render the answer in a right-side panel; progress via `control_request_progress`. Feature-detect (init capabilities / unknown-subtype error) and fall back to SC2.
- **Pros:** Exactly Claude's own /btw/Desktop semantics: same process, same cache, no tools, nothing written to the transcript, usable mid-turn.
- **Cons:** Undocumented request shape (only the progress message and changelog mention it); could change or vanish; no tool access (by design).
- **Loom fit:** Good as a feature-detected fast path, worst case it silently disappears and SC2 takes over.

### SC2. Side chat as an ephemeral fork: `claude -p --resume <id> --fork-session` with a Codex-style boundary first message (cost M)

- **How:** Spawn a Loom-owned read-only child that resumes a COPY of the session (new session id), first user message = boundary text ('everything above is reference only; answer the question; do not mutate'), then the question; keep it in a right panel with its own multi-turn thread; on close, stop the child and delete the fork's JSONL via Loom's existing verified permanent-deletion path. Use a restrictive tool set (e.g. read-only allowedTools, `--permission-mode plan` or dontAsk) and put the boundary in the message, not the system prompt, so the cached prefix is unchanged.
- **Pros:** Works for PTY-mode sessions too (no TUI overlay needed); multi-turn and can use read-only tools; forks are tagged programmatic so they stay out of the user's /resume list; mirrors Codex's shipped `/side` design.
- **Cons:** A new session file exists temporarily (must be cleaned up and kept out of Loom's session list); prompt-cache sharing with the PTY session is unverified (a miss re-bills the whole history); unverified whether `--fork-session` combines with `--no-session-persistence` and whether forking a session that is mid-turn in another process is safe.
- **Loom fit:** Good: bounded, explicit, user-initiated, verified cleanup. Experiment first.

### SC3. Type `/btw` into the PTY / SC4 hand-copy the JSONL under a new session id (cost S)

- **How:** SC3: write `/btw question` into the PTY and show nothing in Loom. SC4: copy the transcript file and rewrite ids to resume a copy.
- **Pros:** SC3 is trivial. SC4 avoids a model call at fork time.
- **Cons:** SC3 gives Loom no structured answer (overlay only; screen scraping needed). SC4 rewrites a CLI-internal format and can corrupt or orphan sessions on any schema change; Anthropic's supported file-level fork is `forkSession()` (Node) or `--fork-session`.
- **Loom fit:** Reject both.

## Recommendation

Recommended path, in order. (1) Ship A1 first: a lenient, incremental, read-only structured transcript for every session, reusing the subagent-transcript machinery. It is the cheapest big win (an ended session becomes readable, searchable and exportable), carries zero billing or ownership risk, and gives a real chat-looking surface without touching the PTY. Keep the decoder tolerant, because the JSONL schema is declared CLI-internal; test it with recorded fixtures per CLI version and show unknown records as raw collapsed blocks rather than dropping them. (2) Build option B as an explicit per-session 'Chat mode', not a replacement for the terminal. It is a Loom-owned stream-json child spoken to directly from Swift: no Node, no Agent SDK, no ACP. Use the typed control protocol from the published SDK typings as the spec, feature-detect through init `capabilities` and `claude_code_version`, treat unknown message and request types as passthrough, and take status from `session_state_changed`. Mode switching is stop plus `--resume`, with exactly one process owning a session id, which is the Desktop/Agent-of-Empires pattern. Stop idle Chat processes (about 230-260 MB each) and resume on the next send. Keep PTY as the default and fallback. (3) Do not do screen-scraping input/dialog automation (Ghostex-style). If a composer is wanted inside PTY sessions before B exists, limit it to plain-text send plus hook-based approvals (A2 subset). (4) Skip C (Node runtime for no new capability) and D (extra adapter layer, Node, SDK billing exposure) for Claude. Reconsider D only if multi-provider returns. (5) Side chat: build it as a right-side panel with two backends. SC1 (`side_question`) when the session is in Chat mode and the request is feature-detected. SC2 (ephemeral `--resume --fork-session` child with a Codex-style boundary message, read-only tools, deleted on close) for PTY sessions and as the fallback. Run the experiments below before committing to SC2. Billing guardrails for B and SC2: use only the user's own signed-in `claude`, never read or forward tokens, never use `--bare`, surface the init/`api_retry` error categories (`billing_error`, `oauth_org_not_allowed`, `authentication_failed`) as drift rather than as failures, put a visible kill switch on Chat mode, and re-read support article 15036540 before each release. Anthropic paused the metering change 'for now', and the Oct 7 article still allows subscription use, but the headless surface is where policy has moved four times in ten months.

## Open questions

- Does a stream-json child (in a throwaway CLAUDE_CONFIG_DIR, never the real ~/.claude) appear in Claude's session registry that Loom reads, fire the existing hooks, and which `entrypoint` does it stamp? Can `CLAUDE_CODE_ENTRYPOINT` be set to `cli` so it shows in terminal /resume, and is that even desirable?
- JSONL write granularity: is each assistant content block flushed as it completes (enabling near-live chat in A1), or only whole messages? What is the latency from tool_use to its JSONL line?
- Does a PermissionRequest hook run concurrently with the TUI dialog (so the user can still answer in the terminal), does answering in the TUI cancel the pending hook, and does a pending hook block the dialog? This decides whether hook-based approval cards in PTY sessions are safe.
- Is `side_question` advertised in init `capabilities`, what is its exact request/response shape on Claude Code 2.1.302, does it persist anything to the transcript, and does it work on a session resumed but not yet turn-complete (an SDK 0.2.89 fix mentions a null result)?
- SC2 experiments: does `--resume <id> --fork-session` work while the parent session is mid-turn in another process; does it combine with `--no-session-persistence`; does the fork reuse the parent's prompt cache (compare cache_read_input_tokens in the result usage) given -p system-prompt/tool-set differences; and does it leave junk under ~/.claude/projects that Loom's deletion path must clean?
- Does `/btw` (TUI) ever write to the JSONL or to the session registry? The docs say it never enters conversation history, but on-disk evidence is unverified.
- How does Anthropic distinguish headless usage for metering (entrypoint, `origin: sdk`, user-agent)? Would a persistent stream-json child with a human typing be classed as 'Agent SDK / claude -p' if the paused plan is revived? The May 13 article lists 'Claude Agent SDK, claude -p, third-party apps'. Ask or watch support article 15036540 and the ClaudeDevs account.
- Per-process memory and idle CPU of a resident stream-json child mid-session versus a TUI process, measured under Loom's 40%-of-a-core budget.
- Is `--permission-prompt-tool stdio` stable? It is what the SDK emits but is absent from the CLI reference. Decide between it, an MCP permission tool Loom ships in its plugin (documented), and hooks-only approvals. Also confirm the exact control_request/response envelopes against a recorded session from the fake-provider harness.
- Channels permission relay: will Anthropic allowlist user-built channels or add a non-warning local-development path? If so, a Loom channel could deliver composer text and permission prompts into a live interactive session cleanly (the best long-term input path for A).
- Product question for the user: is Chat mode meant to replace the terminal in daily use (then B must reach parity on skills/MCP/hooks/plugins loaded in headless, which `--bare` would not) or is it a convenience view (then A1 plus SC2 may be enough)?

### Corrections

- session_state_changed is opt-in. The SDK changelog says 0.2.83 made it opt-in via CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1, and the 0.3.280 entry still names that variable. The sdk.d.ts typing does not mention the env var. The summary and option B say status 'from session_state_changed' as if it were always emitted. A Loom-owned child must set the variable and verify on the target CLI version. Otherwise status has to come from result/assistant messages and hooks.
- Do not present the 230-260 MB figure as the cost of a Chat-mode process. Official wording is 'A spare holds roughly 230 to 260 MB of memory while it waits': a parked process before cwd, CLAUDE.md, SessionStart hooks and session context load. A live session is likely higher. The report's own 'unverified' note is right; the summary and pros/cons lines are looser.
- Issue anthropics/claude-code#6686 closed on 2026-02-09 with state_reason not_planned, not 2026-02-19.
- The 'terms risk is low' framing leaves out parts of the same legal page. It says advertised Pro/Max limits 'assume ordinary, individual usage of Claude Code and the Agent SDK'. It says OAuth is 'designed to support ordinary use of Claude Code and other native Anthropic applications'. It says developers building products 'including those using the Agent SDK, should use API key authentication'. It also forbids customers to 'remove, disable, or restrict any authentication method built into' the binary. The unmodified-binary-with-own-subscription carve-out exists, but those sentences show Anthropic can enforce at its own discretion ('may do so without prior notice'). The Apr 4 email also said the harness policy 'applies to all third-party harnesses and will be rolled out to more shortly'.
- The summary's 'Agent of Empires uses stop plus --resume' is overstated. AoE runs Claude through the ACP adapter, and its terminal view is tmux-based. Claude's native transcript is reused only when AoE can bind the ACP ID to a shared native store; other agents 'start fresh under the new view'. It supports one-owner-at-a-time but is not evidence for a pure --resume handoff.
- `/btw` is 'in-memory only' only in the terminal. In the VS Code extension chat panel the /btw thread survives window reloads on the retention schedule (docs, v2.1.227+). Desktop side chat is unsaved.
- The AskUserQuestion/ExitPlanMode hook-answer path is documented in the -p context (permission host, 'satisfies that requirement', the 'defer' flow). The claim that it works in INTERACTIVE sessions is an inference, not an explicit doc statement.
- Hook timeouts are not uniformly 600s: command/http/mcp_tool default to 600 but UserPromptSubmit is 30s, SessionEnd 1.5s, prompt hooks 30s, agent hooks 60s.
- The Oct 7 credits are API credits granted to a linked Console organization, not a subscription-limit change. They do not alter the subscription-vs-metered question for `claude -p` run with a subscription login.

### Missed by the report

- headless.md line 57: '`--bare` is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release.' Bare mode skips hooks, skills, plugins, MCP, CLAUDE.md and never reads OAuth/keychain. If that default flips, a Loom Chat child run with plain `-p` would lose subscription auth and the user's hooks, skills, MCP servers and memory unless Loom passes an opt-out flag. Add this to the drift watchlist. Source: https://code.claude.com/docs/en/headless
- headless.md line 30: without `--bare` a `-p` session runs the project's .claude/settings.json hooks and connects .mcp.json servers 'even in a folder you've never trusted', with no workspace-trust dialog and no per-server approval prompt. A Chat-mode child therefore bypasses the TUI's trust gate. Loom must show its own trust step or refuse untrusted folders. Source: same page.
- `defer` is a documented headless approval path: a PreToolUse hook returns permissionDecision 'defer', the process exits with stop_reason 'tool_deferred' and a deferred_tool_use payload, and the caller later runs `claude -p --resume <id>`. It works only for a single tool call per turn (hooks.md, 'Defer a tool call for later'). It is an option for AskUserQuestion without a live control channel.
- The `request_user_dialog` control request plus initialize.supportedDialogKinds (sdk.d.ts) lets a stream-json host render tool-driven blocking dialogs. A host must declare only the kinds it can render and must not answer unknown kinds. This partly closes the 'TUI dialogs unavailable' gap and shows the protocol is still growing.
- SDK changelog 0.3.280: 'Added `verbatimPrompts` option: prompts are delivered as written — no @path expansion, no slash-command dispatch ...' and 'Changed headless sessions to cancel an MCP server's pending form question when the tool call that drew it ends'. These are protocol behaviors to know about when Loom builds its own client.
- `--permission-prompts host|none` (v2.1.259+): the default `host` sends prompts to the SDK host or the --permission-prompt-tool tool; `none` denies them. It is the documented way to turn off prompts for unattended runs, and it clarifies the documented path for a hand-rolled client. Source: cli-reference.
- Sources for the unverified `side_question` shape do exist in the ACP adapter, but there is also a `control_request_progress` message with status 'started'|'api_retry', which Loom's decoder must tolerate. The sdk.d.ts text says the SDK passes unknown subtypes through ('Open set — ignore unknown values' for capabilities).
- Agent view CLI surface not named in the report: `claude --bg`, `claude attach <id>`, `claude daemon status|logs|stop [--keep-workers]`, and 'An attached session doesn't report its status to your terminal'. Idle unattended supervisor processes are stopped after about an hour. Source: https://code.claude.com/docs/en/agent-view
- The Zed blog update (June 16) says Anthropic told subscribers the change 'is not taking effect yet' and will 'share advance notice before any future change takes effect'. That gives a concrete watch signal, and the report's recommended 're-read article 15036540 before each release' covers it only partly.
- VS Code's /btw is a panel with a thread that persists, which is a closer precedent for a Loom side-chat panel than the TUI overlay. Anthropic's own Desktop also ships side chat as a panel (Cmd+;). Source: interactive-mode docs and desktop.md.
- Ars Technica's reader-comment (not Ars's own reporting) says the May 13 announcement claimed human-in-the-loop IDE use would not be affected, while Zed/Xcode/JetBrains all use the Agent SDK. This is unverified, but it is the open question for Chat mode: which signal Anthropic would use to class a human-driven wrapper.
