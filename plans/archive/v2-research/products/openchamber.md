# OpenChamber (openchamber/openchamber, "Agentic Development Environment" around OpenCode)

Research note for the Loom v2 brainstorm ([index](../V2-BRAINSTORM.md)). Written by a research subagent on 2026-10-17 and fact-checked by a second one; the fact-check is at the end and wins over the report where they differ. Raw JSON: `../evidence/deep-dive-20261017.json`.

**In one line:** An MIT-licensed Electron/web/mobile/VS Code front end for the OpenCode agent: chat-first, with a server-side control plane (goal loop, message queue, notifications, scheduling, relay) layered over OpenCode's API, shipping a release every one to three days.

**Category:** chat-first (a GUI harness front end; it does not host the agent's own TUI)

## Architecture

Stack: TypeScript monorepo (Bun, Node 24): packages/ui (shared React UI), packages/web (OpenChamber server + CLI), packages/electron (desktop shell, backend started in-process, not as a sidecar), packages/vscode, packages/mobile (Capacitor), packages/sdk (guest/extension contract). See AGENTS.md "Runtime Boundaries".

How it drives the agent: it never owns the CLI's TUI. It talks to a managed or external OpenCode server over HTTP + SSE through the generated @opencode/client. packages/web/server/lib/event-stream/global-hub.js keeps one shared upstream SSE hub with event-id replay and stall recovery; translate-v2.js maps OpenCode 2.x wire events to the server's own vocabulary; delta-coalescer.js merges part deltas; global-ws-bridge.js and directory-ws-bridge.js fan out to browsers over WebSocket.

State detection is authoritative from OpenCode events (session.status idle/busy/retry, permission and question events). Server runtimes (session-goal, message-queue, notifications, session-assist, session-work) all subscribe to the same hub. AGENTS.md "Correctness Invariants": derive live activity from live channels, not persisted history; a fetch failure must never pass as an empty success. notifications/runtime.js does not announce "ready" on idle while a subagent of that session still runs.

Persistence: per-session state lives in OpenCode session metadata under `metadata.openchamber.*` (goal, work, btw link, review link); larger blobs are files under ~/.config/openchamber (goals/<sessionId>.md, chats/, queue). Metadata writes are decided inside a per-session write queue and guarded by id against stale writes (session-goal/DOCUMENTATION.md).

Terminal: a generic project terminal, not the agent. packages/web/server/lib/terminal/runtime.js uses node-pty/bun-pty; a v3 WebSocket protocol starts each attach with an authoritative snapshot (history + the PTY cols/rows it was drawn at); output is coalesced over 12 ms or 32,768 code units; history capped at 512 KiB. The client is libghostty compiled to WASM (root package.json script build:ghostty-wasm).

Remote: Private Relay (QR pairing, end-to-end encrypted), Cloudflare/ngrok tunnels, LAN, SSH. Native push uses APNs with sealed text (notifications/push-seal.js).

Resource notes (the weak point): Electron renderer + Node server + OpenCode process. Many freeze/memory/CPU issues: #3521 (RAM up to 97% of 16 GB), #4607 (freeze opening a long session), #2267 (all rows mounted, no virtualization), #3740 (terminal output blocked the Electron main process), #5023 (visible idle clients reload the global session list every 45 s, useGlobalSessionsPolling.ts), #4407/#3358 (duplicated MCP server processes), #3755 (/btw fork copied active goal metadata and froze the server). A commenter on #2539 reports about 6 GB average on macOS. v2.4.0 notes claim much lower idle CPU/GPU. Code read: packages/web/server/lib/{session-goal,message-queue,notifications,terminal,event-stream,quota,walkthrough,session-work}, packages/ui/src/{lib/btw.ts,lib/sessionBtwMetadata.ts,lib/multirun,components/multirun,components/chat}.

## Core loop

1. Open a project in the sidebar (Tree or List view; "In work" and "Pinned" blocks on top). Start a session from a typed prompt, a GitHub/Linear issue or PR, a todo or a plan, optionally in a fresh worktree.
2. Send a prompt. For long jobs arm the Session Goal target button and the server keeps continuing the agent while you are away. Messages sent while the agent is busy are queued or steer it. Side questions go to a /btw panel.
3. Watch the sidebar and work-status card for working / waiting (shield or question-mark icon) / done. Desktop and phone notifications fire on permission, question, error and goal-settled. HN commenters describe checking in from a phone while commuting or walking, then finishing at a desk.
4. Review: Git tab or Changes panel with line comments sent back to the composer, optional AI Changes Walkthrough, optional auto-review loop; then commit, push, open a PR, merge. Failed CI checks and PR review comments go back to the agent.
5. Mark Done, or leave it In work.
Occasional: multi-run across models with Keep or Fusion, scheduled task or loop file, browser-panel annotation, Mini Chat (floating window with a global shortcut).

## Features

### Session Goals (auto-continue with an independent progress check) (automation, confidence high)

- **What the user sees:** A target button in the composer arms goal mode; the next prompt becomes the objective. A strip above the composer shows objective, status (active, paused, blocked, budget reached, complete), tokens used and pause/resume; while the check runs it shows Evaluating. The sidebar row gets a small coloured target glyph. Per-turn ready notifications are suppressed while a goal runs and you get one notification when it settles. The loop keeps going after you close the tab as long as the server runs.
- **How it works:** packages/web/server/lib/session-goal/runtime.js subscribes to the global SSE hub. session.status idle arms a 15 s per-session timer (IDLE_QUIET_MS = 15_000; kickoff 3 s; Resume about 250 ms). On fire, tick: (1) re-reads live activity and bails if the parent resumed or any subagent is active; (2) loads recent messages; (3) accounts tokens as a snapshot of the latest completed assistant turn (input + cache.read + output), segmented at compactions; (4) hard stops: assistant turn error -> blocked, tokensUsed >= tokenBudget -> budgetLimited, turnsUsed >= cap (default 20, setting 1-200) -> blocked, repeated output truncation -> blocked; (5) otherwise audit.js asks a small model (or the Jev classifier) three yes/no questions (all_done, remaining, needs_user) about ONLY the objective and the last assistant turn (head 2,000 + tail 8,000 chars); decideProgress: needs_user >= 0.5 blocked, all_done >= 0.5 and remaining < 0.5 complete, else continue. If the checker cannot run twice in a row the goal is blocked, so a dead checker never drives the loop blind. Continuation POSTs /api/session/:id/prompt with an XML-escaped objective block and an instruction to end every turn with a done/verified/remaining report, because that report is the checker's only evidence. A user abort pauses the goal in the event path before any tick can send a continuation over the stop. The objective text is stored in a file keyed by session id and metadata only says objectiveFile:true, so user-writable metadata cannot become a file-read vector. The same mechanism serves scheduled tasks and `openchamber session create --prompt ... --goal`. Doc inconsistency: public session-goals.mdx says blocked needs three consecutive auditor verdicts, while session-goal/DOCUMENTATION.md says complete and blocked settle on the first answer; the code doc is likelier current (not verified in code).
- **Reception:** HN: the walk-away workflow is described as working most of the time, not always. Risk signals: #3755 (/btw fork inherited an active goal and spiralled CPU/memory) and the cap/budget machinery itself. The authors' own lab (144 hand-written turns): classifier 142/144 with both misses on the safe side, small model 141/144 (self-measured, not independent).
- **Evidence:** packages/docs/content/docs/session-goals.mdx; packages/web/server/lib/session-goal/runtime.js (IDLE_QUIET_MS, KICKOFF_QUIET_MS, DEFAULT_MAX_AUTO_TURNS, auditFailStreak); packages/web/server/lib/session-goal/audit.js (QUESTIONS, THRESHOLD, excerptAnswer); packages/web/server/lib/session-goal/DOCUMENTATION.md; HN 49233448: commenter milkshakes feeds detailed initiatives to /goals and steers from the phone, "working pretty well in most cases, but not always"

### /btw side chat (a fork that does not pollute the main thread) (chat-input, confidence high)

- **What the user sees:** Typing /btw <question>, or selecting text and choosing By the way, opens a panel floating above the composer in the same session. The question is answered in a side thread that carries the whole conversation as context. The panel can be collapsed to a chip (the composer talks to the main session again), promoted to a normal session, or destroyed. The fork is hidden from the sidebar. If the main session raises a permission/question while the panel is collapsed, that request takes the dock so the parent never waits on a request nobody can see.
- **How it works:** packages/ui/src/lib/btw.ts: forks the parent via the SDK (opencodeClient.forkSession(parentId, {before: lastCompletedAssistantMessageID})), so a /btw typed mid-turn does not inherit a half-streamed turn (findLastCompletedAssistantMessageID). The fork is marked in metadata (openchamber.kind='btw', originalSessionID, btwBoundaryMessageID) BEFORE insertion in local stores so it never flashes in the sidebar; the parent gets openchamber.btwSessionID so the panel is derived from authoritative metadata and survives reloads (lib/sessionBtwMetadata.ts, components/chat/btw/useBtwPanelState.ts). Every message in the fork carries a synthetic BTW_BOUNDARY_INSTRUCTION: inherited history is reference only, do not continue any task/tool call from it, no subagents, do not modify files unless asked inside the btw session. The panel renders only messages after the boundary id (filterBtwTailMessages, by position not id comparison). Promotion adds a BTW_PROMOTION_NOTICE to later sends because old constraint text cannot be removed from the transcript. destroyBtwSession unlinks the parent, deletes the fork and returns false if the server could not confirm deletion. Defaults: agent 'plan' (read-only), model copied once from the main composer.
- **Reception:** No HN praise or complaint specifically. Bug trail: #3755 (open as of 2026-10-17) and the v2.4.0 fix for a parent stuck on an unseen request. It is the closest match to the user's long-standing side-chat wish, and shows the failure modes to design out: inherited plan hijacking the fork, hidden pending requests, leaked state.
- **Evidence:** packages/ui/src/lib/btw.ts (BTW_BOUNDARY_INSTRUCTION, findLastCompletedAssistantMessageID, filterBtwTailMessages, destroyBtwSession); packages/ui/src/lib/sessionBtwMetadata.ts; packages/ui/src/stores/useBtwStore.ts; packages/ui/src/components/chat/composer/DOCUMENTATION.md (BTW composer); https://github.com/openchamber/openchamber/issues/3755; v2.4.0 release note: question or permission request shows while a BTW is collapsed

### Multi-run, Keep and Fusion (parallel-worktrees, confidence high)

- **What the user sees:** Run on several models (model picker) or Run in parallel (palette) opens a launcher: project, group name, prompt, up to five models, and an isolate-runs toggle giving each lane its own git worktree and branch. A Run overview shows one card per lane with status, final reply and diffstat. Per lane: Keep (adopt this lane, archive the others). Fusion lets a judge model merge the strongest parts into a new session; auto-fusion can run when all lanes finish. Ask other models can be applied to a first turn after the fact.
- **How it works:** packages/ui/src/components/multirun/RunOverview.tsx and lib/multirun/*. Lane reply and diffstat are read once per finished turn (useLaneSummaries.ts keys on time.idle changing: no polling; a read failure is its own state, never an empty result). Keep (lib/multirun/keep.ts) snapshots the lane's complete work to a private git ref refs/openchamber/runs/<group>/<session> BEFORE removing its worktree and reports per-lane failures (snapshot-failed, worktree-in-use...). Fusion (lib/multirun/fusion.ts) inlines diffs into the judge prompt only while they stay under 10% of the judge's context window, otherwise the judge reads them with git. One failed lane does not block the others.
- **Reception:** Reviews praise it as a way to pick models on your own tickets and compare cost; no negative reports found specifically. It is a multi-model feature, so less relevant for a Claude-only host, and by design costs N times the tokens.
- **Evidence:** packages/docs/content/docs/multi-run.mdx; packages/ui/src/lib/multirun/keep.ts (runSnapshotRef); packages/ui/src/lib/multirun/fusion.ts (INLINE_DIFF_CONTEXT_SHARE); packages/ui/src/lib/multirun/useLaneSummaries.ts; https://sevmatic.com/en/2026/09/openchamber-the-control-room-for-ai-coding-agents/; LinkedIn Kaushik Gopal post lists multi-run as one of three reasons to pair OpenCode with OpenChamber

### Changes Walkthrough (AI-guided diff reading order) (review-git, confidence high)

- **What the user sees:** An optional panel that turns a diff into ordered stops, each with a one- or two-sentence explanation and the exact code, tagged Key change or Context (where to spend attention), with no verdicts or severities. Scopes: all uncommitted, staged, unstaged, this branch, pull request. Nothing generates until you press Generate. Stops whose code has since changed are marked Outdated; hunks no stop describes are listed as Not covered. Line comments flow back to the composer.
- **How it works:** packages/web/server/lib/walkthrough/* (digest.js, hunks.js, schema.js, store.js, jobs). Results are cached against the exact diff content plus model and language, so returning the tree to an earlier state returns the earlier walkthrough free. Generation runs server-side and survives closing the panel; Cancel is the only stop. Lockfiles/generated files stay out of the model input and are listed as not covered. A model too small for the diff is refused with an explanation instead of silently truncating (a walkthrough written against half a diff reads as confident and is wrong). Regeneration re-authors with the old walkthrough as context and re-anchors to current code.
- **Reception:** HN: one commenter loved the idea and still reads everything that gets committed. Sevmatic review: a real gain for extensive agent changes. No complaints found. Not offered on mobile or VS Code.
- **Evidence:** packages/docs/content/docs/walkthrough.mdx; packages/web/server/lib/walkthrough/ (digest.js, hunks.js, store.js, schema.js); HN 49233448: epistasis, "Oh, I love the idea of a changes walkthrough" and still reads all committed code

### Sessions In work, done hint, recap and next-message suggestion (attention-status, confidence high)

- **What the user sees:** Any session you send a message in goes into an In work block at the top of the sidebar and stays until you mark it Done (check button); a later message reopens it. Pinned sessions have their own block, and pins sync across devices. Optionally a small classifier flags This work looks done with a Mark done button (it never closes anything itself). After a quiet minute a small model can write a recap under the last reply and a suggested next message that fills the composer but never sends itself. Rows show a shield for a pending permission and a question mark for a pending question.
- **How it works:** packages/web/server/lib/session-work/runtime.js and state.js: metadata.openchamber.work = {state open|done, openedAt, openedBy, doneAt, suggestDoneAt}. Invariants: a sent message only opens, nothing automatic ever writes done; writes are decided inside the per-session write queue so a user's Done is never overwritten; a turn-end check is bound to its turn via a counter so a late answer about a past turn writes nothing. Excluded: chats, archived sessions, review sessions, btw forks, scheduled runs. Recap/suggestion is gated by a cheap classifier question first (session-assist/*) so the small model is not called when nothing is useful. Classifier calls are limited to 4 s and fail to the safe side.
- **Reception:** No direct HN comment. Product churn visible: v2.3.0 dropped the Recent view and simplified to every message puts a session in work. (HN user epistasis wishes Orca could hide old worktrees for a week without deleting; not about OpenChamber.)
- **Evidence:** packages/docs/content/docs/sessions-in-work.mdx; packages/web/server/lib/session-work/DOCUMENTATION.md; v2.3.0 release notes (every message you send puts a session in work); v2.4.0 release notes (pins follow you across devices)

### Queue, steer and the composer's top rows (chat-input, confidence high)

- **What the user sees:** While the agent is busy you queue messages (reorderable rows with edit and send-now) or steer. Queue, active goal, staged revert and auto-review stack as rows above the composer. Large pastes offer attach-as-file. Background shell commands get a strip with Stop all. Long messages fold behind Show full message; typing anywhere moves focus into the composer.
- **How it works:** The queue is server-side: packages/web/server/lib/message-queue/runtime.js stores items captured at queue time (text, attachments, context chips, sendConfig {provider, model, agent, variant}) so delivery never re-resolves mutable UI state, and sends the next one the moment the session goes idle, so a closed tab or locked phone does not strand it. Public snapshots strip megabyte payloads and keep a 100-char preview. Skills named with $name are attached to the prompt rather than appended mid-turn, so they ride the prompt's own delivery.
- **Reception:** Release notes show queue regressions fixed in 2.3.0 and 2.4.0 (order, hidden delivery, Enter semantics), so this area is bug-prone. No HN commentary.
- **Evidence:** packages/web/server/lib/message-queue/DOCUMENTATION.md; packages/ui/src/components/chat/QueuedMessagesStrip.tsx; v2.3.0 release notes (queue rows; Enter in an empty composer no longer sends the whole queue into the running turn; queued messages reached the model hidden and out of order)

### Agent control tool (an agent creates sessions and worktrees) (orchestration, confidence high)

- **What the user sees:** From chat the agent can list projects/models/sessions, create or fork sessions (optionally in a new worktree), send follow-ups, read another session's latest reply and manage scheduled tasks. Sessions it starts show up in the sidebar. It cannot delete sessions/worktrees, register project paths, run arbitrary shell commands or call arbitrary URLs. v2.3.0/2.4.0: when the branch is busy the agent decides to move itself into a worktree, taking along only the files it changed.
- **How it works:** packages/web/server/lib/agent-tool/runtime.js materializes a custom tool in the managed OpenCode config, authenticated to the OpenChamber server over loopback; actions are a fixed dispatch to the CLI (openchamber session create|send|fork). On by default with a Settings toggle; unavailable with an external OpenCode server or in VS Code.
- **Reception:** No community reaction found. Compared with Loom's loom:open-session: broader (send, read, schedule), on by default, no per-action user approval; Loom approves each open.
- **Evidence:** packages/docs/content/docs/agent-control-tool.mdx; packages/web/server/lib/agent-tool/runtime.js; v2.3.0 and v2.4.0 release notes (Agents)

### Permission modes and the safety net (attention-status, confidence high)

- **What the user sees:** A shield button in the composer cycles per-session modes: Ask every time, Safety net (a small classifier lets routine actions through and holds risky ones, with a line on the permission card saying why), Accept everything. The mode lives on the server, so requests keep being answered after you close the tab. Permission cards offer Deny / Allow once / Always only where each applies.
- **How it works:** packages/web/server/lib/permission-auto-accept (server authoritative, UI renders a projection). The classifier has a 4 s limit and a failed check never allows an action (fail-closed to asking you). Subagents follow their parent's mode.
- **Reception:** HN commenter sbysb argues dedicated sandboxing tools beat any mode toggle for unattended agents; no feedback specifically on the safety net.
- **Evidence:** packages/docs/content/docs/permissions.mdx; packages/docs/content/docs/classification-providers.mdx; v2.3.0 fix: Always allow no longer behaves like Allow once

### Browser panel with annotation, agent-driven browsing and dev-server preview (browser-preview, confidence high)

- **What the user sees:** A globe button opens a real Chromium page beside the chat (desktop app). Annotate offers Element, Region and Draw tools; you add a note, press Attach, and the chat message gets a card with your marks, note and a screenshot with the marks drawn on it. Running dev servers are found by what is actually listening and listed for one-click open. The agent can open, read, click, type and scroll, switch mobile/tablet layouts, and save screenshots into .openchamber/screenshots/. Cmd+Opt+R runs saved project actions (dev server, tests) with URL auto-open from terminal output.
- **How it works:** Electron guest pages (packages/electron/browser-panel-security.mjs, guest-frame-navigation.mjs); annotation never modifies the page; the agent browses via the OpenChamber Web tool (packages/web/server/lib/browser-control); camera/mic/location are refused; dev-server discovery in packages/web/server/lib/dev-servers.
- **Reception:** Cited as a reason to use ADEs; commenters note several products have it, so it is table stakes rather than differentiating.
- **Evidence:** packages/docs/content/docs/desktop-browser.mdx; packages/docs/content/docs/preview.mdx; packages/docs/content/docs/project-actions.mdx; HN 50097612: a user picked the desktop app because its built-in browser can be fully controlled by the agent; HN 49233448: vulture916, taoh and reverius42 discuss select-an-element-and-comment across Orca, Paseo and OpenChamber

### Remote access and mobile (Private Relay, PWA, native apps, mobile terminal) (remote-mobile, confidence high)

- **What the user sees:** Pair a phone with a one-time QR code (per-device revocable token); reach the same sessions via Private Relay (no open ports), LAN/VPN, Cloudflare/ngrok tunnel or SSH. Push notifications on approvals, questions, errors and goal completion; pins and sessions sync across devices. The app shows per server whether it is reachable and whether over LAN or relay. A terminal with touch scrolling that works on a phone.
- **How it works:** packages/web/server/lib/relay and ui-auth; notifications/push-runtime.js (web push, VAPID), apns-runtime.js (central relay by default, direct fallback), push-seal.js (the phone gets a generic title and the real text encrypted with AES-256-GCM under a key it registered). Mobile terminal scroll is a hand-written pointer state machine in packages/ui/src/components/terminal/TerminalViewport.tsx: gesture idle/pending/scrolling/selecting, 8 px slop, 350 ms long-press selects a word, pixel deltas become scrollLines(n) with the fractional remainder carried over, touch-none + pointer capture on the container.
- **Reception:** Mobile is the main reason people cite. Opposing view on HN (throwatdem12311): doesn't want work in the pocket. Open issues on relay latency (#4836); an idle phone asking the server every 5 s was fixed in v2.4.0. Note the praised terminal is a generic shell terminal, not the agent's TUI.
- **Evidence:** packages/docs/content/docs/mobile.mdx, private-relay.mdx, connect-devices.mdx; packages/web/server/lib/notifications/DOCUMENTATION.md; packages/ui/src/components/terminal/TerminalViewport.tsx (enableTouchScroll effect); HN 49233448: jonotime, only Paseo and OpenChamber handle mobile terminal scrolling well; kyriakos uses OpenChamber on the go; dionian prefers Blink; issue #4836 (iOS on relay, 5 s+ sync delay, open)

### Usage and quota with a pace indicator (usage-cost, confidence high)

- **What the user sees:** Settings Usage page and a header dropdown: per signed-in provider a bar for the current window, a breakdown by model, and a pace indicator (on track to run out or not). A context ring in the right rail fills as the session's context fills; its tooltip shows tokens, limit and session cost.
- **How it works:** packages/web/server/lib/quota/providers/claude/index.js calls https://api.anthropic.com/api/oauth/usage with the OAuth credential Claude Code already holds (header anthropic-beta oauth-2025-04-20), with a last-good cache keyed by a credential fingerprint, Retry-After-driven cooldown (default 5 min, max 60 min) and a single pending fetch. This uses an undocumented endpoint and reuses the CLI's token, unlike Loom's get_usage control request through the CLI itself.
- **Reception:** A Reddit commenter liked seeing 5-hour, weekly and monthly usage next to the chat. Accuracy bugs exist (#4901).
- **Evidence:** packages/docs/content/docs/usage.mdx; packages/web/server/lib/quota/providers/claude/index.js (USAGE_URL, DEFAULT_COOLDOWN_MS); v2.3.0 release notes (context rail ring); issue #4901 (Copilot usage row contradicts GitHub's panel)

### Chat UI design: calm live replies, collapsed activity, panels around the chat (navigation-ux, confidence high)

- **What the user sees:** A streaming reply appears one paragraph or list item at a time, and the chat stops auto-scrolling at the start of a long reply so you can read it from the top. With Activity collapsed, a working turn shows the latest 7 steps and a +N more count. Every tool row is a one-line header by default (the global expand edit/bash tools by default option was removed in v2.3.0 after it froze long sessions; users complain in #4840). A subagent is one tool row with live time, an open action and a Stop button. A work-status card to the right of the chat shows state, branch, quotas and subagents. Terminal, files, diffs, browser and plans can be dragged right, left or under the chat; Shift-click a session opens a second chat column; header tabs reuse one temporary tab while you click through sessions. Sidebar has Tree and List views with sticky project headers.
- **How it works:** components/chat/message/parts/{ProgressiveGroup,ToolPart}.tsx and components/chat/work-status/DOCUMENTATION.md. The work-status card is deliberately not a panel surface and measures the chat AREA, not the chat column, to avoid a resize oscillation when it shows or hides. Stopping a subagent first admits a non-resuming synthetic note, because interrupting the child alone makes the parent see a failed subagent and restart it (opencodeClient.stopSubagent, message/parts/DOCUMENTATION.md).
- **Reception:** HN 50097612: prefers a GUI to illegible terminal walls of text, unrendered markdown and a poor prompt box; a reply defends keyboard-driven terminals. Reddit: some find the UI cluttered. Long-session render performance complaints are persistent.
- **Evidence:** v2.3.0 and v2.4.0 release notes; packages/ui/src/components/chat/work-status/DOCUMENTATION.md; packages/ui/src/components/chat/message/parts/DOCUMENTATION.md; issues #4607, #4840, #2267, #4200

### Scheduled tasks, loop files and the auto-review loop (automation, confidence high)

- **What the user sees:** Scheduled tasks run a prompt once, daily, weekly or by cron, each run in a new session, with a Run as goal option. Loops are cron prompts kept as markdown files in .agents/loops/ (project or user scope), off by default, needing a local opt-in again after a change to schedule, model or prompt. They fire only while the OpenChamber server runs. An auto-review loop pairs the implementer with a read-only reviewer session, forwarding messages between them until nothing important is left, with a max iteration count and Stop on the composer strip.
- **How it works:** packages/web/server/lib/scheduled-tasks/{runtime.js,loops.js}; auto-review state is a persisted store, packages/ui/src/stores/useAutoReviewStore.ts (phase waiting_for_reviewer|waiting_for_implementer, iteration, maxIterations).
- **Reception:** No community reaction found.
- **Evidence:** packages/docs/content/docs/scheduled-tasks.mdx; packages/ui/src/stores/useAutoReviewStore.ts; packages/ui/src/components/chat/AutoReviewStrip.tsx

## UX patterns worth borrowing

- Composer top rows: queue, goal, staged revert, auto-review and background-command strips stack above the input, one panel at a time in a floating dock (ComposerFloatingPanel) that never resizes the transcript. A pending permission/question always outranks a collapsed side panel (btwHoldsDock).
- Session-scoped state as small sidebar glyphs: goal target coloured by state, shield for pending permission, question mark for pending question, grey check for looks done, and an In work block that holds what you have not marked done.
- Fork-based side thread: fork at the last COMPLETED turn, mark the fork before it can appear in lists, render only what follows the boundary, collapse to a chip, promote or destroy.
- Honest staleness in generated content (walkthrough marks Outdated and Not covered; refuses a model too small rather than truncating): never present partial derived data as complete.
- Read-once-per-finished-turn derived summaries (lane reply and diffstat keyed on time.idle) instead of polling; a read failure is a distinct state, not empty.
- Safe-destructive pattern: snapshot a lane's work to a private git ref before removing its worktree, and report per-item failures.
- Reading ergonomics for long replies: stream by paragraph, stop auto-scroll at the start of a long reply, collapse activity to the latest N steps with a +N more count, collapse tool rows by default.
- Panels as movable zones (left/right/under the chat) with state kept when moved; second chat column via Shift-click; temporary header tab reused while clicking through sessions.
- Pace indicator next to a usage bar (on track to run out or not), and a context ring with tokens/limit/cost in the tooltip.
- Mini Chat floating window summoned by a global shortcut for a quick question outside the main window.
- Cmd+P command palette plus per-action keyboard dialogs (Cmd+Opt+R project actions); every shortcut searchable in Settings.
- Notifications: suppress per-turn ready alerts while an automated loop runs and send one when it settles; skip a ready notice on idle while a subagent still runs.

## Anti-patterns

- Resource creep: Electron + Node server + OpenCode with many freeze/memory issues (#3521, #4607, #2267, #4200, #3740, #5023, #4407, #3358; commenter on #2539 reports around 6 GB on macOS; HN Squarex needed reboots after hours). Loom's no-polling, bounded-read, nothing-drawn-when-hidden principles are exactly the missing discipline.
- Mounting all history: long sessions mounted every message and tool row (#2267); an expand-all-by-default option froze the UI and had to be removed (#4607), which then caused a UX-regression complaint (#4840). Window, lazily mount and bound before offering expansion.
- Periodic polling in a visible idle client (global session list every 45 s, #5023; phone asking every 5 s until v2.4.0).
- Duplicated MCP and OpenCode child processes per directory or chat, and a worktree deletion leaving its OpenCode instance running (#3358, #4407, #3764): a process-ownership failure Loom already designs against.
- Fork inherits too much: /btw copied active goal metadata and froze the server (#3755); promotion cannot erase old constraint text from the transcript. Strip control metadata on fork and keep boundary instructions revocable.
- Feature creep and churn: 160-service integrations catalog, voice, tunnels, relay, extensions SDK, Linear/GitHub/GitLab boards, 30 releases in 10 weeks; HN calls it feature creep with 50+ npm dependencies and a Conductor clone; Reddit calls the UI cluttered and buggy.
- Presentation: an AI-looking marketing page with scroll hijacking, a top background that flickers, an overlapping sticky header on mobile, and a hard-to-find statement that it only wraps OpenCode (all HN, 2026-08).
- Hiding the harness dependency: HN complaint that it is a wrapper for OpenCode only is stated too late; per-harness products (Paseo) are preferred by multi-harness users.
- Reusing the CLI's OAuth token against an undocumented usage endpoint with aggressive rate-limit cooldowns (quota/providers/claude/index.js): fragile and risky for a Claude-hosting tool. Prefer the CLI's own interface.
- Autonomous loops without a hard cap are dangerous; OpenChamber needed a turn cap (20), a token budget, a fail-closed checker rule, three terminal states and user-stop-wins precedence.
- Recurring stale-state bugs in queue and model memory (order, hidden delivery, model resets to default on reopen) show the cost of keeping UI state and server state in two places.
- Public docs drift from code (goal blocked-after-three vs first verdict): a documentation-accuracy risk.

## Ideas for Loom

### Side chat as a fork of the real Claude session: a slide-over (or sidebar sub-row) that starts `claude --resume <id> --fork-session` from the last COMPLETED turn, wraps the first side message with a boundary instruction (inherited history is reference only, do not continue its plans or tool calls, no subagents, no file changes unless asked here), and offers Close (delete the fork's local data using Loom's existing verified permanent-deletion path) or Promote (becomes a normal session card, with a notice that the constraints are lifted). (cost L)

- **Inspired by:** OpenChamber /btw: lib/btw.ts (fork before last completed assistant turn, BTW_BOUNDARY_INSTRUCTION, BTW_PROMOTION_NOTICE, destroyBtwSession) and lib/sessionBtwMetadata.ts
- **Gain:** This is the user's long-standing wish: ask a question about the current work without polluting or blocking the main thread, and without losing the context. It avoids opening a new session and re-explaining. OpenChamber evidence suggests demand from heavy users but no direct praise quoted.
- **Fit:** Fits: it hosts a real Claude CLI process, it is user-initiated, and the fork is a Claude session (never replaces the CLI's interface; a PTY slide-over keeps the contract). Process ownership: the fork runs in a Loom run scope and Stop/Quit verifiably stop it; no live process for idle forks (the ended screen / read-only transcript is shown when it is not running). Resilience: relies on a documented CLI flag (--fork-session with --resume); detect drift if the flag is missing. Verified outcomes: only report forked/deleted after the new session id appears in the registry and files are gone. Conflicts: hiding the fork from lists needs a Loom-side marker (no hook writes metadata like OpenChamber does), so keep a Loom-owned sidecar record rather than editing Claude's files; a read-only chat-style transcript view for the side thread is the lighter variant before any composer. Check first (unverified here): whether this CLI version already offers a native side-question command that could be used instead.
- **Risks:** Cost: a fork re-reads the whole context (cache reuse across sessions unverified); doubling resource use if both threads run. The copied transcript may contain plans that the fork can wrongly continue (OpenChamber needs the boundary text on EVERY message; in a PTY Loom can only send the instruction once as the first message, so a long side chat can drift). Strip any Loom-owned goal or ticket-key metadata when forking (#3755 lesson). Writing to PTY needs state certainty (UserPromptSubmit hook can confirm delivery).

### User-armed Goal mode driven by Claude's own Stop hook: the user arms a goal for a session (objective text, token budget, turn cap default 20), and Loom's hook receiver answers the Stop event with a block+reason (the documented Stop hook decision interface) that continues the work, until a small independent check says done / needs-you / budget / cap. The check sees ONLY objective + the last assistant message; three yes/no questions decided in code. Stop button always wins and pauses the goal; per-turn notifications are suppressed while armed and one notification fires when it settles. (cost L)

- **Inspired by:** OpenChamber Session Goals: session-goal/runtime.js (tick, hard stops, abort-pauses-goal), audit.js (three questions, decideProgress), notifications suppression, and the lab-measured checker
- **Gain:** Removes the nudge-continue loop for long jobs and makes Loom the place you start a task and walk away from; the 'finished unviewed' blue state becomes more meaningful because it fires once at the end. HN users describe the walk-away + steer-from-phone workflow as the payoff.
- **Fit:** Event-driven, no polling: Loom already receives Stop hooks; there is no 15 s quiet-window timer needed because the hook IS the turn-end signal, which is lighter than OpenChamber's implementation and avoids races with subagents (Stop is per agent; check whether the hook fires for subagents separately, unverified). Cross-session actions only under user authority: arming is an explicit user act per session and visible on the card. Accurate status: a goal state (active/paused/blocked/budget/complete) shown on the card; a dead checker counts as blocked, never silently continues. Fluency: no extra confirmations beyond arming. Conflicts: Loom owns no model call today; the checker either shells out to `claude -p` with a small model (costs tokens, spawns a process; must run in a Loom run scope and be counted in usage) or stays heuristic. A lighter variant that skips the model check: continue until the agent's last message ends with a user-defined sentinel or the user stops. Also check first (unverified) whether Claude Code's native /goal already exists and could just be surfaced (an HN commenter mentions feeding tasks to /goals).
- **Risks:** Runaway spend and a loop fighting the user's own hooks; stop-hook blocks may behave differently across CLI versions (drift detection needed); checker misjudgment (their lab: ~98%, self-measured). Mitigate with caps and a fail-closed checker.

### Send-when-idle queue with verified delivery: let the user queue follow-up messages for a working session; Loom holds them in Loom's own store and writes the next one to the PTY only when the status says Idle, then marks it Delivered only after the UserPromptSubmit hook for that text arrives (otherwise show Not delivered with Retry). Reorder/edit/send-now rows live in a small strip above the terminal. (cost M)

- **Inspired by:** OpenChamber message-queue/runtime.js and QueuedMessagesStrip.tsx (items captured at queue time, delivered the moment the session goes idle), plus its recurring queue bugs
- **Gain:** Type the next instruction while the agent is still busy without it landing inside the running turn; cheap and always useful for heavy parallel-session users.
- **Fit:** Fits predictable behavior and verified outcomes: Loom already knows Idle vs Working from hooks and the registry; delivery is verified by a hook, never assumed. No daemon survives Quit, so the queue is dropped (or restored as drafts) on Quit and says so. No polling. Conflict with the 'never replace the CLI interface' rule is minimal (it is a prompt buffer, not a chat UI). Pitfall: writing into the TUI while it shows a permission dialog or a plan prompt would answer the wrong thing; only send on Idle/Ready, never on Needs approval.
- **Risks:** Pasting multi-line text into a TUI input has quirks across CLI versions (bracketed paste); OpenChamber's queue had hidden/out-of-order delivery bugs in 2.3.0, so test ordering and Escape/interrupt interplay.

### Explicit In work block with user-owned Done: a persisted per-session flag (open/done) that a sent message opens and only the user closes, shown as a section at the top of the sidebar above the Active section; Done is one click or key; a new message after Done reopens. Optional pin block. No classifier. (cost S)

- **Inspired by:** OpenChamber session-work/state.js and sessions-in-work.mdx (sent message only opens; the user alone closes; reopen only if the message is newer than doneAt)
- **Gain:** Loom's Active section is driven by agent activity (working/unread) and loses a session once it finishes and is viewed; In work is the user's own to-do list of sessions they are still responsible for. For someone with several projects and ticket keys this answers 'what am I in the middle of' without scanning day headings.
- **Fit:** Very cheap: a tiny Loom-owned store, no model call, no polling, no live process. Predictable: the same action always has the same meaning. Conflict risk: two overlapping lists (Active vs In work) can confuse; define precedence (in-work sessions are listed once, in In work) as OpenChamber had to (v2.4.0 fix: a pinned session appeared twice). Skip the classifier 'looks done' hint (a model call per turn; their own measurement is self-reported).
- **Risks:** Duplicates and stale membership if sessions are deleted or archived outside Loom; excluded kinds (subagents, scheduled) must be defined.

### On-demand diff view first, then an optional Changes Walkthrough: after a diff/review view exists (currently a gap), add a Generate walkthrough button that, only when pressed, runs a one-shot `claude -p` over the diff to produce ordered stops, cached by a hash of the exact diff + model, with Outdated and Not covered marks, lockfiles/generated files excluded, and refusal (not truncation) when the diff exceeds the model's window. (cost XL)

- **Inspired by:** OpenChamber walkthrough/* (digest.js, hunks.js, store.js) and walkthrough.mdx; HN praise from epistasis
- **Gain:** Reviewing agent-written changes is where time goes for someone running several sessions; reading in a sensible order and getting a map of key changes cuts review time. The cache makes a revert-and-retry free.
- **Fit:** Cost model fits: nothing generates unless asked, no polling, nothing drawn when hidden, results cached on disk. The honesty rules (stale marks, never present partial data as complete) match accurate status. Conflicts: needs the large prerequisite diff view (git diff, comment-back-to-session) and a model call via the CLI (spawn, process ownership, usage accounting); do not do this before the plain diff view proves useful. Lighter first step: just the diff view with per-line comments that paste back into the session.
- **Risks:** Biggest cost is the prerequisite; model output that sounds confident but is wrong if anchoring fails; token cost on big diffs.

### Transcript conversation view for idle and ended sessions: replace the static 'ended screen' with a lazily windowed, read-only chat-style rendering of the session's transcript (extending the existing subagent transcript panel), collapsed tool rows by default, 'latest N steps' for a working turn, stop auto-scroll at the start of a long reply. Sending a message from it resumes the real CLI session. No live process while idle. (cost L)

- **Inspired by:** OpenChamber chat design (collapsed activity, latest 7 steps with +N more, paragraph-wise streaming, scroll stops at the start of a long reply) and its performance failures (#2267, #4607: all rows mounted; global expand-by-default removed)
- **Gain:** A finished or stopped session becomes readable like a chat (markdown rendered, searchable) without running a process or keeping a terminal, which is also what the user wants for 'sessions that cost nothing when idle'. It is the path toward the chat-centred UI the user is open to without abandoning the real CLI.
- **Fit:** Directly serves the low-resource principle if built with windowing: bounded reads from the local transcript, FSEvents-incremental, nothing drawn when hidden. OpenChamber's lesson is to NEVER mount all history and never offer expand-all by default. Conflicts: the CLI-interface contract (still a read-only view; live sessions keep the PTY). Needs a transcript schema that tolerates CLI changes (drift detection).
- **Risks:** Transcript format changes between CLI versions; large sessions (tool outputs) need truncation with 'show full'; rendering markdown must be cheap.

### Annotated browser panel as a lazily created WKWebView: element/region pick with a note, producing a screenshot with marks saved to a file and the file path plus selector/styles sent to the Claude session (pasted as a message). The panel is created only when opened and destroyed when hidden. (cost L)

- **Inspired by:** OpenChamber desktop-browser.mdx (Element, Region, Draw annotation, screenshot with marks, 'this button, a bit rounder') and the HN note that this is table stakes
- **Gain:** For frontend-adjacent work, replaces describing where a UI element is; but the user is backend-focused, so the gain is moderate.
- **Fit:** Costs nothing when closed if the WKWebView is torn down when hidden; no polling. Conflict: a browser engine is the heaviest component Loom would own (it contradicts 'sessions cost nothing' if left open), and the agent-driven browsing half is a separate large security surface; skip agent-driven browsing. Prefer a smaller variant: a screenshot-region-to-prompt capture (system screenshot into a file path inserted into the prompt) before any embedded browser.
- **Risks:** Security of embedded pages; keyboard focus conflicts with the terminal; scope creep toward a browser.

### Extend loom:open-session into a small, user-authorized cross-session surface: read-only list and status of Loom sessions, read the latest result of a named session, and send a follow-up message to a named session, each requiring a one-time approval per session pair (or per request) in Loom, with the result of delivery verified via hook and shown on both cards. No schedule or delete actions. (cost M)

- **Inspired by:** OpenChamber agent control tool (agent-tool/runtime.js: create, fork, send, read, list; fixed actions; cannot delete or run arbitrary shell) and the auto-review loop (implementer and reviewer forwarding messages)
- **Gain:** Enables the planned orchestration pattern (a coordinating agent drives sub-sessions in other projects, or an implementer/reviewer pair) while the user keeps one place to approve and watch it. The user already runs multi-agent workflows with ticket keys.
- **Fit:** Matches 'cross-session actions only under the user's authority' only if approval is mandatory: OpenChamber's tool is on by default with no per-action approval, which Loom should NOT copy. Keep the fixed action list, loopback authenticated socket (already exists), de-duplication by ticket key. A reviewer loop must have a visible iteration cap and Stop (their AutoReviewStrip has maxIterations).
- **Risks:** Prompt injection through one session's output causing actions in another; message loops; approval fatigue (mitigate with per-pair approval that persists until Stop or Quit).

### Corrections

- Do not say OpenChamber only wraps OpenCode with no Claude Code path. It ships a 'Claude Code' integration (Settings -> Integrations, docs integrations.mdx) that installs the third-party 'opencode-claude' plugin as an OpenCode provider (provider id claude-code). Sessions are still OpenCode sessions and OpenChamber never renders or hosts the Claude Code TUI, so the 'chat-first, no TUI' categorisation stands, but Loom's ground (real Claude CLI sessions) is touched by it.
- The integration doc claims the plugin 'uses Anthropic's official Claude Agent SDK and your installed Claude Code CLI' and 'stays on Anthropic's supported access path'. That is the vendor's own claim, unverified here, and sits uneasily with Anthropic's legal page: developers 'including those using the Agent SDK, should use API key authentication' and Anthropic does not permit routing requests through Free/Pro/Max plan credentials on behalf of users (code.claude.com/docs/en/legal-and-compliance). Anthropic also clarified a ban on third-party harness use of subscriptions in Feb 2026 (The Register, 2026-02-20) and reportedly ended subscription-limit draw for third-party tools on 2026-04-04 (mlq.ai/Reddit, secondary). Treat OpenChamber's Claude path as a policy risk, not a model for Loom.
- The report's Claude usage design critique should add that auth.js reads the macOS Keychain item 'Claude Code-credentials' by shelling out to `security find-generic-password`, i.e. it extracts the CLI's stored OAuth token. That is exactly 'collect/store credentials' territory in Anthropic's terms. 'Undocumented endpoint' is right.
- Issue #3755 (/btw freezes server) is open but the current code already replaces the inherited openchamber metadata namespace on /btw forks and its docs say btw forks drop the goal; the report should say 'reported against 1.24.2, likely mitigated in HEAD, issue not closed' rather than presenting it as a live defect. Do not use it as evidence that the design is broken, only that fork-inheriting metadata needs stripping.
- #3521 is not a general Electron memory leak: it was closed as a duplicate of #3350, caused by the MCP auto-reconnect plugin spawning full MCP fleets per managed OpenCode instance (fixed by PR #3351). Also #2267, #3740, #3358, #3764, #4200 are closed/fixed; only #4607, #5023, #4407 (and #4840, #4836, #4901, #3755) are still open. The '6 GB on macOS' is one commenter's unmeasured remark.
- Public docs session-goals.mdx is stale; code and DOCUMENTATION.md both settle 'blocked' on the first auditor answer. The report hedged this; it can now be stated as verified.
- libghostty WASM build script is in packages/ui/package.json, not the root package.json.
- Download counts are available and the report's 'unverified/null' is wrong: about 200k real installer downloads on GitHub (dmg 63k + exe 118k + AppImage 24k), with the 6.7M raw asset total dominated by updater yml polling. Use the lower number as the adoption signal (and note it excludes npm/VS Code/mobile channels).
- The 'five models' cap for multi-run is documented in README only; the 10% Fusion threshold is a line-count estimate (changedLines * TOKENS_PER_DIFF_LINE), not a measured token count.

### Missed by the report

- Claude Code integration exists: packages/docs/content/docs/integrations.mdx section 'Claude Code'; CHANGELOG lines 709, 758, 1525-1528 ('Claude Code card is back', 'Claude Code can be the small model for titles and commit messages', Usage page names the plan and per-model weekly limits/extra usage, works when signed in via Claude Code on macOS/Linux/WSL); small-model/DOCUMENTATION.md line 112 (claude-code provider from the opencode-claude plugin, picks claude-code/haiku, but plugin models are unavailable for 20-40 s after OpenCode starts).
- Policy/billing context for Loom: Anthropic legal page 'Authentication and credential use' (code.claude.com/docs/en/legal-and-compliance) forbids intermediating Claude.ai credentials and routing through Pro/Max credentials on behalf of users, but explicitly allows 'an end user' signing in to the unmodified Claude Code binary 'including where a platform hosts Claude Code'. That carve-out is the policy basis that favours Loom's hosting-the-real-CLI design over OpenChamber's SDK/plugin route.
- Resource Monitor extension (integrations.mdx, v2.4.0): shows CPU/memory of machine, OpenChamber, OpenCode and dev servers, 'measures only while the panel or the Resources section is on screen' and lists Stop on a dev server ends that command with everything it started. A concrete precedent for Loom's measure-only-when-visible and process-ownership principles; note it is an optional extension and OpenChamber/OpenCode themselves have no Stop.
- Diagnostics timeline (Cmd/Ctrl+Shift+L, v2.4.0) downloadable as .log with paths and session titles stripped; the Integrations catalog of 160+ services installing MCP servers with skills; 'agents can show a page with options and wait for you to pick one' (v2.4.0), which is an interactive agent-UI channel beyond chat.
- Terminal shutdown design (terminal/DOCUMENTATION.md line 46): SIGTERM with a shared 20 s grace, process-table snapshots keep descendant ownership across shell exit and job-control groups, PID start times guard against PID reuse, SIGKILL at deadline. Directly relevant to Loom's verified-Stop/Quit requirement.
- Issue #3358 and #4407/#3764 show OpenChamber creates one managed OpenCode instance per project AND per chat directory, which is the structural cause of process fleets (see bot analysis in #3521). Process ownership per directory was a design choice, not just a bug.
- The README positions OpenChamber as a general 'run agent work, keep control, ship from anywhere' workspace and the HN thread shows the maintainers' own polish is contested: #2539 maintainer reply says Electron is staying ('a Tauri rewrite is not on the active product path'), and Tauri was removed in the 1.12.x line.
- Third-party security stance: HN dakiol flagged 50+ npm deps; AGENTS.md says 'Do not add dependencies unless explicitly requested' and 'Do not run git or GitHub commands unless the user explicitly asks', which suggests the code base is largely agent-written under strict rules; relevant to how much weight to give the self-reported lab numbers (142/144 classifier) and why docs drift from code.
