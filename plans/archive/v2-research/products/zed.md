# Zed (Parallel Agents + Threads Sidebar + Terminal Threads) and the Agent Client Protocol (ACP) with the Claude Agent ACP adapter

Research note for the Loom v2 brainstorm ([index](../V2-BRAINSTORM.md)). Written by a research subagent on 2026-10-17 and fact-checked by a second one; the fact-check is at the end and wins over the report where they differ. Raw JSON: `../evidence/deep-dive-20261017.json`.

**In one line:** Zed is a Rust/GPUI editor that hosts many agent threads in one sidebar. Its threads are either ACP-driven structured chats (Claude through an Agent SDK adapter) or plain terminal "threads" (the escape hatch). ACP is the open JSON-RPC protocol, now co-owned by Zed and JetBrains, that makes the structured path portable.

**Category:** hybrid

## Adoption

Zed: about 91.8k GitHub stars (gh api, 2026-10-17). Zed 1.0 shipped on 2026-04-29 and the post claims "hundreds of thousands" of daily users. Releases are weekly (v1.24.2 on 2026-10-14, v1.25.0-pre the same day). Parallel Agents + Threads Sidebar launched 2026-04-22. Terminal Threads launched about 2026-05-20, and the Zed blog says the change was timed with Anthropic's SDK billing announcement.

ACP: agentclientprotocol/agent-client-protocol has about 4.46k stars and was pushed 2026-10-17. The Claude adapter agentclientprotocol/claude-agent-acp has about 2.65k stars, is at v0.93.0 (2026-10-16), and ships several releases a week. The ACP Registry went live 2026-01-28 and the registry lists Claude, Codex, Copilot, Gemini, Cursor, OpenCode, Cline, Goose, Kiro, Factory Droid and others. The docs "Clients" page lists roughly 100 clients, including JetBrains IDEs and JetBrains Air (agentic IDE, public preview March 2026), VS Code extensions, Neovim, Emacs, Obsidian plugins, Sublime, Qt Creator, mobile apps and many desktop apps. At least three Swift SDKs are linked: wiedymi/swift-acp (32 stars, MIT, pushed 2026-07-24, built for the macOS app Aizen), rebornix/acp-swift-sdk (used by Agmente, 547 stars, iOS) and aptove/swift-sdk. Stable protocol version is v1; v2 is published in Draft. Rust and TypeScript SDKs reached 1.0.

## Architecture

ACP wire model (docs/protocol/v1/overview.mdx in the cloned repo): JSON-RPC 2.0 over stdio (local) with the agent as a subprocess of the client. A WebSocket/HTTP transports working group exists but remote support is still a work in progress. Flow: initialize with capability negotiation, then session/new, session/resume or session/list. A prompt turn is session/prompt, then a stream of session/update notifications (message chunks, thoughts, tool_call and tool_call_update, plan, available_commands_update, config_option_update, usage_update, session_info_update, notice and compaction updates), and finally the prompt response with a stopReason. Agent-to-client requests are session/request_permission (options allow_once, allow_always, reject_once, reject_always) and elicitation/create (form and URL modes, stabilized). v1 also has optional client-side fs/read_text_file, fs/write_text_file and terminal/create, output, wait_for_exit, kill and release.

Tool calls carry a kind (read, edit, delete, move, search, execute, think, fetch, switch_mode, other), status, locations for follow-along, and content that can be text, a diff (path, oldText, newText) or an embedded terminal. Subagents are an RFD (docs/rfds/subagents.mdx): a subagent_update announces a child session with a title and a work state (running, requires_action, idle) and an optional per-child cancel capability. session/fork is Draft.

ACP v2 (docs/protocol/v2/migration.mdx), Draft: the session/prompt response only acknowledges the prompt, and progress and the stop reason move to state_update notifications. Updates become upserts by id. The client fs and terminal APIs and session modes are removed ("not widely adopted"; use client-provided MCP servers instead). session/load is replaced by session/resume with replayFrom. session/list and session/close become required. Diffs get a structured changes[] plus an optional git patch (rfds/v2/diff-file-states.mdx).

How Claude is connected: agentclientprotocol/claude-agent-acp, the successor of zed-industries/claude-code-acp, is a Node >=22 TypeScript program (package.json engines). It calls the Claude Agent SDK query() (src/acp-agent.ts around line 11390, SDK 0.3.300) with streaming input. query() spawns the claude native binary, either the SDK-bundled platform package or the path in CLAUDE_CODE_EXECUTABLE (claudeCliPath(), about line 2034). It loads settingSources user, project and local (line 11198), so the user's CLAUDE.md, hooks and plugins still apply. The SDK's canUseTool callback is mapped to session/request_permission (canUseTool(), about line 10015, requestPermissionFromClient, about line 9772). SDK hooks (TaskCreated, TaskCompleted) feed ACP plans. enableFileCheckpointing is turned on only for clients that negotiate file-change reports. Fork uses the SDK forkSession (src/fork-session.ts). Subagents are exposed as child sessions (src/native-subagents.ts). One adapter process hosts many sessions, and each session is its own CLI child. session/close frees a session without killing the adapter. The adapter has a --hide-claude-auth flag that refuses claude.ai subscription accounts (src/hide-claude-auth.ts); JetBrains uses it.

Zed side: crates/agent_servers/src/acp/v1.rs builds client capabilities (fs read and write, terminal, auth.terminal, elicitation form and url, config boolean options, compaction, notices, plus _meta terminal_output). crates/agent_servers/src/acp/v2.rs is the v2 client (ProtocolVersion::V2) and is in progress. Cargo.toml pins agent-client-protocol =3.4.0 with unstable_protocol_v2. crates/acp_thread (about 24.6k lines in acp_thread.rs) is the thread model. crates/action_log/src/action_log.rs tracks agent buffer edits for keep and reject per hunk. crates/sidebar/src/sidebar.rs (about 8.4k lines) is the Threads Sidebar.

State detection in Zed: for ACP threads, the thread status enum is Completed, Running, WaitingForConfirmation, Error (crates/ui/src/components/ai/thread_item.rs). A "notified" (blue dot) is set when a non-active thread goes Running to Completed (sidebar.rs around lines 1780-1850) and cleared on activation. For Terminal Threads, state comes only from terminal events: TitleChanged, Wakeup and Bell (crates/agent_ui/src/agent_panel.rs around lines 2225-2240). Persisted terminal-thread metadata is only terminal_id, title, custom_title, created_at, worktree paths, remote connection and working_directory (crates/agent_ui/src/terminal_thread_metadata_store.rs line 48). There is no agent session id and no resume link. After restart, the shell is recreated and agent.terminal_init_command is re-run, so a Claude terminal thread does not resume its conversation. Claude Code must be told to ring the bell (preferredNotifChannel "terminal_bell").

Persistence: thread metadata in a local DB (ThreadMetadataStore, TerminalThreadMetadataStore); agent conversation history lives with the agent. Archive removes a linked worktree from disk and restore recreates it (see worktree feature). Resources: Zed is native Rust, but ACP adds a Node adapter process plus one claude child per live session. A Zed issue (#43338, Nov 2025) reports slow and frozen sessions with Claude via ACP, and an HN user reported memory growth. I did not measure any resource use myself.

## Core loop

A typical Zed agentic day: (1) Use the agentic layout with Agent Panel and Threads Sidebar on the left and Project and Git panels on the right (option-cmd-j toggles the sidebar). (2) Start a thread per task from the project header "+" button, choosing the agent per thread (Zed Agent, Claude via ACP, Codex via ACP, or a Terminal Thread running the `claude` CLI). (3) For overlapping work, start the thread in a new git worktree from the title-bar worktree picker. Worktrees open as detached HEAD, and a create_worktree task hook can bootstrap env files or databases. (4) Watch the sidebar status (spinner, waiting for confirmation, blue dot, error), get an OS notification or sound when a thread finishes, and use ctrl-tab (MRU thread switcher) to jump. (5) For ACP threads, open the Review Changes multibuffer, keep or reject hunks, use the checkpoint "Restore Checkpoint" button, and optionally follow the agent through files. (6) Merge through normal git, then archive the thread, which saves and removes the worktree; restore from Thread History (cmd-g) if needed. Users report the main gap is that only one conversation is visible at a time (no tiling of threads): discussion #54911 has several users who went back to a tmux grid of `claude` CLIs or to `workspace: new center terminal`.

## Features

### Agent Client Protocol (ACP) as the structured agent-host contract (other, confidence high)

- **What the user sees:** Any ACP agent (Claude, Codex, Gemini, Copilot, OpenCode, Cursor, and others) appears as a normal thread with streaming chat, tool cards, permission prompts, plans, diffs, a model/mode picker, slash-command list and context usage. One install path (the ACP Registry) works across Zed, JetBrains and other clients.
- **How it works:** JSON-RPC 2.0 over stdio, capability-negotiated. The host must implement at least initialize, session/new (and ideally resume/list/close), session/prompt, handling of the session/update stream, session/request_permission, and session/cancel. fs, terminal, elicitation, auth and config options are optional capabilities. v1 spec: docs/protocol/v1/*.mdx in agentclientprotocol/agent-client-protocol. Distribution: ACP Registry (agent.json with an npx or binary distribution, e.g. claude-acp is '@agentclientprotocol/claude-agent-acp@0.93.0'). In v2 Draft, the client fs/terminal surface is removed and agent-owned display terminals are added; the prompt response only acknowledges the prompt, and state_update carries running, idle and requires_action plus the stop reason.
- **Reception:** Positive on the ecosystem: ACP is the interoperability layer behind Zed, JetBrains and tens of clients, and the ACP site lists about 100 clients. Complaint pattern: the host must keep up with each agent's own features. HN thread https://news.ycombinator.com/item?id=47949140 says /mcp, /plugins, skill autocomplete, custom agents, subagent display, background processes, effort level and context view were missing or partial for Claude in Zed at the time. One commenter reported memory ballooning to many GB; the v2 migration guide itself admits the client fs/terminal surface saw little adoption.
- **Evidence:** https://agentclientprotocol.com/get-started/introduction; repo docs/protocol/v1/overview.mdx, tool-calls.mdx, initialization.mdx; repo docs/protocol/v2/migration.mdx and docs/rfds/v2/client-filesystem-terminal-capabilities.mdx; https://agentclientprotocol.com/updates; https://github.com/agentclientprotocol/registry (claude-acp/agent.json)

### Claude Code over ACP: Agent SDK adapter (claude-agent-acp) (other, confidence high)

- **What the user sees:** Claude as a first-class structured thread: @-mentions, images, tool calls with permission requests, TODO/plan list, nested subagent transcripts, background terminals, edit review, custom slash commands, /mcp status in chat, session fork/resume/list/delete, a predicted next-prompt suggestion, and /remote-control.
- **How it works:** src/acp-agent.ts calls query() from @anthropic-ai/claude-agent-sdk (0.3.300). query() spawns the claude native binary (the SDK platform package or CLAUDE_CODE_EXECUTABLE) and talks the stream-json control protocol. canUseTool is mapped to session/request_permission. settingSources user, project and local are loaded, so CLAUDE.md, hooks and plugin skills run. Subagent traffic is turned into child sessions with subagent_update states (src/native-subagents.ts). Fork uses SDK forkSession (src/fork-session.ts). Requires Node >=22. The adapter reports it follows Claude Code's changes closely: v0.90 to v0.93 landed in Oct 13-16, 2026, almost all subagent, cancel and replay fixes.
- **Reception:** Mixed. HN https://news.ycombinator.com/item?id=47949140: nice to see code while chatting and less 'busy' than the TUI, but 'you're going to be missing a lot of features' and some went back to the terminal. Discussion https://github.com/zed-industries/zed/discussions/54911 (YutorinX, 2026-07-25): ACP sessions are Agent SDK sessions, so the CLI's `claude agents` monitor does not see them; they switched to CLI terminal tabs. A separate request (discussion #62269, Aug 2026) asks for Claude Remote Control support in the ACP agent.
- **Evidence:** ~/Library/Caches/loom-v2-research/repos/claude-agent-acp/src/acp-agent.ts (query at ~11390, canUseTool at ~10015, settingSources at ~11198, claudeCliPath at ~2034); repo README.md (feature list, Subagent sessions section); repo CHANGELOG.md 0.90.0-0.93.0; https://github.com/agentclientprotocol/claude-agent-acp

### Billing and policy exposure of the SDK path (usage-cost, confidence high)

- **What the user sees:** Using Claude through ACP is billed as 'Agent SDK / third-party app' usage, not as first-party Claude Code. In May 2026 Anthropic announced that it would move to a separate capped credit (about $20 Pro, $100 Max 5x, $200 Max 20x at API rates). Zed answered with Terminal Threads as the way to keep subscription limits.
- **How it works:** Anthropic announced the split on 2026-05-14 for 2026-06-15 and paused it on launch day. The support article (updated 2026-10-07) says that, for now, Agent SDK, `claude -p` and third-party apps still draw from subscription limits, and that Max and Team plans now include monthly API credits. Anthropic told subscribers it is revising the plan and will give notice. The adapter has a --hide-claude-auth mode (src/hide-claude-auth.ts) that refuses claude.ai subscription accounts; JetBrains Air uses it.
- **Reception:** Developer sentiment was strongly negative to the announced change. Zed's own May 20 post still claims Terminal Threads are 'the only way' to keep a subscription; that was true for the announced plan but is stale after the pause. The lesson is the volatility, not the final policy.
- **Evidence:** https://zed.dev/blog/anthropic-subscription-changes (with the 2026-06-16 update); https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan; https://thenewstack.io/anthropic-pauses-claude-agent-sdk-subscription-change/ (found in search; the fetched page returned only a signup form, so the article text was not read); repo src/hide-claude-auth.ts

### Threads Sidebar (parallel agents across projects) (navigation-ux, confidence high)

- **What the user sees:** A left sidebar of threads grouped by project. Each row has title, status icon, agent icon and worktree/branch info. Threads in linked worktrees nest under their main project. Hover actions are stop, archive and new thread in this project. Cmd-f searches, ctrl-tab opens an MRU switcher, and Thread History (cmd-g) holds archived threads, searchable by title, with restore and permanent delete (trash icon removes the history and worktree data). An import button pulls in existing external-agent threads.
- **How it works:** crates/sidebar/src/sidebar.rs builds ListEntry rows (project headers, ThreadEntry, TerminalEntry). Live ACP status is merged from AgentThreadStatus (Running, WaitingForConfirmation, Completed, Error). A thread that goes Running to Completed while not active gets a 'notified' dot that clears on activation (around lines 1780-1850). Thread metadata is persisted in ThreadMetadataStore. Running threads cannot be archived until they finish. Multi-root projects allow one thread to read and write across several folders.
- **Reception:** Praised for polish. Complaints (https://github.com/zed-industries/zed/discussions/54865 and #54911): the blue 'finished' dot disappears as soon as you focus the thread, so 'needs attention' is not persistent; no filter or sort by state; worktrees as headers are noise; no context-size display on rows. Users also cannot see more than one conversation at a time (no tiling), which is 'the main thing pulling me back to a tmux grid of claude CLIs' (Pran-Ker, 2026-07-13). Maintainers (macraig, 2026-05-28) said they are still studying how tabs would interact with the sidebar.
- **Evidence:** https://zed.dev/docs/ai/parallel-agents; https://zed.dev/blog/parallel-agents; repo crates/sidebar/src/sidebar.rs, crates/ui/src/components/ai/thread_item.rs

### Terminal Threads (CLI escape hatch) (attention-status, confidence high)

- **What the user sees:** New Thread then Terminal opens a shell as a thread in the same sidebar. Run `claude`, `codex`, `amp`, `opencode`, `pi` or anything. The title follows the running process. A notification and sound fire when the terminal rings the bell while not focused. They are closed, not archived, and do not go to Thread History. agent.terminal_init_command can auto-run `claude` in each new one.
- **How it works:** Zed owns only the thread surface (sidebar entry, grouping, switching). The CLI owns auth, models, tools, skills and MCP. Status is inferred from terminal events only: TitleChanged, Wakeup and Bell (agent_panel.rs around lines 2225-2240). The user must configure Claude Code with preferredNotifChannel 'terminal_bell'; Amp needs AMP_FORCE_BEL=1; OpenCode and Pi need small plugins that print BEL; Codex can set its terminal title through [tui] terminal_title. Persisted metadata has no session id (terminal_thread_metadata_store.rs line 48), and on reopen the shell is recreated and the init command re-run, so there is no conversation resume link. Note: 'Big Terminal Mode' from the brief is not a Zed feature; it is Conductor's escape hatch, mentioned by Conductor's founder in the HN thread https://news.ycombinator.com/item?id=47866750. I grepped the Zed repo and docs and found no mention.
- **Reception:** Zed itself says 'there is more we can do to make Terminal Threads feel native'. The design confirms that a generic terminal host gets only a coarse bell/title signal, which is far weaker than Loom's hook-based states (working, approval, finished-unviewed, failed). No dedicated complaints found; it is new.
- **Evidence:** https://zed.dev/docs/ai/terminal-threads (also repo docs/src/ai/terminal-threads.md); https://zed.dev/blog/terminal-threads; repo crates/agent_ui/src/agent_panel.rs, crates/agent_ui/src/terminal_thread_metadata_store.rs

### Worktree isolation with archive and restore (parallel-worktrees, confidence high)

- **What the user sees:** A worktree picker and branch picker in the title bar. New worktrees are created detached to avoid sharing a branch. A create_worktree task hook runs setup (ZED_WORKTREE_ROOT, ZED_MAIN_GIT_WORKTREE). Archiving a thread removes its worktree from disk but keeps its git state; restoring recreates the worktree and its staged/unstaged files.
- **How it works:** crates/agent_ui/src/thread_worktree_archive.rs: on archive, two detached 'WIP' commits are created (WIP staged = a tree matching the index parented on HEAD; WIP unstaged = a tree with all files including untracked), pinned by a git ref so GC cannot drop them (around lines 489-600), then the worktree is removed. On restore it recreates the worktree, switches branch and restores the index and working tree from the WIP trees (around lines 642-780).
- **Reception:** HN commenters call parallel threads in worktrees plus setup/teardown hooks 'the real gamechanger'. Pain points are shared test databases, ports and secrets across worktrees; one commenter stopped using parallel agents because of shared migrations.
- **Evidence:** https://zed.dev/docs/ai/parallel-agents (Worktree Isolation section); repo crates/agent_ui/src/thread_worktree_archive.rs; HN https://news.ycombinator.com/item?id=47866750 (worktree lifecycle hooks seen as the real game changer)

### Review of agent edits: Review Changes, per-hunk keep/reject, checkpoints, follow (review-git, confidence high)

- **What the user sees:** An accordion above the composer shows files and line counts changed. 'Review Changes' opens a multibuffer with all hunks, with accept/reject per hunk or for all. Optional inline review in each file (agent.single_file_review). 'Restore Checkpoint' on every edited message, even after an interrupt. A crosshair 'follow' mode jumps the editor to each file the agent touches.
- **How it works:** crates/action_log/src/action_log.rs (about 3.5k lines) tracks buffers the agent read, created or edited, keeps a diff against the original per buffer, and supports keep_edits_in_range, reject_edits_in_ranges and an undo of the last reject. This depends on Zed being the editor that holds the buffers. For ACP, edits arrive as tool_call content of type diff plus locations; the adapter enables Claude's file checkpointing only when the client negotiates per-turn file-change reports. In ACP v2, diffs become structured changes[] plus an optional git patch.
- **Reception:** Docs themselves note that checkpoints, token display and thread restore 'depend on the agent integration', so external agents get fewer features. The per-hunk review is considered a core strength of an editor-hosted agent, and also the reason it cannot be copied without an editor.
- **Evidence:** https://zed.dev/docs/ai/agent-panel (Reviewing Changes, Checkpoints, Following the Agent) and repo docs/src/ai/agent-panel.md; repo crates/action_log/src/action_log.rs; repo docs/rfds/v2/diff-file-states.mdx; repo claude-agent-acp/src/acp-agent.ts around lines 11219-11222 (enableFileCheckpointing)

### Message queue and steering (chat-input, confidence high)

- **What the user sees:** Messages sent while the agent is generating are queued by default, can be edited or removed (one or all), sent immediately with 'Send Now' (double enter) or the stop button. A 'Steer' toggle lets a queued message interrupt the Zed Agent at its next step.
- **How it works:** Zed docs state steering is only available for the Zed Agent 'since Zed can't detect turn boundaries for external agents'. The Claude adapter documents a steering extension only on v1 and for the JetBrains Air client (docs/air-extensions.md).
- **Reception:** No complaints found. It validates the need for a queue; the stated limitation is exactly where Loom's hook-derived turn boundaries are an advantage.
- **Evidence:** repo docs/src/ai/agent-panel.md (Queueing Messages); repo claude-agent-acp/docs/air-extensions.md

### Subagent sessions and a usage meter in ACP (orchestration, confidence medium)

- **What the user sees:** In clients that implement the RFD, each Agent/Task subagent is its own child session with its own transcript, a state (running, requires_action, idle) and a stop button for that child alone. Context fill and cost come from usage_update (used/size tokens plus optional cost).
- **How it works:** subagent_update on the parent announces the child (title, description, capabilities.cancel). The adapter maps SDK task events to child sessions, and session/cancel on a child calls SDK Query.stopTask, sparing the parent. A client capability, clientCapabilities.subagents, gates it. usage_update is stable. In Zed's own sidebar a Zed Agent thread can spawn_agent, and Zed's action log links a subagent log to the parent review.
- **Reception:** HN complaint (sodacanner, maherbeg) that Zed showed no subagent display and no context/usage view for Claude. That is now being filled in by the adapter work in Oct 2026, so the state of Zed's rendering is not confirmed.
- **Evidence:** repo docs/rfds/subagents.mdx; repo claude-agent-acp/README.md Subagent sessions section; src/native-subagents.ts; src/acp-subagents.ts; repo docs/rfds/session-usage.mdx; repo crates/action_log/src/action_log.rs (linked_action_log)

### Session fork (a side thread on shared context) (context-knowledge, confidence medium)

- **What the user sees:** A session/fork RFD lets a client branch a conversation to ask extra questions or summarize without polluting the main history. The adapter implements fork for Claude.
- **How it works:** RFD docs/rfds/session-fork.mdx by josevalim (explicit goal: 'without polluting the user history'). The adapter uses SDK forkSession (src/fork-session.ts), optionally from a specific message with AIR metadata. Still Draft in the protocol (session.fork is 'Draft only' in v2). The Claude CLI has a matching flag, --fork-session when resuming (https://code.claude.com/docs/en/cli-reference, found in search results; I did not read the whole page). Claude Code also has a /btw side-question command that reuses context without adding to history (third-party write-ups from March 2026, e.g. https://wmedia.es/en/tips/claude-code-btw-side-question; not verified against Anthropic docs).
- **Reception:** No user feedback found in Zed channels; the RFD is the only direct signal. It matches Loom's long-standing 'side chat' wish.
- **Evidence:** repo docs/rfds/session-fork.mdx; repo claude-agent-acp/src/fork-session.ts; https://code.claude.com/docs/en/sessions (--fork-session mentioned in search snippet)

### Idle-sleep prevention and desktop/sound notifications (attention-status, confidence high)

- **What the user sees:** While any agent thread is generating (not while waiting for confirmation), Zed holds the system awake; the display can still sleep. Notifications and sounds fire when a thread finishes or waits.
- **How it works:** agent.prevent_idle_sleep (default on) asks the OS not to idle-sleep only while a thread is in the generating state; agent.notify_when_agent_waiting and agent.play_sound_when_agent_done control notifications.
- **Reception:** No complaints found. Small but practical for long unattended runs.
- **Evidence:** repo docs/src/ai/agent-panel.md (Keeping the System Awake, Get Notified)

### Cross-thread messaging (requested, not shipped) (orchestration, confidence medium)

- **What the user sees:** A feature request wants an @ mention that posts into another sidebar thread, a post_to_thread tool and a wait_for_peer_replies tool, to stop copy-pasting between a Claude thread and a Codex reviewer thread.
- **How it works:** Only a proposal in GitHub discussion #55122 (author m2015agg, 2026-04-28). A related permission-UX discussion #54084 was closed. Nothing in the repo that I found implements it.
- **Reception:** Shows real demand for exactly the user-authorized cross-session channel that Loom has planned.
- **Evidence:** https://github.com/zed-industries/zed/discussions/55122

## UX patterns worth borrowing

- Threads grouped under project headers, with linked-worktree threads nested under the main project; a per-project '+' to start a thread already scoped to that project.
- Status is a single leading icon: spinner (running), a distinct waiting-for-confirmation state, a transient dot for 'finished while you were elsewhere', and an error state. Users ask that 'needs attention' persist until acknowledged and that rows can be filtered or sorted by state (discussion #54865). Loom's Active section already answers this.
- MRU thread switcher on ctrl-tab (hold shift to go backwards) that works from panel or sidebar, in addition to the sidebar list.
- Archive versus delete as two separate verbs: archive hides from the list but keeps history and restores the worktree; permanent delete is a second trash action in Thread History. Running threads cannot be archived.
- Queue-by-default composer: typing while the agent works queues the message (editable, removable, Send Now); stop button remains separate.
- One 'New thread' menu offers every thread kind (Zed Agent, each ACP agent, Terminal) so the sidebar mixes structured chats and raw terminals in one list.
- Native OS notifications that are cleared by clicking through to the thread, and a prevent-idle-sleep assertion tied to the generating state.
- Panel layout presets ('agentic' vs 'classic') so agents sit on the left and project/git panels on the right.
- Config surface split: Zed owns the thread surface; the external agent owns auth, models, tools, skills and MCP, and docs have a table stating which settings do not carry across (docs/src/ai/external-agents.md).

## Anti-patterns

- Single visible conversation with only a sidebar list of the others. Several users call this the blocker for supervising 3-5 parallel threads; they want tiling or tabs (discussion #54911).
- Non-persistent 'finished' indicator: it clears on focus, so users lose track of which thread needs review (#54865).
- Hosting Claude through the Agent SDK instead of the real CLI brings feature lag (no /mcp or /plugins at times, skills autocomplete, custom agents, subagent display, background processes, effort level, context view), CLI-only tools like `claude agents` do not see those sessions, a Node runtime, and exposure to billing policy changes (May-June 2026 announcement and pause).
- Terminal Threads infer state from bell and title only and require per-agent setup (preferredNotifChannel terminal_bell, AMP_FORCE_BEL, small plugins). Metadata has no session id, so a restart does not resume the conversation.
- Steering is limited to the Zed Agent because turn boundaries of external agents are unknown. A host that does not know turn boundaries cannot offer reliable queue or steer semantics.
- Reports of slow or frozen Claude sessions in Zed and memory growth (issue #43338; HN comments); a resident adapter process plus a CLI child per live session needs explicit close and resume discipline.
- Shipping an in-protocol client fs/terminal surface that few agents or clients used; ACP v2 removes it. Lesson: do not build host-side tool surfaces unless agents will use them.
- Zed's blog claiming Terminal Threads were 'the only way' to keep a subscription turned stale within weeks. Do not design around a vendor's pending billing change.

## Ideas for Loom

### Side chat as a forked real CLI session: a 'Side chat' button on a session opens a side panel running `claude --resume <id> --fork-session` (or the CLI's /btw for a one-off question) in its own PTY. It is linked to the parent card, hidden from the normal session list, shows its own status, and on close is stopped and (by default) deleted with the existing verified permanent-deletion path. (cost M)

- **Inspired by:** ACP session/fork RFD and the adapter's forkSession (src/fork-session.ts); Zed's New From Summary; Loom's own long-standing side-chat wish
- **Gain:** Gives the exact 'ask without polluting the main thread' flow with no new engine. The forked prefix is the same as the parent, so prompt-cache reuse may cut cost (unverified, depends on cache TTL).
- **Fit:** Fits well. It uses a documented CLI flag, runs a real CLI in a Loom-owned run scope, costs nothing when closed (process stopped, no idle record), and deletion is verified. It needs a parent/child marker in Loom's own store. It does not need ACP or any chat UI, and it can render as a terminal now and as a chat later.
- **Risks:** Fork creates a new Claude session record that must not leak into the activity list, usage double-counting must be tagged, and a side chat inherits the parent's pending state (do not fork mid-approval). The CLI flag name and semantic need drift detection like other CLI options. /btw route is unverified from Anthropic docs.

### Composer queue driven by verified turn boundaries: a per-session queue of follow-up prompts (edit, remove, 'send now') that Loom delivers into the PTY only when hooks and registry say the session is idle (Stop hook seen, state Ready). The same queue lets the user line up a prompt for a session that is 'Working' or in another project. (cost M)

- **Inspired by:** Zed Agent Panel queued messages with Send Now; Zed's explicit admission that it cannot steer external agents because it cannot see turn boundaries
- **Gain:** Lets the user stack work and leave, instead of waiting at the keyboard for each turn to end across several sessions. It also reduces accidental mid-turn interruption from typing into a running TUI.
- **Fit:** Strong fit: Loom's accurate status is exactly the missing ingredient, delivery is an observable outcome (state moves to Working after send, otherwise report 'not delivered'), and nothing polls. Keep the queue in Loom's store (small, bounded) and show queued count on the card. Conflict to watch: Loom's contract of never replacing the CLI interface; the queue is an input aid, the TUI stays the interface.
- **Risks:** Typing into a PTY is brittle if the TUI is in a dialog, a slash-command picker or a /resume menu. Use hook state plus bracketed paste and a short 'delivery verified by next UserPromptSubmit hook' check; fail visibly. Interplay with CLI's own internal message queue.

### Hold the Mac awake only while a session is truly Working: take an IOKit PreventUserIdleSystemSleep assertion when the first session enters Working and release it when none are (not during Needs approval, matching Zed). Show a small 'keeping awake' badge in the footer and a Settings toggle. (cost S)

- **Inspired by:** Zed agent.prevent_idle_sleep
- **Gain:** Long unattended multi-session runs stop dying when the lid-idle timer fires; one of the few features that saves real time with zero UI.
- **Fit:** Fits: event-driven off the existing status transitions, no polling, negligible cost, and the assertion's state is verifiable. Release on Quit/crash is automatic. Conflict: battery use, so default should be on only while plugged in or a visible setting.
- **Risks:** Assertion leak if state tracking misses a transition (watchdog-silenced sessions); tie release to the same hook-silence watchdog. Corporate Macs may restrict it.

### Context fill meter on each session card and in the header: used tokens as a thin bar or number, turning yellow and then red near the window limit, plus a one-click 'compact' or 'new session from summary' hint. (cost S)

- **Inspired by:** ACP usage_update (used/size), Zed token display and the request in discussion #54865 to show context size on sidebar rows; Zed's New From Summary
- **Gain:** Context bloat is the main silent cause of slow and expensive sessions; seeing it per card across five sessions tells the user which one to compact or restart before quality drops.
- **Fit:** Very good: Loom already reads transcripts incrementally via FSEvents, and the last assistant message carries usage, so no extra polling or process. Window size per model may be unknown (1M variants); show only tokens when size is not certain and detect drift rather than guessing.
- **Risks:** Wrong denominator = false alarms; incremental parser must handle sidechain/subagent usage separately. Accuracy principle says label as 'estimate' if size is inferred.

### Changes-since-last-prompt chip and a read-only diff panel: capture a bounded git baseline at the UserPromptSubmit hook, compute a diff stat on Stop, show '+N -M in K files' on the card, and open a read-only syntax-highlighted unified diff in the detail pane with 'Open in editor' and 'Copy patch' buttons. No keep/reject buttons. (cost L)

- **Inspired by:** Zed Review Changes and checkpoints; ACP v2 diff changes[] + git patch; Zed's WIP-commit trick in crates/agent_ui/src/thread_worktree_archive.rs
- **Gain:** Review is the step users still leave Loom for; knowing 'this finished session touched 7 files' and seeing the diff beside the session saves a context switch to a separate git tool, and it makes the 'Finished unviewed' blue state more meaningful.
- **Fit:** Partial fit. Keep it bounded and event-driven (git only at hook events, size caps, skip binary and huge files), and render only when visible. Zed's per-hunk keep/reject needs an editor holding buffers and conflicts with Loom's 'no editor' scope, so skip it; git (restore, add -p) stays the revert mechanism. Does not conflict with the PTY contract.
- **Risks:** Snapshot cost in large repos; baseline must not touch the user's index (use a temporary index file); dirty trees before the prompt confuse attribution; monorepos. Needs a diff renderer which Loom does not have yet.

### A chat-style rendering of a session that is read from Claude's own transcript and hooks, not from ACP: a 'Chat' tab next to the terminal that shows messages, tool cards (kind icons from the ACP vocabulary: read, edit, execute, search, fetch), plans/TODOs and diffs, with the composer sending text into the same PTY. Reuse the read-only subagent transcript panel as the base. (cost L)

- **Inspired by:** ACP content and tool-call model as a view-model (kind, status, locations, diff content, plan), Zed's thread view
- **Gain:** Gets most of the readability win of a chat UI (skimmable history, collapsed tool noise, jump between prompts, copy a response) while the real CLI keeps running underneath, so slash commands, /mcp, skills and subagents all still work.
- **Fit:** Good if done as a pure view: no second engine, no SDK billing exposure, no Node. Costs only when the tab is visible (render nothing when hidden). Risk is transcript-format drift (Loom already has drift detection) and streaming latency, since the JSONL is written after the fact; use hooks and registry for live state and accept 'last complete message' semantics for text.
- **Risks:** Transcript lag for partial output; format changes in Claude's JSONL; two input surfaces (composer vs TUI) can disagree about mode (plan/permission/dialog), so the composer must be disabled whenever status is Needs approval or a dialog is open.

### Show subagent 'waiting for you' on its own row and attribute the approval box to the subagent that asked, using hook payload fields if present (agent id/type on PreToolUse and permission events). Keep the finished-fold; only the running rows get the state. (cost S)

- **Inspired by:** ACP subagents RFD (state running/requires_action/idle per child); adapter test 'report a subagent as requires_action while its request is open'
- **Gain:** With multi-agent workflows the user currently sees 'session needs approval' but not which subagent; routing the click to the right row speeds triage.
- **Fit:** Fits: it only adds an attribute to events Loom already receives; no polling. Per-subagent stop is a different matter: ACP does it through the SDK's Query.stopTask control request, and I could not confirm that the interactive TUI exposes a safe equivalent, so do not promise a per-subagent Stop.
- **Risks:** Hook fields for agent identity are unverified for the current CLI version (the adapter gets agentID via canUseTool, not necessarily hooks). Must degrade silently to the session-level state, with drift detection.

### Do NOT adopt ACP for Claude. If Loom later wants non-Claude agents (Codex is currently frozen) or a native structured chat without a PTY, implement a thin ACP client behind an agent-provider seam and use it only for agents whose CLI has no good hook story (Codex via codex-acp, Gemini, OpenCode). A Swift host is feasible: JSON-RPC over newline-delimited stdio, with existing MIT Swift SDKs (wiedymi/swift-acp: actors, AsyncStream updates, client and agent runtimes, ACPRegistry module). (cost XL)

- **Inspired by:** ACP and its registry; Zed's mix of ACP and Terminal Threads in one sidebar
- **Gain:** One protocol would give structured permissions, plans, diffs, usage and session list/resume for every agent in the ACP Registry without Loom writing a bespoke integration per CLI.
- **Fit:** Conflicts for Claude: it replaces the real CLI interface with an SDK-driven session (feature lag, no `claude agents`), adds Node >=22 and one adapter process plus a CLI child per session (resource and run-scope ownership work), bundles or pins an SDK CLI version unless CLAUDE_CODE_EXECUTABLE overrides it (against 'never pin'), and ties Loom to Anthropic's SDK billing policy which changed twice in 2026. It also moves status truth from hooks to protocol events. A lighter variant is to treat ACP as an optional second provider, strictly additive, and keep Claude on the PTY path; revisit only after v2 stabilizes (v2 changes prompt-response semantics and removes fs/terminal).
- **Risks:** Churn: ACP v2 is Draft, the adapter ships many releases per week, subagent and AIR extensions diverge by client. Sandboxing, auth flows and account guards (--hide-claude-auth) add policy surface Loom does not have today.

### Corrections

- Memory-growth attribution is wrong: the HN comment (bicepjai, item 47949140) is about running the Claude CLI in Zed's terminal, not ACP. Do not cite it as evidence that the ACP adapter bloats memory. Zed issue #43338 is CLOSED (2025-11-22) and predates the claude-agent-acp rename; do not present it as a current ACP problem.
- The Anthropic billing announcement date is likely 2026-05-13 (Zed's post dated 05/14 says 'Yesterday Anthropic announced'). The credit amounts ($20/$100/$200) are from Zed's blog, not from an Anthropic primary source the reviewer saw. The 'Anthropic is revising the plan' line is Zed's paraphrase.
- The 'JetBrains uses --hide-claude-auth' statement is not supported by the adapter repo; say only that the flag exists.
- The HN thread 47949140 feature-gap list dates from 2026-04-29; the adapter has since added subagent sessions, usage, /mcp status etc., so treat the gap list as stale, not current.
- The Swift SDKs are thin and low-activity (32, 7 and 11 stars; the last pushes were July, February and April 2026), so 'maintained' is overstated. None is a safe dependency without a review. Zed's repo license is not a clean permissive one (GitHub reports NOASSERTION).
- Zed's notified dot is only set on Running to Completed for a non-active thread; WaitingForConfirmation is a status icon but did not set the dot in the code I read.

### Missed by the report

- Claude Code has its own first-party multi-session monitor: `claude agents` (agent view, research preview) with `--json` and `--cwd` flags, background sessions that run without a terminal, rows showing working/needs-input/done (https://code.claude.com/docs/en/agent-view, cli-reference). It directly overlaps Loom's Active-sessions concept and is what the Zed user complaint says ACP sessions cannot join. Loom should decide how it relates to it (CLI reference line for `claude agents`).
- Claude Code's official terminal notification route: by default desktop notifications only in Ghostty, Kitty and iTerm2; other terminals need preferredNotifChannel terminal_bell or a Notification hook (code.claude.com/docs/en/terminal-config). A host that embeds its own terminal sees no bell unless the setting is changed, which is why Zed docs ask users to edit Claude settings; Loom's hooks avoid this.
- Zed docs state which Agent Panel features depend on the agent integration (thread restore, checkpoints, token display) and that Zed Agent profiles, tool permissions, Skills and MCP settings do not apply to Terminal Threads (docs/src/ai/terminal-threads.md, agent-panel.md line 29).
- The ACP v2 migration guide explicitly tells implementers to gate v2 behind version negotiation and feature flags until it stabilizes (docs/protocol/v2/migration.mdx line 20), and Zed pins agent-client-protocol =3.4.0 with unstable_protocol_v2 (Cargo.toml line 532). This is a concrete churn signal for any Swift ACP client.
- The registry entry for claude-acp lists authors Anthropic, Zed Industries and JetBrains, distribution via npx only (needs Node on the user's machine), and the adapter's own LICENSE is Apache-2.0 while the registry labels it 'proprietary' (inconsistent metadata, minor).
- ACP wire-level steering exists in the adapter via docs/air-extensions.md (_session/steering, capability _meta.steering) for JetBrains AIR, so 'external agents cannot be steered' is a Zed limitation, not an ACP-level impossibility.
- Zed worktree lifecycle: create_worktree task hook (docs/tasks hooks) is the feature HN users praise; there is no matching teardown hook (jamie_ca on HN says cleanup must be set up as tasks).
