## Theme chat-ui-paths

- Summary: Researched 2026-10-17 against primary docs, the published SDK typings (@anthropic-ai/claude-agent-sdk 0.3.302 = Claude Code 2.1.302), and shallow clones of claude-agent-acp, Paseo, T3 Code, Orca, Ghostex, Agent of Empires and Codex. Recommendation: stay PTY-first, and add the structured UI in two layers. (1) A read-only structured transcript decoded leniently from Claude's JSONL for every session. (2) An opt-in Chat mode backed by a Loom-owned `claude -p --input-format stream-json --output-format stream-json` child spoken to directly from Swift, with no Node, SDK or ACP. ## Theme review-git-loop

- Summary: The field has converged on one loop: a diff pane with a per-line "+", comments batched and sent back as one prompt, then commit/push/PR, a PR chip with CI checks, and "ask the agent to fix" buttons. The PR is the merge unit, and conflicts are previewed read-only and then handed to an agent. Almost everyone reads git through the git CLI and GitHub through `gh` or Octokit. Most also poll: Superset refetches PR status every 10 s and PR comments every 30 s. Orca debounces file-watch refreshes at 125 ms and treats PR data as stale after 120 s. The apps differ mainly in how they deliver comments to the agent:
- Conductor, Claude Code desktop, Codex app, Emdash and Vibe Kanban drive the agent through an SDK, app-server or ACP-style channel, so a comment becomes a composer attachment or a structured follow-up message.
- Orca, Superset and Warp drive the real terminal UI. They paste into the PTY, with different levels of safety: Orca gates on agent status and hook evidence and verifies a turn started; Warp writes text to the PTY or a rich input; Superset pastes and presses Enter, with no readiness gate found in the code I read.
Loom hosts the real CLI in a PTY, so its delivery problem is Orca's and not Conductor's.

For Loom the most important finding is that Claude Code has acquired several documented, structured ways to put text into a live interactive session. Until recently the only one was PTY paste.
- Mods (2.1.287 and later, official docs) can call `$.prompt.submit({text, asUser:true})`, which runs once the session is idle. A mod can also read the draft with `$.prompt.read()` and insert into the draft with `$.prompt.fill()`.
- Settings hooks can inject `additionalContext` at the next prompt, tool boundary or Stop. `asyncRewake` can wake an idle session.
- The per-session cross-session inbox socket is documented in its existence, its path (`CLAUDE_CODE_MESSAGING_SOCKET`) and its auth token. Its frame format is only reverse-engineered, though it does give delivery receipts.
- Skills can inline command output with the documented !`cmd` syntax.
- Typed input has documented queue-while-working semantics.

PTY paste remains the only mechanism that carries real user authority. It is also the most fragile: open Claude Code issues report silent truncation of long input bursts, Enter intercepted by autocomplete, and a long delay needed between paste and Enter.

Loom has an unusual advantage. Its hook receives the exact prompt text on UserPromptSubmit, and it owns the PTY, so it sees every byte the user typed. That means it can verify delivery exactly (hash match on the submitted prompt) and can know whether a draft is sitting in the prompt box. This fits Loom's "verified outcomes" principle better than any competitor's approach.

Claude Code's own /rewind restores only edits made through Claude's file tools. It misses Bash edits, subagent edits and outside changes, and it cannot be driven programmatically in a TUI session. The competitor mechanism is a private git ref per turn (Conductor, T3 Code), built with a temporary index, `write-tree`, `commit-tree` and `update-ref`. It is cheap, works with any CLI version, covers Bash edits, and is triggered by the UserPromptSubmit hook instead of by polling.
- Recommendation: Build the review loop in this order, and keep Loom out of git's write path at the start.

1. Read-only foundation (option F plus the read-only part of H): a native diff panel on the git CLI, invalidated by Loom's existing Stop/UserPromptSubmit hooks, FSEvents only while the panel is visible, and window activation. Add the PR and CI chip, event-triggered, with `gh`, ETag conditional requests, and bounded back-off only while checks are pending. Add a `merge-tree` conflict preview cached by OID pair. This is the prerequisite for everything else and fits every Loom principle.

2. Comment delivery: build option B as the default and option A as the fallback.
   - Comments live in Loom's store as the system of record, with staleness anchors. Send is a batch, never one comment at a time (Orca's evidence).
   - Default delivery is 'pull at skill': the only thing that crosses the PTY is a short constant `/loom:review`. Loom has an authenticated $LOOM_CLI socket and a plugin, so the skill can pull the comments with !`cmd`. The export call is Loom's own proof of handover, and the UserPromptSubmit hook confirms the prompt that triggered it.
   - If the session is busy, keep the comments pending and offer 'after this turn' (deliver via the Stop hook or paste once idle) and an explicit 'send now (may interrupt)'.
   - Never write when the registry or hooks say waiting. Use option A's gating (idle or busy by the user's choice, no draft in Loom's PTY input log) and offer 'draft only' (paste without Enter) as the zero-risk mode.
   - Verified states: 'queued', 'handed over' (export ran), 'delivered (prompt observed)', and 'outcome unknown' (no automatic retry). A hash mismatch between sent and observed text shows as truncated or modified.

3. Watch option C (mods): detect `mods` support at runtime and, if it proves stable over a few releases, use `$.prompt.submit({asUser:true})` and `$.prompt.read()` as the preferred, dialog-safe path. Do not make it the only path now. It is 15 days old, its API moved in nearly every release since, and it adds unsandboxed code inside the CLI.

## Theme persistence-remote-orchestration

- Summary: Four conclusions. (1) Keep the contract: no Loom-built PTY daemon. Daemon-owned PTYs are the biggest source of pain in the field (Happy: session management was the top contribution topic, 158 items; Superset: pty-master fd leak that exhausted kern.tty.ptmx_max on macOS; Anthropic's own supervisor: leaked workers, upgrade races, env/identity inheritance bugs). Loom's existing mix of ended screen, --resume and idle sessions that cost nothing already matches what Orca (hibernation, experimental, 30 min default) and Claude's supervisor (idle process stopped after about 1 hour) converge on. The cheap gains are a stay-awake assertion while sessions work and a one-click 'resume interrupted' after Quit or crash. Supacode's quit dialog (Quit / Quit and Terminate Sessions, with an orphan sweep) is the precedent if an opt-in keep-running mode is ever built, and Claude's own supervisor (claude --bg, claude attach, claude agents --json, claude stop) is the only 'keep running' backend that does not make Loom own a daemon. Loom disables it today (CLAUDE_CODE_DISABLE_AGENT_VIEW=1, Sources/LoomCore/ProviderLaunchProfile.swift:147). (2) Phone: the cheapest credible path is Claude's own Remote Control, started by Loom per session with --remote-control. It is outbound-only HTTPS and needs no server or app on Loom's side, but the transcript is stored on Anthropic servers while connected, it needs a Pro/Max-class login, and it is flaky in practice. Pair it with a stay-awake assertion and, optionally, an outbound push (ntfy-style) on 'needs approval'. A Loom-owned relay or mobile app (cmux's iroh/APNs stack, Superset/Orca/Happy React Native apps) is XL and should be skipped. Users mostly approve, answer, check progress and kick off tasks from the phone; complaints are truncated approval cards, approvals that never reach the host, silent disconnects, and no way to start sessions. (3) Claude Code itself now ships cross-session messaging (ListAgents/SendMessage over a per-session Unix socket, since v2.1.224, with notify_when_idle and accept/hold/refuse inbound controls). So Loom's planned channel should be an authority broker (grants, scope, verified delivery states, labelled provenance) over Loom's existing authenticated control socket, not a second transport competing with the CLI. The posting wire format of the CLI socket is undocumented, so native transport stays a later adapter.
